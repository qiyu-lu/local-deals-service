# 06 订单闭环：状态机、支付、关单、退款

## 一、这一章解决什么问题

抢到的资格必须变成一笔能付钱、会过期、能退款的订单，否则「抢到不付款怎么办」在代码里没有答案。
难点全在并发与异步：支付结果由渠道异步回调送来，同一条结果会重复送、乱序送；关单由定时消息触发，
消息可能重投也可能丢失；库存分别记在数据库和 Redis 两处，回补必须恰好一次；而用户关单之后还要能再买一次，
这又和「一人一单」的唯一键直接冲突。这一章把这条链路写清楚：一笔订单从创建到终态，中间每一个岔口是怎么定胜负的。

券资产本身（发券、核销码、核销、过期）属于第 07 章，这里只写订单侧与之交接的那半步；
订单表分库分表之后这些语句怎么路由属于第 08 章。

## 二、涉及的数据

- **订单表**：订单号是主键，同时是秒杀准入时就发好的号（低位嵌了用户 id 的基因，见第 05 章）；
  另有用户 id、券 id、下单时快照的门店/商户/应付金额、状态、支付截止时间、四个时间戳（支付/关闭/核销/退款完成）、
  一个「Redis 预占待释放」标记、一个每次流转 +1 的版本号，以及一个**生成列**：
  状态属于「已关闭」或「已退款」时它是 NULL，否则是 1。
  唯一键建在（用户 id，券 id，生成列）上；另有（状态，截止时间）、（待释放标记）两个索引供兜底扫描走。
- **状态流转审计表**：一行一次流转，记源状态、目标状态、事件名、操作者（系统 / 渠道 / 用户 / 后台账号）。
  创建时也写一行，源状态为空。
- **支付流水表**：我方支付单号唯一、渠道流水号唯一；有金额、状态（等待中 / 成功 / 异常）、渠道回调金额、支付时间。
- **退款流水表**：退款单号唯一、渠道退款单号唯一；有类型（用户申请 / 自动退）、原因、状态（处理中 / 成功）、
  请求次数、完成时间；还有（状态，更新时间）索引供重试扫描走。
- **券资产表**：本章只用到「券号由来源推导」和它的状态（可用 / 已用 / 已过期 / 已退 / 冻结）两件事，详见第 07 章。
- **Redis 侧**：每个库存桶下的剩余库存计数与一个「谁预占了」的哈希（用户 id → 订单号）。关单回补只碰这两个，详见第 05 章。
- **消息**：一个关单主题，消息体只有订单号和 traceId，用 RocketMQ 5 的任意时刻定时消息投递。

**状态与事件**：状态有六个——待支付、已支付、已核销、已关闭、退款中、已退款。合法迁移只有五条边，
每条边的源状态唯一：支付（待支付→已支付）、关单（待支付→已关闭）、核销（已支付→已核销）、
申请退款（已支付→退款中）、退款成功（退款中→已退款）。其中关单和退款成功这两条边带「回补库存」标记，
关单这条边额外带「必须已过截止时间」标记。

## 三、详细流程

### 3.1 一次状态流转是怎么做的（下面四条链路共用）

任何一次状态变化都走订单状态机的同一个方法，它是全仓库唯一调用那条状态更新语句的地方。

● 状态机按事件查出源状态与目标状态，发一条条件更新：`UPDATE 订单表 SET 状态=目标状态, 版本号=版本号+1,
  （按目标状态顺带写对应的那个时间戳）, （若该边回补库存则 待释放标记=1）
  WHERE 订单号=? AND 状态=源状态 （若该边要求超时则 AND 支付截止时间 <= NOW(3)）`。
  ○ 影响 1 行 = 本次调用赢了；影响 0 行 = 订单不在源状态（或还没到截止时间），本次调用是并发失败方，返回 false。
  ○ 两个事件同时打到同一行时，InnoDB 的行锁天然把它们排成先后，后者看到的已经是前者改完的状态，必然 0 行。
    不需要版本号乐观锁，也不需要分布式锁：源状态唯一，状态本身就是版本。
  ○ 截止时间的判断用的是数据库时钟，而截止时间当初也是由数据库时钟算出来的（插入时 `NOW(3) + 超时秒数`）。
    这样应用和 Broker 的时钟偏差只会让定时消息「早到一点」，早到的结果是这次 CAS 失败、消息重投，不会误关。
● 赢了才写一行状态流转审计，和更新在同一个事务里。
● 方法上声明事务传播为 MANDATORY——必须由调用方开事务。因为胜者的副作用（回补库存、发券、冻结券、生成退款单）
  必须和这次流转一起提交或一起回滚。
● 订单实体里状态字段**连 setter 都没有**；另有一个源码扫描测试守护两条约束：全仓库只有状态机这一个文件调那条更新方法，
  也只有映射层这一个文件里出现「更新订单表、并且在 WHERE 之前写状态列」的语句。
  这样「到处改状态」这类漏洞在编译期之外也被堵住。

### 3.2 预下单：用户点「去支付」

用户对一笔待支付订单发起支付，希望拿到一个可以付钱的收银台地址。这次请求到向渠道登记支付单、返回地址为止，
钱有没有到账是后面异步回调的事。

● 先按订单号 `SELECT ... FOR UPDATE` 锁住订单行，顺便校验订单属于当前用户，否则报「订单不存在」
  （不区分不存在与不属于你，避免枚举别人的订单号）。
  ○ 这把行锁的作用是把同一笔订单的并发预下单排成队，避免两个请求各建一张支付单。
● 再查一次「这笔订单现在还能不能付」：状态是待支付**且**截止时间还没到——同样交给数据库时钟判断。
  不能付就返回冲突，提示已关闭或已支付。
● 查这笔订单有没有还处于「等待中」的支付流水，有就复用；没有就新建一张：
  ○ 支付单号是 `订单号-序号`，序号取该订单已有支付流水条数 +1。单号由来源确定，不需要额外的发号服务；
    同时支付单号有唯一键，重复生成会直接撞键而不是产生两张。
  ○ 金额抄订单上的应付金额快照，不重新去券表读——价格必须是下单那一刻的价格。
● 拿着支付单号和金额向渠道登记（登记本身按支付单号幂等），得到收银台地址返回给用户。

### 3.3 支付回调：钱到了

渠道在用户付款之后异步回调我方一个公开接口。这个接口不靠登录态鉴权，靠签名。它可能被同一笔支付调用很多次，
到达顺序也没有保证。这次调用到「订单变成已支付并发券」或「自动退款单已生成」为止。

● 先验签：对除签名外的全部字段按字段名排序拼成 `k1=v1&k2=v2...`，用共享密钥做 HMAC-SHA256，
  和来签做**常量时间比较**（不泄露前多少个字符对上了）。验不过返回 401。
  ○ 任何非 2xx 的应答都会让渠道继续重试，所以「暂时处理不了」和「拒绝」在协议层是同一件事，要谨慎选。
● 按支付单号 `SELECT ... FOR UPDATE` 锁住支付流水行。**这一行就是这笔支付的幂等闸门**：
  重复回调全部在这里排队，前一个提交之后，后面的看到的状态已经不是「等待中」。
  ○ 支付单不存在：抛 404。渠道会继续重试——用户可能刚在另一个实例预下单、事务还没提交，等一会儿就有了。
  ○ 状态已经不是「等待中」：这是重复回调，直接返回「重复」让上层回 2xx，结束。
    顺带比对渠道流水号，不一致说明同一张支付单被渠道认了两笔钱，记 error 日志（渠道流水号本身还有唯一键兜底）。
  ○ 金额和应付金额不符：把支付流水置为「异常」并记 error，**永不入账**，也不改订单状态，留人工处理。
● 金额对得上：把支付流水从「等待中」改成「成功」，写入渠道流水号、回调金额、支付时间。
  这条更新自己也带「当前仍是等待中」这个条件。
● 然后触发订单的支付事件（待支付→已支付）。这里是第一类竞态的裁决点：
  ○ **赢了**：在同一个事务里给这笔订单发一张券（券号 = `P` + 订单号，券号唯一键让发券天然幂等），返回「已支付」。
  ○ **输了**：说明关单（或另一笔支付）先到，但钱已经在我们手里。读一下订单当前状态定原因——
    已关闭记「关单后到账」，否则记「重复支付」——在同一个事务里生成一张**自动退款单**
    （退款单号 = `RA` + 支付单号），提交之后再向渠道发起退款请求。返回「自动退款」。
● 整个方法一个事务。回调的幂等性来自「支付流水行锁 + 只在等待中→成功这一次变化上做事」，
  和订单侧的胜负判定是两件独立的事：前者保证同一笔钱只入账一次，后者保证这笔钱要么买到订单要么被退回去。

### 3.4 超时关单：主路定时消息，兜底扫描

一笔订单默认允许 15 分钟不支付。到点要关闭它、把库存还回去、并且让这个用户可以重新买。

● **投递**：秒杀消息的消费者在订单落库成功之后，投一条关单定时消息，投递时刻 = 当前时刻 + 支付超时 + 1 秒。
  ○ 多加 1 秒，是因为截止时间是 MySQL 在插入那一刻算的，比应用这里读的时钟稍晚；早到会被 CAS 判成「还没到期」，
    白白走一轮 Broker 重试。
  ○ 投递是**尽力而为**：失败只记一行 warn 日志，订单已经提交，兜底扫描会收拾。
  ○ 单条消费路径用同步发送；批量消费路径改用异步发送回调，因为批量之后一单一次 Broker 往返就成了消费线程上的大头（见第 05 章）。
  ○ 消息里带上买家那次请求的 traceId，这样十五分钟后的那行「未支付订单已关闭」能和当初下单的请求串在同一条链路上
    ——那次下单甚至可能落在另一个实例上。
● **消费**：到点消息投递回来，消费者调关单服务。
  ○ 消息体缺订单号直接丢弃并记 error（重投也没用）。
  ○ 结果是「还没到期」时**主动抛异常**，让 Broker 按退避重投——这是应用与 Broker 时钟偏差的兜底。
    其余结果一律当成功应答。
● **关单服务本体**（一个事务）：
  ○ 先触发关单事件（待支付→已关闭，并且要求「支付截止时间已过」，按数据库时钟判断）。
    - **赢了**：读出订单行，把库存还回去（见 3.5），记一行 info，结果是「已关闭」。
    - **输了**：再读订单判断为什么输——订单不存在 → 「未找到」；已经是已关闭 → 「已关闭过」；
      仍是待支付 → 「还没到期」；其余（已支付 / 已核销 / 退款中 / 已退款）→ 「支付赢了，无事可做」。
  ○ 「已经是已关闭」这一支里还有一件事：如果订单上的「Redis 预占待释放」标记还是 1，
    说明上一次关单提交之后释放 Redis 那一步没成功，就着这次重投把它补上。**重投因此不是浪费，是一次重试机会。**
  ○ 五种结果各自打一个计数器指标，便于看「兜底扫描到底捡了多少」。
● **兜底扫描**（一个定时任务，每个实例都在跑，因为关单是 CAS、释放脚本幂等，多实例并发扫是安全的）：
  ○ 启动后 20 秒开始，之后每轮结束再隔 10 秒跑下一轮；单轮每类最多取 200 条。
  ○ 第一件事：捞出「状态是待支付且已经超过截止时间 **30 秒以上**」的订单，逐个走关单服务。
    留 30 秒宽限，是因为定时消息才是主路，让两条路径尽量不撞；真撞上了也安全——CAS 只会有一个赢家。
    单条失败只记 error，下一轮再来。
  ○ 第二件事：捞出「待释放标记 = 1 且更新时间在 10 秒以前」的订单，重放 Redis 释放。
  ○ 第三件事：捞出「处于处理中、且更新时间在 1 分钟以前」的退款单，向渠道再请求一次（渠道按退款单号幂等）。
    这一步整体套 try-catch，失败不影响前两步。

### 3.5 库存回补与「关单后可以再买」

关单和退款成功这两条边带「回补库存」标记，回补被**拆成两半**：数据库那半在事务里，Redis 那半在提交之后。

● 事务内：把秒杀库存表这张券的 `stock + 1`。只有赢了 CAS 的那一方会走到这里，所以恰好加一次；
  更新影响 0 行说明库存行不存在，直接抛异常让整个事务回滚（宁可不关单也不能凭空改数）。
  同时那条状态更新语句已经把「待释放」标记写成了 1。
● 注册一个事务提交后的回调，提交成功后释放 Redis 预占。之所以不能放在事务里：Redis 不参与数据库事务，
  事务回滚了 Redis 改不回来，就会凭空多出一个库存单位。
● **释放脚本**（一段 Lua，参数是用户 id 和订单号，操作这个用户所属库存桶下的库存计数和预占哈希）：
  ○ 先取预占哈希里这个用户对应的值，**不等于本订单号就直接返回 0**，什么都不做。
  ○ 相等才删掉这个用户的预占，并且在库存计数键存在时 `INCR` 一次；计数键不存在说明这场活动根本没预热或已被清掉，
    此时凭空建键会放进没人配置过的库存，所以只删预占不加库存。
  ○ **它不需要幂等标记**：预占哈希里这个用户指向本订单号，只在「本订单被释放之前」成立；释放后这个字段就没了，
    用户再次下单会写入一个新的订单号。所以任何重放都必然找不到可释放的东西，返回 0。
● 释放成功（返回 1）时顺手清掉该桶的售罄标记：本实例直接清，并广播一条消息让其他实例也清，
  这样各实例的准入层都重新放人进来（详见第 05 章）。
● 释放这一步整体 try-catch：抛异常只记 warn 并返回 false，「待释放」标记留着，交给兜底扫描重试；
  正常走完则把标记清空（清空语句带「标记当前仍是 1」的条件）。
● **数据库侧的「可以再买」靠生成列**：唯一键建在（用户 id，券 id，生成列）上，
  生成列在已关闭/已退款时取 NULL。MySQL 的唯一索引允许任意多个 NULL，
  所以进行中的订单对一个用户一张券仍然唯一，而关闭或退款的订单自动**退出**这个唯一键的约束，同一用户可以再买。
  不需要在应用里判重，也不需要删历史订单。
  ○ 订单按用户 id 分片之后，同一个用户的全部订单落在同一张物理表，这个唯一键因此仍然有效（详见第 08 章）。
● **Redis 侧的判重也必须同时放开**，否则数据库放行了、准入层还认为这个用户占着坑。这正是释放脚本删预占那一步的意义。

### 3.6 用户退款

用户对一笔已支付订单申请退款，希望钱退回去、券作废、库存还回去。这次请求到「订单进入退款中、券被冻结、
退款单已生成」为止；真正退款成功是渠道回调之后的事。

● 按订单号 `FOR UPDATE` 锁住订单行（同样校验归属）。
  **锁顺序：先拿订单行，再动券行**——核销那条链路不显式加锁，但它第一步就是那条状态条件更新，
  同样是先拿到订单行的排他锁、再去改券行。两边顺序一致，所以核销与退款不会死锁，且必然只有一方成功。
● 订单状态不是已支付就直接拒：退款中 → 「退款处理中」；已核销 → 「券已核销，不可退款」；其余 → 「状态不允许退款」。
● 触发申请退款事件（已支付→退款中）。订单行已经被锁住，此时 CAS 理应必胜，失败则说明状态机出了问题，抛异常。
● 同一个事务里把这笔订单的券（券号 = `P` + 订单号）从「可用」改成「冻结」；改不动再试一次从「已过期」改成「冻结」
  （过期未用的券允许退款）。两次都改不动就抛冲突，**整个事务回滚，订单退回已支付**。
  冻结而不是直接作废，是因为渠道还没确认退款成功；但冻结之后门店已经核销不了了。
● 取这笔订单第一笔成功的支付流水（没有就是数据不一致，抛异常），生成退款单，
  退款单号 = `RU` + 订单号——**确定性单号就是幂等键**：同一笔订单再申请一次退款，
  插入会撞退款单号唯一键，而不是产生第二笔退款。
● 注册提交后回调：事务提交之后才向渠道发起退款请求；请求前先把请求次数 +1。
  请求失败只记 warn，兜底扫描每轮会重捞超过 1 分钟仍未确认的退款单再请求（渠道按退款单号幂等）。
● **退款回调**（渠道 → 我方的另一个公开接口，同样先验签）：
  ○ 按退款单号 `FOR UPDATE` 锁住退款流水行；不存在抛 404 让渠道重试。
  ○ 已经是成功 → 返回「重复」结束。金额不符 → 抛异常（非 2xx，渠道重试）。
  ○ 把退款单从处理中改成成功，写入渠道退款单号和完成时间。
  ○ 只有**用户申请**类型的退款才继续推订单：触发退款成功事件（退款中→已退款），把券从「冻结」改成「已退」，
    并回补库存（走 3.5 的同一套）。自动退款单到这里就结束了——它对应的订单本来就没有收下这笔钱（已关闭或已由另一笔支付买下），
    不该再动订单状态，也不该再回补一次库存。

### 3.7 五类竞态各自是怎么解的

| 竞态 | 解法 |
| --- | --- |
| 1 支付回调 vs 超时关单 | 两者都要改同一行订单的状态，且源状态都是「待支付」。行锁串行化，CAS 只有一个赢家。关单赢了，支付回调这边转去生成自动退款单，钱原路退回；支付赢了，关单那边读到已支付，判「支付赢了，无事可做」。 |
| 2 同一笔支付回调重复 N 次 | 支付流水行锁把它们排队，只有第一个看到「等待中」并入账、推订单、发券；其余看到已是成功，直接返回「重复」。渠道流水号上的唯一键是第二道锁。券号由订单号推导且带唯一键，就算发券被重放也只有一张。 |
| 3 关单消息重复 / 多实例扫描同时关 | 同一条 CAS，只有赢家回补库存。输家若发现订单已关闭且「待释放」标记还在，就顺手把上次没做完的 Redis 释放补上——重投变成重试机会。Redis 释放脚本本身以「预占仍指向本订单」为条件，重放是空操作。 |
| 4 退款中再退款 / 核销后退款 / 核销与退款同时 | 退款申请的源状态是「已支付」，第二次申请读到的是「退款中」，直接被拒；已核销同理。核销与退款都**先拿订单行锁再动券行**（退款用显式行锁，核销靠那条条件更新本身），顺序一致所以不死锁。二者分别是「已支付→已核销」和「已支付→退款中」两条源状态相同的边：核销输时是 CAS 影响 0 行，退款输时是拿到行锁后读出的状态已经不是「已支付」；两种情况下输家整个事务回滚（包括已经改过的券状态）。 |
| 5 关单之后再买 | 数据库侧：生成列在已关闭时变 NULL，退出唯一键，同一用户可再下单。Redis 侧：释放脚本删掉该用户的预占并把库存计数加回去，准入层重新放行。两侧必须同时放开，缺一边就会出现「数据库允许但抢不到」或「抢得到但落库撞唯一键」。 |

集成测试是怎么把这些交错逼出来的（这部分值得记，因为追问「你怎么知道真的并发过」时要答得出）：

- 竞态 1：20 轮，每轮换一个买家、新建订单并预下单，先把截止时间改到过去，再用两个线程同一个闩锁同时放出。
  前 10 轮完全同时，中间 5 轮让关单晚 20 ms（支付先手），最后 5 轮让支付晚 20 ms（关单先手）。
  每轮按最终状态分支断言：已支付时两个结果必须恰好是「支付成功」和「支付赢了无事可做」，券 1 张、自动退款单 0 张、库存不变；
  已关闭时必须是「自动退款」和「已关闭」，券 0 张、自动退款单 1 张、库存比开始时多 1。最后断言两种赢家都出现过。
- 竞态 2：同一条已签名的回调通知，10 个线程同时打进来。断言「支付成功」恰好 1 次、其余 9 次都是「重复」，
  成功的支付流水 1 条、券 1 张、支付事件的状态审计恰好 1 行、退款单 0 条。
- 竞态 3：走真实准入和秒杀消费者买一单，改过期，10 个线程同时关单，**再额外让关单消费者收一次重投**（共 11 次）。
  断言「已关闭」恰好 1 次、其余都是「已关闭过」，数据库库存和 Redis 库存都回到初值、预占哈希里该用户的字段没了、
  「待释放」标记为空、关单事件的状态审计恰好 1 行。
- 兜底扫描单独有两个测试：一个把定时消息丢掉、只靠扫描关单；另一个把「待释放」标记置 1 并把更新时间回拨一分钟，
  同时模拟 Redis 当时没写成（把预占加回去、库存减回去），然后跑一轮扫描，断言标记清空、Redis 恢复；
  **再跑一轮扫描不会多加一个库存单位**——这一条验的就是释放脚本的幂等。
- 竞态 4：10 个线程同时申请退款，断言只有 1 个拿到退款单号、其余 9 个都是「退款处理中」，退款单 1 条、券已冻结、
  向渠道的退款请求恰好发了 1 次，之后再去核销会被拒。核销与退款的对撞另有 10 轮，同样按 0 延迟 / 各自先手 20 ms 三段编排，
  按最终状态分支断言输的一方拿到的正是「券不可用」或「券已核销不可退款」，并断言两种赢家都出现过。
- 竞态 5：Redis 那半走真实准入——买一单、再抢一次得到「重复」、关单、再买成功，断言两边库存都只被扣了一次；
  数据库那半直接用状态机关单再插一单，断言状态审计正好是「创建」和「关单」两行，而且此时再插第三单仍然会被唯一键挡住。

## 四、口述版

**4.1 状态流转。** 订单一共六个状态，合法的迁移只有五条边，关键是我把每条边设计成**源状态唯一**，
这样一次流转就退化成一条条件更新：把状态从源状态改成目标状态，条件是订单号加上当前状态等于源状态。
影响一行就是我赢了，影响零行就是别人先改过了，我是并发失败方。这样做的好处是不用乐观锁版本号也不用分布式锁，
因为源状态本身就是版本，而 InnoDB 的行锁天然把并发的竞争者排成先后。关单那条边还多带一个条件，
要求截止时间已经过了，而且这个判断用的是数据库时钟，截止时间当初也是数据库时钟算出来的，
所以应用和消息 Broker 的时钟偏差最多让定时消息早到一点，早到的后果只是这次条件更新失败、消息重投，绝不会把没到期的订单误关。
赢了才在同一个事务里写一行状态审计。这个方法要求调用方必须已经开了事务，因为赢家的副作用——回补库存、发券、冻结券、
生成退款单——必须跟这次流转同生共死。另外订单实体里状态字段我连 setter 都没给，还写了一个扫源码的测试，
断言全仓库只有状态机这一个类调那条更新语句，防的是以后有人图省事在别处直接改状态。

**4.2 支付。** 用户点去支付，我先把订单行锁住，一是校验订单是不是他的，二是把同一笔订单的并发支付请求排队，
免得建出两张支付单；然后再查一次这笔订单现在还能不能付，也就是状态是待支付并且没过截止时间，同样交给数据库判断。
能付的话，看有没有已经存在的、还在等待中的支付单，有就复用，没有就新建一张，支付单号就用订单号加一个序号，
单号由来源确定，就不需要额外的发号服务，而且单号上有唯一键，重复也撞不出第二张。金额直接抄订单上的快照，
不能重新去券表读，价格必须是下单那一刻的。最后拿这个支付单号去渠道登记，把收银台地址返回给用户。

钱到账之后渠道会异步回调我一个公开接口，这个接口不靠登录态，靠签名。我把除签名外的字段按字段名排序拼成一个串，
用共享密钥做 HMAC-SHA256，再和来签做常量时间比较，这样不会泄露前面对上了几个字符。验签不过就返回 401。
这里要注意，任何非 2xx 的应答都会让渠道继续重试，所以什么时候回错、什么时候回成功要想清楚。
验完签我按支付单号把支付流水那一行锁住，**这一行就是这笔支付的幂等闸门**：渠道保证至少一次投递，重复的回调全部在这里排队，
第一个提交之后，后面的看到状态已经不是等待中了，直接回一个重复就结束。如果支付单根本不存在，我回 404 让渠道接着重试，
因为很可能用户刚在别的实例预下单、事务还没提交。金额对不上的话我把这笔流水记成异常，永不入账，也不碰订单，留人工看。
金额对得上就把流水从等待中改成成功，写入渠道流水号。

然后才去推订单的状态，从待支付改成已支付。这一步就是第一类竞态的裁决点：如果我赢了，就在同一个事务里给这笔订单发一张券，
券号是 P 加订单号，券号有唯一键，所以就算这段逻辑被重放也只会有一张券。如果我输了，说明关单或者另一笔支付先到了，
但是钱已经在我手里，不能不管，所以我在同一个事务里生成一张自动退款单，单号是 RA 加支付单号，提交之后再去找渠道退款。
也就是说支付流水的行锁负责「同一笔钱只入账一次」，订单的条件更新负责「这笔钱要么买到订单要么被退回去」，两件事互不干扰。

**4.3 关单。** 一笔订单默认给 15 分钟支付。秒杀消息的消费者在订单落库成功之后，会投一条定时消息，
投递时刻是当前时间加上支付超时再加一秒，多这一秒是因为截止时间是 MySQL 插入那一刻算的，比我在应用里读的时钟稍晚，
早到会被那个「必须已过期」的条件挡回来，白跑一轮 Broker 重试。这条消息是尽力而为的，发失败只记一行日志就算了，
因为订单已经提交，后面有兜底扫描。消息里我还带上了买家当初那次请求的 traceId，这样十五分钟之后那行关单日志
能跟当初下单的请求串在同一条链路上，哪怕当初下单的是另一个实例。单条消费的时候用同步发送，批量消费之后改成异步发送加回调，
因为数据库那部分批量掉以后，一单一次 Broker 往返就成了消费线程上的大头。

到点消息回来，我就去关单：先做那条带过期条件的条件更新。赢了就读出订单把库存还回去。输了我再读一次订单看是为什么输——
如果已经是关闭状态，说明是重复的消息或者扫描已经关过了；如果还是待支付，说明还没到期，这种情况我会主动抛异常，
让 Broker 按退避把消息重投，这是时钟偏差的兜底；如果已经是支付、核销、退款这些状态，那就是支付赢了，我什么都不用做。
这里还有个细节：输家如果发现订单已经关闭、但那个「Redis 预占待释放」的标记还挂着，说明上次关单提交之后释放 Redis 那一步没成功，
它会就着这次重投把释放补上，所以重复投递对我来说不是浪费，是一次额外的重试机会。

光靠消息还不够，消息可能丢，所以还有一个兜底扫描，每个实例都在跑，因为关单是条件更新、释放脚本是幂等的，多实例一起扫也安全。
它启动二十秒后开始，每轮跑完隔十秒跑下一轮，每类一次最多取两百条。它捞三种东西：一是超过截止时间三十秒还在待支付的订单，
留这三十秒宽限是因为定时消息才是主路，让两条路尽量不撞，真撞上了也没关系，反正只有一个赢家；
二是「待释放」标记挂了十秒以上的订单，重放一次 Redis 释放；三是处理中超过一分钟还没被渠道确认的退款单，再请求一次。

**4.4 库存回补。** 关单和退款成功这两条边都要把一个库存单位还回去，我把回补拆成两半。数据库那半跟条件更新在同一个事务里，
因为只有赢了 CAS 的那一方才会走到这里，所以恰好加一次；同时那条更新语句已经顺手把「待释放」标记写成了 1。
Redis 那半必须放到事务提交之后再做，因为 Redis 不参与数据库事务，万一事务回滚了 Redis 改不回来，就凭空多出一个库存。
释放本身是一段 Lua，参数是用户 id 和订单号，操作的是这个用户所属的那个库存桶——注意要还回他当初取走的那个桶，
不能还到别的桶去。脚本先看预占哈希里这个用户对应的值是不是本订单号，不是就直接返回零什么都不做，是才删掉预占、
再把库存计数加一；如果库存计数这个键压根不存在，说明这场活动没预热或者已经被清掉了，那我只删预占不建键，
不然就会放出一批谁也没配置过的库存。这个脚本妙在**不需要幂等标记**：预占指向本订单号这个条件，
只在本订单被释放之前成立，一旦释放这个字段就没了，用户再下单写进去的是一个新订单号，
所以任何重放都必然找不到可释放的东西。释放整个套了 try-catch，失败只记警告并且把「待释放」标记留着，
交给扫描重试；成功了才把标记清掉，顺便清一下这个桶的售罄标记——本实例清完还要广播一条消息，
让其他实例的准入层也重新放人。

关单之后要让用户能再买，这需要数据库和 Redis 两侧同时放开。数据库侧我用的是**生成列**：
订单表上有一个生成列，状态是已关闭或已退款时它算出来是 NULL，否则是 1，唯一键建在用户 id、券 id、这个生成列三个字段上。
MySQL 的唯一索引允许任意多个 NULL，所以进行中的订单对一个用户一张券还是唯一的，而关闭和退款的订单自动退出这个约束，
同一个用户就可以再买了，既不用在应用里判重，也不用删历史订单。Redis 侧就是刚才那个释放脚本删掉预占，
不然会出现数据库放行了、准入层还认为这个人占着坑的情况。

**4.5 退款。** 用户申请退款，我先把订单行锁住，这里有个约定：**退款和核销都是先拿订单行、再动券行**，
退款是显式的行锁，核销是那条状态条件更新自己拿的锁，两边顺序一致所以不会死锁，而且一定只有一方能成。状态不是已支付的直接拒掉，退款中就说处理中，已核销就说券已核销不可退。
然后把订单从已支付改成退款中，因为行锁已经拿在手里，这一步理论上必胜，失败就说明状态机有问题，直接抛。
同一个事务里把券从可用改成冻结，改不动就再试一次从已过期改成冻结，因为过期没用的券我也允许退；
两次都改不动就抛冲突，整个事务回滚，订单退回已支付。冻结而不是直接作废，是因为渠道还没确认钱退回去，
但冻结以后门店已经核销不了了。接着取这笔订单第一笔成功的支付流水，生成退款单，单号是 RU 加订单号，
这个确定性单号本身就是幂等键：同一笔订单再申请一次，插入会撞唯一键而不是退两次钱。
退款请求同样放在事务提交之后再发，发之前把请求次数加一，发失败只记日志，扫描每轮会把超过一分钟没确认的退款单再请求一遍，
渠道那边按退款单号幂等，所以多请求几次没有副作用。

渠道确认退款以后回调另一个接口，一样先验签，然后按退款单号锁住退款流水行，已经成功就回重复，金额不符就抛异常让它重试，
正常就把退款单改成成功。最后一步有个分支：只有**用户申请**类型的退款才继续推订单，把订单从退款中改成已退款、
把券从冻结改成已退、并且回补库存；自动退款单到这里就结束了，因为它对应的那笔订单本来就没收下这笔钱，
要么已经关闭要么已经被另一笔支付买下了，再去动订单状态或者再回补一次库存都是错的。

## 五、为什么这么设计 / 会被怎么追问

**为什么用「源状态唯一 + 条件更新」，不用版本号乐观锁，也不用分布式锁？**
备选是：读出订单、改状态、按版本号写回；或者对订单号加分布式锁。选条件更新的理由是——
既然每个事件的源状态唯一，状态本身就已经是版本了，再加一个版本号是冗余；而加分布式锁等于为一个 InnoDB 行锁
已经能解决的问题引入一个额外的、会挂的依赖。条件更新还有一个附带好处：所有流转都收敛成一条语句，
可以用源码扫描测试守住「只有状态机能改状态」这条约束。版本号字段我保留了，每次流转 +1，但它是给审计和排查用的，
不参与并发控制。

**为什么关单的过期判断要放在 SQL 里、用数据库时钟？**
因为参与这件事的有三个时钟：应用、Broker、数据库。如果用应用时钟判断，Broker 早投递一点、应用时钟又快一点，
就会把还没到期的订单关掉，用户正在付款的钱就变成自动退款。把截止时间的计算和判断都收到数据库这一个时钟上，
偏差就只剩「早到」这一种表现，而早到的结果是条件更新影响零行、消息重投，是安全的。

**为什么不直接在关单时删掉旧订单，而要引入生成列？**
删订单会丢掉「他确实抢到过又放弃了」这段事实，风控和客服都需要它；而且删除和并发的支付回调之间还要再设计一次竞态。
生成列的做法是让关闭的订单**自动退出**唯一键的管辖，一条 DDL 解决，应用层零判断。代价是这个唯一键的语义藏在表结构里，
读代码看不出来，所以得靠注释和测试说明。

**库存回补为什么要拆成两半？只留数据库那半不行吗？**
不行，因为准入层是纯 Redis 的（见第 05 章），数据库的库存数不参与放行。只补数据库，用户会遇到「明明还有库存却抢不到」。
反过来只补 Redis 也不行，会超卖。拆两半是因为 Redis 不能加入数据库事务：数据库那半必须和 CAS 同事务，
保证「只有赢家加一次」；Redis 那半必须等提交之后，否则事务回滚会凭空多出库存。中间这段不一致窗口用订单上的
「待释放」标记显式记下来，由扫描收敛。

**释放脚本为什么不需要幂等标记？**
因为它的前置条件天然一次性：预占哈希里这个用户指向本订单号，只在本订单被释放之前成立。
释放把这个字段删了，用户再次下单写进去的是新的订单号，所以任何重放读到的要么是空、要么是别的订单号，都会直接返回零。
换句话说，幂等键就是「订单号」这个业务事实本身，不需要另外存一份。

**关单赢了、支付回调后到，钱怎么办？**
这是必问的一问。答案是：支付回调发现自己 CAS 输了，就在同一个事务里生成一张自动退款单，单号是 `RA` + 支付单号，
提交之后向渠道发起退款。它和用户主动申请的退款是两种类型：自动退款不推订单状态，因为订单已经是关闭态，
也不回补库存，因为关单那一方已经补过了。重复支付（同一订单两笔支付都成功）走的也是这条路。

**所有单号都是自己拼的，会不会撞？为什么不用发号服务？**
支付单号是「订单号-序号」，退款单号是 `RU`/`RA` 加来源单号，券号是 `P`/`G` 加来源 id——
全部由来源唯一确定，**确定性单号本身就是幂等键**，重复生成会撞唯一键而不是造出第二条流水。
这比引入一个发号服务简单，也比随机单号好：随机单号在重试场景下反而需要额外的去重表。订单号是例外，
它在秒杀准入阶段就要发出来，用的是 Snowflake 并把用户 id 的基因嵌在低位（见第 05、08 章）。

**mock 渠道为什么要故意做得这么难缠？**
因为真实渠道就是这样：至少一次投递、非 2xx 指数退避重试、没有顺序保证。我让它每条通知固定投递 2 次、
最多重试 8 次、初始退避 1 秒指数增长（上限 60 秒），每次投递前加 0 到 300 毫秒的随机抖动制造乱序。
这样「重复回调」「乱序回调」「回调先于本地事务提交」这些情况在本地就能稳定复现，而不是上线之后靠日志猜。
配套的竞态测试起初有个问题：两个循环里总是同一方赢（关单 20/20、退款 10/10），只验证了一半交错。
后来改成部分轮次给一方 20 ms 先手，并断言两种结果都出现，连续 3 次运行结果一致。最终记录是：
支付/关单 20 轮里支付胜 5、关单胜 15；核销/退款 10 轮里核销胜 3、退款胜 7；每轮恰好一方胜。
定时消息这条路另有一个连真实 Broker 的测试：把支付超时配成 3 秒，断言订单确实是被定时消息关掉的、
关闭时刻**不早于** 3 秒（不能早关），并且库存已回补。

**这一圈新增的写入，对落库吞吐有影响吗？**
同场 A/B 的结果是 189.4 vs 177.5（区间重叠，新增开销 < 2%）——测不出回退。但这是因为瓶颈在别处：
当时 44% 的时间花在同一行库存的 `UPDATE` 上。这 2% 会在热点行消掉之后按比例变大（见第 05 章的批量消费）。

## 六、已知边界

- **mock 渠道的状态在进程内存里**：用户在 A 实例预下单、在 B 实例点「付款」会找不到支付单。
  真实渠道没有这个问题；多实例验证时把渠道固定到一个实例。压测脚本扮演渠道时是自己按签名规范直接发回调的。
- **回调密钥有开发默认值**，生产必须用环境变量覆盖。
- **没有「订单过期」这个状态**：已支付但一直没核销、券已经过期的订单仍然停在「已支付」，只有券变成已过期。
  过期券允许退款（冻结时接受已过期），但「过期自动退款」没有做。
- **退款回补库存是一个业务选择**：活动已经结束时回补的库存不会再卖出去，无害；若要改成「退款不回补」，
  只需把退款成功这条边的「回补库存」标记改成 false。
- **金额异常的支付只记录不处理**：记成「异常」等人工，没有自动退款，也没有告警通道。
- **定时消息在单条消费路径里是逐单同步投递的**；批量消费路径已改为异步发送，但仍是一单一条消息，没有批量投递。
- **关单主路依赖 Broker 的定时消息**：Broker 长时间不可用时，全部关单都压到兜底扫描上，
  单轮 200 条、每 10 秒一轮，积压订单的关闭会被拉长。
- **状态流转审计表没有归档策略**，一单至少一行（创建），最多四行（创建、支付、申请退款、退款成功），
  长期会比订单表还大。
- **后台订单列表直接按商户 id 查订单表**，分片之后这条查询会变成广播（详见第 08 章）。
- 券资产的核销、防枚举、限频与过期，以及发券的另外四个入口，都在第 07 章。
