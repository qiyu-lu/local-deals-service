# 08 订单分库分表

## 一、这一章解决什么问题

订单是这个系统里唯一持续增长且没有上限的数据：券、店铺、用户是有限的，订单不是。诊断表里的 D7 说的就是
「订单表没有分片键设计，无法水平扩展」。要把它拆开，难点不在把一张表变成八张，而在**同一行有两种被叫到的方式**：
买家查自己的订单只带用户 id，而支付、退款、核销、关单、定时关单的消息只拿得到订单号。
如果这两种查法落在不同的片上，每一条语句都会变成对八张表的广播——结果正确，但分片等于白做。

这一章讲的就是怎么让这两种查法必然落同一片、为此付出了哪些代价（哪些 SQL 写法从此不能用、事务不再跨库原子），
以及哪些东西**明确不拆**。落库链路本身详见第 05 章，订单状态机详见第 06 章，那个跟着订单一起写进库的追踪 id 详见第 11 章。

## 二、涉及的数据

**分片的五张表**，全部用同一套槽位方案：

- **订单表**。主键是订单号；分片键是用户 id 列。其余字段里与本章有关的是：券 id、下单时的商户与店铺快照、金额、
  状态枚举、支付截止时间、一个「库存已回补、预占待释放」的待办标记、乐观锁版本号，以及一个**生成列**——
  状态为已关闭或已退款时为 NULL，否则为 1。限购唯一键建在（用户 id、券 id、这个生成列）上，靠 NULL 不参与唯一性
  让同一个用户在同一张券上只能有一笔活跃订单（详见第 06 章）。
- **订单状态流水表**（审计），按订单号分片。
- **支付流水表**，按订单号与支付单号分片；支付单号唯一，渠道流水号唯一。
- **退款流水表**，按订单号、退款单号、支付单号分片；退款单号唯一，渠道退款单号唯一。
- **用户券资产表**，按用户 id 与券编号分片；券编号唯一，核销码唯一。

**留在第一个库里不拆的单表**：券、秒杀库存、店铺、用户、营销（活动/发放/标签/批次）、权限。它们被声明成
「单表」而不是广播表，理由见第五节。

**编号的构造**（这是整章的地基，M3 就埋好了，详见第 04 章）：

- 订单号是一个 64 位的 Snowflake，从高到低是 41 位毫秒、5 位 worker、7 位序列、**最低 10 位是用户 id 对 1024 取模**。
- 支付单号是「订单号-第几次」。
- 退款单号是「RU + 订单号」（买家发起）或「RA + 支付单号」（按支付单自动退）。
- 购买得到的券编号是「P + 订单号」；营销发放的券编号是「G + 发放 id」，**这一种不含基因**。

**槽位方案**：2 个库 × 每库 4 张表 = 8 个槽位。

```
slot = key % 8      库 = slot % 2      表 = slot / 2
```

所以第一个库拿偶数槽位、第二个库拿奇数槽位，连号的用户交替落两个库，而不是先把一个库填满。
关键的一步是 **8 整除 1024**：订单号最低十位既然是用户 id 对 1024 取模，那么订单号对 8 取模 = 用户 id 对 8 取模。
基因法的全部收益来自这一个整除关系。

## 三、详细流程

### 3.1 一条语句被路由到哪一片

任何走这条数据源的语句都会被解析，找出规则里为这张表声明的「能叫到这一行的列」，再由一个复杂分片算法给出目标节点。
算法被调用两次，一次决定库、一次决定表，两次用的是同一个槽位，只是取地址的不同一半。

● 规则里每张分片表都声明了自己的可路由列：订单表是用户 id 与订单号；审计表是订单号；支付流水是订单号与支付单号；
  退款流水是订单号、退款单号与支付单号；券资产表是用户 id 与券编号。声明的是「有哪些方式能叫到这一行」，不是「必须都带」。
● 算法先看这条语句给的是不是**范围条件**（`BETWEEN`、`>`、`<`）。是的话直接广播。
  ○ 理由：槽位是取模的结果，不是一个序。「订单号大于 X」在槽位上不连续，没有任何片可以被排除。
● 再看等值条件的各列，逐列算槽位：
  ○ 用户 id 与订单号：都是对 8 取模，同一段代码，因为低位本来就相同。驱动可能把值递过来是数字也可能是字符串，两种都认。
  ○ 支付单号：取最后一个连字符前面那段当订单号。
  ○ 退款单号：按前缀剥成订单号或支付单号，再往下算。
  ○ 券编号：只有「P」开头的能剥出订单号；「G」开头的**报告为算不出**。
  ○ 剥出来的订单号还要求大于 0（订单号是 2^57 以上的数），否则算不出——给一个不可能是订单号的值猜槽位，
    会把语句发到一个根本不可能有这行的片上。
● 多个列的结果**取交集，不是并集**：它们是对同一行的谓词，每多一个只可能让答案更窄。
  ○ 某一列算不出槽位（典型是营销发放的券编号）就**跳过它**，由旁边的用户 id 定位，而不是退化成广播。
  ○ 某一列里有多个值（`IN`），每个值都要能算出槽位；有一个算不出，**整列作废**——
    作废的意思是这一列被跳过、不参与交集，不是整条语句退化成广播。
  ○ 两列指向**不同**槽位时不选边，返回全部节点。对一条 INSERT 来说这会被中间件当场拒绝——
    一行自己的两个键互相矛盾是 bug，不该被悄悄写进其中一片。
● 交集为空、或者一个可路由列都没带：返回全部节点，即广播。
  ○ 「读一片但行在另一片」是错误答案，「读八片」只是慢，所以拿不准时永远选慢的那个。
● 拿到槽位后各自取地址：决定库的那一层取槽位对 2 取模，决定表的那一层取槽位除以 2，再从可用节点里按后缀挑出来。
  ○ 挑不到任何节点（配置的节点和这套方案对不上）时同样广播，而不是随便选一个。

**结果**：按用户 id 查、按订单号查、按支付单号查、按退款单号查、按购买券编号查，**都是单片命中**。
取单行的查询里会广播的只有三种：按核销码查（店员扫码核销，低频）、按营销发放的券编号查、
商户后台按商户 id 分页查订单。此外还有一类**本来就该广播**的：兜底扫描与券过期扫描这种按状态和
时间取一批的查询，它们不带任何可路由列，广播归并正是想要的行为（见 3.6）。

### 3.2 唯一键：哪些还是全局的，哪些收窄成片内的

分片之后数据库只能保证「一张物理表内唯一」。所以每一个唯一键都要重新回答一次「它还成立吗」。

● **限购键（用户 id、券 id、活跃标记）**：语义完全不变。一个用户的所有订单行永远在同一张物理表里，
  所以片内唯一就是全局唯一。
  ○ 这也是分片键选用户 id 而不是券 id 的直接理由：选券 id 的话，限购就需要跨片判重，而限购是秒杀的最后一道去重。
● **支付单号、退款单号、购买券编号**同理：它们都由订单号派生，任何可能冲突的两行必然同片。
● **渠道流水号、渠道退款单号、核销码**：**收窄成片内唯一**，这是真的放弃了一点东西。
  ○ 前两者只会被同时带着支付单号 / 退款单号的语句碰到，所以回调的幂等仍然是按支付单行判的，不受影响（详见第 06 章）。
  ○ 核销码是 80 bit 随机串，跨片撞号不是需要设计的事情。
  ○ 渠道流水号与核销码写进了列注释，免得以后有人以为它还是全局的；渠道退款单号那一列漏了注释。
● **附属四张表的主键去掉了自增**：八张物理表会各自从 1 数起。没有任何查询按它路由，于是交给中间件的 Snowflake 生成。
  代价是这个 id 不再是递增的小整数，但按它排序仍然是时间序。

### 3.3 一个消费批次跨两个库落库，事务是 LOCAL

批量消费的细节详见第 05 章，这里只看分片带来的那一部分。

● 一个消费批次会被按券分组，每组在**一个事务**里做三件事：一条多行 `INSERT IGNORE` 写订单、一次
  `stock >= n` 的条件更新扣库存、一条多行 INSERT 写审计。
● 这一个事务通常同时写**两个库**：批次里的买家来自不同槽位，订单行与审计行分散在两个库的八张表上，
  而库存那一行只在第一个库。
● 券快照**必须在事务里单独读一次**：订单表是分片表、券表是单表，`INSERT ... SELECT ... JOIN` 这种写法被拒绝
  （见 3.4 第一类），所以改成先读一次快照，再拼普通的多值 `VALUES`。一个批次一张券只读一次。
● 事务类型是中间件默认的 **LOCAL**：它**逐个物理连接提交**，不保证跨库原子。没有上 XA。
  ○ 崩在两次提交之间的后果是**有界的少卖，不是超卖**：没提交的那一半订单仍然持有 Redis 预占，对账器发现 DB 无单会重投，
    `INSERT IGNORE` 让重放幂等；但这一批的库存已经扣过一次，重放会再扣一次，于是 DB 库存比真实值更低。
    方向是安全的（宁可少卖），量级被批大小限住，而且要求进程恰好死在两次提交之间那个窗口里
    （窗口有多宽没有量过）。
  ○ 「一个批次确实横跨两个库」是被测试钉死的事实：一个批次放 8 个不同槽位的买家，用**物理连接**分别去数，
    第一个库 4 行、第二个库 4 行，库存只扣一次。非原子窗口的存在是这条测试的直接推论。
  ○ **故障注入没有做**。这一条目前是推理加机制证据，不是实测。

### 3.4 五类被分片拒绝的 SQL

分片不是「加个中间件就透明」。这次被当场挡住、必须改写的有五类：

● **第一类：`INSERT INTO 分片表 ... SELECT ... JOIN 单表`**。报错是「插入的表和查询的表必须是同一张」。
  ○ 改法：应用侧先读券快照，再拼普通多值 `VALUES`（见 3.3）。
● **第二类：`DELETE a FROM 分片表 a JOIN b`**。报错是「不支持多表 DML」。
  ○ 改法：先读出订单号，再按订单号逐条删附属行。主要出现在测试清理路径。
● **第三类：`UPDATE 分片表 ... LIMIT n`**。报错是「带 LIMIT 的 UPDATE 不能路由到多个节点」。
  ○ 栽在这里的是券资产的**过期任务**：原本一条 `UPDATE ... SET status='EXPIRED' ... LIMIT n` 就地批量过期。
    改法是先 `SELECT id, 用户 id ... ORDER BY 有效期 LIMIT n`（跨片归并的语义是对的），
    再逐条按（id、用户 id）更新，更新语句本身仍带状态与有效期的判断，所以重复执行是安全的。
    这个任务一批 500 条、一次最多 20 批，定时每 60 秒跑一次。
  ○ **这个拒绝是对的，不是中间件的毛病**：放行的话 LIMIT 会**按节点**生效，「这一批最多过期 500 张」
    会变成「每张物理表各 500 张」，也就是八倍。
  ○ 关单的兜底扫描不在这一类里：它本来就是「先查订单号、再逐条 CAS 关单」，一批 200 条（见 3.6）。
● **第四类：`WHERE 主键 = ?` 且不带分片键的 `FOR UPDATE`**。**它不报错**——这是最危险的一类，只会变慢和多锁。
  ○ 一条按券资产表自增主键锁行的语句，会在八张表上各锁一行。改法是谓词里带上用户 id，让它单片命中。
  ○ 订单、支付、退款那三处的行锁本来就按订单号 / 支付单号 / 退款单号取，天然带基因，不受影响。
● **第五类：`SELECT ... FROM 单表 WHERE EXISTS (SELECT 1 FROM 分片表 ...)`**。它被路由到一个没有那张单表的库。
  ○ 最隐蔽的一类：它不是 join，是子查询，SQL 表面上看不出跨了两种表。
  ○ 栽在这里的是营销那边「这个用户和这个商户有没有业务关系」的判定，拆成了三问在应用里合：
    有没有给他发过券；他有没有在这个商户下过单；这个用户存不存在。

还有一条不属于这五类、但同样是「解析器对每条语句都生效」的教训：一条**从未分片**的点赞清理语句，
因为用了 `TIMESTAMPADD(SECOND, ...)` 这种把单位当参数的写法，单位被解析成列名，每次执行都报「未知列 SECOND」。
改成 `DATE_SUB(..., INTERVAL ? SECOND)`。所以「只有分片表要小心」是错的判断。

### 3.5 启动时：两个库各自迁移，附属表主键的 workerId

● 框架自带的迁移被**关掉**，改由构造数据源的那段代码在把路由数据源交给任何人**之前**，分别迁移两个物理库：
  第一个库跑完整历史，第二个库只跑分片表那一份。
  ○ 理由很实际：DDL 走路由层就得告诉它每条语句归谁，而迁移本来就是按物理库做的事。
  ○ 代价之一是**两个库的 DDL 要各改一次**：M8 给订单表加追踪 id 列时，两边各有一份迁移，
    只改一边会变成「偶数 id 的买家正常、奇数 id 的买家全失败」。
● 第二个库的连接串默认由第一个库**推导**：同一个服务器、schema 名加一个后缀。所以隔离栈、压测脚本、全部集成测试
  用的还是原来那套环境变量，只是多了一个 schema。
  ○ 代价：把旧表里的行搬进第二个库时要跨 schema 读，**因此两个库必须是同一个实例的两个 schema**；
    指到别的服务器上这条迁移会直接失败，而不是悄悄丢掉奇数槽位。
  ○ 旧的五张表是**改名**加后缀而不是删除，V1 数据的迁移结果因此还留着，可恢复。
● 附属表主键用的那个 Snowflake **需要一个 worker id**，它从自己的属性里读，**默认 0**。
  规则文件里放的是一个占位符，解析之前被填掉，启动时打一行日志。
  ○ 号的来源：显式配置优先；没配就用进程监听的端口对 1024 取模。
  ○ **为什么不复用订单号那个 Snowflake 的 Redis 租约**（一个机制显然比两个好）：分片数据源要跑迁移，
    从 Redis 取号意味着 Redis 一挂就没有任何数据库能迁移。端口对「同一台机器上跑几个实例」这种部署形态够用——
    一台机器不可能把同一个端口给两个实例。**跨机部署端口会重复，那时必须显式配**，这是留着的缺口。
  ○ 这个缺陷是 M8 全链路冒烟第一次跑就抓到的：1000 单里 24 次主键冲突，报错指向审计表的某一张物理表。
    一个实例永远看不到它——所以此前每一次单测、每一次压测都是绿的。

### 3.6 不带分片键的兜底扫描：不需要额外做什么

计划里原本写了「关单兜底扫描按分片并行」「对账器读主库」，实际都不需要：

● 兜底扫描的两条查询（超期未支付的订单号、待释放预占的订单）都**不带分片键**，中间件本来就把它们并行发往全部八个节点
  再归并，`ORDER BY ... LIMIT` 的归并语义也是对的。应用层不需要再分片一次。一次最多 200 条，随后逐条按订单号
  做 CAS 关单或释放，那一步是单片的。
● 「读主库」目前是空操作：这个项目没有配读写分离，每个分片只有一个节点，不存在从库可读。
  等真的加了读写分离再谈强制走主库的提示，现在写进去只是装饰。

## 四、口述版

### 4.1 路由

订单分了两个库、每个库四张表，一共八个槽位，槽位就是键对 8 取模，库是槽位对 2 取模、表是槽位除以 2，
所以连号的用户交替落两个库而不是先填满一个。这里最关键的一件事是订单号的构造：M3 做准入漏斗的时候就把用户 id 对 1024
取模塞进了订单号的最低十位，而 8 整除 1024，所以订单号对 8 取模和用户 id 对 8 取模是同一个数——
买家拿着自己的用户 id 查，和支付回调、退款、关单只拿着订单号查，必然落在同一张物理表上。这就是基因法，
它换来的是「一行有两种叫法但只有一个位置」。派生的单号也继承这个基因：支付单号是订单号加一个序号，
退款单号是前缀加订单号或者前缀加支付单号，买来的券编号是 P 加订单号，所以支付回调、退款、券核销都是单片命中，
不会变成广播。唯一没有基因的是营销发放出去的券，它的编号是 G 加发放 id，按这个编号查就只能广播。

具体到一条语句，我实现的是一个复杂分片算法，规则里给每张表声明「有哪些列能叫到这一行」。算法先看有没有范围条件，
有就广播，因为槽位是取模出来的不是一个序，大于小于在槽位上没有意义。然后逐列算槽位，多列之间是**取交集**不是并集，
因为它们描述的是同一行，每多一个条件只可能更窄；某一列算不出槽位，比如那个没有基因的营销券编号，就跳过它，
让旁边的用户 id 来定位，而不是整条退化成广播。如果两列算出来的槽位互相矛盾，我不选边，返回全部节点，
这样一条 INSERT 会被中间件当场拒掉——一行自己的两个键对不上本来就是 bug，不能被写进其中一片。
什么都算不出来的时候也是广播，原则是读错片是错误答案，读八片只是慢。

### 4.2 唯一键

分片之后数据库只保证一张物理表内唯一，所以每个唯一键都要重问一遍。限购那个键是（用户 id、券 id、活跃标记），
语义一点没变，因为一个用户的所有订单永远在同一张表里，片内唯一就是全局唯一——这也正是分片键选用户 id
而不是券 id 的原因，选券 id 的话限购就得跨片去重了。支付单号、退款单号、买来的券编号也一样，都由订单号派生，
可能撞的两行必然同表。真正收窄成片内唯一的是三个：渠道流水号、渠道退款单号和核销码。前两个我能接受，
是因为回调总是带着支付单号或退款单号，幂等是按那一行判的，不靠渠道号；核销码是 80 bit 随机串，跨片撞号不是需要设计的事。
渠道流水号和核销码这两处我写了列注释说明它只在片内唯一，渠道退款单号那一列漏了。还有附属四张表的主键，自增在每张物理表里会各自从头数，所以去掉自增交给中间件的雪花生成，
反正没有任何查询按它路由。

### 4.3 事务

一个消费批次按券分组，每组在一个事务里做三件事：一条多行 INSERT IGNORE 写订单、一次条件更新扣库存、一条多行 INSERT 写审计。
这个事务通常横跨两个库，因为一批买家来自不同槽位，而库存那一行只在第一个库。我用的是中间件默认的 LOCAL 事务，
它是逐个物理连接提交的，不保证跨库原子，我没有上 XA。理由是代价和收益不成比例：2PC 的额外往返和锁持有时间正好落在
落库这条热路径上，而原子性并不是这条链路正确性的唯一来源。更重要的是崩在两次提交之间的后果是**有界的少卖，不是超卖**：
没提交的那半批订单还握着 Redis 预占，对账器发现数据库里没单会重投，INSERT IGNORE 保证重放幂等；
但这批库存已经扣过一次，重放会再扣一次，所以数据库库存会比真实值更低——方向是安全的，量级被批大小限住，
而且要求进程恰好死在两次提交之间那个窗口里，那个窗口有多宽我没有量过。顺带说一句，这个窗口我只做到了「机制上证明它存在」——
有一条集成测试用物理连接证明了一个批次真的写了两个库，窗口是它的推论——**故障注入本身没做**，这个我不会说成实测。

### 4.4 分片逼我改的 SQL，和启动时的那两件事

分片绝不是加个中间件就透明。这次被当场挡住的有五类：插入分片表时 join 单表取快照不行，改成应用侧先读一次快照再拼多值插入；
多表 DELETE 不行，改成先查键再逐条删；带 LIMIT 的 UPDATE 不行——券过期那个定时任务原来就是一条 UPDATE 带 LIMIT 500，
而且这个拒绝是对的，因为 LIMIT 会按节点生效，一批 500 会变成八张表各 500，所以改成先 SELECT 出键再逐条按键更新，
更新语句自己还带着状态和有效期的判断，重复跑也安全；
第四类不报错，是最危险的，一条按自增主键加 FOR UPDATE 的语句会在八张表上各锁一行，只是变慢和多锁不会失败，
改法是谓词里带上用户 id；第五类最隐蔽，是单表里套一个查分片表的 EXISTS 子查询，表面看不出跨了两种表，
被路由到一个根本没有那张单表的库，拆成三问在应用里合。另外有一条根本没分片的定时清理语句也报错了，
因为把时间单位写成了函数参数被当成列名——说明解析器对每条语句都生效，「只有分片表要小心」是错的。

启动这边有两件事。一是框架的迁移我关掉了，改成在构造路由数据源之前分别迁移两个物理库，第一个库跑完整历史，
第二个库只跑分片表，因为 DDL 走路由层就得告诉它每条语句归谁，而迁移本来就是按物理库做的。第二个库的连接串从第一个推导，
同一个实例换个 schema 名，这样压测脚本和集成测试用的还是原来那套环境变量；代价是旧数据搬进第二个库要跨 schema 读，
所以两个库必须是同一实例，指到别的服务器上这条迁移会直接失败而不是悄悄丢掉奇数槽位。二是附属表主键那个雪花需要 worker id，
它从自己的属性里读、默认是 0，两个实例都是 0 就会在同一毫秒铸出同一个 id——M8 全链路第一次跑 1000 单就撞了 24 次。
我在规则文件里放了个占位符，解析之前填掉，号优先取显式配置，没配就用端口对 1024 取模。为什么不复用订单号那个雪花的 Redis 租约？
因为分片数据源要跑迁移，从 Redis 取号意味着 Redis 一挂就没有任何数据库能迁移。端口这个办法对「一台机器上跑几个实例」够用，
跨机部署端口会重复，那时必须显式配，这条我写在边界里。

## 五、为什么这么设计 / 会被怎么追问

**Q：为什么分片键选用户 id 而不是券 id 或订单号？**
券 id 会让一场秒杀的全部订单压在一片上，等于没分；更要命的是限购唯一键（用户 id、券 id、活跃标记）会变成跨片判重。
选用户 id 之后一个用户的所有行都在同一张物理表里，限购片内唯一就是全局唯一。至于订单号——它**也是**分片键，
因为低十位就是用户基因，两者算出同一个槽位，这正是基因法的意义。

**Q：为什么是 2 库 × 4 表，8 这个数是怎么来的？**
约束是「必须整除订单号里那个 1024 的基因空间」，所以只能取 2 的幂。8 是在「能演示分库 + 分表两层」和
「单机压测跑得动」之间选的。要扩到 16 个槽位，基因还够用（1024 仍然整除 16），但已有数据要重新搬；
真要做在线扩容应该上一致性哈希或者双写迁移，这个项目没做。

**Q：为什么秒杀库存表不做广播表？它看着就是低频只读的配置表。**
因为它的库存字段是**写热点**，不是只读的。广播表的写会复制到每个库，两个库里的同一个库存数要保持是同一个数字就需要分布式事务。
最后一道防线是数据库里的 `stock >= n` 条件更新，把这道防线建立在一个需要 2PC 才能自洽的数字上，是把问题变复杂。
所以它是单表，只在第一个库。顺带说，压测已经证明这一行是写路径水平扩展的上限（提交次数每秒恒在 70–115、与实例数无关），
拆它是下一步，但拆的方向是按券分桶而不是复制到两个库。

**Q：LOCAL 事务不保证跨库原子，为什么敢用？**
见 4.3：后果是有界的少卖不是超卖，重投加 `INSERT IGNORE` 能补回订单，补不回的是多扣的那一次库存。
XA 的代价我**没有实测**，所以不报数字；但 2PC 的额外往返正好落在落库这条热路径上。在有证据说明 LOCAL 不够用之前不引入。
被追问「你怎么知道后果有界」，答案是那条测试证明了一个批次确实横跨两库，窗口是它的推论；**故障注入没做**。

**Q：分片之后有哪些查询还是广播？为什么不修？**
取单行的查询里有三个：按核销码查（店员扫码，低频）、按营销发放的券编号查（没有基因）、
商户后台按商户 id 分页查订单。不带分片键的批量扫描（兜底关单、券过期）也是广播，但那是设计如此，不是遗留问题。
前两个量级可以接受。第三个是**明确不修的**：它会向八张表各发一次查询再归并，结果正确但不随分片数扩展，
分页越深越贵。要修它需要一条独立的读路径（binlog 订阅 → MQ → 搜索引擎里的订单读模型），那是另一个子系统。
被问到时的答案就是这一段，而不是「分片之后商户查询也很快」。

**Q：分片让性能变好了吗？**
准入侧**没有代价**，这是这一档要证明的事：同场对照里 10k 档 9936.5 → 9961.7 req/s（p99 68.3 → 58.6 ms），
20k 档 19725.1 → 19721.5（p99 87.3 → 101.0），每一档 `accepted = stock`、无超卖。
落库侧那一行是 982.7 → 2088.9 单/s（中位）、负载停止后的积压 10.7 / 55.8 / 16.1 s 降到 0.1 / 0.1 / 0.1 s，
但报告里 M6 那一行同时包含了**消费参数的调整**，所以这个提升不能单独归给分片。
分片本身的正确说法是：它买的是水平扩展的可能性，不是当下的吞吐。

**Q：加了中间件之后有什么意外？**
两件和分片无关但被分片翻出来的事，值得讲，因为它们说明「引入一个解析层」的影响面：其一，中间件的元数据仓库带进了
一个 XML 序列化依赖，Spring 把 XML 转换器排到了 JSON 前面，不带 `Accept` 头的请求开始收到 XML；
排除依赖会让启动直接失败（运行时真要它），最终在 Web 配置里按媒体类型删掉那个转换器。
其二，关掉框架自带迁移之后，一个 bean 上的「依赖于迁移 bean」声明指向了一个不再存在的 bean，**应用在正常配置下启动失败**，
而 473 个单测和 94 个集成测试都没看见——那个 bean 在测试 profile 下不创建，唯一会创建它的是真实 jar。
这条是**冒烟抓到的**，不是测试抓到的。

**Q：为什么附属表的主键不继续用自增？**
八张物理表的自增会各自从 1 数起，同一个 id 在八张表里各有一行。没有任何查询按它路由，所以换成中间件的 Snowflake。
换来的新问题就是 worker id（见 4.4），这是「换一个机制就得接管它的全部前提」的一个例子。

## 六、已知边界

- **LOCAL 事务的非原子窗口没有做故障注入**。它目前是推理加机制证据（那条跨两库的批次测试），不是实测。
- **两个库必须是同一个实例的两个 schema**，因为旧数据的搬迁跨 schema 读。指到别的服务器上迁移会失败。
- **附属表主键的 worker id 跨机部署必须显式配置**。不配就取端口对 1024 取模，跨机端口会重复。
- **商户后台按商户 id 分页是跨八张表的广播归并**：结果正确，不扩展，分页越深越贵。明确不修。
- **多表 DML 在分片表上不再可用**，包括测试清理。
- **在线扩容没做**：改槽位数要重新搬数据，没有双写迁移或一致性哈希。
- **没有读写分离**，所以「对账器读主库」目前是空操作。
- 附属四张表（审计、支付流水、退款流水、券资产）的主键不再是递增小整数（按它排序仍是时间序）。
- 写路径的水平扩展上限是库存表的那一行，这是已测实、尚未修的边界（详见第 05 章与压测报告）。
