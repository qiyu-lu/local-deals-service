# 01 消费者登录

## 一、这一章解决什么问题

消费者端没有密码，登录的全部凭据就是一串六位数字：**申请一次验证码，再用它换一个会话 token**。
难点不在流程长短，而在这条链路是整个站点唯一的身份入口，两头都要守住：申请端要防短信轰炸——
同一个手机号被反复触发；消费端要防暴力猜码——六位数字只有一百万种，允许无限试就等于没有验证码。
而这两种防护都是「读一个状态、判断、再写回去」，**中间不能被另一个并发请求插进来**，否则冷却会被绕过、
失败次数会被覆盖。

另一半问题在请求侧：登录之后的每个请求都要知道「你是谁」，而且用户在连续操作时不该被突然踢下线。
所以要有一个**只解析、不拦截**的环节把身份放进当前线程并顺手续期，和一个**只拦截、不查询**的环节
决定这个接口允不允许匿名访问——把「你是谁」和「这里要不要登录」拆成两件事。

商户与管理员是另一套完全独立的登录与鉴权（失败锁定、RBAC、认证版本号），详见第 02 章；
秒杀链路自己的购买令牌与分层限流详见第 04 章。

## 二、涉及的数据

**用户表**：关键字段是用户 id（主键、自增）、手机号（**有唯一索引**）、昵称、头像、创建/更新时间。
密码字段留着但消费者链路不用。首次登录时按手机号建一条记录，昵称是固定前缀加十位随机串。

**验证码相关的三个 Redis key**，都以手机号作后缀，并且后缀被包在花括号里——也就是用手机号做 hash tag，
保证在 Redis Cluster 上三个 key 落在同一个 slot，一个 Lua 脚本才能同时操作它们：

- **验证码本身**：字符串，存六位数字，有效期 120 秒。
- **发送冷却**：字符串，值无意义，存在即表示「这个号 60 秒内刚发过」，有效期 60 秒。
- **失败计数**：字符串，存这一轮验证码已经输错了几次，上限 5 次；它的过期时间**始终对齐验证码的剩余寿命**，
  而不是自己另设一个 TTL。

**会话 token**：登录成功后生成一个去掉短横的 UUID，以它为后缀建一个 Redis 哈希，字段只有用户 id、
昵称、头像——**手机号不进这个哈希**，所以即使 token 泄露也读不到手机号。有效期 30 分钟，**滑动续期**。

**当前用户**：一个线程本地变量，存上面那三个非敏感字段构成的对象，请求结束时清空。

本章不涉及消息队列。

## 三、详细流程

### 3.1 申请验证码

消费者带一个手机号来，希望取得一轮可用于登录的验证码。这个请求到「验证码写进 Redis 并返回成功」为止结束，
同一次请求里不会继续登录。

- 请求先过消费者拦截器链。申请接口在**公开 POST 白名单**里，未登录也放行（白名单的判定见 3.3）。
- 服务先校验手机号格式，不合法直接返回业务失败（HTTP 仍是 200，body 里 success 为 false），不碰 Redis。
- 生成六位随机数字，用手机号拼出冷却、验证码、失败计数三个 key，连同验证码、验证码有效期 120 秒、
  冷却时长 60 秒一起交给**一个 Lua 脚本**：
  - 脚本先判断冷却 key 是否存在。存在就**立即返回 0，原来的验证码和失败计数一个都不动**——
    这点很重要：冷却期内重复申请不会把已经发出去的那个码冲掉，用户手上的短信仍然有效。
  - 不存在时，依次写入验证码并设 120 秒、写入冷却并设 60 秒、**删除失败计数**，返回 1。
    删失败计数是因为「新发一轮码」意味着重新给满 5 次的试错预算。
  - 三条写命令在同一次脚本里连续执行，另一个并发申请只可能在脚本结束后才看到冷却，所以
    「同一手机号 60 秒一条」这个约束不会被并发绕过。
- Java 侧只有返回值等于 1 才算成功；不等于 1 就抛 429「发送过于频繁」。
- 执行脚本时 Redis 抛异常，统一转成 503「认证状态暂不可用」——**不降级、不放过**：认证状态读不到时
  宁可拒绝，也不能默认通过。
- 项目没有接真实短信通道。成功只代表验证码状态已写入 Redis，不代表短信送达；有一个默认关闭的开关
  可以在本地把验证码打到日志里，日志中的手机号做掩码处理。

### 3.2 用验证码换 token

消费者提交手机号 + 验证码，想换一个会话 token。这个请求到「token 哈希写入 Redis 并把 token 返回前端」为止。

- 登录接口同样在公开 POST 白名单里。
- **两道格式校验都在碰 Redis 之前**：手机号格式；验证码必须是严格六位 ASCII 数字。
  格式不对的码直接返回「验证码不正确」，**不消耗失败次数**——否则攻击者可以用乱码把别人的账号刷到锁定。
- 验证码 key 与失败计数 key 交给**第二个 Lua 脚本**，参数是提交的码和失败上限 5。脚本返回三态：
  1 成功、0 普通失败、2 已锁定。
  - 先读失败计数，已经**达到 5 次就直接返回 2，连验证码都不读**——锁定优先于一切判断。
  - 再读验证码，不存在（过期或已被用掉）返回 0。
  - 与提交的码一致：**在同一次脚本里把验证码和失败计数一起删掉**，返回 1。删验证码保证一个码只能被消费一次，
    两个并发请求拿同一个码只有一个能成功。
  - 不一致：先取验证码的剩余毫秒数。
    - 剩余不大于 0（刚好卡在过期边界）：两个 key 都删掉，返回 2。
    - 否则失败计数加一，并把它的过期时间**改写成验证码的剩余寿命**——这样锁定最多只跟着这一轮码存在，
      不会变成一个独立的长期惩罚。
    - 加一之后若达到 5 次，把计数固定写成 5、TTL 仍取剩余寿命，**最后才删掉验证码**，返回 2。
      顺序是「先读剩余寿命 → 按它把计数写死 → 再删码」：码删掉之后就读不到剩余寿命了，
      所以锁定的寿命必须在删码之前定好。删的只有验证码那一个 key，计数不能跟着一起删，否则锁定当场失效。
- Java 侧只认 1。**0 和 2 对外是同一句「验证码不正确」**，不告诉对方「你被锁了」也不告诉「这个号根本没申请过码」，
  避免用错误信息枚举出手机号是否注册、是否正在登录。
- Redis 抛异常同样是 503「认证状态暂不可用」。
- 验证码消费成功后才碰数据库：按手机号查用户，查到就沿用，查不到就用手机号 + 随机昵称建一条并落库。
- 生成一个去掉短横的 UUID 作为 token，把用户对象里的 id、昵称、头像转成字符串映射写进以 token 为后缀的哈希，
  再单独设 30 分钟过期，最后把 token 字符串返回前端。前端此后把它放在请求头里。
- 注意这里是**先建号再发 token**，顺序不能反：token 里要带用户 id。

### 3.3 带 token 访问，两级拦截器与续期

任何一个非管理端请求进来，都要先确定「是否有合法身份」和「这个接口要不要身份」。这两件事由两个拦截器分担，
顺序固定：**解析在前、拦截在后**——注册时给的执行顺序值是解析 0、拦截 1，注意这和代码里两者的书写顺序
相反，排序只认这个值（两者都排除管理端路径，管理端有自己的一对拦截器，详见第 02 章；
秒杀的售罄拦截器用 -1 排在这两者更前面，因为售罄答复对谁都一样、不需要身份，详见第 04 章）。

- **第一级：解析与续期**，挂在全部路径上，**它永远放行，从不返回 401**。
  - 请求头里没有 token：直接放行，**一次 Redis 命令都不发**。这意味着匿名访问公开接口的鉴权成本是零。
  - 有 token：按 token 拼 key 取整个哈希。
    - 哈希是空的（token 不存在或已过期）：放行，但线程本地变量里没有用户——后面自然会被第二级拦下。
    - 非空：填回用户对象、放进线程本地变量，然后把这个 key 的过期时间**重设为 30 分钟**。
      这就是滑动续期：只要用户在持续操作，会话不会在固定 30 分钟后突然断掉；连续静默 30 分钟才掉线。
    - Redis 抛异常：先清掉线程本地变量，再抛 503「登录状态暂时不可用」。
  - 请求结束后在拦截器的收尾回调里**清理线程本地变量**。线程池会复用线程，不清就会把上一个请求的用户
    泄漏给下一个请求，这是这类实现最经典的坑。
- **第二级：判定这个接口要不要登录**，它不查 Redis，只看线程本地变量。
  - 先判是不是公开请求：
    - `OPTIONS` 一律放行，否则浏览器的跨域预检会拿不到 401 以外的答复。
    - 取出路径并去掉结尾的一个斜杠（只去一个，所以带两条斜杠的路径不会被规整成公开路径），
      再按方法分流：GET 与 HEAD 查**公开读白名单**（店铺详情、按类型/搜索、
      店铺类型列表、热门笔记、笔记详情与点赞列表、按用户/按店铺的笔记、笔记搜索、某店铺的券列表），
      POST 查**公开写白名单**（申请验证码、登录、两个支付回调、mock 支付页）；其他方法一律不公开。
    - 这个「方法 + 路径都要匹配」的设计是有意的：同一条路径的写操作**不会**因为读是公开的就跟着公开。
      对同一个店铺路径发 POST 会被要求登录。
  - 不是公开请求且线程本地变量为空，直接写 401 并中断；有用户就放行。
  - 支付回调靠签名自证身份，所以放在公开白名单里而不是靠 token，属于第 06 章的范围。
- 受保护接口里的业务代码此后都直接从线程本地变量取当前用户 id，不再重复解析 token。

### 3.4 登出，以及 WebSocket 握手复用同一套会话

- 登出接口**不在公开白名单里**，要带着有效 token 才能调；服务端就是把这个 token 对应的哈希删掉。
  线程本地变量不用管，第一级拦截器的收尾逻辑会统一清理。删掉之后该 token 立即失效——
  这是会话放在 Redis 而不是 JWT 的直接好处：**能撤销**。
- WebSocket 握手拿不到自定义请求头，所以 token 从查询参数里取，再用**同一个哈希**校验并把用户 id
  放进会话属性。两点差别要记住：一是握手校验**不续期**（否则一条长连接会让会话永不过期）；
  二是失败就拒绝握手，不存在「匿名连上再说」。

## 四、口述版

**4.1 申请验证码。**
用户输入手机号点发送，请求先过拦截器，申请验证码是公开接口所以放行。服务先校验手机号格式，
不合法就直接返回、根本不碰 Redis，避免一个畸形输入也要付一次网络往返。格式没问题就生成六位数字，
然后用手机号拼出三个 key：这个号的发送冷却、验证码本身、登录失败次数。这三个 key 的后缀都用花括号
把手机号包起来，也就是共用一个 hash tag，因为在 Redis Cluster 上一个 Lua 脚本只能操作同一个 slot 的 key，
不带 tag 的话三个 key 会散到三个节点，脚本根本跑不起来。

接着把三个 key 连同验证码、两个有效期交给一个 Lua 脚本一次做完：先看冷却键在不在，在就说明这个号
一分钟内刚发过，直接返回，原来的验证码和失败次数都不动——这点是有意的，重复点发送不能把用户
手里那条还有效的短信冲掉；不在的话就写验证码并设两分钟过期、建冷却并设一分钟过期，最后把失败次数删掉，
因为重新发码就该给满新的试错预算。之所以要用脚本而不是分三步写，是因为检查冷却和写验证码之间
一旦被另一个并发申请插进来，两个人就都会觉得自己拿到了发送权，限频就形同虚设。Java 这边只认返回 1，
不是 1 就答 429。如果脚本执行本身抛了异常，说明认证状态读不到，这时候统一答 503，不做任何降级放行，
因为认证这条链路宁可拒绝也不能默认通过。要说明的是项目没接真实短信通道，成功只表示码写进了 Redis。

**4.2 用验证码换 token。**
用户填手机号和验证码来登录。先做两道格式校验：手机号合法、验证码必须是严格六位数字。
第二道特别重要，它挡在 Redis 前面，作用是让乱码不消耗失败次数——否则任何人都能用一堆非法字符
把别人的手机号刷到锁定，那本身就成了一种攻击。

过了校验就拿验证码和失败次数两个 key，交给第二个脚本，同样是因为读计数、读码、判断、写回
这一串中间不能被别人插进来。脚本先读失败次数，已经到 5 次就直接返回锁定，连验证码都不读，
锁定的优先级最高；没到上限就读验证码，读不到说明过期了或者已经被用掉，返回失败；读到了并且和输入一致，
就在同一个脚本里把验证码和失败次数一起删掉再返回成功，删验证码是为了保证一个码只能被消费一次，
两个并发请求拿同一个码只有一个能成。如果不一致，就先取验证码的剩余存活时间，把失败次数加一，
并且让失败次数的过期时间跟验证码的剩余时间对齐，这样锁定最多只跟着这一轮码存在，不会变成一个
独立的长期惩罚；万一加到了 5 次，就把计数固定成上限、按同样的剩余时间设过期，然后把验证码删掉——
顺序必须是先算好剩余时间再删码，因为码删掉之后就查不到它的剩余时间了。

Java 这边只有返回成功才继续，另外两种结果对外说的是同一句「验证码不正确」，既不说你被锁了也不说
这个号压根没申请过码，免得攻击者靠错误信息去枚举哪些手机号注册过。验证码消费成功之后才去查数据库，
按手机号查用户，查到就沿用，查不到就建一个新用户，昵称给一个随机串。最后生成一个 UUID 作为 token，
把用户对象里只有 id、昵称、头像这三个非敏感字段转成字符串写进一个 Redis 哈希，设三十分钟过期，
把 token 返回给前端。手机号不进这个哈希，token 泄露也读不出手机号。

**4.3 带着 token 访问业务接口。**
之后每个请求都带着这个 token 在请求头里。拦截器有两级，顺序是解析在前、拦截在后，这么拆是因为
「你是谁」和「这个接口要不要登录」是两件不同的事，合在一起写就会出现公开接口也被迫查一次 Redis 的浪费。

第一级只负责解析，它永远放行。没带 token 就直接过，一条 Redis 命令都不发，所以匿名逛店铺、看笔记
这些公开接口的鉴权开销是零。带了 token 就按 token 去取那个哈希，取到空的就当没登录、照样放行，
取到了就还原成用户对象放进 ThreadLocal，然后顺手把这个 key 的过期时间重新设成三十分钟。
这就是滑动续期，目的是只要用户在持续操作就不该掉线，只有连续静默半小时才过期。如果这一步 Redis 抛异常，
就先清掉 ThreadLocal 再答 503。请求结束时一定要在收尾方法里把 ThreadLocal 清掉，因为 Tomcat 的线程是复用的，
不清就会把上一个请求的用户身份泄漏给下一个请求。

第二级才决定拦不拦，它不查 Redis，只看 ThreadLocal 里有没有人。它先判断这是不是公开请求：跨域预检
一律放行；然后按方法分开匹配，GET 和 HEAD 查公开读白名单，比如店铺详情、店铺搜索、热门笔记这些，
POST 查公开写白名单，也就是申请验证码、登录和支付回调。这里方法和路径必须同时匹配，
所以同一条店铺路径你发 POST 是进不去的，一个写接口不会因为跟某个公开读共用路径就意外变成公开的。
不是公开请求而 ThreadLocal 又是空的，就返回 401。支付回调之所以能公开，是它靠签名自证身份，不走 token。

**4.4 登出与长连接。**
登出接口本身是要登录才能调的，服务端就是把这个 token 对应的哈希删掉，删完立刻失效——
这也是我把会话放在 Redis 而不是用 JWT 的主要理由：JWT 签出去就撤不回来，而这里踢人只要删一个 key，
并且计划里也明确写了没有业务理由为换而换。WebSocket 那边复用的是同一个会话哈希，
只是因为握手拿不到自定义请求头，所以 token 从查询参数走；另外握手校验故意不续期，
不然一条挂着的长连接会让会话永远不过期。

## 五、为什么这么设计 / 会被怎么追问

- **为什么用 Lua 而不是分布式锁或 `SETNX`？**
  需要原子的是「读一个值 + 按结果决定写哪几个 key」，不是单纯的互斥。Lua 在 Redis 里单线程串行执行，
  一次往返完成，成本比拿锁再操作低一个量级，而且不存在锁超时、误删别人锁这些附带问题。
  代价是脚本只能操作同一个 slot 的 key，这直接决定了下一条。

- **为什么三个 key 要用手机号做 hash tag？**
  Cluster 下同一个脚本涉及的 key 必须落在同一个 slot，不带 tag 这三个 key 会散到三个节点，脚本根本跑不起来。
  tag 选手机号而不是固定常量，是因为固定常量会把全部手机号的验证码压到同一个 slot，等于自造一个热点节点；
  而按手机号分，天然就散开了。反过来说，一份全局共享的结构（例如全站一份的热榜）用固定常量做 tag 是合理的，
  因为它本来就只有一份、没有可分散的维度。

- **失败次数的过期时间为什么跟验证码对齐，而不是自己设一个？**
  两个目的。一是锁定不能超出这一轮码的寿命，否则就变成一个能被人随意触发的长期封禁。
  二是最后一次失败时脚本会把验证码删掉，而锁定要靠计数这个 key 继续存在才生效——所以那一步
  先按剩余寿命把计数写死，再**单独**删验证码；别的分支里两个 key 是一起删的，这一处不能顺手带上计数。

- **锁定 5 次会不会被用来恶意锁别人？**
  会。攻击者只要知道手机号，连着提交 5 个格式合法的错码就能把这一轮码锁掉——那道六位数字格式校验
  只挡住畸形输入，挡不住这种攻击，别把它当成防线。真正让代价有限的是 TTL 对齐：锁定最多只活到
  这一轮验证码过期，也就是 120 秒以内；而且受害者只要过了 60 秒冷却重新申请一次验证码，
  发码脚本会直接删掉失败计数，预算立刻恢复。所以这是一个上限 120 秒、且受害者自己能解除的骚扰，
  不是账号级封禁。

- **两个拦截器为什么不合成一个？**
  合成一个的话，公开接口也要走完整套解析，或者要在同一处同时维护「解析」和「白名单」两套分支。
  拆开之后第一级的规则只有一条——有 token 就解析并续期，没有就放行；第二级的规则也只有一条——
  没人就 401。另外秒杀的售罄判定要排在认证之前才能做到零网络 IO，这个位置也是靠拦截器的执行顺序值
  排出来的（详见第 04 章）。

- **为什么白名单要按 HTTP 方法分开？**
  因为路径匹配是带路径变量的模式匹配（公开读白名单里的条目本身就是模式，例如带数字 id 约束的店铺详情），
  很容易出现「公开一个读，顺带公开了同路径的写」。按方法分开之后，
  公开读白名单上的路径发 POST 仍然要求登录，这一条是有测试覆盖的。

- **为什么不用 JWT？**
  主计划里这条链路的结论是「保留不动」，理由是够用、为换而换没有业务理由。技术上的取舍是：
  JWT 省掉每请求一次 Redis 读，但签出去撤不回来，登出和踢人都要再加一个黑名单，
  那个黑名单又得放 Redis——等于把省下的读又加回来，还多了一套逻辑。
  而现在这种方式顺便拿到了滑动续期，JWT 想做续期就得反复重签。

- **token 哈希里为什么只放三个字段？**
  取它的地方每个请求都要执行，字段越少反序列化越便宜；更重要的是手机号这类敏感信息不该留在
  一个拿到 token 就能读的结构里。业务需要更多用户信息时自己去查库。

## 六、已知边界

- **写 token 哈希和设过期是两条命令**，不是一个原子操作。写完之后、设过期之前如果进程挂掉或 Redis 连接断开，
  这个 key 会**永不过期**地留在 Redis 里。正确做法是用一次带过期的写入或用脚本合并。
- **首次登录建用户没有处理唯一键冲突**。同一个手机号的两个并发首次登录都会查不到用户、都去插入，
  第二条会撞上手机号唯一索引抛出异常，最终对用户表现为 500。实际发生概率很低（一个验证码只能被消费一次，
  要撞上得是两轮码并发），但这是个真实缺口；对照之下，签到接口就显式接住了唯一键冲突并当作幂等成功。
- **解析拦截器在 Redis 故障时会波及公开接口**：只要请求头里带了 token，哪怕访问的是公开读接口，
  Redis 异常也会让它变成 503，而不是退化成匿名访问。
- **没有接真实短信通道**，发送成功只代表状态写进了 Redis。同样地，冷却只按手机号做，
  没有按客户端 IP 或设备的维度限频，换手机号就能继续发。
- **登出只销毁当前 token**，同一账号在别处登录拿到的 token 不受影响；也没有「同一账号最多几个会话」的约束。
- **续期是每次请求都写一次过期时间**，高频请求下这是一次额外的 Redis 写。没有做「剩余时间低于某阈值才续」的优化。
- **WebSocket 握手和 HTTP 请求在 Redis 故障时的行为不一致**：HTTP 侧把异常抛成 503，握手侧把异常吞掉、
  当作校验不通过直接拒绝。单看安全性握手这边是 fail-closed、没问题，但客户端拿到的是「token 无效」而不是
  「服务暂时不可用」，排查时容易误判。
- **本章没有性能数字**：现有的基准报告覆盖的是秒杀链路，登录链路没有单独压测过。
