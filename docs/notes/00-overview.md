# 00 总览：一句话、一条闭环、一张数字表

> 这一章是其余十三章的入口，也是面试开场那三分钟要讲的东西。
> 全书的术语以本章末尾的「角色名表」为准：同一个角色在各章叫同一个名字。

## 一、这一章解决什么问题

面试的前三分钟决定后面问什么。这三分钟要说清四件事：这个系统是干什么的、难在哪、
我把难点解决到了什么程度（有数）、哪些没做（先说出来，别等被挖）。
后面十三章是「每条链路怎么工作」，这一章是「把它们串成一个能讲出口的故事」。

难点只有一个形状：**一瞬间来的人远多于货**。10 万人抢 1000 件，99% 的请求注定失败，
但每一个都要被处理、被计费、被排队。系统的全部设计都是围绕「让注定失败的那部分尽早、
尽便宜地死掉」和「让成功的那部分可靠地落到账上」展开的。

## 二、业务闭环与模块

```text
商户建活动 → 用户抢 / 领 / 买 → 券进资产 → 到店核销 → 退款或过期
```

定位是**本地生活商户券营销与交易平台**，不是「点评 App 的后端」。
所以「券」是这个系统的中心概念：秒杀购买、用户领取、后台发放、签到奖励、批量发放——
五个来源，最后都落成同一种券资产；核销、过期、退款只操作这一张表。

五个模块各一句话：

| 模块 | 一句话职责 | 主要在哪几章 |
| --- | --- | --- |
| 交易 | 秒杀准入与批量落库、订单状态机、支付与退款、分片路由、券资产与核销 | 04 05 06 07 08 |
| 营销 | 活动与标签、定向发放与额度、批量发放、签到奖励、通知 Outbox | 09 |
| 商户 | 商户与店铺、后台身份与权限、数据隔离、操作审计、店铺搜索 | 02 03 |
| 内容 | 笔记与点赞（先写事实后异步投影）、可重建的热榜、图片上传 | 10 |
| 平台 | 消费者登录与会话、拦截器、实时推送扇出、消息基础设施、追踪与指标 | 01 09 11 |

## 三、架构与各层职责

一句话概括：**让 99% 注定失败的请求在最便宜的层死掉，让 1% 成功的请求以批量方式落库；
缓存只做可丢的准入层，数据库的条件更新是最后防线。**

请求从外到内经过五层，每一层只放行下一层需要的量：

- **入口代理**：静态资源、入口限流、生成每个请求的追踪标识。压测时这一层的限流是关掉的
  （见第 12 章「配置偏离」）。
- **L1 本地售罄标记**：进程内的一个标记，命中就直接答复「没了」，**零次网络往返**。
  标记由准入脚本的返回值置上，并通过发布订阅广播给其他实例；库存被归还时清掉。
- **L2 本地令牌桶**：按这张券在本实例分到的剩余库存定速，把明显超出的部分挡在进程内。
- **L3 一次缓存脚本**：限频、活动校验、判重、分桶扣减、写预占，**五件事在一次往返里做完**，
  因为它们之间不能被另一个并发请求插进去。只有这一步成功的人，才会发出一条普通消息。
- **异步落库**：批量消费者把一批成功者按券分组，一个事务里做一次多值插入加一次条件扣减。

各层的定位必须说清楚，这是这个项目最值钱的一句话：

| 层 | 角色 | 坏掉会怎样 |
| --- | --- | --- |
| 缓存（3 主 3 从，按券分桶） | **准入层，允许丢** | 丢了预占，对账器重驱动；极端情况多放一些人进来 |
| 消息 | 削峰与重投 | 整批重投，靠幂等吸收 |
| 数据库 | **最后防线** | 条件更新拒批，超卖不可能发生 |

「缓存可丢」不是口号，是被演练逼出来的结论：复制空窗那次，缓存最多多放了 **10.3%** 的人，
而数据库**每一轮都恰好建了 30000 单、超卖恒为 0**（第 12 章 3.6）。

故障演练三行：

- 应用 `kill -9`：收敛时间 **102.8 s → 44.7 s**。
- 缓存主节点宕机 ×2：**丢失预占 0、超卖 0**，代价是约 **1.26 万个 503**。
- 复制空窗后杀主，两晚四轮：缓存最多多放 **10.3%**，**数据库每轮恰好建 30000 单、超卖恒为 0**，
  收敛需要 **150–308 s**，靠对账器。

**没达成的目标也写在这里**：M4 定的「落库 ≥3000 单/s」在单实例上没有达成，
原因在下一节第 4 条。

## 五、瓶颈是怎么一层层移动的

这是整个项目最好讲的一条线——每一步都是「量出来的，不是想出来的」。

1. **起点：瓶颈在消息 Broker。** 每个请求——包括 99% 注定失败的——都先发一条事务半消息，
   15k 档 Broker 先流控。落库 264 单/s，火焰图里 **44.7%** 花在库存那一行的行锁上、
   **49.5%** 在连接池等待。
2. **把 99% 挡在最便宜的层（第 04 章）。** 半消息从「等于请求数」变成 0，10k 档应用 CPU
   从 3.04 核降到 0.60 核，拐点从 5k 抬到 20k。**准入侧从此不再是瓶颈**，
   之后每个里程碑的准入数字只用来证明没有回退。
3. **把落库从「每单一次提交」改成「每批一次提交」（第 05 章）**，吞吐翻倍，但没到目标。
   补上仪表后发现真正卡住的不是提交速率而是**批大小**：实测 **1.03**——消费线程本来就跟得上
   到达速率，队列里永远没有第二条消息在等。
4. **调拉取间隔把批攒起来**：批大小均值 **2.16（0 ms）→ 12.68（50 ms）**，换参数后 **2001.5 单/s**，
   而且那是场景发压速率的上限、不是系统的。
5. **加实例测出来的答案是「写路径不扩展」（第 08、12 章）。** 三个实例烧掉三倍 CPU，
   只多落了约 25% 的单，而数据库只用了 **0.24 核**；提交次数/s 在 **70–115** 之间，
   **与实例数没有关系**——瓶颈是每个批次都要更新的**同一行库存**。
   这一行**明确不拆**：测实了、知道怎么拆、为什么现在不拆，比多一个分桶更值得讲。
6. **准入侧的扩展曲线测不出来，而且原因不在系统**：1/2/3 实例在 30k 档都是 ~25.5k req/s，
   因为 **k6 自己吃满了 3.52–3.58 核**，而三个实例加起来只用了 1.26 核。
   **客户端先满**。任何「水平扩展提升了准入吞吐」的说法都不能从这份数据得出。

## 六、口述版

### 6.1 三分钟项目介绍

这是一个本地生活的商户券营销与交易平台，业务闭环是商户建活动、用户抢或领或买、券进到用户的资产里、
到店核销、最后要么退款要么过期。技术上最难的一段是秒杀：一瞬间十万人抢一千件，
百分之九十九的请求注定失败，但每一个都要被处理，所以整个设计就是围绕「让注定失败的请求尽早、
尽便宜地死掉」和「让抢到的那一小部分可靠地落到账上」这两件事展开的。

先说准入这一半。一个下单请求进来，最外面是入口代理，然后到应用里的三层漏斗。
第一层是进程内的一个售罄标记，命中就直接回「没了」，一次网络请求都不发，
这个标记是准入脚本返回售罄的时候置上的，再通过发布订阅广播给其他实例，
库存被归还的时候清掉。第二层是本地令牌桶，按这张券在本实例分到的剩余库存来定速，
把明显超出的量挡在进程内，不让它们去打缓存。第三层才真正碰缓存，用一个脚本一次做完五件事：
限频、活动有没有在卖、这个人是不是买过、扣库存、写预占。之所以必须合成一个脚本，
是因为「检查」和「扣减」之间不能被另一个并发请求插进去，否则就超卖了。
订单号是本地发的雪花号，不依赖缓存，而且低位嵌了用户 id 的基因，后面分库分表要用。
最关键的一点是：**只有这一步成功的人才会发一条消息**，改造前是每个请求都先发一条事务半消息，
所以百分之九十九的请求都在打 Broker，Broker 先被打垮。改完之后半消息从等于请求数变成零，
十千档的应用 CPU 从三核降到零点六核，拐点从五千抬到两万。

再说落库这一半。抢到的人只是在缓存里有一条预占，订单还没建。消费者是自己写的批量消费者，
拿到一批消息之后分三步：先按桶一次往返把这批认领下来，带一个三十秒的租约，
这样别的实例和对账器就不会同时处理它们；然后按券分组，一个事务里做一次多值插入加一次条件扣减，
插入用忽略重复的写法所以重复消费不会重复建单，扣减带着「库存大于等于本批数量」的条件，
这是最后一道防线；最后再按桶一次往返把状态置成功、清掉认领、移出到期索引。
整批要么一起确认要么一起重投，不做部分确认，因为幂等已经保证了重投是安全的。
这么改之后落库从一百五十几涨到单实例中位两千零八十八，三实例三千零二十六。
中间有个很值得讲的插曲：一开始只是改成批量提交，吞吐翻倍但离目标还远，
补上仪表才发现批大小实测只有一点零三——消费线程本来就跟得上，队列里根本没有第二条消息在等，
所以「批量」一直没生效。后来把拉取间隔调上去把批攒起来，批大小才从二点一六变成十二点六八。

可靠性这块，我做了三次故障演练。应用直接 kill -9，收敛时间从一百零二秒降到四十四秒；
缓存主节点宕机两次，丢失的预占是零、超卖是零，代价是一万两千多个 503；
最有意思的是第三次，我故意制造了一个复制空窗——先让从节点睡着、再从主节点上切断复制链路，
让主节点在这个窗口里继续接单然后杀掉它，这样才真的把最后一道防线逼出来。
结果是缓存最多多放了百分之十点三的人，但数据库每一轮都恰好建了三万单、超卖恒为零。
这也是我愿意说「缓存是可丢的准入层、数据库的条件更新才是最后防线」的底气——不是设计上这么写的，
是演练逼出来的。

最后说没做的。写路径的水平扩展上限是库存那一行，三个实例烧掉三倍 CPU 只多落了百分之二十五的单，
提交次数每秒七十到一百一十五，和实例数没关系。这一行我明确没有拆，因为对当前目标场景够用了，
而且我知道怎么拆、也写好了回归条件。另外准入侧的扩展曲线在这台机器上测不出来，
因为压测客户端自己先满了，所以我不会说「水平扩展提升了准入吞吐」。支付是 mock 渠道，
多机房、消息多副本切换、数据库主从切换都没做。

### 6.2 一分钟精简版

本地生活的券营销与交易平台，核心是秒杀到核销这条闭环。难点是一瞬间人远多于货，
所以我把请求分三层拦：进程内的售罄标记、本地令牌桶，最后才是一次缓存脚本把限频、判重、
扣库存、写预占一次做完，只有成功的人才发消息。抢到之后不是同步建单，而是批量消费者一批一个事务，
插入用忽略重复的写法保证幂等，扣减带条件所以超卖不可能发生；崩了有对账器重驱动。
结果是准入拐点从五千到两万、半消息从等于请求数变成零、落库从一百五十几到两千多。
做了三次故障演练，其中复制空窗那次把最后一道防线真的逼了出来：缓存多放了百分之十的人，
但数据库一单都没多建。写路径的上限是库存那一行，我测实了但没拆，原因可以展开讲。

## 八、已知边界

这些在被问到之前主动说，不要等着被挖：

- 单机测得的是这台机器上的拐点和扩展趋势，**不是生产容量**。
- **写路径的水平扩展上限是库存的那一行**：加实例只加 CPU、不加吞吐。已测实、未修。
- **准入侧的扩展曲线是客户端受限的**，不能用它论证水平扩展。
- 支付是 mock 渠道；没有真实资金、对账文件、风控。
- 没做：多机房、消息多副本切换、数据库主从切换、日终对账、多级缓存。
- 商户后台按商户分页是跨八张表的广播归并：结果正确，不扩展（第 08 章）。
- 追踪标识：HTTP 全量覆盖；消息到数据库只接了秒杀链与关单链，批量落库路径的日志行不带（第 11 章）。
- 各章末尾还有各自更细的「已知边界」，那里是真正会被追问的地方。

| 兜底扫描器 | 定时消息没送到时，按截止时间扫出该关的订单的那个定时任务 |
| 支付渠道（mock） | 预下单、按签名回调、乱序重试的模拟渠道 |
| 发券组件 | 五个来源统一汇入的那个发券出口 |
