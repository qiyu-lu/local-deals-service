# 04 秒杀准入漏斗 ★简历重点

## 一、这一章解决什么问题

秒杀的形态是：库存一千，请求三万，其中 99% 注定失败。难点不在于让一千个人成功，而在于**让注定失败的那
99% 尽可能便宜地失败**——最好连一次网络往返都不付。早期版本反过来：每个请求都要先发一条事务半消息、
再进本地事务做准入，结果消息队列上的半消息条数等于请求条数，整个系统被一群必然失败的请求压垮。

所以这一章要解决的是三件事：**把失败尽早挡住**（分层漏斗，每层只放行下一层需要的量）；
**把必须做的判定压成一次原子操作**（限频、活动窗口、判重、扣减、写预占放进同一个脚本，一次往返）；
**只让成功者碰消息队列**（成功一千个就发一千条普通消息，而不是三万条半消息）。

准入的终点是「Redis 里有一条预占」，不是「数据库里有一张订单」。预占之后的批量落库、认领、对账
详见第 05 章；订单从待支付到支付/关单/退款的状态机详见第 06 章。

## 二、涉及的数据

**库存分桶**：一张券的库存不是一个 key，而是被拆成 K 份（K 是 2 的幂、默认 16、最大 1024）。
桶号由**买家**决定——用户 id 对 1024 取模后再取低位，也就是 `userId % K`。每个桶下有五样东西，
它们的 key 都带同一个 hash tag（tag 里只有桶号，**不带券号**），因此在 Redis Cluster 上落在同一个 slot：

- **库存计数**：一个字符串，存的是这个桶分到的那一份库存。K 份加起来等于总库存，彼此相差最多一件
  （前 `总库存 % K` 个桶多一件），所以不会凭空多也不会少。
- **活动元数据**：一个哈希，字段是活动状态（活跃 / 已挂起）、开始时间、结束时间（都是 epoch 秒）。
  这份数据在**每个桶里各存一份**——准入脚本只能读自己 slot 的 key，所以必须冗余 K 份。
- **预占哈希**：一个哈希，字段名是用户 id、值是订单号。它同时是「这个人已经抢过了」的判重依据，
  和「这个订单号归谁」的归属证据（后者第 05 章的消费、补偿、对账都会用）。
- **订单状态哈希**：按订单号一个 key，字段有状态、订单号、用户 id、券 id、失败原因、创建时间、
  更新时间、对账尝试次数。准入写入时状态是「处理中」，并显式去掉过期时间。
- **处理中到期索引**：一个 ZSET，成员是订单号、分数是「该被对账器过问」的时间戳。

**限频窗口**：每个桶下还有两类计数器 key，一类按用户、一类按客户端 IP 的哈希值，key 名里带当前时间窗口
的序号。它们同样带桶的 hash tag，所以也在同一个 slot 里。

**订单号**：本地 Snowflake 生成的 64 位数，布局是「最高位 0 | 41 位毫秒（纪元 2025-01-01Z）| 5 位实例
编号 | 7 位序号 | 10 位用户基因」。低 10 位就是 `userId % 1024`，因此**桶号可以从订单号单独反推**。

**消息**：成功者发一条普通消息，体里是券 id、用户 id、订单号，外加一个链路追踪 id。

## 三、详细流程

### 3.1 领取秒杀令牌

买家在下单之前先调一次领令牌接口，带着登录态，想换一个短期有效、绑定「本人 + 本券」的凭证。
这个请求到返回令牌字符串为止，不碰库存也不产生任何预占。

- 请求经过登录拦截器拿到用户 id，服务按「这个用户的桶」拼出活动元数据的 key，一次批量读取三个字段。
  - 三个字段缺任何一个、或时间字段不是数字，答 503「活动正在初始化」。这说明预热没跑到或桶没写全。
  - 当前时间早于开始时间，答「尚未开始」；状态不是活跃、或当前时间晚于结束时间，答「已结束或暂停」。
- 通过后算出过期时刻（当前秒 + 令牌有效期，默认 10 分钟），令牌体是
  「过期秒 . base64url(HMAC-SHA256(密钥, "用户 id:券 id:过期秒"))」，直接返回给前端。
  - 令牌本身不落 Redis：服务端只要拿着同一个密钥就能重算，**验签是纯本地计算，零网络 IO**。
  - 代价是签出去就撤不回来，最长可能比活动结束多活一个有效期；活动结束的判定由下单链路兜底。

### 3.2 下单准入（主链路）

买家调下单接口，带登录态、券 id、秒杀令牌，想要拿到一个订单号并让这张券的一件库存被记在自己名下。
这个请求到「Redis 里写下一条处理中的预占、并把消息交给 Broker」为止结束，**数据库这时还没有任何一行订单**。

- **L0：网关限流**。反向代理上按登录态的 token 做每 2 r/s、按客户端地址做每 50 r/s 的漏桶
  （突发分别是 2 和 100），超出直接答 429，一个字节都不进应用。
  - 只挂在下单这一个路径上；领令牌和查单走普通转发，不受这个限制。
- **L1：本地售罄标记拦截器**，排在**认证之前**（它的顺序值比登录和续期拦截器都小），只管这条路径的
  POST 请求。
  - 从路径变量里解析券 id，解析不出来就放行（交给后面的参数校验）。
  - 查这个实例内存里这张券的桶标记数组：**只有 K 个桶全被标记为售罄时**才本地拒绝。单个桶空了不能
    挡住别的桶的买家——它们的库存还在。
  - 本地拒绝时直接写回一个业务失败的 JSON（HTTP 200，文案「库存不足」），**不查 token、不读 Redis、
    零网络 IO**。把它放在认证前是有意的：售罄的答复对任何人都一样，不泄露信息；放在认证后就还要
    付登录拦截器的两次 Redis 命令，「售罄后零网络 IO」就做不到了。代价是未登录用户在售罄后看到的是
    「库存不足」而不是 401。
  - 即使全桶标记都在，也**每个探针间隔（默认 1 秒）放一个请求过去**：用一次 CAS 把下次探针时间往后推，
    只有推成功的那一个请求继续往下走。陈旧标记因此最多活一个间隔，不依赖广播必达。
- **认证与令牌校验**。登录拦截器解析 token 拿到用户 id 并续期；控制器随即验签秒杀令牌——
  过期时刻早于当前秒、或重算的签名与来的不一致（用常量时间比较），答 403。
  - 校验用的用户 id 和券 id 来自当前会话和路径，所以冒用他人或他券的令牌必然验不过。
  - 这一层是否强制可配，默认强制。
- **L2：本地令牌桶**，按（券，桶）一个桶，每实例独立。
  - 速率是 `max(每桶下限, 本桶剩余库存 × 系数)`，系数默认 2、下限配置里写的是**按券**的每秒 50，
    实现里除以 K 分摊（至少 1），否则拆成 K 个桶会让打到 Redis 的流量翻 K 倍。容量等于速率，也就是
    一秒的突发量。
  - 「本桶剩余库存」来自上一次脚本的返回值，**零额外开销**；还没见过库存的桶不限流，直接放行。
  - 取不到令牌答 429。它挡掉的是「比剩余库存还多得多」的那部分请求——在秒杀语义里它们本来也抢不到。
- **本地发号**。调发号器要一个订单号。
  - 发号器先取自己持有的实例编号（见 3.4），编号无效直接抛错。
  - 同一毫秒内序号自增，7 位用满（每毫秒 128 个、即每实例 12.8 万/秒）就自旋等到下一毫秒。
  - 时钟回拨 ≤ 5 毫秒就等过去，超过就**拒绝发号**（宁可失败也不签出一个小号）。
  - 算出的毫秒差还要落在一个区间里：下界保证每个新号都 ≥ 2^57，上界保证不溢出符号位。下界的用处是
    与老版本基于 Redis 自增的号段**不相交**——老号全都小于 2^57，迁移来的历史订单号不可能与新号撞车。
  - 发号抛异常（通常是没有实例编号租约）时，整条请求答 503。
- **L3：一次 Lua，一次往返**。服务先算桶号，并且**校验订单号的低位基因与买家一致**，不一致直接抛错
  ——否则这个订单的状态 key 会落到另一个桶、另一个 slot，之后按订单号谁也查不回来。
  然后把七个 key（库存、活动元数据、预占、订单状态、到期索引、用户限频前缀、IP 限频前缀）和七个参数
  （用户 id、券 id、订单号字符串、到期秒数、窗口毫秒、用户配额、IP 配额）交给脚本。脚本的顺序是：
  - **参数自检**：到期秒数 ≤ 0、窗口小于 1 秒、配额为负，返回「元数据不可用」。
  - **取 Redis 服务器时间**，之后所有时间判断都用它——所有应用实例共享同一个时钟，不受各自机器时间影响。
  - **限频**：用服务器时间除以窗口长度得到窗口序号，拼出本用户、本 IP 的计数 key。
    默认窗口 1 秒、每用户 2 次、每 IP 100 次（配额为 0 表示这一维关闭）。
    先读两个计数，任何一个已达上限就返回对应的限频码，**并且不递增任何计数**——被拒的请求不占别人的
    名额；都没到上限才各自自增一次，并把过期时间设成「两个窗口 + 1 秒」，让上一窗口的计数自己消失。
    IP 是先在 Java 侧做 SHA-256 再拼进 key 的，Redis 里不存明文地址。
  - **活动窗口**：批量读元数据的三个字段。缺字段、时间不是数字、开始晚于结束，返回「元数据不可用」
    （答 503，因为这是服务端没准备好，不是用户的错）；状态不是活跃返回「已结束或暂停」；
    时间早于开始返回「尚未开始」；晚于结束返回「已结束」。
  - **库存**：读本桶库存，不存在或 ≤ 0 返回「库存不足」，并把剩余库存报成 0。
  - **判重**：预占哈希里已经有这个用户的字段就返回「重复购买」。因为桶是按用户切的，同一个用户永远落
    同一个桶，**判重天然只需要看一个 key，不用跨桶**。
  - **订单号占用**：这个订单号的状态 key 已经存在就返回「订单号已被占用」，**不动库存、预占和订单状态**
    （此前递增的限频计数除外——脚本只对通过了限频的请求记这一次）。
    正常情况下不可能发生；只有两个实例短暂共用同一个实例编号（租约异常）时才会。
  - 以上全过，才开始写：库存自减一、预占哈希里写下「用户 → 订单号」、订单状态哈希写成「处理中」
    并填齐字段、显式去掉状态 key 的过期时间（处理中的状态不能在库存和预占还在的时候先消失）、
    把订单号按「当前时间 + 到期秒数」（默认 2 分钟）加进本桶的到期索引。
  - 返回「结果码 + 剩余库存」。剩余库存在没读库存的分支里是 -1。
- **脚本调用失败的处理**。脚本本身是原子的，但**回包可能在脚本已经跑完之后丢掉**。这时 Java 不能直接
  判失败：它按订单号去读状态哈希，如果存在、且订单号/用户/券三者都对得上、状态是处理中或已成功，
  就认定这次请求其实已经被准入，按成功继续（剩余库存记为未知）。否则才答 503。
- **订单号冲突的重试**。拿到「订单号已被占用」时，重新发一个号、**再调一次脚本**。第二次仍然冲突
  就答 503 并打错误日志。因为第一次脚本没有动库存、预占和订单状态，重试不会重复扣减；代价是这个用户
  在本窗口里多花了一次限频配额。
- **回填两个本地层**。拿到剩余库存后：
  - 喂给 L2，更新这个（券，桶）的令牌桶速率；
  - 更新 L1 标记：结果是「库存不足」、或者「成功且剩余为 0」时，标记本桶售罄；
    反过来，成功且本桶此前被标记过，说明这次请求就是那个探针、而且实际上还有货，于是清除标记。
- **只有成功者发消息**。成功分支发一条**普通**消息（同步发送），Broker 没有确认存下就抛错。
  - 发送失败**只记日志和指标，不影响答复**：预占已经在 Redis 里了，它本身就是 outbox；
    消息丢了这单会停在处理中，由对账器重投（详见第 05 章）。
  - 返回给客户端的是订单号字符串，前端拿它去轮询下单结果。
- **其余分支的答复**：库存不足 / 重复购买 / 未开始 / 已结束都是业务失败（HTTP 200 + 失败码），
  限频是 429，元数据没准备好和其他意外是 503。每个分支都各自打一个计数器。

### 3.3 售罄标记的广播与自愈

这条链路没有外部请求触发，它跟在 3.2 的结果后面跑，目的是让一个实例学到的「某桶空了」尽快让所有实例知道。

- 某实例第一次把某个（券，桶）标记为售罄时，往一个 Redis 频道广播一条「+券号:桶号」；
  其他实例收到后设置自己的本地标记。
- 库存回到某个桶的三个地方都会广播「-券号:桶号」并清本地标记：
  - 消费侧发现数据库库存不足等原因做首次补偿、把一件库存还回本桶时；
  - 订单关闭或退款成功，把一件库存还回买家自己的桶时（先在事务里加数据库库存，提交后再动 Redis）；
  - 3.2 里探针请求发现「其实还有货」时。
- 广播是 fire-and-forget：发送失败只记日志；不同实例的消息可能交错；订阅者收到格式不合法的消息就忽略。
  **正确性不依赖它**——每个实例的标记只影响自己的本地拒绝，而全桶标记下每秒仍有一个探针会去 Redis
  问真话，所以陈旧标记最多存活一个探针间隔。
- 本地标记是「每张券一个布尔数组 + 一个下次探针时刻」，全部桶都清掉时整张券的条目从表里移除。

### 3.4 实例编号租约与发号器的自我栅栏

应用启动时要先拿到一个 5 位的实例编号才能发号，这条链路一直活到进程退出。

- 启动时尝试从 0 到 31 逐个抢：对编号 key 做带过期时间的 `SET NX`，值是本进程随机生成的 token，
  过期时间默认 30 秒。抢到就记下编号；32 个槽都被占就打错误日志，在抢到之前下单接口一律 503——
  续期调度每 ttl/3 还会再试一次抢占。
- 之后每 ttl/3（默认 10 秒）续一次：用一个小 Lua **比对 token 相同才续期**，避免续到别人的槽上。
  - 续期返回不是成功，说明租约已经被别人接手：把本地编号作废，立刻重新走一遍抢占。
  - 续期时 Redis 抛异常（网络问题）**不放弃槽位**，由下面的本地栅栏决定什么时候停。
- **本地栅栏**是这套方案的关键：每次续期成功时记下「有效到 = 发起续期的时刻 + ttl − ttl/6」，
  也就是只信任 ttl 的 5/6。发号前先检查本地时钟是否已过这个时刻，过了就抛错。
  于是在续期失败的那段时间里，**Redis 还没让出这个槽，本实例就已经不再发号了**，接手者与本实例不会重叠。
- 进程正常退出时再用一个「token 相同才删」的小 Lua 主动释放，删不掉也无所谓——它自己会过期。

## 四、口述版

**（1）领令牌。** 买家在下单前先来领一个秒杀令牌。登录拦截器给我用户 id，我按这个用户所属的桶去读活动
元数据，看状态是不是活跃、当前时间在不在起止区间里；没到点或者已经结束就直接告诉他，元数据读不出来
就答服务暂不可用，因为那说明预热没做好，不是用户的问题。都通过了，我算一个过期时刻，用一个服务端密钥
对「用户 id、券 id、过期时刻」做 HMAC，把过期时刻和签名拼成一个字符串给他。这个令牌不存 Redis，
因为存了就要在下单时再读一次——而下单时我只要用同一个密钥重算一遍签名就能验，是纯本地计算，不花一次
网络往返；它又绑死了用户和券，所以别人的令牌、别的券的令牌都用不了，活动开始前也根本签不出来。

**（2）下单准入。** 请求先撞到反向代理上的限流，按 token 和按客户端地址各一个速率，脚本刷单在这里就被
429 掉了，一个字节都不进应用。进了应用，第一个拦截器是本地售罄标记，它排在认证**前面**，因为售罄的
答复对谁都一样、不需要知道你是谁，放在认证后面就还得先花两次 Redis 命令去读登录态，那「售罄之后零网络
IO」这句话就不成立了。这个标记是按桶记的：一张券被拆成了 K 个桶，只有 K 个桶全都标记为空我才敢在本地
答库存不足，因为单个桶空了不代表别的桶的买家买不到。即使全空了我也每秒放一个请求去 Redis 探一下，
用一次 CAS 决定谁是那个探针，这样万一标记是陈旧的——比如库存被退款还回来了而广播丢了——最多一秒就自己
好了，我不依赖广播必达。

过了这一层才认证，拿到用户 id，然后验秒杀令牌，签名对不上或过期了就 403。接着是本地令牌桶，速率跟着
「这个桶上一次报回来的剩余库存乘以一个系数」走，剩几件就大概放几倍的人进去，其余的直接 429——他们本来
也抢不到，没必要去挤 Redis。这个剩余库存是白来的，就是上一次脚本的返回值。

然后我在本地发一个订单号，用 Snowflake：毫秒、实例编号、序号，**最低十位放用户 id 对 1024 取模的基因**。
放基因有两个用处，一是订单表按用户分片，按订单号查也能单分片命中；二是桶号可以从订单号单独反推出来，
而查单接口手里只有订单号，没有用户也没有券。发号是纯本地位运算，失败者也只多花这一点点。实例编号是从
Redis 抢的一个租约，32 个槽，定期续期，并且我给自己加了一道本地栅栏：只信任租约有效期的五分之六，
过了这个时间就算 Redis 那边还没过期我也停止发号，这样续不上的时候接手的实例不会和我用同一个编号。

再往下就是那一次 Lua 了。我把这个桶的库存、活动元数据、预占哈希、订单状态、到期索引和两个限频计数一起
交给一个脚本，它们的 key 都带同一个 hash tag，所以在集群上是同一个 slot，一次往返就能做完。脚本里先取
Redis 自己的时间，因为多个实例的本地时钟不一定一致；然后按窗口查每用户和每 IP 的计数，**只有通过的请求
才给计数加一**，被拒的不占别人的名额；再查活动状态和起止时间；再看库存；再看预占哈希里有没有这个用户，
有就是重复购买——因为桶是按用户切的，同一个人永远落同一个桶，判重不需要跨桶，天然是原子的；最后还看一眼
这个订单号的状态 key 存不存在，存在就不动库存、预占和状态，只返回一个特殊码，让 Java 换个号重来，这是防两个实例
短暂共用实例编号的最后一道闸。全过了才开始写：库存减一、预占里记下这个人的订单号、写一条处理中的订单
状态并显式去掉过期时间、把订单号按到期时间放进本桶的处理中索引。这些必须在一个脚本里，因为「查到有库存」
和「扣掉库存并记下是谁」之间不能被另一个请求插进来，否则就超卖。脚本最后把剩余库存一起返回，我拿它去
更新本地令牌桶的速率和售罄标记。

成功之后我才发消息，而且是一条**普通**消息，不是事务半消息。以前的做法是每个请求先发半消息再做准入，
于是 Broker 上的半消息条数等于请求条数，99% 都是注定失败的。现在预占本身就是 outbox：如果消息没发出去，
或者我刚写完预占就被杀掉，Redis 里会留下一条没有订单的处理中预占，对账器扫到它会重投这条消息，所以
发送失败我只记一条日志，照样把订单号返回给用户——后面的落库和对账详见第 05 章。还有一种情况是脚本跑完了
但回包丢了，这时我不能直接算失败，我会按订单号去读那条状态，如果它确实存在、归属也对，就当这次是成功的。

**（3）售罄广播。** 某个实例第一次发现某张券的某个桶空了，就往一个 Redis 频道广播一条「加上这个桶」，
别的实例收到就设自己的标记；库存回到桶里的三个地方——补偿、关单释放、退款释放——广播「去掉这个桶」。
这只是加速手段，丢了也没关系，因为每个实例每秒都有一个探针会去 Redis 问真话。

## 五、为什么这么设计 / 会被怎么追问

**为什么不用事务消息？** 事务消息要解决的是「本地事务成功了但消息没发出去」，但它只覆盖半消息与
提交之间那一小段。我的准入成功点在 Redis 脚本里，在「脚本成功」到「半消息发出」之间崩溃，同样会留下
一条没有消息的预占——所以事务消息**并不能省掉重投**，只是在每个成功者身上多付一次半消息加一次提交，
还要在每个失败者身上也付一次。既然重投必须有，不如让预占直接当 outbox，成功者发一条普通消息就够了。
正式复测里半消息从「等于请求数」变成 0。

**为什么把判重、扣减、写预占塞进一个脚本，而不是分几次命令？** 检查和写入之间不能有别人插进来，
否则要么超卖、要么一个人抢到两件。分成多次命令就得引入分布式锁或者 WATCH 重试，前者更慢、后者在高冲突
下几乎必然重试。Lua 在 Redis 里是单线程串行执行的，天然就是这个原子区间；顺便把十几条命令压成了一次往返。

**为什么桶按用户切而不是按请求随机切？** 按用户切换来两个性质：同一个人永远落同一个桶，所以**判重只看
一个 key**，一次脚本就能完成；再加上订单号低位带了用户基因，**桶可以从订单号反推**，查单接口只有订单号
也能找到状态。按请求随机切的话，判重要扫 K 个桶，查单要扫 K 个 slot。

**hash tag 里为什么不带券号？** 带券号的话任何一个 key 都必须先知道券号才能拼出来，而按订单号查状态时
手里没有券号。至于热点分散，秒杀期间热的本来就是一张券，它的 K 个桶已经散在 K 个 slot 上了，带不带
券号没有区别。代价是不同券的同号桶会落在同一个 slot，多张券同时热时负载略不均——认了，写在边界里。

**某个桶空了、别的桶还有货，这个买家怎么办？** 现在的实现是「不借库存」：他的桶空了就是库存不足。
借库存要两步——扣邻桶、写回本桶预占——两步之间崩溃要靠幂等 token 串联加对账器归还，复杂度不小。
复测里每一档 `accepted` 都精确等于库存，**尾部浪费实测 0**，因为秒杀场景下需求远大于库存，每个桶都会
被买空；浪费只在「需求和库存量级相当且分布不均」时才出现，那是日常领券不是秒杀。真到那天，正确做法
多半是直接调小 K。

**本地令牌桶是每实例的，多实例不就放行 N 倍了吗？** 是的，而且是有意的。L2 只防洪峰、不做精确配额；
**精确判定永远在那一次 Lua 里**，超卖是由「读库存和扣库存在同一个原子区间」保证的，不是由限流保证的。
同理，一部分「还有库存时」的请求会被答 429，在秒杀语义里他们本来也抢不到。

**这些数字怎么样？** 准入拐点（p99 < 100 ms 且丢弃 < 1% 的最高档）从 5k 抬到 20k req/s，天花板从
13.2k 到 ≥26.2k；10k 档 p99 从 128 ms 降到 33 ms、应用 CPU 从 3.04 核降到 0.60 核；半消息从等于请求数
变成 0。集群化之后准入无回退：10k 档 −0.1%、20k 档 −1.7%，代价是 p99 +28~45 ms。多实例那一场
1/2/3 个实例在 30k 档都是 ~25.5k req/s——**那是压测客户端的天花板不是系统的**，因为 M3 之后一次准入
几乎不花钱，客户端先被打满了。

**压测时限流是怎么处理的？** 必须声明的配置偏离：每 IP 限流被调到 10 万，因为所有压测请求都来自
127.0.0.1，默认配额会让 99% 的请求在最外层就 429，测到的将只是限流器本身；每用户限流保持默认，靠
10 万个预生成 token 轮转避免同一个用户撞进自己的窗口。多实例那一场的反向代理**不开**边缘限流，同一个理由。

**Redis 主节点挂了会怎样？** 理论上异步复制会丢掉尚未复制的预占和扣减，切换后 Redis 的库存比真相多；
兜底在数据库侧的条件更新（扣库存时带 `stock >= n`），超放的请求会在落库阶段失败并走补偿，对用户可见地
失败。但**主节点宕机的那场演练没有复现这个场景**：丢失预占 0、库存差 0、超卖 0，转移 5.2/7.8 s，
代价约 1.26 万个 503（42% 请求）——因为转移期间那些 slot 直接不可写，买家收到的是 503 而不是假的成功。
要逼出数据库那道防线，得先人为制造复制空窗（让副本睡着再切断链路）再杀主：那四轮里 Redis 最多多放了
10.3%（33104 vs 30000），**MySQL 每一轮都恰好建了 30000 单、超卖恒为 0**，其中一轮是被条件更新拒批
337 次挡下的，另外几轮是预占随主节点一起死、消费者认领时发现状态不在。

## 六、已知边界

- **尾部浪费**：不借库存，买家的桶空了就买不到，尽管整券还有库存。K 越大越明显。复测里实测 0，
  但那是因为需求远大于库存；日常领券场景下这个洞是真的。
- **两个本地层都是每实例的**：N 个实例时 L2 的总放行量是 N × 剩余库存 × 系数；L1 的探针也是每实例每秒
  一个。这是有意的，但不要说成「精确配额」。
- **陈旧的售罄标记**：广播会丢、不同实例的消息会交错，所以标记最长可能陈旧一个探针间隔（默认 1 秒）。
- **令牌撤不回来**：令牌是无状态签名，不落 Redis，所以活动被挂起后已经签出的令牌仍然验得过；
  真正拦住它的是下单脚本里的活动状态检查。
- **活动元数据冗余 K 份**：写入点有三处（发券预热、启动补齐、挂起券），都要写 K 份。
  活动窗口不高频变化时这份静态冗余没问题；如果将来要频繁改窗口，这里要重新考虑。
- **不同券的同号桶共用一个 slot**：多张券同时热时负载会略不均。
- **实例编号只有 32 个**：超过 32 个实例就抢不到租约，下单接口会 503。当前规模下够用。
- **Redis 异步复制会丢预占**：主节点宕机后 Redis 库存可能比真相多，靠数据库条件更新兜底。直接杀主的演练
  里丢失预占实测为 0（转移期间 slot 不可写），要先制造复制空窗才会发生；空窗演练里数据库条件更新确实
  拒批过，超卖仍为 0。
- **下单接口对未登录用户的行为不一致**：售罄后本地拦截器直接答「库存不足」，而不是 401。
- **准入侧的真实天花板没被测到**：单实例和多实例两场都是压测客户端先满，要继续上探得换多机压测。
