# 07 券资产：统一发券、到店核销与过期 ★简历重点

## 一、这一章解决什么问题

平台上的券有两个来源：用户花钱买的（秒杀下单、支付成功）和营销发的（领取、后台发放、签到奖励、批量发放）。
如果这两条路各自造一张表，那么「我的券包」要查两张表、到店核销要认两种码、有效期要写两套逻辑，
后面每加一个发放入口都要再改一遍核销。所以这一章只做一件事：**把「券」这个资产收敛成一张表**，
两个来源都只负责产出一条券资产记录，核销、过期、退款冻结全都只认这张表。

难点有三个。第一，发券必须幂等——支付回调会重投、发放接口会重试，一个来源最多只能出一张券。
第二，核销是「钱已经花出去、东西要交付」的那一刻，必须只能成功一次，而且要和退款互斥。
第三，核销码是拿在用户手机上、在门店被人肉输入的秘密，必须既防猜、又防商户后台被拿去批量枚举。

## 二、涉及的数据

**券资产表**（本章的主角，按用户 id 分片，2 个库 × 4 张表共 8 片）

- 券号：确定性字符串，购买券是 `P` 加订单号、发放券是 `G` 加发放流水 id；表上有唯一键。
  这个字段本身就是发券的幂等键，不需要额外发号服务。购买券的订单号里嵌了用户 id 的基因，
  所以按券号查能直接路由到单片；发放券的 id 没有基因，按券号查会广播（详见第 06 章讲分片的部分）。
- 用户 id：分片键。表上**所有**语句都必须带它，否则会变成八片广播。
- 券模板 id、商户 id、门店 id：发券那一刻快照下来的。门店 id 和券模板 id 来自券模板快照，
  商户 id 来自调用方传进来的那条订单或发放流水（它们自己在创建时已经快照过一次）。
  核销时的数据范围判断只看券上的这个商户 id，不用再回查券模板。
- 来源枚举（购买 / 领取 / 后台发放 / 任务奖励 / 批量发放）与来源引用（订单号或发放流水 id）：
  核销时靠来源枚举判断要不要连带推订单状态机。
- 状态枚举：可用 / 已核销 / 已过期 / 已退款 / 冻结中。冻结中表示它的购买订单正在退款，此期间不许核销。
- 生效时间与失效时间：发券那一刻由数据库时钟算出来，失效时间 = 发券时刻 + 券模板上的有效天数（默认 30 天）。
  **不存「过期与否」这个布尔**，过期是时间的函数，状态字段上的「已过期」只是定时任务追认的结果。
- 核销码：16 位定长随机串，唯一键。
- 核销时间、核销人（后台账号 id）。
- 索引：按（用户 id，状态，主键）、按（状态，失效时间）、按（商户 id，状态，主键）三条。
  过期任务走的是第二条；券包目前只按用户 id 查、按主键倒序取，只用到第一条的最左前缀，
  状态那一列是给「按状态过滤的券包」留的，那个查询还没写（见第六节）。

**券模板表**（不分片）：发券真正用到的只有有效天数和门店 id 两个字段。
因为券资产表分片而它不分片，一条语句不可能同时 JOIN 两边，所以发券时是**先把这几个字段读出来，再用纯 VALUES 插入**。
（读快照的那条查询本身还 JOIN 了门店表，顺带带出门店所属商户和面额——那两个是下单链路用的，发券不用。）

**发放流水表**（营销侧，不分片）：保留下来作为「发放这件事」的记录——幂等键、活动额度扣减都记在它上面；
它不是券资产，券资产是上面那张表。活动与批量 Job 详见第 09 章。

**订单表**：本章只用到它的状态字段，核销时要把购买订单从已支付推到已核销。状态机本身详见第 06 章。

**Redis**：只有一个东西——每商户每分钟一个核销尝试计数器，键里带商户标识和分钟序号，自然分桶。
平台级账号不属于任何商户，它们共用一个固定标识的桶（见第六节）。

## 三、详细流程

### 3.1 发券：两个来源汇到一个出口

购买与营销发放两条路都调用同一个发券组件，并且都**在调用方自己的事务里**执行，
这样「订单变成已支付」或「发放流水写入」和「券产出」要么一起提交、要么一起回滚。
这一步以券资产行写入并返回给调用方为止。

● 发券组件按来源拼出券号。购买券是 `P` 加订单号，发放券是 `G` 加发放流水 id。
  ○ 两者都是**确定性**的：同一个来源无论被调用几次，算出来的券号都一样。幂等靠券号上的唯一键兜底，
    不靠调用方自己去查一遍再写（查再写有竞态）。
● 发券组件先按券模板 id 读一次券模板快照，发券要用的是里面的门店 id 和有效天数
  （券上的商户 id 不取自这里，取自调用方传进来的订单或发放流水）。
  ○ 读不到（券模板被删了或它的门店没了）直接抛异常，让整个调用方事务回滚——宁可让支付回调重投，
    也不能产出一张没有有效期的券。
● 然后进入最多 3 次的插入循环。
  ○ 每次循环先抽一个新的核销码，再执行插入：状态写死为「可用」，生效时间取数据库的当前时间，
    失效时间取当前时间加上快照里的有效天数。时间全部走**数据库时钟**，应用实例之间的时钟漂移不参与。
  ○ 插入成功就按券号回读整行返回。
  ○ 插入撞唯一键时，先按券号回查：查得到，说明是**同一个来源重复发券**，直接把已有的那张返回，
    这就是幂等路径；查不到，说明撞的是核销码那个唯一键，也就是随机码碰撞，循环重抽一个再试。
  ○ 3 次都撞核销码则抛异常。80 位随机能连撞三次基本只说明随机源坏了，这时候失败比继续重试更安全。
● 购买这一侧的入口是支付回调：订单状态机把订单从待支付推到已支付、CAS 成功之后，才在同一事务里发券。
  ○ 重投的回调其实走不到发券这一步：支付单状态已经不是待确认了就直接按「重复通知」返回，
    就算越过它，订单那次 CAS 也会失败。券号上的唯一键是最后一道兜底，不是主路径。
  CAS 失败说明这单已经被超时关单或被另一笔支付抢走了，那就不发券，改走自动退款。详见第 06 章。
● 营销这一侧的入口是发放事务：活动行加锁、额度自增、发放流水写入、发券通知 Outbox 写入之后，
  最后一步才是发券。领取、后台发放、签到奖励、批量发放四个入口都收敛到这一个事务方法，
  所以发券逻辑只有一处。活动规则校验与批量 Job 详见第 09 章。

### 3.2 到店核销：一次 POST，两处 CAS

门店店员在后台输入（或扫）用户出示的核销码，希望把这张券消费掉。
这个请求到券资产行变成「已核销」并返回整张券为止。

● 请求先过后台鉴权：要有核销权限，并且当前登录主体带着自己的商户 id（平台账号则是全局范围）。
● 进入接口方法后，**先过限频再进业务**。
  ○ 限频按「商户 + 当前分钟」拼一个计数键（平台级账号没有商户，用一个固定标识，所有平台账号共用一个桶），
    用一个 Lua 脚本做自增：脚本里先自增，发现结果是 1
    （说明这个分钟桶刚建）就顺手给它设 120 秒过期。自增和设过期必须在一个脚本里，
    否则两条命令之间进程挂掉会留下一个永不过期的计数键。
  ○ 脚本返回本分钟内累计的尝试次数（含本次），超过每分钟上限就抛 429，上限是配置项、默认 120。
    计数键的 120 秒过期是写死的，和这个上限没有关系。
  ○ Redis 抛异常时**放行**（fail open），只打一条告警日志。这是个明确的取舍：限频挡的是枚举攻击，
    而 Redis 抖一下就让所有门店没法给顾客核销，代价更大。
● 业务层先把输入去空白、转大写，再用 16 位定长格式正则过一遍。格式不合就当作「查不到」处理，不去查库。
● 格式合法则按核销码查券资产表。核销码是纯随机的、不带任何路由信息，所以这条查询是**八片广播**。
  广播在这里是可接受的：门店核销是低频操作，而且每片都走核销码上的唯一索引，各自只回一行。
● 拿到券之后做归属判断：券不存在，或者（非平台账号时）券上的商户 id 和当前登录主体的商户 id 不一致，
  **抛同一个「券码无效」的 404**。
  ○ 这点是故意的：如果「别人商户的码」和「不存在的码」返回不同的错，商户就能拿自己的后台当预言机，
    把整个码空间扫一遍、判断哪些码是别家的真券。两种情况答案必须一模一样。
● 如果这张券的来源是「购买」，先推订单状态机：订单从已支付到已核销，是一条带源状态的条件更新。
  ○ 条件更新影响行数为 0，说明订单不在已支付态（已经被核销过、或正在退款、或已退款）。
    这时重读券状态并按它抛出对应的冲突错误。
  ○ 这里**先锁订单行再动券行**，和退款的加锁顺序完全一致，所以核销与退款只会互相排队、不会死锁。
● 然后是核销本身：一条条件更新，条件是主键 + 用户 id（必须带，否则八片都会上行锁）+ 状态仍是「可用」
  + 当前时间落在生效时间与失效时间之间。
  ○ 影响行数为 1 表示核销成功，同时写下核销时间和核销人，然后按主键 + 用户 id 回读整行返回。
  ○ 影响行数为 0 就抛异常，让**整个事务回滚**——包括上一步已经推过去的订单状态。
    也就是说订单变「已核销」和券变「已核销」是原子的，不会出现订单已核销但券还可用。
● 失败时的重读用的是**加锁读**（`FOR UPDATE`），不是普通读。
  ○ 原因：本事务运行在可重复读下，普通读看到的是事务开始时的快照，那里券还是「可用」，
    于是会把「刚刚被另一个店员核销掉」误报成「券已过期」。加锁读看的是最新已提交版本。
  ○ 重读到「已核销」报 409 券已核销；读到「已过期」或仍是「可用」（说明条件更新是被时间窗口挡的）
    都报 409 券已过期；读到「冻结中」或「已退款」报 409 券正在退款或已退款。
● 返回给前端的是整张券。审计切面在这之后记录一行：记券号，**不记核销码**。

### 3.3 过期：定时任务追认

券的「过期」本质上是失效时间小于当前时间，核销那条条件更新已经自带时间窗口判断，
所以即使定时任务完全不跑，过期券也核销不掉。定时任务只是把状态字段追认成「已过期」，
让券包和商户侧的按状态查询能走索引、不必每行算时间。

● 任务默认开启（可配置关掉），启动后延迟 30 秒开始，之后每轮结束 60 秒再跑下一轮（固定延迟，不是固定频率）。
● 每轮最多做 20 批，每批 500 条。某一批**实际改动的行数**不到 500 就结束本轮——通常意味着扫干净了
  （但 CAS 落空也会让行数变少，见第六节）。
  ○ 也就是一轮最多推进 10000 张券，给单轮设上限是为了任务不会在积压时占着连接不放。
● 每批先做一次查询：捞状态仍为「可用」且失效时间已过的券，按失效时间排序取前 500，
  只取主键和用户 id 两列。
  ○ 这条查询是广播 + 归并的，走的是（状态，失效时间）索引。
  ○ 为什么不直接写一条 `UPDATE ... LIMIT 500`：分片中间件会拒绝路由到多个节点的带 LIMIT 的更新，
    因为那个 LIMIT 会**在每个节点上各生效一次**，语义就不是「总共 500 条」了。
    先查再更新还有一个好处——读出来的每一行都带着自己的用户 id，也就是分片键。
● 然后逐行执行条件更新：主键 + 用户 id + 状态仍是「可用」+ 失效时间已过 → 置为「已过期」。
  ○ 状态本身就是 CAS 条件，所以这一步天然幂等：另一个实例刚好也在扫、或者上一轮跑到一半挂掉，
    重复执行只会影响 0 行，不会把已核销的券误伤成已过期。
  ○ 一批的这些更新在同一个事务里提交。

### 3.4 退款与核销互斥

退款的状态机主干在第 06 章，这里只讲它在券资产上留下的三步。

● 用户申请退款时，退款流程**先对订单行做加锁读**，确认是本人的、且处于已支付态，
  然后把订单从已支付推到退款中。
  ○ 加锁顺序和核销一致：订单行在前、券行在后。两边谁先提交，另一边的条件更新就失败，
    不会形成循环等待。
● 同一事务里紧接着冻结券：按券号把券从「可用」改成「冻结中」；如果影响行数是 0，
  再试一次把「已过期」改成「冻结中」。
  ○ 允许已过期的券进入退款，是业务选择：券过期没用掉，钱应该能退。
  ○ 两次都改不动（券已经是「已核销」了）就抛 409，**整个事务回滚，订单退回已支付**。
    这就是互斥的另一半：核销赢了，退款申请不下去。
  ○ 这条更新按券号定位，购买券的券号里带订单号基因，所以能路由到单片，不是广播。
● 渠道确认退款成功的回调里，订单从退款中推到已退款，然后把券从「冻结中」改成「已退款」，
  并把库存单位归还（和超时关单共用同一条归还路径）。

## 四、口述版

### 4.1 发券

我们平台上的券有两个来源，一个是用户秒杀下单付钱买的，一个是营销活动发的，
但我只做了一张券资产表，两个来源最后都汇到同一个发券组件上，这样核销、过期、退款这些下游逻辑只有一份。

发券这一步永远是在调用方自己的事务里跑的，因为券必须和产生它的那件事同生共死：
支付回调那边是订单 CAS 成功地从待支付变成已支付之后、在同一个事务里发券，
营销那边是活动额度扣减、发放流水写入之后、在同一个事务里发券。
如果发券失败了，订单那次状态流转或者那条发放流水也要一起回滚，宁可让上游重试，不能出现钱收了券没出。

幂等我没有用「先查再插」，而是用确定性券号加唯一键。购买券的券号就是 P 加订单号，发放券就是 G 加发放流水 id，
同一个来源算出来的券号永远一样。所以就算同一个来源被重复调进来，第一次插进去，后面都会撞唯一键，
撞了我就按券号回查、把已经存在的那张券原样返回，对调用方来说就跟成功一样。
实际上支付回调重投一般走不到这里，支付单和订单那两层各自先挡掉了，这条唯一键是最后一道兜底。
这里有个细节，撞唯一键有两种可能，一种是券号撞了，那就是幂等；另一种是核销码撞了，那是随机碰撞，
所以我撞了之后必须回查一次券号才能区分：查得到是幂等，查不到就说明是核销码碰撞，重新抽一个码再试，最多试三次。

还有一点是有效期。券的有效天数是配在券模板上的，而券模板表没有分片、券资产表按用户 id 分了八片，
一条语句不可能既写分片表又去 JOIN 不分片的表，所以我是先把券模板的有效天数和门店读成一个快照，
再用纯 VALUES 插入券资产，生效时间取数据库的当前时间、失效时间就是当前时间加有效天数，
时间全部用数据库时钟，不用应用时钟，因为多实例之间会有漂移。

### 4.2 核销

核销是店员在后台把用户手机上那个码输进来。这个链路我是先限频、再查券、再判归属、再两处 CAS。

限频放在最前面，按商户加当前分钟拼一个计数键，用一个 Lua 脚本自增，脚本里发现自增完是 1
就顺手设过期时间，自增和设过期必须在一个脚本里，不然两条命令中间挂掉会留下一个永不过期的键。
超过每分钟的上限就返回 429，上限是配置出来的，默认一百二十。这里我特意做成 Redis 出问题时放行，因为限频挡的是枚举攻击，
但 Redis 抖一下就让所有门店没法给顾客核销，那个代价更大。

然后是查券。核销码是十六位随机码，完全不带路由信息，所以按码查是八片广播的。
这个我是认的，因为门店核销本身低频，而且每片都走码上的唯一索引，各自只回一行。
查完做归属判断：券不存在，或者这张券的商户不是当前登录的这个商户，我返回的是**同一个**「券码无效」。
这点很关键，如果两种情况返回不同的错，商户就能拿自己的后台当预言机去扫码空间、
判断哪些码是别家的真券，那防枚举就白做了。

判断完才真正核销。如果这张券是买来的，我先推订单状态机，把订单从已支付 CAS 成已核销；
推不动就说明订单已经不在已支付态了，那就重读券状态、按它报错。
推得动再去改券，这条更新的条件是主键加用户 id、加状态还是可用、加当前时间在生效和失效之间。
用户 id 必须带，因为它是分片键，不带的话这条更新会在八张表上都去上锁。
如果这条更新影响行数是 0，我会抛异常让整个事务回滚，连带刚才那次订单状态流转也一起撤销，
所以订单变已核销和券变已核销是原子的。

两个地方值得讲。一个是加锁顺序：核销和退款都是先锁订单行、再动券行，顺序一致所以不会死锁，
只会互相排队，谁先提交谁赢，另一个的条件更新影响 0 行然后报冲突。
另一个是失败之后重读券状态时我用的是加锁读而不是普通读，因为这个事务是可重复读，
普通读会读到事务开始时的快照，那里券还是「可用」，结果就会把「刚被另一个店员核销掉」
误报成「券已过期」——这个是我写测试的时候抓出来的。加锁读能看到最新已提交的版本，才能报对。

### 4.3 过期与退款互斥

过期我是双保险。真正管用的是核销那条更新里自带的时间窗口条件，所以哪怕定时任务一次都不跑，
过期券也核销不掉。定时任务只是把状态追认成「已过期」，让券包和商户侧按状态查的时候能走索引。
任务是固定延迟跑的，每轮最多二十批、每批五百条，某一批实际改动的行数不满五百就结束本轮。
每批是先查后更新，不是一条带 LIMIT 的更新——因为分片中间件会拒绝路由到多节点的带 LIMIT 更新，
那个 LIMIT 会在每个节点各生效一次，语义就变了；而且先查一遍还能把每行的用户 id，也就是分片键，一起读出来。
更新的时候状态本身就是 CAS 条件，所以重复扫、多个实例同时扫都没关系，只会影响零行。

退款这边，用户申请退款时先锁订单行、把订单推到退款中，然后在同一个事务里按券号把券从可用改成冻结中；
改不动就再试一次把已过期改成冻结中，因为券过期没用掉钱是该能退的。
两次都改不动说明券已经被核销了，那就抛冲突、整个事务回滚、订单退回已支付。
这就是核销和退款互斥的另外一半。最后渠道回调确认退款成功，订单推到已退款，券从冻结中改成已退款，
库存单位也归还回去。

## 五、为什么这么设计 / 会被怎么追问

**为什么不让发放流水表本身当券？**
发放流水记的是「发放这件事」——幂等键、活动额度、规则版本、操作人，它天然属于营销域，而且不分片。
券资产记的是「用户手上这个东西」——有效期、核销码、核销人，要按用户查、按用户分片。
两者的生命周期和访问模式都不一样。合成一张表的话，购买券也得塞进发放流水里，
那「活动额度」这种字段对购买券就没有意义了。现在的分工是：发放流水是凭证，券资产是资产。

**追问：发券为什么不用「先查有没有、没有再插」？**
查和插之间有窗口，两个并发的支付回调都查到没有、都去插，结果要么出两张券（没唯一键）、
要么一个报错给上游（有唯一键但不处理）。用确定性券号加唯一键，把并发交给数据库判，
撞了就回查返回已有的那张，上游看到的永远是成功。

**追问：券号撞和核销码撞都是唯一键冲突，你怎么分？**
撞了之后按券号回查一次。查得到就是同一来源重复发券，返回已有的；查不到就说明是核销码随机碰撞，
重抽一个码重试，最多三次。三次都撞我选择抛异常而不是继续重试，因为那时候更可能是随机源坏了。

**追问：核销码为什么是 16 位 Crockford base32？**
字母表 32 个字符正好 5 bit，16 位就是 80 bit 随机，用安全随机源生成。
Crockford 这套字母表去掉了 I、L、O、U，因为这个码是要在门店被念出来、被人肉输进去的，
去掉形近字符能少一大半输错。80 bit 加上每商户每分钟 120 次的限频，硬猜是没有指望的；
限频真正防的其实不是外部暴力破解，是**某个商户后台账号泄漏之后被拿去当枚举工具**。

**追问：限频 Redis 挂了为什么选择放行？**
这是可用性和安全的取舍。核销失败意味着顾客站在柜台前没法用券，是直接的业务中断；
而限频只是纵深防御的一层——就算全部放开，80 bit 随机码也不是能扫出来的，
而且归属判断（别人商户的码一律返回券码无效）那一层还在。所以这里选择 fail open 并打告警。

**追问：按核销码查是全分片广播，不怕吗？**
核销是低频的柜台操作，不是秒杀那种量级；而且核销码上有唯一索引，每一片都是一次索引查找、最多回一行。
如果以后要消掉这次广播，思路是在码里嵌用户分片基因——但那会泄漏「这两张券是不是同一个用户的」，
也会让码更长。现在的量级不值得换。

**追问：核销和退款为什么不会死锁？**
因为两条链路的加锁顺序是同一个：先订单行、后券行。核销是订单已支付→已核销再改券，
退款是订单已支付→退款中再冻结券。两个并发请求会在订单行上排队，先到的把订单从已支付推走，
后到的条件更新影响 0 行，直接报冲突回滚。真正让它们互斥的其实是订单行那一次 CAS，
券上的那次 CAS 是第二道保险（也是发放券唯一的那道，因为发放券没有订单）。

**追问：已经核销失败了，为什么重读要加 `FOR UPDATE`？**
因为这个事务是可重复读，快照是在事务第一条语句时确定的。条件更新看的是最新版本、所以会失败，
但紧接着的普通读看的还是老快照，会读到「可用」，于是错误地走进「过期」那个分支。
加锁读读最新已提交版本，才能区分出到底是被核销了、过期了、还是正在退款。
这个 bug 是写并发测试的时候抓出来的。

**追问：过期任务为什么不直接一条 UPDATE 带 LIMIT？**
分片中间件会拒绝路由到多个节点的带 LIMIT 的更新，因为 LIMIT 会在每个节点各自生效一次，
「总共 500 条」的语义就变成「每片 500 条」了。改成先查主键和用户 id、再逐行条件更新，
既绕过这个限制，也让每条更新都带上分片键、只打一片。代价是一批要发 N 条语句，
但过期是后台任务，不在用户请求路径上。

**追问：过期任务跑挂了、或者多实例重复跑，会怎样？**
不会有正确性问题。每条更新的条件里都带着「状态仍是可用」和「失效时间已过」，
是幂等的 CAS，重复执行影响 0 行；跑到一半挂掉就是留了一些券给下一轮。
而且过期的**判定**根本不依赖这个任务——核销的条件更新自带时间窗口，状态字段只是让查询能走索引。

## 六、已知边界

- **过期的已付订单不会自动退款。** 券会被标成「已过期」，但订单状态机里没有「过期」这一态，
  订单会一直停在已支付。过期券允许发起退款（冻结时接受「已过期」），但「过期自动退」没做。
- **冻结中没有回滚路径。** 退款申请成功之后券就是冻结中，如果渠道那边退款一直不成功，
  只有重试，没有把券从冻结中改回可用的代码。也就是说一次退款申请就永久让这张券不可核销。
- **核销码的唯一键只在单片内生效。** 分片之后唯一约束是每张物理表各自的，
  跨片撞码数据库是拦不住的，靠的是 80 bit 的随机空间。真撞了的话按码查会在两片各返回一行，
  当前代码没有处理这种情况。
- **格式正则比字母表宽。** 入参校验用的是十六位的数字加大写字母，而生成用的字母表去掉了四个形近字母，
  所以一个含 I/L/O/U 的码仍会通过格式校验、白白发起一次广播查询。不影响正确性，是一次可以省掉的查询。
- **过期任务没有分布式互斥。** 多实例部署时每个实例都会跑自己的那一份，靠 CAS 保证不出错，
  但重复的扫描查询是实打实的浪费。目前没有接选主或分布式锁。
- **过期任务判「扫干净了」用的是改动行数，不是捞出来的行数。** 多实例同时扫时，只要一批里有几行的 CAS
  被别的实例抢先改掉，本轮就会提前结束，剩下的积压留给下一轮。正确性没问题，清理会慢一点。
- **平台级账号的核销限频是一个全局桶。** 它不按商户分，所以多个平台账号共享同一份配额；
  结合下面那条「平台账号可以核销任何商户的券」，泄漏一个平台账号的后果比泄漏一个商户账号大。
- **退款成功回调里把券从「冻结中」改成「已退款」那条更新，影响行数没有检查。** 如果券当时不在冻结中，
  退款流水和订单照样推进，券会停在原状态，没有告警。
- **发券组件本身没有声明事务传播。** 「在调用方事务里」靠的是两个调用点自己都开了事务，
  而不是一个 MANDATORY 之类的约束；将来有人从无事务的地方调它，不会报错，只会悄悄丢掉原子性。
- **限频是固定窗口，不是滑动窗口。** 跨窗口边界的一小段时间里最坏可以放过接近两倍的配额（上一分钟末尾用满、下一分钟开头再用满）。
  对枚举防护来说这个精度足够，但要注意别把它说成精确限流。
- **券包接口只返回最近 200 张，且没有分页、没有按状态过滤。** 重度用户的老券看不到。
- **平台级账号可以核销任何商户的券。** 归属判断对平台范围的主体是跳过的，目前只靠后台权限点控制。
- **没有前端。** 用户端的券包页面、管理端的核销页面都没做，接口是齐的。
