# 05 秒杀异步落库：批量消费、认领租约与对账收敛 ★简历重点

## 一、这一章解决什么问题

秒杀的准入已经在 Redis 里把「谁买到了」定下来了（详见第 04 章），但那只是内存里的一条预占记录：
订单还没进数据库，库存也还没从数据库里扣。这一章负责把预占**异步**变成一条真实订单，并且保证
「Redis 里放出去多少个名额，数据库里就恰好建多少单」。

难点有三个。一是**吞吐**：早期每单一次提交、每单一次 `UPDATE ... stock = stock - 1`，全部撞在同一张券的
同一行上，压测火焰图里 44.7% 的时间花在那一行的行锁上、49.5% 在连接池等待，落库只有 264 单/s。
二是**幂等**：消息会重投、进程会被杀，同一个订单号可能被处理两次，不能扣两次库存、也不能建两单。
三是**不丢也不漏**：发消息失败、进程在写完 Redis 之后、发消息之前崩了，预占就成了孤儿——必须有人
定期回来把它变成订单，或者在确认无望之后把名额还回去。

## 二、涉及的数据

只列与本章有关的部分，结构本身的来历见第 04 章。

- **每个库存桶下的四样东西**（一个桶就是一个 Cluster 槽，键上带同一个 hash tag）：剩余库存计数、
  一个记录「谁预占了哪一单」的集合（按用户 id 存订单号）、一个按订单号存状态的哈希、一个按到期时间
  排序的「处理中」索引。
- **订单状态哈希**里与本章有关的字段：状态（处理中 / 成功 / 失败）、订单号、用户 id、券 id（后三个
  一起构成「精确归属」，任何一项对不上都不许动；状态是另一层判断）、创建时间、失败原因、对账尝试次数，以及本章新增的
  两个——**认领者令牌**和**认领到期时间**。终态之后整个哈希被打上 7 天的留存 TTL。
- **处理中索引**是一个有序集合，成员是订单号，分数是「什么时候该被对账器看一眼」。准入写进去时分数是
  「现在 + 2 分钟」的过期判定窗口。
- **订单表**：本章只写入一种行——待支付状态、带一个由数据库时钟算出的支付截止时间、带产生它的
  那次请求的链路 id。用户 id 是分片键（详见第 08 章）。还有一张**状态流水表**，每建一单写一行创建审计。
- **券的秒杀库存表**：一张券一行，本章唯一要动的就是那一行的剩余库存。
- **消息**：订单主题上的一条普通消息，内容只有券 id、用户 id、订单号和链路 id。**没有事务消息、
  没有半消息**——Redis 里那条处理中的预占本身就是发件箱。

## 三、详细流程

### 3.1 批量消费一批消息：认领 → 落库 → 收尾

消费者从订单主题上取一批消息，希望把这一批变成数据库里的订单行并把 Redis 状态推到「成功」。
一次调用要么整批确认，要么整批重投。

- **消费者自己持有一个推模式消费者实例**，而不是用框架的监听器注解。
  - 框架的监听容器把一批消息**逐条**喂给监听方法，所以只把「一次消费几条」调大，不会让任何一段工作
    真的变成批量；自己持有消费者才能把整批交给批处理器。
  - 启动参数是一组：一次消费最多 256 条、消费线程数 4（不超过数据库连接池，线程不会在等连接）、
    一次拉取 256 条（拉取批小于消费批时自动抬到消费批，否则批永远填不满）、**两次拉取之间等 50 ms**。
  - 没有位点时从最早的位点开始消费，而不是默认的最新位点：全新部署如果在主题还没建出来时就接了单，
    默认行为会跳过最早那几条。已有位点仍然以位点为准。
  - 消息体解析不了的，占位成一个空元素带下去，由批处理器计数并**直接丢弃**——重投只会让它更晚进死信队列。
- **第一步：一次 Redis 往返认领整批。**
  - 先把字段不全的消息剔掉（丢弃并计数），再按**用户所在的桶**把这一批拆开：一个脚本只能读自己槽里的键，
    所以每个桶一次往返；整批来自同一个桶时就是一次往返。返回结果按原下标拼回去。
  - 脚本对每条消息做与单条路径完全相同的归属校验（状态哈希里的订单号/用户/券三项必须与消息一致，
    且预占集合里这个用户对应的正是这个订单号），并对可以落库的那些写入认领者令牌和「现在 + 30 秒」的
    认领到期时间，同时把处理中索引里的到期分数推后一个租约。
  - 每条消息一个决策：可落库 / 已成功（幂等确认）/ 已失败（已补偿，确认）/ 归属不符（毒消息）/
    状态缺失（重试）/ 别人持有未过期的租约（稍后再来）。后三种让整批需要重投。
  - 推后到期分数时用了两个修饰：**只更新已存在的成员**，这样一条迟到的认领不会把已经收尾的订单重新
    放回到期索引；**只允许把分数改大**，这样一个比过期判定窗口短的租约不会把到期时间往前拉、
    反而给对账器送去一堆它只能拒绝的订单。
  - 认领者令牌是**每个 JVM 一个**的随机串，所以同一个进程重投自己的批次时是可重入的（直接续租），
    而进程崩掉之后它的租约只会自然过期。
- **第二步：按券分组，每组一个事务。**
  - 同一批里可能有多张券的订单，按券 id 分组；一组就是一次「一条插入 + 一次扣减」。
  - 先按券 id 读一次快照（价格、店铺、商户）。订单表是分片的、券表不是，没法在插入语句里 join，
    所以每券每批读一次，把快照写进行里。
  - 一条**多值 `INSERT IGNORE`** 插入整组订单行。`IGNORE` 让一条重投的消息变成空操作而不是让整批失败；
    分片中间件把这些行分发到各自用户所属的表里，再把影响行数加起来。
  - **实际插入行数 ≠ 组内消息数**就整组回滚并退化（见 3.2）：`IGNORE` 只告诉我们插了几行、
    不告诉我们是哪几行被忽略，而下一步扣库存必须用精确的 n。
  - 然后**一次** `stock = stock - n WHERE stock >= n`，只落在这张券的那一行上。影响行数不是 1 就退化——
    库存撑不住这一批，绝不允许把那一行扣成负数。这一步是整个优化的核心：把「每单一次行锁」
    变成「每批每券一次行锁」。
  - 最后一条语句批量写入创建审计行。
- **第三步：一次 Redis 往返收尾。**
  - 同样按桶拆分，每桶一次往返。每条消息做的事等于单条版的「置成功」再加上释放认领：
    校验预占与精确归属 → 状态由处理中改成成功、清掉失败原因与两个认领字段 → 从处理中索引里移除 →
    给状态哈希打上 7 天留存 TTL。已经是成功的走幂等分支，只做清理。
  - 脚本对每条消息返回是否收尾成功。收尾不成功的记错误日志并让整批重投。
  - 收尾成功的订单才做两件对外的事：**异步**发一条延迟的关单定时消息（同步发会在消费线程上每单多一次
    Broker 往返，那正是批量化之后剩下的开销；发失败由兜底扫描补，详见第 06 章），以及把整批的
    通知用一次管道批量发布出去（每单三条：买家的「你抢到了」、平台后台、这张券所属商户的后台）。
    通知里的商户 id 走实例内缓存，不再每单补查一次数据库。
- **返回值：只有整批全部办完才确认。**
  - 只要还有一条需要重投，整批 `RECONSUME_LATER`。重投是安全的——认领、`INSERT IGNORE`、置成功
    三步都幂等——代价是同批已完成的消息会再走一遍前两步（第二遍会在认领阶段被判为「已成功」直接跳过）。
  - 之所以不做部分确认：确认下标只能确认一个**前缀**，而一批里完成情况是乱序的。

### 3.2 快路径退化为逐条

批量事务一旦发现自己的前提不成立，就整组回滚，交给保留下来的单条路径逐条重放。这条路径是
M2/M3 时期的老实现，分类、补偿、挂起券的规则一条没改，只是不再是默认路径。

- 触发只有两种，分开计数：**插入被忽略**（重投撞上了已经存在的行，或者券/店铺的行不见了）和
  **库存不够**（这一批超过了数据库里还剩的量）。
- 退化后逐条走单条路径：先用只读脚本做一次归属校验（可落库 / 已成功 / 已失败 / 归属不符 / 状态缺失），
  可落库的才去写数据库。
  - 单条插入撞到主键冲突时，按订单号回查：**查到的就是同一个用户同一张券**，说明是重放，直接返回
    且**不再扣库存**；订单号被别人占了，抛订单号冲突；订单号没被占但这个用户这张券已有活跃订单，
    抛预占冲突。
  - 单条路径的扣库存是 `stock = stock - 1 WHERE stock > 0`，不成立就抛库存耗尽。
  - 上面三种「永久失败」的处理方式一样：**先挂起这张券**（把券的活动元数据置为挂起，写进每一个桶，
    因为准入脚本只能读买家自己那个槽），再对这一单做精确补偿——库存加回一、删掉预占、状态置失败并
    写明原因、从处理中索引移除、打上留存 TTL。挂起在前是 fail-closed：Redis 与数据库已经对不上了，
    不能一边还库存一边继续放人进来。
  - 单条路径自己完成置成功、发关单定时消息和通知，所以被它处理过的消息在批处理器这边就算完事了。
  - 逐条重放时把消息里带的链路 id 装回当前线程，日志才仍然属于那个买家的那次请求。
- 退化期间已经被单条路径办完的消息不会再进第三步收尾；它们不计入「批量落库」的统计。

### 3.3 对账器一轮：重驱动与补偿

对账器是一个定时任务：启动 30 秒后开始，每轮结束 10 秒后再跑一轮，一轮最多处理 100 个到期的预占。
它的职责是把「Redis 里还处在处理中、但已经超过判定窗口」的预占，按数据库的事实收敛掉。

- **取到期列表**：逐个桶执行一个脚本，按分数取「到期时间 ≤ Redis 服务器时间」的订单号，**只读不删**，
  每桶分摊这一轮的配额。成员不是规范的正整数就直接从索引里删掉并记错误——一个坏成员不能让每一轮
  都在 Java 的类型转换那里失败。
- **逐单处理，先取本单的调度锁**（分布式锁，只作用在少量到期订单上）。拿不到就让给别人，本轮跳过。
  先锁再读属主字段，赢的那个实例在这一单上是唯一负责人。
- **读状态快照**。字段缺失或不可解析的，不做任何业务判断，只把索引分数**延后 1 分钟**保留证据，
  并打错误日志等人处理——桶还能从订单号的基因里还原出来，但没有可信的用户 id 和券 id 就拼不出
  认领脚本要校验的那份精确归属，任何自动动作都成了瞎猜。
- **认领这一单**（对账器自己的脚本）。它会：
  - 校验精确归属；终态的直接从索引移除并返回终态；
  - **别人持有未过期的认领租约就返回「不到期」**——这正是消费者批次正在落库的情形，此时补偿会把一单
    马上要提交的订单干掉；
  - 索引里的分数还没到也返回「不到期」，成员不在索引里返回「索引缺失」；
  - 都通过就把尝试次数加一、写上自己的令牌和「现在 + 1 分钟」的租约、把索引分数推到「现在 + 1 分钟」，
    并对状态哈希执行 `PERSIST`，免得证据被留存 TTL 抹掉。
  - 顺带返回 Redis 当前时间、创建时间和累计尝试次数，供下一步判断年龄。
- **拿认领到的这一单去问写库**（按订单号查，再按用户+券查活跃订单），四种答案：
  - **完全一致**：订单已经建好了，只是 Redis 没来得及收尾。直接把状态修成成功并通知，本单收敛。
  - **不存在**：
    - 年龄 < **15 分钟**的硬期限 → **重新发一次消息**。重复是无害的：消费者会发现预占已成功或
      订单已存在然后确认。发送失败也不要紧，分数已经推后，下一轮再来。
    - 到了硬期限且补偿开关打开 → 精确补偿（还库存、删预占、置失败并写明原因、清索引、打留存 TTL）。
      补偿真的把一个名额放回桶里时，顺手清掉这个桶的售罄标记——本进程内清掉，同时用发布订阅广播出去，
      让每个实例都重新可以放人。开关关着就只记一条告警，**绝不擅自还库存**。
  - **同一用户同一张券已有别的活跃订单** / **这个订单号属于别的订单**：说明这条预占从来没有被持久化过，
    它的名额该还回去。同样是**先挂起券再补偿**，补偿开关关着就只挂起加告警。
- **需要人介入的状态**（归属不符、预占不符、字段损坏）一律不自动处理：延后 1 分钟、计数、打错误日志，
  让它在到期列表和日志里反复出现直到有人修。
- **失败时一律 fail-closed**：扫描失败就整轮跳过；问写库失败就什么都不做（禁止在不知道数据库事实的
  情况下补偿）；单个订单出异常不影响这一轮剩下的订单。

### 3.4 进程被 kill 之后怎么收敛

把一次 `kill -9` 放在链路的不同位置上，各自靠什么机制收回来：

- **写完预占、还没发出消息就死了。** 消息根本不存在，但处理中索引里有这个订单号，分数是
  「准入时刻 + 2 分钟」。两分钟后对账器扫到它，问写库、发现订单不存在、年龄还没到 15 分钟，
  于是**把消息重新发一遍**。这就是「预占即发件箱」的含义，也是这里不需要事务消息的原因。
- **认领之后、插入之前死了。** 数据库什么都没写，消息没被确认，Broker 会重投。重投可能落到别的
  实例上，而认领者令牌是每个进程一个，所以新实例要等那 **30 秒**租约过期才能认领成功——这是崩溃
  恢复的延迟代价。对账器在同一段时间里看到的是「别人的租约还没过期」，不会动它。
- **插入提交了、收尾之前死了。** 订单已经在库里，Redis 还是处理中。消息重投后：认领通过 →
  多值插入的影响行数是 0（被 `IGNORE` 掉了）≠ 组内条数 → **整组退化** → 单条路径撞到主键冲突 →
  回查发现是同一个用户同一张券 → 判定为重放、**不再扣库存**，然后置成功、发关单消息、通知。
  如果消息干脆丢了，对账器也会走到同一个结果：写库答「完全一致」，直接把状态修成成功。
- **主节点连同预占一起没了**（复制空窗演练）：消费者拿着消息去认领时发现状态哈希根本不在，判为
  「状态缺失」并重投，最终进死信队列；而复活的库存如果被重新卖掉，那一批走到数据库时会被
  `stock >= n` 挡下来。压测报告记的是：四轮里 Redis 最多多放了 10.3% 的人，**MySQL 每一轮都恰好
  建了 30000 单、超卖恒为 0**，收敛需要 150–308 s，靠的是对账器。
- 收敛的判据在演练里是三条同时成立：预占数 = 订单数、Redis 库存 = 数据库库存、没有残留的处理中状态。
  报告里记的批量消费上线前后的对比是 `kill -9` 收敛 102.8 → 44.7 s。

## 四、口述版

### 4.1 一批消息是怎么落库的

秒杀的准入只在 Redis 里放名额，真正建订单是异步的，所以消费端就是整条链路的吞吐瓶颈所在。
我们没有用框架的消息监听注解，因为它的容器会把一批消息逐条喂给监听方法，那样不管把「一次消费几条」
调多大，实际工作都还是一条一条做的；所以消费者自己持有推模式的消费者实例，把整批原样交给批处理器。

拿到一批之后先把字段不全、或者根本解析不了的消息剔掉丢弃——这种消息重试多少次都不会变好，只会更晚
进死信队列。剩下的整批做**一次** Redis 往返去认领。认领要按买家所在的库存桶拆，因为一个 Lua 脚本
只能碰自己那个槽里的键，同一个桶的就是一次往返。脚本对每条消息做和单条路径一样的归属校验：状态哈希里
记的订单号、用户、券必须跟消息完全对上，并且预占集合里这个用户对应的确实是这个订单号；校验过了就写上
自己的认领者令牌和一个三十秒的到期时间，同时把处理中索引里的到期分数往后推一个租约。写认领的意义是
把「这单我正在落」告诉对账器——从前这里是给每条消息加一把分布式锁，两次网络往返，现在它跟对账器
用的是同一套字段，更便宜而且语义一致。推分数的时候只更新已经存在的成员、而且只许把分数改大，
前者是怕一条迟到的认领把已经收尾的订单重新放回到期索引，后者是怕一个比判定窗口短的租约反而把到期
时间提前，给对账器送去一堆它只能拒绝的单子。脚本给每条消息返回一个决策：能落库的、已经成功的、
已经补偿失败的、归属不符的、状态读不到的、还有别人的租约没过期的；后三种意味着这一批得重投。

能落库的那些按券分组，一组一个事务。先按券读一次价格和店铺的快照，因为订单表是分片的、券表不是，
没法在插入语句里 join。然后一条多值的 `INSERT IGNORE` 把整组订单插进去，用 `IGNORE` 是为了让重投
撞上已有的行时变成空操作而不是整批失败。插完要比较影响行数和组内条数，不相等就整组回滚退化——因为
`IGNORE` 只告诉你插了几行、不告诉你是哪几行被忽略，而接下来扣库存必须用精确的 n。相等的话就做
**一次** `stock = stock - n WHERE stock >= n`，这一步是整个优化的核心：以前是每单一次更新同一张券的
同一行，压测火焰图里 44.7% 的时间都耗在那一行的行锁上，现在是每批每券一次。这个条件更新也是超卖的
最后一道闸：Redis 因为主节点故障多放了人，批次走到这里也会被拒绝。最后批量写一遍创建审计行。

事务提交完再做一次 Redis 往返收尾，也是按桶拆。每条消息把状态从处理中改成成功、清掉认领的两个字段、
从处理中索引里移除、给状态哈希打上七天的留存 TTL；已经是成功的走幂等分支只做清理。收尾成功的单子
才去发关单的延迟定时消息，而且是异步发的——同步发会在消费线程上每单多一次 Broker 往返，那正是把
数据库批量化之后剩下的那块开销；发不出去也没关系，还有兜底扫描会关单。通知也是整批一次管道发出去，
商户 id 走实例内缓存，不再每单补查一次数据库。

最后，只要这一批里还有一条没办完，就整批要求重投。重投本身是安全的，认领、插入、置成功全是幂等的，
已经办完的那些第二遍会在认领阶段就被判成「已成功」跳过去；不做部分确认是因为确认下标只能确认一个
前缀，而一批里的完成情况是乱序的。

### 4.2 退化为逐条

批量的前提一旦不成立就整组回滚，逐条重放。触发只有两种，而且分开计数：插入被忽略，通常是重投撞上了
已有的行；还有就是库存撑不住这一批。逐条走的是老的单条路径，它保留着全部的分类和补偿规则。单条先做
一次只读的归属校验，然后单条插入，如果撞到主键冲突就按订单号回查：查出来还是同一个用户同一张券，
那就是重放，直接返回而且**不再扣库存**；订单号被别人占了，或者这个人这张券已经有活跃订单了，那就是
真冲突。真冲突和库存耗尽这类永久失败的处理是一样的：先把这张券挂起，再对这一单做精确补偿——库存
加回一、删掉预占、状态置失败写上原因、从处理中索引移掉。挂起一定在补偿之前，因为这时候 Redis 和
数据库已经对不上了，不能一边还库存一边继续放人进来。

### 4.3 对账器

对账器是个定时任务，十秒一轮，一轮最多一百单。它先按桶从处理中索引里取出到期的订单号，只读不删，
这样即使自己中途崩了证据也还在。每一单先拿一把这一单的调度锁，保证同一时刻只有一个实例对它负责；
然后读状态快照，字段要是坏的就只把索引分数延后一分钟、打错误日志等人来修，因为桶虽然还能从订单号里
还原出来，但用户 id 和券 id 都不可信的话，就拼不出认领脚本要校验的那份精确归属了。接着用脚本认领这一单：终态的直接从索引里摘掉；别人的认领租约还没过期就跳过，
这一条很关键——那说明某个消费者批次正在落这一单，这时候补偿会把一单马上要提交的订单干掉；
都没问题就把尝试次数加一、写上自己的租约、把索引分数推后一分钟，顺便对状态哈希做一次 `PERSIST`，
免得证据被留存 TTL 抹掉。

认领到之后拿着这一单去问写库，答案只有四种。订单存在而且完全一致，说明只是 Redis 没来得及收尾，
直接把状态修成成功。订单不存在，那就看这条预占多大年纪了：不到十五分钟的硬期限，就**把消息重新发
一遍**，重复是无害的，消费者会发现已经成功或者订单已存在然后直接确认；过了硬期限，而且补偿的开关
是开着的，才做精确补偿把名额还回去，开关关着就只告警，绝不擅自还库存。剩下两种是数据库里另有一单
占了这个人这张券、或者这个订单号属于别人，说明这条预占从来没被持久化过，一样是先挂券再补偿。
至于归属对不上、预占对不上这种，一律不自动处理，延后一分钟让它反复出现在日志里等人来修。
整个对账器所有的失败都是 fail-closed 的：扫描失败整轮跳过，问写库失败就什么都不做，
因为在不知道数据库事实的情况下补偿等于凭空还库存。

### 4.4 进程被杀之后怎么收敛

这里没有用事务消息，因为 Redis 里那条处理中的预占本身就是发件箱。如果进程在写完预占、还没发出消息
时就被杀了，消息根本不存在，但处理中索引里有它，分数是准入时刻加两分钟；两分钟后对账器扫到，问写库
发现订单不存在、年龄又还没到硬期限，就把消息重新发一遍。如果是认领之后、插入之前被杀，数据库什么都
没写，消息也没确认，Broker 会重投，只是新的进程得等那三十秒租约过期才能认领成功——这是崩溃恢复要付的
延迟。如果是提交之后、收尾之前被杀，订单已经在库里了而 Redis 还是处理中：消息重投过来，认领能过，
但多值插入的影响行数是 0，跟组内条数对不上，于是整组退化、逐条重放，单条撞主键冲突、回查发现是同一个
人同一张券，判成重放，不再扣库存，然后置成功；就算这条消息彻底丢了，对账器最后也会走到同样的结论，
因为它问写库得到的是「完全一致」，直接修成成功。收敛的判据我们在演练里是三条一起看：预占数等于订单数、
Redis 库存等于数据库库存、没有残留的处理中状态。

## 五、为什么这么设计 / 会被怎么追问

**为什么不用事务消息 / 本地消息表？** 预占本身就是发件箱：它是一条带到期时间、进了有序索引、能被扫到的
持久证据，对账器扫到就能重发。引入事务半消息的代价在准入侧非常具体——基线阶段每个请求（包括 99% 注定
失败的）都要先发一条半消息，15k 档 Broker 先被压住；准入漏斗做完之后半消息数从「等于请求数」变成 0。

**批量到底快在哪？** 不在「提交更快」，而在「一次提交带走整批」。压测报告的说法是「一次提交上限约
80 次/s」，那是同一行的行锁加提交的代价；批量不改变这个数，只是让每次提交带走 n 单。所以吞吐
≈ 提交速率 × 实际批大小。

**那为什么第一次批量化没达标？** 因为批根本没攒起来。补上批大小指标之后测到实际批大小 1.03——
消费线程本来就跟得上到达速率，队列里永远没有第二条消息在等，「一次消费最多多少条」是上界不是目标。
后来的参数扫描里，拉取间隔是唯一有干净单旋钮证据的一项：批大小 2.16（0 ms）→ 12.68（50 ms），
换成那组参数后 2001.5 单/s。报告记的里程碑对比是中位 982.7 → 2088.9 单/s，负载停止时的积压
10.7 / 55.8 / 16.1 s → 0.1 / 0.1 / 0.1 s。

**那组消费参数为什么是一整组进默认值？** 因为只有这一整组被测过。有证据的是拉取间隔；
一次消费多少条和一次拉取多少条实测从未被触到（交付的批远没有撞到这个上界）；线程数方向对但落在
噪声带里——同一个 jar、同一组参数、相隔两分钟重跑的两轮，吞吐差得比线程数那几行彼此的差距还大，
所以这张表里的小幅单轮差异读不出结论。
拆出一个「只改拉取间隔」的组合就等于交付一个从没跑过的配置。

**等 50 ms 不是变慢了吗？** 是一笔交易：每条订单多等最多一个拉取间隔才落库，买到的是批大小和排空时间。
秒杀的落库本来就是异步的，用户看到的是准入结果。要注意的是这个间隔必须远小于对账器的过期判定窗口
（2 分钟对 50 ms 有三个数量级余量），把间隔调到上限时要重新看这一条。全链路场景里落库可见时间
中位 5.2 s、p99 15.7 s、最大 16.0 s。

**为什么消费锁换成了 Redis 里的认领字段？** 原来每条消息要取一把分布式锁，至少两次往返——
在火焰图里不是瓶颈，但每条消息都要白花这两次往返。改成在状态哈希上加认领者和到期时间两个字段之后：对外状态仍然是「处理中」，
查询接口的契约不变；对账器读的是同样两个字段，所以**不可能**在消费者落库过程中把同一单补偿掉；
进程崩了租约自然过期，对账器照常接手；同一个进程重投自己的批次时是续租，不会被自己挡住。

**为什么整批重投而不是只重投失败的那几条？** 确认下标只能确认一个前缀，而一批里的完成情况是乱序的。
整批重投是安全的（三步都幂等），代价是已完成的消息再走一遍前两步，第二遍会在认领阶段被直接判成已成功。

**加实例能不能提高落库吞吐？** 实测答案是不能。三实例烧掉三倍 CPU 只多落了约 25% 的单，
提交次数/s 在 70–115 之间且与实例数无关，而 MySQL 只用了 0.24 核。报告里的中位是
1→2→3 实例 2415 / 2435 / 3026 单/s，应用 CPU 1.41 → 2.7 → 4.0 核。瓶颈就是每批都要更新的那一行券库存，
行锁不会因为多了两个进程而变快。这是已经测实、尚未修的边界。

**超卖到底靠什么兜住？** 三道：准入的 Lua 在 Redis 里原子扣减（第 04 章）；落库时每批一次的
`stock >= n` 条件更新；以及对账器只在数据库确认订单不存在时才还库存。复制空窗演练里 Redis 最多
多放了 10.3% 的人，多出来的人分别在「消费者认领时发现状态不在」和「批次被 `stock >= n` 拒绝」
两处被挡下，两条路径通向同一个结果，四轮超卖恒为 0。

## 六、已知边界

- **认领租约默认 30 秒**：消费者进程崩溃后，它认领过的那一批要等租约过期才会被对账器或另一个实例接手。
- **退化是整组回滚再逐条重放**：重投多的场景下这条路径明显更慢，换来的是扣减用的 n 一定正确。
- **对账器的重驱动没有批量化**：仍然是每 10 秒最多 100 单，批量落库缩短的是每单的处理时间，
  重驱动的节奏由配置决定。报告里「先杀 Broker」这一类演练的收敛时间因此没有因批量化而改善。
- **一次消费 256 条和一次拉取 256 条目前是够不着的上界**：实测交付的批从未接近它，真正封顶的是 Broker 侧的一个
  更小的值，而且没有去读 Broker 的运行配置。如果将来那个上界被抬高，一次事务会带走多达 256 单、在热点行上持锁更久，
  那时要重新量而不是假定更大的批一定更好。
- **热点行没有拆**：按券分桶扣减 + 定期合并，或者把库存从 MySQL 移走，是下一步有数据支撑的优化，
  设计尚未定稿；真正让它生效的前提是消费批次尽量来自同一个桶，否则一个事务要持有 K 把行锁，竞争更糟。
- **每实例的商户缓存没有失效机制**（本项目里券的店铺不可改）。
- **通知是尽力而为**：管道发布失败只记日志，权威来源是可查询的订单状态接口。
- **解析不了的消息体被直接丢弃**，只有日志和计数，没有单独的归档；毒消息则靠重投次数进死信队列。
