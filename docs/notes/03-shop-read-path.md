# 03 店铺读路径：详情缓存、附近店铺与搜索

## 一、这一章解决什么问题

店铺是整个平台读得最多、写得最少的东西：首页按类型翻页、地图上找附近、搜索框里打关键词、点进详情页，
全都落在同一份店铺数据上。写只发生在商户后台偶尔改一次资料。所以这一章的目标是：
**把读扛住，并且在依赖出问题时仍然能给出一个确定的结果**。

难点有三层。第一层是缓存本身——不存在的店铺 id 被反复请求（穿透），热点店铺缓存到期的一瞬间大量请求同时回源（击穿）；
第二层是依赖不可靠——Redis 可能整个连不上、Elasticsearch 可能慢或挂，这时候不能让请求线程全部堆在数据库上把数据库也拖垮；
第三层是一致性——同一份店铺数据同时存在于数据库、Redis 字符串缓存、Redis 地理集合、搜索索引四个地方，
后台改一次资料，这四份要怎么对齐。

顺带把一件与「读」相关但方向相反的事收在本章：**用户上传的图片的归属**——上传是写，但它产出的是被读路径返回的静态资源，
而且它同样是「文件系统 + 数据库两份状态要对齐」的问题。

## 二、涉及的数据

**店铺表**（不分片）：id、所属商户 id、名称、类型 id、图片列表（逗号分隔的相对路径字符串）、商圈、地址、
经度与纬度两个独立的列、人均价格、销量、评论数、评分（乘 10 存成整数避免小数）、营业时间、创建与更新时间。
实体上还有一个**不落库的距离字段**，只在附近查询时被填进去返回给前端。所属商户 id 是商户后台做数据隔离用的，详见第 02 章。

**店铺类型表**（不分片）：本章只用到它的排序字段——类型列表按它升序取全量。

**上传文件表**：主键就是**受管相对路径**本身（不是自增 id，路径天然唯一，也省掉一次按路径查 id）。
其余字段是上传者的用户 id、状态（临时 / 删除中 / 已发布）、发布后关联的笔记 id、创建与更新时间。
两个索引：按（上传者，状态）和按（笔记 id）。

**Redis 里有三样东西**：

- **店铺详情缓存**：一个店铺一个字符串键，值是整行的 JSON；不存在的店铺写一个约定好的空值占位串。
- **店铺类型列表缓存**：一个字符串键存整个列表的 JSON 数组，空列表就存 `[]`。
- **附近店铺的地理集合**：**每个店铺类型一个 GEO 集合**，成员是店铺 id、坐标是店铺经纬度。
  按类型分集合而不是全站一个，是因为查询永远带着类型，分开之后半径搜索的候选集就小得多。

**搜索索引**（Elasticsearch 里的店铺索引）：文档 id 就是店铺 id；名称和地址是中文分词的全文字段
（索引时用细粒度分词、查询时用粗粒度分词，这样索引覆盖得全、查询词不会被切得太碎）；
类型 id 是 keyword；人均价格、评分、销量是数值；还有一个 geo_point 字段存「纬度,经度」。
**索引里只放用来过滤和排序的字段**，图片、营业时间这些展示字段不放——它们只会让索引变大，最后还是要回数据库取。

**一条同步消息**：Canal 盯着数据库 binlog，把店铺表（以及笔记表）的行变更发成 MQ 消息，
消息里有表名、操作类型（INSERT / UPDATE / DELETE）、是否 DDL、以及变更后的行数组。

## 三、详细流程

### 3.1 查店铺详情：空值占位 + 单飞 + 并发隔离舱

任何人（不需要登录）按店铺 id 请求详情，希望拿到整行店铺数据。这个请求到返回整行、或者返回「店铺不存在」为止。
读路径上的缓存逻辑不写在店铺服务里，而是收在一个**通用缓存组件**上——它只认「键前缀 + id + 目标类型 + 一个回源函数 + 一个校验函数」，
店铺详情和店铺类型列表复用同一套。

● 组件先用前缀拼出键去 Redis 取字符串。这一步有四种结果，分别对应四条路。
  ○ **Redis 抛异常**（连不上、超时）：记一次 Redis 故障，然后走回源，但**带上「本次不要回写缓存」的标记**。
    理由是 Redis 已经不可用了，回写多半也会失败，而且失败的异常还要再处理一遍；这时候的正确姿势是直接当无缓存用。
  ○ **取到的是空值占位串**：直接返回 null，**完全不碰数据库**。这就是防穿透——一个不存在的 id 只会打穿一次。
  ○ **取到普通值**：反序列化成目标类型，再过一道**校验函数**。店铺详情的校验函数是「请求的 id 必须等于反序列化出来的对象里的 id」。
    这道校验防的是键被写脏或者键前缀撞了导致 A 的请求拿到 B 的数据；反序列化抛异常也走同一条修复路。
    校验不过或解析失败，就当成坏值，回源重新加载并覆盖写回。
  ○ **取到的是 null（键不存在）**：正常未命中，回源。
● 回源这一步套了两层保护，顺序是**先单飞、再隔离舱**。
  ○ **单飞**：以「缓存资源 + 具体键」为单位，在**本进程内**只允许一个线程真正去加载。
    第一个到的线程是 leader，在自己的请求线程上执行加载；同一时刻同一个键的其他线程是 follower，直接等 leader 的结果。
    follower 最多等 750 毫秒，等不到就抛 503。leader 做完无论成败都把这个键从在途表里摘掉。
    这是这个项目对「缓存击穿」的答案：**用进程内的一次加载合并，代替给每个键加一把分布式锁**。
  ○ **隔离舱**：leader 真正查数据库前，要先拿到数据库读的信号量许可。许可总数 4，最多等 20 毫秒。
    拿不到直接抛 429（读请求过多），**不排队**。这是为了让数据库前面有个硬上限：
    宁可快速拒掉一部分读，也不要让几百个线程一起压到连接池上，连带把下单这类写请求也拖死。
  ○ 隔离舱里跑的加载体还会打点：耗时、以及结果是「查到 / 查到空 / 抛异常」。
  ○ 加载体里抛出的**未知**运行时异常（例如数据库连不上）会被隔离舱统一换成 503（数据暂不可用）；
    已经带明确状态码的异常原样向上抛，不会被改写。
● 加载结果决定回写什么。
  ○ 查不到（null）：把**空值占位串**写进去，TTL 30 秒，然后返回 null。空值的 TTL 由配置单独控制，
    并且启动时会校验它**不得长于**正常值的 TTL——空值缓存久了，新建的店铺就会在这段时间里一直被判定为不存在。
  ○ 查到：把整行序列化成 JSON 写进去，TTL 30 秒。
  ○ 两种回写都是**尽力而为**：写 Redis 抛异常只记一次失败指标、打一条日志（同一进程 30 秒内最多打一条，防日志刷屏），
    **不影响本次返回**。这一次的数据已经从数据库拿到了，没有理由因为缓存写不进去而让用户看到错误。
● 店铺服务拿到 null 就返回「店铺不存在」，拿到对象就原样返回。

### 3.2 查店铺类型列表：同一套缓存的列表版

首页左侧的类型列表是典型的「几乎不变、每次首页都要」的数据，所以它用同一个缓存组件的列表方法，
差别只在校验和 TTL 上。

● 缓存键是固定的一个，没有 id 参与。命中后解析成数组。
  ○ 解析时**刻意保留 null 元素**——如果把 null 忽略掉，一个写坏成 `[null]` 的值会被当成「空列表」直接返回，
    那就永远修不回来了；保留下来才能被下面的校验判定为坏值并触发修复。
  ○ 解析出来是空数组，当成「合法的空结果」直接返回。
  ○ 非空则校验：每个元素非 null、id 非 null 且为正、且**互不重复**。任何一条不满足就当坏值回源重写。
● 回源同样走单飞 + 数据库读隔离舱，查出来按排序字段升序的全量类型。
● 回写：空结果写 `[]`、TTL 30 秒；非空写 JSON 数组、TTL 100 分钟。
  正值 TTL 比店铺详情长得多，因为类型表基本不动，而且它没有对应的失效钩子——只能靠 TTL 自然过期。

### 3.3 按类型查店铺与「附近的人」：GEO 集合

前端按类型翻页，可能带上自己的经纬度和一个排序方式，希望拿到这一页的店铺；带坐标时还要拿到每家店的距离。
这个请求到返回一页店铺列表为止。页大小固定 5。

● 先按排序方式分三条路。
  ○ 排序方式是「评论数」或「评分」：**直接走数据库分页**，按类型等值过滤 + 按该字段倒序。这两种排序和位置无关，
    没必要经过 Redis。
  ○ 没有传坐标：也走数据库分页，只按类型过滤，不排序。
  ○ 传了坐标且不是上面两种排序：走 GEO。
● GEO 这条路的关键是「Redis 只出 id 和距离，字段还是回数据库取」。
  ○ 按类型拼出该类型的地理集合键，以用户坐标为圆心做半径 5000 米的搜索，带上距离，
    并且 **limit 传的是「当前页的结束下标」**（页码 × 5），而不是页大小。
    Redis 的 GEO 搜索只能限制返回条数、不能跳过前 N 条，所以只能取满前 N 条再在应用里跳过前面的部分。
    这意味着**页码越深、从 Redis 拿回来的数据越多**，是典型的深翻页放大。
  ○ 搜索结果为空或为 null（例如 Redis 重启后这个集合还没被重新灌进去），**降级回数据库**按类型分页返回——
    只是丢掉了距离和距离排序，不会报错。
  ○ 结果条数不超过本页起始下标，说明翻过头了，直接返回空列表。
  ○ 否则跳过前面的部分，把剩下的成员名解析成店铺 id 列表，同时把「店铺 id → 距离」记在一张内存里的映射表上。
● 拿 id 列表回数据库查整行，并且在 SQL 末尾拼一段**按给定 id 顺序排序**的子句，把 Redis 排好的近远次序原样带回来。
  数据库的 `IN` 查询本身不保证顺序，不强制排序的话距离排序就白做了。
● 最后按店铺 id 把距离回填到那个不落库的距离字段上，返回。

### 3.4 关键词搜索：全文 + 地理过滤 + 回表

搜索框里输入关键词（可选）、可带坐标与半径、可带类型，希望拿到匹配的一页店铺。页大小同样是 5。

● 入口先校验页码必须为正，然后整个查询体被放进**搜索隔离舱**：信号量许可 4、最多等 20 毫秒，
  拿不到抛 429（搜索请求过多）。这个隔离舱和数据库读的那个是**两个独立的舱**，
  搜索被打爆不影响详情页读缓存回源，反过来也一样。
  ○ 舱内抛出的未知运行时异常会被统一换成 503（搜索暂不可用）；已经是明确状态码的异常原样抛出。
  ○ 除了并发上限，客户端本身也有超时：连接 500 毫秒、socket 1 秒。一个慢查询最多占住一个许可 1 秒。
● 组查询：关键词非空就对名称和地址做多字段匹配，为空就 match_all。
● 组过滤：类型和坐标都是可选参数。传了类型就加一个 term 过滤；传了坐标再加一个 geo_distance 过滤，
  半径取传入值、没传就默认 5000 米；两个都没传就根本不设 filter。
  ○ **所有过滤条件必须合进同一个 bool 里再交给 builder**——builder 只保留一个 filter，分两次设置会把前一次覆盖掉。
    这是写的时候踩过的坑。
  ○ 带坐标时同时加一个按距离升序的排序，单位米。
● 分页用「页码 - 1」和固定页大小，也就是 **from / size**。
● 拿到命中后**只取文档 id**，再用这批 id 回数据库查整行，并同样拼上按给定 id 顺序排序的子句保序。
  ○ 这么做的理由：索引里没有图片、营业时间这些展示字段，而且索引是异步同步的、可能比数据库旧；
    **让索引负责「排序和筛选」，让数据库负责「字段的真实值」**。
  ○ 命中为空就直接返回空列表，不发这条数据库查询。

### 3.5 索引怎么建起来、又怎么跟上数据库

● **启动时**（测试环境以外）有一个初始化动作：先看店铺索引在不在，不在才按文档类上的注解创建索引和 mapping；
  **随后不管索引原来在不在**，都把店铺表全量查出来逐条写进索引，最后 refresh 一次。
  也就是说建索引是条件性的，全量灌入是每次启动都做的。
  ○ 写入用店铺 id 作为文档 id，所以重复启动是覆盖写，不会产生重复文档。
  ○ 它依赖数据源，而建库脚本是在数据源构建过程中跑完的，所以这个初始化天然排在建表之后。
● **运行时**靠 Canal：Canal 订阅数据库 binlog，把店铺表与笔记表的行变更发到一个 MQ 主题，本服务有一个消费者。
  ○ 消息解析失败：记失败指标并抛异常，**让 MQ 重投**，而不是吞掉。
  ○ 是 DDL 或者表名不是关心的那两张：记一次「忽略」后直接返回，不重投。
  ○ 行数组为空：视为异常并抛出重投。
  ○ 按表名分流。删除操作按文档 id 删；其余操作把行 map 转成文档对象后**按文档 id 覆盖写**。
    因为是覆盖写而不是增量修改，**重复消费同一条消息是幂等的**，这正是敢于「失败就重投」的前提。
  ○ 行转文档时要注意经纬度：数据库里两列分别是经度和纬度，而 geo_point 要的是「纬度,经度」，**顺序是反的**。
  ○ 逐行处理，单行失败只记这一行的失败并继续处理同一条消息里的其他行；整条消息处理完，只要有失败行就抛异常整条重投
    （已经成功的行会被重复写一遍，但因为是覆盖写所以无害）。全成功 / 全失败 / 部分失败在指标上是三种不同结果。

### 3.6 后台改了店铺资料，三份数据怎么对齐

商户或平台在后台新建、修改店铺，或者改店铺的归属商户。权限与数据隔离属于第 02 章，这里只看写完之后的缓存动作。

● 写库在事务里完成，缓存动作**全部注册成 afterCommit 回调**，而不是在事务里就做。
  ○ 进入注册前先断言「当前必须处于事务同步中」，否则直接抛异常——防止有人把写方法的事务注解漏掉，
    导致缓存动作在没有事务的情况下静默执行。
  ○ 提交之后才删缓存，保证**不会出现「缓存已删、事务回滚」导致缓存被回填成旧值**的窗口；
    代价是提交到删除之间有一个很短的窗口里缓存还是旧的，配合 30 秒 TTL，这个窗口的上界是可接受的。
● 回调里做三件事：删掉这个店铺的详情缓存；**如果这次写带着一个「旧类型」**（也就是修改，不是新建），
  就先从旧类型的地理集合里把这个店铺移掉；如果类型和经纬度都齐备，再把它加进**当前类型**的地理集合。
  ○ 注意移除这一步**并不判断类型有没有真的变**：只要是修改，就无条件先移再加。类型没变时等于「移掉再原样加回来」，
    结果正确，代价是多一次 Redis 往返；新建没有旧类型，所以只有「加」。
    好处是不必维护「类型是否变化」这个分支——判错一次就会在旧类型的集合里留下一个幽灵成员。
  ○ 三个动作各自 try/catch，失败都**不抛出**——事务已经提交了，这时候抛异常没有任何补救作用，
    只会让一个已经成功的写操作对调用方显示为失败。详情缓存 30 秒后自然过期，地理集合则要等下一次写或重新灌库才会纠正。
  ○ 三者的可观测性并不对称：删详情缓存成功和失败都记了指标、失败另打错误日志；
    两个地理集合动作**只在失败时打一条错误日志，没有任何指标**——地理集合漂了，只能从日志里发现。
● 搜索索引不在这里处理——它走 3.5 的 binlog 链路，是异步最终一致的。
● 改归属商户只删详情缓存，不动地理集合（坐标和类型都没变）。

### 3.7 图片上传的归属：文件系统与数据库两份状态

用户在发笔记前先逐张上传图片，上传成功拿到一个路径；发笔记时把这些路径提交上去。
难点是文件落在磁盘上、归属记在数据库里，两者不在一个事务里，必须设计成「任何一步失败都不会留下别人能用的东西」。

● **上传**：要求已登录。先挡掉空文件，再做三道校验——大小不超过配置上限（默认 5MB）、
  扩展名在白名单内（jpg/jpeg/png）且与声明的 MIME 类型一致、
  再读前 8 个字节比对**文件头魔数**（PNG 的 8 字节签名 / JPEG 的三字节开头）。
  魔数这一道是防止把可执行内容改个扩展名传上来。
  ○ 路径不由用户决定：取一个随机 UUID 作为文件名，用它的 hash 的低 4 位和次低 4 位切出两级目录，
    得到 16×16 共 256 个目录，避免所有图片堆在一个目录下。
  ○ 落盘前先把上传根目录和目标目录**解析成真实路径**（跟随符号链接），再断言它仍然在根目录之下，防止被符号链接带出根目录。
  ○ 文件写完才在数据库里登记一条「临时」状态的归属记录（主键是相对路径，记上传者 id）。
    **登记失败就把刚写的文件删掉再把异常抛出去**——宁可两边都没有，也不要留下一个无主文件。
  ○ 返回给前端的是加了前导斜杠的相对路径。
● **删除（用户在发布前撤掉一张图）**：先把文件名**规范化**——去掉前缀和前导斜杠、归一化分隔符、排除绝对路径和 `..`，
  最后用一个正则断言它完全符合上传时生成的格式（固定的一级业务目录 + 两级 0–15 的数字目录 + 小写 UUID + 允许的扩展名）。
  不符合就拒绝。
  这一步是整条路径上防目录穿越的主闸。
  ○ 文件不存在：把对应的「临时」记录删掉就返回成功（幂等，允许重复调用）。
  ○ 存在：再做一次真实路径校验，并拒绝符号链接和目录。
  ○ 然后是关键的一步——**先把数据库记录从「临时」条件更新成「删除中」**，条件里带上路径、上传者 id 和原状态。
    更新影响行数不是 1 就返回「图片不存在或无权删除」。这一条语句同时做了三件事：鉴权（只能删自己的）、
    状态前置校验（已发布的删不掉）、以及**并发互斥**（两个并发删除只有一个能把状态推走）。
  ○ 抢到「删除中」之后才删磁盘文件，删成功再按「删除中」状态把记录删掉。
  ○ 删文件或删记录中途失败，则把状态**回滚成「临时」**再抛异常——这样用户可以重试，记录也不会卡死在「删除中」。
    「删除中」这个中间态就是为此而加的（建表时只有临时和已发布两种，后来单独加了一次迁移把状态列的取值扩成三种）。
● **发布（发笔记时）**：在笔记保存的同一个事务里，先校验图片列表——拆分、数量不超过 9 张、逐个规范化、
  **不允许重复**、且每一张都必须是「当前用户名下的、临时状态的」记录。任何一张不过就整体拒绝。
  ○ 笔记插入成功拿到笔记 id 之后，逐张把记录从「临时」条件更新成「已发布」并写上笔记 id，
    条件同样带路径、上传者 id 和原状态；影响行数不是 1 就抛异常让**整个事务回滚**。
    这挡住的是「校验之后、发布之前」被另一个并发请求（比如一次删除）把状态改走的竞态。
  ○ 因为和笔记插入同一个事务，「笔记存在但图片还挂在临时」这种不一致不会出现。笔记本身的链路详见第 10 章。

## 四、口述版

**3.1 店铺详情。** 查店铺详情是不用登录的，进来之后店铺服务并不自己操心缓存，而是交给一个通用的缓存组件，
因为店铺详情和店铺类型列表的缓存逻辑其实一模一样，只是键和 TTL 不同。组件先拿前缀加 id 拼出键去 Redis 读。
如果读 Redis 直接抛异常，说明 Redis 这会儿不可用，那就当没有缓存，直接去查库，但会打一个标记说这次别回写了，
因为回写大概率也是失败，没必要再处理一次异常。如果读到的是那个约定的空值占位串，就直接返回不存在，
一次数据库都不查，这就是防穿透——一个乱猜的 id 最多打穿一次，之后三十秒内都被这个占位串挡住。
如果读到的是正常的值，反序列化之后还要再过一道校验，校验的内容是「我请求的 id 是不是等于我拿到的这个对象里的 id」，
这是防止键写脏或者前缀撞了把别人的数据返回给我；解析失败或者校验不过，就当成坏值，走回源并覆盖写回去。

回源这一步套了两层。第一层是单飞：以「这个资源加这个键」为单位，在本进程里只让第一个线程真正去加载，
后面同一个键的线程都等这第一个线程的结果，最多等 750 毫秒，等不到就抛 503。这就是我对缓存击穿的处理方式，
用进程内合并加载代替给每个热点键加分布式锁——因为代价小得多，而且效果在单机上是一样的。第二层是隔离舱，
真正查库之前要先抢一个信号量许可，一共 4 个，最多等 20 毫秒，抢不到就直接返回 429，不排队。
这是给数据库前面立一个硬上限，宁可拒掉一部分读，也不能让读把连接池占满、把下单也拖死。
查完之后回写缓存：查到就写整行 JSON、三十秒过期；没查到就写空值占位串，也是三十秒，而且配置启动时会校验
空值的 TTL 不能比正常值的还长，否则新建的店铺会在这段时间里一直被当成不存在。回写是尽力而为的，
写失败只打指标和一条限流的日志，不影响这次返回，因为数据已经从库里拿到了，没理由因为缓存写不进去就报错。

**3.2 类型列表。** 类型列表走同一个组件的列表版本，键是固定的一个。解析的时候特意保留 null 元素，
因为如果把 null 忽略掉，一个写坏成只有一个 null 的值会被当成空列表直接返回，就永远修不回来了；保留下来才能被校验发现。
校验是每个元素非空、id 是正数、而且互不重复，不满足就当坏值重新回源。空数组是合法结果，直接返回。
正常值的 TTL 是一百分钟，比店铺详情长很多，因为类型表基本不变，而且它没有失效钩子，只能靠自然过期。

**3.3 附近店铺。** 按类型查列表的时候先看排序方式，如果是按评论数或者评分排，那跟位置没关系，直接走数据库分页；
如果前端根本没给坐标，也走数据库。只有带了坐标、而且不是这两种排序的时候才用 Redis 的 GEO——默认就是这一条路。每个店铺类型有自己的一个地理集合，
不是全站一个，因为查询永远带类型，分开之后半径搜索的候选集小很多。以用户坐标为圆心搜五公里，
这里有个细节：Redis 的 GEO 搜索只能限制返回多少条、不能跳过前面多少条，所以 limit 传的是「这一页的结束下标」，
也就是页码乘以页大小，拿回来之后在应用里再跳过前面的部分。这意味着翻得越深、从 Redis 拿回来的越多，
是典型的深翻页放大。如果搜出来是空的，比如 Redis 重启之后这个集合还没灌回去，就降级回数据库按类型分页，
只是没有距离和距离排序，但不会报错。正常情况下我拿到的是店铺 id 和距离，id 拿去数据库查整行，
SQL 后面要拼一段按给定 id 顺序排序的子句，因为 IN 查询本身不保证顺序，不这么做距离排序就白排了；
最后把距离按 id 回填到一个不落库的字段上返回。

**3.4 搜索。** 搜索的入口先校验页码为正，然后整个查询放进一个搜索专用的隔离舱，也是四个许可、最多等二十毫秒，
抢不到就 429。它和刚才那个数据库读的隔离舱是两个独立的舱，搜索被打爆不会影响详情页的回源，反过来也一样；
另外 ES 客户端自己还有超时，连接半秒、socket 一秒，所以一个慢查询最多占住一个许可一秒。查询本身是：
关键词非空就对名称和地址做多字段匹配，为空就全匹配；类型和坐标都是可选的，传了类型就加一个 term 过滤，
传了坐标就再加一个地理距离过滤，半径用传进来的、没传就默认五公里，同时加一个按距离升序的排序。这里踩过一个坑是所有过滤条件必须合进同一个 bool
再设置进去，因为 builder 只保留一个 filter，分两次设会把前一次覆盖掉。分页用的是 from 加 size。
最关键的是拿到结果之后我只取文档 id，然后用这批 id 回数据库查整行，同样拼保序子句。
这么做是因为索引里只放了用来过滤和排序的字段，图片这些展示字段没放，而且索引是异步同步的可能比库旧，
所以让索引负责排序和筛选，让数据库负责字段的真实值。

**3.5 索引同步。** 索引的来源有两条。启动的时候先看索引在不在，不在才按文档类上的注解建索引和 mapping；
建不建索引是一回事，全量灌是另一回事——不管索引原来在不在，每次启动都会把店铺表全量灌一遍，
用店铺 id 当文档 id，所以重启是覆盖写、不会重复。运行期靠 Canal 盯 binlog，
把店铺表和笔记表的变更发成 MQ 消息，我这边有个消费者。消息解析不了、或者行数组是空的，就抛异常让 MQ 重投；
是 DDL 或者表名不是我关心的那两张，就记一次忽略直接返回，不重投。正常的消息按表分流，删除就按文档 id 删，
其他都转成文档对象按文档 id 覆盖写。因为是覆盖写而不是增量改，重复消费是幂等的，这正是我敢让失败就重投的前提。
转换的时候有个容易错的地方是经纬度顺序：库里两列是经度和纬度，而 geo_point 要的是纬度在前。
处理是逐行的，单行失败先记下来继续处理同一条消息里的其他行，整条处理完只要有失败就整条抛出去重投，
已经成功的行会被重写一遍，但因为覆盖写所以无害。

**3.6 写侧对齐。** 后台改完店铺资料之后，缓存动作全部注册成事务提交后的回调，而不是在事务里就做。
注册之前会先断言当前确实在事务同步里，否则直接抛异常，防止哪天有人把事务注解漏了导致这些动作静默执行。
提交之后才删缓存，是为了不出现「缓存删了但事务回滚了」从而把缓存回填成旧值的窗口；代价是提交到删除之间有一小段
缓存还是旧的，但详情缓存本来就只有三十秒，这个窗口的上界可以接受。回调里做三件事：删这个店铺的详情缓存；
如果这次是修改、手上有一个旧类型，就先从旧类型的地理集合里把它移掉——这里我没有去判断类型到底有没有变，
只要是修改就无条件先移再加，类型没变时相当于移掉再加回来，多一次往返但不会漏；最后如果类型和坐标都在，
就把它加进当前类型的地理集合。三个动作各自捕获异常，失败都不抛出——事务都提交了，这时候抛异常没有任何补救作用，
只会让一次成功的写对调用方显示成失败。不过这三件事的可观测性是不对称的：删详情缓存有指标，
两个地理集合动作失败时只打一条错误日志、没有指标。
搜索索引不在这里管，它走 binlog 那条异步链路。

**3.7 图片归属。** 上传图片要求登录，先校验大小、扩展名白名单和 MIME 一致、再读文件头的魔数比对，
防的是把可执行内容改个扩展名传上来。路径不让用户决定，用一个随机 UUID 当文件名，拿它 hash 的低四位和次低四位
切出两级目录，一共两百五十六个目录，免得所有图片堆在一起。落盘之前先把根目录和目标目录解析成真实路径，
再确认它还在根目录底下，防止被符号链接带出去。文件写完才去数据库登记一条临时状态的归属记录，主键就是这个相对路径，
记上传者是谁；如果登记失败，就把刚写的文件删掉再抛异常，宁可两边都没有也不要留一个无主文件。

用户在发布前撤掉一张图的时候，先把文件名规范化，去前缀、去前导斜杠、排掉绝对路径和上跳，最后用一个正则确认
它完全符合我上传时生成的那个格式，这是防目录穿越的主闸。如果文件已经不在了，就把那条临时记录删掉返回成功，做成幂等的。
文件在的话，关键一步是先把数据库记录从临时条件更新成「删除中」，条件里带路径、带上传者 id、带原状态，
影响行数不是一就直接拒绝。这一条语句同时做了三件事：鉴权只能删自己的、状态校验已发布的删不掉、
以及两个并发删除只有一个能抢到。抢到之后才删磁盘文件，删完再按「删除中」把记录删掉；中间任何一步失败，
就把状态回滚成临时再抛异常，这样用户能重试、记录也不会卡死。「删除中」这个中间态是后来单独加了一次迁移补上的，
建表的时候只有临时和已发布两种。

发笔记的时候在同一个事务里先校验图片列表：数量不超过九张、逐个规范化、不许重复、每一张都必须是当前用户名下的临时记录，
有一张不过就整体拒绝。笔记插进去拿到 id 之后，再逐张把状态从临时条件更新成已发布并写上笔记 id，
影响行数不是一就抛异常让整个事务回滚，挡的是「我校验完、还没发布」的那一瞬间被一个并发的删除把状态改走。
因为和笔记插入同一个事务，所以不会出现笔记存在但图片还挂在临时状态的不一致。

## 五、为什么这么设计 / 会被怎么追问

**为什么用单飞而不是分布式互斥锁重建？** 互斥锁要处理加锁、续期、锁超时、持锁进程崩溃这一整套问题，
而热点键回源的核心痛点是「同一瞬间成百上千个线程压到库上」，这个量绝大部分本来就集中在**同一个进程内**。
进程内合并加载没有网络往返、没有锁泄漏风险，代码量也小得多。代价是多实例部署时每个实例仍会各回源一次——
N 个实例就是 N 次，而不是 1 次。对这个规模来说 N 次完全扛得住，所以选了便宜的那个。

**那逻辑过期呢？为什么代码里没有？** 逻辑过期（值永不过期、把过期时间写在值里、发现过期就异步重建、期间返回旧值）
在 V1 的缓存组件里确实写过，连带还有一个注释掉的互斥锁重建版本和一个自己实现的 `SETNX` 锁，
但**它们都没有任何调用方**——真正跑在读路径上的一直只有「空值占位 + 回源」这一条。
V2 的第一步清理就把这些没有调用方的教程残留整体删掉了（一并删掉的还有那个自研锁，因为真要用锁的地方用的是成熟的分布式锁框架）。
所以这里要说的是两层：第一层是事实——**现在的实现是空值占位 + 单飞 + 隔离舱，既没有逻辑过期，也没有互斥重建**；
第二层是即使重做也不会把逻辑过期加回来——它用「重建期间返回旧数据」换「并发回源」，而并发回源单飞已经解决了，
代价却是值永不过期、**冷数据永不淘汰**，而且「返回旧值」在店铺资料这种场景收益很小。

**为什么空值也要设 TTL，而且不能比正常值长？** 空值占位是防穿透的手段，但它同时也是一个「否定的断言」。
如果不设过期，一个后来才被创建的店铺会永远查不到；如果设得比正常值还长，新建的店铺会有一段明显的不可见期。
所以配置类在启动时就把这条约束校验死了，配错直接起不来，而不是等线上出问题。

**缓存删除为什么放在事务提交之后，而不是「先删缓存再写库」？** 先删再写的问题是：删完到写完之间，
一个并发的读会把**旧值**重新加载回缓存，而这份旧值的 TTL 是完整的三十秒。放在提交后删，最坏情况只是
提交到删除之间的一小段时间里读到旧值，而且这段时间远短于 TTL。至于「删除本身失败了怎么办」——
不重试、不抛异常，靠 TTL 兜底，因为这里的一致性要求本来就是「最终」，不值得为它引入重试队列。

**为什么搜索要回数据库查一遍，不直接返回索引里的文档？** 三个理由：索引里没有展示字段（图片、营业时间），
放进去只会让索引变大；索引是 binlog 异步同步的，可能比数据库旧，展示字段以数据库为准更安全；
以及索引的职责就该是「给出 id 和顺序」。代价是多一次数据库查询，但这次查询是主键 `IN`，很便宜。

**两个隔离舱为什么要分开，许可为什么这么小？** 分开是因为它们保护的是两个不同的下游——一个是数据库连接池、
一个是搜索集群，任何一个被打爆都不应该连累另一个。许可只有 4、等待只有 20 毫秒，是**刻意的快速失败**：
隔离舱的价值在于「不排队」，一旦允许排队，队列本身就会变成新的延迟来源，压力反而被藏起来看不见。

**深翻页怎么办？** 现在两条路都是浅分页：附近店铺是「取满到当前页尾再跳过前面」，搜索是 from / size。
两者页码越大代价越大。正经的做法是 search_after——用上一页最后一条的排序值作为游标，
让每一页的代价固定，不随页码增长。**但这个项目里没有实现**，搜索用的还是 from / size。
被问到要直接说没做，并说清楚为什么它能解决问题（把「跳过 N 条」换成「从某个排序值之后开始」，
避免协调节点把前 N 条全部收上来排序）。

**Canal 这条链路如果重复投递怎么办？** 天然幂等，因为写入是「按文档 id 覆盖写」而不是增量修改，
删除也是按 id 删。正因为幂等，才敢在任何失败时直接抛异常让 MQ 重投，而不用额外维护一张消费去重表。

## 六、已知边界

- **没有逻辑过期，也没有分布式互斥重建**。击穿的处理只有进程内单飞，多实例时每个实例各回源一次。
- **没有多级缓存**（本地一级 + Redis 二级）。这是计划里被砍掉的一项，性能报告里也明确写了「多级缓存（M7 砍）」。
- **搜索没有 search_after**，翻页是 from / size；附近店铺更是「取满再跳过」。两者深翻页都会放大。
- **附近店铺的半径固定五公里且写死在代码里**，搜索接口的半径可以传但默认也是五公里。
- **地理集合的失效是尽力而为的**：后台改了坐标或类型之后，如果这一步写 Redis 失败，集合里就会留下错误的位置，
  没有任何定时任务去纠正它，只能等下一次对这家店的写操作或者重新灌库。详情缓存靠三十秒 TTL 兜底，地理集合没有这个兜底。
  而且这两个地理集合动作**只在失败时打日志、没有指标**，所以它漂掉了在监控上看不出来（详情缓存的删除是有指标的）。
- **Redis 重启后地理集合是空的**，没有自动重建；读路径能降级回数据库（丢掉距离），但要恢复距离排序需要人工灌一次。
- **店铺类型列表缓存没有失效钩子**，改了类型表最长要等一百分钟才生效。
- **启动时对搜索索引做的是全量重灌**，店铺表大了之后这会明显拖慢启动，也没有分批或跳过的开关。
- **索引与数据库之间是最终一致的**，中间的延迟取决于 Canal 和 MQ；如果 Canal 没起来，索引就会一直停在上次全量灌入的状态，
  而搜索接口本身不会报错，只会返回旧结果——**没有对这个延迟的监控告警**。
- **上传的图片没有孤儿清理任务**：用户传了图但一直不发笔记，那条临时记录和磁盘文件会一直留着。
  状态和索引（按上传者 + 状态）都已经为这样一个清理任务准备好了，但任务本身没写。
- **图片存的是本机文件系统路径**，没有对象存储；多实例部署时上传到 A 实例的图片在 B 实例上读不到。
- 商户后台的权限校验与按商户的数据隔离不在本章，详见第 02 章。
