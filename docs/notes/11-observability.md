# 11 可观测：一个 trace 三跳、有限的指标词表、积压怎么被看见

## 一、这一章解决什么问题

这个系统里一次下单被拆成了三段：一台实例做准入、一条消息跨进程、另一台实例落库，一分钟或十几分钟
之后还有第三台实例来关单。出问题时最常被问的那句「这个买家到底怎么了」，在单实例时代靠翻一个日志文件
就能回答，多实例之后没有一根线把这些段串起来就只能猜。

所以这一章只做三件事。第一，**给一次请求一个 id，让它跨进程、跨存储活下来**——HTTP 一跳、MQ 一跳、
落库一跳，三跳用的是三种完全不同的机制。第二，**把指标词表约束成有限的**：指标是长期驻留的，标签值
一旦来自用户输入就会把注册表撑爆，所以这个项目里所有维度都是枚举，先注册后使用。第三，**把「积压」
变成可以被看见的数字**：可靠性靠的是几条异步补偿链（对账、发件箱），它们不出错，只会变慢，慢的表现
就是积压；积压不采样，就等于没有。

要注意的是这一章只管「看得见」，不管「怎么敲命令查」、也不管「压测怎么做、结论是什么」
（两者都详见第 12 章）。

## 二、涉及的数据

- **链路 id 本身**：32 个十六进制字符（两个 64 位随机数拼起来），也就是边缘代理用它自带的请求 id
  生成时的形状；接受外来 id 时的上限是 64 个字符，字符集只允许字母、数字、连字符和下划线。
- **线程上下文**：id 放在日志框架的诊断上下文里（一个 ThreadLocal 的 map），日志格式串里用一个占位符
  取它，于是**每一行日志**自动带上，而不是一个参数一个参数地传。日志前缀里还有实例名，所以一行日志
  能同时回答「哪个请求」和「哪个实例」。
- **HTTP 头**：请求头带进来、响应头原样写回去，调用方（浏览器、压测器、上游服务）能拿着它来问。
- **秒杀消息体**：除了券 id、用户 id、订单号之外多一个链路 id 字段。对账器从 Redis 预占重建的消息
  没有这个字段（那次请求早就结束了），值是空。
- **关单定时消息**：只有订单号和链路 id 两个字段。
- **订单表上的一列**：可空的链路 id 列，字符集是 ascii、排序规则是二进制——它是个不透明令牌，不做
  大小写无关比较。可空是故意的：对账器重建的订单、以及这次迁移之前建的订单，背后本来就没有请求。
- **七个积压/年龄类仪表盘数字（gauge）**：点赞发件箱的待处理条数与最老一条的年龄、热榜快照的年龄、
  秒杀处理中索引里已到期的预占数与最老一条超期多久、券发放通知发件箱的待处理条数与最老一条年龄。
  （另外还有两个和积压无关的仪表：两种本地受限读资源当前握着的许可数。）
- **一批计数器与分布**：秒杀消息的消费结局（十种，枚举）、落库耗时（成功/失败两种）、批大小
  （「Broker 投递的」与「一条 INSERT 真正承载的」两个阶段）、批次退化原因、准入漏斗的放行/拒绝/
  不可用与拒绝原因、缓存命中与回源、认证结局、检索同步结果，以及**三个**采样器（点赞发件箱、
  秒杀处理中索引、热榜）自己的成功/失败计数——券发放通知那个没有，见第六节。
- **暴露方式**：管理端口独立于业务端口、默认只绑回环地址，只暴露健康检查和指标抓取两个端点。

## 三、详细流程

### 3.1 一个买家的 trace：从边缘到一分钟后的关单日志

一个买家发起秒杀下单，希望这次请求在事后可以被完整地追出来：它进了哪个实例、准入是放还是挡、
哪台实例把它落的库、最后是付掉了还是被关掉。这条链路从边缘代理生成 id 开始，到关单那行日志为止，
中间跨了两次进程边界。

- **第 0 跳：边缘生成**。反向代理里做了一个映射：调用方带了链路 id 头就用它，没带就用代理自己的
  请求 id 变量。代理的访问日志格式里第一列就是这个 id，后面是上游地址、状态码、请求耗时——所以
  「这个请求打到了哪个实例、多久、什么状态码」在应用之外就能回答。代理向上游转发时把这个 id
  作为请求头写进去。
  - 压测时**故意没有开限流模块**：漏斗在应用里，代理前面摆一个限流器测的就是限流器（详见第 12 章）。

- **第 1 跳：HTTP → 线程上下文**。应用侧的第一个过滤器（注册时给了最高优先级，排在所有过滤器和
  拦截器之前）读请求头。
  - 排在最前面是有讲究的：**被准入漏斗第一层的本地售罄标记挡掉的请求、被登录校验挡掉的请求，
    正是最值得查的那一类**；如果过滤器排在拦截器后面，这些请求就没有 id。
  - 外来的 id 要过一道校验：非空、不超过 64 个字符、只含字母数字连字符下划线。**不合法就整个换掉，
    绝不修补**。两个理由：一是这个值会进入这次请求的每一行日志，能往里塞换行的人就能伪造日志行；
    二是修补过的 id 仍然来自调用方，还和发送方自己记下的那个对不上，留着反而误导。
  - 通过校验就用它，否则现场生成一个 32 位十六进制的新 id。然后写进诊断上下文。
  - **响应头在调用链之前就设好**：业务处理可能提前提交响应，之后再设头会被无声丢掉。
  - 异步派发也要经过这个过滤器，否则异步那一段的日志会掉 id。
  - `finally` 里把线程上下文清空。容器的工作线程是复用的，不清的话下一个请求会继承上一个的 id——
    这是所有基于 ThreadLocal 的链路追踪最容易翻车的地方。

- **第 2 跳：线程上下文 → 消息体**。准入成功之后，发送秒杀订单消息的那一步，从当前线程上下文里
  取出 id 放进消息体。
  - 这里有个判断：**消息体里已经有 id 就不覆盖**，只有还没有 id 时才从上下文里取。写成这样是为了
    让「id 属于最初那次请求」这件事不被重投改写：谁重投都不会把自己这一刻的上下文盖上去。
  - 但要讲准一条：**目前唯一的另一个发送方——对账器——重建的消息压根不带 id**（它从 Redis 预占里
    只能重建券 id、用户 id、订单号），而且它跑在定时线程上、上下文本来就是空的。所以这条判断在
    现在的代码里实际从没救回过一个 id，它的真实效果是「重投不会伪造一个 id」，结果就是这类订单
    那一列为空（见第六节）。
  - 从此这个 id 离开了请求线程，活在消息体里。请求线程随即返回给买家一个「排队中」。

- **第 3 跳：消息体 → 落库线程 / 订单行**。落库那一侧有两条路径，用的机制不同：
  - **批量路径**：一个批次里混着几百个买家，**批次本身不属于任何一个 trace**，所以批量路径不往
    线程上下文里写任何 id——批处理的日志行因此一律不带 id：整批级别的（认领整批失败、整批重投、
    整批降级）带批大小和券 id，逐条级别的（预占归属不符、提交后标记成功失败）带订单号。
    每条消息的 id 被放进那一行订单的一个字段，随 `INSERT IGNORE` 一起写下去。
  - **从消息体里拿出来的 id，在写进订单行、装到线程上、放进关单消息之前，都要再过一遍和 HTTP
    入口同一道校验**（长度、字符集），不合法就当成没有。理由一样：这个值要么进日志、要么进库，
    来源都是进程外。
  - **退化到单条路径**时（批次被拒或数量对不上，详见第 05 章），每条消息在自己的 trace 下执行并
    恢复线程原样：这些日志行属于买家，不属于崩掉的那个批次。
  - **为什么落库用「列」而不是 SQL 注释**：一个批次把 N 个买家合成一条 INSERT，这条语句根本没有
    单一的 trace，注释写谁都不对；而且每请求不同的注释会让预编译语句的文本每次都变，等于在热路径上
    把语句缓存扔掉。列不会——它只是那条本来就要执行的 INSERT 多写的一个字段，而且**比日志轮转
    活得久**：日志滚掉之后，「哪个实例接的、哪个实例落的库」还能从数据里查回来。

- **第 4 跳（时间上的一跳）：一分钟之后的关单**。落库成功后，调度器给关单主题发一条定时消息，
  投递时间是「现在 + 支付超时 + 1 秒」的冗余（那 1 秒是因为截止时间由数据库时钟算、比发送这一刻略晚，
  早投一点会被判定「还没到期」而白白走一轮 Broker 重试）。消息体里带着买家的链路 id。
  - 支付超时默认 15 分钟；全链路演练把它调成 60 秒，所以演练里是「一分钟后」那行关单日志。
  - 到点后关单消费者拿到消息，**先把买家的 id 装到自己这条消费线程上，执行完再把线程还原**——
    消费线程是池化的，不还原就会污染下一条消息。于是那句「未支付订单已关闭」和当初那次下单请求
    共用一个 id，**而且写在三个实例中的哪一个都无所谓**。
  - 如果关单时发现还没到期（Broker 与数据库的时钟有出入），抛异常让 Broker 按退避重投；定时消息
    彻底没送到时还有兜底扫描（详见第 06 章）。

- **失败与缺口**：整条链路上没有任何一步会因为 id 的问题让业务失败——生成不了就生成新的，校验不过
  就换新的，消息里没有就留空。id 只影响「事后查不查得到」。覆盖面是：**HTTP 全量；MQ → DB 这一跳
  只接了秒杀链和关单链**，支付回调和营销发放的消息没接，因为它们不跨实例交付一笔订单的所有权。

### 3.2 一轮积压采样：把「变慢」变成数字

两个采样组件各自按固定节奏跑一轮，目的是把几条异步补偿链的**队头年龄**和**待办数量**写进仪表盘。
一轮从定时触发开始，到这个组件负责的那几个数字被刷新（或被置成 NaN）为止，全程只读。两个组件
用的是同一份配置（同一个开关、同一个初始延迟、同一个间隔），但各自有自己的调度，不共享一轮。

- **开关与节奏**：采样整体受一个开关控制，关掉时组件连实例都不创建；启动后先等 10 秒（给依赖留出
  连接时间），此后每轮之间固定间隔 30 秒，**并且配置校验强制最小间隔 15 秒**——采样要读数据库和
  Redis，间隔太小会让「观测」自己变成负载。用的是固定延迟而不是固定频率：上一轮慢了不会堆出第二轮。
- **点赞发件箱**：一条 SQL 取「未处理条数」和「最老那条的 id」，强制走未处理专用索引；条数为 0 就
  直接把两个数字都写成 0 并返回——**空是一个真实的计数，但没有「最老的一行」可以算年龄**。非 0 时
  再按 id 单点查它的创建时间，用当前时间减出年龄（下限 0）。
- **秒杀处理中索引**：库存是按桶分片的（详见第 04 章），每个桶有自己的「按到期时间排序的处理中
  索引」，所以**待办数是各桶之和、最老超期取各桶的最大值**。每个桶跑一个只读的 Lua：
  - 脚本第一件事是取 **Redis 服务端时间**，而不是接受应用传进来的时间戳。多实例各自的时钟不一定
    一致，用服务端时间才能保证「到期」这个判断在所有采样者眼里是同一个基准。
  - 用这个时间对有序集合做一次区间计数，得到已到期的预占数；数量大于 0 时再取分数最小的那一个
    成员，用「现在减它的分数」算出最老一条超期了多久（下限 0）。
  - 返回一个用竖线分隔的字符串，Java 侧按严格的非负整数正则解析，形状不对就当这一轮失败。
- **热榜**：直接问热榜服务「当前发布的那份快照多久之前生成的」。
- **券发放通知发件箱**：同样是「待处理条数 + 最老一条创建时间」，只是走 mapper 而不是裸 SQL；
  条数为 0 时年龄写成 NaN 而不是 0——这里选择了「没有这个数」而不是「这个数是 0」。
- **失败行为**：每个采样各自 try/catch，**运行时异常一律不向上抛**，而是把这一组仪表盘数字置成
  NaN 并给这个采样器的失败计数加一（券发放通知那个只置 NaN，没有计数器）。
  - 置 NaN 而不是留住上一轮的值，是因为**留住旧值会让一个已经瞎了的仪表看起来一切正常**——这是
    监控里最危险的一种假象。抓取端看到 NaN 就知道「这个数现在不可信」，和「这个数是 0」完全区分开。
  - 采样器成功/失败各有一个计数器，所以「仪表为什么没数」本身也是可观测的。
  - 一个采样失败不影响同一轮里的其他采样（它们是顺序执行但各自包了异常）。

### 3.3 指标词表：为什么它必须是有限的

这不是一条请求链路，而是一个约束：**任意字符串永远不会变成标签值**。

- 所有维度都是枚举（消费结局十种、缓存资源两种 × 结果八种、认证入口三种 × 结局六种、落库结果
  两种、批次阶段两种……），并且在组件构造的时候**把枚举的全部组合预先注册一遍**。
  - 只有准入漏斗那一组是例外：结果三种、原因七种，但不是叉乘，而是**按真实可能的搭配手工列出来
    注册**（秒杀资源只有「放行/无原因」和四种拒绝或不可用的搭配；两种本地受限读资源各三种）。
    叉乘会造出「放行，原因是 Redis 故障」这种永远不会发生、只会让看板多出空序列的组合。
- 预注册带来两个好处。一是**基数封顶**：指标是长期驻留在注册表里的，如果标签值来自券 id、用户 id、
  异常消息，注册表会随流量无限增长，这类事故在生产里很常见。二是**「零」也是一个值**：预注册之后
  一个从未发生过的结局也会以 0 出现在抓取结果里，看板不会因为「这个序列不存在」而画不出线，
  也不会把「没发生」和「没埋点」混为一谈。
- 记录方法都是**按枚举取已注册的表项**，而不是现场拼字符串建指标。
- 埋点本身不许影响业务：**每一次计数器自增、每一次耗时/分布记录都包在 try/catch 里**（取不到已注册
  的表项时直接跳过），记录批大小那一步还单独注释了原因——**一个已经提交的批次不能因为指标出错
  而失败**。
- 批大小故意分成两个阶段量：「Broker 投递给消费者的一批有多少条」和「一条 INSERT 加一次扣库存
  真正承载了多少单」。**这两个数之间的差，就是一次批量落库快或慢的全部故事**；正是这个仪表
  在 M6 一开头量出了「批大小实测 1.03」，从而把瓶颈从「提交速率」改判成「批根本没攒起来」
  （详见第 12 章）。
- 消费结局枚举得很细（已成功、已失败、认领被占、预占归属不符、状态缺失、已补偿、临时错误、
  补偿错误、格式错误、已落库），因为复制空窗演练里「多放出来的人在哪一步被挡下」这个问题，
  答案就藏在这几个计数器的相对大小里。

## 四、口述版

### 4.1 一个 trace 三跳

我先说这个链路要解决什么：下单被拆成准入、落库、关单三段，分别跑在不同的实例上，所以必须有一个
id 把它们串起来，不然多实例之后「这个买家怎么了」只能靠猜。

最前面是反向代理。调用方带了链路 id 头就用它，没带就用代理自己的请求 id 生成一个，写进访问日志的
第一列，再作为请求头转给上游——这样边缘日志和应用日志共用一个 id，我能先知道这个请求打到了哪台实例、
状态码和耗时是多少。

请求进到应用，第一个过滤器就是处理这个 id 的，我把它注册成最高优先级，排在所有过滤器和拦截器前面，
因为被准入漏斗第一层售罄标记挡掉、或者被登录校验挡掉的请求恰恰是最值得查的，晚一步它们就没有 id 了。
过滤器先校验外面带进来的值，长度、字符集都得对；不对我不修，直接换一个新的，因为这个值会进到这次
请求的每一行日志里，能往里写换行的人就能伪造日志行，而且修补过的 id 和发送方自己记下的那个也对不上。
然后把 id 放进日志框架的诊断上下文，日志格式串里有个占位符会去取它，于是每一行日志自动带 id，我不用
一个参数一个参数地传。响应头必须在调用链之前就设，因为业务可能提前提交响应，之后再设头会被无声丢掉。
最后在 finally 里把上下文清掉，因为容器的线程是复用的，不清下一个请求就继承了上一个的 id。

准入成功以后要发消息，这里是第二跳：id 从线程上下文搬进消息体。只有消息体里原本没有 id 时我才写，
已经有的不覆盖，这样「id 属于最初那次请求」就不会被任何一次重投改写掉。不过我得讲准：现在唯一的
另一个发送方是对账器，它从 Redis 预占里重建的消息本来就没有 id，而且它跑在定时线程上、上下文也是
空的，所以这个不覆盖在今天的代码里实际上从没救回过一个 id，它真正保证的是重投不会伪造一个——
代价就是这类订单那一列是空的。发完消息请求就结束了，返回买家一个排队中。

第三跳是落库。这里我没有用 SQL 注释，而是在订单表上加了一列。原因是一个消费批次会把几百个买家合成
一条 INSERT，这条语句根本没有单一的 trace，注释写谁都不对；而且每请求不同的注释会让预编译语句的
文本每次都不一样，等于在热路径上把语句缓存扔了。列就没有这个问题，它只是那条本来就要执行的 INSERT
多写的一个字段，而且比日志轮转活得久——日志滚掉以后，哪台实例接的、哪台实例落的库，还能从数据里查。
这一列是可空的，因为对账器从 Redis 预占重建的订单背后已经没有请求了。批量路径上我不往线程上下文里
写任何 id，因为批次本身不属于任何一个 trace——代价是这一批打的日志行全都不带 id；只有退化成单条
处理的时候，我才把每条消息的 id 装到线程上，执行完还原，那些日志行属于买家而不属于崩掉的批次。
还有一点：从消息体里拿出来的 id，不管是写进订单行、装到线程上还是塞进关单消息，都要再过一遍和
HTTP 入口同一道长度与字符集校验，因为它同样是从进程外来的。

最后还有时间上的一跳。落库成功后给关单主题发一条定时消息，带上买家的 id，投递时间是现在加支付超时
再加一秒——那一秒是因为截止时间由数据库时钟算，比发送这一刻略晚，早投会被判成还没到期、白走一轮
Broker 重试。默认超时是十五分钟，演练里调成六十秒。到点之后关单消费者拿到消息，先把买家的 id 装到
自己这条消费线程上，处理完再还原，因为消费线程是池化的，不还原会污染下一条消息。于是一分钟以后那句
「未支付订单已关闭」和当初那次下单请求共用一个 id，而且落在三个实例的哪一个上都无所谓。

覆盖面我得说清楚：HTTP 这一跳是全量的，MQ 到 DB 这一跳只接了秒杀链和关单链，支付回调和营销发放的
消息没接，因为它们不跨实例交付一笔订单的所有权。

### 4.2 积压采样

可靠性在这个系统里靠的是几条异步补偿链——对账器、点赞发件箱、券发放通知发件箱——它们的特点是不容易
出错，只会变慢，而变慢的唯一表现就是积压。所以我做了低频只读的采样，把队头年龄和待办数量写成仪表盘。

节奏是启动后先等十秒给依赖留连接时间，之后每轮之间固定间隔三十秒，用的是固定延迟不是固定频率，
上一轮慢了不会堆出第二轮；配置里还强制最小十五秒，因为采样本身要读库读 Redis，间隔太小观测就变成了
负载。整个采样有开关，关掉时组件都不创建，因为它跟业务没有任何耦合。

点赞发件箱那边是一条 SQL 拿到未处理条数和最老那条的 id，走未处理专用索引；条数为零就直接把两个
数字都写成零返回，因为空是一个真实的计数，而这时候没有「最老的一行」可以算年龄。非零时再按 id
单点查创建时间，用当前时间减出年龄。券发放通知那个发件箱是同一套做法，只是走 mapper 不是裸 SQL，
而且条数为零时年龄写的是 NaN 不是零——同一个问题我在两处做了不同的选择，这一点我得承认不统一。

秒杀那边麻烦一点，因为库存是分桶的，每个桶有自己的按到期时间排序的处理中索引，所以待办数是各桶之和、
最老超期取各桶的最大值。每个桶跑一个只读 Lua，脚本第一件事是取 Redis 服务端时间而不是用应用传进来的
时间戳，因为多实例的时钟不一定一致，只有用服务端时间，「到期」这个判断在所有采样者眼里才是同一个基准。
然后按这个时间做一次区间计数拿到已到期的数量，数量大于零时再取分数最小的那个成员，用现在减它的分数
算出最老一条超期了多久。

失败行为是这里最值得讲的一点：任何异常我都不往上抛，而是把这一组数字置成 NaN，再给这个采样器的失败
计数加一。置 NaN 而不是留住上一轮的值，是因为留旧值会让一个已经瞎了的仪表看起来一切正常，那是监控里
最危险的假象；抓取端看到 NaN 就知道这个数现在不可信，和「这个数确实是零」完全区分得开。而且采样器
自己的成功失败也是计数器，所以「仪表为什么没数」这件事本身也是可观测的——不过这只做到三个，
券发放通知那个采样器只有置 NaN、没有成对的计数器，这是个已知的漏。

### 4.3 指标词表

我这边有一条硬规则：任意字符串永远不会变成标签值。所有维度都是枚举，而且在组件构造的时候就把它们
预先注册一遍——大部分是整个叉乘，只有准入漏斗那一组是手工列出真实可能的搭配，因为叉乘会造出
「放行，原因是 Redis 故障」这种永远不发生、只会多出空序列的组合。这么做一是基数封顶——指标是长期驻留在注册表里的，标签值要是来自券 id、用户 id
或者异常消息，注册表会随流量无限增长；二是让零成为一个值，预注册之后一个从没发生过的结局也会以零
出现在抓取结果里，看板不会因为序列不存在而画不出线，也不会把「没发生」和「没埋点」混在一起。埋点
本身不许影响业务，所以每一次自增、每一次耗时记录都包了异常，因为一个已经提交的批次不能因为指标
出错而失败。

指标里我最看重两个。一个是批大小，它故意分成两个阶段量：Broker 投递给消费者的一批有多少条，和一条
INSERT 加一次扣库存真正承载了多少单；这两个数的差就是一次批量落库快或慢的全部故事，也正是这个仪表
量出了批大小实测一点零三，把瓶颈从「提交速率不够」改判成「批根本没攒起来」。另一个是消费结局，
它枚举得很细——已落库、已成功、已失败、认领被占、预占归属不符、状态缺失、已补偿、临时错误、补偿错误、
格式错误——因为复制空窗演练里「多放出来的人到底在哪一步被挡下」这个问题，答案就藏在这几个计数器的
相对大小里。

## 五、为什么这么设计 / 会被怎么追问

- **为什么不直接上 OpenTelemetry / SkyWalking？** 这个项目要回答的问题非常具体：一个买家跨三个实例
  的一条链、几条补偿链的积压。一个 MDC 里的 id 加一列数据库字段就能回答，代价是几十行代码和一个可空列；
  引入完整的追踪体系要额外跑采集器和存储，而且**订单行上的那一列是追踪系统给不了的**——追踪数据有
  保留期，订单行没有。代价写在下面「已知边界」里：没有 span、没有耗时拓扑，只有「同一个 id 的日志行」。
- **为什么落库是列而不是 SQL 注释？** 批量 INSERT 没有单一 trace；每请求不同的注释会让预编译语句
  文本每次都变，热路径上丢掉语句缓存；日志会轮转，列不会。
- **不合法的 traceId 为什么不修补而是换掉？** 它会进入这次请求的每一行日志，允许换行就等于允许
  伪造日志行——这是日志注入。而且修补过的 id 仍然来自调用方、和发送方记的对不上，留着反而误导。
- **MDC 是 ThreadLocal，线程池怎么办？** 三处都处理了：HTTP 过滤器在 finally 清空（容器线程复用）、
  消费线程在执行前后装上/还原（消费线程池化）、批量路径干脆不装（批次不属于任何 trace）。
  异步派发也走同一个过滤器，否则异步那一段会掉 id。
- **对账器重投的消息，trace 从哪来？** 没有。发送那一步只在消息体还没有 id 时才从上下文取，
  所以**任何重投都不会伪造一个 id**；而对账器从 Redis 预占重建的消息本来就不带 id、它那条定时线程
  的上下文也是空的，于是订单行上那一列是空——这正好告诉你「这单不是某次请求直接建的」，
  是一条有信息量的空值。
- **采样失败为什么置 NaN 而不是保留上一次的值？** 保留旧值会让一个已经失效的仪表看起来正常，
  这是监控里最危险的假象。NaN 把「不可信」和「确实是 0」区分开，另外成功/失败计数器让仪表本身
  也可被观测。
- **采样会不会把自己变成负载？** 低频（间隔 30 秒、强制下限 15 秒）、只读、固定延迟（不会堆叠）、
  可整体关闭、失败不抛；Redis 侧那个脚本只做一次区间计数加一次最小分数查询。
- **指标为什么全是枚举？** 标签基数一旦来自用户输入就会爆，而且预注册让「零」也成为一个值。
- **积压之外怎么判断落库侧健康？** 看「投递批大小」与「落库批大小」的差，再看提交次数/秒——
  1、2、3 个实例下这个数都在 70–115 之间、**与实例数没有关系**，指向的是每批都要更新的同一行
  库存（详见第 12 章）。
- **指标暴露在哪、安全吗？** 独立的管理端口，默认只绑回环地址，只暴露健康检查和指标抓取；
  健康检查不显示细节，就绪探针包含数据库和 Redis。另外日志级别被压到 info，为的是不让 mapper
  参数（里面有密码哈希和用户数据）进日志。

## 六、已知边界

- **没有分布式追踪，只有一个 id**。没有 span、父子关系、跨服务耗时拓扑；「这一跳花了多久」只能靠
  同一个 id 的日志行时间戳去减。
- **覆盖面不全**：MQ → DB 这一跳只接了秒杀链与关单链；支付回调链、营销发放链的消息没有携带 id。
- **批量落库路径的日志行不带 trace**（已核对代码：批量那一侧全程没有写线程上下文，只有退化到单条
  时才写）。订单行上有 id，但那台实例处理这一批时打的日志都不属于任何 trace：整批级别的只能靠
  券 id、批大小和时间去对，逐条级别的至少还带订单号，可以从订单号反查回那一行的 id。这是
  「批次不属于任何一个 trace」的直接代价。
- **对账器重建的订单没有 id**，迁移之前的订单也没有，所以那一列可空，按 id 反查订单时这些单查不到。
- **没有看板**。指标以抓取端点的形式暴露，聚合与告警没有做（原计划里的看板在 M8 被砍掉）；现在看
  这些数靠的是压测脚本自己采集和事后查。
- **没有告警**：积压仪表存在，但没有任何阈值会主动通知人；NaN 也只是一个值，没人盯就没人知道。
- **券发放通知发件箱的采样器没有成功/失败计数器**，只有仪表置 NaN——另外三个采样有成对的计数器，
  这一个漏了，所以它「为什么没数」比别的难查。
- **「空积压」的年龄在两处不一致**：点赞发件箱条数为 0 时年龄写 0，券发放通知发件箱写 NaN。
  两种都说得通，但同一套仪表里应该统一，现在没有。
- **单条消费路径上还留着一对更早的成功/失败计数器**，和词表里那十种消费结局并存；它们标签固定、
  不会撑爆基数，但同一件事被数了两遍，看的时候要知道该看哪个。
- **日志本身没有集中收集**：多实例时是逐个实例的日志文件，按 id 查要一个文件一个文件地查
  （命令详见第 12 章第八节）。
