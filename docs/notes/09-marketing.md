# 09 营销：定向活动、额度与幂等、批量发放与到账通知

## 一、这一章解决什么问题

商户想做的事很朴素：挑一批人（老客、到过店的、投诉过的），给他们发一张普通券，发完为止，
发过的人不能重复领，后台随时能暂停。难点不在「发」，难在**同一张券有四个发放入口**——
用户自己点领取、后台给单个用户发、用户签到换奖励、后台按标签批量发几万人——
而这四个入口必须共用同一份额度、同一套资格判断、同一个幂等边界，否则额度一定会超发。

第二个难点是**运营改规则和用户领券是并发的**：商户在后台把额度从 1000 改成 500、把活动暂停、
把绑定的券换掉，这些动作发生的同一秒钟里有人正在领。所以活动定义需要一个版本号，
所有写操作都带上「我看到的是第几版」。

第三个难点是**发完之后要让用户知道**。应用是多实例的，发券的那个实例不一定是用户 WebSocket
连着的那个实例；而且用户可能压根没开着页面。所以通知既要能跨实例扇出，又不能把「通知」
当成事实——事实永远是数据库里那条发放记录。

## 二、涉及的数据

**标签表**（商户维度的人工标签）：所属商户、标签编码（商户内唯一，大写字母数字下划线短横线 2–64 位）、
名称、状态（启用 / 停用）、创建人。除了主键之外还建了一个（主键，商户 id）的复合唯一键——
它本身没有查询用途，唯一作用是**让别的表可以用（标签 id，商户 id）两列一起做外键**，
从数据库层面堵死「A 商户的活动绑到 B 商户的标签上」。

**标签成员表**：（标签 id，用户 id）唯一键、所属商户、状态（有效 / 已移除）、可空的过期时间、
挂标签的后台账号、挂的时间。外键用（标签 id，商户 id）指向上面那个复合唯一键。
过期时间为空表示永不过期；不为空且已经到点，等同于没有这个标签。

**活动表**（本章主角）：所属商户、绑定的券模板 id、名称、
发放模式（用户领取 / 后台发放 / 两者都可 / 任务奖励）、
资格类型（全体 / 人工标签）、需要的标签 id（只有人工标签模式才有，且必须有）、
开始与结束时间、额度总数、已发放计数、
状态（草稿 / 生效 / 暂停 / 关闭）、**规则版本号**（建的时候是 1）、创建人。
已发放计数和额度总数在同一行上，所以「扣额度」就是一条带 `granted_count < quota_total` 条件的自增。
规则版本号在**每一次定义变更和每一次状态变更**时加一。

**发放流水表**（「谁在哪个活动上拿到过什么」的唯一事实）：活动 id、商户 id、券模板 id、用户 id、
来源枚举（用户领取 / 后台发放 / 任务奖励 / 批量发放）、**幂等键**、发放时的规则版本、
后台操作人（用户自己领取时为空）、发放时间。
唯一键是（活动 id，用户 id，幂等键）三列。
最初的唯一键只有（活动 id，用户 id），加签到奖励时才换掉——迁移里先把存量行的幂等键回填成
一个固定串，再把列改成非空，最后才换唯一键，顺序不能反。
这张表只是「发放这件事」的记录，用户手里那张券是另一张表，**详见第 07 章**。

**签到表**：用户 id、年、月、日期，（用户 id，日期）唯一键。加这个唯一键的迁移里先按
（用户 id，日期）分组删掉 id 较大的重复行、只留最早的一条，否则唯一键建不上去。

**批量发放 Job 表**：商户 id、活动 id、操作人、**请求 id**（与商户组成唯一键，就是接口的幂等边界）、
**快照下来的规则版本**、目标标签 id、
状态（快照中 / 待跑 / 运行中 / 暂停 / 完成 / 部分失败）、目标人数、开始与结束时间。

**批量条目表**：（Job id，用户 id）唯一键、状态（待处理 / 已发放 / 幂等命中 / 业务跳过 / 技术失败）、
发出去的流水 id、尝试次数、最后一次的错误码与错误信息。
外键对 Job 是级联删除，对发放流水是删除置空——条目是结果快照，不该反过来钉住业务数据。

**通知 Outbox 表**：发放流水 id（唯一键，一条发放最多一条通知）、商户 id、用户 id、
事件类型（目前只有「券已发放」一种）、状态（待发 / 已发布）、尝试次数、**下次尝试时间**、
最后一次错误、创建时间、发布时间。取待发任务的索引是（状态，下次尝试时间，主键）三列复合。

**Redis**：每个用户一个发放通知频道，频道名里带用户 id。每个应用实例都按模式订阅这一族频道。
（秒杀回执、平台与商户后台的实时订单频道复用同一套机制，详见第 04、06 章。）

## 三、详细流程

### 3.1 后台建标签、往标签里挂人

商户后台的运营人员想把某个用户打上「老客」标签，以便后面只对这批人发券。
这个请求到成员行写入数据库并回读为止。

● 请求先过后台鉴权，要求营销写权限；数据范围在这里就收敛好了：平台账号必须显式传商户 id，
  商户账号只能用自己的商户 id，传了别人的直接 403。**详见第 02 章**。
● 建标签时编码统一转大写再校验格式，插入撞唯一键就翻译成「当前商户已存在相同标签编码」。
● 挂成员时先按（标签 id，商户 id）把标签行锁住，确认它是启用状态；过期时间如果传了，
  必须晚于当前时刻。
● 然后检查这个用户和这个商户**是否已经有业务关系**——要么在这个商户下拿到过券，要么在这个商户下过单。
  没有关系就拒绝，这是防止商户拿后台当用户枚举器。
  ○ 这两个条件是**两条独立的语句**，不是一条 SQL 的 OR。因为订单表按用户分片而用户表不分片，
    一条语句同时碰两边会被路由到一个没有用户表的库上去（分片规则详见第 08 章）。
    所以「在这个商户下过单」这一条还要再补一条「这个用户真的存在」。
● 最后是一条带「重复则更新」的插入：已经存在同一对标签与用户就把状态改回有效、刷新过期时间和挂标人。
  移除成员不是删行，是把状态置为已移除——标签成员关系本身是审计材料。

### 3.2 后台定义活动：规则版本号是并发边界

运营创建或修改一个活动，希望修改要么整体生效要么整体不生效，并且不会覆盖掉别人刚刚做的改动。
这一步到活动行更新成功并回读为止。

● 创建时活动落成草稿状态、已发放计数 0、规则版本 1。
  ○ 绑定的券必须是**当前商户已上架的普通券**（券类型是普通券、状态是上架、且它所在店铺属于这个商户），
    这三个条件写在一条计数语句里，返回不等于 1 就拒绝。
  ○ 人工标签资格与标签 id 必须**同时存在或同时不存在**，多一个少一个都算参数错误。
  ○ 开始时间必须早于结束时间，额度必须是正数。
● 修改定义时，调用方必须同时带上「我看到的状态」和「我看到的规则版本」。
  ○ 只有草稿和暂停两个状态可编辑。
  ○ 先把活动行锁住比对状态，再执行一条**条件更新**：更新语句的 WHERE 里同时带上商户、
    期望状态、期望规则版本、状态仍在草稿或暂停、**新额度不小于已发放数**、
    以及「已发放数为 0，或者券没被换掉」。SET 里规则版本加一。
  ○ 影响行数不是 1 就报冲突。这里是真正的并发边界：前面那次读与锁只是为了给出更准的错误信息，
    正确性由这一条带条件的 UPDATE 保证。
● 改状态走另一条同样形态的条件更新。允许的流转是：草稿→生效 / 关闭，生效→暂停 / 关闭，
  暂停→生效 / 关闭。关闭是终点（把状态改成当前状态也放行，见第六节）。
  ○ **每一次状态变更之前都会再校验一次绑定的券和标签仍然有效**，不只是改成生效的时候。
    改成生效时这道校验是为了别把绑着已下架券的活动放出去；关闭时它也照跑，这是副作用（见第六节）。

### 3.3 发放：四个入口，一个出口

用户点「领取」、后台点「发给某人」、用户签到后领今日奖励、批量 Job 逐个发——
四条路都走同一个发放门面，以一条发放流水提交、并连带产出一张券为止。

● **外层门面自己不开事务**（批量发放时它仍然跑在批量 worker 的外层事务里，见第六节）。它做三件事：补服务端字段、校验参数、走快路径查一次有没有发过。
  ○ 幂等键是**服务端算的，不接受客户端传**：普通领取与后台发放共用一个固定串（表示「这个活动一辈子一次」）；
    签到奖励是「任务奖励 + 每日签到 + 业务日期」拼成的串，业务日期由应用侧一个统一的业务时钟给出，
    时区固定为东八区。所以同一个活动上，普通模式每人一条，任务模式每人每天一条。
  ○ 快路径查到已有流水就直接返回「幂等命中」，**连活动行的锁都不去拿**。批量发放重跑时
    绝大多数条目走的就是这条路。
● 查不到才进入内层事务，事务传播是 `REQUIRES_NEW`。
  ○ 如果是签到奖励，事务里第一件事是查签到表有没有今天这一行；没有就抛「请先完成今日签到」。
    签到本身是另一个接口，靠（用户 id，日期）唯一键幂等，撞键就当作已签到，不报错。
  ○ 然后再查一次流水（还没拿锁）。
  ○ 接着 `SELECT ... FOR UPDATE` 锁住活动行。后台发放与批量发放按（活动 id，商户 id）锁，
    用户领取只按活动 id 锁——用户侧没有商户上下文。
  ○ **拿到锁之后必须再查一次流水**。一个请求可能在「查过、没有」和「拿到锁」之间被另一个
    并发请求插进来发完了；不复查就会重复发。
  ○ 比对规则版本：调用方带来的期望版本和活动行上的当前版本不一致，直接报「规则已变化」。
  ○ 校验发放模式与来源是否匹配（领取模式不允许后台发、任务模式只允许任务奖励，以此类推）。
  ○ 取**数据库当前时间**判断时间窗和状态：不是生效状态、还没开始、已经结束，三种情况分别报错。
    时间一律走数据库时钟，不用应用实例的本地时钟。
  ○ 复核绑定的券仍是这个商户的、上架的普通券，否则按「规则已变化」处理。
  ○ 人工标签资格的活动，还要按**活动 → 标签 → 成员**这个固定顺序把标签行和成员行锁住，
    确认标签启用、成员有效、成员没过期。顺序固定是为了和挂标签那条链路用同一个加锁顺序，避免死锁。
● 扣额度：先读一眼已发放数是否已经满额（满了直接报「额度已用尽」，省掉一次写），
  再执行条件自增——WHERE 里同时带活动 id、商户 id、券 id、规则版本、状态生效、时间窗、
  以及 `granted_count < quota_total`。
  ○ 影响行数不是 1 时，用当时读到的活动快照**逐条分类**：先看规则版本、再看时间窗、
    再看额度，都说得通就笼统报「规则已变化」。这一步只影响错误码的精度，不影响正确性。
● 写发放流水，把来源、幂等键、当前规则版本、操作人一起写进去。
● 同一个事务里写一条待发的通知 Outbox 行。
● 同一个事务里调发券组件产出券资产（券号、核销码、有效期都在那边算，**详见第 07 章**）。
  至此提交：额度、流水、通知、券四件事同生共死。
● 内层事务如果撞上唯一键异常（两个请求同时通过了复查），门面会**在事务外**再查一次：
  查到就返回幂等命中。门面不开事务正是为了这个——内层那次失败的事务（包括它已经做的额度自增）
  必须先回滚掉，回查才读得到干净的状态。
● 其它失败的归类：数据库不可用翻译成 503；业务冲突原样抛 409。
  每一次发放不论成败都会按「来源 × 结果」打一个计数、并记一次耗时。

### 3.4 批量发放 Job：快照、分批、四种结果

运营选一个人工标签活动，说「把当前这批标签成员都发一遍」。这条链路从建 Job 开始，
到 Job 落到完成或部分失败为止，中间可以暂停、恢复、重试。

● **建 Job**（同步接口）：请求必须带一个请求 id，格式限定为 1–96 位的安全字符。
  ○ 先按（商户，请求 id）查一次，查到就直接返回那个 Job——接口重试不会建出第二个 Job。
  ○ 校验活动：规则版本一致、发放模式允许后台发、资格类型必须是人工标签、状态必须是生效；
    目标标签必须存在且启用。
  ○ 插入用的是「重复则把主键回填成已存在那行的主键」的写法，插完**再按（商户，请求 id）回读一次**，
    因为并发下可能是别人赢了那个唯一键。
  ○ Job 落地时状态是「快照中」，目标人数 0，并且把**活动当时的规则版本抄在 Job 上**。
    这一份抄件是后面每一次发放要带的期望版本：Job 跑到一半运营改了活动，剩下的条目就会全部
    因为版本不匹配而停下，而不是按新规则继续发。
● **快照**（后台 worker 的一个 tick）：取一个状态为「快照中」的 Job 并锁住，
  用一条 `INSERT ... SELECT` 把此刻满足条件的成员一次性写成条目——标签启用、成员有效、
  成员没过期，全部写在这条语句的 WHERE 里。然后数一次条目数，把 Job 置为「待跑」并写上目标人数。
  ○ 快照之后再加入标签的用户**不会**被补进这个 Job，这是有意的：Job 的目标集合是不可变的。
● **执行**（同一个 worker 的同一个 tick，快照之后）：
  ○ 取一个状态为「待跑」或「运行中」的 Job 并锁住；「待跑」的话先条件更新成「运行中」并记开始时间。
  ○ 取一批状态为待处理的条目并锁住，批大小默认 50（配置上限 500）。
  ○ 逐条调 3.3 那个发放门面，来源标成批量发放，期望规则版本用 Job 上抄下来的那份。
    每条发放是自己的 `REQUIRES_NEW` 事务，**互相独立提交**。
  ○ 结果落成四类：新发成功记「已发放」并回填流水 id；快路径命中记「幂等命中」；
    抛出来的是一组**稳定业务码**之一（规则已变、模式不支持、未生效、未开始、已结束、
    不满足标签、额度用尽、活动不存在、活动拒绝）就记「业务跳过」——重试也没用。
  ○ 兜底比这张白名单更宽：**凡是带 4xx 状态的业务异常一律记「业务跳过」**，错误码统一落成「活动拒绝」。
    活动查不到时抛的是一个不带错误码的 404，实际走的就是这条兜底而不是白名单。
    只有 4xx 之外的（典型是数据库不可用翻译出来的 503）才记「技术失败」，等人工触发重试。
  ○ 条目结果的写入语句带「这一条仍然是待处理」的条件，尝试次数自增。
  ○ 这一批处理完，如果整个 Job 已经没有待处理条目了，就按有没有技术失败把 Job 收成
    「完成」或「部分失败」，并写结束时间。
● worker 是定时任务：启动后 5 秒开始，每轮结束后 1 秒再来一次，可以用开关整体关掉。
  一次 tick 抛异常只写一条错误日志，事务回滚后持久状态原样留给下一个 tick。
● **暂停 / 恢复 / 重试失败项**都是带条件的更新：暂停只对待跑或运行中生效；恢复只对暂停生效，
  回到待跑；重试只把「技术失败」的条目重置回待处理并清掉错误信息，一条都没重置就报
  「没有可重试的技术失败项」，如果 Job 当时是部分失败还要把它重开成待跑。
  **业务跳过的条目永远不会被重试**。
● Job 详情页上的各状态条目数不是存下来的字段，是查询时用五个相关子查询现算的。

### 3.5 到账通知：Outbox → Redis 扇出 → WebSocket，以及离线兜底

券发出去了，希望正开着页面的用户立刻看到「优惠券已到账」，而没开页面的用户下次进来也不会漏掉。
这条链路从 3.3 里那条 Outbox 行写入开始，到消息进入用户浏览器、或者被判定为暂时发不出去为止。

● Outbox 行是**和发放流水、券资产在同一个事务里**写的，所以不存在「发了券没通知」或
  「通知了没发券」。这是用 Outbox 而不是在事务里直接推的唯一理由：Redis 的推送不能参与数据库事务。
● 通知 worker 每轮取一批到期的待发行并锁住，批大小默认 50。
  「到期」的定义是状态为待发且下次尝试时间已经到了，按（下次尝试时间，主键）排序，取前缀。
  取的时候顺便 JOIN 出流水上的活动 id 和券 id，通知负载里要用。
● 对每一行：往**该用户专属的那个 Redis 频道**发一条 JSON，内容包括事件类型、事件 id、
  发放流水 id、活动 id、券 id 和一句提示文案。id 全部转成字符串——
  它们超出 JavaScript 安全整数范围。
  ○ 发送成功就把这一行条件更新成已发布并记发布时间。
  ○ 抛异常就走退避：尝试次数加一（封顶 10），下次尝试时间 = 现在 + 退避时长，
    退避是 `2^(尝试次数-1)` 秒、封顶 5 分钟，并记下错误原因。**行仍然是待发**，下一轮还会被取到。
● 每个应用实例启动时都按模式订阅这一族用户频道。收到消息的实例从频道名里解析出用户 id，
  交给本实例的会话注册表。
  ○ 这就是多实例扇出的全部机制：发券的实例不需要知道用户连在谁身上，
    所有实例都收到，只有真正持有那条连接的实例发得出去，其余实例查不到会话直接返回没发出去。
  ○ 会话是在 WebSocket 握手时按查询参数里的 token 验出来的，验的是和 HTTP 请求同一份登录态。
  ○ **每次发送之前还要再验一次 token 仍然有效**，不刷新有效期。用户登出或 token 过期，
    已经建立的连接会在下一次推送时被关掉，而不是一直活到超时。
  ○ 同一个用户再连一次会顶掉旧连接。每条会话都套了并发发送装饰器，发送超时 10 秒、
    缓冲上限 256 KB，防止一个卡住的客户端拖住推送线程。
● **「已发布」只表示消息交给了 Redis，不表示用户收到了。** 用户没开页面时这条消息就是丢的，
  而这不要紧，因为事实在数据库里。
● 前端的兜底是显式的：WebSocket 断开或建不起来时，降级成轮询「我的发放记录」，
  每 2 秒一次、最多 10 次、总时长 30 秒；连上之后停止轮询。
  收到推送时先用事件 id 去重，再重新拉一次列表，然后才弹提示。
  ○ **页面上的券一律来自那次重新拉取，不来自推送消息**；只有弹窗那一句文案是直接用推送里带的，
    推送没带才退回前端的默认文案。所以推送决定的是提示的时机和措辞，不决定页面上的事实。
● 可观测性上另有一个只读采样器，定期数一次待发条数和最老那条待发的年龄，写进指标。
  待发条数为 0 时年龄写成非数，因为这时候没有「最老的行」可言。

## 四、口述版

**4.1 标签与成员。** 商户后台要先有标签才能定向。建标签的时候编码在商户内唯一，
所以同一个商户不会出现两个一样的标签，不同商户可以各自用同一个编码。挂成员之前我先把标签行锁住，
确认它还是启用的，然后检查这个用户和这个商户到底有没有业务关系——在这个商户下过单，
或者在这个商户下拿到过券——没有关系就不让挂，否则商户后台就成了一个可以枚举全站用户的接口。
这两个条件我是分两条语句问的，因为订单表是按用户分片的而用户表不分片，
一条语句同时碰两张表会被路由到一个根本没有用户表的库上。挂的时候用的是「撞了就更新」的写法，
所以重复挂不会报错、只会把状态改回有效并刷新过期时间；移除也不删行，只改状态，
因为这条关系本身要留作审计。

**4.2 活动定义。** 活动上有一个规则版本号，每改一次定义或状态都加一。
所有的写操作都要求调用方带上「我看到的状态」和「我看到的版本」，然后我把这两样东西
连同其它约束一起写进 UPDATE 的 WHERE 里，影响行数不是一行就报冲突。
这样做的好处是我不需要先读再判断再写——先读那一下只是为了给出更准的错误信息，
真正的并发正确性在那条带条件的更新里。额度也一样，改额度的时候 WHERE 里带一句
「新额度不小于已经发出去的数量」，所以运营不可能把额度改到比已发数还小；
已经发过券之后也不允许换绑定的券，这条同样写在 WHERE 里。状态的流转是草稿到生效或关闭、
生效到暂停或关闭、暂停到生效或关闭，关闭是终点；要改成生效之前我还会再确认绑定的券
和标签都还有效，免得放一个绑着已下架券的活动出去。

**4.3 发放。** 四个入口共用一个发放门面：用户自己领、后台发给某个人、用户签到后领今天的奖励、
批量 Job 一条一条发。门面本身故意不开事务，它只做三件事：算幂等键、校验参数、先查一次有没有发过。
幂等键一定是服务端算的，客户端传什么都被覆盖掉——普通领取和后台发放共用一个固定串，
意思是这个活动每人一辈子一次；签到奖励则是拿任务名和业务日期拼出来的，所以每人每天一次，
业务日期来自应用里统一的那个业务时钟，时区固定。先查一次是快路径，查到就直接返回幂等命中，
连活动行的锁都不去碰，批量重跑的时候绝大多数条目走的就是这一条。

查不到才进内层事务，传播级别是新起一个事务。如果是签到奖励，我先看签到表里今天有没有这个人，
没有就直接告诉他先去签到；签到本身是另一个接口，靠用户和日期的唯一键幂等，撞键就当已签到。
然后我把活动行锁住，**拿到锁以后必须再查一次流水**，因为在我等锁的这段时间里
另一个并发请求完全可能已经发完并提交了，不复查就会重复发。接着比对规则版本，
不一致就说规则变了让前端刷新；再看发放模式和这次的来源合不合，再用数据库时间判断
状态和时间窗，再确认绑的券还是这个商户上架的普通券。如果这个活动是人工标签资格，
我还要按活动、标签、成员这个固定顺序把标签和成员也锁住，确认标签启用、成员有效没过期——
顺序固定是为了跟挂标签那条链路一致，不然两条链路反着锁就会死锁。

额度的扣减是一条带条件的自增，WHERE 里同时钉住活动、商户、券、规则版本、状态、时间窗，
还有已发放数小于总额度这一句，所以超发在 SQL 这一层就不可能发生。更新失败的时候我再拿
刚才读到的快照逐条分类，是版本变了、还是时间窗过了、还是额度满了，这只影响错误码好不好看，
不影响正确性。然后写发放流水，同一个事务里再写一条待发的通知，再调发券组件产出真正的券资产，
最后一起提交——额度、流水、通知、券这四件事同生共死。万一两个请求同时挤过了复查，
后提交的那个会撞上流水的唯一键，这时候异常会一路抛出内层事务、把它刚才那次额度自增一起回滚掉，
门面再在事务外查一次，查到就返回幂等命中。门面不开事务就是为了这个顺序：
必须先让脏的那次回滚，回查才读得到干净的状态。

**4.4 批量发放。** 运营建 Job 的时候必须带一个请求 id，它和商户组成唯一键，
所以接口重试只会拿到同一个 Job。建的时候我把活动当时的规则版本抄一份在 Job 上，
这一份抄件后面每一条发放都带着；意思是 Job 跑到一半运营改了活动，剩下的条目会全部停下来，
而不是偷偷按新规则继续发。Job 落地时是「快照中」，后台 worker 下一轮把它捞起来，
用一条插入加查询的语句，把此刻标签启用、成员有效、没过期的人一次性冻成条目，
数一下写上目标人数，置成待跑。快照之后再挂进来的人不会被补进这个 Job，要发就新建一个。

跑的时候每一轮取一个能跑的 Job 锁住，再取一批待处理条目锁住，默认一批五十个，
然后逐条调发放门面。每一条发放是自己独立的事务，所以一个人失败不会把整批拖下水。
结果分四种：新发成功、幂等命中、业务跳过、技术失败。业务跳过首先是一组我事先列好的稳定错误码——
规则变了、模式不支持、活动没生效或已结束、不满足标签、额度用尽——这些重试一万次也是同样的结果，
所以直接判死；除了这张白名单，凡是 4xx 的业务异常我也统统判成业务跳过、错误码记成「活动拒绝」，
真正留给技术失败的只有 4xx 以外的东西，比如数据库暂时不可用，那些才等人手动触发重试。重试只会把技术失败的那些重置回待处理，
业务跳过的永远不动。整个 Job 的条目都处理完之后，看有没有技术失败，有就收成部分失败，
没有就收成完成。暂停、恢复也都是带条件的更新，暂停只对待跑或正在跑的生效，恢复只对暂停的生效。

**4.5 到账通知。** 通知那一行是和发放流水、券资产在同一个事务里写进去的，
所以绝对不会出现发了券没有通知、或者通知了没发券。之所以不在事务里直接推，
是因为 Redis 的推送没法参与数据库事务，推成功了事务回滚就成了假通知。
然后有一个通知 worker，每轮按「状态待发而且下次尝试时间已经到了」取一批锁住，
默认五十条，一条一条往那个用户专属的频道上发。发成功就把行改成已发布；
发失败就把尝试次数加一、按二的次方秒数往后推下一次尝试、最多推五分钟，
行还留在待发状态，下一轮继续。

扇出靠的是每个实例都订阅这一族用户频道。发券的那个实例根本不需要知道用户连在谁身上，
所有实例都收到这条消息，只有真正持有这条连接的那个实例能发出去，其它实例在自己的会话表里
查不到人就什么都不做。连接是在握手的时候用查询参数里的 token 验出来的，验的是跟普通 HTTP 请求
同一份登录态；而且每次要发消息之前我还会再验一次这个 token 还在不在，所以用户一登出，
已经建立的连接下一次推送就被关掉，而不是一直挂到超时。同一个用户重新连会把旧连接顶掉。

最后一点很重要：「已发布」只代表消息交给了 Redis，不代表用户收到了。用户没开页面这条消息就是丢的，
这不要紧，因为事实是数据库里那条发放记录。所以前端的兜底是显式的——WebSocket 一断就降级成轮询
「我的发放记录」，每两秒一次、最多十次、总共半分钟，连上就停。而且收到推送之后，
我并不拿推送里的数据去改页面，而是先用事件 id 去重，再重新拉一次列表，页面上显示的券始终来自那次拉取；
推送里被直接用掉的只有提示框那句文案。所以推送在这条链路里基本只是一个「你该刷新了」的信号。

## 五、为什么这么设计 / 会被怎么追问

**为什么幂等键要单独立一列，而不是直接用（活动，用户）唯一？**
因为签到奖励是「每人每天一张」，它和「每人一辈子一张」必须共用同一张表和同一套额度逻辑。
把「一辈子一次」表达成一个固定串的幂等键之后，两种语义就统一成同一个唯一键了，
发放门面里不需要为任务奖励分叉出另一套表。代价是这一列对普通发放来说是冗余的常量。

**为什么门面不开事务，内层才开？**
因为唯一键冲突的回查必须发生在内层事务回滚之后。如果门面和内层是同一个事务，
撞键时那次已经执行的额度自增还挂在当前事务里，回查读到的是一个脏状态，
而且这个事务已经被标记成只能回滚，再查也没有意义。分开之后，失败的那次连额度带流水一起干净回滚，
门面在事务外重新看到的是最终状态。

**拿到活动行的锁之后为什么还要再查一遍流水？**
因为第一次查的时候没有任何锁。两个并发请求可以同时查到「没发过」，然后一个先拿到锁发完提交，
另一个拿到锁之后如果不复查就会发第二张。这个锁同时也是同一个活动的串行边界：
额度的正确性其实由 UPDATE 的条件保证，锁保证的是**同一个用户**不会被并发发两次的窗口足够小，
以及后面那些校验读到的是一致的快照。

**额度已经有条件 UPDATE 了，为什么前面还读一次满没满？**
纯粹是为了在已经满额的情况下省掉一次写和一次冲突，以及给出更精确的错误码。
删掉它正确性不变。同理，更新失败之后的那段逐条分类也只为错误码服务。

**批量 Job 为什么要把规则版本抄下来，而不是每次发放时读当前版本？**
因为一个几万人的 Job 要跑很久，运营中途完全可能改活动。抄下来之后，规则一变，
剩下的条目会整齐地全部停在「规则已变化」上，运营看到的是一个明确的部分失败，
而不是「前一万人按旧规则发、后一万人按新规则发」这种没人能解释的结果。
代价是运营改完必须新建一个 Job。

**业务跳过和技术失败为什么要分开？**
因为重试语义完全不同。「不满足标签」「额度用尽」「活动已结束」重试多少次都是同一个结果，
把它们放进重试队列只会让 Job 永远跑不完；而连接超时、数据库暂时不可用是重试能解决的。
所以我维护了一张稳定错误码的白名单，命中的判死，其余的留给人工触发的重试接口。

**为什么通知用 Outbox，而不是在事务提交之后直接推？**
提交之后推，进程在提交和推送之间挂掉，这条通知就永远没有了；而且没有重试、没有退避、
没有可观测的积压。Outbox 把「通知这件事」变成了和业务数据同生共死的一行，
worker 只负责把它搬出去。代价是多一张表、多一个 worker、多一跳延迟。

**为什么不直接用 RocketMQ 发这个通知？**
项目里秒杀链路确实用了 RocketMQ（详见第 05 章）。这里的通知是「给在线用户的一次提示」，
不是必须送达的业务事件，真正的事实是数据库里的发放记录，前端可以随时拉。
用 Redis 的发布订阅做一次机会性的扇出，成本最低；Outbox 已经把持久性那一半解决掉了。

**多实例下同一条通知会不会被推两遍？**
取待发行用的是 `FOR UPDATE`，所以同一时刻只有一个实例能持有这一批行；
标记已发布的语句也带「这一行仍然是待发」的条件。重复的风险不在这里，
而在「发到 Redis 成功了但标记之前进程挂了」——这时下一轮会再发一次，
所以推送必须是幂等的，这也是前端要用事件 id 去重的原因。

## 六、已知边界

- **通知 worker 在数据库事务里做 Redis 网络 IO**。整批行的锁要一直持有到这一批全部发完，
  Redis 慢的时候这个事务会变长。
- **取待发行和取可跑 Job 都没有用 `SKIP LOCKED`**。多实例部署时其它实例会阻塞在锁等待上，
  实际是串行推进；批量发放更是全局一次只推进一个 Job（按主键升序取第一个可跑的），
  没有公平性，一个大 Job 会把后面排队的饿住。
- **通知的尝试次数封顶只封了退避时长，没有封重试本身**。尝试次数到上限之后仍然按 5 分钟一轮
  无限重试，没有死信、没有终止状态、没有到达阈值的告警。
- **通知只有「券已发放」一种事件类型，而且没有已读状态**。前端的去重集合在内存里，
  刷新页面之后同一条事件会再提示一次。
- **后台侧没有发放通知**：运营看批量 Job 的进度只能刷新列表页，实时频道目前只服务秒杀订单事件。
- **批量 Job 的条目结果和发放本身不在同一个事务里**。发放各自独立提交，条目结果写在外层事务里
  最后一起提交。如果外层在中途回滚，会出现「券已经发了但条目还是待处理」；下一轮重跑时
  这些条目会走发放门面的快路径，落成「幂等命中」，所以不会重复发，但那一批的统计会偏。
- **状态变更的券与标签复核写在公共路径上**：绑定券一旦下架，这个活动连「关闭」都会被这道校验挡住，
  得先把券重新上架才能关。
- **批量路径下那次撞键回查是在 worker 的外层事务的快照里做的**，未必读得到另一个事务刚提交的流水。
  真落到这一步只会把这一条记成技术失败，重试时会走快路径变成幂等命中，不会重复发券。
- **快照不可变**：Job 建好之后新挂进标签的用户不会被补发，也没有「增量补跑」的入口。
- **标签成员只能一个一个人工挂**，没有批量导入、没有按行为自动打标的规则引擎。
- **签到只有事实与连续天数统计**，没有连签阶梯奖励；任务奖励目前也只有「今天签到了」这一种任务。
- 活动状态更新允许「改成当前状态」这种空转，它同样会把规则版本加一，
  于是所有持有旧版本的前端都会拿到一次规则冲突。
- 券资产、核销与过期不在本章，**详见第 07 章**；点赞 Outbox 与热榜**详见第 10 章**；
  后台账号、角色与数据范围**详见第 02 章**；订单表分片**详见第 08 章**。
