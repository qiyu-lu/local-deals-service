# 12 压测方法与故障演练

## 一、这一章解决什么问题

前面几章讲的是机制：漏斗怎么挡、批量怎么落、分桶和分片怎么排布。这一章只回答一件事——**凭什么
相信它们有用**。一个没有方法的数字比没有数字更糟：它经不起追问，而面试里一定会被追问。

所以本章要交代三样东西。第一，**怎么测**：为什么用开环模型而不是线程池压测，为什么必须分核，
为什么每轮之前要预热，为什么一次运行的结果默认不可信、要靠什么才能被采信。第二，**每个里程碑
改完之后数字怎么动的**，以及瓶颈是怎么从 Broker 一层层挪到那张券库存表的同一行上的。第三，
**三次故障演练**：`kill -9` 杀应用、杀 Redis 主节点、以及制造复制空窗之后再杀主节点——直接杀
主节点那次没能把最后一道防线逼出来，先造出复制空窗才做到。

具体命令怎么敲、结果目录长什么样，详见第 13 章；被测的机制本身详见第 04–08 章。本章只讲方法
与结论。

## 二、涉及的数据

本章不碰业务表，涉及的是一次运行会产出的东西。

- **一份阶梯结果表**：每一档一行，列有目标到达速率、实际达成速率、丢弃数、p50/p95/p99、
  被接收的成功人数、应用 CPU 核数、MySQL / Redis / Broker 各自的 CPU 核数、压测客户端自己的
  CPU 核数，以及事务半消息主题与订单主题的消息条数。多实例的运行另有一份边缘层（nginx）的
  CPU 表。
- **一份落库结果表**：每轮一行，列有落库速率（已接收订单从 10% 落到 90% 之间的斜率）、
  负载停止之后还要多久排空、以及一个**批大小均值**指标——本轮实际交付批次的条数除以批次数，
  它是判断「批到底攒没攒满」的唯一硬证据。
- **一份运行清单**：commit、场景参数、分核方式、JVM 参数、机器型号、开跑与收尾时的 loadavg、
  当时还有哪些容器在跑。
- **一个状态文件**：运行中 / 完成 / 失败加失败阶段与原因。
- **每次演练一行 CSV**：被杀的对象、下手时已预占多少、事后的预占数、订单数、Redis 库存、
  DB 库存、残留的处理中索引、丢失的预占数、超卖数、条件更新拒批次数、收敛耗时。

约定两个贯穿全章的口径：**「拐点」固定指 p99 < 100 ms 且丢弃 < 1% 的最高一档**；
**「同场对照」指同一次运行里、同一台机器、同一份分核、同一组参数下，用上一个 tag 的 jar 和
当前 jar 各跑一遍**——跨天的数字不相减，这台机器不同时段快慢能差 10%。

## 三、详细流程

### 3.1 一次准入侧阶梯压测

目的是找出单实例准入接口的拐点和天花板，并定位当时的瓶颈在哪一层。一次阶梯从起环境开始，
到一份逐档的结果表结束，中间不需要人看着。

- **模型选开环**。压测客户端按固定到达速率发请求，**发多少与系统回得快不快无关**。
  - V1 的证据是 JMeter 1000 线程 / 5 s ramp-up 得到的 208 req/s。那是**发压速率不是系统容量**：
    线程发完一个要等响应才发下一个，系统越慢压力越小，所以永远测不出拐点，也永远不会过载。
  - 开环下系统跟不上就表现为两件事：延迟上升、以及客户端发不出去的迭代被记为丢弃。
    拐点就定义在这两件事上。
- **分核**。一台 8C/16T 的机器上同时跑被测系统、依赖和压测客户端，不分核等于三方互相偷 CPU。
  按物理核分配，SMT 兄弟是 N 与 N+8。
  - M0–M6 的单实例运行：应用 4C/8T，依赖（MySQL / Redis / Broker / ES）2C/4T，压测客户端 2C/4T。
  - M8 的多实例运行：**每个实例独占一对核**，nginx 单独一对，依赖和客户端不变。
    给每个实例独占的核而不是切分一份固定预算，是因为后者只能测出多开进程的开销，测不出扩展性。
    代价是 M8 的曲线是「每实例 2 核」的曲线，**与 M0–M6 的「一个实例 8 核」不可直接比较**。
- **预热**。每次测量之前先以 500 req/s 跑 30 s，这一段不进结果表。
- **用户轮转**。10 万预生成 token，每一轮从上一轮停下的位置继续，所以同一个用户不会落进自己的
  每用户限流窗口。每个请求都是不同的用户——**首秒售罄、其余 99% 是注定失败的请求**，这正是
  秒杀的形态，也是 M3 漏斗要打的那一类流量。
- **必须声明的配置偏离**。每 IP 限流调到 10 万。所有压测请求都来自本机回环地址，默认的每 IP
  限流会让 99% 的请求在最外层就 429，那样测到的只是限流器不是系统。每用户限流保持默认；
  M8 的 nginx 同理**不开请求限流**。
- **每一列怎么来的**。
  - 达成速率、丢弃、各分位延迟：压测客户端的汇总 JSON。
  - 成功人数：应答里标记成功的计数，也就是真正拿到预占的人数。每一档都断言它等于库存。
  - 应用 CPU：窗口内进程用户态 + 内核态时间的差值除以墙钟；**多实例时是所有实例之和**。
  - 依赖 CPU：容器 cgroup 累计用量的差值除以墙钟；Redis 在 Cluster 下是六个节点之和。
  - **压测客户端自己的 CPU 也是一列**——它满了，阶梯就到顶了，这与被测系统无关。这一列在 M3
    之后变成最重要的一列，理由见 3.3。
- **一次运行能不能被采信**，由四道关卡决定，缺一不采信。
  - 开跑前的预检会直接拒绝：**工作区有未提交改动**（结果必须对应得上一个 commit）、端口被占、
    磁盘不足、没有 JDK 21、容器运行时不可用。
  - 状态文件不是「完成」就不分析。
  - 每个阶段有超时，第一个失败就停下、写明原因，并且无论如何拆掉自己起的那套栈。
  - 冒烟运行的数字**永远不进结论**，它只用来验证链路通了、目录结构对。

### 3.2 一次落库测量与消费参数扫描

准入侧和落库侧是两条独立的测量。落库测量的做法是：一张新券、库存两万，以 2000 req/s 发到
全部被接收（发压时长就是库存除以速率再加一秒），然后量消息队列被排空的速度——**这个数字卡不住
在客户端**，因为单子已经进队列了。

- 取两个口径：**斜率**（第 10% 单到第 90% 单）和**负载停止时还剩多少积压**。后者比前者硬——
  积压 0.1 s 意味着负载还在发的时候就已经落完了。
- M6 开头补了**批大小均值**这个指标，然后做了一轮消费参数扫描。它回答的是 M4 留下的问题：
  批量消费明明配了很大的批，为什么吞吐只翻了一倍？
  - 答案是批根本没攒满。**批大小实测 1.03**——消费线程本来就跟得上到达速率，队列里永远没有
    第二条消息在等。**无论批的上限配成多少都一样**。
  - 扫描里唯一有干净单旋钮证据的是**拉取间隔**：批大小均值从 2.16（0 ms）一路升到 12.68（50 ms）。
    换成新的一组消费参数后测到 2001.5 单/s，而那是**场景发压速率的上限不是系统的**——负载停止
    时已经落完了，这一轮根本没把消费端逼到头。
- **为什么落库数字特别不稳**：同样的输入、同样的代码，M0 的三轮分别是 123 / 264 / 478 单/s。
  消费端存在双稳态——同一次运行里同一行被量到约 394 次提交/s 与约 73 次提交/s 两段。
  - 直接后果：**落库侧的单轮差异，小到一定程度就读不出来**，所以结论要么取中位、要么依赖
    批大小均值这类稳定的指标（它同配置两轮几乎不动），要么依赖积压这种差两个数量级的量。
  - M5 的落库 A/B 就是被这件事吃掉的：九轮平均由双稳态决定，基线与 M5 混在同一条曲线上，
    所以那一格如实写的是「**无可测变化，而且这次量不出来**」，不是「没有提升」。

### 3.3 逐里程碑数字怎么动的，瓶颈怎么迁移

每个带性能影响的里程碑都做同场对照，只回答「有没有回退 / 提升了多少」。连起来是一条瓶颈
迁移的线。

- **M0 基线**：准入拐点约 1 万 req/s（p99 63 ms），天花板 15.9k，15k 时是 **Broker 先流控**；
  落库 123 / 264 / 478 单/s（中位 264）。火焰图里消费线程 44.7% 花在那张券库存表的一行的行锁上，
  49.5% 在连接池等待。瓶颈在 Broker 和那一行。
- **M1（Java 21 + Boot 3 + ES 8）**：天花板 14.5k → 17.5k，10k 档 p99 73.7 → 51.8 ms、CPU −20%，
  **拐点仍是约 1 万**；落库 180.8 vs 155.6，区间重合，无差别。升级换来的是余量不是拐点。
- **M2（订单闭环）**：落库 189.4 vs 177.5，区间重叠，**新增开销 < 2%**。这一格的意义是
  「加了这么多业务没有变慢」。
- **M3（准入漏斗）**：拐点 **5k → 20k**（p99 83 ms），天花板 13.2k → ≥26.2k；10k 档
  p99 128 → 33 ms、应用 CPU 3.04 → 0.60 核；**事务半消息从「等于请求数」变成 0**。
  从此准入侧不再是瓶颈，后面每个里程碑的准入数字只用来证明没有回退。
  - 这里的 5k 是**同场对照组（上一个 tag 的 jar）那一轮**测到的拐点，和 M0 那天单独测到的
    「约 1 万」不是同一场，按本章的口径两者不能相减，也不该并排读成「拐点退回去了」。
- **M4（批量消费）**：落库 156.3 → 319.1 单/s（最好轮 945.2），**待验证目标 ≥3000 单/s 未达成**。
  当时的解释是「一次提交的上限约 80 次/s，吞吐 ≈ 80 × 实际批大小」。
- **M5（Cluster + 库存分桶）**：准入 10k 档 −0.1%、20k 档 −1.7%，代价是 p99 上升 28~45 ms；
  落库无可测变化（见 3.2）。
- **M6（订单分 2 库 × 4 表 + 新消费参数）**：准入 10k 档 9936.5 → 9961.7 req/s（p99 68.3 → 58.6），
  20k 档 19725.1 → 19721.5（p99 87.3 → 101.0），每档成功人数等于库存，**无退化**；
  落库**中位 982.7 → 2088.9 单/s**，负载停止时的积压 10.7 / 55.8 / 16.1 s → **0.1 / 0.1 / 0.1 s**。
- **M8（nginx + 3 实例）**，两条曲线两种结论：
  - **准入侧测不出扩展性，原因不在系统**。1 / 2 / 3 个实例在 30k 档分别是 25498 / 25573.6 /
    25625.1 req/s，三条线重合。CPU 说明了一切：**压测客户端在自己的 4 个 vCPU 上吃到 3.52–3.58 核**，
    而三个实例加起来只用了 1.26 核（各自 2 核共 6 核），nginx 用了 0.59 核（共 2 核）。
    M3 之后一次准入几乎不花钱，所以在这台机器上**客户端先满**——加实例不可能改变一个由客户端
    决定的数字。要量准入侧的扩展曲线得换多机压测。
  - **落库侧能测，答案是「不扩展」**。1 / 2 / 3 实例的落库中位是 2415 / 2435 / 3026 单/s，
    应用 CPU 1.41 → 2.7 → 4.0 核，而 MySQL 只用了 0.24 核（共 4 核）。**三倍 CPU 只多落了
    约 25% 的单**；把落库速率除以批大小折算出的**提交次数/s 在 70–115 之间，与实例数没有关系**。
    那正是 M4 量到的上限，也就是每个批次都要更新的**那张券库存表的同一行**。行锁不因为多了
    两个进程而变快。
  - M6 曾把回归条件写得很具体：到达速率远高于 2000/s、负载后积压重新大于 0、且落库速率除以
    批大小不再随负载上升。这一轮**三条同时成立**，所以「那一行是写路径水平扩展的上限」
    从推断变成了实测。

### 3.4 演练一：`kill -9` 应用

目的：在买家正在被放行的时候把应用整个打死，看**「Redis 里有预占、MySQL 里没有订单」的那批人
最后会不会都拿到订单**，以及要多久。这是「宕机不丢单」这句话的全部证据。

- 库存两万、2000 req/s 发压，**第 6 秒下手**——这个时机挑在售罄之前，让死的时候手里正好有
  上万条预占。
- 直接 `kill -9`，不给优雅停机的机会：优雅停机能测出的东西没有意义，线上机器不会先跟你打招呼。
- 重新拉起应用，然后每两秒轮询一次，直到**预占数等于订单数、且处理中索引为空**，记下从
  下手到这一刻的秒数。这两个条件是收敛的定义（详见第 05 章的对账器）。
- 结论逐里程碑地移动：M3 两次分别 102.8 / 102.7 s；M4 批量化之后 44.7 s；M5 上 Cluster 之后
  56.8 s（到期索引从一个 ZSET 变成按桶均分，方向一致，但单轮数据不足以称之为回退）。
  三个版本都是**预占 = 订单、Redis 库存 = DB 库存、无残留处理中**。
- **变体：先杀 Broker 再杀应用**。提前两秒杀 Broker，制造一批「准入 Lua 已经成功、消息却从未
  存进 Broker」的预占——这正是对账器必须重投的那一类。M3 这一轮重投了 4249 单，**三方一致收敛**，
  代价是耗时 574.2 s；M4 是 572.1 s，**因为对账器本身没有批量化**，与预期一致。

### 3.5 演练二：杀 Redis 主节点

目的：Redis 在这套设计里是「可丢的性能层」，那就把它的一个主节点真的杀掉，看代价到底是什么。

- 同样是库存两万、2000 req/s、第 6 秒下手。
- **被杀的节点在运行时才决定**：取当前正在服务 0 号桶的那个主节点。写死名字是错的——第一轮
  被杀的节点回来之后会变成自己那个副本的从节点，第二轮再杀它就只是杀了一个从节点，什么也
  证明不了。
- 所有读都走一个活得下来的节点，否则读的是被杀对象自己。
- 记两个不同的时刻：**集群察觉**到主节点没了，和**每个桶重新可读**。应用感受到的是第二个，
  它才是值得引用的数字——前几秒幸存节点还在说「一切正常」，因为它们根本还没发现。
- 结果：两轮**丢失预占 0、库存差 0、超卖 0**，转移 5.2 / 7.8 s、恢复 7.3 / 9.4 s、
  收敛 40.2 / 31.4 s。
- **代价不是零**：约 1.26 万个 503，占那一轮全部请求的 42%。库存明明还有，买家却被拒——
  这就是「Redis 是可丢的性能层」的真实价格。
- **这一轮没能证明的事**（必须主动说）：预期中的「异步复制丢掉最近的扣减 → 新主库存变多 →
  Redis 超放 → MySQL 条件更新兜底」**没有复现**，实测 RPO = 0。原因不是运气：主节点一死，
  它负责的 slot 直接不可写，买家收到 503 而不是一个假的成功，**被拒绝的买家不算丢失**；
  真正的丢失窗口只有不到 1 ms 的复制延迟。于是整个设计赖以成立的最后一道防线，**到 M5 为止
  一次都没有被真实触发过**。

### 3.6 演练三：复制空窗

目的：把 3.5 没能触发的那道防线逼出来——让被提升的副本带着几秒前的世界观回来，相信已经卖掉的
库存还在，于是放进比真实库存更多的买家；这时挡在超卖前面的只剩 MySQL 的条件更新。

- 做法分三步，顺序是关键：**先让副本睡着**（睡着的副本无法重连），**再从主节点这边切断复制
  链路**，然后让主节点在空窗里继续接单几秒，最后杀掉它。
- **这个空窗造了四次才对，三次失败各自说明一件事**，这三件事比结论本身更值得讲：
  1. **杀晚了**。第一次在库存卖光之后才下手，被提升的副本回来时本来就没有东西可信。
     一整行 0 读起来像「防线成立」，其实是「什么都没测」。所以结果行里加了一个字段，
     让一次时机不对的运行自己说出来。
  2. **只让副本睡着造不出空窗**。它只是停止**应用**复制流，字节早就躺在它的 socket 缓冲区里，
     醒来以后一条不落地补上，RPO 仍然是 0。**要真丢，主节点必须停止发送**——所以才有第二步。
  3. **买家必须多于库存**。链路切断之后确实量到了空窗，但条件更新一次都没开火——复活的库存
     根本没人来抢，自然没有东西可拒。所以空窗轮必须在售罄之后继续发压一段时间。
- 正式结果，两晚四轮，库存都是 30000：

  | 轮次 | 杀主时未售 | Redis 放进 | MySQL 建单 | 多放 | 条件更新拒批 | 超卖 |
  | --- | ---: | ---: | ---: | ---: | ---: | ---: |
  | 9-21 03:41 ① | 14001 | 30124 | 30000 | 124 | 10 | **0** |
  | 9-21 03:41 ② | 14051 | 33096 | 30000 | 3096 | 337 | **0** |
  | 9-21 04:43 ① | 14123 | 33104 | 30000 | 3104 | 0 | **0** |
  | 9-21 04:43 ② | 14047 | 33101 | 30000 | 3101 | 0 | **0** |

- 读法：**Redis 最多多放了 10.3% 的人，而 MySQL 每一轮都恰好建了 30000 单，超卖恒为 0**。
  多出来的人在两个地方之一被挡下——要么**预占随主节点一起死了**，消费者认领时发现状态不在
  （后两轮）；要么**复活的库存被重新卖掉**，批次走到 MySQL 才被条件更新整批拒绝（第二轮 337 次）。
  **两条路径通向同一个结果**，区别只在于复活的库存有没有在「丢失预占」的消息被处理之前被抢走。
- 收敛需要 150–308 s，靠的是对账器。
- 已知代价：副本睡着期间也无法参与选举，所以转移时间比 3.5 那两次长——这是制造空窗的代价，
  不是回归。

### 3.7 多实例全链路对账

目的：前面每一项都是单点验证，最后要有一次把整条业务闭环跑完的运行，且必须在多实例上跑。

- 场景：10 万人抢 1000 件，三个实例在 nginx 后面。第一波每人抢一次，赢家等自己的订单落库，
  其中一部分去付款，其余的走人；未付款的订单到期被定时消息关掉、库存回到它原来那个桶和
  MySQL 的库存行；第二波用**全新的买家**去抢回补的那些库存——这一步才证明回补是真的，
  而不只是改了个状态。
- 支付由压测脚本扮演渠道：走 API 预支付，然后按约定规范自己签名发回调。因为 mock 渠道把支付
  登记在进程内存里，收银台只在下单的那个实例上有效；而**多实例下必须站得住的端点是回调**
  （详见第 06 章）。
- 最终核对七项：在册订单数 = 库存、零超卖、零重复买家、Redis 库存归零、DB 库存归零、
  零残留处理中、以及拿一个买家的 traceId 从 nginx 一路查到订单行再查到关单那行日志。
- 结果：成功单 1000 = 库存，249 件因超时关单回补并被再次抢完，三个实例各接 422 / 424 / 403，
  **零超卖零重复零残留**；落库可见中位 5.2 s、p99 15.7 s。
- 一个必须主动交代的数字：**214 个赢家在 30 s 内没等到订单可见就放弃了付款**。他们的订单
  **都落了库**——那是压测脚本给买家设的耐心上限，不是丢单。落库可见最大 16.0 s。
- 顺带一提，多实例冒烟第一次跑就抓到一个**单实例永远看不见的缺陷**：附属表主键用的那个
  Snowflake，workerId 默认取 0，两个实例同一毫秒铸出同一个 id，1000 单里 24 次主键冲突（已修，
  详见第 08 章）。这条本身就是「为什么必须真的多开实例测一次」的最好论据。

## 四、口述版

**4.1 方法。** 我先说怎么测，因为方法错了后面的数字都不用看。V1 的证据是 JMeter 一千个线程
压出来的两百零八 req/s，那个数其实是发压速率不是系统容量——闭环模型下线程发完一个要等响应才发
下一个，系统越慢我压得越轻，所以永远压不出拐点，也永远不会过载。V2 全部换成开环：请求按我
指定的速率到达，跟系统回得快不快无关，系统跟不上就表现成延迟上升和客户端发不出去的迭代被丢弃，
拐点我固定定义成 p99 小于一百毫秒且丢弃小于百分之一的最高一档。然后是分核，因为被测系统、
依赖和压测客户端跑在同一台八核机器上，不按物理核分开就是三方互相偷 CPU，测出来的东西谁也不
代表；多实例那次我给每个实例独占一对核而不是把一份固定预算切三份，因为切预算只能测出多开进程
的开销，测不出扩展性，代价是那条曲线是「每实例两核」的曲线，不能拿去跟单实例八核的数字比。
每轮测量之前先低速预热三十秒不计入结果。用户是十万个预生成的 token 轮着用，每轮接着上一轮的
位置走，这样同一个用户不会撞上自己的每用户限流，而且每个请求都是不同的买家——首秒售罄、其余
百分之九十九是注定失败的请求，这才是秒杀的真实形态。有一个必须主动声明的配置偏离：我把每 IP
限流放到十万，因为所有压测请求都来自回环地址，不放开的话九成九的请求在最外层就被限流器拒了，
我测到的只是限流器不是系统；多实例那次 nginx 的请求限流也是同一个理由没开。

**4.2 一次运行凭什么能被采信。** 我的默认立场是「一次运行不可信」，所以做了四件事。第一，
开跑之前预检会直接拒绝运行：工作区只要有未提交的改动就不让跑，因为结果必须对应得上一个 commit；
端口被占、磁盘不够、JDK 版本不对也一样拒。第二，每次运行都写一份清单，记 commit、场景参数、
分核方式、JVM 参数、机器型号和开跑与收尾时的负载，还有当时机器上还跑着哪些别的容器。第三，
每个阶段都有超时，第一个失败就停下来把原因写进状态文件，并且无论如何把自己起的那套环境拆掉——
状态不是「完成」我就不分析。第四，冒烟跑出来的数字永远不进结论，它只用来验证链路通了。除此
之外还有一条更重要的纪律：跨天的数字我不直接相减，因为这台机器不同时段快慢能差一成，所以每个
里程碑的对比都是同场对照——同一次运行里用上一个 tag 的 jar 和当前的 jar 在同一份分核、同一组
参数下各跑一遍。

**4.3 落库这一侧为什么特别难测。** 准入侧的数字很稳，落库侧非常不稳：同样的输入、同样的代码，
基线那三轮分别是一百二十三、二百六十四和四百七十八单每秒。原因是消费端有个双稳态，同一次运行
里同一行库存被量到过每秒约三百九十四次提交和每秒约七十三次提交两段，为什么会翻转我到现在也没量出来。这件事
的后果是落库侧的小幅差异根本读不出来，所以 M5 那一格我如实写的是「无可测变化而且这次量不出来」，
而不是「没有提升」——这两句话在面试里完全不是一回事。真正让我看清楚的是后来补的批大小均值这个
指标：它同配置两轮几乎不动，比吞吐硬得多。补上它之后立刻发现 M4 的批实测只有一点零三条，
也就是批根本没攒满，消费线程本来就跟得上到达速率，队列里永远没有第二条消息在等，所以批的上限
配多大都一样。扫参数时唯一有干净单旋钮证据的是拉取间隔，批大小均值从二点一六涨到十二点六八，换上新参数
之后测到两千零一点五单每秒，而那个数还是场景发压速率的上限不是系统的上限，因为负载还在发的时候单子就
已经落完了。

**4.4 瓶颈是怎么一层层挪的。** 基线的时候拐点在一万 req/s 左右，天花板一万五点九，而且是 Broker
先流控，因为每个请求——包括那百分之九十九注定失败的——都要先发一条事务半消息；落库那一侧火焰图
里将近一半时间在同一行库存的行锁上，另一半在等连接池。升级 JDK 和框架那一轮把天花板抬了、同档
延迟和 CPU 都降了，但拐点没动，换来的是余量不是拐点。真正的转折是准入漏斗：同场对照里拐点从对照组那一轮的五千抬到两万（这个五千和基线那天的
「约一万」不是同一场，不能相减），
半消息从「等于请求数」变成零，十k 档应用 CPU 从三核降到零点六核，从那以后准入侧就不再是瓶颈了，
后面每个里程碑的准入数字只用来证明没有回退。接下来批量消费把落库从每单一次提交变成每批一次提交，
吞吐翻倍但没到目标。分库分表加新的消费参数之后落库中位从九百八十二点七涨到两千零八十八点九，更关键的是负载停止
时的积压从十几秒几十秒直接掉到零点一秒。最后多实例那一轮给出了两条结论：准入侧三条曲线完全重合，
但那不是系统的天花板而是压测客户端的——客户端在自己四个核上吃到三点五二到三点五八核，三个
实例加起来才用一点二六核；落库侧倒是能测，答案是不扩展，三倍 CPU 只多落了约两成半的单，而折算出来的提交次数
每秒恒在七十到一百一十五之间、跟实例数完全没关系，那就是每个批次都要更新的那张券库存表的同一行，
行锁不会因为多了两个进程就变快。这条结论以前是推断，这一轮三个回归条件同时成立，它变成了实测。

**4.5 第一次演练，直接把应用打死。** 库存两万、两千每秒发压，第六秒下手，挑在售罄之前是因为
我要让它死的时候手里正好攥着上万条预占。不给优雅停机的机会，线上不会先跟你打招呼。然后把应用
拉起来，每两秒轮询一次，直到预占数等于订单数并且处理中索引清空，这两个条件同时成立才算收敛。
三个版本的收敛时间分别是一百零二点八秒、四十四点七秒和五十六点八秒，每一次都是预占等于订单、
Redis 库存
等于数据库库存、没有残留的处理中。这个演练还有一个更狠的变体：提前两秒先把 Broker 杀掉再杀应用，
这样就造出一批「准入脚本已经成功、消息却从来没进 Broker」的预占，正是对账器必须重投的那一类；
那一轮重投了四千二百四十九单全部落库，三方一致收敛，但耗时五百七十四点二秒，比普通那两轮
长得多，原因是对账器本身没有批量化——
这个代价我是认的，写在已知边界里。

**4.6 第二次演练，杀 Redis 主节点。** 挑节点这件事有个坑：不能写死名字，得在运行时找出当前
正在服务零号桶的那个主节点，因为第一轮被杀的节点回来之后会变成自己那个副本的从节点，第二轮
再按名字杀它就只是杀了个从节点，什么都证明不了。所有读也得走一个活得下来的节点。我记两个时刻，
一个是集群察觉主节点没了，一个是每个桶重新可读，应用感受到的是后面那个，因为前几秒幸存节点
还在说一切正常，其实它们根本没发现。结果是两轮丢失预占零、库存差零、超卖零，转移五点二秒和七点八秒、
恢复七点三秒和九点四秒、收敛四十点二秒和三十一点四秒。但代价不是零：那一轮约一点二六万个请求
被拒，占全部请求的四成二，库存明明还有买家却被拒绝，这就是「Redis 是可丢的性能层」的真实
价格。更重要的是这一轮**没能**证明的东西——我预期的是异步复制丢掉最近的扣减、新主的库存变多、Redis 超放、最后由
MySQL 的条件更新兜底，结果实测丢失为零，那道防线根本没上场。原因不是运气：主节点一死它负责的
槽位直接不可写，买家收到的是五百零三而不是一个假的成功，被拒绝的买家不算丢失，真正的丢失窗口
只有不到一毫秒的复制延迟。

**4.7 第三次演练，先造复制空窗再杀主。** 为了把那道从没上过场的防线逼出来，我得先制造几秒钟
的复制空窗。这个空窗造了四次才对，三次失败每次教我一件事。第一次我杀晚了，库存已经卖光才下手,
被提升的副本回来时本来就没有东西可信，结果一整行零读起来像「防线成立」，其实是什么都没测——
所以我在结果行里加了一个字段让这种运行自己说出来。第二次我只让副本睡着，以为它停止复制就算
空窗，结果它只是停止**应用**复制流，字节早就在它的 socket 缓冲区里了，醒来一条不落地补上,
丢失还是零；要真丢，得让主节点停止**发送**,所以正确做法是先让副本睡着——睡着的副本没法重连——
再从主节点这边把复制链路切断，之后主节点收的每一笔都谁也到不了。第三次链路是断对了，空窗也
量到了，但条件更新一次都没开火，因为复活的那批库存根本没人来抢，没有东西可拒，所以空窗轮还得
保证买家多于库存、售罄之后继续发压。三件事同时做对之后，正式跑了两晚四轮：库存三万,Redis
最多多放了百分之十点三，而 MySQL 每一轮都恰好建了三万单，超卖恒为零。多出来的人在两个地方之一被挡下,
要么预占跟着主节点一起死了、消费者去认领的时候发现状态不在，要么复活的库存被重新卖掉、批次
一路走到 MySQL 才被条件更新整批拒绝——有一轮拒了三百三十七次。两条路径通向同一个结果，区别
只在于复活的库存有没有在那批丢失预占的消息被处理之前先被抢走。收敛要一百五十到三百零八秒，
靠的是对账器。

**4.8 最后一次是全链路。** 前面每一项都是单点验证，最后我要有一次把整条业务闭环在多实例上跑
完的运行：十万人抢一千件，三个实例在 nginx 后面，第一波赢家里一部分去付款、其余走人，没付款的
到期被定时消息关掉、库存回到它原来那个桶和数据库的库存行，然后用全新的一批买家去抢回补的那些
库存——这一步才证明回补是真的而不只是改了个状态。支付是压测脚本自己扮渠道，走预支付再按规范
签名发回调，因为 mock 渠道把状态放在进程内存里、收银台只在下单那个实例上有效，而多实例下真正
必须站得住的端点是回调。最后核对七项：在册订单等于库存、零超卖、零重复买家、Redis 和数据库
库存都归零、没有残留的处理中，再拿一个买家的 traceId 从 nginx 一路查到订单行、查到一分钟后
关单那行日志。结果全部闭合，三个实例各接了四百二十二、四百二十四和四百零三单。有一个数我一定主动说：
有两百一十四个赢家在三十秒内没等到订单可见就放弃付款了，但他们的订单全都落了库，那是我给压测脚本里的买家设的
耐心上限，不是丢单。另外多实例冒烟第一次跑就抓到一个单实例永远看不见的缺陷，附属表主键那个
发号器的 workerId 默认是零，两个实例同一毫秒铸出同一个 id——这件事本身就是「为什么必须真的
多开几个实例测一次」最好的论据。

## 五、为什么这么设计 / 会被怎么追问

- **为什么不用 JMeter 继续测？** 不是工具问题是模型问题。线程池模型是闭环的：一个线程发完请求
  要等响应才发下一个，系统越慢到达速率越低，所以它**永远测不出拐点也永远不会过载**，压出来的
  数只是「我这台客户端能发多快」。开环模型把到达速率变成自变量，系统的响应变成因变量，
  拐点才有定义。
- **为什么没到 3000 单/s？** 这是全章最值得讲的一题，因为答案变过两次。
  - M4 的解释是「一次提交的上限约 80 次/s，吞吐 ≈ 80 × 实际批大小」，当时中位 319.1、
    最好轮 945.2，目标没达成，如实记下。
  - M6 补上批大小仪表后发现**卡住的是批大小不是提交速率**：实测批只有 1.03，消费线程跟得上
    到达速率，队列里没有第二条消息在等，所以批攒不满。调拉取间隔把批填到 12.68 之后落库中位
    涨到 2088.9 单/s，而且**那一轮的 2001.5 是发压速率的上限不是系统的**——负载停止时积压
    只有 0.1 s。
  - 同时还发现「80 次/s」这个前提本身是错的：**同一行在同一次运行里被量到过约 394 次/s**，
    那 80 次/s 是双稳态的慢档不是那一行的能力。
  - M8 高速率落库那一轮才给出最终答案：提交次数/s 恒在 70–115 且与实例数无关，
    **写路径的上限就是那张券库存表的同一行**。所以「没到 3000」在 M4 是「没测清楚」，
    到 M8 变成「测清楚了，瓶颈在哪、怎么拆都有数据支撑」——拆它（按券分桶扣减 + 定期合并，
    或者把库存从 MySQL 移走）是下一件有数据支撑的优化。
- **为什么当时决定不拆那一行，现在又说该拆？** 因为决策依据变了，这不是反复。当时的三条理由是：
  那一行被实测做到过约 394 次提交/s，所以拆行的收益前提「80 次/s × K」里的那个 80 是双稳态的
  慢档、不是那一行的能力，前提本身不成立；当时的约束
  是到达速率不是提交速率；而且拆行要真生效得让一个批次尽量来自同一个桶，否则一个事务要持 K 个
  行锁、竞争更糟，那是一笔比加一张表大得多的改动。当时还写死了回归条件——到达速率远高于
  2000/s、负载后积压重新大于 0、且落库速率除以批大小不再随负载上升。M8 那一轮**三条同时成立**，
  所以结论翻转是**按事先写好的条件翻的**，不是事后找补。
- **M8 的准入曲线为什么测不出扩展性？** 因为**客户端先满**。三个实例在 30k 档分别是 25498 /
  25573.6 / 25625.1 req/s，三条线重合；但压测客户端在自己 4 个 vCPU 上吃到 3.52–3.58 核，
  而三个实例加起来只用 1.26 核、nginx 只用 0.59 核。M3 之后一次准入几乎不花钱，所以这个数是
  由客户端决定的，加实例不可能改变它。**任何「水平扩展提升了准入吞吐」的说法都不能从这份数据
  得出**，要测得换多机压测。落库侧之所以能测，是因为单子先全部进了队列，排空速度卡不住在客户端。
- **把每 IP 限流放到十万，是不是把限流测没了？** 限流器在生产里挡的是真实分布的来源 IP，而压测
  请求全部来自同一个回环地址，不放开的话 99% 的请求在最外层就 429，测到的将只是限流器本身。
  要测的是准入漏斗，所以这一项必须偏离，而偏离必须写在方法一节里——**每用户限流保持默认**，
  因为用户轮转保证了每个请求都是不同的买家，它不会误伤。
- **为什么每个实例给独占的核，而不是把 8 核切三份？** 切固定预算测出来的是「多开进程的开销」，
  那是个已知的负数，测它没有意义；要测的是「加机器加不加吞吐」。代价是这条曲线的单位是
  「每实例 2 核」，**不能和单实例 8 核的数字直接比**，这一条必须跟着曲线一起说出来。
- **一次故障演练的结论凭什么可信？** 三点。第一，收敛条件是可判定的谓词而不是肉眼看曲线——
  预占数等于订单数且处理中索引为空，到了才算。第二，被杀的对象在运行时按角色挑，不按名字写死，
  否则第二轮杀的可能根本不是主节点。第三，一次「全是零」的结果**先当成可疑**：空窗演练的第一次
  就是杀晚了，一整行零读起来像防线成立其实什么都没测，所以结果行里专门加了一个字段让这种运行
  自己招供。
- **Redis 挂了为什么不是零代价？** 演练里一轮有约 1.26 万个 503、占全部请求的 42%。库存还有
  买家却被拒。这说明「Redis 是可丢的性能层」这句话丢的是**可用性不是正确性**——正确性由复制
  空窗那一轮兜住了：Redis 最多多放 10.3%，MySQL 每轮恰好建 30000 单，超卖恒为 0。

## 六、已知边界

- **单机测得的是这台机器上的拐点和扩展趋势，不是生产容量。**「万级」的论证方式是：单实例实测值
  × 已验证的水平扩展性 + 各层无共享瓶颈的设计说明。
- M8 的扩展曲线里，Redis Cluster、Broker、两个订单库、nginx 和压测客户端本身**都是共享的**。
  曲线一旦不线性，先看它们。
- **M8 的准入曲线是客户端受限的**：25.5k req/s 是这台机器上压测客户端的上限，不是应用的。
- **写路径的水平扩展上限是那张券库存表的一行**：加实例只加 CPU、不加吞吐。**已测实，尚未修。**
- **落库侧的双稳态成因至今没有量出来**。现在知道翻转的是提交速率（约 394 → 约 73 次/s）
  而不是批大小，但为什么翻转，仪表还不够。
- 消费参数改的是**一组四项**，其中只有拉取间隔有干净的单旋钮证据；**线程数那几行的差异全部
  落在噪声带里，不能据此说 4 线程优于 16 线程**；另外两项因为实测批从未触到上界而**一次都没被
  用到**——整组一起改，是因为只有整组被测过。
- M4 与 M5 期间**没有批大小与退化计数的仪表**，所以那两个里程碑的落库 A/B 结论在补上仪表之前
  一律不可信，这一点在当时就写明了。
- 支付是 mock 渠道；不涉及真实资金、对账文件、风控。**没做**：多机房、Broker 多副本切换、
  MySQL 主从切换。
- 多实例分片事务选的是 LOCAL 而不是 XA，崩在两次提交之间的后果是**有界的少卖而不是超卖**——
  但**这一条是推理不是实测，故障注入没有做**（详见第 08 章）。
- 全链路里 214 个赢家在 30 s 内没等到订单可见就放弃付款，他们的订单**都落了库**；
  落库可见中位 5.2 s、p99 15.7 s、最大 16.0 s。这是脚本给买家设的耐心上限，不是丢单。
- 宿主机上还跑着其它项目的容器，未绑核，属于背景噪声，每次运行的清单里都记了当时的负载。
