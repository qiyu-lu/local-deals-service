# 02 商户后台：登录、权限与数据隔离

## 一、这一章解决什么问题

平台从「点评 App」变成「面向商户的券营销后端」之后，后台不再是一个人用的运维页面，而是多租户的：
平台方要能看全量、建商户、分配历史商铺，商户主账号要能管自己的店、券和员工，商户员工只能看不能改。
所以后台需要一套和消费者完全分开的身份体系（消费者登录详见第 01 章），以及三件互相配合的东西：
**谁能进来**（登录与失败锁定）、**能调哪个接口**（权限点注解）、**看得到哪些行**（商户数据范围）。

难点有三个。第一，后台账号是长期有效的高权限身份，改了密码或被停用以后，那些已经发出去、还没到期的会话必须立刻失效，
不能等它自然过期。第二，权限漏配的代价很大——新加一个后台接口如果忘了写注解，绝不能默认放行。
第三，后台的实时订单推送走 WebSocket，而浏览器发起握手时没法自定义请求头，长期令牌不能直接拼在 URL 里。

## 二、涉及的数据

**商户主体表**：商户编码（唯一键，稳定标识）、名称、状态（待分配 / 启用 / 停用）。
里面有一条迁移时预置的「历史待分配」商户，V1 时期留下的、还没认领的商铺都先挂在它名下。

**后台账号表**：账号 id、所属商户 id（平台账号为空，商户账号必填）、用户名（唯一键）、口令哈希、
显示名、范围类型（平台 / 商户）、状态（启用 / 停用）、**认证版本号**、最后登录时间。
认证版本号是这一章的关键字段：会话里记着签发时的版本号，改密或停用时把它加一，所有旧会话下一次请求就对不上了。

**角色表 / 权限表 / 账号-角色表 / 角色-权限表**：标准的 RBAC 四张表。角色本身也带范围类型，
内置三个角色——平台角色、商户主账号角色、商户员工角色。权限点是「模块:动作」形式的字符串，
迁移里按角色预置了授权关系：平台角色拿全部权限点；商户主账号拿仪表盘、商铺读写、券读写、订单读、实时订单、
账号读写；商户员工只拿仪表盘、商铺读、券读、订单读、实时订单。后来两次迁移又补了营销读写（主账号读写、员工只读）
和到店核销、审计查看——**核销权限三个角色都有**（店员站柜台就是干这个的，核销链路详见第 07 章），
**审计查看只给平台和商户主账号**（员工不该看得到同事被记了什么）。

**门店表**上加了所属商户 id（非空、外键、带（商户 id，主键）索引），这是商户数据隔离落到行上的那一列。

**审计表**：账号 id、商户 id（平台账号为空）、用户名、动作名、目标类型、目标 id、结果（成功 / 失败）、
错误码、客户端 IP、毫秒精度的时间。索引按（商户 id，主键）和（账号 id，主键）建，正好服务于「按商户翻页」这一种查法。

**Redis 里四样东西**（都是普通字符串键）：

- 会话键：键里带不透明令牌，值是「账号 id:签发时的认证版本号」，TTL 30 分钟；
- 登录失败计数：键是「用户名|客户端 IP」拼起来做 MD5 之后的摘要，值是失败次数；
- IP 维度的尝试计数：键是客户端 IP 的摘要，值是这个 IP 的登录尝试次数；
- WebSocket 握手票据：键里带票据，值是签发它的那个会话令牌，TTL 30 秒。

## 三、详细流程

### 3.1 管理员登录

管理员带用户名和口令调登录接口，希望换到一个可以访问后台的令牌。这个请求到令牌写入 Redis、
连同会话有效期和本人权限点一起返回为止结束。

- 请求先进后台会话拦截器再进后台授权拦截器。登录接口是授权拦截器唯一排除的路径，所以未登录也能进来；
  消费者那一套拦截器对整个后台路径前缀是排除的，两套身份不会互相干扰。
- 服务先把用户名规范化：去空白、转小写，再用「4 到 64 位小写字母、数字、点、下划线、短横线」的正则校验，
  不匹配就当作空用户名继续往下走（不是立刻报错，理由见下一条）。
- 先查锁定。用「用户名|IP」的摘要键读失败次数，达到上限 5 次就直接返回 429，**连库都不查**。
  - 读 Redis 抛异常，或者读回来的值不是数字，都统一返回 503。登录这条链路对 Redis 是 fail-closed 的：
    宁可整个后台登不进去，也不能在限流失效时放开暴力破解。
- 再查 IP 维度的尝试次数。这一次是先加一再判断，超过 30 次返回 429。这个计数**不因为登录成功而清零**，
  它挡的是「一个 IP 换着用户名猛试」。
- 两个计数用的是同一段很短的 Lua：`INCR`，如果返回值是 1 就补一个 15 分钟的 `EXPIRE`，然后返回计数。
  - 放进 Lua 是因为 `INCR` 和 `EXPIRE` 之间如果被别的请求插进来、或者进程在这中间挂掉，会留下一个**永不过期**的计数键，
    那个用户名就被永久锁死了。
  - 过期时间只在第一次失败时设，所以这是一个从首次失败算起的 15 分钟固定窗口，不是每次失败都续期。
  - 脚本执行抛异常同样是 503。
- 然后按用户名查后台账号表。
  - 无论账号存在与否都要跑一次口令比对：账号不存在时拿一个启动时就算好的假哈希去比。
    这样「用户名不存在」和「口令错」花的时间接近，不给枚举用户名留时间侧信道。口令超过 256 个字符直接判定不匹配，
    避免拿超长输入去压 bcrypt。
  - 口令编码器是 bcrypt，强度 10。
- 口令对上以后还要再解析一次账号，这一步同时是资格检查：账号状态必须是启用；平台范围的账号不能挂商户 id，
  商户范围的账号必须挂商户 id 且它的商户主体存在并处于启用；角色也要对得上——平台账号必须持有平台角色，
  商户账号必须持有主账号或员工角色之一、且**不能**持有平台角色。任何一条不满足，这一步返回空，
  外面按「登录失败」处理。
  - 也就是说停用一个商户主体，等于一次性停掉它名下所有账号，不需要逐个改账号状态。
- 解析成功就拿到本次登录的主体：账号 id、商户 id、用户名、显示名、范围类型、认证版本号，
  以及用两条 SQL 查出来的角色码和权限点集合（权限集合在主体对象里是不可变的）。
- 登录失败的分支：把「用户名|IP」的失败计数加一，加完如果已经达到 5 次就返回 429，否则返回 401，
  **两种情况的文案都是「账号或密码错误」**，不告诉对方是哪一步错的。
- 登录成功的分支：删掉这一对「用户名|IP」的失败计数；生成 32 位十六进制的不透明令牌；
  把「账号 id:认证版本号」写进会话键并设 30 分钟 TTL；更新账号的最后登录时间；返回令牌、有效期秒数和主体。
- 整条链路无论成功、被锁、Redis 不可用、参数非法还是其他异常，都会打一个带结果分类的认证指标。

### 3.2 一次带令牌的后台请求

管理员拿着令牌调任意后台接口，请求要依次过「认出你是谁」「允许不允许」「能看到哪些行」三道关。

- **会话拦截器**（后台路径前缀，顺序 0）：从 `Authorization` 头里取 Bearer 令牌，取不到就直接放行——
  它只负责「认人」，不负责「拒绝」。
  - 令牌先过 32 位十六进制的正则，形状不对直接当没有，省掉一次 Redis 往返。
  - 读会话键，值按冒号切成账号 id 和签发时的认证版本号两段；切不出两段或者不是数字，说明这是一个脏值，
    **顺手把这个键删掉**再当作未登录。
  - 用账号 id 重跑一遍 3.1 里那套资格检查，拿到当前主体。主体为空（账号被停、商户被停、角色被摘）
    或者**当前认证版本号和会话里记着的那个不相等**，就把会话键删掉并当作未登录——这是撤销会话的那一刀，详见 3.3。
  - 都通过才给会话键续 30 分钟，并把主体放进线程局部变量。请求结束时无条件清掉，避免线程复用串号。
  - 代价是每个后台请求都要一次 Redis 读加三到四次库查（账号、角色、权限，商户账号还要多查一次商户主体
    来确认它没被停用）。目前没有缓存，见第六节。
- **授权拦截器**（同一路径前缀、排除登录接口，顺序 1）：
  - 预检请求直接放行。
  - 线程局部变量里没有主体 → 401。
  - 处理器不是一个控制器方法（比如静态资源、找不到映射） → 403。
  - 先取方法上的权限注解，没有再取类上的；**两处都没有就 403**。这是这套设计的要点：后台接口是
    「白名单准入」，漏写注解的新接口直接不可用，而不是默认放行。
  - 注解的值为空字符串表示「登录即可」（登出、查自己、改密码就是这一类）；非空就要求主体的权限集合里含有这个权限点，
    没有则 403。
- **数据范围**：拦截器只管到接口这一层，**行级隔离在每个服务方法里自己做**，判断依据是主体的范围类型：
  - 列表类查询：平台账号不加条件（账号列表还可以用参数指定看哪个商户），商户账号强制加上「商户 id = 自己的商户」。
  - 单条读取：商户账号按（主键，商户 id）查，查不到一律返回 404——不存在和不属于你返回同一个东西，
    不给跨商户探测留信号。
  - 更新：商户账号先按（主键，商户 id）带 `FOR UPDATE` 锁住（平台账号只按主键锁），更新语句的 `WHERE` 里**再带一次商户 id**，
    影响行数不为 1 就当 404。锁一次、条件再带一次，是为了不依赖「读到的东西在写的时候还属于我」。
  - 仅平台可做的动作（列商户、建商户、把历史商铺分配给某个商户）在服务里显式判断范围类型，不是平台就 403。
    这些动作同时也挂了权限点注解，等于双保险。
  - 商铺归属只允许「认领」不允许「换绑」：目标商铺当前必须还挂在那条「历史待分配」商户下，
    并且更新语句以「当前商户 id 仍是原来那个」为条件，两个管理员同时认领只有一个能成。
  - 商铺的写操作提交后才去失效商铺缓存和维护地理索引，注册的是事务同步回调；不在事务里调用会直接抛异常。

### 3.3 改密码与停用账号：认证版本号

后台会话是服务端 Redis 里的一行，本来删掉就撤销了；但一个账号可能同时有多个会话，令牌又不记录在库里，
没法枚举。认证版本号解决的就是「一刀撤销一个账号的全部会话」。

- **改密码**（登录即可，不需要额外权限点）：
  - 新口令要求至少 12 位字符且 UTF-8 编码不超过 72 字节——上限是 bcrypt 自身的截断长度，
    超过的部分不参与哈希，与其悄悄丢掉不如直接拒绝。
  - 按账号 id 读出账号，校验状态为启用、原口令匹配；不匹配统一报「原密码不正确」。新口令和原口令相同也拒绝。
  - 真正的更新是一条 CAS：`SET 口令哈希 = 新值, 认证版本号 = 认证版本号 + 1 WHERE 主键 = ? AND 认证版本号 = 读到的值 AND 状态 = 启用`。
    影响行数不是 1 就返回 409 让对方重登再试——说明在这中间有人改过这个账号的凭据或状态。
- **停用 / 启用员工账号**（需要账号管理权限点）：
  - 不允许改自己的状态，避免把自己锁在门外。
  - 目标账号要落在自己的数据范围内（商户账号加商户 id 条件），找不到就是 404。
  - 目标持有平台角色或商户主账号角色的，拒绝——员工接口不能拿来停内置主账号。
  - 同样是一条带认证版本号 CAS 的更新，商户账号的 `WHERE` 里额外带商户 id；影响行数不是 1 返回 409。
- **效果**：版本号一加一，那个账号所有在途会话里记的版本号就都变旧了。下一次请求走到 3.2 的会话拦截器，
  版本号比对不上，会话键被删、请求按未登录处理。不需要遍历 Redis，也不需要额外的黑名单。
  代价是失效发生在「下一次请求」而不是「立刻」，对已经建立的 WebSocket 连接则由推送前的复验兜住（见 3.5）。
- 主动登出就简单了：删掉那一个会话键，其他会话不受影响。

### 3.4 写操作审计

需求是「一张表 + 一个切面」：谁在什么时候、从哪个 IP、对哪个对象做了什么、成没成功。
关键在于**新接口不会漏记**。

- 切点直接挂在「方法上带权限注解」这件事上，而不是逐个接口加审计注解。因此所有**方法级**带权限注解的非 GET 后台接口
  自动被记录。
- 切面在处理器内部执行，也就是在授权拦截器之后，所以主体一定已经在线程局部变量里了。
- 取不到当前 HTTP 请求，或者是 GET 且没有显式审计注解，就直接放行不记。带了显式审计注解的 GET 也会被记
  （留给「查询本身就敏感」的接口）。
- 调用真正的业务方法：
  - 抛异常：记一行失败，错误码取业务异常自带的码，取不到就用异常类名，然后把异常继续往外抛。
  - 返回了一个「不成功」的统一响应体：也记一行失败，错误码取响应体里的码。
  - 正常返回：记一行成功。
- 记什么：
  - 账号 id、商户 id、用户名从主体拿。
  - 动作名默认是「HTTP 方法 + 路由模板」（用模板不用实际 URI，这样同一个接口的动作名是稳定的、可聚合的）；
    显式审计注解可以覆盖成一个稳定的业务动作名。
  - 目标 id 默认取路由上的路径变量，按变量名排序后拼成「名=值」的串；显式注解里可以写一段 SpEL，
    对着处理器的返回值求值（核销那条链路就是靠它记下券号而**不记核销码**，详见第 07 章）。这段 SpEL 只在
    成功返回时求值，失败那一行仍然退回路径变量；求值抛异常也只打日志、退回默认取法。目标 id 超过 255 字符截断。
  - 客户端 IP 走可信代理解析：只有直连对端落在配置的可信代理网段里时才认 `X-Real-IP` / `X-Forwarded-For` 的第一跳，
    否则一律用直连地址。否则任何人都能伪造审计里的 IP。
- 写入用**独立事务**（`REQUIRES_NEW`）：业务事务回滚了，这条「失败」的审计还是要留下来。
- 写审计本身失败只打 error 日志，**不向上抛**：操作已经发生了，不能因为审计写不进去就把一次成功的操作报成错误。
- 查询侧：审计列表需要审计查看权限点，平台账号看全部，商户账号强制按自己的商户 id 过滤，按主键倒序，
  每页上限 100 条。

### 3.5 后台实时推送的握手票据

后台要接实时订单事件，但浏览器的 WebSocket 握手不能带自定义请求头，令牌只能进 URL——而 URL 会进日志、
进 Referer、进浏览器历史。所以用一次性短票据换连接（推送的内容和扇出路径详见第 09 章）。

- **领票**：带令牌调领票接口，接口本身要求实时订单权限点。服务再解析一次令牌，主体为空或没有实时订单权限就返回 401；
  否则生成一个 32 位十六进制票据，把**令牌**作为值写进票据键，TTL 30 秒，返回票据和有效期。
- **握手**：客户端把票据拼在握手 URL 的查询参数里。
  - 握手拦截器从查询参数里取票据，为空 401；票据同样要先过 32 位十六进制的正则，形状不对就不去 Redis。
  - 消费票据用一小段 Lua：`GET`，取不到返回空；取到就 `DEL` 再返回。放进 Lua 是因为「读出来」和「作废」
    之间不能被另一次握手插进来——两个人拿同一个票据只能有一个连上。
  - 拿到令牌后再解析一次主体（这一次**不续**会话 TTL，握手不该延长一个人的登录时间）。主体为空就是 401。
  - 再查一次实时订单权限（403），再查范围自洽性：平台主体不能带商户 id，商户主体必须带商户 id（403）。
  - 全过就把账号 id、商户 id、范围类型、**令牌本身**和连接类型写进会话属性。令牌留着是为了后面复验。
- **每次推送前复验**：平台频道和商户频道的消息分发时，对每个本地会话都要重新解析一次它存着的令牌，
  核对账号 id 一致、仍有实时订单权限、范围类型一致、商户 id 一致。任何一条不符就把这个会话从注册表里摘掉并
  以「违反策略」关闭。所以 3.3 那一刀对已连上的长连接同样生效，只是生效时机是「下一条要推给它的消息」。
  连接已经关闭、或者发送抛异常的会话也会被顺手清掉。

## 四、口述版

### 4.1 登录

管理员输用户名和口令来换令牌。先把用户名去空白转小写，用一个正则卡格式，格式不对也不立刻报错，
而是当成一个不存在的用户名往下走，因为我不想让「格式错」「不存在」「口令错」这几种情况在返回上或者耗时上有区别。
然后查锁：用「用户名加客户端 IP」拼起来做一个摘要当 key，读失败次数，到了 5 次就直接 429，连数据库都不查，
这样暴力破解打不到库。接着是 IP 维度的一个计数，先加一再看，超过 30 次也 429，挡的是同一个 IP 换着用户名试。
这两个计数都用同一段很小的 Lua 脚本来加，脚本里先 `INCR`，如果返回 1 说明是这个窗口的第一次，再补一个 15 分钟的过期，
之所以要放进 Lua，是因为如果加完还没来得及设过期就出问题，这个键就永远不过期，这个账号等于被永久锁死了。
Redis 读写只要出异常，整条登录就返回 503，我宁可后台登不进去也不能在限流坏掉的时候放开验证。

限流过了才查账号。这里有个细节：账号不存在的时候我也照样跑一次口令比对，拿一个启动时就算好的假哈希去比，
目的是让「用户名不存在」和「口令错」耗时差不多，不给人做时间侧信道枚举用户名。口令对上之后，
还要再做一次资格检查，也就是账号必须是启用的、平台账号不能挂商户、商户账号必须挂一个启用中的商户、
角色也得对得上——平台账号得持有平台角色，商户账号得是主账号或员工并且不能同时是平台角色。这一步顺带就把它的角色和
权限点查出来了。任何一条不满足，都按登录失败处理。

失败就把那对「用户名加 IP」的计数加一，加完到 5 次返回 429，没到返回 401，但文案都是「账号或密码错误」。
成功就反过来，先把失败计数删掉，生成一个 32 位十六进制的随机令牌，往 Redis 里写一个会话键，
值不是单纯的账号 id，而是「账号 id 加上当前的认证版本号」，设 30 分钟过期，再更新一下最后登录时间，
把令牌、有效期和这个人的权限点一起返回。值里带版本号，是为了后面能一刀撤销这个账号的所有会话。

### 4.2 一次带令牌的请求

后台请求要过两个拦截器。第一个只负责认人：从 Authorization 头里取 Bearer 令牌，没有就放行，因为「拒绝」不是它的活。
令牌先过一遍 32 位十六进制的正则，形状不对就当没有，省一次 Redis 往返。然后读会话键，把值按冒号切成账号 id 和
签发时的版本号，切不出来说明是脏值，顺手把这个键删掉。拿账号 id 重新跑一遍刚才那套资格检查，得到当前的主体，
再把当前的认证版本号和会话里记的那个比一下，账号被停了、商户被停了、或者版本号对不上，都把会话键删掉、当没登录。
都过了才给会话键续 30 分钟，把主体塞进线程局部变量，请求结束时清掉。

第二个拦截器才是判断允不允许。没有主体就 401；拿到的不是一个控制器方法就 403；然后找权限注解，
先看方法上有没有，没有再看类上有没有，两个地方都没有就直接 403。这一条我觉得是这套东西里最值钱的设计：
后台接口是白名单准入的，新写一个接口如果忘了加注解，它是不可用而不是敞开的。注解值为空表示登录就行，
比如查自己、改密码、登出；值非空就去主体的权限集合里查这个权限点，没有就 403。

但是接口能调不等于什么行都能看，所以第三层在每个服务方法里：判断这个人是平台范围还是商户范围，
商户范围的话所有列表查询强制加上自己的商户 id 条件，单条读取按主键加商户 id 查、查不到统一返回 404，
不存在和不属于你在外面看起来是一样的，不给跨商户探测留信号。更新的时候先按主键加商户 id 带 `FOR UPDATE` 锁住行，
更新语句的 where 里再带一次商户 id，影响行数不是 1 就当 404，我不依赖「读的时候属于我、写的时候还属于我」。
只有平台能做的事，比如建商户、列商户、把历史商铺分给某个商户，在服务里再显式判断一次范围类型。
商铺归属还多一条规则：只允许认领那些还挂在「历史待分配」商户下的老商铺，已经有主的不许换绑，
而且更新是以「当前归属仍是原来那个」为条件的，两个人同时认领只有一个能成。

### 4.3 改密与停用

后台账号是长期身份，改了密码之后那些还没过期的会话必须马上失效。会话是 Redis 里的一行，删掉就撤销了，
问题是一个账号可能同时有好几个会话，令牌又不落库，我没法枚举它们。所以账号表上有一个认证版本号，
会话里记着签发时的那个版本号，改密码和停用账号的时候把它加一。

改密码是登录就能做的，不需要额外权限点。新口令要求至少 12 位、UTF-8 不超过 72 字节，上限是因为 bcrypt 本身就只看
前 72 字节，超出的部分会被悄悄截掉，与其让人以为自己设了个很长的密码，不如直接拒绝。校验原口令之后，
真正的更新是一条 CAS：改口令哈希、版本号加一，条件是主键匹配、版本号还是我刚才读到的那个、状态还是启用，
影响行数不是 1 就返回 409 让他重登再试。停用员工账号也是一样的套路，多几条前置规则：不能停自己，
免得把自己关在门外；目标必须在自己的数据范围里，不在就是 404；目标如果是平台角色或者商户主账号，
不许用这个员工接口停掉；更新同样带版本号 CAS，商户账号还要在条件里带上自己的商户 id。

这么一来撤销就变成了自然发生的事：版本号一加一，所有在途会话里记的那个数就都旧了，下一次请求走到会话拦截器那里，
比对不上，会话键被删掉，请求按未登录处理。不用遍历 Redis 也不用维护黑名单。代价是它不是「立刻」失效而是
「下一次请求时」失效，已经建好的长连接则靠推送前的复验兜住。主动登出反而最简单，把那一个会话键删掉就行，
同一个账号的其他会话不受影响。

### 4.4 审计

后台写操作要能追责，需求是一张表加一个切面。我没有给每个接口挂审计注解，而是把切点直接挂在「方法上带权限注解」
这件事上，这样所有**方法上**带权限注解的非 GET 接口自动被记录，新加接口漏不掉——漏了注解的接口本来也进不来。
代价是注解写在控制器类上的那几个接口（登录、登出、改密、查自己）切点匹配不到，目前确实没有审计行。
切面跑在处理器里面，在授权拦截器之后，所以主体一定已经有了。

它把业务方法包起来，抛异常就记一行失败、错误码取业务异常自带的码、取不到就用异常类名，然后把异常照常往外抛；
返回的统一响应体里标着不成功，也记一行失败；正常返回记一行成功。记的内容是账号、商户、用户名、动作名、目标、
结果、错误码和 IP。动作名默认是「HTTP 方法加路由模板」，用模板不用实际 URI，这样同一个接口的动作名是稳定的、
能聚合统计。目标默认取路由上的路径变量拼成串，需要更准的话可以在注解里写一段 SpEL 对着返回值求值，
比如核销那条链路就是用它把券号记下来，而故意不记核销码——核销码是用户手里的秘密，不能因为审计反而泄露出去。
IP 不是直接拿远端地址，而是只有在直连对端落在配置的可信代理网段里时才去信那些转发头，不然谁都能伪造审计里的 IP。

有两个细节是刻意的。一是审计行走独立事务，业务事务回滚了这行失败记录还得留着，不然最值得查的那种情况反而没有记录。
二是写审计本身失败只打日志不往外抛，操作已经真实发生了，不能因为审计写不进去就把一次成功的操作向操作员报成失败。
查询侧要审计查看权限，平台看全部，商户强制按自己的商户过滤，每页最多一百条。

### 4.5 握手票据

后台要接实时订单推送，但浏览器发 WebSocket 握手的时候不能自定义请求头，令牌只能塞 URL 里，
而 URL 会进访问日志、进浏览器历史。所以我让它先用令牌调一个领票接口，这个接口要求实时订单权限点，
服务端再解析一次令牌确认权限，然后生成一个随机票据，把令牌作为值存进票据键，只给 30 秒。
客户端拿票据去握手，握手拦截器用一小段 Lua 消费它：先 GET，拿不到返回空，拿到就 DEL 再返回。
必须放在 Lua 里，是因为「读出来」和「作废」之间不能被另一次握手插进来，同一个票据只能换一次连接。

换出令牌之后再解析一次主体，这次不给会话续期，握手不应该延长登录时间；然后再查一次实时订单权限，
再查范围自洽——平台主体不能带商户 id，商户主体必须带商户 id。都过了，就把账号 id、商户 id、范围类型
和令牌本身存进这个连接的会话属性里。令牌留着不是为了图省事，是因为每次要往这个连接推消息之前，
我都会拿它重新解析一遍主体，核对账号 id、权限、范围和商户 id 是不是还对得上，对不上就把这个会话摘掉、
以违反策略关闭。这样前面说的那一刀对已经连上的长连接也生效，只是生效时机变成了「下一条要推给它的消息」。

## 五、为什么这么设计 / 会被怎么追问

**为什么后台身份要和消费者身份完全分开？** 两套的威胁模型不一样。消费者是短信验证码登录、量大、单个账号权限小；
后台是口令登录、量小、单个账号能改商铺和券。分开之后消费者的拦截器对后台路径整体排除，后台的两个拦截器只管后台路径，
一套的漏洞不会横向变成另一套的越权；令牌的键前缀、TTL、失效机制也各自独立。消费者侧详见第 01 章。

**权限为什么用注解而不是在网关或过滤器里配一张路径表？** 路径表和代码分处两地，改路由就会不同步。
注解跟着方法走，而且这套是 fail-closed 的：**没有注解等于 403**。路径表通常反过来，没命中就放行。
代价是注解只表达「要哪个权限点」，表达不了「这一行是不是你的」，所以行级隔离还得在服务里手写。

**那行级隔离手写会不会漏？** 会，这是这套设计的真实弱点。目前靠的是每个服务方法固定的写法
（列表加条件、单条按主键加商户查、更新的 where 里再带一次商户 id）和集成测试，没有像 MyBatis 拦截器那样
自动往 SQL 里注入租户条件。好处是逻辑显式、看得见；坏处是新写一个查询全靠人记得。

**为什么撤销用版本号而不是把令牌记到库里？** 令牌落库就要维护一张会话表，每次请求还得写一次续期。
版本号是账号表上的一个整数，改密和停用本来就要写这一行，加一不花额外的写；撤销是「懒失效」——
下一次请求自己发现对不上。缺点是失效延迟到下一次请求，而且粒度是整个账号，做不到「只踢掉某一台设备」。

**版本号为什么必须是 CAS 而不是直接加一？** 因为改密和停用可能并发。如果直接 `版本号 = 版本号 + 1`，
两个操作都会成功，但其中一个读到的账号状态可能已经过期了（比如在我校验完原口令之后别人把账号停了）。
带上「版本号仍是我读到的那个」做条件，影响行数不是 1 就返回 409，让对方重新来一遍。

**失败计数为什么按「用户名+IP」而不是按账号？** 按账号锁的话，任何人只要连着输错 5 次就能把别人的账号锁死，
这是个现成的拒绝服务。按「用户名+IP」锁，外加一个 IP 维度的总尝试上限，是在「防爆破」和「防恶意锁人」之间取的折中。
代价也很直白：一个攻击者如果有大量 IP，针对同一个用户名的爆破不会被这条计数拦住，只能靠口令强度和 bcrypt 的成本兜。

**Redis 挂了为什么登录直接 503，不放行？** 因为放行等于把限流和锁定一起关掉，而后台账号是高权限的。
这和别处的取舍是反的——比如核销限频在 Redis 故障时是放行的，不能让门店停业（详见第 07 章）。
同一个系统里 fail-open 还是 fail-closed，取决于这个动作失手的代价。

**握手票据为什么要 30 秒这么短，而且只能用一次？** 票据一定会出现在 URL 里，所以要假设它会泄漏到日志和历史记录。
短到只够客户端立刻发起握手，用掉就作废，泄漏出去的那一份基本没有价值。真正的长期令牌始终只在请求头里。
消费必须原子，否则同一条日志里的票据可能被并发换出两条连接。

**审计为什么挂在权限注解上，而不是每个接口写一个审计注解？** 计划里要的是「新接口不会漏」。挂在权限注解上，
覆盖范围和「受保护的后台写接口」这个集合天然一致，不需要人记得加；显式的审计注解退化成一个可选项，
只用来起一个稳定的动作名和挑出业务目标。

**审计写失败为什么不影响主流程？** 因为操作已经发生了。把审计写入放进业务事务，看起来更「严谨」，
实际后果是审计表抖一下就会让真实的商铺修改回滚，操作员看到一个失败但数据其实可能已经变了；
而且失败的业务事务回滚时会把那行「失败审计」一起带走，最该留的记录反而没有。独立事务加打日志是权衡后的结果，
真要做到不丢，得把审计写成消息投出去。

## 六、已知边界

- **登录接口、登出、改密码、查自己这几个接口不会被审计。** 审计切点只看**方法上**的权限注解，
  而这几个接口的注解写在控制器类上，切点匹配不到。也就是说「谁在什么时候改了自己的密码」目前没有审计行，
  只有认证指标里的成功/失败计数。这是一处实打实的缺口。
- **领票接口反而会被审计**（它是 POST 且有方法级注解），页面每次重连都会写一行，属于噪音。
- **每个后台请求都要一次 Redis 读加三到四次数据库查询**（账号、角色码、权限点，商户账号再加一次商户主体），
  没有任何缓存。
  后台 QPS 低所以没做，但这是「能立刻撤销」的直接代价——一旦缓存权限，版本号那一刀就不再是下一次请求生效。
- **IP 维度的尝试计数不会因为登录成功而清零。** 15 分钟窗口内同一个出口 IP 的第 31 次登录尝试会被拒，
  哪怕前 30 次全是成功的。办公室或商场这种共用出口 IP 的场景下会误伤。
- **失败锁定是固定窗口，不是滑动窗口**，也没有指数退避：从第一次失败算起 15 分钟后计数整体消失。
- **没有二次验证、没有口令有效期、没有历史口令复用检查**，口令规则只有长度下限 12 和 UTF-8 上限 72 字节，
  不校验复杂度。
- **平台初始账号靠环境变量引导，没有配就不建。** 启动时如果一个平台账号都没有、引导用户名和口令又都没配，
  只打一条告警日志，后台保持登不进去的状态；只配了其中一个则直接启动失败。这是刻意的 fail-closed，
  代价是新环境第一次拉起来必须先想起来配这两个变量。
- **行级隔离全靠各个服务方法自觉**，没有统一的租户条件注入，也没有一个「所有后台查询都必须带商户条件」的静态检查。
- **平台范围的账号在业务上是全通的**，包括核销任何商户的券（详见第 07 章）；目前只靠「平台账号很少」这个前提控制，
  没有再分一层（比如只读运营和可写运营）。
- **审计表只增不删**，没有归档或分区策略；查询只支持按商户过滤加主键倒序翻页，没有按动作名、时间范围、
  操作人筛选的接口。
- **商户后台按商户翻页订单是跨 8 张分片表的广播归并**（ES 读模型已决定不做），详见第 08 章。
- **后台前端页面没有做**，这一章讲的全部是接口。
