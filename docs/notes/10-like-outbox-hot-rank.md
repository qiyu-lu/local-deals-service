# 10 点赞 Outbox 与热榜：先写事实、再投影

## 一、这一章解决什么问题

点赞是典型的「写很碎、读很集中」。写的一面：同一条笔记的点赞在热点时刻会打到同一行上，
如果每次点赞都直接 `UPDATE 笔记表 SET 点赞数 = 点赞数 + 1`，热点行锁会把写入串成一条线；
而且「谁点过」这件事必须是持久事实，不能只活在缓存里，否则 Redis 一丢，用户的点赞状态全没了。
读的一面：首页热榜要按点赞数排序分页，而排序字段恰恰是被高频改动的那一列，直接查库分页既慢又抖。

所以这一章做两件事。第一，**点赞写入只落两张表的事实**——一条「谁赞了哪条笔记」的关系行，
和一条「这条笔记 +1 / -1」的事件行，两者在同一个事务里提交；计数列由一个后台 worker 批量合并后再改，
把 N 次热点行更新压成一次。第二，**热榜是一份可以随时重建的派生读模型**——后台定时从库里取前 K 名，
整份构建、整份原子发布；读的时候任何一个不安全的迹象都算未命中，直接回数据库分页。

难点在于：异步投影必须**恰好生效一次**（重放不能把计数加两遍），整份发布必须**不能把旧快照盖到新数据上**，
而读出来的一页必须要么是同一份快照里的连续排名，要么干脆算未命中。

## 二、涉及的数据

**点赞关系表**（持久事实，本章的真相源）

- 笔记 id + 用户 id 作联合主键：这就是天然的幂等键，重复点赞会撞主键，不需要额外的去重结构。
- 点赞时间（毫秒精度）：用来算「最早点赞的五个人」。
- 索引：按（笔记 id，点赞时间，用户 id）给「前五个点赞的人」用；按（用户 id，笔记 id）给「这一页里我赞过哪些」用。
- 两个外键：指向笔记表的是级联删除（笔记没了，点赞关系跟着没），指向用户表的是禁止删除。

**点赞事件表（Outbox）**

- 自增主键：既是事件顺序，也是 worker 每轮取批时的排序键（worker 不保存游标，每轮都从未处理的最前面重新扫）。
- 笔记 id、增量（只允许 +1 / -1，表上有 CHECK 约束）、创建时间、处理时间（可空）。
- 也有一个指向笔记表的级联删除外键：笔记被删时，它尚未处理的事件行跟着消失。
- 处理时间为空表示「还没投影到计数列」。索引按（处理时间，主键）建，未处理的一段永远在索引最前面，
  扫描代价与历史总量无关。
- 还有一个按（笔记 id，主键）的索引，用于按笔记追查事件。

**笔记表**

- 点赞计数列：无符号整数、非空、默认 0，**由 worker 独占维护**，任何在线请求都不直接改它。
- 联合索引（点赞数降序，id 降序）：热榜降级回数据库时就靠它；另有一个（商户 id，点赞数降序，id 降序）给「本店笔记」用。
- 历史包袱已清：早期为灰度切换留的「未归属点赞偏移列」和「切换完成标记表」在后来的迁移里被删掉了，
  现在计数列的含义非常干净——**它就是点赞关系表中对应行数的异步投影**。

**热榜的 Redis 结构**（五个 key 共用同一个 hash tag，保证在集群里落到同一个槽，才能被一段 Lua 一起操作）

- 一个**在线 ZSET**：成员是补零到 19 位的笔记 id，分数是点赞数。定长补零是为了让同分时的字符串比较等价于 id 的数值比较。
- 一个**元数据哈希**：是否就绪、当前代号、成员数、容量（即配置的 K）、发布时间戳（毫秒）。
- 一个**代号计数器**：单调递增的整数，用来判断「我这份构建还是不是最新的」。
- 一个**按代号命名的临时 ZSET**：构建期间的暂存区，构建完成后被改名成在线 ZSET。
- 一把**重建锁**：只用来减少重复构建，不承担正确性。

## 三、详细流程

### 3.1 点赞 / 取消点赞：一次请求只写事实

用户对某条笔记点赞或取消点赞，用两个不同的 HTTP 方法表达**期望状态**（要赞 / 不要赞），
而不是「切换」。请求到关系行与事件行一起提交为止就结束了，返回里带的是「本次是否真的改变了状态」，
点赞计数此刻还没有变。

● 参数校验：笔记 id 与用户 id 必须为正。用户 id 来自登录态。

● 开启一个事务，先用共享锁读一次笔记行（`SELECT id ... LOCK IN SHARE MODE`）。
  ○ 读不到就直接返回「笔记不存在」，接口层翻成 404。
  ○ 用共享锁而不是排他锁，是因为**同一条笔记的并发点赞之间不需要互斥**（它们写的是不同的关系行），
    要挡住的只有「一边删笔记、一边点赞」：删除方需要排他锁，会被这个共享锁挡在存在性检查之后、提交之前。
  ○ 外键仍然是最后一道数据库层的完整性兜底，这把锁只是把竞态提前变成等待而不是报错。

● 按期望状态改关系行。
  ○ 期望「赞」：直接插入关系行。撞到主键唯一键（重复点赞）时捕获，返回「未改变」，**不写事件行**。
  ○ 期望「不赞」：按笔记 id + 用户 id 删除。影响行数为 0 说明本来就没赞，返回「未改变」，同样不写事件行。
  ○ 影响行数既不是 0 也不是 1，说明数据层出了预期外的情况，直接抛异常让事务回滚。

● 只有状态**真的发生了改变**，才在同一个事务里插入一条事件行，增量是 +1 或 -1。
  插入影响行数不等于 1 就抛异常回滚——这条断言保证了「一次状态改变」与「一条事件」严格配对，
  不会出现关系行提交了而事件丢了的情况。

● 提交。到这里用户已经能在「我赞过吗」上看到正确结果（那是直接查关系表的），
  但笔记的点赞数还是旧值，要等 worker 投影。

### 3.2 投影 worker：把 N 次热点行更新压成一次

一个定时任务把已提交的事件行按主键顺序成批地合并进点赞计数列。启动后延迟 5 秒开始，
每次执行完固定间隔 200 毫秒再跑下一次，单批上限 500 条。

● 先尝试拿一把 Redis 上的分布式锁（点赞投影专用，与热榜那把不是同一把），**不等待**。
  ○ 拿不到：说明别的实例正在跑，本次直接返回空结果，记一个「锁忙」计数。
  ○ 拿锁时 Redis 抛异常：**不中止**，记一个「Redis 锁异常」计数后照常往下走。
    这把锁只是减少多实例空转，真正的互斥来自数据库的行锁，Redis 挂了不影响正确性，只是变吵。

● 进入一个读已提交隔离级别的事务：
  ○ 按主键顺序取一批「处理时间为空」的事件行，并加 `FOR UPDATE` 排他锁。
    这既锁住了这批行，也保证另一个实例只能取到后面的行或阻塞等待。
  ○ 逐条校验增量只能是 +1 或 -1，出现别的值直接抛异常整批回滚（数据库上的 CHECK 之外的第二道闸）。
  ○ 在内存里按笔记 id 把增量**合并求和**（用按 id 有序的 map，后续更新语句的发出顺序因此是确定的）。
    500 条事件如果全打在同一条热点笔记上，合并后只剩一次更新——这就是省掉热点行锁的地方。
  ○ 合并后增量为 0 的笔记（赞了又取消）**跳过更新**，但事件行照样会被标记为已处理。
  ○ 逐个笔记执行一条带守卫的更新：
    `UPDATE 笔记表 SET 点赞数 = CAST(点赞数 AS SIGNED) + ? WHERE 主键 = ? AND CAST(点赞数 AS SIGNED) + ? >= 0`。
    - 转成有符号数再算，是因为计数列是无符号的，直接减会在下溢时报错而不是被守卫挡住。
    - 守卫条件保证计数永不为负；影响行数不是 1 就抛异常，整批回滚。
    - 这里是**一条一条发**而不是 JDBC 批量更新，因为批量更新允许驱动返回「成功但不知道行数」，
      那样这条安全断言就形同虚设。
  ○ 把这一批事件行的处理时间置为当前时间，条件里仍带「处理时间为空」；
    标记成功的行数必须等于本批行数，否则抛异常整批回滚。

● **计数更新与已处理标记在同一个事务里提交**，这是恰好生效一次的核心：
  提交前崩溃，整批回滚、下次重放；提交后崩溃，这批事件已带标记，不可能被再加一遍。
  ○ 但「恰好一次」不是只靠这一条，它有三个前提缺一不可：写入侧「一次状态改变严格配对一条事件」；
    取批时的 `FOR UPDATE` 让两个实例不可能同时应用同一段事件；标记语句的条件里仍带「处理时间为空」，
    并要求标记行数等于本批行数，所以一批里混进已被别人处理的行会当场回滚而不是重复累加。
  ○ 注意这里的「恰好一次」说的是**增量被应用到计数列恰好一次**，不是「事件只被读取一次」——
    回滚后同一批会被原样重新读取和重新应用。

● 事务抛出的异常被定时任务最外层捕获并记 error 日志，事件行保持未处理状态等待下一次重试。

● 每次执行记录三类指标：批次结果（成功 / 空 / 锁忙 / 数据库异常 / Redis 锁异常）、耗时、本批事件数。
  另有一个低频采样器周期性地查「未处理事件条数」和「最老未处理事件的年龄」两个仪表，
  这两个数才是判断投影是否积压的依据。

### 3.3 清理：有界保留已处理的事件

已处理的事件行是证据，但不能无限长。另一个定时任务（同样延迟 5 秒启动、间隔 1 秒）做有界删除。

● 每次最多删 5 批，每批 2000 行，条件是「处理时间非空且早于保留期（1 天）」，
  按（处理时间，主键）排序后 LIMIT 删除。某一批删的行数少于批大小就提前结束，说明已经追上了。
● **只碰已处理的行**，绝不影响未处理事件；异常只记 warn 日志，不让清理拖垮投影。
● 一个真实的坑：这里的时间条件必须写成 `DATE_SUB(..., INTERVAL ? SECOND)`。
  用 `TIMESTAMPADD(SECOND, -?, ...)` 时，分库分表中间件的解析器会把单位 `SECOND` 当成列名，
  报「Unknown column 'SECOND'」——因为接入之后**所有语句**都要过它的解析器，哪怕这张表根本没分片。

### 3.4 热榜重建与原子发布

后台定时任务（延迟 10 秒启动、间隔 30 秒，受一个开关控制）把「前 K 名」整份重建一次。K 默认 1000。

● 尝试拿重建锁，**不等待**：拿不到就记「跳过，锁忙」直接返回，多实例不会重复扫库。
  连锁句柄都取不到（Redis 不可用）时记一次「失败」并返回，本轮不构建。

● 对代号计数器执行 `INCR`，拿到属于**本次构建**的代号 g，并据此拼出一个按代号命名的临时 key。
  代号是这条链路的核心：它让「我开始构建时的世界」和「我发布时的世界」可以被比较。

● 从数据库按（点赞数降序，id 降序）取前 K 行，走的正是笔记表上那个联合索引。
  行里出现非正的 id 或负的点赞数，直接判为数据异常抛出。

● 把候选写进临时 ZSET：先删一次同名 key，再一次性 ZADD，
  写入条数与候选数不符就抛异常；随后给临时 key 设一个等于「最大容忍陈旧时间」（2 分钟）的过期时间，
  这样即使构建中途崩溃，垃圾 key 也会自己消失——过期时间没设上同样抛异常，不允许留下一个没有寿命的暂存区。
  ○ 候选为空是合法的（库里还没有笔记），此时不写临时 key。

● 调用发布脚本，把在线 ZSET、元数据哈希、代号计数器、临时 ZSET 四个 key 和
  （本次代号、候选数、当前毫秒时间戳、容量 K）一起交给一段 Lua **原子**执行：
  ○ 读当前代号，与本次代号不相等 → 说明构建期间有人推高了代号，本次是陈旧构建：**删掉临时 key、返回 0**，
    Java 记一条「丢弃陈旧构建」的日志，本轮到此为止。这是防止旧快照覆盖新数据的关键。
  ○ 校验候选数与容量的合法性（非负、容量为正、候选数不超容量），不合法直接返回错误。
  ○ 候选数为 0：删掉在线 ZSET 和临时 key——「就绪但为空」和「尚未初始化」是两种不同的状态，
    后面还要写元数据把它标成就绪。
  ○ 候选数非 0：临时 key 不存在返回 -1；临时 key 的基数与预期不符则删掉它并返回 -2；
    都对就 `RENAME` 临时 key 覆盖在线 ZSET——**整份切换就是这一条命令，读者看不到中间态**。
  ○ 最后一次性写元数据哈希：就绪标志、代号、成员数、容量、发布时间戳。返回 1。

● Java 侧：返回 1 记「已发布」，返回 0 记「陈旧代号」，其他值一律当成异常。
  构建过程中的任何异常都会尽力删掉临时 key，并把结果记成「失败」；最后释放锁（只在确实由本线程持有时释放）。

● 另有一条**新笔记发布后的即时补充**路径：笔记创建事务提交之后（注册在事务同步的提交后回调里）
  调用一段 Lua，把新笔记以 0 分插入在线 ZSET：
  ○ 元数据未就绪 → 直接返回，不做任何事，也绝不把未就绪的榜单变成就绪。
  ○ 校验代号：代号计数器和元数据里的代号都必须是合法的正整数（并且不越过有符号 64 位上界），
    在此之上，只有「当前代号比元数据里的代号更小」才算非法。
    当前代号比元数据大一步是**正常**的——那说明某个构建正在扫库，而这恰恰是本脚本要围栏的窗口。
  ○ 还要求元数据里的容量与本次传入的 K 相等，防止改过 K 之后往一份旧容量的榜里插新笔记。
  ○ 上面任何一项不成立，脚本直接返回错误（不是静默返回），Java 侧按 Redis 异常吞掉并记 error 日志。
  ○ `ZADD NX`，已存在则不覆盖分数、直接返回。
  ○ 插入后若超出 K，按升序排名删掉最低的若干个（升序是分数升序再成员升序，正好是读取时逆序取的反面，
    包括 0 分之间按 id 的平手规则）。
  ○ 如果被删掉的正是刚插进去的这条（它本来就进不了前 K），就**什么都不做地返回**，没必要去打断一个正在跑的构建。
  ○ 否则 `INCR` 代号，并把元数据里的代号与成员数一起改掉——这就是**围栏**：
    某个在这条笔记提交之前就把库读完了的构建，它的发布脚本此刻会发现代号对不上，只能丢弃自己那份快照。
  ○ 整段过程中的任何 Redis 异常只记 error 日志，绝不让它影响笔记创建接口的返回。

### 3.5 热榜读取与降级回数据库

用户请求热榜第 n 页。这一页要么来自 Redis 的一份自洽快照，要么整页降级回数据库，**不存在混着来**。

● 页码必须为正；用配置的页大小算出偏移与结束下标。
  **整页都必须落在前 K 之内**，否则算一次「超出 top-K」的未命中——深翻页本来就不该由这份有界读模型承担。

● 读元数据哈希：
  ○ 就绪标志不是 1 → 「未就绪」未命中。
  ○ 代号、成员数、容量、发布时间戳任一格式非法，或**容量与当前配置的 K 不相等** → 「元数据异常」未命中。
    容量校验是为了防止有人改了 K 之后仍然按旧容量读一份旧榜。
  ○ 发布时间戳晚于当前时间，或已经超过最大容忍陈旧时间（2 分钟） → 「陈旧」未命中。
    这个值被强制要求大于刷新间隔（30 秒），否则启动时配置校验就会失败。

● 读在线 ZSET 的基数，必须等于元数据里的成员数、且不超过 K，否则算「快照不一致」未命中。

● `ZREVRANGE` 取这一页的成员，然后**再读一次代号与成员数**，与第一次读到的比对：
  ○ 任一不同 → 「快照不一致」未命中。因为元数据和 ZSET 是两次往返，中间可能正好被一次发布或一次新笔记插入切换过；
    代号单调递增，所以这个比对不会被 ABA 骗过。
  ○ 这是一个乐观的读围栏：它只负责把可疑的读变成未命中，**正确性最终由降级路径兜底**。

● 逐个解析成员：必须是 19 位纯数字且为正，否则算「成员非法」未命中。

● 整段读取被包在 try/catch 里，任何 Redis 异常都翻成「Redis 不可用」未命中；
  为避免故障期刷屏，warn 日志被限流成每 30 秒最多一条，其余降为 debug。
  每一种命中/未命中原因都有独立计数器——排查时能直接看出是没就绪、陈旧、还是连不上。

● 回到业务层：
  ○ 命中且结果为空 → 直接返回空列表，不查库。
  ○ 其余情况都进入一个**本地读并发隔离舱**再做真正的数据库读，防止降级瞬间把连接池打满：
    一个固定许可数（4）的信号量，拿不到最多只等 20 毫秒，等不到就直接拒绝（429），不排无界队列。
  ○ 命中时按 id 批量取笔记，再按榜单顺序重排。只要有一个 id 查不到（榜上有已删除的笔记），
    **整页作废、退回数据库分页**——宁可多查一次，也不返回一个带窟窿的页。
  ○ 未命中（或上一步作废）时：先异步触发一次预热，再用「点赞数降序、id 降序」直接分页查库，
    并且**不查总数**；这次降级查询的耗时单独计时，用来回答「降级到底有多贵」。
  ○ 预热是本地单飞：一个原子布尔保证同一实例同时只有一次预热在跑，丢进共享线程池执行；
    跨实例的单飞由重建自己那把不等待的锁提供——也就是说**单飞只覆盖到实例内**，
    多实例同时预热靠的是抢锁失败后跳过，而不是不发起。线程池拒绝任务时把标志复位并记 warn。
  ○ 预热和定时重建受同一个刷新开关控制：开关关掉时未命中不会触发预热，只是一直走降级。

● 最后是一页的装配：一次批量查作者、一次批量查「当前用户赞过这一页里的哪些」，
  避免逐条查询；未登录时跳过第二次查询。

## 四、口述版

### 4.1 点赞与投影

用户点赞的时候，我不去动笔记的点赞数，我只写事实。开一个事务，先用共享锁把笔记行读一下，
读不到就返回笔记不存在；用共享锁是因为同一条笔记的并发点赞彼此之间根本不冲突，它们写的是不同的关系行，
我要挡的只是「一边在删这条笔记、一边有人点赞」，删除要拿排他锁，会被我这把共享锁卡住。
然后按期望状态改关系行：要赞就插一条「用户加笔记」的关系行，主键就是这两个 id，所以重复点赞会撞唯一键，
我捕获它并返回「没有变化」；要取消就按这两个 id 删，删到 0 行同样是「没有变化」。
只有状态真的变了，我才在同一个事务里插一条事件行，值是 +1 或 -1，插入影响行数不是 1 就抛异常回滚——
这样「一次状态改变」和「一条事件」是严格配对的，不会出现关系写进去了而事件丢了。事务提交，请求就结束了，
这时候点赞数还是旧的，但用户查「我赞过吗」是直接查关系表的，所以他自己看到的状态是对的。

后面有一个定时 worker，每隔两百毫秒跑一次，一次取五百条。它先去 Redis 上抢一把不等待的锁，
抢不到就这一轮不干活，抢锁的时候 Redis 报错也不管、继续往下走，因为这把锁只是减少多实例空转，
真正的互斥是数据库的行锁。然后开一个事务，按主键顺序把还没处理的事件行取出来并加排他锁，
在内存里按笔记 id 把增量加起来——这一步是整个设计的意义所在，五百次点赞如果都打在同一条热点笔记上，
合并完只剩一次更新，热点行锁就从五百次变成一次；加完是零的（赞了又取消）就不更新，但事件照样标记掉。
更新的时候我把计数列转成有符号再加，并且在 where 里带一个「加完之后大于等于零」的守卫，
因为那一列是无符号的，直接减会在下溢的时候报错而不是被挡住；影响行数不是一就抛异常整批回滚。
我是一条一条发的，没用 JDBC 批量，因为批量更新允许驱动只回一个「成功但不知道行数」，那我这条断言就白写了。
最后把这一批事件的处理时间打上，条件里仍然带「处理时间为空」，标记条数对不上也回滚。
关键就是**计数更新和已处理标记在同一个事务里提交**：提交前崩，整批回滚下次重放；提交后崩，这批已经有标记了，
不可能再加一遍。所以效果上是恰好生效一次：一批事件要么整批没应用、下次原样重放，要么应用了就带着标记，
不会被第二次累加；这里的「恰好一次」说的是增量落到计数列恰好一次，不是事件行只被读一次。
再往后还有一个清理任务，每秒一次，每次最多五批、每批两千行，只删处理时间超过一天的已处理行，
绝对不碰未处理的，出错也只是记个日志。这里踩过一个坑：时间条件不能用 TIMESTAMPADD，
因为分库分表中间件接进来之后所有 SQL 都要过它的解析器，它会把 SECOND 这个单位当成列名报错，
虽然这张表压根没分片。

### 4.2 热榜的构建、发布与读

热榜我是当成一份**可以随时丢掉重建的派生读模型**来做的，真相永远在数据库里。
后台每三十秒重建一次。重建的时候先抢一把不等待的锁，抢不到就说明别人在建，我直接跳过，省掉一次全量扫库。
拿到锁之后我先给一个代号计数器加一，拿到属于这次构建的代号，并用这个代号拼出一个临时 key。
代号是整条链路的核心，它让「我开始构建时的世界」和「我发布时的世界」能够比较。
然后我按点赞数降序、id 降序从库里取前一千行——这个顺序正好有一个联合索引，
写进临时 ZSET，成员是补零到十九位的笔记 id、分数是点赞数；补零是为了让同分时的字符串比较等价于 id 的数值比较，
排序规则才能和数据库那一侧对上。临时 key 我还会设一个过期时间，万一建到一半崩了，垃圾自己会消失。

发布是一段 Lua，四个 key 因为共用同一个 hash tag 所以在集群里一定落在同一个槽，才能被一段脚本一起操作。
脚本先读当前代号，跟我这次的代号不一样就说明我这份已经旧了——比如我扫库期间有新笔记进榜——
那就删掉临时 key 直接返回零，绝不能把旧快照盖上去。代号一致的话，校验一下数量和容量，
数量是零就把在线 ZSET 删掉，因为「就绪但是空的」和「还没初始化」是两种不同的状态；
数量不是零就检查临时 key 还在不在、基数对不对，都对就把临时 key 改名盖到在线 key 上——
整份切换就是这一条改名命令，是原子的，读的人不会看到半份榜。最后把元数据写上：就绪、代号、成员数、容量、发布时间戳。

另外还有一条即时路径：新笔记发布之后，在事务提交后的回调里我会用另一段 Lua 把它以零分塞进榜里。
它先看榜有没有就绪，没就绪就什么都不做；然后校验代号，注意这里只有「当前代号比元数据里的还小」才算非法，
比元数据大一步是正常的，因为那说明有个构建正在扫库，而那恰恰是我要围栏的窗口。
接着用 ZADD NX 插入，不覆盖已有分数；插完超过一千就把最低的几个删掉；如果被删掉的正好是我刚插的这条，
说明它本来就进不了榜，那我就什么都不做地返回，没必要去打断一个正在跑的构建。
只有它真的留在榜上，我才给代号加一并更新元数据——这样那个在这条笔记提交之前就把库读完的构建，
发布时会发现代号对不上，只能自己丢掉。整段里任何 Redis 异常我都只记日志，绝不让它影响发笔记这个接口。

读的时候是这样：先算偏移，要求整页都落在前一千名之内，超出就当未命中，深翻页本来就不该由这份有界的榜来扛。
然后读元数据，看就绪标志、代号、成员数、容量和发布时间；容量要跟我现在配置的 K 相等，
防止有人改了 K 之后还按旧容量读旧榜；发布时间不能是未来、也不能超过两分钟，超过就算陈旧。
接着读在线 ZSET 的基数，要跟元数据里的成员数对上，然后逆序取这一页，**取完再读一次代号和成员数跟之前比对**，
因为元数据和 ZSET 是两次往返，中间完全可能被一次发布切换过；代号是单调递增的，所以这个比对不会被 ABA 骗过。
成员还要校验是十九位纯数字。这一整段包在 try 里，Redis 出任何问题都翻成「不可用」这种未命中，
日志限流到三十秒一条，免得故障的时候刷屏。

最关键的是：**所有这些检查失败的结果都只是「未命中」，不是报错**。未命中就降级——先进一个本地的读并发隔离舱，
许可数是固定的，拿不到最多短暂等一下就直接拒绝，绝不排队，免得降级那一瞬间把连接池打满；然后异步触发一次预热，
预热在单实例内用一个原子布尔做单飞，跨实例的单飞由重建那把锁负责；最后直接按点赞数降序、id 降序查库分页，
而且不查总数。命中的时候我还要按 id 把这一页的笔记捞出来按榜单顺序重排，
只要有一个 id 查不到——比如榜上有条笔记已经被删了——我就把整页作废、退回数据库查，
宁可多查一次也不返回一个带窟窿的页。最后装配一页的时候，作者信息一次批量查，
「这一页里我赞过哪些」也是一次批量查，不做逐条查询。

## 五、为什么这么设计 / 会被怎么追问

**Q：为什么不直接把点赞数就地加一？**
因为那会把同一条热点笔记的所有点赞串行在一把行锁上，并且和「谁赞过」的写入绑在同一个事务里，
事务持锁时间被拉长。拆成 Outbox 之后，在线写入只碰两张各自独立的行，计数的更新被后台按笔记合并：
一批 500 条事件如果全打在同一条热点笔记上，合并后只发出 1 条更新。代价是计数有秒级延迟。

**Q：这个延迟用户会感知吗？**
用户对**自己**的点赞状态没有延迟，因为「我赞过吗」是直接查关系表的。有延迟的是展示的总数，
以及热榜的排序（还要再叠加一层最多 30 秒的刷新间隔）。这是有意识的取舍：点赞数不是钱。

**Q：为什么不用消息队列，而用数据库表做 Outbox？**
因为要的就是「事实与事件同一个事务提交」。发消息没法和数据库事务原子；
而这条链路的消费者只是把增量加到同一个库的一列上，本来就在同一个事务边界内，走 MQ 反而要多解决一次投递可靠性。
另外这张表天然是可查询的证据，积压多少、最老一条多久，两条 SQL 就能采样成指标。

**Q：那和第 09 章的通知 Outbox 有什么区别？**
一句话：**这一章的 Outbox 要的是「恰好生效一次」，第 09 章的通知 Outbox 要的是「至少送达一次、送不到也不要紧」**。
这里的消费者在同一个数据库事务里既改聚合列又打已处理标记，所以重放绝不可能把计数加两遍；
那边的消费者是把消息扇出到 WebSocket 会话，投递本身是尽力而为的，真相留在持久化的发放记录里，用户刷新就能看到。

**Q：worker 崩在中间会怎样？**
只有两种情况。事务提交前崩：行锁释放、整批回滚，事件行还是未处理，下一轮原样重放。
事务提交后崩：这批事件已经带上了处理时间，标记语句的条件又带「处理时间为空」，所以不可能被再算一次。
没有第三种状态，因为计数和标记是同一个提交。

**Q：那把 Redis 锁如果失效或者根本拿不到呢？**
无所谓。锁只是削减重复工作：多个实例同时跑，最坏的后果是它们都去抢数据库那批行的排他锁，
先到的处理、后到的要么阻塞、要么取到下一段。正确性完全由 `FOR UPDATE` 和单事务提交保证。
所以拿锁时 Redis 抛异常我是继续执行的，只记一个指标。

**Q：热榜为什么整份重建，而不是点赞的时候实时改 ZSET 的分数？**
实时改分数意味着 Redis 变成了另一份需要被维护正确的状态：漏一次加分就永久偏，重建的时候还要对账。
整份重建让 Redis 彻底退化成「可以随时删掉」的派生数据——任何时刻把它清空，30 秒后自动恢复，
期间读走降级路径。代价是排名最多滞后一个刷新周期，以及每 30 秒一次前 K 的扫库。

**Q：整份发布怎么保证读的人看不到半份榜？**
构建写的是一个按代号命名的临时 key，发布用一段 Lua 先比代号、再 `RENAME` 覆盖在线 key。
改名是单条命令，整份切换是原子的。代号比对负责的是另一个问题：**防止一个慢构建把它扫库时的旧数据盖到新数据上**。
新笔记进榜的那段脚本会主动把代号加一，就是为了让那个慢构建的发布失败。

**Q：读的时候前后两次读代号，真能保证一致吗？**
它不是一个真正的快照读，是一个**乐观的围栏**：代号和成员数在取完这一页之后再确认一次，
中间发生过切换就作废。因为代号单调递增，不会 ABA。但我不依赖它保证正确，
任何可疑迹象的结果都只是未命中，而未命中一律降级回数据库——**这份读模型的每一个失败分支都指向同一个兜底**。

**Q：降级会不会把数据库打垮？**
降级路径本身是有索引的（点赞数降序、id 降序的联合索引），分页也不查总数。
另外整个数据库读被放在一个本地并发隔离舱里：固定 4 个许可、最多等 20 毫秒、等不到就直接拒绝，
所以榜挂掉的时候是「一部分请求被快速拒绝」，而不是所有请求一起排队拖死连接池。
同时未命中会异步触发一次预热，让榜尽快恢复。

**Q：为什么点赞状态不缓存？**
现在「我赞过吗」和「这一页我赞过哪些」都是直接查关系表，靠的是（用户 id，笔记 id）那个索引，
而且列表页是一次批量查、不是逐条查。缓存它意味着又多一份要失效的派生状态，
而这条链路的 QPS 特征还不值得付这个代价——这是明确选择「先不做」的部分，不是遗漏。

## 六、已知边界

- **投影延迟没有上界保证。** 正常是亚秒级（200 毫秒间隔、单批 500 条），但如果写入速率长期超过单批吞吐，
  积压会持续增长。目前只有「未处理条数」和「最老未处理事件年龄」两个仪表，**没有基于积压的自动扩容或告警动作**。
- **一条坏事件会阻塞队首。** 如果某条笔记的计数因为外部改动而与事件不一致，
  导致守卫条件让更新影响 0 行，整批会抛异常回滚并且**无限重试同一批**——没有死信、没有跳过、没有重试次数上限。
  这是有意选的「宁可卡住也不丢改动」，但要知道它会卡住。
- **投影吞吐受限于单实例单线程。** worker 是一个定时任务加一把全局锁，同一时刻整个集群只有一批在跑，
  没有按笔记 id 分片并行。
- **热榜每轮都是全量扫库**，不管这 30 秒里有没有笔记的点赞数变过；K 越大这次扫描越贵。
- **新笔记以 0 分进榜的平手规则值得注意**：同为 0 分时按成员（即补零后的 id）升序排在更前的会先被裁掉，
  也就是 id 更大的新笔记会压过 id 更小的 0 分笔记。这与数据库侧「id 降序」的平手规则一致，但它确实意味着
  「0 分的老笔记会被 0 分的新笔记挤出去」。
- **删除的笔记不会被即时移出榜单**，要等下一次重建；期间读到它会让**整页**降级回数据库，
  而不是只跳过那一条——一条脏成员会放大成整页的降级。
- **点赞数的取消路径没有补偿对账。** 计数列与关系表行数是否严格相等，目前只由「事件与状态改变严格配对」这一条断言保证，
  **没有一个周期性的对账器去重新数一遍**。如果历史上出现过偏差，只能人工重算。
- **热榜只有全局榜。** 「本店笔记」那条路径虽然有对应的联合索引，但走的是纯数据库查询，没有派生读模型。
- **这条链路没有跑过压测。** 本仓库的压测报告里没有点赞与热榜的数据，
  所以关于「省掉多少热点行锁」只能讲机制，不能报数字。
- **早期的灰度双路径已被删除。** 旧的「读/写开关切新旧实现」的分支、旧 Redis 点赞集合的导入工具、
  切换完成标记表和未归属点赞偏移列都在后续迁移里清掉了，现在计数列就是点赞关系的异步投影，没有第二种含义。
  剩下的开关（worker 启停、热榜刷新启停）是运维开关，默认都是开的。
