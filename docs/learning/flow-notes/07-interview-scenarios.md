# 项目高频场景问答

配合 [项目介绍与重点流程](00-core-flows-summary.md) 复习。回答先说业务上要守住什么，再说明当前代码怎样做；标为“补充设计”的内容是建议方案，尚未在项目中实现。

涉及自动任务时，要结合配置回答：秒杀定时对账、对账补偿、启动索引回填，以及点赞写入与聚合、热榜读取与刷新、批量发券和发券通知 worker，当前默认都关闭，需要按各自开关启用。以下“会重试、会对账”均以对应执行者可用、所需记录仍在为前提。

## 一、秒杀、宕机与消息

### Q01｜秒杀过程中应用宕机怎么办？

**答：** 我先判断进程停在哪一步，再查看留下的状态，不能把没有响应直接当作下单失败。下面先讨论应用进程退出、Redis/MySQL/Broker 中的数据仍保留的情况：

| 中断位置 | 留下什么 | 当前怎样继续 |
| --- | --- | --- |
| 还没发送半消息 | 没有本次库存预占 | 用户可以重新申请 |
| Broker 已保存半消息，尚未执行 Redis 准入 | 有半消息，没有本次预占 | Broker 后续回查，发现没有匹配预占，回滚半消息 |
| Redis 准入成功，提交半消息的结果没有传回 Broker | 精确预占、`PROCESSING` 和待对账记录 | 回查核对同一订单的归属与状态，满足条件就提交消息 |
| 消费者执行中退出，MySQL 事务尚未提交 | Redis 预占仍在，数据库事务未完成 | 数据库连接断开后未提交事务回滚，MQ 后续重投 |
| MySQL 已提交，还没把 Redis 改为成功 | 正式订单和数据库扣库存已成立 | 重投查到同一订单，跳过重复扣库存，继续标成功；查询和启用后的对账也可修复 |
| Redis 已成功，消费确认或在线提示前退出 | 订单与成功状态都在 | 重投识别同一笔成功并结束；用户通过查询确认结果，在线提示可能缺失 |

应用在等待 Lua 响应时退出，并不会自动撤销 Redis 已经执行的命令；提交结果未知时要回查。Broker 回查可以联系同一生产者组的其他可用实例，但它也要能读到用于裁决的状态。[RocketMQ 4.x 事务消息说明](https://rocketmq.apache.org/docs/4.x/producer/06message5/)介绍了这项机制。Redis 本身丢数据的情况见 Q08。

### Q02｜如何防止超卖和同一个用户重复下单？

**答：** 我分两层处理。Redis Lua 把活动检查、库存判断、用户查重和预占放在一次脚本中，先挡掉大部分无效竞争。正式落单时，MySQL 再用 `stock > 0` 的条件更新扣库存，用订单主键和“用户 + 券”唯一约束防重，插订单与扣库存处于同一个事务，扣库存失败就一起回滚。

用户级分布式锁减少重复消费与对账的交错，数据库约束仍是最终写入边界。唯一键冲突后要检查是不是同一订单；同订单重放、同用户同券的另一订单、订单号归属冲突，处理方式不同。这些机制也不等于所有跨存储故障都已经解决，锁失效后的限制见 Q06。

### Q03｜Lua 是原子的，是不是执行失败会全部回滚？加事务注解能一起回滚 Redis 吗？

**答：** Lua 的原子执行主要保证其他命令不会插进脚本的执行过程，运行中报错不会自动撤销此前已经成功的写入。例如先扣了库存，后面的命令因为 key 类型错误而失败，不能假设库存自动加回。当前准入脚本把正常业务拒绝放在写入之前；遇到脚本异常，生产者按结果不确定处理，后续还要核对现场。[Redis 官方原子执行与回滚说明](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)明确区分了这些语义。

项目中的 Spring 数据库事务只覆盖相应 MySQL 操作，不能把 Redis、MQ 和 MySQL 合成一个共同事务。跨存储仍然要靠明确的状态、幂等重试和有条件的补偿。若继续完善脚本，还应在写入前补充必要的参数和 key 类型检查，降低部分写入后才出错的概率。

### Q04｜MySQL 已下单，Redis 还是处理中，或者同一条 MQ 消息又来了怎么办？

**答：** 已提交的订单不能因为 Redis 回写失败就退库存。当前消费者会抛异常，让 MQ 重投；重投插订单时遇到重复键，再核对订单号、用户和券，完全一致就直接复用已有订单，跳过数据库扣库存，继续把 Redis 改为 `SUCCESS`。

用户查询遇到 `PROCESSING` 时，也会查 MySQL，查到同一笔订单就返回成功并尽力修复 Redis；定时对账启用后还能接手。如果数据库提交时连接断开，应用没拿到明确结果，同样先按订单身份查询，不能直接认定事务失败。这里保证的是重复处理不重复产生业务效果，消息本身仍可能多次投递。

### Q05｜订单一直 PROCESSING，可以设置过期时间，到点自动退库存吗？

**答：** 当前不会让处理中状态靠 TTL 自动消失，因为预占还在，状态先丢失会失去后续判断依据。准入时把订单加入待对账 ZSET，对账任务启用后取到期订单，与消费者共用用户锁，再核对精确预占并查询写库。

查到同一订单就修复成功；数据库查询异常就保留现场；只有确认没有订单、超过最终处理期限、预占仍属于本次订单，并且对账补偿开关开启，才释放预占并标失败。当前默认最终期限是 15 分钟，对账和补偿开关分别控制。消费者遇到明确数据库库存不足等错误时的即时补偿，是另一条路径，不需要等待这项定时补偿。

### Q06｜用了分布式锁，宕机或长时间 GC 后就一定不会并发出错吗？

**项目现状：** Redisson 会为未显式指定租期的锁提供续期机制，但长暂停、网络故障或进程退出仍可能使续期无法持续。当前存在一种竞争：消费者验证预占后暂停，用户锁失效；对账拿到锁，查不到尚未提交的订单并补偿；旧消费者恢复后，仍可能把订单提交到 MySQL。唯一键和 `stock > 0` 可以约束重复与负库存，却不能阻止这次迟到提交。

**补充设计：** 如果要求“取消成功后旧消费者绝不能再落单”，我会先为申请建立持久的数据库状态，让落单与取消竞争同一条记录。落单必须在同一事务内把 `PENDING` 改为 `SUCCESS`、写订单并扣库存；取消只能把 `PENDING` 改为 `CANCELLED`，提交后再通过持久待办释放 Redis 预占。两方通过行锁或条件更新裁决，失败的一方停止后续动作，Redis 再反映数据库结果。这需要调整当前流程，也会增加数据库写入。

这个补充方案依据数据库事务和行锁进行裁决；[MySQL 锁定读说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html)可用于理解该过程。[Redisson 锁文档](https://redisson.pro/docs/data-and-services/locks-and-synchronizers/)也说明了续期及通过 fencing token 拒绝旧持有者写入的思路；项目尚未实现这类最终写入裁决。

### Q07｜用了事务消息，能保证消息不丢、订单一定生成吗？

**答：** 事务消息处理的是本地准入结果与消息能否提交的问题。`COMMIT` 让消息可以被消费，MySQL 正式订单仍由消费者完成。当前消费者遇到暂时异常会重试，超过 MQ 重试范围后可能进入死信队列，项目没有自动处理秒杀死信并完成业务收尾的能力。

**补充设计：** 我会分别检查生产者确认、Broker 的刷盘和复制策略、消费失败重试、消息保留与死信处置；再监控未决订单的数量和最老年龄。修复死信前先核对订单与预占，之后沿同一套幂等流程重放，不能手工补一次库存后又直接重放消息。Broker 故障恢复和复制能力还需要部署配置与演练验证，不能只凭用了事务消息就承诺零丢失。

### Q08｜Redis 宕机，或者 Redis 的数据全部丢了怎么办？

**项目现状：** 暂时不可用时，登录认证和秒杀准入依赖 Redis，不能跳过检查继续放行。店铺详情的缓存层可以在受控范围内回源 MySQL，但带 token 的请求若先在身份恢复阶段失败，仍到不了详情业务。订单查询的 MySQL 回退也以请求已经通过身份校验为前提。

数据全部丢失后，正式订单与数据库库存还在；会话丢失需要重新登录，详情缓存和热榜可以重建。但在途秒杀的精确预占、处理中状态与隔离记录不能只靠订单表无损还原。当前启动初始化主要补库存和活动元数据，不能当作在途订单的完整恢复。

**补充设计：** 先暂停新准入，核对数据库订单、库存、Broker 在途消息和可恢复记录，再决定如何处理旧申请。平时根据可接受的数据损失窗口配置持久化、备份与复制；若要求完整重建在途申请，还需要持久申请记录。持久化与复制都不能直接等同业务零丢失，参见 [Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)与[复制说明](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)。

### Q09｜用户请求超时，又点了一次，会重复下单吗？如果第一次订单号没收到呢？

**项目现状：** 超时只能说明用户没拿到结果。第一次可能已预占甚至已经落单，重复请求会受到 Redis 查重和数据库唯一约束限制。当前在生产者调用报错后，会尝试检查本次订单状态并返回订单号；但如果整个 HTTP 响应丢了，用户重新点击，重复拒绝并不会自动把上次订单号返回给他。

**补充设计：** 增加客户端请求标识，服务端持久保存它与用户、券、订单号的映射，重试相同请求时返回原结果，同时校验请求参数未变化；另提供按当前用户查未决申请或历史订单的入口。这样防重复之外，用户还能找回第一次操作的结果。前端防连点只能改善体验，服务端仍要防重。

## 二、数据库与 Redis 一致性、缓存故障

### Q10｜面试官笼统问“数据库和 Redis 不一致怎么办”，怎么回答？

**答：** 我先确认是哪一种数据、哪一边保存什么事实，再决定修复方向：

| 数据 | 判断依据 | 处理方式 |
| --- | --- | --- |
| 店铺详情缓存 | MySQL 店铺记录 | 删除或更新缓存，失败可重试，允许约定的短暂陈旧 |
| 秒杀订单状态 | 正式订单看 MySQL，未决申请还要核对 Redis 预占 | 已落库就修复成功，未知结果保留，满足条件才补偿 |
| 秒杀两份库存 | 数据库已扣库存与尚未落库的有效预占 | 在途阶段两份数值可以不同，要逐笔核对，不能直接用数据库剩余量覆盖 Redis |
| 点赞与热榜 | 用户关系、待处理增量、数据库聚合，以及热榜构建时间 | 先判断是否只是异步滞后，必要时修复聚合或重建榜单 |
| 登录会话 | Redis 表示 token 是否有效，后台账号和权限还取决于 MySQL | 会话丢失重新登录，账号失效拒绝访问，不能把认证故障当匿名放行 |

一致性要求也要按业务区分：店铺展示可以接受短暂旧值，库存扣减、重复发券和权限判断需要在各自的权威存储中守住约束。项目没有一套定时任务能自动修复所有类型的不一致。

### Q11｜先更新数据库再删除缓存，删除失败或旧值又被写回来怎么办？

**项目现状：** 店铺更新在 MySQL 提交后删除详情缓存，失败只记录日志，靠缓存 TTL 限制陈旧时间。并发时还有旧值回填：读请求查到旧店铺但尚未写缓存，写请求提交新店铺并删缓存，较慢的读请求随后又把旧店铺写回。当前没有持久删除重试、延迟二次删除或版本校验。

**补充设计：** 删除失败可以用与数据库更新同事务写入的 Outbox 记录失效任务，后台反复删除直到成功；也可基于数据库变更日志触发失效。慢读回填需要另外考虑，延迟再删一次只能覆盖部分时间窗口；更严格时要给数据加版本，并保留可校验的最新版本标记，由原子写入拒绝旧版本回填，不能删掉缓存后也把比较依据一起丢掉。要求实时准确的关键读取直接走数据库写库。Outbox 和重删改善恢复能力，并不自动得到缓存强一致。

### Q12｜缓存穿透、击穿、雪崩分别怎么处理？项目做了哪些？

**答：** 穿透是频繁查询不存在的数据，当前用短期空值缓存减少同一不存在 ID 的回源；数据库异常不能当空值缓存。击穿是热点 key 失效后大量请求一起查库，当前 SingleFlight 合并同一实例内的同 key 加载。雪崩是大量缓存同时失效或 Redis 不可用，当前本机数据库读取并发许可会限制回源，超出就拒绝，避免无限排队。

**补充设计：** 大量随机不存在 ID 可以考虑布隆过滤器，但要维护新增数据并接受可能误判为存在；大量 key 同时过期可以增加 TTL 抖动并预热热点。跨实例热点回源可进一步协调重建，或者对允许旧数据的展示使用逻辑过期。当前主路径采用真实 TTL；本机合并与并发许可也不等于整个集群的数据库总并发上限。

## 三、异地登录、会话与商户权限

### Q13｜同一个用户在两个地方同时登录怎么办？怎样做到新登录踢掉旧登录？

**项目现状：** 每次成功登录都会生成独立 token，当前没有“用户只能对应一枚有效 token”的约束，也没有设备列表或异地识别。因此先后完成两次有效登录，可以同时保留两个会话；退出只删除本次 token。这里和“并发使用同一个验证码”不同，同一份验证码只能被一个请求成功消费。

**补充设计：** 我会先确定业务规则。消费者可以允许手机和电脑同时在线，提供设备列表及远程退出；如果后台要求单端登录，就为用户维护当前有效的 sessionId。登录时通过 Lua 原子切换这份记录并写入新会话，每次鉴权都核对 token 是否对应当前 sessionId，旧会话即使尚未物理清理也失效。两个登录并发时，以服务端最后成功完成原子切换的会话为准；登出也要比较是否仍为当前会话再删除，避免旧端退出误删新端会话。若只限制同类设备，就把约束范围改成“用户 + 设备类型”。

IP 变化可以作为风险信号，但移动网络、代理和 VPN 都会影响判断，不能只凭换 IP 就断言盗号。新设备或异常登录可要求二次验证并通知用户。允许并发登录以及让用户查看、终止会话，属于应用的产品决策，参见 [OWASP 会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)；上面的原子切换是针对本项目的补充实现方案。

### Q14｜token 泄露、修改密码或管理员撤权后，怎么让旧会话失效？

**项目现状：** token 是持有即可使用的凭据，随机且难猜不代表泄露后仍安全。消费者当前主要靠删除这枚 token 或 TTL 失效，没有统一的会话版本校验。后台已经有 `authVersion`：改密、停用员工时更新数据库版本，后续请求将 Redis 签发版本与数据库版本比较，不一致就拒绝；权限也会重新查库，所以有效账号撤掉某项权限后，访问对应接口会被拒绝。后台 WebSocket 在下一次发送前复核身份，已经进入业务的 HTTP 请求不会被自动撤回。

**补充设计：** 给消费者增加账号级会话版本和设备会话索引，支持踢某台设备或撤销全部旧会话；同时设置绝对有效期，避免活跃 token 一直续期。传输使用 HTTPS，日志不记录完整 token，高风险操作重新验证身份。这些措施分别减少泄露机会、缩短被利用时间和提供撤销入口。[OWASP 认证建议](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)说明了加密传输与风险事件后重新认证的要求。

### Q15｜两个请求同时提交同一个验证码，或者有人不断猜验证码怎么办？

**答：** 当前消费验证码的 Lua 把比较、失败计数和成功后的删除放在一起。两个正确请求并发时，先执行的成功并删除验证码，后一个只能验证失败。输入错误会累计次数，达到 5 次删除验证码，并让失败计数保留到这份验证码原来的有效期结束；发送冷却限制同一手机号再次申请的频率。

**补充设计：** 还可以增加手机号、IP、设备等维度的发送和校验预算，异常时要求额外验证，并限制真实短信发送成本。后台当前是“用户名 + IP”的失败预算和单 IP 总尝试预算，针对大量不同 IP 试同一账号的情况，还应补充账号维度的策略，同时避免被恶意请求轻易锁死正常用户。[OWASP 登录节流说明](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#login-throttling)也强调账号维度与锁定策略的取舍。

### Q16｜商户有修改权限，为什么还要检查 merchantId？如何避免跨商户访问？

**答：** 权限回答的是“能不能修改店铺”，归属回答的是“能修改谁的店铺”。当前先从后台会话恢复可信的账号和商户范围，再检查功能权限；商户更新店铺时，查询和最终 UPDATE 都带当前身份的商户 ID。即使把路径中的店铺 ID 换成别人的，范围内也查不到，不能靠前端传来的 merchantId 获得授权。

ThreadLocal 只是请求内传递身份的容器，本身不会形成权限保障，所以仍需要服务层和 SQL 条件检查，请求结束还要清理。若把工作交给异步任务，应显式传递必要身份与业务范围，并按业务需要重新授权，不能假定线程池自动带着当前登录用户。

## 四、发券、通知、点赞与热榜

### Q17｜用户领券和管理员发券同时发生，怎样避免重复发放和额度超发？

**答：** 当前这些入口共用单人发券逻辑，普通发放统一使用 `ONCE` 幂等标识，按“活动 + 用户 + 幂等标识”查重。新发时锁定活动、复核规则和资格，并通过条件更新占用额度；额度变化、权益记录和通知待办在同一个 MySQL 事务内提交。

并发请求仍可能同时查不到，因此数据库唯一键不能省。发生唯一键竞争时，失败事务先回滚，包括刚才增加的已发数量，然后到事务外查回已经存在的权益。这里一次领取是否成功以数据库权益为准，Redis 在线通知不参加这笔事务。批任务的 requestId 是创建任务的另一层防重，不能拿它替代逐用户发券的唯一约束。

### Q18｜批量发券到一半服务重启，怎样继续？暂停时已经发出去的券会撤销吗？

**答：** 总体任务、目标快照和逐用户明细都保存在数据库，worker 每次锁定有限一批待办处理。每位用户的发券使用独立事务，发成功后再在外层批事务记录进度。如果权益已经提交、进度还没提交时进程退出，下次会重新取到这位用户，通过幂等查询拿回原权益，再把进度补齐。

已经标为技术失败的明细需要通过失败重试入口重置，业务条件不满足的跳过项不会一起重试。暂停阻止后续批次，当前持锁批次可能先完成，已经提交的权益不会撤销。恢复后继续处理剩余待办；目标快照也不保证用户永远有资格，需要新发时仍会核对当前资格和规则版本。

### Q19｜发券已经成功，但用户没收到 WebSocket 通知，怎么保证消息送达？

**项目现状：** 发券事务已经留下权益和通知 Outbox。通知 worker 启用后，Redis 发布调用失败会延后重试；调用成功且数据库标记成功才记为 `PUBLISHED`。用户离线或订阅连接中断时，Pub/Sub 不会替他保存离线通知，不能据此说用户已经收到。反过来，发布后完成标记失败又可能触发重复发布。[Redis Pub/Sub 文档](https://redis.io/docs/latest/develop/pubsub/)说明了单次发布的至多一次投递语义。

**补充设计：** 如果业务需要离线可查和接收确认，可以持久保存用户通知，以 eventId 去重，连接恢复后按游标补拉，并让客户端 ACK 表示已接收；未确认的在约定窗口内重试。用户是否实际阅读还需要单独的已读操作。订单或券权益始终能查询，通知重复也不能再次触发发券。当前没有这套离线通知和 ACK 闭环。

### Q20｜点赞成功但数量没变，是不是数据错了？worker 中途宕机又怎么办？

**答：** 当前点赞关系和 `+1/-1` 待办先同事务提交，聚合计数由后台任务稍后更新，短暂不同可能只是积压。worker 把一批增量合并后，更新计数和标记待办也在同一事务中，提交前退出就一起回滚，提交后则不会再选到这批已处理事件。

排查时先看待处理数量和最老年龄。对没有历史迁移偏差的数据，在同一数据库视图里应满足“聚合计数 + 待处理增量之和 = 当前关系数”；混有历史基数时要先核对迁移口径，不能直接覆盖成关系表行数。当前非法事件可能让一批反复回滚，尚无完整隔离机制；补充设计是记录异常事件、告警并提供受控修复。目标状态接口能使同一目标的重复请求幂等；如果还要求多端点赞与取消按操作版本排序，则需要额外的版本控制。

### Q21｜两次热榜构建并发，旧任务反而最后完成，会覆盖新榜吗？Redis 榜单坏了怎么办？

**答：** 当前每次构建在查数据库前取得递增版本号，把完整候选写入这一代的临时 ZSET。发布 Lua 会比较版本并校验数量，只有仍有效的版本才能替换正式榜并写元数据；旧构建器晚到会失去发布资格。这样正式榜不会在构建过程中逐条暴露半成品。

读取还会检查就绪标记、时效、数量和读取前后版本。发现不可信、回库详情不完整或请求超出缓存范围，就按数据库聚合点赞数和 ID 排序返回，并在允许时触发异步重建。Redis 故障可以走回退，但数据库聚合本身若落后，重建榜单也不会自动补上未处理的点赞增量，要先确认聚合任务状态。

## 五、数据库读取、容量与验证

### Q22｜MySQL 主从延迟导致查不到刚写的订单，可以认定下单失败吗？

**项目现状：** 当前应用配置是单数据源，没有已实现的读写分离路由；秒杀对账方法明确要求读取写库。不能因为方法加了 `readOnly=true` 就认为它天然读取从库，也不能把未来复制延迟当成现在已被解决的问题。

**补充设计：** 若引入读写分离，订单补偿、权益防重和关键权限检查应选择满足一致性要求的读取，特别是决定能否退库存时要查写库。一般展示可以容忍复制延迟，用户刚写后的查询可以暂时路由到写库。还要注意：写库也看不到其他事务尚未提交的订单，因此“查主库”仍不能替代 Q06 中落单与取消竞争同一状态记录的设计。

### Q23｜访问量突然扩大，或者 MQ、Outbox 积压越来越多，怎么处理？

**答：** 我先区分请求入口、数据库和异步处理哪一段变慢。项目已有入口限流、数据库回源许可和相关指标，可以检查拒绝比例、数据库执行与锁等待、消费速度，以及待办数量和最老年龄。HTTP 返回很快但订单长期处理中，说明只看接口耗时不够。

**补充设计：** 先把接入速率控制在下游可承受范围内，排查慢 SQL、锁竞争和依赖失败，再结合 MQ 队列数、消费者并行度与数据库余量增加处理能力。批任务逐人独立事务仍可能占着外层任务锁和连接，盲目加线程会加剧连接池紧张；单活动行锁也可能成为热点。确实达到瓶颈后，再讨论额度分段、缩小批事务或拆分任务，同时重新验证总额度和幂等约束。重试应避免无间隔集中轰击故障依赖，永久坏数据则应告警并隔离处理。

### Q24｜如何证明“不重复、不超卖、可恢复”？面试时性能数字怎么讲？

**答：** 我会把结论拆成可检查的业务结果，再做针对性的故障验证：

| 验证场景 | 要检查的结果 |
| --- | --- |
| 同一用户并发秒杀、重复投递同一消息 | 同用户同券没有多笔订单，同一订单不重复扣数据库库存 |
| MySQL 提交后阻断 Redis 成功回写 | 正式订单保留，恢复后能修复成功，不错误退库存 |
| 数据库查询异常时触发对账 | 保留未决现场，不把异常当成订单不存在 |
| 消费者暂停直到锁失效，再让对账与旧消费者交错 | 暴露并验证 Q06 的限制，补充设计落地后再验证能否拒绝迟到提交 |
| 发券成功后、明细进度提交前中断批任务 | 重跑拿回原权益，额度不多占，进度能继续 |
| 点赞聚合计数更新后、待办标记前失败 | 整批回滚，下轮重试不多算 |

结果要同时看订单、库存、权益、预占、终态、待办与死信，失败项应有明确去向；不能只看 HTTP 200。性能数字需要说明硬件、依赖、开关、数据量、并发方式、持续时间以及测的是接口响应还是最终落单。没有实际运行记录就只讲实现和验证方案，不能把“存在测试类”说成“这次验证通过”，也不把本地结果扩展成生产保证。
