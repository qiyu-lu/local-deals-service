# 项目重点流程简版

按“请求带来什么 → 先判断什么 → 数据怎样变化 → 谁继续处理 → 最后得到什么”来复习。重点放在秒杀、营销发券、点赞热榜和商户隔离，登录与店铺缓存保留主要过程。每一条尽量讲完一个业务动作，源码细节可以回看对应的原笔记。

## 项目介绍：自我介绍中的项目部分

我做的是一个本地生活平台的后端项目。消费者可以查看店铺、发布探店内容、点赞、领取优惠券和参与秒杀，平台和商户通过后台管理店铺与营销活动。主要使用 Spring Boot、MySQL、Redis 和 RocketMQ，另外用 Elasticsearch 支持搜索、WebSocket 提供在线结果提示。

我重点处理的是并发请求和异步处理过程中，重复操作、服务中断以及多个存储之间状态不一致的问题。比如秒杀，我先通过限流控制入口压力，再由 RocketMQ 事务消息的本地回调执行 Redis Lua，原子检查资格并预占库存，消息提交后交给消费者落单。数据库用唯一约束和条件扣库存防止重复订单、库存扣成负数，同时保留订单状态、消息重试和可开启的定时对账，让处理中断后仍然有依据查询和恢复。

另外，我把普通领券、后台发券和批量发券统一到一套规则中，通过幂等标识、活动行锁和独立事务控制重复发放与额度；批量任务保存每个用户的处理进度，重启后可以继续。点赞则保存用户关系，并把计数更新的待办一起写入数据库，后台再聚合计数和构建热榜。后台权限除了判断账号能做什么操作，还会把商户范围带到查询和更新条件中，限制跨商户访问。

这个项目让我重点梳理了几类问题：一笔业务在哪一步才算成功，失败后应该重试、补偿还是保留现场，以及哪些数据可以从数据库重建。面试中我可以围绕秒杀故障恢复、发券幂等和商户数据隔离展开具体流程。

| 重点处理的问题 | 采用的方法 | 可以展开讲的亮点 |
| --- | --- | --- |
| 秒杀重复请求、库存竞争、异步中断 | Redis Lua 准入、事务消息、数据库唯一约束与条件扣库存、状态查询与对账 | 区分受理和正式落单，按可确认的结果选择重试、补偿或隔离 |
| 多入口重复发券、批量任务中途失败 | 统一发券规则、活动行锁、幂等唯一键、目标快照、逐人独立事务 | 券已发出但进度未保存时，重跑通过查重继续推进 |
| 点赞重试反转、计数与榜单更新滞后 | 目标状态接口、关系与 Outbox 同事务、批量聚合、带版本的完整榜单发布 | 业务关系可以追溯，聚合可重试，Redis 榜单可以重建 |
| 后台账号越权、访问其他商户资源 | 独立后台身份、角色权限、商户范围、带归属条件的查询和更新 | 功能权限与资源归属分别检查，旧会话重新加载当前权限 |

故障场景和补充设计见 [24 个高频场景问答](07-interview-scenarios.md)。介绍中的机制指当前代码能力，默认开关在下面各流程中说明；性能数字要结合实际运行记录单独回答。

## 一、消费者申请验证码并登录

- 首先用户带着手机号申请验证码。验证码接口允许未登录访问，服务检查手机号格式后生成六位数字验证码，再根据手机号拼出三个 Redis key：发送冷却、验证码、登录失败次数。接着通过一个 Lua 脚本检查和写入：冷却 key 存在就拒绝本次发送，原验证码和失败次数不变；不存在就写入新验证码，设置 120 秒有效期，再设置 60 秒发送冷却，并删除旧失败次数。这里冷却控制的是多久可以再次申请，和验证码是否过期是两个判断。

- 然后用户另发登录请求，提交手机号和验证码。检查手机号与六位数字验证码的格式后，用另一个 Lua 脚本读取失败次数：达到 5 次就直接拒绝；未达到才读取验证码，不存在就返回验证失败。验证码相同就同时删除验证码和失败次数，使它只能成功消费一次；不相同时，如果验证码已无有效 TTL，就清理相关记录，否则失败次数加一，过期时间跟随验证码的剩余有效期。累计到第 5 次时删除验证码，但保留失败计数到原有效期结束。

- 验证码消费成功后，服务按手机号查询 MySQL 用户表，存在就使用原用户，不存在就创建，手机号唯一索引负责防止重复建号。然后生成随机 token，以 token 为 key 的一部分，把用户 ID、昵称和头像写入 Redis Hash，再设置 30 分钟有效期，成功后返回 token。后续请求带 token，拦截器据此恢复用户身份并续期，业务从恢复出的身份取得用户 ID。

这里记住两个边界：当前没有接入真实短信服务，申请成功只表示验证码写入了 Redis；消费验证码、查建用户和写会话没有共同事务，后两步失败不会恢复已经消费的验证码。

对应原笔记：[登录与访问](01-login-and-access.md)。

## 二、平台账号和商户账号登录，以及商户数据范围

- 后台账号带用户名和密码登录，登录入口允许未登录访问。服务先取得客户端 IP，只有请求来自配置的可信代理时才采用转发头，然后规范化用户名。接着准备两类 Redis 计数：用户名加 IP 的失败次数、单 IP 的总尝试次数。两类 key 都对相应身份信息做 MD5 摘要，避免直接把原值放进 key。用户名加 IP 的失败次数达到默认 5 次就拒绝，否则通过 Lua 增加单 IP 尝试次数，超过默认 30 次也拒绝。计数首次自增为 1 时才设置默认 15 分钟过期时间。

- 通过限流后，按用户名查后台账号，用 BCrypt 比较密码。账号不存在时也会使用预先生成的 dummy hash 做比较，减少通过响应耗时枚举账号的机会。密码正确后继续检查账号是否启用、商户是否启用、平台或商户范围与角色组合是否匹配，并加载当前权限。密码错误或身份组合无效，就用 Lua 增加用户名加 IP 的失败次数，返回统一的登录失败或超限响应。

- 全部通过后，删除用户名加 IP 的失败计数，生成随机 token，把“账号 ID + 凭据版本”写入 Redis，并在同一次 SET 中设置默认 30 分钟有效期；随后更新最近登录时间，返回 token 和账号身份。单 IP 总尝试次数不会因为登录成功而清除。后续请求带后台 token，服务根据 Redis 会话回 MySQL 重新加载账号、商户、角色与权限，并检查凭据版本，再交给业务使用。

- 进入后台业务时，还要区分功能权限和数据范围。例如商户 A 修改店铺，先检查账号是否有店铺修改权限，再用“店铺 ID + 当前身份中的商户 A ID”查询并锁定店铺，最终 UPDATE 也带相同的商户条件；前端不能通过换一个商户 ID 来扩大范围。平台账号通过对应权限检查后，可以按店铺 ID 操作目标店铺。具体接口权限不足发生在访问接口时，不能笼统说成“没有某项权限就登录失败”。

对应原笔记：[登录、后台权限与商户范围](01-login-and-access.md)。

## 三、秒杀从受理到正式落单，失败后怎样继续

- 用户点击秒杀，带来券 ID，服务从登录身份取得用户 ID，并取得客户端 IP。先用一个 Lua 脚本检查活动、用户、IP 三个固定时间窗口的请求量，任何一个超限都拒绝；都通过才一起增加计数。随后生成订单号，用它关联后面的 Redis 状态、MQ 消息和 MySQL 订单。

- 接着发送 RocketMQ 事务消息。Broker 先保存消费者暂时看不到的半消息，确认后才由生产者执行本地回调。回调通过 Lua 检查活动状态、时间、Redis 库存和用户是否重复抢券；通过后在一次脚本中扣减 Redis 库存、记录已购用户，保存“这个用户预占的是哪个订单号”，写入 `PROCESSING` 状态，并把订单号放入待对账 ZSET，分数表示最早检查时间。

- Lua 准入成功就提交半消息，让消费者可以处理，并向用户返回订单号；明确的业务拒绝就回滚半消息；执行结果不确定则交给 Broker 后续回查。**返回订单号只说明请求已经受理，正式订单还要等消费者写入 MySQL。**

- MQ 消费者收到消息后，先取得用户级分布式锁，再核对消息中的订单、用户、券与 Redis 预占和状态是否一致。已经是同一笔终态就结束，状态不完整或归属不安全就停止落库并等待重试。可以继续时，在一个 MySQL 事务里先插入订单，再用 `stock > 0` 的条件更新扣库存，任一步失败就回滚。订单主键和“用户 + 券”唯一约束负责防重；遇到重复键，还要查清是否确实是同一订单，不能一律当成功。

- MySQL 提交后，再把对应 Redis 状态改成 `SUCCESS`，移出待对账集合，并尽力发送在线提示。如果数据库已经成功、Redis 标成功却失败，就让 MQ 重试；下次根据数据库已有的同一订单跳过重复扣库存，继续修复状态。数据库超时等暂时异常同样交给 MQ 重试。如果数据库明确库存不足或出现预占冲突，消费者先暂停活动，再通过 Lua 核对并释放本次精确预占、恢复 Redis 库存、标记 `FAILED`；同一个订单号却属于其他用户或券时，则暂停活动并隔离现场，不自动退库存。

- 用户拿订单号另发请求查询结果，只能查询自己的订单。Redis 已经是终态就返回；仍是 `PROCESSING` 时再查 MySQL，查到同一笔正式订单就返回成功并尝试修复 Redis。Redis 状态缺失或不可用时，也可以通过 MySQL 查询已落库订单。查询接口负责反馈和必要的状态修复，不会重新下单；在线提示没有收到时，用户仍可查询结果。

- **半消息回查和订单对账分别处理不同问题。** Broker 回查根据 Redis 的精确预占、归属、隔离记录和状态，判断半消息应提交、回滚还是继续等待。定时对账则从 ZSET 取到期订单，与消费者共用用户锁，核对预占后查询 MySQL：同一订单已经存在就修复成功；确定没有订单且超过最终期限，才在补偿开关开启时释放预占；数据库查询异常就保留现场再查。对账发现同用户同券另有订单时会暂停活动，并受补偿开关控制；订单号归属冲突则暂停并隔离。

定时对账和对账补偿默认都关闭，需要分别开启；消费者处理明确失败时的即时补偿不受这个补偿开关控制。这里重点记住：暂时查不清结果不能直接判失败，更不能直接退库存。

对应原笔记：[秒杀与订单恢复](02-seckill.md)。

## 四、普通活动券领取、批量发放和通知

- 用户领取普通活动券时，带来活动 ID 和页面看到的规则版本，服务从登录身份取得用户 ID，组装发券命令。用户领取、后台单发、批量发放都进入同一套发券逻辑，并使用服务端确定的 `ONCE` 幂等标识，使同一活动、同一用户通过这些入口重复申请时，返回同一份权益。签到奖励也复用发券逻辑，使用带业务日期的幂等标识区分不同日期的奖励，新发时还要检查当天签到。

- 服务先查询已有发券记录，存在就直接返回；不存在才开启这位用户的独立 MySQL 事务，事务内再次查重，再锁定活动行，取得锁后还会复查。随后检查规则版本、发放方式、活动状态与时间、券状态和商户归属；要求标签资格的活动，还要锁定并检查标签及用户成员记录。都满足才通过条件 UPDATE 增加已发数量，要求活动仍有效且剩余额度充足。活动行锁让同一活动的额度竞争有先后顺序，条件更新继续守住规则和额度。

- 占到额度后，写入用户权益记录，也就是 Grant，再写一条通知 Outbox。Outbox 就是保存在数据库中的“后续还有工作要处理”的待办。额度增加、权益、通知待办在同一个事务里提交，任何一步失败一起回滚。数据库还用“活动 + 用户 + 幂等标识”唯一键防重；如果并发请求撞到唯一键，要先让失败事务回滚，再到事务外查回已经存在的权益，避免重复占用额度。提交后用户就可以查询券包，通知由另一个任务继续处理。

- 批量发放时，管理员提交活动、请求标识和规则版本。服务先按“商户 + 请求标识”防止重复创建，再检查活动及标签等条件，保存总体任务并返回。后台 worker 启用后，先把当时有效的标签成员固化成目标快照，每位用户对应一条待处理明细；之后每次锁定一个可运行任务和有限一批明细，逐人调用前面的统一发券逻辑。快照决定处理谁，已有权益直接按幂等返回；需要新发时，仍要复核当前规则、资格和额度，任务保存的规则版本也必须仍匹配。

- 每位用户的发券事务独立提交，批量明细随后记录“新发成功、已经发过、业务跳过、技术失败”。如果券已经发出，但进程在保存明细进度前退出，下次会再次处理这条待办，通过幂等查重拿回原权益，再补齐进度。已记录的技术失败可由管理员重置后重试，业务跳过不会随之重试；暂停让后续批次停止，恢复后继续处理剩余明细。这样中途失败不用重新给所有人发券。

- 通知 worker 启用后，定时锁定一批到期的通知待办，通过 Redis Pub/Sub 转给在线 WebSocket 连接。发布失败就保留待办，推迟到下次重试；发布调用成功后标记 `PUBLISHED`。发布后如果数据库标记失败，后续可能重复发布，因此这个状态只表示发布调用及标记成功，不表示用户一定收到。通知失败不会撤销已经发放的券，用户以券包查询为准。

批量 worker 和通知 worker 默认都关闭，需要分别启用；普通单人领取本身不依赖它们完成发券。

对应原笔记：[营销发券与批量任务](03-voucher-grant.md)。

## 五、点赞关系怎样变成计数和热榜

- 用户点赞时提交“希望已点赞”，取消时提交“希望未点赞”，分别对应 PUT 和 DELETE。服务从登录身份取得用户 ID，在 MySQL 事务中检查并共享锁住 Blog，再新增或删除用户与 Blog 的点赞关系。已经点赞又收到点赞请求，或者本来没点赞又收到取消请求，都按未变化返回；因此请求重试不会把点赞状态反转。只有关系真的改变，才在同一事务里写一条 `+1` 或 `-1` 的 Outbox 待办，关系与待办一起提交。

- 点赞关系与待办提交后，后台聚合 worker 另行处理。它在 MySQL 事务里锁定有限一批未处理待办，按 Blog 合并增量，例如 `+1、+1、-1` 合成 `+1`，再更新 Blog 的聚合点赞数，并把这批原始待办全部标记为已处理。更新计数与标记同事务提交，中途失败一起回滚，下轮仍能处理这些待办，不会只加了计数却忘记完成标记。

- 热榜重建是另一个任务。它先取得递增版本号，再从 MySQL 按“点赞数降序、ID 降序”取前 K 篇 Blog，写到这一版本的临时 Redis ZSET 中。全部写完后，用 Lua 检查版本是否仍有效、临时榜数量是否完整，再把临时榜一次性替换为正式榜，同时发布版本、数量和时间等信息。旧任务即使更晚完成，也会因为版本落后而失去发布资格，避免覆盖新榜。

- 用户读取热榜时，先检查 Redis 榜单是否就绪、是否过旧、数量是否匹配，以及读取前后版本是否变化。可信时取得有序 Blog ID，再回 MySQL 批量补齐正文、作者和当前用户的点赞状态，并恢复榜单顺序；榜单不可用、详情不完整或页码超出缓存的前 K 范围时，就按同样排序查 MySQL。符合条件时可以顺带触发异步重建，本次请求继续返回数据库结果。

这里要分清三层数据：点赞关系记录谁点过赞，聚合计数记录已处理增量的总数，Redis 热榜保存某次构建出的排序快照。所以点赞成功时，计数和榜单允许稍后才变化。当前点赞写入、聚合 worker、热榜读取、热榜刷新都有独立开关，默认关闭；上述流程在相应开关启用后执行，热榜读取关闭时查询走 MySQL。

对应原笔记：[点赞与热榜](04-like-and-hot-rank.md)。

## 六、店铺详情缓存与修改后的失效

- 用户查询店铺详情，先按店铺 ID 查 Redis。读到能解析且 ID 匹配的店铺就直接返回；读到专门的空值占位就返回店铺不存在。缓存缺失、损坏或读取 Redis 异常时，进入回源流程。这里是先查缓存、未命中再查数据库的旁路缓存方式，空值占位用于减少不存在的店铺 ID 反复穿透到数据库。

- 回源时，同一个应用实例内，相同店铺的并发请求会共享一次加载任务，也就是 SingleFlight；由第一个请求查库，其他请求有时限地等待同一结果。真正查询前还要取得本机数据库读取的并发许可，拿不到就拒绝本次读取。MySQL 查到店铺就尝试缓存详情，明确查不到才缓存空值，并设置短 TTL；数据库异常不会被写成“店铺不存在”。缓存写入失败仍可返回已经查到的数据，前面 Redis 读取已异常时则跳过缓存写入。

- 商户修改店铺时，先按权限和商户范围完成 MySQL 更新，事务提交后再删除详情缓存，让后续读取重新查库。删除失败不会回滚已经提交的修改，详情缓存还有 TTL 作为过期边界。这个流程仍可能短暂读到旧数据；SingleFlight 和读取并发许可都只作用于当前应用实例。
