## 1. 项目总览：这不是功能拼盘，而是围绕一致性边界做的本地生活平台

### 1.1 概括版

这是一个本地生活平台后端，消费者可以登录、浏览和搜索店铺、发布内容、关注点赞、领券和参加秒杀；商户和平台人员则通过独立后台管理店铺、营销活动和发券任务。我没有把它拆成微服务，而是在 Java 8、Spring Boot 2.3.12 的模块化单体里按业务职责拆分。项目真正想解决的不是“接入了多少中间件”，而是不同业务对数据一致性和读取性能的要求不同：MySQL 保存订单、点赞关系和券权益等长期事实；Redis 负责会话、热点保护、过程状态和可重建读模型；RocketMQ 承接秒杀异步落单；Elasticsearch 负责搜索；WebSocket 只做结果提示。我的设计重点是先确定事实源，再为跨组件链路补上幂等、状态、重试、回退和隔离。

### 1.2 完整版

#### 业务场景与要解决的问题

项目同时面对消费者端和后台端。消费者链路强调低延迟和突发流量，后台链路强调权限、商户数据隔离和可恢复的批量任务。难点不在某一个接口，而在于一次操作往往会同时经过 MySQL、Redis、消息队列、搜索索引和在线通知；这些组件不能被一个普通数据库事务一起提交。

如果只按功能堆 Controller 和 Service，很容易出现三个问题：不知道哪个数据才是最终结论；重试一次就产生重复订单或重复权益；某个组件故障后，为了“恢复”反而覆盖了已经成立的事实。

#### 整体方案

我先按数据职责划分系统：

| 数据角色 | 项目中的例子 | 设计原则 |
| --- | --- | --- |
| 长期事实 | 用户、店铺、订单、点赞关系、发券权益、任务与 Outbox | 由 MySQL 事务、唯一约束和条件更新最终仲裁 |
| 协议状态 | 登录会话、秒杀精确预约和 PROCESSING | 用来协调多个步骤，不能随意当普通缓存删除 |
| 派生读模型 | 店铺缓存、GEO、ES 索引、Redis 热榜 | 允许短暂滞后，但必须明确回源、重建或失败边界 |
| 在线提示 | Redis Pub/Sub 和 WebSocket | 只提醒客户端刷新，不能证明送达或业务成功 |

请求入口负责恢复身份和拒绝明显非法流量；业务服务负责规则、事务和状态迁移；MySQL 保存事实；Redis、MQ、ES 和 WebSocket 根据各自角色参与加速、异步或通知。三条最复杂的核心业务独立放在 [09](09-core-business-chain-review.md)，本文重点解释其余模块。

#### 核心实现与技术亮点

第一个亮点是消费者身份与后台身份完全分域，而不是共用一枚 token 后只靠角色判断。第二个亮点是读取链路没有统一套一个“缓存模板”，而是根据详情、位置和全文搜索的语义分别设计故障策略。第三个亮点是后台授权不仅检查功能权限，还继续检查商户范围、资源归属和带商户条件的 SQL。第四个亮点是我把在线通知明确放在 best-effort 层，订单或权益的最终结果仍通过事实接口查询。

项目还使用功能开关控制高风险迁移。点赞新写与 worker、热榜读取与刷新重建、秒杀对账与补偿和回填、批量发券与通知 worker 当前默认都关闭；其中部分开关还有先后或依赖关系，例如秒杀补偿依赖对账主开关，回填不能和在线对账在同次启动中混用。代码存在不等于默认正在运行，更不等于已经证明生产容量。

#### 为什么这样设计

我选择模块化单体，是因为当前项目最需要验证的是业务边界和一致性协议，而不是承担分布式部署本身的额外复杂度。模块化能把身份、订单、内容和营销职责隔开，同时保留同库事务带来的确定性；如果未来确实需要拆服务，现有的事实源、幂等键、Outbox 和状态机也能成为拆分边界。

我也没有笼统地说“Redis 是缓存、MySQL 是数据库”。例如普通详情缓存可以失败后回源，但秒杀预约是跨 MQ 和数据库判断所有权的协议状态，不能在故障时随意丢弃。先说清数据角色，比先列技术栈更能解释设计。

#### 异常、一致性与当前边界

MySQL 本地事务只覆盖同一数据库事务里的 SQL。跨 Redis、MQ、ES 或 WebSocket 时，项目分别使用事务消息、Transactional Outbox、幂等消费、版本发布、回退或 best-effort 通知，但没有把这些组件包装成一个全局强事务。

当前后端是模块化单体，不是微服务；没有实现支付超时取消链路；没有消息必达或用户已读保证；没有从当前源码推出生产吞吐、P99、Redis 高可用或容灾 RPO。仓库里的测试和历史记录只能证明限定环境中的行为，不能直接当生产 SLA。

### 1.3 面试官最可能追问的 5 个问题

1. **为什么没有拆成微服务？**
   - 回答要点：当前重点是业务一致性和安全边界；模块化单体降低分布式事务、部署和排障成本；模块仍按领域职责拆分；未来是否拆分应由独立扩缩容、团队边界和真实容量证据驱动。

2. **MySQL、Redis、MQ、ES 各自是什么角色？**
   - 回答要点：MySQL 保存长期事实；Redis 同时承担会话、流控、协议状态和派生读模型，必须按场景区分；MQ 负责异步交付而不是最终事实；ES 是可重建搜索索引；WebSocket 只是提示。

3. **这个项目最大的技术难点是什么？**
   - 回答要点：不是某个框架用法，而是跨组件不能共同事务时，怎样确定事实、让重复执行收敛，并在证据不足时避免错误补偿。

4. **模块化单体将来怎样演进？**
   - 回答要点：先围绕身份、订单、内容、营销明确数据所有权和接口；保留幂等键、Outbox、状态机；只有出现独立扩缩容或组织边界后再拆，避免为了架构名词提前分布式化。

5. **你怎样证明项目能力已经成立？**
   - 回答要点：区分源码已实现、默认已启用和测试已验证；控制流与约束来自当前源码，运行结论来自对应测试或实验；不把 HTTP 200、进程存活或局部单测扩大成生产可靠性。

### 1.4 详细项目边界（保留原复习层）

#### 系统角色和部署形态

系统有三类主要身份：

- **消费者**：浏览店铺和笔记，关注、点赞、签到、领券、参与秒杀并查询自己的结果；
- **商户后台账号**：只能在自己的商户范围内管理店铺、券、标签、活动和批量任务；
- **平台后台账号**：管理平台资源，并在需要操作具体商户数据时显式确定目标商户。

当前后端是 Java 8、Spring Boot 2.3.12 的模块化单体。业务代码按 Controller、Service、Mapper 等职责拆分，但最终仍作为一个应用进程部署，不应描述成微服务系统。

~~~text
用户端 / 管理端
       ↓
Interceptor：恢复身份、判断入口权限
       ↓
Controller：解析 HTTP 输入和组织响应
       ↓
Service：业务规则、事务、状态迁移
       ↓
Mapper / 外部客户端
       ↓
MySQL / Redis / RocketMQ / Elasticsearch / WebSocket
~~~

MySQL 本地事务只能覆盖同一数据库事务中的 SQL，不能自动让 Redis、MQ、ES 或 WebSocket 一起提交和回滚。跨组件能力必须另外设计幂等、状态、重试、回退或隔离。

#### 请求层各自承担什么

- **Interceptor** 在 Controller 之前恢复身份、判断入口是否允许访问；它不能替代 Service 中的资源归属和业务规则。
- **Controller** 负责把路径、查询参数、请求体和当前身份转换为业务调用，不负责跨组件恢复协议。
- **Service** 承担业务不变量、事务边界和状态迁移。`@Transactional` 由 Spring 代理开启和提交 MySQL 本地事务，只对进入同一事务的数据库操作生效。
- **Mapper / MyBatis-Plus** 最终生成 SQL；唯一键、外键、行锁和条件更新仍由 MySQL 仲裁，不能因为 Java 中已经“先查过一次”就省略。
- **Flyway** 在启动时按 V1～V11 的顺序应用迁移，使表、约束和索引的演进可追踪。迁移存在不表示当前数据库已经实际执行，运行环境仍要单独核对。

因此一次请求是否成功至少要分两层判断：HTTP 是否进入了业务代码，以及事务或外部协议是否形成了可查询事实。HTTP 200、消息已发送和 WebSocket 已推送都不能相互替代。

#### 数据角色

| 数据类型 | 当前例子 | 判断原则 |
| --- | --- | --- |
| 持久事实 | 用户、店铺、订单、点赞关系、Grant、Job / Item、Outbox | 重启后仍要存在，可作为争议仲裁依据 |
| 协议状态 | 秒杀精确预约和 PROCESSING、登录会话 | 用于多个步骤协作，不能随意当缓存删除 |
| 派生读模型 | ES 索引、Redis 热榜、普通详情缓存 | 可从更权威数据回查或重建；无法做到时必须明确失败边界 |
| 在线提示 | Redis Pub/Sub、WebSocket 消息 | 只提示客户端刷新，不证明送达或已读 |

不要笼统地问“Redis 和 MySQL 谁是真相”。订单、点赞关系和发券权益的长期事实在 MySQL；消费者会话当前依赖 Redis；秒杀预约是关键协议状态；热榜、普通缓存和 ES 是读模型。

#### 默认开关

- 秒杀入口流量保护默认开启；
- 点赞新写、点赞 Outbox worker、热榜读取和刷新重建默认关闭；
- 秒杀 reconciler、自动补偿和启动回填分别由门禁控制，默认关闭，且存在依赖或互斥关系；
- 批量发券 Job worker 和通知 worker 默认关闭；
- CacheClient 管理的详情/分类回源和显式搜索入口分别有当前 JVM 内的并发上限。

这些开关用于受控迁移和灰度启用。复述时应说“具备这项能力并可按 rollout 开启”，不能说“所有部署都会自动运行”。

门禁也不是任意组合：点赞 legacy backfill 启动时要求新写和 Outbox worker 都关闭；秒杀 PROCESSING backfill 与在线 reconciler 不能在同一次启动中同时开启；对账中的破坏性补偿还需要在 reconciler 主开关之外单独授权。这里的目的不是增加配置数量，而是避免迁移程序和在线 writer 同时改写同一批状态。

## 2. 消费者登录：把验证码、会话恢复和接口授权拆成三个责任

### 2.1 概括版

消费者登录使用的是 Redis token 会话，不是 JWT，也不是服务器内存中的 HttpSession。验证码签发和校验分别通过 Lua 在 Redis 内原子完成，解决冷却时间、失败次数和验证码只能成功消费一次的问题；登录成功后生成随机 token，并把精简用户信息存进 Redis。后续请求先由第一个拦截器恢复身份和续期，再由第二个拦截器判断当前接口是否必须登录，业务代码只从请求线程上下文取用户。这里我特别做了失败关闭：带 token 但 Redis 无法确认身份时返回不可用，而不是把异常当匿名用户放行。

### 2.2 完整版

#### 业务场景与要解决的问题

验证码登录看起来只是“发码再比对”，但并发申请、重复使用、暴力尝试、会话续期和线程复用都会带来安全问题。另一个难点是公开接口允许匿名访问，而受保护接口必须明确区分“没登录”和“身份依赖故障”。

#### 整体方案

我把它拆成三层。验证码层用 Redis 保存短生命周期状态；登录层在验证码成功消费后查询或创建 MySQL 用户，再签发随机 token；请求层先恢复身份，再做接口授权：

~~~text
申请验证码 → 原子建立验证码、冷却和失败预算
验证码登录 → 原子校验并消费 → 查询或创建用户 → 写 token 会话
后续请求 → 恢复身份并续期 → 判断接口是否要求登录 → 清理线程上下文
~~~

#### 核心实现与技术亮点

验证码签发脚本先检查手机号冷却期，只有成功签发新验证码时才同时写验证码、冷却状态并清除上一轮失败次数。校验脚本会把“比较、增加失败次数、达到上限后作废、成功后消费”放在一次原子执行中。当前默认验证码有效 2 分钟、60 秒内不能重复申请，连续错误上限为 5 次。

登录成功后生成不可预测的随机 token，Redis 保存精简的用户快照，默认 30 分钟滑动过期。token 本身不携带 userId，所以它是需要保护的会话凭证，而不是可以公开解析的业务 ID。

请求进入后，身份恢复拦截器无论接口是否公开都会尝试解析 token，并刷新有效会话；登录拦截器只负责判断当前 method 和 path 是否要求身份。恢复出的用户放进 ThreadLocal，方便下游读取，并在请求结束时强制清理，避免 Tomcat 复用线程时串号。

#### 为什么这样设计

Lua 的价值不是“用了 Redis”，而是避免并发命令之间留下半状态。例如验证码已经比对成功却还没有删除时，第二个请求可能再次使用；原子消费后，同一验证码最多成功一次。

两个拦截器分开后，公开页面也能识别已登录用户并返回个性化信息，而权限判断不会和会话续期混在一起。ThreadLocal 只承担一次请求内的上下文传递，不承担长期会话职责。

我没有使用 JWT，是因为当前方案希望服务端能够主动失效会话并滑动续期。代价是 Redis 成为在线身份依赖；这不是绝对优劣，而是撤销能力与无状态之间的取舍。

#### 异常、一致性与当前边界

没带 token，或 Redis 正常返回会话不存在时，公开接口可以匿名继续，受保护接口返回 401；客户端带了 token 但 Redis 访问异常时，系统无法安全确认身份，当前返回 503。

验证码在查询或创建 MySQL 用户、写 session 之前已经被消费。如果后两步失败，验证码不会恢复，用户需要重新申请。这是当前实现选择的可用性窗口，不应说成 Redis 与 MySQL 共同事务。

当前没有接入真实短信供应商，接口成功只能证明验证码状态已写入 Redis，不能证明短信已送达。验证码日志默认关闭，只允许在隔离的本地开发环境显式开启。消费者 HTTP 头直接使用 raw token，不要求 Bearer 前缀；后台身份采用另一套规则，二者不能混用。

### 2.3 面试官最可能追问的 5 个问题

1. **为什么验证码要用 Lua？**
   - 回答要点：把冷却、失败预算、校验和消费变成 Redis 内原子状态迁移；防止并发重复申请和同一验证码重复成功；Lua 不解决后续 MySQL 与 Redis 的跨组件事务。

2. **为什么要两个拦截器？**
   - 回答要点：第一个负责尽可能恢复身份和续期，第二个只做入口授权；公开接口也能获得可选用户信息；职责分离便于维护 method + path 白名单。

3. **UserHolder 会不会串用户？**
   - 回答要点：它是请求线程的 ThreadLocal；容器线程会复用，所以必须在 afterCompletion 清理；长期身份仍在 Redis，不在 ThreadLocal。

4. **Redis 挂了为什么不当成未登录？**
   - 回答要点：MISS 表示已知没有会话，异常表示无法判断；把异常降为匿名可能绕过身份边界，所以受保护路径失败关闭。

5. **为什么不用 JWT？**
   - 回答要点：当前随机 token + Redis 便于主动失效和滑动续期；代价是每次请求依赖 Redis；项目没有证明它在所有场景优于 JWT，只是符合当前撤权需求。

### 2.4 详细登录与拦截器链路（保留原复习层）

#### 验证码签发、消费和登录

消费者没有使用服务器内存中的 HttpSession，而是使用 Redis token 会话：

~~~text
手机号申请验证码
  → Redis 原子写验证码、冷却时间和失败预算

手机号 + 验证码登录
  → Redis 原子校验并消费验证码
  → 查询或创建 MySQL 用户
  → 生成随机 token
  → Redis 保存 token → UserDTO

后续请求携带 token
  → 拦截器恢复当前用户
  → 需要登录的接口再判断是否已恢复成功
~~~

##### 手机号与验证码格式

申请验证码前，Service 先用项目正则校验手机号，再生成六位数字验证码。当前项目没有接入真实短信供应商；验证码日志默认关闭，只允许在隔离的本地开发环境显式开启。因此接口成功只证明 Redis 中产生了验证码状态，不证明短信已经送达。

校验会先拒绝 `null`、空字符串和纯空白，再要求整个字符串匹配当前手机号正则。登录时还要求验证码匹配 `^[0-9]{6}$`。这只是输入格式检查，不能证明号码真实存在、属于请求者或能够收到短信。当前手机号正则中的 `5[0-3,5-9]` 字符类还包含了逗号，这是源码中的已知表达缺口；复习时应按当前实现说明，不能把它扩大成运营商级号码认证。

##### 签发 Lua：冷却、验证码和失败预算一次建立

签发验证码的 Lua 同时操作三类状态：

| 状态 | 作用 |
| --- | --- |
| cooldown | 同一手机号在冷却期内不能重复申请 |
| code | 保存六位验证码并设置有效期 |
| failure | 记录本次验证码已经输错多少次 |

当前默认验证码有效 2 分钟、发送冷却 60 秒。脚本先检查 cooldown；存在就返回拒绝且不改变其他状态。只有成功签发新验证码，才写 code、写 cooldown 并清除上一轮 failure。

脚本可以简化为：

~~~text
如果 cooldown 已存在：
  返回 0，不写 code，也不清 failure

否则：
  SET code = 六位验证码，EX = 120 秒
  SET cooldown = 1，EX = 60 秒
  DEL 旧 failure
  返回 1
~~~

检查与三项变更在一次 Redis Lua 中执行，两个并发申请不能都越过 cooldown 判断。这里的“原子”表示执行期间不会插入另一个客户端命令，并不等同于 MySQL 事务的异常自动回滚。

##### 消费 Lua：错误计数和一次性消费

登录 Lua 会在 Redis 内原子完成校验和消费：

1. 达到最大失败次数时保持锁定；当前上限是 5 次。
2. code 不存在或已过期时返回失败。
3. 验证码正确时同时删除 code 和 failure，确保同一验证码最多成功消费一次。
4. 验证码错误时增加 failure，并让它跟随本次 code 的剩余寿命过期。
5. 达到第 5 次错误时删除 code，之后即使输入原正确值也不能登录。

脚本内部结果可理解为：`1` 表示正确并已消费，`0` 表示普通校验失败，`2` 表示达到失败上限或状态已锁定。Java 不把“验证码不存在、输错、已锁定”等内部差异暴露给调用方，而是保持统一的校验失败信息，避免帮助外部枚举验证码状态。

错误分支会读取 code 的剩余 TTL，并让 failure key 按相同剩余时间过期；达到第五次时把失败数固定在上限并删除 code。正确分支在返回前同时删除 code 和 failure，因此 TTL 只能保证最终过期，而原子删除才保证有效期内也不能重复使用。

需要注意一个真实窗口：验证码在查询或创建 MySQL 用户和写 Redis session 之前已经消费。如果后两步失败，验证码不会恢复，用户需要重新申请。这是当前可用性取舍，不是 Redis 与 MySQL 的共同事务。

登录成功后，客户端持有随机 token；Redis 保存的是：

| 项目 | 当前实现 |
| --- | --- |
| key | login:token 加随机 token |
| 类型 | Hash |
| 内容 | UserDTO 的 id、nickName、icon 等非空字段 |
| TTL | 30 分钟，随有效 HTTP 请求刷新 |

token 不是 JWT，也不包含 userId。拿到这个随机字符串的人可以尝试代表该用户访问，所以它本身就是需要保护的凭证。

更准确的数据关系是：客户端持有随机 UUID 去掉连字符后的 32 位十六进制 token，Redis 用这个 token 组成 key，Hash 中不再重复保存 token。`UserDTO` 是从完整用户实体裁剪出的请求身份快照，当前只需要 id、昵称和头像，手机号等字段不会进入会话。

#### 两个拦截器和 UserHolder

消费者请求依次经过两个职责不同的拦截器：

~~~text
请求进入
  ↓
RefreshTokenInterceptor，order = 0
  读取原始 authorization token
  恢复 UserDTO，刷新 Redis TTL
  ↓
LoginInterceptor，order = 1
  按 method + path 判断接口是否公开
  受保护接口检查当前线程是否已有用户
  ↓
Controller / Service
  ↓
afterCompletion 清理 UserHolder
~~~

UserHolder 是项目自己的 ThreadLocal。它只让本次请求的下游代码方便取得用户，不是长期会话库。Tomcat 会复用工作线程，所以请求结束必须删除；否则下一个请求可能错误读到上一个用户。

`UserHolder` 只有保存、读取和删除当前线程 `UserDTO` 的职责。它不访问 Redis，也不负责会话过期。第一层拦截器从 Redis 恢复成功后把 DTO 放进去，第二层拦截器和业务代码只读取它，`afterCompletion` 最终清理。

公开路径不是只按字符串判断。当前规则同时检查 HTTP method 与 path：公开 GET/HEAD 读取和登录用 POST 可以匿名进入，OPTIONS 也会放行；写接口不会因为路径相似就自动公开。消费者拦截器整体排除 `/admin/**`，后台请求由另一套身份链处理。

两种失败要区分：

- 没带 token，或 Redis 正常回答 key 不存在：公开接口可匿名继续，受保护接口随后返回 401；
- 带 token 但 Redis 访问异常：系统无法判断会话真伪，当前失败关闭并返回 503，而不是猜测身份。

消费者 HTTP 头中的值直接作为 raw token 使用，不要求 Bearer 前缀。这个约定与后台身份域不同，不能混用。

会话采用滑动过期：每次有效 HTTP 身份恢复都会把 TTL 重新设为 30 分钟，当前没有另外设置绝对最长登录期限。登出会删除 token 对应的 Redis key；下一次请求无法再恢复用户，本次请求线程中的身份仍由 `afterCompletion` 统一清理。

替代方案可以是服务器 `HttpSession`、关系数据库 session 或自包含 JWT。当前 Redis 随机 token 便于多实例共享、主动删除和滑动续期，代价是每次认证依赖 Redis；JWT 可减少在线 session 读取，但撤销、权限变化和密钥管理要另行设计，不能简单说成更高级。

## 3. 读取与搜索：按语义设计回退，而不是给所有查询套同一种缓存

### 3.1 概括版

读取侧我把“店铺详情、附近店铺、全文搜索”当成三种不同问题。详情查询使用 Cache Aside，并通过空值缓存解决穿透、SingleFlight 合并单实例同 key 的回源，再用数据库 bulkhead 限制总并发；附近店铺由 Redis GEO 负责半径候选和距离计算，MySQL 补齐完整数据；店铺全文搜索由 Elasticsearch 返回排序后的 ID，再回 MySQL 读取事实。设计重点不是命中缓存，而是依赖异常时仍保持语义：详情可以受控回源，GEO 不能用普通分页冒充地理结果，ES 失败也不会自动放开无界 LIKE 查询。当前 GEO 查询虽然保留 Redis 返回顺序，但没有显式指定距离升序，因此不能把它描述成已经严格实现“最近优先”。

### 3.2 完整版

#### 业务场景与要解决的问题

消费者读请求数量通常大于写请求，但几类查询的含义不同。店铺详情是按 ID 查事实；附近店铺要求半径过滤和距离顺序；全文搜索要求分词、过滤和相关性或地理排序。如果只用“Redis 失败就查数据库”这一条规则，缓存故障时可能压垮数据库，甚至返回语义错误的结果。

#### 整体方案

我让 MySQL 保存店铺和内容事实，再按查询特点建立三类读路径：

| 场景 | 加速或索引组件 | 回到 MySQL 后做什么 |
| --- | --- | --- |
| 店铺详情 / 分类 | Redis 普通缓存 | MISS 时查完整事实并尽力回写 |
| 附近店铺 | Redis GEO | 按候选 ID 批量补齐，并保持 Redis 返回顺序 |
| 店铺全文搜索 | Elasticsearch | 按搜索结果 ID 批量补齐，并恢复 ES 顺序 |
| Blog 全文搜索 | Elasticsearch | 当前直接返回索引文档，不做 MySQL hydration |

由 CacheClient 管理的详情或分类回源使用 DB_READ bulkhead，显式搜索入口使用独立的 SEARCH bulkhead，避免这两类受保护请求相互挤占。附近店铺的普通数据库分支等路径并不都在这两个舱内；当前许可也只属于单个应用实例，不是集群总限额。

#### 核心实现与技术亮点

详情缓存能识别合法对象、空占位、缓存未命中和损坏值。不存在的店铺也短时缓存，避免恶意或热点无效 ID 每次穿透数据库。分类列表复用列表型 Cache Aside：合法非空列表要求成员 ID 有效且不重复，空列表用空 JSON 数组短时缓存。相同资源和 key 在同一个 JVM 内由 SingleFlight 共享一次加载；但不同 key 仍可能同时回源，所以外层再由数据库 bulkhead 限制总量。拿不到许可时快速拒绝，而不是让请求在连接池前无限排队。

GEO 只存分类下的店铺 ID 与坐标。查询得到 5 公里内的 ID、距离和结果顺序后，再批量查询 MySQL。因为 SQL 的 IN 查询不保证按输入顺序返回，Service 会恢复 Redis 的返回顺序。不过当前调用只使用 `includeDistance().limit(end)`，没有显式设置 `sortAscending()`；所以它完成了半径筛选和距离返回，但严格的“按距离从近到远”仍是实现缺口。

店铺搜索使用 ES 的分词字段、精确过滤字段和地理字段完成组合查询，随后只拿排序 ID 回 MySQL。这样搜索能力和完整事实职责分开。Blog 搜索目前实现不同，它直接返回 ES 文档，因此可能缺少最新数据库内容、作者补全或当前用户点赞状态，不能把店铺结论套过去。

索引同步设计为 MySQL binlog 经 Canal 和 RocketMQ 到消费端，再以固定业务 ID 幂等 upsert 或 delete ES 文档；另有只覆盖 shop_index 的启动初始化能力。

#### 为什么这样设计

SingleFlight 解决的是“同一进程内、同一个 key 被同时回源”，bulkhead 解决的是“所有受保护查询的总并发”，二者保护的竞态不同。即使 SingleFlight 工作正常，一百个不同店铺同时冷启动仍可能产生一百次数据库查询。

ES 和 GEO 都只保存适合查询的有限字段，避免把派生索引误当业务事实。回查 MySQL 能补齐当前行，但也存在短暂窗口：索引刚返回的 ID 可能已经在数据库变化。当前店铺 ES 回查没有严格校验返回行数是否与 ES ID 数一致，这是仍需完善的边界，不能说成已经自动识别并修复不完整映射。

我没有把所有失败都降级成 MySQL LIKE 或普通列表。LIKE 不具备同样的分词、组合过滤和地理语义；普通列表也不具备半径筛选和距离信息。错误的“可用结果”有时比明确失败更危险。

#### 异常、一致性与当前边界

详情缓存读取异常时，可以在数据库 bulkhead 保护下回源；Redis 写回失败不覆盖已经查到的事实。缓存损坏也会回源修复。SingleFlight follower 有有限等待时间，超时不会取消 leader。

GEO 返回 null 或空集合目前无法区分“半径内确实无店”和“索引还没有构建”，当前代码会退回普通 MySQL 分类分页；这个结果没有半径和距离语义，是已知的非等价降级缺口。GEO 也没有默认运行的全量重建闭环。ES 搜索失败当前返回明确错误，不会自动切到 LIKE；调用方可显式选择另一条受保护的名称查询路径，但二者语义不同。

ES 同步目前能从源码和 consumer 测试确认消息处理方式，不能据此声称本轮已经完成真实 Canal Server → RocketMQ → ES 的端到端验证。启动初始化只覆盖店铺索引，也不是分页式大规模离线重建，失败可能影响启动。

### 3.3 面试官最可能追问的 5 个问题

1. **SingleFlight 和 bulkhead 有什么区别？**
   - 回答要点：前者合并同 JVM 同 key 的重复加载；后者限制一类依赖的总并发；前者减少重复工作，后者限制故障扩散；当前都不是集群级全局控制。

2. **为什么要缓存不存在的店铺？**
   - 回答要点：防止无效热点 ID 持续穿透；空占位使用有限 TTL；正常对象与空值要能区分；缓存永远不能替代数据库事实。

3. **GEO 为什么还要查 MySQL？**
   - 回答要点：Redis 保存的是坐标候选并返回距离，完整店铺信息仍在 MySQL；批量回查后要保持 GEO 返回顺序；普通列表不能作为等价地理回退；当前未显式指定距离升序，不能夸大为严格的最近优先。

4. **ES 查到结果后为什么店铺还要回库？**
   - 回答要点：ES 是近实时读模型，只负责检索和排序；MySQL 补齐完整事实；代价是一次额外读取和索引/数据库变化窗口；Blog 搜索当前没有这一步，要明确区分。

5. **缓存或搜索服务故障时怎样保护数据库？**
   - 回答要点：详情仅在 DB_READ bulkhead 下回源；搜索有独立 SEARCH bulkhead；拿不到许可快速失败；不自动打开语义不等价、压力不可控的 LIKE fallback；本地许可不代表集群总上限。

### 3.4 详细读取与搜索链路（保留原复习层）

#### 店铺详情：Cache Aside、SingleFlight 与 DB_READ

店铺详情的完整读取路径是：

~~~text
读 cache:shop:{id}
  ├─ 合法 JSON：直接返回
  ├─ 空占位：返回不存在
  └─ MISS / 坏值 / Redis 异常
        ↓
     同 key SingleFlight
        ↓
     DB_READ 并发保护
        ↓
     查询 MySQL
        ↓
     尽力回写对象或空占位
~~~

正常店铺对象和空占位都有有限 TTL；当前店铺详情两者默认都是 30 秒。空占位防止大量请求反复查询一个不存在的 ID。缓存 JSON 无法解析或对象 ID 与请求不符时，不继续相信该值，而是回源修复。

SingleFlightLoader 用 resource 与 cacheKey 标识当前 JVM 内的一次共享加载：

- 第一个成功放入任务的线程成为 leader，负责查数据库和回写；
- 同 key 的后续线程成为 follower，只等待这个任务结果；
- follower 当前最多等待 750ms，超时不会取消 leader；
- 任务完成后映射会删除，下一次未命中可以重新选 leader。

它只合并**同 key、同进程**的重复工作。若 100 个不同店铺同时冷启动，仍会产生 100 个不同任务，因此还需要 DB_READ bulkhead 限制这类受保护回源的总并发。

LocalReadBulkhead 使用 JVM 本地 Semaphore 建立 DB_READ 和 SEARCH 两个独立舱。两者当前默认都是 4 个许可、最多等待 20ms：

- 拿不到许可返回 429，避免请求无限排队；
- 依赖调用失败或等待被中断返回 503；
- finally 归还许可；
- 每个应用实例各有一套许可，不是集群总上限。

这里不能扩大成“所有数据库读取都受 DB_READ 保护”。当前是 CacheClient 管理的详情和分类回源使用 DB_READ，显式搜索入口使用 SEARCH；附近店铺的普通数据库分支等并不都在这两个舱内。

Redis 读取异常时，店铺详情允许在 DB_READ 保护下回源 MySQL，但会跳过对故障 Redis 的写入；回写本身失败也不覆盖已经查到的数据库结果。这是 best-effort cache write：缓存可以降级，事实读取仍有并发边界。

店铺分类列表复用列表型 Cache Aside：

- 合法非空列表会检查成员 ID 有效且不重复；
- 空列表用 JSON 空数组表达，不与缓存 MISS 混淆；
- MISS 或坏值经过同 key SingleFlight 和 DB_READ 回源；
- 当前正常列表默认缓存 100 分钟，空列表默认 30 秒；
- Redis 回写仍然是 best-effort。

#### 附近店铺：Redis GEO 负责半径候选和距离计算

Redis GEO 的数据角色是：

| 项目 | 含义 |
| --- | --- |
| key | 按店铺分类组织 |
| member | shopId |
| point | longitude / latitude |

附近店铺接口有三条主要分支：

1. 按评论或评分等非地理条件排序时，直接走 MySQL 分页；
2. 没有经纬度时，也走普通 MySQL 分页；
3. 带经纬度时，从对应分类的 GEO key 查 5km 内候选，取得 ID、距离和 Redis 返回顺序，再从 MySQL 批量补齐店铺详情。

MySQL 的 IN 查询不保证按传入 ID 返回，所以正常 GEO 命中后会用 `ORDER BY FIELD` 恢复 Redis 给出的结果顺序。Redis 只保存有限候选，MySQL 仍保存完整店铺事实。当前 GEO 调用包含距离和数量限制，但没有显式调用 `sortAscending()`，因此这里不能声称 Redis 返回顺序一定就是严格的距离升序；若要保证“最近优先”，还需要补上明确排序并做对应验证。

当前实现还存在明确边界：

- GEO 返回 null 或空集合时，代码会退回普通 MySQL 分类分页；
- 这个回退没有相同的半径与距离语义，是非等价降级；
- 空结果无法区分“索引尚未构建”和“半径内确实没有店”；
- 当前没有默认运行的 GEO 全量重建闭环；
- 这条路径也不是所有 Redis 异常都已统一映射为 503。

#### Elasticsearch 店铺和 Blog 搜索

店铺搜索使用 Elasticsearch 做全文检索、精确过滤和地理排序：

1. 有关键词时对店铺名称和地址做全文匹配，没有关键词时使用 match-all；
2. typeId 使用精确过滤；
3. 有坐标时增加地理半径过滤，并按距离升序；
4. ES 按页返回排好序的店铺 ID；
5. Service 按这些 ID 查询 MySQL 完整行，并恢复 ES 顺序。

text 字段适合分词检索，keyword 适合精确过滤，geo_point 支持距离过滤和排序。ES 是近实时读模型，不是店铺写入事实。ES 查到 ID 后回 MySQL，是为了补齐完整行并保持事实边界，代价是多一次数据库访问和短暂不一致窗口。

当前店铺回查不会严格校验 MySQL 返回行数是否与 ES ID 数一致，因此索引命中已经删除或变化的数据时，可能得到不完整结果。这是当前缺口，不能描述成系统已经自动把它识别为无效快照并重建。

整个“ES 查询 + MySQL 补全”位于 SEARCH bulkhead 内：拿不到许可返回 429，依赖异常返回 503。当前没有在店铺 ES 搜索失败时自动改走 MySQL LIKE，因为二者的分词、组合过滤、地理语义和数据库压力不等价。

按名称的 MySQL LIKE 接口是调用方显式选择的另一条路径，也受 SEARCH bulkhead 保护；它不是 ES 接口的自动 fallback。

Blog 搜索的读取边界不同：它在 SEARCH bulkhead 内按 title 和 content 查询 ES，当前直接返回 BlogDoc，不再回 MySQL 补齐最新 Blog、作者详情或当前用户点赞状态。因此“ES 返回 ID 后回查 MySQL”只适用于店铺搜索。

#### ES 数据同步和证据边界

当前同步设计是：

~~~text
MySQL 店铺 / Blog 变更
  → binlog
  → Canal
  → RocketMQ
  → EsSyncConsumer
  → 按固定文档 ID upsert / delete ES
~~~

固定业务 ID 作为 ES 文档 ID，使同一变更重复投递时覆盖同一文档，而不是创建重复文档。目标消息格式错误或 ES 操作失败时，consumer 抛异常交给 MQ 重试。

ShopIndexInitializer 可以在启动时把 MySQL 店铺全量写入 shop_index。它不覆盖 Blog 索引，不受请求路径的 SEARCH bulkhead 保护，也不是分页式的大规模离线重建；初始化失败可能影响应用启动。

现有验证主要在 consumer-level：能证明同步消费者如何处理给定消息，不能据此声称真实 MySQL 提交一定已经完整经过 Canal Server、RocketMQ 并最终可搜索。ES 没有普通缓存那样的 TTL；同步链路停滞时，它会保留最后一次已应用的旧文档。

## 4. 内容发布与关注流：事务内保证内容事实，事务后尽力扩散

### 4.1 概括版

内容发布时，真正需要强保证的是 Blog 记录和图片归属，所以它们在同一个 MySQL 事务中提交；热榜触发和粉丝 Feed 写入放在事务提交后的回调里，避免数据库回滚后 Redis 却已经展示内容。关注流采用推模式，发布时把 Blog ID 写进粉丝的有序集合，读取时按时间游标滚动分页。这个方案让普通用户读取很快，但它不是持久消息链：进程在提交后回调前退出、单个粉丝写入失败或大 V 写放大，目前都没有 Outbox 补偿，所以我会把它明确描述为可优化的 best-effort 链路。

### 4.2 完整版

#### 业务场景与要解决的问题

用户发布内容后，既要保证正文和图片不会出现孤儿关系，又希望粉丝尽快在关注流里看到新内容。两者的一致性等级不同：内容本身不能丢，Feed 可以短暂缺失，但不能展示最终回滚的内容。

#### 整体方案

发布事务先写 Blog，并确认临时图片属于当前用户，再把图片转为正式归属。只有数据库提交成功后，回调才尝试触发热榜更新并把 Blog ID 推入各粉丝的 Redis Feed。读取 Feed 时按发布时间倒序，通过时间分数和 offset 解决相同时间戳下的滚动分页。

关注或取关以 MySQL 关系为主要记录，同时维护 Redis Set 以支持共同关注等快速查询。这里与点赞链路不同，当前没有用 Outbox 把关系变化和 Redis 更新持久串联。

#### 核心实现与技术亮点

事务提交后回调是这条链最关键的边界。它保证只有已经提交的 Blog 才会向外扩散，避免“Redis 已经出现内容，MySQL 最终却回滚”的脏展示。

Feed 使用推模式：发布一次会写多个粉丝收件箱，查询时只需要读自己的有序集合。滚动分页不依赖页码，而是带上上一页最小时间和同分 offset；多篇内容拥有相同毫秒时间时也不会简单重复或遗漏。

#### 为什么这样设计

对于普通关注规模，推模式把成本放在相对低频的发布侧，让高频读取更快。只在事务提交后推送，是在不引入完整消息基础设施时保持“先有内容事实，再有派生展示”的最小安全边界。

这条链也保留了很好的设计对照：秒杀、点赞和发券对关键跨组件步骤使用事务消息或 Outbox，而普通 Feed 仍是 after-commit best effort。不是所有功能都需要同一一致性等级，但必须诚实说明差异。

#### 异常、一致性与当前边界

after-commit 不是持久待办。数据库提交后、回调执行前进程崩溃，或者某个粉丝的 Redis 写入失败，目前只会留下日志，不保证自动补发。Feed key 丢失后也没有根据关注关系和历史 Blog 自动重建的闭环。

推模式还存在大 V 写放大；当前实现没有冷热粉丝分层、推拉结合或持久消息扇出。关注/取关的 MySQL 与 Redis 双写也没有共同事务，早期关系约束并未完整覆盖所有重复竞态。这些都是已知边界，不能把当前链路说成可靠消息流。

### 4.3 面试官最可能追问的 5 个问题

1. **为什么要等事务提交后再写 Feed？**
   - 回答要点：避免数据库回滚但 Redis 已展示；after-commit 建立了事实先于派生展示的顺序；它仍不保证提交后一定完成推送。

2. **为什么选择推模式？**
   - 回答要点：普通用户发布低于读取，把计算移到发布侧可提高读取速度；代价是大 V 写放大和收件箱存储，需要规模证据后再考虑推拉结合。

3. **滚动分页为什么需要 offset？**
   - 回答要点：只带最小时间时，同一时间戳的多条内容会重复或漏读；offset 记录上一页已消费的同分成员数量。

4. **after-commit 和 Outbox 有什么差别？**
   - 回答要点：after-commit 避免回滚前发送，但没有持久待办；Outbox 与事实同事务落库，崩溃后 worker 还能继续；当前 Feed 使用前者，点赞和发券使用后者。

5. **Feed 丢了怎样恢复？**
   - 回答要点：当前没有自动重建闭环，只能以 MySQL Blog 和关注关系作为事实定位；不能声称系统会自动补发；可演进为持久 Outbox、消息扇出和按事实重建。

### 4.4 详细发布与关注流链路（保留原复习层）

#### 图片先成为受管理的临时资源

上传接口先从 UserHolder 确认当前用户，再同时校验文件大小、扩展名、Content-Type 和文件头签名。当前只接受 JPG/JPEG/PNG，默认上限 5MB。服务端生成 UUID 文件名和两级分片目录，而不是直接使用客户端文件名。

写文件前会规范化配置根目录，并检查解析后的真实父目录仍在根目录中，避免目录穿越和已存在的符号链接绕过。文件落盘后，MySQL 记录其路径、ownerUserId 和 `TEMP` 状态；如果临时记录写入失败，接口会尝试删掉刚写入的文件。

删除临时图片时，只接受项目自己生成的受管路径，并再次校验归属、状态和文件真实位置。数据库先条件更新 `TEMP → DELETING`，抢到删除权的请求才删文件并删记录；删除文件或后续数据库调用抛出异常时会尝试退回 `TEMP`。完成删除记录的调用当前没有检查影响行数，因此零行结果不会触发该回退。

#### Blog 事实和图片归属同事务确认

发布 Blog 的 MySQL 事务按下面的顺序执行：

1. 从 UserHolder 取当前 userId，忽略客户端自报的作者；
2. 规范化图片列表，限制最多 9 张，拒绝重复路径，并确认每张图都是该用户的 `TEMP` 记录；
3. 写入 Blog 记录；
4. 通过带 path、ownerUserId 和原状态条件的更新，逐张转为 `PUBLISHED` 并关联 blogId；
5. 查出当前作者的 followerIds，注册事务提交后回调。

Blog 插入和图片归属转换同在一个 MySQL 事务中；任意一张图的条件更新不是 1，整个发布事务回滚。这防止用户引用别人的临时图片，也防止同一张图被并发发布到两篇 Blog。

#### 提交后更新派生读模型

只有 MySQL 提交后，afterCommit 回调才尝试把新 Blog 放入已就绪的热榜，并向粉丝的 Redis feed 写入新笔记：

| 项目 | 当前含义 |
| --- | --- |
| key | 每个 follower 的 feed |
| member | blogId |
| score | 发布时间毫秒 |

当前每次最多取 2 条，用 `max + offset` 做 score 倒序滚动分页：`max` 是上一页的最小时间，`offset` 是上一页已经消费的同分成员数。取到 ID 后再批量查 MySQL，用 `ORDER BY FIELD` 恢复 feed 顺序，并补齐作者和当前用户点赞状态。

这是推模式：发布时写多个粉丝收件箱，读取快，但大 V 会产生写放大。如果日后出现高粉作者，可考虑普通用户推、大 V 拉，但当前没有这个混合闭环。

#### afterCommit 和关注关系的一致性边界

afterCommit 能避免 MySQL 最后回滚而 Redis 提前展示，但它不是持久 Outbox。数据库刚提交、进程在回调前退出时，没有一条待办保证补发；单个 follower 的写入失败也只记录日志。feed 丢失时当前读取直接返回空，没有从关注关系和 Blog 事实自动重建的兜底。

关注时先向 MySQL 插入关系，成功后再把 followUserId 加到当前用户的 Redis Set；取关时先按 userId + followUserId 删数据库，再移除 Set 成员。`isFollow` 查 MySQL，“我的关注”和“共同关注”则读 Redis Set 并回查用户。

这组 MySQL + Redis 双写当前没有共同事务或 Outbox；早期表结构也没有 userId + followUserId 唯一键完整兜底重复关系。因此 MySQL 成功而 Redis 失败时，读接口可能暂时相互矛盾。这条普通链路可以用来对照一致性等级：同一项目中的功能并不天然具有与三条核心链相同的恢复能力。

图片文件系统与 MySQL 也不在一个事务中。当前没有定时清理长期 `TEMP` / `DELETING` 记录、扫描孤儿文件或反向补齐缺失文件的闭环；排查时必须分别保留文件状态和 MySQL 归属证据，不能用删记录来掩盖不一致。

## 5. 后台安全与实时通知：权限只是第一层，数据范围和长连接撤权同样重要

### 5.1 概括版

后台同时服务平台账号和商户账号，所以我没有只做一个角色注解，而是建立独立于消费者的后台身份域。登录成功后，后台 token 在 Redis 里只关联账号和签发时的权限版本；每次请求都会回 MySQL 重建当前账号、商户、角色和权限。真正访问资源时依次经过身份、功能权限、平台或商户 scope、资源归属和带商户条件的 SQL 五层校验。WebSocket 又单独使用 30 秒一次性 ticket，握手和发送前都会重新确认权限，防止长期 token 出现在 URL，也让停用、改密或撤权能影响已经建立的连接。通知仍然只是 best-effort，最终结果必须回查订单或券权益。

### 5.2 完整版

#### 业务场景与要解决的问题

后台最大的风险不是“没有登录”，而是一个已经登录且拥有某类功能权限的商户员工，通过篡改资源 ID 访问另一家商户的数据。WebSocket 连接还会长期存在，握手后账号可能被停用、改密或撤权，单次 HTTP 鉴权无法覆盖整个连接生命周期。

#### 整体方案

消费者和后台使用独立 token 格式、Redis 会话空间、请求上下文和拦截器。后台请求恢复身份后，先检查接口权限，再确定平台或商户 scope，随后由 Service 验证目标资源归属，最终 SQL 仍携带 merchantId 条件。

后台 WebSocket 不直接在 URL 中携带长期 Bearer token。已认证 HTTP 请求先申请短期一次性 ticket，握手时原子消费 ticket，并重新恢复后台身份。连接按平台账号或 merchantId 精确登记；跨实例事件通过 Redis Pub/Sub 广播到各实例，只有真正持有目标连接的实例发送，发送前再次复核会话、账号、scope 和实时权限。

消费者 WebSocket 走另一条已实现路径：握手 URL 当前直接携带消费者 session token，服务端从 Redis 恢复并绑定精确的 userId 与 token，同一用户的新连接替换旧连接；发送前再次确认 token 仍映射到该用户，过期或 Redis 无法确认时关闭连接。只有后台链路使用 30 秒一次性 ticket，不能把这项改进误说成消费者端也已完成。

#### 核心实现与技术亮点

后台密码使用 BCrypt。用户名不存在时仍计算一次 dummy hash，并统一返回账号或密码错误，减小账号枚举的时间差。登录限制同时看用户名加 IP 和单 IP 总尝试；只有直连来源属于显式可信代理时才接受转发头，避免客户端自行伪造 IP 绕过限制。

后台 token 对应的 Redis 值包含账号 ID 和签发时的 authVersion。每次请求都回库查询当前账号、商户、角色和权限，并比较版本。改密或账号状态变化可推进 authVersion，让旧 token 在下一次使用时失效；角色权限变化也会因重新查询而很快生效。

五层边界分别回答不同问题：

| 层次 | 回答的问题 |
| --- | --- |
| 身份 | 当前账号是谁，是否仍有效 |
| permission | 能不能执行这类功能 |
| scope | 本次身份允许触达哪个商户范围 |
| ownership | 目标店铺、券或活动是否真的属于该范围 |
| scoped SQL | 最终查询或写入是否仍带商户条件 |

#### 为什么这样设计

RBAC 只能说明“能不能管理店铺”，不能说明“能不能管理这一家店铺”。把商户边界继续下沉到 Service 和 SQL，能防止 Controller 漏校验、资源 ID 被替换以及先查后写期间的竞态。

后台会话每次回库的成本高于完全自包含 token，但换来了更短撤权窗口。一次性 WebSocket ticket 则减少长期凭证出现在访问日志、代理日志和浏览器历史中的风险。发送前复核解决的是握手后权限变化，不能被一次握手校验替代。

#### 异常、一致性与当前边界

后台常见响应要区分：没有有效身份是 401；身份有效但无功能权限或 scope 明确不合法是 403；在当前商户范围内找不到资源通常返回 404，避免泄露外商户资源是否存在。登录频率或读取舱拥塞可返回 429。

消费者与后台 token 完全不能互换。后台 ticket 只有 30 秒且只能成功消费一次，但它不是离线消息凭证；消费者 WebSocket 当前仍把长期 session token 放在查询参数中，这是已有实现边界。Redis Pub/Sub 不持久保存事件；publish 成功不代表目标实例有连接，WebSocket send 成功也不代表浏览器展示或用户已读。当前没有应用级 ACK、断线补发和离线消息中心。

后台 session 恢复中的部分依赖异常目前仍可能落到统一 500，并非所有路径都精确映射为 503。商户事件如果无法解析出明确 merchantId，不会退化成全商户广播。订单结果和券权益始终以事实查询接口为准。

### 5.3 面试官最可能追问的 5 个问题

1. **RBAC 为什么不能解决全部越权问题？**
   - 回答要点：RBAC 判断功能权限，不判断目标数据归属；还需 scope、ownership 和 scoped SQL；数据库外键只证明商户存在，也不知道当前请求是谁。

2. **怎样阻止商户 A 修改商户 B 的店铺？**
   - 回答要点：后台身份恢复 A 的 merchantId；权限只放行功能；资源查询带 A 的范围；Service 校验归属；最终 UPDATE 再带 A 的 merchantId，影响行数异常不能报告成功。

3. **为什么后台 token 每次请求都要回库？**
   - 回答要点：重建最新账号、商户、角色和权限；authVersion 让改密或停用后的旧 token 失效；以数据库读取成本换更短撤权窗口。

4. **WebSocket 为什么不用后台 Bearer token 直接握手？**
   - 回答要点：URL 更容易被日志和历史记录收集；后台一次性短票据降低长期凭证暴露；握手时再次恢复身份；发送前还要复核长期连接期间的撤权。消费者端目前仍直接传 session token，要明确这是尚未统一的边界。

5. **Redis Pub/Sub 加 WebSocket 能保证通知送达吗？**
   - 回答要点：不能；Pub/Sub 无离线持久化，连接可能不在当前节点或已经断开，send 也没有用户已读语义；只做刷新提示，事实接口负责最终结果。

### 5.4 详细后台身份、RBAC 与 WebSocket 链路（保留原复习层）

#### 两个身份域

消费者和后台不是共用一套 token 后再靠角色区分，而是两个独立身份域：

| 身份域 | HTTP 凭证 | Redis 会话 | 请求内身份 | 入口组件 |
| --- | --- | --- | --- | --- |
| 消费者 | authorization 头中的 raw token | login:token 对应 Hash | UserHolder | RefreshTokenInterceptor + LoginInterceptor |
| 后台 | Authorization: Bearer token | admin:login:token 对应 String | AdminPrincipalHolder | AdminSessionInterceptor + AdminAuthorizationInterceptor |

消费者拦截器排除 admin 路径，后台拦截器只处理 admin 路径。即使有人把合法消费者 token 放进后台请求，它也无法被后台 Redis 空间和 Bearer 规则恢复为 AdminPrincipal；反方向同样不成立。

AdminPrincipal 是服务端验证后为本次请求建立的身份快照，包含 accountId、merchantId、scopeType、authVersion 和 permission 集合。业务 Service 从这里取得操作者和商户范围，不相信请求体自报的身份字段。

#### 后台登录与会话恢复

后台登录的详细过程是：

1. 规范化并校验用户名，解析可信客户端 IP；
2. 检查“用户名 + IP”的失败计数，并增加 IP 总尝试计数；
3. 查询账号，用 BCrypt 校验本次明文密码和数据库 hash；
4. 校验账号状态、scope、商户状态、角色与权限组合；
5. 登录成功后生成随机后台 token，把 accountId 和签发时 authVersion 写入 Redis，默认 TTL 30 分钟。

当前默认“用户名 + IP”最多失败 5 次，单 IP 在 15 分钟窗口内最多尝试 30 次。计数脚本使用原子的 INCR 和首次 EXPIRE，避免并发丢计数或生成永久 key。只有直连节点属于配置的可信代理时，系统才接受合法的 X-Real-IP 或 X-Forwarded-For；否则只使用直连地址。

用户名会先 trim 并转小写，然后限制为 4～64 位小写字母、数字、点、下划线或连字符。登录输入密码最长接受 256 字符；改密时新密码至少 12 位且 UTF-8 编码不超过 BCrypt 的 72 字节边界。通过“用户名 + IP”预检查后的每次尝试都会增加 IP 总尝试计数；如果前者已经锁定，请求会在增加 IP 计数前返回。成功登录只清除“用户名 + IP”失败数，不会提前清除 IP 总计数。

BCrypt hash 不可逆，也不需要解密。登录使用 matches 重新计算后比较。用户名不存在时仍对 dummy hash 执行一次匹配，再统一返回“账号或密码错误”，减小账号枚举的时间差。

后台请求每次恢复身份时都会：

1. 从 Bearer 头取出格式合法的随机 token；
2. 读取 Redis 中的 accountId 与 issuedAuthVersion；
3. 回 MySQL 查询当前账号、商户、角色和权限；
4. 检查签发版本与当前 authVersion 一致；
5. 构造 AdminPrincipal 并刷新会话 TTL。

改密或账号状态变化会推进 authVersion，旧 token 下一次使用时会被拒绝并删除。角色或权限变化即使没有推进版本，也会因为每次重新查询而在下一次请求生效。这个方案用数据库读取成本换取较短的撤权窗口。

#### 五层商户隔离

后台安全必须同时回答“能不能做这类操作”和“能不能操作这一条数据”：

~~~text
1. Admin token → 当前有效 principal
       ↓
2. Controller permission → 能否执行这类功能
       ↓
3. platform / merchant scope → 本次允许触达哪个商户
       ↓
4. Service ownership → 资源关系是否属于该商户
       ↓
5. scoped SQL / 条件更新 → 数据库写入仍携带 merchant 条件
~~~

- **认证**确认是谁；**授权**确认能做什么；
- **RBAC**把账号关联到角色，再由角色得到权限码；
- **scope**限制本次身份可以触达的数据集合；
- **ownership**校验店铺、券、活动等资源的真实归属；
- **scoped SQL**在查询和更新中再次带 merchantId，防止遗漏前置校验或出现先查后写竞态。

例如商户 A 的员工拥有店铺写权限，却把 shopId 改成商户 B 的店铺：权限检查可能通过，但带 merchantId 的资源查询不会返回该行；真正 UPDATE 仍带相同商户条件，影响行数不为 1 就不能报告成功。

数据库外键只能证明 merchantId 指向真实商户，不知道当前请求是谁；权限注解只能证明账号有某个功能权限，不知道目标资源属于谁。因此任何一层都不能单独替代其余层。

权限注解优先读方法，方法没有时再读 Controller 类。没有任何注解的后台 Handler 默认 403；空权限码仅表示需要有效后台身份。当前没有全局 ORM 租户插件自动补 merchantId，所以新增后台查询和写入时，仍要审核 Service 归属校验和最终 SQL 范围。

常见 HTTP 结果应保持语义区分：

| 状态 | 典型含义 |
| --- | --- |
| 401 | 没有可用后台身份，或 token 已失效 |
| 403 | 身份有效，但缺少功能权限或请求 scope 明确不合法 |
| 404 | 当前商户范围内找不到资源，避免泄露外商户资源是否存在 |
| 429 | 登录尝试或受保护资源的并发超过入口限制 |
| 503 / 500 | 显式映射的依赖故障可返回 503；普通后台 session resolve 的部分异常当前仍可能落到统一 500 |

#### 消费者与后台 WebSocket 鉴权

HTTP 鉴权只覆盖一次请求；WebSocket 握手成功后可能保持很久，期间账号、权限和商户状态都可能变化。当前四种凭证不能混淆：

| 凭证 | 用途 | 关键特点 |
| --- | --- | --- |
| consumer raw token | 消费者 HTTP | Redis Hash 会话 |
| admin Bearer token | 后台 HTTP | Redis String 会话，每次回库复核 |
| consumer WS token | 消费者 WebSocket 握手 | 查询参数携带，复用消费者长期会话 |
| admin WS ticket | 后台 WebSocket 握手 | 30 秒、一次性，只用于换取已验证连接 |

消费者通过 `/ws/connect?token=...` 握手，拦截器直接读取消费者 Redis 会话，把精确 userId 和原 token 绑定到连接。同一 userId 的新连接会替换旧连接；每次发送前还会确认该 token 仍映射到同一 userId，失效或 Redis 无法确认时关闭连接。

后台先在已认证 HTTP 请求中申请短期 ticket，再通过 `/ws/admin/connect?ticket=...` 握手。签发时要求当前账号具有 `order:realtime` 权限；握手时 Lua 原子读取并删除 ticket，再用 ticket 关联的后台 token 重新恢复当前账号、scope 和权限。第二次使用同一 ticket 会失败。握手和发送前复核都不刷新原 session TTL，所以长连接不能独自让后台会话永久存活。

连接按身份进入精确 registry：平台账号单独保存，商户账号按 merchantId 分区。订单结果先发布到 Redis Pub/Sub，使各应用实例都能看到事件；真正持有目标 WebSocket 的实例才向本地连接发送：

~~~text
业务线程 / MQ Consumer
  → Redis 精确频道
  → 各实例订阅器
  → 持有目标连接的实例命中 registry
  → 发送前重新 resolve token、账号、scope 和实时权限
  → 发送或关闭已撤权连接
~~~

商户事件只有在能够从券解析出明确 merchantId 时才发布到对应商户频道；解析失败不会退化成全商户广播。发送前再次复核，使停用、改密、撤权或商户状态变化在长连接期间仍能生效。

这条链只提供 best-effort 在线提示：

- Redis Pub/Sub 不保存离线消息；
- publish 成功不表示某个实例一定有目标连接；
- WebSocket send 返回不表示浏览器已经展示或用户已读；
- 当前没有应用级 ACK、断线补发、离线消息中心或跨节点必达证明。

两个握手端点都有显式 Origin 允许列表，默认只包含本地前端地址。连接 registry 仅存在当前 JVM，Redis Pub/Sub 只负责让多实例看到事件；应用重启会丢连接，负载均衡器仍需支持 WebSocket Upgrade 和合理长连接超时。发送使用并发会话包装器，当前单连接发送时间上限 10 秒、缓冲上限 256KiB；这些是防止慢连接拖累进程的局部边界，不是送达保证。

订单结果应查询订单状态，券权益应查询 MySQL Grant。WebSocket 不能替代持久事实接口。

## 7. 回答横向问题时可以复用的框架

### 7.1 先说事实，再说加速层

回答任何跨组件问题时，先说明长期事实在哪里，再说明过程状态、派生读模型和在线提示。不要用缓存命中、消息已提交或 WebSocket 已发送证明业务事实已经成立。

### 7.2 不要把所有锁说成“为了线程安全”

| 机制 | 当前用途 | 不能提供的保证 |
| --- | --- | --- |
| Redis Lua | 同一个 Redis 内原子校验和迁移状态 | 不能让 Redis、MySQL、MQ 一起回滚 |
| MySQL 行锁 | 稳定一批事件、活动额度或资源存在性 | 不能跨数据库协调 |
| Redisson 锁 | 减少多实例对同一业务并发操作 | 不能替代唯一约束、条件更新和状态 fence |
| JVM bulkhead | 限制单实例依赖并发并快速拒绝 | 不是集群总流量控制 |
| generation | 拒绝过时热榜 builder 发布 | 不能证明 MySQL 点赞聚合绝对无误 |

### 7.3 异常策略要说出使用条件

- **重试**：同一动作重放可能成功，而且副作用已经幂等。
- **补偿**：能够证明之前的预约属于当前操作，并确认长期事实没有成立。
- **回退**：加速层失效后存在语义正确、压力受控的权威读取路径。
- **失败关闭**：身份、资格或归属无法安全判断时停止，而不是猜测。
- **best-effort**：失败不能反向撤销已经成立的业务事实，例如 WebSocket。
- **隔离**：证据冲突时停止自动动作并保留现场，避免错误“修复”。

## 8. 故障排查与恢复判断（保留原复习层）

### 8.1 先保留事实，再决定动作

遇到“用户说失败了”，不要先删 Redis、重启 worker 或手工补数据。按下面顺序缩小范围：

1. **确认身份和业务标识**：消费者还是后台账号，userId、accountId、merchantId、业务对象 ID、orderId、requestId 或 idempotencyKey 是什么；
2. **记录传输结果和业务结果**：HTTP status、统一响应体中的 success、code、data 都要保留；HTTP 200 也可能承载库存不足等业务拒绝；
3. **先查持久事实**：MySQL 中的订单、关系、Grant、Job / Item、Outbox 是否存在；查询异常绝不能解释成“不存在”；
4. **再查协议状态和读模型**：区分 session、预约/过程状态、普通缓存、GEO、热榜、ES 和 Pub/Sub；
5. **查看异步进度**：MQ retry / DLQ、Outbox pending、到期处理索引、FAILED Item 的数量、最老年龄和失败分类；
6. **用业务 ID 关联日志与指标**：指标帮助判断范围和趋势，但不能替代具体事实检查；
7. **执行恢复前写出前提**：重试是否幂等，补偿是否能证明所有权，证据冲突时是否必须隔离。

### 8.2 常见现象先查什么

| 现象 | 第一事实检查 | 第二检查 | 不应直接做 |
| --- | --- | --- | --- |
| 受保护接口突然 401 / 503 | token 是否存在、账号或用户是否有效 | Redis 是正常 MISS 还是访问异常，后台再看 authVersion | 跳过身份依赖继续放行 |
| 商户看到了外商户数据 | 账号、商户、角色权限与资源归属 | principal scope、Service ownership、scoped SQL | 只隐藏前端菜单 |
| 店铺详情把数据库压高 | MySQL 和连接池是否健康 | cache hit / miss / error、single-flight follower、DB_READ 拒绝 | 无界增加线程或等待时间 |
| 附近店铺为空 | MySQL 是否有该分类和坐标 | GEO key、成员、半径和当前非等价回退 | 把普通 MySQL 排序解释成距离结果 |
| 搜索结果旧或不可用 | MySQL 当前行 | ES 文档、MQ consumer、Canal 链与 SEARCH 拒绝 | 把 ES 当写入真相；故障时无界 LIKE |
| 关注流漏了新内容 | MySQL Blog 和关注关系 | afterCommit 日志、目标 feed ZSET | 声称当前链路一定会补发 |
| 秒杀一直处理中 | 按 orderId 查 MySQL 订单 | Redis 状态、预约、对账索引、隔离与 MQ | 数据库查询失败时补库存 |
| 点赞数或热榜异常 | 点赞关系与 MySQL 聚合数 | Outbox 精确行、榜单元数据与 generation | 直接手改 ZSET 当作修复事实 |
| 发券通知没收到 | MySQL Grant | 通知 Outbox、Pub/Sub、WebSocket 在线状态 | 撤销 Grant；把 PUBLISHED 当已读 |

### 8.3 怎样判断已经恢复

恢复完成不能只看进程存活、HTTP 200、队列 lag 为零或平均延迟正常：

- 身份问题要确认当前凭证、账号状态、permission、scope 和资源归属共同成立；
- 缓存和搜索问题要确认请求返回了正确语义的数据，派生索引可以继续收敛，而不是只把异常隐藏；
- 核心业务要回到订单、关系或 Grant 等持久事实及其不变量；
- 自动动作停止在隔离区时，应保留足够证据供人工判断，不能为了“状态都结束”伪造终态。

### 8.4 后台任务和积压

- **Scheduler**：按时间触发一次尝试，不保存完成事实；
- **Worker**：每次取得有限待办并执行；
- **Job**：一项持久整体任务；
- **Item**：Job 中可以独立重试或分类的最小目标；
- **State machine**：规定允许的状态和迁移前置条件；
- **Reconciler**：正常链路没有及时到终态时，根据事实源重新分类并安全推进。

有限批次用于限制锁范围、事务时长、内存和回滚成本，不自动等于高吞吐。判断异步链是否健康，至少要同时看“积压数量 + 最老年龄 + 失败分类 + 最终业务不变量”。队列 lag 为零只说明消息层没有已知积压，不能证明消费者产生了正确业务结果。
