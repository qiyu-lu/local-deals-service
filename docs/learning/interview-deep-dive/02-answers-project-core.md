## 一、项目总览与个人贡献（Q01～Q04）

### Q01｜请介绍项目和你能讲清的一项工作

**详细口述回答**

这是一个本地生活平台：普通用户查商铺、发探店内容、领普通优惠券或参与限量秒杀；后台员工按权限管理店铺和营销活动。项目把不同业务的结果放在合适的位置：正式秒杀订单和库存记录在 MySQL，普通券是否已发给某位用户看 `tb_voucher_grant`；Redis 保存登录会话、商铺详情缓存，也保存秒杀进行中的库存预占和订单状态；RocketMQ 把已经获准的秒杀请求交给订单消费者；Elasticsearch 保存用于搜索和排序的商铺字段。

如果面试官问实现难点，我会讲秒杀。HTTP 请求拿到订单号时，数据库订单可能还没生成。中间可能遇到半消息回查、消息重投，或数据库已经提交而 Redis 仍显示处理中。因此入口要保存“券 ID—普通用户 ID—订单 ID”的对应关系；消费者落库前核对它，数据库用条件扣库存与唯一键阻止超卖和重复，后续再依据真实订单更新 Redis。这个过程能体现我对异步时序的理解。

但“我独立完成了哪一块、当时怎么排查”必须用本人提交、记录和实际操作回答。仅从这个仓库能确认机制存在，不能确认每个模块的个人归属。面试前应填上 **[待本人确认：本人修改的文件/提交、亲历问题、亲自运行的验证]**，不要把后续整理与早期开发混成一次经历。

**追问与回答**

- **哪一项结果必须同步确认？** 普通领券返回成功前，要让用户权益和活动已发数量在同一个数据库事务提交；秒杀 HTTP 只同步确认准入与订单号，正式订单由 MQ 消费者稍后提交。商铺搜索返回候选 ID 后还会回 MySQL 查当前商铺，索引更新可滞后。
- **怎样证明不是只会搭组件？** 可以拿两笔订单说明：A 失败释放预占后，B 重新预占；A 的旧消息晚到时，消费者必须检查当前用户预占指向 B，从而拒绝 A。再说清楚测试覆盖和锁失效后的限制，而不是只列 Redis、MQ 的名字。

**核对备注**

源码入口见 `VoucherOrderServiceImpl`、`SeckillOrderProducer`、`SeckillOrderConsumer`；营销券见 `VoucherGrantTransactionService` 与 V9～V11 迁移。历史压测文件仅是历史材料，本次没有复跑；个人贡献与时间线待本人确认。

### Q02｜一次请求怎样经过这些组件

**详细口述回答**

请求先过相应身份拦截器。普通用户令牌到 Redis 普通会话区取用户信息，后台令牌则走另一套会话解析，并重新查员工状态和权限。身份通过后才进控制器、服务。商铺详情会尝试 Redis 缓存，必要时受控查 MySQL；商铺搜索索引保存商铺 ID、名称、地址、类型、均价、评分、销量和坐标，用名称/地址匹配关键词，可按类型和距离过滤、按距离排序。服务拿到 ES 排好的商铺 ID 后，按这个顺序回 MySQL 取图片等完整字段，所以索引文档本身不是最终详情。秒杀请求则经过限流、生成订单号和半消息里的 Redis 准入，随后由 MQ 消费者在 MySQL 创建正式订单。

不能把 Redis 笼统当成可清空缓存。商铺详情缓存丢了可以回源，但秒杀快速库存、用户到订单的预占、单笔订单状态、待检查 ZSet 和隔离记录在异步期间都参与判断。若这些数据丢失，数据库已提交的订单仍在，未落库请求的归属却不能仅靠数据库完整还原。消息队列承载待投递订单消息，不能代替正式订单表；ES 里的商铺字段用于检索，不是库存、领券或订单记录。

**追问与回答**

- **为什么搜索后还查数据库？** 搜索索引可能比 MySQL 慢一步。当前流程用 ES 确定候选与排序，再按 ID 读取商铺的当前数据库资料和图片等完整字段；若商铺行已删除，就不会出现在回库结果中。当前这条回库 SQL 主要按 ID 查询并保留 ES 顺序，不能额外声称它实现了商铺状态过滤。
- **小规模部署会先简化什么？** 可以先用 MySQL 的受限查询替换 ES 搜索链路，省去同步和索引运维，但会失去现有全文检索与排序能力。若把秒杀改为同步落库，仍须保留数据库的条件扣库存和唯一约束。

**核对备注**

商铺读与搜索见 `docs/learning/flow-notes/06-shop-read-and-search.md` 及商铺服务；秒杀见 Q05。各组件在不同入口承担不同职责，不能把 ES 索引、详情缓存、排行榜和预占状态归为同一类。

### Q03｜数据库订单已成功，Redis 还显示处理中怎么办

**详细口述回答**

我先确认故障点：消费者已经在 MySQL 提交了这笔订单，同时扣减了数据库的秒杀库存；随后把 Redis 单笔状态从 `PROCESSING` 改成 `SUCCESS` 时失败。此时不能加回 Redis 库存，因为券已经卖出。当前消费者会抛出异常，使 MQ 后续重投。重投再次执行数据库插入时会撞到同一订单的唯一键，服务再查订单号、用户 ID 和券 ID；三者一致就当作同一笔消息重放，直接返回，不再扣数据库库存，然后再次尝试标记 Redis 成功。

普通用户按订单号查状态时，若 Redis 仍为 `PROCESSING`，接口会先确认这份 Redis 状态属于当前用户，再查 MySQL 中同订单号且属于当前用户的订单，并比对券 ID。查到后会尽力把 Redis 改为成功；即便这次写 Redis 失败，也向该用户返回成功，因为数据库订单已经提交。Redis 查询失败或状态缺失时，也会尝试按订单号回查数据库；数据库查询本身失败则不能猜成成功或不存在。

**追问与回答**

- **为什么重投不会第二次扣库？** 插订单是数据库事务里的第一步。同订单号重复插入触发唯一键后，代码读取旧订单并比对用户和券；完全一致即从持久化方法返回，条件扣库存代码不会再执行。
- **这是亲历故障吗？** 目前可依据消费异常单测、真实数据库下的重复消费测试和 Broker 重投测试说明机制；这些测试文件存在不等于本次运行通过，也不能证明我亲历了线上故障。**[待本人确认：是否做过该故障注入及运行记录]**。

**核对备注**

见 `SeckillOrderConsumer`、`VoucherOrderServiceImpl.querySeckillOrderStatus/createVoucherOrder`、`seckill_mark_success.lua`。定时对账默认关闭，不能把它当作默认恢复步骤。

### Q04｜这个项目的技术难点体现在哪里

**详细口述回答**

我会选一条具体的失败时序，而不是罗列技术名词。比如秒杀请求通过 Redis 后，半消息要被提交，消费者要在 MySQL 插订单、条件扣库存，最后再把 Redis 状态改成功。每个环节可能重复或失败，所以代码要保留当前预占对应哪个订单，遇到旧消息时不能拿新订单的预占继续执行。普通数据库唯一键只挡同用户同券重复订单；条件扣库存只挡数据库库存变负；Redis 条件脚本只保证仍属于原订单的预占被改动。这三层解决不同问题。

更难的边界是消费者已经验证 Redis 预占并开始数据库事务后，若进程长暂停、用户锁失效，对账器可能查不到未提交订单并释放 Redis 库存。旧消费者恢复后，数据库唯一键和 `stock > 0` 仍可能允许它提交。这说明现行代码没有“补偿成功后禁止迟到数据库提交”的跨存储裁决。若面试问怎么加强，我会提出让消费与取消争同一条数据库申请状态，并在订单事务内条件迁移；那是改进方案，不是现有功能。

**追问与回答**

- **为何不只存用户已购集合？** 集合能回答用户是否被占用，不能分辨当前持有的是订单 A 还是后来订单 B。迟到的 A 消息可能误用 B 的资格，或误加回 B 的库存，因此还要保存用户到订单 ID 的映射和单笔状态。

## 二、秒杀事务、一致性与恢复（Q05～Q18）

### Q05｜一次秒杀从点击到提示怎样走

**详细口述回答**

普通用户登录后进入秒杀接口，服务先用用户 ID、券 ID 和客户端 IP 做固定窗口限流。限流脚本用 Redis 服务器的 `TIME` 得到当前毫秒，再用“当前毫秒除以窗口毫秒取整”得到窗口编号；活动计数 Key 按券和窗口区分，用户计数 Key 再带用户 ID，IP 计数 Key 带 IP 的 SHA-256 值。它先依次看活动、用户、IP 是否已达到上限，任一超限返回限流错误，三个计数都不变。全部未超限才一起 `INCR` 三个 Key，并给这三个**计数 Key** 各设 `PEXPIRE(窗口毫秒 × 2 + 1000)`，清理旧窗口计数。默认限流开启，窗口 1 秒，活动 300、同用户 2、同 IP 100；Redis 出错则返回暂不可用。限流通过后，服务从 Redis 日计数器生成候选订单号。

接着请求线程调用生产者发送 RocketMQ 事务消息。Broker 先保存消费者不可见的半消息；生产者客户端随后触发本地事务回调，回调执行 Redis 准入 Lua。因此真实顺序是“半消息在前、Lua 预占在后”。脚本先检查重试时长参数和活动元数据 `status/beginAt/endAt` 是否齐全，再要求状态为 `ACTIVE`，用 Redis 秒级时间检查是否未开始或已结束，随后检查快速库存是否大于零。再查旧的已购用户 Set 和新的用户到订单 Hash，任一个已有该用户都拒绝。通过后才 `DECR` 快速库存，把用户加入旧 Set，把“用户 ID → 本订单 ID”写入预占 Hash，把单笔状态 Hash 写成 `PROCESSING`，包含订单、用户、券、创建/更新时间和对账次数；对这笔处理中状态执行 `PERSIST`，再把订单 ID 加入待检查 ZSet，score 为 `当前 Redis 秒 + staleAfter 秒`，默认两分钟。脚本返回 0 表示准入成功，库存不足、重复、活动未开始、结束/暂停、元数据无效分别有明确返回码。

回调拿到 0 向 Broker 返回 `COMMIT`，明确业务拒绝返回 `ROLLBACK`，Lua 抛错、空结果或未知码返回 `UNKNOWN`。这是生产者给出的事务结论；Broker 完成提交处理后消息才对消费者可见，尚不能说订单已写入数据库。发送方法把回调结果交给 HTTP 服务；正常准入返回字符串订单号。发送调用异常或回调结果不明确时，入口还会按候选订单号查 Redis 单笔状态；若精确匹配且仍为处理中/成功，可以返回该订单号，否则返回暂不可用。这个兜底不能证明 Broker 一定完成了提交。

消费者收到可见消息后，先用**用户 ID** 取 Redisson 锁。拿不到锁会抛错等待 MQ 重试；消息字段不全也会抛错。拿到锁后先运行只读 Lua：检查订单是否在隔离集合中，单笔状态里的订单 ID、用户 ID、券 ID 是否与消息一致，`PROCESSING` 时还要求该券的预占 Hash 中这个用户指向本订单。状态为 `SUCCESS` 或 `FAILED` 的同笔重复消息直接确认；缺状态重试，归属冲突重试并最终可能进入死信。只有确认为本笔 `PROCESSING` 才调用数据库服务。数据库事务先插 `tb_voucher_order`；插入成功后对 `tb_seckill_voucher` 执行 `stock = stock - 1` 且 `voucher_id` 匹配、`stock > 0` 的条件更新，并以是否更新成功判断结果。扣减失败抛错，本地事务整体回滚。重复插入只有在已存订单 ID、用户 ID、券 ID 全一致时才当幂等成功并跳过再次扣库。

数据库方法正常返回、事务已提交后，消费者执行**写入** Lua：再次检查预占 Hash 仍把用户指向本订单，单笔状态三项归属也一致；若为 `PROCESSING` 则改 `SUCCESS`、更新时间、删失败原因；若已是同笔 `SUCCESS` 也返回成功。两种成功分支都会从待检查 ZSet `ZREM` **这个订单成员**，并给**单笔状态 Hash Key** `EXPIRE` 七天。这里没有给整个 ZSet 设置 TTL，也没有删除用户预占。标记失败会抛错重投；重投靠数据库同订单幂等判断避免第二次扣库。数据库明确库存不足、同用户同券已存在另一订单会先暂停活动再尝试精确释放本次预占；订单号属于其他记录则暂停、隔离并继续重试；数据库/Redis 暂时访问失败交给 MQ 重试。

标记成功之后，消费者调用 `WebSocketNotifier` 向 Redis Pub/Sub 发布普通用户、平台后台、所属商户后台的秒杀结果；订阅端按频道转给在线 WebSocket，会在发送前复核会话或权限。确定补偿成功的失败结果也会尝试发布。发布异常被捕获记录，不把已经完成的订单消费改成失败。它不是普通券发放的 Outbox 链路。HTTP 拿到订单号、MySQL 订单提交、Redis 状态变成功和用户屏幕看到提示，是四个不同时间点；用户最终应按订单状态接口核实。

**追问与回答**

- **HTTP 响应丢失后再次点击会怎样？** 第二次会产生新的候选订单号，但 Lua 看到同一用户已有预占或已购标记会拒绝，不会再扣快速库存。当前入口没有直接返回第一次订单号；若客户端也没保存首次响应，就缺少按“用户+券”公开找回旧订单号的入口。
- **半消息回查与消费重试有什么区别？** 回查决定生产端的半消息是否可投递；消费重试发生在消息已提交之后，处理数据库落单及 Redis 成功标记。`COMMIT` 只表示生产端提交结论，不能替代消费者数据库成功。

**核对备注**

逐项核对：[限流服务](../../../src/main/java/com/localdeals/service/SeckillTrafficGuard.java)/[限流 Lua](../../../src/main/resources/lua/seckill_traffic_guard.lua)、[HTTP 服务](../../../src/main/java/com/localdeals/service/impl/VoucherOrderServiceImpl.java)、[事务消息生产者](../../../src/main/java/com/localdeals/mq/SeckillOrderProducer.java)/[预占 Lua](../../../src/main/resources/lua/seckill_check.lua)、[订单消费者](../../../src/main/java/com/localdeals/mq/SeckillOrderConsumer.java)、[消费校验 Lua](../../../src/main/resources/lua/seckill_validate_reservation.lua)、[成功标记 Lua](../../../src/main/resources/lua/seckill_mark_success.lua)、[在线发布](../../../src/main/java/com/localdeals/websocket/WebSocketNotifier.java)/[订阅](../../../src/main/java/com/localdeals/config/WebSocketConfig.java)、[V2 迁移](../../../src/main/resources/db/migration/V2__voucher_order_constraints.sql)、[默认配置](../../../src/main/resources/application.yaml)。七天保留期来自 `RedisConstants.SECKILL_ORDER_STATUS_TTL_SECONDS`；本次仅静态核对，未启动 Broker/数据库或运行测试。

### Q06｜为什么准入要用一段 Redis Lua

**详细口述回答**

问题不只是“库存减一”。若把读库存、查用户、扣库存、写预占拆成多条命令，甲乙可能同时读到最后一张；同一用户的两次请求也可能都先读到“还没买”，然后各写一笔。Lua 让这些判断和写入在 Redis 执行期间不被另一条命令穿插。因此准入成功时，快速库存少一、旧已购 Set 增一人、预占 Hash 有这位用户对应的订单、单笔状态为处理中，四项是同一次脚本执行的结果。它把明显失败的请求挡在 MySQL 前，也给 Broker 回查留下能判断本地准入结果的记录。

脚本先读取活动元数据和 Redis 时间，检查状态、时间、库存、旧已购 Set 与精确预占 Hash，之后才开始写。必须提醒：Redis Lua 的“执行不交错”不等于执行中抛错会撤销已做的写入。现有脚本没有在写前验证所有相关 Key 的类型，也没有严格验证库存是整数。若 `DECR` 后，写 Set、Hash 或 ZSet 遇到错误，可能留下部分结果。此时不能只凭候选订单号盲目加库存；要先看预占是否已经写成，若连“谁占了这份库存”都没有记录，应暂停活动并人工盘点。

**追问与回答**

- **扣库存后状态写入失败，能自动释放吗？** 若用户到订单映射已写成、单笔状态仍准确且数据库没有该订单，还要确认旧消息不会合法提交，才有条件按本订单释放。若故障恰好发生在扣库存之后、预占映射之前，当前脚本没有足够信息把那一份扣减归属到某个请求，不能按订单号自动补。
- **怎样减少这种错误？** 在首个写入前检查库存是合法整数，检查 Set、Hash、ZSet 各 Key 类型和参数范围；写阶段只执行已验证的操作。更强协议还要记录可持久识别每次扣减的证据。这里是加固建议，当前没有完整类型预检。

**核对备注**

见 `seckill_check.lua`。原稿“Lua 原子所以可恢复”需限定为不交错，不能当作失败自动回滚。

### Q07｜为什么要记住预占属于哪一个订单

**详细口述回答**

旧的已购 Set 只存用户 ID，适合快速拒绝重复，但无法回答“这条 MQ 消息是不是当前占用库存的订单”。现在准入时还在每张券的预占 Hash 保存“用户 ID → 订单 ID”，并在单笔状态 Hash 写订单 ID、用户 ID、券 ID。消费前检查消息的三项字段和状态字段，还要求预占指向同一订单。补偿时也做同样比对，状态必须仍为处理中。这样即使消息乱序，也只处理或释放自己的预占。

例如 A 的预占后来明确失败，脚本加回 Redis 库存、删 A 的预占和已购 Set；普通用户又以 B 成功预占。A 的迟到消息到来时，A 的单笔状态是 `FAILED`，消费侧直接确认，不碰数据库。即使状态出现异常，预占 Hash 当前指向 B，A 也不能借用 B 的资格；A 的补偿脚本同样不会再增加库存。若订单号在数据库属于另一人，则不能靠这份 Redis 记录自动决定释放，要暂停并隔离。

**追问与回答**

- **归属冲突时各组件怎样处理？** Broker 回查若预占缺失或指向别的订单，返回回滚半消息；消费侧若状态与消息不匹配，抛错重试/死信，不能写 MySQL；补偿脚本遇到不同订单或隔离记录返回不执行。三者职责不同，不能说“都会回滚库存”。
- **已购 Set 还为何存在？** 它兼容旧预占/已购数据，并继续用于快速重复判断；新订单同时写 Set 和精确 Hash。释放本订单时脚本会在确认本笔归属后删除对应用户的 Set 成员。

**核对备注**

见 `seckill_check.lua`、`seckill_validate_reservation.lua`、`seckill_compensate.lua`、`SeckillOrderProducer.checkLocalTransaction`。

### Q08｜事务消息在这里保证到哪一步

**详细口述回答**

事务消息协调的是“Redis 是否接受预占”与“这条订单消息是否开始对消费者可见”。请求线程先让 Broker 保存半消息，消费者此时读不到；生产者客户端执行 Redis 本地回调。准入成功返回 `COMMIT`，明确业务拒绝返回 `ROLLBACK`，不确定返回 `UNKNOWN`，Broker 再根据结论处理半消息。若提交处理完成，消费者才可能收到消息并启动自己的 MySQL 事务。生产者的 `COMMIT` 不是数据库订单已经提交，更不是普通用户已经收到通知。

这样安排是为了避免普通消息的两个窗口：先预占再发普通消息，发消息失败会留下无消费渠道的预占；先发普通消息再预占，消费者可能先到而找不到合法预占。半消息让生产端能在回调后决定是否投递，仍要靠回查应对二次确认丢失。消费端仍会重试，也仍要在数据库里用唯一键和条件更新。

**追问与回答**

- **发送方法抛异常能断言什么？** 只能说请求方没有拿到可靠的发送结果，不能断言 Broker 一定没存半消息。入口会按候选订单号尝试确认 Redis 是否已经写出精确状态，但即使找到了也不能由此证明 Broker 已提交。
- **`UNKNOWN` 会一直回查吗？** 不能承诺无限。实际停止时间、最大次数和耗尽后的处置取决于 Broker 部署配置，当前仓库没有足够的运行证据给出值。自动回查停止后，若 Redis 仍有未决预占，需要按数据库与消息侧证据排查；当前对账不补发 MQ 消息。

**核对备注**

见 `SeckillOrderProducer` 与 RocketMQ 事务接口。Broker 参数及真实部署处置 **待部署配置核实**。

### Q09｜Broker 回查按什么决定消息去留

**详细口述回答**

Broker 没拿到明确二次确认时，会让生产者按半消息内容回查。代码先解析订单 ID、用户 ID、券 ID；消息缺字段或无法解析时返回 `ROLLBACK`。然后查这笔订单是否在隔离 ZSet 中：已隔离就回滚。再读这张券的预占 Hash，只有当前用户对应的订单 ID 正好等于半消息的订单 ID 才继续；缺失或指向另一笔就回滚。之后读取单笔状态里的 `status/orderId/userId/voucherId`，若状态本身没有读到，返回 `UNKNOWN`；若任一归属字段不一致，返回 `ROLLBACK`。

全部一致后，`PROCESSING` 或 `SUCCESS` 返回 `COMMIT`，`FAILED` 返回 `ROLLBACK`，其他状态值返回 `UNKNOWN`。Redis 读取抛错也返回 `UNKNOWN`，因为访问失败不等于准入失败。回查只决定半消息的投递，不查询数据库、不执行库存释放。若回查返回回滚，Redis 预占是否需要释放是另一条恢复问题，不能把消息回滚说成库存已加回。

**追问与回答**

- **为什么状态缺失与预占缺失返回不同？** 代码把预占缺失视作这条半消息没有当前所有权，直接回滚；已经读到匹配预占但状态本身不可见时证据不完整，继续未知。状态存在但其中订单、用户或券字段不匹配，则不能提交。
- **Redis 长时间不可用时怎么办？** 先确认 Broker 的实际回查限制和半消息状态。Redis 恢复后，若完整预占与待检查项仍在，可以用有开关控制的对账检查数据库；若 Redis 全丢，无法靠当前数据库订单自动重建所有在途申请。不能把 `UNKNOWN` 描述为无限保护。

**核对备注**

回查分支逐项见 `SeckillOrderProducer.checkLocalTransaction`；对账见 Q13。Broker 最大回查次数与耗尽行为 **待部署配置核实**。

### Q10｜Redis 已经扣过，数据库为什么还要防重复和超卖

**详细口述回答**

Redis 快速扣减让大部分失败请求不用进数据库，但消息会重复投递，Redis 与 MySQL 也不是一个事务。数据库写入因此仍独立检查两件事。`tb_voucher_order` 的订单 ID 是主键，V2 迁移又给 `(user_id, voucher_id)` 加唯一键，阻止同一普通用户同一秒杀券落两笔。`tb_seckill_voucher` 的扣减不是先读再无条件改，而是在更新时带 `voucher_id` 和 `stock > 0`，成功更新一行才算拿到数据库库存。

源码里的顺序是先插订单，再条件扣数据库库存，二者由 `createVoucherOrder` 的 MySQL 事务包住。库存更新失败会抛 `StockExhaustedException`，所以刚插入的订单也随事务回滚。若插入先撞唯一键，代码先按订单 ID 查已有记录：订单 ID、用户 ID、券 ID 都一致就说明同一消息重放，直接返回，不再次扣库；同用户同券已有另一订单是预占与数据库冲突；订单 ID 属于另一用户或券是更严重的编号冲突。两者不能混成普通幂等成功。

**追问与回答**

- **两个用户争数据库最后一张会怎样？** 条件更新由数据库对同一库存行串行处理。先更新成功的事务把库存减到零，后一个更新时 `stock > 0` 不再成立，受影响行数为零并回滚自己刚插的订单。
- **数据库约束能保证 Redis 一定正确吗？** 不能。它能阻止数据库超卖、重复订单，却不能撤销已经错误回补的 Redis 快速库存，也不能阻止被撤销预占对应的旧消费者稍后提交一笔本来不存在的数据库订单。这个跨存储竞争见 Q14。

**核对备注**

见 `VoucherOrderServiceImpl.createVoucherOrder`、V2 迁移。原稿中“扣减成功而插入失败也会回滚”的表述与当前先插后扣的执行顺序不符，已按源码改写。

### Q11｜MySQL 已提交但 Redis 标记失败后，三条恢复路径怎样区别

**详细口述回答**

消费者在数据库方法返回后调用 `markSuccess`。脚本要求预占 Hash 中该用户仍指向这笔订单，还要单笔状态的订单 ID、用户 ID、券 ID 完全相同。`PROCESSING` 才改成 `SUCCESS`；已经是同笔 `SUCCESS` 则幂等返回。两种成功都从待检查 ZSet 删除**订单成员**，给单笔状态 Hash 设置七天 TTL。若脚本返回失败或访问 Redis 抛错，消费者抛异常给 MQ 重试，不会释放快速库存。下一次消息重放通过数据库唯一键认出已提交的同一订单，只重试 Redis 标记。

普通用户主动查询是另一条路径。接口先读 Redis；如果看到属于自己的 `PROCESSING`，它再查同订单号、同用户、同券的 MySQL 记录。有正式订单就尽力标记 Redis 成功，失败也返回该用户的成功结果。若 Redis 状态不存在或访问异常，接口直接用订单号查数据库；查到自己订单就返回成功，但这条分支当前没有调用成功标记脚本。后台对账器则必须被显式开启，扫描到期 `PROCESSING` 后查数据库，精确命中时调用相同的成功标记脚本；标记失败会记录并等后续调度，不把数据库订单改失败。

**追问与回答**

- **为什么查询接口不能看 Redis `PROCESSING` 就一直回答处理中？** 数据库可能已经提交，只是 Redis 更新失败。按订单 ID、当前用户和券 ID 查到正式订单后，继续报处理中会误导用户。
- **查询接口看到 Redis `FAILED`，还查数据库吗？** 当前源码在有状态且不是 `PROCESSING` 时直接返回该状态；不会普遍地对每个 `FAILED` 再查库。这意味着异常跨存储交错仍可能使状态与数据库相反，不能宣称查询总能识别全部不一致。

**核对备注**

见 `VoucherOrderServiceImpl.querySeckillOrderStatus`、`SeckillOrderReconciler.repairSuccess`、`seckill_mark_success.lua`。原稿“Redis 缺失后回库并修复 Redis”过宽：该分支只回库返回成功。

### Q12｜哪些订单失败可以释放 Redis 预占

**详细口述回答**

释放是业务上的反向操作，不是数据库事务回滚。数据库事务里扣库存失败会自动回滚刚插入的订单；但 Redis 快速库存早在本地回调里减少了，MySQL 回滚不会自动把它加回来。消费者如果明确遇到数据库库存不足，或发现同一用户同一券已有另一正式订单，会先把这张券的 Redis 活动元数据改为 `SUSPENDED`，阻止新准入，然后执行精确补偿 Lua。脚本检查订单不在隔离 ZSet 中、用户当前预占仍指向本订单、单笔状态仍为 `PROCESSING` 且订单/用户/券字段相符。通过才给快速库存 `INCR` 一次，删除该用户的预占 Hash 字段和旧已购 Set 成员，把单笔状态改为 `FAILED`、写失败原因、从待检查 ZSet 删除本订单成员，并给单笔状态设置七天 TTL。第二次调用见到同笔 `FAILED` 只清理旧待检查成员和刷新 TTL，不再增加库存。

对账器的释放条件不同：它先查询写库。若确认没有本订单，也没有同用户同券的另一订单，并超过默认 15 分钟最终期限，只有自动补偿开关开启才释放；没到期仅把检查时间后移。若查到同用户同券的另一单，可暂停活动，再按补偿开关决定是否释放当前多余预占；订单号被别的记录占用则暂停、隔离，绝不自动补。数据库查询失败只表示没有答案。任何归属不匹配、Redis 脚本返回不匹配也不能强行加库存。

需要保留一个重要边界：即使对账器当时查到数据库没有订单，也可能有一个已经过了 Redis 验证、正在未提交数据库事务里的消费者。用户锁若因长暂停失效，对账补偿后该消费者可能恢复并提交。因此现有超时补偿是有条件的恢复措施，不能保证补偿成功就绝无迟到订单。若要严格防止，须让消费者和取消方在同一数据库申请记录上争先后；这不是当前实现。

**追问与回答**

- **A 失败后 B 接着预占，A 再补偿会怎样？** A 的用户到订单映射已删除，B 成功预占后映射指向 B；A 的补偿检查不通过，不会再给快速库存加一，也不会删 B 的成员。
- **“数据库查不到”与“数据库访问失败”为什么不同？** 前者是在查询正常完成后的一次观察，仍要考虑未提交事务和最终期限；后者连观察结果都没有，绝不能当成订单不存在。订单号归属冲突则是明确不安全状态，靠时间流逝也不能自动释放。

**核对备注**

见 `SeckillOrderConsumer.handlePermanentFailure`、`SeckillOrderReconciler.handleAbsent/handleUserVoucherConflict`、`seckill_compensate.lua`。消费者明确永久失败的补偿不受“对账自动补偿”开关控制；对账补偿受该开关控制。

### Q13｜后台怎样发现长时间没有结果的秒杀订单

**详细口述回答**

准入脚本把每笔 `PROCESSING` 订单 ID 加到全局待检查 ZSet，score 是 Redis 当前秒数加 `staleAfter`，默认两分钟。后台定时器只有显式开启 `reconciliation.enabled` 才运行。它按 score 找到到期的有限数量订单，**扫描并不删除成员**。处理单笔先拿订单级调度锁，读单笔状态以找到用户，再尝试拿与 MQ 消费者同一把用户锁。状态缺少可信用户时无法安全共用用户锁，当前会把 ZSet 成员的 score 延后，避免坏数据一直卡在本批开头；归属明显错误则隔离。

拿到共享用户锁后，认领 Lua 再核对单笔状态、订单/用户/券三项字段、精确预占、隔离标记和当前到期 score。认领成功会增加单笔状态中的 `reconcileAttempts`，把**这个订单成员的 score** 改成 `Redis 当前秒 + retryDelay 秒`，默认一分钟，作为下一次检查时间；不是给整个 ZSet 设置 TTL，也不是删成员。随后服务用写库查订单 ID，若有订单并且用户和券匹配，就标记 Redis 成功；若订单 ID 被别人占用，暂停券并隔离。按订单 ID 未查到时还查同用户同券的订单：有另一笔就按冲突处理；两处都没有才按年龄、补偿开关判断延后或精确释放。查数据库报错时记录失败、保留待检查状态，不能当“未下单”。

开启对账并不意味着它会重新发送 MQ 消息。默认三个相关开关——对账、自动补偿、启动索引回填——均关闭。启动回填只会利用还在 Redis 的精确处理中状态补缺失索引，不会从零重建丢掉的单笔状态。

**追问与回答**

- **扫描后进程退出会丢单吗？** 扫描不删成员；认领成功也只是把该成员 score 延后。任务退出后，到新的到期时间仍可被捞到。状态成功、失败或隔离时，相关脚本才按各自条件删待检查成员。
- **为什么不能到十五分钟就说订单绝无可能提交？** 一次正常查询只能看见当时已提交的数据，看不见另一个尚未提交但已经越过 Redis 校验的消费者。锁失效交错下，超时释放和迟到提交仍可并存。默认关闭自动补偿正是需要谨慎上线的一项控制，但开关本身不是证明。

**核对备注**

见 `SeckillOrderReconciler`、`seckill_reconcile_due.lua`、`seckill_reconcile_claim.lua`、`seckill_reconcile_defer_unresolved.lua`、`SeckillProperties` 和 `application.yaml`。本次未运行定时任务。

### Q14｜用户锁解决了什么，还留下什么竞争

**详细口述回答**

MQ 消费者按用户 ID 加 Redisson 锁；对账器处理订单时先用订单级锁避免多个调度实例抢同一项，再用同一用户锁，尽量不要一边落库一边把同用户的预占认定为超时。消费者用不等待的 `tryLock`，拿不到就抛错让 MQ 重试；对账器拿不到会延后该订单的检查。锁按用户而不是整张券，是为了让不同用户仍能并发落单。

但锁不把 Redis 和 MySQL 合成一个事务。消费者验证 Redis 时持锁，开始 MySQL 事务后若线程长暂停或续期失效，锁可能失效。对账器此时拿锁，读数据库看不到未提交的订单；若超过期限且自动补偿开启，便把 Redis 预占改失败、加回快速库存。旧消费者恢复后，如果数据库尚无同用户同券订单且库存大于零，插入与条件扣减仍可能提交。之后它的 Redis 成功标记会因预占已删、状态已失败而失败；MQ 重试看到 `FAILED` 可能直接确认。于是正式订单和 Redis 失败状态可以冲突。数据库唯一键只防重复，条件更新只防负库存；Redis 条件脚本只防误操作另一笔预占，它们不能共同阻止这个迟到提交。

如果产品要求“取消完成后旧消费者绝不能再落单”，应新增数据库申请状态，消费者在订单事务里锁定并把 `PENDING` 条件改为 `COMMITTING/COMPLETED`，取消方竞争同一记录并只能将 `PENDING` 改为 `CANCELLED`。谁先取得并提交该状态，另一方必须据此退出；Redis 再反映结果。当前只有锁和两边各自的条件，尚无这项数据库裁决。

**追问与回答**

- **续期失败与拿锁失败有什么区别？** 拿锁失败时消费者尚未读写本笔数据库，可以直接重试。续期失效发生在已进入临界区后，另一个执行者可能并发作出相反决定，此时不能用“重试即可”概括。
- **单人两条重复消息是否也有风险？** 用户锁减少同一用户两条消费的交错；即使锁失效，数据库主键和 `(user_id,voucher_id)` 唯一键仍挡重复订单，重复消息需要按现有订单三项字段判断是否同笔。但这不处理补偿与首次提交的跨存储竞争。

**核对备注**

现有行为见 `SeckillOrderConsumer`、`SeckillOrderReconciler`、`VoucherOrderServiceImpl` 和 V2。数据库申请状态是尚未实现的方案；原稿“下层约束兜住锁失效后的全部一致性”已纠正。

### Q15｜Redis 全部丢失后能恢复多少

**详细口述回答**

已经提交的 `tb_voucher_order` 订单和 `tb_seckill_voucher` 数据库库存仍在 MySQL，知道订单号的普通用户可以通过状态接口查到属于自己的正式订单。非测试环境启动时，初始化器会读取秒杀券记录并验证数据，然后补 Redis 里缺失的快速库存与活动时间元数据，让新准入有基本字段。但这不等于把丢失前正在处理的请求恢复了：每用户当前占的是哪个订单、单笔 `PROCESSING` 状态、待检查索引、隔离和暂停原因没有完整数据库副本；启动回填也依赖仍存在的状态 Hash。

所以全量丢失后不能只把 MySQL 剩余库存写入 Redis 就立即放量。已成功用户的旧已购 Set 若没重建，可能再次通过快速查重；尚未消费的旧 MQ 消息没有原预占，会在消费前校验失败或重试。实际恢复要先暂停新流量，核对正式订单、数据库库存、Broker 在途消息和可恢复记录，明确处置旧预占后再开放。当前仓库没有一键无损恢复这批进行中申请的能力。

**追问与回答**

- **数据库订单能重建已购 Set 吗？** 已成功订单可以作为重建已购用户的依据，但当前启动初始化器没有完整重建旧 Set，也推不出那些尚未提交的预占应该继续还是释放。
- **待检查索引回填能救全量丢失吗？** 不能。它只扫描 Redis 中仍存活的单笔处理中状态并补 ZSet 成员；状态也丢了就没有要回填的订单归属。

**核对备注**

见 `SeckillVoucherRedisInitializer`、`SeckillProcessingIndexBackfillRunner`；全量丢失恢复是源码边界分析，本次未做故障演练。

### Q16｜订单号怎样生成，有哪些边界

**详细口述回答**

当前生成器拿本地时间计算相对秒数，左移 32 位；再对 Redis 中按日划分的 `icrorder:yyyy:MM:dd` 计数 Key 执行 `INCR`，把返回计数直接与时间部分按位或。代码期望序列占低 32 位，却没有把它截到 32 位，超限后还可能污染时间部分。跨实例共享计数器能减少同一时间的重复分配。HTTP 和 WebSocket 把订单号转成十进制字符串；Redis Lua 也把它当字符串存取和比较，因为浏览器普通 JSON 数字和 Lua 双精度数都不能安全表示所有 Java 64 位整数。

当前实现有边界：它调用本地时间两次，按 UTC 偏移解释本地日期时间来算秒，又用本地日期分日计数，跨时区配置和跨日瞬间需要谨慎；计数 Key 没有过期策略；也没有检查计数是否超过 32 位空间。代码直接按位或，没有掩码或拒绝逻辑。即使将来加掩码也只会截断位数，不保证唯一。例如时间高位同为 T 时，计数 1 与 `2^32+1` 的低 32 位都为 1，若高位同样是 T 就得到同一个号。Redis 当日计数丢失或时钟回拨也可能复用已发组合，需单独设计持久水位、拒绝/等待新时间窗或真正编码新号段。

**追问与回答**

- **为什么不能只加 `& 0xffffffff`？** 掩码保证低位不越界，但把 `2^32+1` 变回 1；若高位时间相同就直接撞号。应在分配时检查上限并拒绝，或保证新高位严格未使用且可跨重启保持。
- **与雪花算法如何取舍？** 当前方案依赖 Redis，却不用部署机器号；雪花算法可本地生成，但要保证机器号唯一并处理时钟回拨。两种方案都要明确故障与重启条件，不能只拿位数说安全。

**核对备注**

见 `RedisIdWorker`、`VoucherOrderServiceImpl`、`WebSocketNotifier`、`seckill_check.lua`。原稿把“检查上限并掩码”并列为安全方案不准确，已统一改为检测、拒绝或重新设计号段。

### Q17｜活动写库后 Redis 预热失败，接口会怎样

**详细口述回答**

创建秒杀券时，服务在 MySQL 事务里先保存券模板，再保存秒杀库存与时间记录。只有事务提交成功，注册的 `afterCommit` 回调才写 Redis 快速库存和活动元数据 `ACTIVE/beginAt/endAt`。这样数据库创建失败时不会提前开放一份 Redis 库存。相反的窗口是 MySQL 已经提交，但 Redis 预热失败。代码在 `afterCommit` 里捕获 `RuntimeException` 并记日志，异常不向上抛；因此就这个预热异常而言，调用方不会因它收到失败，HTTP 创建接口可按正常返回，而 Redis 元数据未就绪的秒杀请求会被 Lua 拒绝为初始化中/暂不可用。不能只凭“数据库不能回滚”推出 HTTP 一定成功；这里能这么说，是因为回调异常确实被捕获，还要以入口后续代码没有其他错误为前提。

进程内回调只尝试这一次，运行中没有这条预热的持久待办自动重试。下一次非测试环境启动，初始化器可按 MySQL 记录补 Redis 缺失的库存和元数据；依赖失败时可能阻止启动。它是缺项补齐，不会自动识别所有错误值，也不会重建丢失的在途预占或暂停原因。

**追问与回答**

- **为什么不在事务提交前写 Redis？** 若先开放快速库存，后面数据库券创建回滚，用户可能预占一个不存在的活动。提交后写避免这一边，却留下活动已入库而暂时不可售的窗口。
- **不想依赖重启如何改？** 在创建券的同一数据库事务写一条预热待办，后台按活动版本幂等重试，避免旧任务覆盖后续暂停或修改。这是建议，现有创建逻辑没有该待办。

**核对备注**

见 `VoucherServiceImpl.registerRedisPreheatAfterCommit`、`SeckillVoucherRedisInitializer`。已核对 `afterCommit` 的异常确实被捕获。

### Q18｜把 Redis 换成 Cluster 只改地址行吗

**详细口述回答**

不行。当前秒杀准入 Lua 一次访问快速库存、旧已购 Set、活动元数据、预占 Hash、单笔状态 Hash 与全局待检查 ZSet。Redis Cluster 要求同一脚本的所有键同槽；这些现有 Key 没有统一槽标签，直接切连接会遇到跨槽错误。成功标记、补偿、对账认领与隔离脚本也各有多 Key 操作，不能只修准入脚本。

可行的改造方向是先列出每段 Lua 的完整读写 Key，把单张券的库存、元数据、预占、订单状态和该券待检查集合放到同一活动槽。原来的**全局**待检查 ZSet 无法同时与每张券同槽；可改为每券索引，再用可重建的活动提示去找需要扫描的券。这样单券 Lua 的原子操作才仍成立。爆款券仍会集中在一个槽，若再拆库存桶，就必须重新设计跨桶的一人一单与总库存分配。当前没有完成这个迁移。

**追问与回答**

- **为什么不能给所有 Key 同一个标签？** 那确实能让脚本同槽，却把所有券聚到一个槽，失去 Cluster 分散不同活动负载的目的；并且所有相关脚本及历史数据都要迁移。
- **每券索引会不会漏单？** 活动提示若只当调度线索，必须能从每券的持久待检查项重建；不能让一个可丢失的全局提示成为唯一记录。迁移时还要处理旧全局成员与新索引的双写/切换，属于尚未实现的方案。

**核对备注**

见 `seckill_check.lua`、`SeckillOrderStateService` 和各 `seckill_reconcile_*.lua`。本题是迁移设计分析，不是当前 Cluster 支持声明。

## 三、身份、商户隔离与统一发券（Q19～Q28）

### Q19｜普通用户和后台员工为什么分开认证

**详细口述回答**

普通用户令牌代表平台使用者，后台令牌代表有管理权限的员工。路由进入不同的拦截链：普通用户会话从普通 Redis Key 读用户 ID 等信息，后台会话从后台 Key 读账号 ID 与签发时的凭据版本，再查 MySQL 员工是否启用、所属商户是否启用、员工角色和当前权限。随后两类身份分别放进不同的线程上下文。请求头格式和后台 `Bearer` 要求让协议更清楚，但它们本身不是授权依据；后台最终能做什么还要由权限代码和商户范围判断。

不能说“即使两个 token 字符串完全相同也绝不会冒用”。不同 Key 前缀阻止普通会话记录被后台解析器直接读取，但若两套命名空间**各自恰好存在同一字符串的有效令牌**，把这个字符串交给另一入口，解析器会按那一套存储找到其有效会话。当前实现没有把 token 本身加上不可跨类型使用的绑定证明，因此不存在无条件的“同字符串不可能跨身份使用”保证。实际安全依赖令牌随机性、存储隔离、路由鉴权、后台账号状态与权限重载；令牌泄漏仍须按对应体系撤销。

**追问与回答**

- **请求头、Redis Key 和权限检查各管什么？** 请求头让入口知道按哪种协议取令牌；不同 Key 空间避免把普通会话直接解析成后台记录；线程上下文避免业务代码混用身份；后台重新读账号/角色/权限决定该请求是否能操作。仅靠 `Bearer` 字样不构成安全保证。
- **验证码一次性与登录成功是一回事吗？** 不是。验证码校验并删除由 Lua 原子完成，避免并发重复消费；后续创建/读取用户与写会话不在同一个跨 Redis、MySQL 事务。若验证码已消费但后续登录失败，普通用户需要重新获取验证码。

**核对备注**

见 `WebConfig`、`RefreshTokenInterceptor`、`AdminSessionService`、`consume_login_code.lua`。原稿“相同 token 也不能跨空间冒用”论证过强，已删除绝对保证。

### Q20｜有后台权限为何仍可能越权访问另一商户

**详细口述回答**

RBAC 是“这个员工有无营销修改权限”的检查，不能从中推出他能修改哪家商户的活动。请求带一个商户乙的活动 ID，而员工属于商户甲时，若服务只按活动 ID 查，再根据角色允许写，就会越权。当前营销服务先根据后台身份确定可操作商户：平台员工需要显式传目标商户 ID，商户员工只能用自己所属商户 ID，请求若传别的商户就拒绝。然后按活动 ID 加商户 ID 查询和锁定记录，更新 SQL 继续带商户、旧状态或规则版本条件，并检查受影响行数。

同样的约束要覆盖店铺、券模板、营销标签、标签成员、批任务和查询列表。后台单发虽然能指定普通用户 ID，却仍须在已确定的商户活动范围内进行；若活动要求人工标签，还要核对该普通用户与商户的有效标签关系。在线秒杀提示也按券所属店铺查商户，再发到对应后台频道，发送时重新核对员工会话、商户和实时订单权限。

**追问与回答**

- **甲员工提交乙的活动 ID 会怎样？** 角色权限可能允许“管理营销”，但带甲商户 ID 查询乙活动查不到；后续有条件更新也不应影响乙活动。对外可用同一种不存在或无权错误，避免泄露乙是否有此资源。
- **哪些入口容易漏范围？** 列表/分页计数会漏商户过滤，详情会直接按主键查，更新可能只在前置 Java 判断而最终 SQL 不带范围，批任务结果查询和 WebSocket 广播也容易漏。测试应准备甲乙两个商户及资源，逐一尝试跨商户读取、更新和通知订阅。

**核对备注**

见 `MarketingAdminService.resolveMerchant`、`VoucherCampaignMapper`、`AdminCatalogService`、`SeckillWebSocketHandler`。批量导出不是本项目已实现的入口，不列为现有覆盖。

### Q21｜停用员工或撤权后，旧会话何时失效

**详细口述回答**

后台 Redis 会话存账号 ID 和签发时 `authVersion`，不是把权限名单永久塞进 token。每次后台 HTTP 鉴权会重新读取员工、商户、角色和权限：员工或商户已停用时解析失败；改密提高数据库凭据版本后，旧会话里的版本不匹配会被删除；角色权限改变后，下次解析得到新权限，缺少接口要求的权限就拒绝。这些变化的通常生效点是**下一次鉴权**，已通过鉴权并在执行中的请求不会被自动撤销。WebSocket 后台连接在发送订单事件前也重新解析会话与实时订单权限，发现无效会关闭或跳过，但空闲连接不会因为数据库更新瞬间自动断开。

若要求“撤权事务提交后，旧权限绝不能再提交任何新写入”，只在高风险服务提交前再查一次仍不够：查完与业务提交之间，撤权可能先提交。要做到严格排序，业务写入和撤权需要在数据库里竞争同一账号或商户的授权版本行。业务事务锁住并校验版本，持锁直到写入提交；撤权事务也锁同一行并更新版本。业务先拿锁就先提交，撤权随后生效；撤权先提交则业务读到新版本而拒绝。该协调方案尚未实现，不能把现有“下一鉴权点生效”说成严格即时撤权。

**追问与回答**

- **凭据版本和权限重载能互相替代吗？** 版本用于一次性使改密前的令牌失效；每次重载角色权限用于发现新撤销或赋权。若只存旧权限快照，撤权要等令牌过期；若只重载而不比版本，改密后拿旧令牌仍可能解析成新主体。
- **提交前重查为何仍有竞态？** A 事务检查版本仍旧，B 撤权事务提交，A 随后提交。两次读取都可能正确，却不满足“B 提交后 A 不能写”的要求；必须让两个事务在同一持久行上建立明确先后关系。

**核对备注**

见 `AdminSessionService`、`AdminManagementService`、`SeckillWebSocketHandler`。数据库授权版本竞争是设计建议，不是当前功能。

### Q22｜请求身份放在 ThreadLocal 有什么风险

**详细口述回答**

ThreadLocal 让同一请求线程里的业务服务能拿到已经认证的普通用户或后台员工，但服务端线程会复用。若前一个请求结束时没 `remove`，下一请求可能误读到旧身份。当前普通用户与后台员工使用不同容器，各自拦截器在请求完成回调清理；身份恢复过程中遇到异常也要清掉可能残留的上下文。正常结束、业务异常和拦截器提前拒绝都应按实际拦截链检查清理路径，而不能因为“通常有 finally”就假定安全。

异步任务、MQ 消费线程不是原 HTTP 线程，不能直接取原来的 ThreadLocal 作为授权依据。若任务要记录发起人，应把操作员工 ID、商户 ID、规则版本等必要字段显式存入任务；执行时涉及敏感操作，还要按当前账号/权限重新判断或采用受控的服务身份。把整个可变权限快照隐式复制给线程池会让撤权后任务继续使用旧权限。

**追问与回答**

- **为何用 `remove` 而不是设成 null？** `remove` 删除当前线程条目，明确结束这次请求身份，避免线程池复用时残留；设置 null 仍可能留下条目且更易掩盖遗漏的清理路径。
- **怎样验证？** 用同一测试线程依次模拟成功、401、Redis 访问失败和业务异常请求，在第二次请求开始前检查两种身份容器均为空。现有测试文件可参考，但本次文档修改没有运行测试。

**核对备注**

见 `RefreshTokenInterceptor`、后台认证拦截器、`UserHolder`、`AdminPrincipalHolder`。普通用户与 MQ 消息消费者在本文分别称呼，避免“消费者”一词混淆。

### Q23｜用户领券、后台单发、批量和每日奖励怎样共用发放逻辑

**详细口述回答**

四个入口确定“给谁、由谁操作”的方式不同，最后才汇入同一个发放服务。普通用户主动领取或领取每日签到奖励时，活动 ID 来自路径，`expectedRuleVersion` 来自请求，领券用户 ID 由普通用户登录态确定，不能由客户端随意指定。后台单发时，活动 ID 来自路径，请求可指定**实际领券普通用户**的 `userId`、目标 `merchantId` 和预期规则版本；控制器从后台登录态取**操作员工** ID。平台员工必须明确指定目标商户，商户员工只能用自己的商户，不能靠请求字段越界。批量发放创建任务时，请求带目标商户、请求 ID 和规则版本，任务服务记录活动、商户、操作员工与标签；后台快照后，逐条从 `tb_voucher_batch_item.user_id` 取得真正领券用户，不是当前操作员工。这里的商户是活动及标签的归属范围，普通用户本身不被简单地等同于“属于该商户”。

发放核心先由服务端设置来源和幂等身份：普通领取、后台单发、批量发放用 `ONCE`，每日奖励用服务端上海业务日期组成 `TASK_REWARD:DAILY_SIGN_IN:日期`。新事务先核对是否已有同活动、同用户、同幂等身份的权益，再锁活动行并复查；按来源允许的领取方式、活动状态与时间、规则版本、券是否有效及同商户关系校验。活动要求人工标签时，还锁定标签和该用户的标签成员，确认仍有效。之后条件增加 `granted_count`，插入 `tb_voucher_grant`，并在同一 MySQL 事务插入通知 Outbox。`tb_voucher_grant` 的一行才表示这个普通用户实际得到券；批任务 Item 只记后台执行进度。秒杀的 `tb_voucher_order` 是另一条限量下单链，不复用这套普通券权益记录。

**追问与回答**

- **为什么不能说四个入口都从当前登录人取领券用户？** 后台单发的登录人是员工，请求另指目标普通用户；批量任务的目标来自名单明细。把员工 ID 当普通用户 ID 会发错人；把客户端随意传的商户 ID 当身份会越权。
- **券 ID 与活动 ID 怎样区分？** `tb_voucher` 是券模板，`tb_voucher_campaign` 是某商户为该模板建立的发放活动，控制模式、时间、额度与目标标签；`tb_voucher_grant` 记录某位普通用户因这次活动得到哪张券。一个活动 ID 不能随意拿来代替券 ID。

**核对备注**

见 `VoucherCampaignController`、`MarketingAdminController.grant`、`VoucherCampaignUserService`、`VoucherBatchJobService`、`VoucherGrantTransactionService`、V9～V11。原稿“所有用户 ID 都由当前登录人决定”已改为按入口分别说明。

### Q24｜发券前先查重为什么还需要数据库唯一键

**详细口述回答**

两个请求可以同时查到“这个用户还没有权益”，然后都尝试发。发放服务外层不带事务，先做一次快速查重；真正发放在 `REQUIRES_NEW` 新事务中，再查一次、锁住这次营销活动行、锁后再查一次。锁让同一活动的额度与规则校验尽量串行；条件更新要求活动仍是目标商户和券、状态时间版本仍合适且额度未满，只有更新一行才占到一个名额。随后插 `tb_voucher_grant`，V10 的 `(campaign_id,user_id,idempotency_key)` 唯一键挡住同一用户同一领取身份重复权益。计数增加和权益插入在同一事务中，插入撞唯一键会连计数一起回滚；事务退出后外层才按幂等键重读已有权益。

这三道检查不能互相替代：活动锁和条件更新保护两名不同普通用户争最后一个额度；权益唯一键保护同一普通用户的重复请求。但重读的**返回结果**还受事务快照影响。MySQL 可重复读下，锁前普通查询可能建立旧快照，锁后再次普通查询不一定看到另一个事务刚提交的权益。若竞争方先用尽额度，后一个请求甚至可能在插入前就报额度不足；即使唯一性仍成立，也不保证每次重复请求都能返回已有权益。批任务外层事务的旧快照会放大这类返回语义风险。

**追问与回答**

- **同用户同时领取会多加活动计数吗？** 最终唯一键只允许一份同幂等身份的权益；若第二个事务已经增加计数又撞唯一键，整笔新事务回滚，计数不会多加。但第二请求也可能先遇到额度或规则拒绝，不能保证总返回“已领取”。
- **怎样稳定返回已有权益？** 可以在独立、较新的读取事务中按唯一键查，或采用合适的当前读；要同时审视外层事务是否持有旧快照。这里是进一步加固返回语义，不是当前已实现保证。

**核对备注**

见 `VoucherGrantService`、`VoucherGrantTransactionService`、`VoucherCampaignMapper.incrementGrantCount`、V10 迁移。快照交错是源码与隔离级别推演，未当作已发生事故。

### Q25｜批任务逐人发券用了怎样的事务边界

**详细口述回答**

后台 `processNextBatch` 本身有一个外层 MySQL 事务。它锁住可运行的任务行，必要时把任务从 `READY` 改成 `RUNNING`，再锁本批 `PENDING` 明细，逐条调用发放服务。每位普通用户的发放核心用 `REQUIRES_NEW` 开独立物理事务，原外层事务会被挂起：单人的活动计数、权益和通知待办可以一起提交或回滚。发放结果返回后，外层才把 Item 写成 `GRANTED`、`IDEMPOTENT`、`SKIPPED` 或 `FAILED`，最后统计是否有待处理项并把任务改成完成或部分失败。因此单人权益已提交、外层 Item 更新却回滚时，下一轮可能看到 Item 仍待处理；必须靠同一权益幂等键读出已发事实，再更新 Item，而不能以 Item 为“尚未发券”的证明。

`REQUIRES_NEW` 缩小了每位用户权益事务，却**没有**把整批外层事务消掉。外层持有任务和 Item 行锁及数据库连接期间，内层另取连接，还可能锁活动、标签和成员。连接池容量不足时，多个批工作器都占着外层连接等内层连接会有饥饿/超时风险。若未来外层和内层碰巧要锁同一行，外层挂起也不会释放锁：内层等外层释放，调用线程又等内层返回，可能一直等到锁超时；数据库未必能识别应用调用栈上的等待边。当前已确认外层锁 Job/Item、内层锁 Campaign/Tag/Member；“同一行自阻塞”是扩展代码后需防范的风险，不能说当前已发生。

**追问与回答**

- **单人已发，批进度没提交，重试会多发吗？** 任务 Item 可能仍是 `PENDING`。发放服务会先查 `tb_voucher_grant`；看得见同活动、用户和 `ONCE` 的既有权益时返回幂等结果，不再增额、不再插通知待办，外层可把 Item 标为 `IDEMPOTENT`。若外层可重复读快照太旧，普通查询可能暂时看不见已提交权益；数据库唯一键仍挡第二份权益，但这轮 Item 未必顺利变为幂等完成，可能被记录成技术失败并需要重新读取/重试。
- **怎样降低外层锁与连接占用？** 可先用短事务认领一批 Item 并提交，释放任务锁；事务外逐人发；再用短事务按任务状态/版本写进度。要设计认领过期后的重试和幂等键，不能只是去掉注解。当前实现仍是外层整批事务。

**核对备注**

见 `VoucherBatchJobService.processNextBatch`、`VoucherGrantTransactionService.grantWithResult`。原稿将“逐人独立事务”解释成整个批处理没有长事务，已纠正。

### Q26｜名单变动、暂停和失败重试怎样影响批任务

**详细口述回答**

后台创建批任务时只在事务里保存 Job：商户、活动、操作员工、请求 ID、活动规则版本和目标人工标签，初始状态是 `SNAPSHOTTING`。它不会在 HTTP 创建那一刻展开全部用户。开启批工作器后，`snapshotOne` 锁住待快照 Job，用一次 `INSERT ... SELECT` 把当时有效的标签成员写成 Item，然后记录数量并改成 `READY`。所以创建请求至快照执行之间成员变化会影响最终名单。真正逐人发放时，核心事务还会锁定并复核当前标签和成员状态、有效期、活动状态、规则版本、时间及额度：快照后被移除的人，若此前未获券，会被跳过；已有权益则可能按幂等结果返回。

运行批次时 Job 和本批 Item 由外层事务锁住。暂停请求要更新同一任务状态，通常会等当前批释放锁后才能生效，因此不能承诺即时中断已开始的一批。业务上稳定不满足条件的 Item 标 `SKIPPED`，技术异常标 `FAILED`；`retryFailures` 只把失败项重置成待处理，不盲目重做已发、幂等或跳过项。若活动规则版本变化，旧 Job 仍带创建时版本，逐人发放会拒绝，应该新建使用新规则的任务，不能把旧任务悄悄改口径。

**追问与回答**

- **重复提交创建请求会生成两个 Job 吗？** `(merchant_id,request_id)` 有唯一键。服务先普通查重，插入时用幂等插入，再按商户和请求 ID 锁定重读持久行；请求 ID 是 Job 创建去重，不代替每个用户的权益唯一键。普通预查在可重复读下也有旧快照风险，因此当前后续使用加锁重读。
- **暂停时当前批已给一部分用户发券怎么办？** 内层单人事务已经提交的权益不会因后来暂停撤回；当前外层批次继续完成/提交，暂停后阻止后续批。若业务要强制中途停，需要更细粒度认领和每人前重新检查任务状态，当前没有这项保证。

**核对备注**

见 `VoucherBatchJobService`、`VoucherBatchItemMapper.snapshotActiveMembers`、V11、`application.yaml`。Job 工作者默认关闭；本次未启动执行。

### Q27｜每日签到奖励如何保证同日一次、次日可领

**详细口述回答**

签到和领奖是两个动作。普通用户签到先在 MySQL 留下用户与业务日期的记录，V10 给 `(user_id,date)` 加唯一键；签到成功不会自动发券。领奖请求带活动 ID 和预期规则版本，用户 ID 从登录态来，发放服务用服务端 `Asia/Shanghai` 业务日期设定 `TASK_REWARD:DAILY_SIGN_IN:日期` 作为幂等身份，并在新事务里检查这位普通用户当天确实签到。活动还必须允许 `TASK` 来源，处于可发时间、额度与规则版本满足要求。成功后在同一事务增加活动已发数量、写 `tb_voucher_grant` 和通知待办。

同一天重试，活动 ID、用户 ID、幂等日期相同，权益唯一键只允许一份；第二天日期改变，可生成第二份权益。客户端即使修改本地日期，服务也按自己的业务时区生成日期。当前日期在发放服务准备命令时决定，请求跨午夜继续执行仍使用进入时那一天；午夜后重发昨天的请求会按今天检查签到，并非自动补领昨天。

**追问与回答**

- **应用时间与数据库时间是否完全同一个来源？** 任务日期由应用可注入时钟按上海时区给出；活动窗口的再次校验取数据库当前时间。部署时要保持时钟同步，临界点测试也应分别覆盖日期与活动时间。
- **要允许隔天补领怎么改？** 需服务端确定并签发可验证的任务日期或任务实例，并明确补领期限；不能直接信任客户端传任意日期。现行实现是执行日领奖。

**核对备注**

见 `BusinessDateProvider`、`VoucherCampaignUserService`、`VoucherGrantService`、`VoucherGrantTransactionService`、V10。已有任务契约测试，但本次没有运行。

### Q28｜写了通知 Outbox，普通用户就一定看到提示吗

**详细口述回答**

不能。发放普通券时，同一 MySQL 事务写活动已发计数、`tb_voucher_grant` 用户权益和 `tb_voucher_grant_notification_outbox` 的 `PENDING` 待办。这样数据库提交后，即使进程在发消息前退出，也还留着一条可查询的待办；事务回滚时三者一起撤销。通知工作器默认关闭，显式开启后才会按到期时间锁定有限条待办，用 `WebSocketNotifier` 向 `ws:voucher-grant:{userId}` 发布带稳定事件 ID 和权益 ID 的 `VOUCHER_GRANTED` 消息。发布调用未抛错，工作器再将待办标 `PUBLISHED`；Redis 发布失败则保留 `PENDING`，增加尝试次数并设置下一次时间。

这些是不同层次的结果：`PENDING` 表示数据库留下待办；`PUBLISHED` 表示这次 Redis 发布调用成功并且数据库标记提交；Redis Pub/Sub 订阅端收到后才可能按 userId 找本机在线 WebSocket；`sendMessage` 返回只说明服务端尝试把文本写给会话；浏览器实际收到、显示或用户已读，当前没有持久确认。若 Redis 已发布但数据库标记失败，外层事务可能回滚，下一轮重新发布，因而提示可重复。默认最大尝试次数是 10、退避最长 5 分钟，但“最大尝试次数”目前只是计数上限：查询 SQL 没按次数排除 `PENDING`，达到上限仍会被再次选中；没有自动失败终态，也不能称为送达保证。V11 没为旧权益回填通知待办，已有权益的幂等重试也会在创建待办前返回，所以旧权益缺待办时工作器无法凭空补发。普通用户要查是否真领到券，应看 `/voucher-grants/mine` 中的 MySQL 权益。

这条普通券通知与秒杀结果通知不同。秒杀消费者在标记订单结果后直接调用 Pub/Sub 发布，发布异常被捕获，不通过这张 Outbox 表；普通券的 Outbox 只保证发券事务内保留通知待办，不保证 WebSocket 在线或用户已读。

**追问与回答**

- **为什么可能重复提示？** Redis 已接受一次发布，但更新 `PUBLISHED` 失败或数据库事务回滚，待办仍是 `PENDING`；下轮再次发布。事件 ID 可供客户端去重，但当前没有持久的用户已读确认。
- **要支持离线补发还缺什么？** 需要持久用户收件箱、每用户游标/确认时间和按稳定事件 ID 去重，重连时按游标拉取；Pub/Sub 本身不保存离线消息。这属于下一阶段设计，不是现有能力。

**核对备注**

见 `VoucherGrantTransactionService`、`VoucherGrantNotificationOutboxService`/Mapper、`VoucherGrantNotificationOutboxWorker`、`WebSocketNotifier`、`WebSocketConfig`、V11 与 `application.yaml`。默认通知工作器关闭；本次仅静态核对，没有验证客户端实际收到。
