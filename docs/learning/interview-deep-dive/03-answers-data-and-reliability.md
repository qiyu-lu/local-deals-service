### Q29｜点赞接口为什么表达目标状态，而不是每调用一次就翻转

**口述回答**

“点赞”和“取消点赞”应表达客户端希望达到的最终状态，而不是把现状机械取反。因为客户端超时后无法知道服务端是否已提交，同一请求可能重发：若采用翻转，第二次会把第一次的成功结果撤销；采用目标状态后，已有关系再点赞、无关系再取消都只是无变化。当前实现以 MySQL 点赞关系为事实源，在同一事务里完成关系插入或删除，并且只有关系确实改变时才写一条正负增量待办；显示计数由后台异步聚合，所以关系可以已成功而计数短暂滞后。相关新链路已有实现，但默认关闭的开关表示尚未切流，不等于功能不存在。

**追问展开**

1. **追问一：响应丢失后重试点赞、重复取消点赞分别怎样保持幂等？关系变化与增量事件怎样同时提交？**

   **回答：** 点赞响应丢失后重试，唯一关系约束把第二次插入识别为“已经是点赞状态”；重复取消时，删除影响零行也返回“已经是未点赞状态”。只有插入或删除恰好改变一条关系时，才在同一数据库事务中追加 `+1` 或 `-1` 的事务发件箱（Outbox，持久待办）事件；任一步失败会整体回滚，避免“关系变了却没有增量”这一提交缝隙。

2. **追问二：点赞关系已改变但显示计数还没变，如何向用户解释？怎样区分合理异步滞后和真正丢失事件？**

   **回答：** 用户刚操作后看到旧计数，可以解释为“我的关系已提交，公共聚合值异步收敛”，客户端应优先正确呈现本人的状态。合理滞后要有上界和证据，例如待处理数量、最老事件年龄持续下降；若事件年龄越过告警线、关系与“已聚合计数＋未处理增量”的不变量长期不符，才是积压、毒事件或事件丢失，不能继续用最终一致性作笼统解释。

#### Q29-D1｜面试官追加深挖

**追问：** 用户先点赞请求 A，随后取消点赞请求 B，B 先完成，A 因网络延迟最后才到：目标状态接口还能保证用户最后一次意图吗？请区分同一请求重复的幂等性与相反操作乱序，并说明需要何种序号或版本约束。

**追问缘由：** 现有回答充分解释同方向重试，但目标状态并不自动解决相反意图的到达乱序。

**回答：** 不能。目标状态只解决“同一意图重复到达”：例如两次都要求点赞，第二次看到已经点赞便不再产生增量。但 A 和 B 是两个相反意图；若系统没有顺序信息，服务端只看到 B 先到、A 后到，A 最终仍可能把状态改回点赞。请求到达顺序不等于用户操作顺序，所以单靠“设为真/设为假”无法保证最后一次操作获胜。

要保留用户的最后意图，需要给同一“用户＋内容”的命令流增加可比较的单调序号。例如果 A 带序号 41、B 带 42，数据库除点赞关系外还要保留最后接受序号；即使 B 先完成并删除关系，也必须留下版本水位或未点赞墓碑。A 后到时发现 `41 <= 42`，只返回当前状态，不改关系，也不写反向增量。序号判断、关系变更、最后序号和增量待办必须在同一事务中提交；请求标识则另用于识别同一请求重试。

客户端本地序号只在单设备单会话内可比较，多设备各自从 1 开始会冲突。跨设备可采用服务端授权的版本加条件更新：客户端携带读取到的期望版本，版本不符返回冲突并要求刷新；或者把该业务键的命令交给一个服务端串行序列器。现有材料没有显示已实现上述序号或版本协议，因此当前能声称的是同方向重试幂等，不能声称相反操作乱序时仍保持客户端最后意图。

### Q30｜点赞关系、聚合计数和 Redis 热榜之间如何对账

**口述回答**

我会把三层数据按权威程度分开：点赞关系是用户行为事实；MySQL 聚合计数是由增量事件维护的持久读模型；Redis 热榜是从持久计数整代构建的可丢失派生视图。对账不能直接要求“关系数等于聚合数”，因为切换前可能已有无法归属到当前关系行的历史点赞，还可能存在尚未处理的增量。正确做法是显式保留历史偏移，并核对“聚合计数＋未处理增量＝历史偏移＋当前关系数”；事件清空后才化简。热榜再抽样比对数据库排序、成员、分数和代号，而不是反过来拿缓存修正事实源。

**追问展开**

1. **追问一：存在未处理增量和历史不可归属点赞数时，应该建立什么等式检查三者关系？**

   **回答：** 对每篇内容核对：`持久聚合值 + 待处理增量之和 = 历史偏移 + 当前有效关系数`。历史偏移只承担旧数据迁移边界，不能被新写入随意修改；当未处理集合为空时，应满足`聚合值 = 历史偏移 + 关系数`。Redis 只需与最近一次完整构榜所读取的持久快照一致，不能要求它在每次点赞后实时相等。

2. **追问二：后台先更新聚合再标记事件，中间失败怎样避免多算？永久坏事件卡在批次前部时，当前恢复上限是什么？**

   **回答：** 后台批次在同一个 MySQL 事务中先锁住待办，按内容合并增量，更新聚合值，再把这一批精确标成已处理；更新后若标记失败，事务回滚，所以重试不会在“计数已加、标记未写”状态上再次累加。当前没有按毒事件隔离、跳过或死信的完整机制，永久非法增量位于批次前部时可能令该批反复回滚，这是现行恢复能力的上限和应告警的边界。

#### Q30-D1｜面试官追加深挖

**追问：** 对账先读关系数，再读聚合值，最后读未处理增量，期间后台恰好提交一批聚合，会不会得到假不一致？请用一条 +1 事件手推，并说明怎样取得可比较的同一数据库视图。

**追问缘由：** 现有等式成立依赖一致观察时点，分步读取的并发前提尚未展开。

**回答：** 会。假设历史偏移为 0，某次点赞关系已经提交，所以关系数是 11；聚合值仍是 10，另有一条未处理 `+1`，此时等式为 `10 + 1 = 11`。对账任务先读到关系数 11，再读到聚合值 10；随后后台事务把聚合值加到 11，并把这条事件标成已处理，二者原子提交；对账任务最后读到未处理增量 0，于是拼出 `10 + 0 != 11`。每次读取都是真值，组合起来却跨了两个提交时点，产生假不一致。若后台恰好在另外两个读取间提交，也可能偶然仍相等，不能据此认为分步读安全。

可比较的做法是让三项查询在同一个数据库只读事务、同一连接和同一个一致性快照中完成，例如在可重复读下先显式建立一致快照，再全部使用非加锁一致性读。这样后台提交若发生在快照前，会同时看到聚合 11 和未处理 0；若发生在快照后，则同时看到聚合 10 和未处理 `+1`。不能中途混入读取最新版本的加锁查询，也不能把三个查询拆到不同事务。在读已提交隔离级别下，每条语句通常可取得新快照，可改成单条 SQL 在一个语句快照内计算，或通过锁定并按与聚合器一致的顺序串行化。现有材料给出了等式，但尚不能确认线上对账已采用哪一种快照方案。

**核对依据**：[点赞对账与聚合说明](../flow-notes/04-like-and-hot-rank.md)、[增量批处理事务源码](../../../src/main/java/com/localdeals/service/BlogLikeOutboxBatchService.java)、[聚合批次测试](../../../src/test/java/com/localdeals/service/BlogLikeOutboxBatchServiceTest.java)

### Q31｜为什么热榜先写临时榜，再发布一代完整快照

**口述回答**

如果直接清空并逐条写在线榜，读请求会依次看到空榜、半榜和最终榜；两个重建任务交叉时，还可能把不同数据库时刻的数据混成一份结果。当前做法先从 MySQL 按点赞数和内容标识稳定排序，完整写入某一代临时有序集合，最后用脚本一次发布该代及元数据。分布式锁减少并行重建，代号栅栏决定谁仍有发布资格，临时榜隔离未完成数据，三者解决的问题并不相同。读取先检查就绪状态，再在取成员前后复核代号和数量；跨越切版或元数据异常就视为未命中并回退。

**追问展开**

1. **追问一：分布式锁、临时榜和版本栅栏分别防止什么问题？旧任务晚完成怎样避免覆盖新榜？**

   **回答：** 分布式锁减少正常情况下的重复数据库扫描，但锁可能过期或旧任务可能晚完成，不能单独保证新旧顺序；临时榜使构建过程对线上读不可见；单调代号和发布脚本组成版本栅栏，只有当前代才能替换在线榜，旧任务即使拿到旧数据晚到，也只能删除自己的临时结果而不能覆盖新榜。

2. **追问二：同分内容如何保持 Redis 与 MySQL 顺序一致？读取跨越切版时又如何判断结果可信？**

   **回答：** 数据库以“点赞数降序、内容标识降序”解决同分顺序；Redis 分数保存点赞数，成员使用定长十进制表示，因此同分时的反向字典序与数值标识降序一致。读取先取元数据和分页成员，再复核代号、总数及集合基数；若切版发生在两次核对之间，就放弃这一页，避免把旧成员和新元数据拼在一起。

**核对依据**：[热榜构建与读取说明](../flow-notes/04-like-and-hot-rank.md)、[热榜代际构建源码](../../../src/main/java/com/localdeals/service/BlogHotRankService.java)、[原子发布脚本](../../../src/main/resources/lua/blog_hot_rank_publish.lua)、[Redis 有序集合相同分数排序语义](https://redis.io/docs/latest/commands/zrange/)

### Q32｜有限 Top-K 热榜如何支持分页和故障回退

**口述回答**

Top-K 是容量有限的热门内容快照，不是完整结果集，所以分页只在已发布容量内可靠。当前读取把“命中”定义得较严格：元数据已就绪、未超过陈旧阈值、代号在读前后不变、集合基数一致、页内成员格式正确，才返回热榜页；尚未构建、过期、损坏或跨代都按未命中处理，由受并发保护的 MySQL 排序查询回退。已就绪的合法空榜以及页码超过当前榜单数量，则直接返回空页，不能误当故障。若热榜标识对应的正文已删除，当前会放弃整页热榜并回库，保证不把残缺页伪装成正常命中。

**追问展开**

1. **追问一：合法空榜、缓存尚未构建、榜单过期、当前页超出 Top-K 和正文缺失如何区分？**

   **回答：** “尚未构建”没有可信就绪元数据；“过期”有代号但发布时间越界；“损坏”包括成员格式、声明数量和实际基数不符；这些都回退数据库。合法空榜必须有一代明确发布的就绪元数据；页起点超过已发布成员数也是业务空页。Top-K 外的更深页本来不在缓存契约内，应查数据库，而不是把空数组解释为“全站再无内容”。

2. **追问二：榜单丢失后大量请求触发重建，如何限制重复工作与数据库压力？点赞数实时性和重建频率如何取舍？**

   **回答：** 当前热榜读取未命中会触发重建；本进程的“正在进行”标记只合并同一时段的重复触发，任务结束后会复位，后续仍可再次触发。分布式锁再把跨实例构建串行化；请求不等待构建，失败时走本实例的数据库并发许可。重建越频繁越新鲜，但数据库扫描、Redis 写入和切换次数越高；应按允许陈旧窗口、增量处理延迟和重建耗时共同定周期，并监控榜龄，而不是承诺实时排名。

#### Q32-D1｜面试官追加深挖

**追问：** 请分别判断：全站100条、缓存Top-K为20条时请求第3页（每页10条），以及全站只有15条时请求第3页，应该回库还是返回空页？元数据至少要表达什么，才能区分“超出缓存覆盖范围”和“业务确实没有更多”？

**追问缘由：** 主答中的超榜数量返回空页与追问答案中的Top-K外回库容易混淆，需明确两种边界。

**回答：** 第 3 页对应排名 21～30，页起点已经到 20；在 Top-K 为 20 的当前读取契约下，两种情况都越过缓存覆盖范围，因此当前路径都应回 MySQL，而不是直接采用缓存空数组。区别只在回库结果：全站 100 条时数据库返回第 21～30 条；全站只有 15 条时数据库查询确认没有更多，返回空页。这样“缓存没有这一页”始终只表示未覆盖，业务上是否没有更多由事实源裁决。

若以后希望在第二种情况省掉回库，可以扩展元数据语义，但要明确这是优化设计，不是当前路径。元数据应绑定同一代号、查询范围、发布时间和已发布成员数，并至少增加“本代结果完整”还是“达到 K 后被截断”的标志；不一定必须保存精确全站总数。完整标志为真且页起点已越过成员数，才能直接判定业务空页；截断标志为真时，越过缓存成员的页仍必须回库。读取还要复核声明成员数与实际集合基数，防止把损坏或跨代结果误判成完整空榜。

### Q33｜店铺详情采用什么缓存读写模式，请讲完整过程

**口述回答**

现行店铺详情入口使用旁路缓存（Cache-Aside Pattern）：应用先读 Redis，命中正常对象就返回；命中约定的空值占位则返回“不存在”，用较短寿命抑制同一不存在标识反复穿透；未命中或缓存内容损坏时，通过本进程请求合并和数据库并发许可回源 MySQL。查到实体后尽力写回带期限的缓存，查不到则写空值；Redis 读取或写入失败时，详情接口可在许可范围内直接读数据库。关键边界是数据库异常必须作为服务失败返回，不能伪装成“查无数据”并缓存，否则会把依赖故障放大为持续的错误空值。

**追问展开**

1. **追问一：旁路缓存（Cache-Aside Pattern）中，正常命中、空值命中、坏数据和 Redis 异常分别怎样处理？数据库异常能否写成空值？**

   **回答：** 正常对象命中后还要校验其业务标识与请求相符；空值只有精确符合占位协议才代表不存在。反序列化失败、对象标识错误等坏数据按未命中回源，并尝试用新结果覆盖。Redis 读异常跳过缓存但仍受回源许可约束，写异常不改变已查到的数据库结果。数据库明确返回空才可缓存空值；超时、连接失败或 SQL 异常返回服务不可用，不能写空。

2. **追问二：项目现行入口是否使用逻辑过期？如何区别“工具类中存在某方案”和“实际业务正在调用某方案”？**

   **回答：** 工具层还提供逻辑过期、互斥重建等通用方案，但“代码库中有工具”不等于“当前店铺入口采用”。沿调用点核对后，现行入口调用的是带真实过期时间的旁路缓存路径，正值和空值默认都有物理 TTL；没有读取逻辑过期包装、返回旧值并异步重建的业务调用证据。因此面试时只能把逻辑过期说成备选设计，不能说成当前实现。

### Q34｜先更新数据库，再删除缓存，还可能出现旧数据回填吗

**口述回答**

仍然可能。当前写路径是 MySQL 更新成功后尽力删除详情缓存，这能处理常见的“缓存已有旧值”，却无法封闭一个并发读写窗口：读请求先缓存未命中并读到数据库旧行；随后写请求提交新行并删缓存；最后较慢的读请求把手中的旧行写回，于是旧值在缓存寿命内再次可见。删除失败同样会保留旧缓存。当前靠过期时间最终收敛，没有延迟二次删除、变更订阅修复或按版本拒绝旧回填。因此应准确表述为旁路缓存的最终一致方案，而不是数据库与缓存强一致。

**追问展开**

1. **追问一：请给出读请求取到旧行、写请求提交并删除缓存、读请求最后回填的交错时序。**

   **回答：** 交错顺序是：读 R 发现缓存空；R 查询 MySQL 得到版本 1，但尚未回填；写 W 把 MySQL 更新为版本 2并提交；W 删除缓存；R 最后把版本 1写入缓存。W 的顺序本身没有颠倒，旧值仍被“迟到的读”复活。若 W 的删除 Redis 操作失败，则连这个特定交错都不需要，已有版本 1会继续存活。

2. **追问二：短 TTL、延迟二次删除、变更订阅与版本校验分别能改善什么，哪些仍不能无条件提供强一致？**

   **回答：** 短 TTL 缩短最坏陈旧窗口，但增加回源；延迟二次删除能覆盖部分迟到回填，却依赖延迟选择和执行可靠性；变更订阅能在提交后持续失效缓存，但仍有传输延迟、重复和丢事件要处理；版本校验能阻止低版本覆盖高版本，但需要把单调版本带到缓存并原子比较。它们都可改善最终一致，若没有读写事务、同步双写协议或版本化读约束，不能无条件宣称强一致。

**追问：** 如果删除缓存时连同版本也删掉，迟到的版本1发现缓存为空，原子版本比较还能阻止它写入吗？请说明版本水位或失效墓碑存在哪里、保留多久，以及它再次过期后的保证边界。

**追问缘由：** 现有回答提出版本校验，但未说明高版本证据在删除后如何继续存在。

**回答：** 不能。写请求把版本 2 的缓存实体和版本信息一起删除后，迟到读请求拿着版本 1 回填；原子脚本看到“当前键不存在”，若把不存在当作可写，就失去了比较对象，版本 1 仍会复活。版本校验有效的前提不是比较动作原子，而是较新的证据在比较时仍然存在。

### Q35｜同一个热点键的请求合并，与数据库并发隔离分别解决什么

**口述回答**

请求合并解决“同一个键”缓存失效时的重复工作：当前进程只让一个加载者访问数据库并回填，其他请求等待同一个任务结果。数据库并发隔离解决的是“所有受保护回源”对连接池的总冲击：每个应用实例只有有限许可，短时间拿不到就快速拒绝。二者维度不同，必须叠加；只合并无法阻止许多不同键同时回源，只设许可又会让同一热点占满全部名额。两者现在都是本 JVM 范围，不是集群全局限流，扩到十个实例后会有十组任务登记和十份许可。

**追问展开**

1. **追问一：加载者与等待者如何共享同一个任务结果？等待者超时是否应该取消任务或删除登记，为什么？**

   **回答：** 第一个请求原子登记一个未来任务并成为加载者，在自己的请求线程执行数据库查询；后来者发现已有任务，等待该任务完成并复用相同结果。当前加载者不设等待超时，等待者有短超时；等待者超时只返回服务不可用，不取消底层任务，也不删除登记，因为任务可能仍在为其他等待者和后续缓存回填产生正确结果。只有加载者结束后才按同一任务身份移除登记，避免误删新一轮任务。

2. **追问二：从一台应用扩到十台后，本地请求合并和信号量还保证什么？随机不存在 ID 的穿透又与单个热点有什么不同？**

   **回答：** 十台应用最多会对同一键形成十个加载者，数据库许可上限也近似乘十；它们仍能保护各自进程，却不等于全局只有四个回源。随机不存在标识是大量不同键，无法被单键合并；空值缓存只能抑制同一个不存在标识的重复访问。若攻击者不断换 ID，还需全局容量规划、入口速率限制或布隆过滤器等额外方案，当前详情路径并未因此自动获得保护。

### Q36｜发布探店内容后的粉丝动态扩散，有没有与点赞相同的持久恢复能力

**口述回答**

没有。当前发布内容时，正文和图片状态在 MySQL 事务中提交；事务提交后的回调再尽力更新作者热榜信息，并逐个把内容标识写入粉丝的 Redis 动态索引。这个扩散步骤没有与数据库同事务的持久待办，也没有重放消费者或从关注关系重建动态索引的任务。因此进程在提交后回调前退出、某个粉丝写入失败，正文仍然成功但对应动态可能永久缺失；关注关系或整个动态索引丢失也不会自动补齐。它与点赞“关系＋增量待办同事务、后台可重试”的恢复等级不同，只能说是提交后尽力扩散。

**追问展开**

1. **追问一：数据库提交后进程退出或某位粉丝写入失败，当前有没有待办可重放？关注关系和动态索引丢失能否自动补齐？**

   **回答：** 事务中注册、仅在提交后执行的内存回调不是持久事实：提交后进程退出时回调会消失，逐粉丝写入中途失败也没有记录“哪些已完成、哪些未完成”。当前既无动态扩散待办，也无定时扫描正文和关注关系重放的证据；Redis 索引丢失时查询只会得到空结果。要获得同等级恢复能力，应另行设计事务待办、幂等消费和可审计重建，这些属于改进方案。

2. **追问二：同一毫秒有多条动态跨越多页时，时间游标加偏移怎样避免重复或漏读？请手推至少三页。**

   **回答：** 假设同一毫秒 T 有六条动态，页大小为 2。第一页以`最大时间=T、偏移=0`取第 1～2 条，并返回偏移 2；第二页以`T、2`取第 3～4 条。当前只重新统计“本页末尾有几条等于 T”，仍返回 2，而不是把传入偏移累计成 4；第三页再次以`T、2`取第 3～4 条，出现重复并卡住。正确游标在最小时间仍等于上页最大时间时应累计偏移；时间变小时才重置为该时间在本页的出现数，并用稳定次序测试三页无重无漏。

### Q37｜为什么商铺搜索使用 Elasticsearch，而不是只写 MySQL 模糊查询

**口述回答**

MySQL 的前后模糊匹配适合小数据量、简单包含判断，却很难同时提供中文分词、多字段相关性、分类过滤、地理半径和距离排序。Elasticsearch 先把名称、地址等全文字段分析为词项并建立倒排索引，查询时分析用户关键词，再按匹配位置、频率和字段权重计算相关性；分类标识用精确过滤，坐标用地理字段。当前搜索先让 ES 选候选和顺序，再按标识回 MySQL 取最新正文，因此要区分“某文档被索引命中”与“最新业务事实”：索引有同步延迟且可含已删除候选，MySQL 回查只能刷新命中项的内容，不能补回 ES 漏掉的候选。

**追问展开**

1. **追问一：倒排索引、分词和相关性排序如何配合？IK 的索引分词与搜索分词如何选择，换词典后旧文档是否自动改变？**

   **回答：** 当前中文全文字段在建索引时使用较细粒度分词，扩大可召回词项；搜索时使用较粗粒度分词，减少过度拆分带来的噪声。索引分词器决定旧文档写进了哪些倒排词项，搜索分词器决定本次查询生成哪些词项。修改 IK 词典后，已有文档不会自动重分词，通常需要新索引重建或显式重写文档，并验证召回与相关性变化。

2. **追问二：哪些字段应该全文检索，哪些应该精确过滤？“检索命中”与“返回最新业务事实”有什么区别？**

   **回答：** 名称、地址这类自然语言适合全文检索；分类、状态、业务标识适合精确过滤；经纬度应映射为地理点。ES 命中表示“按当前可见索引满足检索条件”，不是事实源已经最新。当前回库能拿到候选的最新字段并过滤数据库已删除行，却不能纠正旧分类造成的错误候选，也不能发现尚未同步进 ES 的新店，所以同步延迟和索引对账仍需单独监控。

**核对依据**：[店铺搜索流程笔记](../flow-notes/06-shop-read-and-search.md)、[商铺索引文档映射](../../../src/main/java/com/localdeals/dto/ShopDoc.java)、[搜索入口源码](../../../src/main/java/com/localdeals/service/impl/ShopServiceImpl.java)、[Elasticsearch 索引与搜索分析说明](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/analysis-index-search-time.html)

### Q38｜关键词、分类和地理位置同时传入时，搜索条件应怎样组合

**口述回答**

正确语义通常是：关键词进入全文查询，分类和地理半径都进入布尔过滤，二者取 AND，若有坐标再按距离升序。当前代码先设置分类过滤，再设置地理过滤；本次核对项目实际依赖的 Spring Data Elasticsearch 4.0.9 字节码，发现连续设置过滤并非追加，而是覆盖同一个字段，所以同时传分类与坐标时，后设置的地理条件会覆盖分类条件。这是当前缺口，不能描述成已经正确组合。拟议修复是一次构造包含两个条件的布尔过滤，并增加对生成 DSL（查询描述语言）及真实搜索结果的断言；本次没有启动 ES 做回归。

**追问展开**

1. **追问一：连续调用构造器的过滤设置是否一定累加？你如何通过依赖行为和测试验证分类条件没有被地理条件覆盖？**

   **回答：** 不能凭构造器方法名猜“连续调用就是累加”。我会先固定依赖版本，查看源码或字节码确认赋值行为，再对构建出的原生查询断言只存在一个布尔过滤，内部同时含分类精确条件和地理距离条件；集成数据至少放置“半径内不同分类、目标分类半径外、目标分类半径内”三组，最终只能命中第三组。当前仓库尚无这条组合条件回归证据。

2. **追问二：经纬度顺序、单位、半径和距离排序怎样验证？Redis 附近查询回退普通分类页是否保持相同业务语义？**

   **回答：** 坐标顺序必须按具体 API 核对：当前 Java 地理点和距离排序调用传“纬度、经度”，索引字符串也是 `lat,lon`，而 GeoJSON 数组通常是 `lon,lat`，不能套一句固定顺序。半径单位为米，可用同点、边界内外和南北/东西对称点验证单位与升序；当前 ES 距离只参与候选排序，回查 MySQL 后没有把距离写回响应。Redis 附近索引为空则回退普通分类页，不再保证半径和距离顺序，只是不同语义的可用性回退。

### Q39｜从 MySQL 行变更到 ES 可搜索，请说明完整同步链路

**口述回答**

完整链路应从 MySQL 事务提交开始：提交产生 binlog（数据库变更日志）；Canal 订阅并解析行事件，将其投递到 RocketMQ；消费者按表名和操作类型处理，删除事件按业务标识删文档，新增或更新事件转换并以固定标识写索引；ES 完成刷新后，搜索才可见。当前消费者只筛表名和 DDL，没有校验数据库来源，这是链路契约缺口。延迟可能出现在数据库提交到位点读取、Canal 拉取与投递、Broker 排队和重试、消费写入，以及 ES 的近实时刷新周期。任一环节“调用成功”都不能跨阶段推出端到端已同步。

**追问展开**

1. **追问一：binlog、Canal、RocketMQ、消费写索引和索引刷新各承担什么职责，在哪些地方可能有延迟？**

   **回答：** binlog 提供已提交变更及顺序位置；Canal 把数据库日志翻译成行级事件；RocketMQ 提供持久传输、削峰和至少一次重投；消费者负责过滤、转换和索引写删；ES 刷新把已写内容开放给搜索。除排队外，重试、消费者停机、热点分区和刷新间隔都会增加可搜索延迟，因而应分别观察日志位点差、队列最老消息年龄、消费结果和索引可见时间。

2. **追问二：直接调用消费者的集成测试与真实提交数据库、经 Canal 和 MQ 的端到端测试有什么证据差别？**

   **回答：** 当前集成测试直接构造 Canal 形状的消息并调用消费者，连接真实 ES 验证新增、更新、删除及重复处理。它能证明“消费者解析到索引结果”这一段，却绕过真实 MySQL 提交、binlog 生成、Canal 配置与位点、MQ 生产确认、Broker 重投和订阅路由，因此是 consumer-level（消费者级）集成证据，不是完整 E2E（端到端）同步证据。

### Q40｜使用业务 ID 覆盖同一 ES 文档，是否已经解决所有重复和乱序问题

**口述回答**

没有。固定文档标识主要解决同一“写入当前值”事件重复投递：两次写会落到同一文档，而不是新增两份。但普通覆盖是最后到达者生效，不知道业务时间。旧更新晚于新更新会把新状态降级；删除成功后旧更新重放还会把文档复活。当前消费者没有用业务版本、binlog 位点或按业务键有序队列拒绝旧事件，也没有在每次处理时回查 MySQL 最新状态，所以只能称为重复写的有限幂等，不能称为解决乱序。数据库回查搜索结果也只能过滤当次候选，不能修复索引内的陈旧状态。

**追问展开**

1. **追问一：同一更新重复两次、旧更新晚于新更新、删除后旧更新重放，这三种情况分别会怎样？**

   **回答：** 完全相同的更新重复两次，固定标识让第二次覆盖同一文档，最终通常不变；版本 1晚于版本 2到达时，当前会用版本 1覆盖版本 2；删除之后若旧更新再到，会重新创建已删除文档。删除重复本身通常仍是无害的。可见“不会多出重复文档”只是集合唯一性，不等于状态按业务因果顺序单调前进。

2. **追问二：使用业务版本、binlog 位点、按业务键有序消费或回查最新数据库状态，各有什么前提与代价？**

   **回答：** 业务版本要求数据库为每行维护单调版本并随事件传递，消费端原子拒绝低版本；binlog 位点天然代表日志顺序，但要可比较、持久化到文档，并处理不同分片或主库切换；按业务键路由到同一有序队列可减少重排，却牺牲并发且仍要处理重投。消费时回查 MySQL 增加数据库负载，删除还需要墓碑；若两个消费者先后读到新旧状态却反向完成写入，单靠回查仍会被慢写覆盖，必须再配合串行化或版本条件。当前均未完整实现。

**追问：** 采用外部版本写入后，文档被删除且删除版本保护已经过期，此时历史更新才重放，会不会复活文档？你怎样设计删除墓碑的保留时间与死信重放期限，使版本方案真正覆盖这个场景？

**追问缘由：** 原答案提出版本和墓碑，却没有明确删除保护寿命与无限期旧事件之间的矛盾。

**回答：** 会。外部版本只能拿“到达事件的版本”与索引当前保存的版本证据比较。删除时若版本 20 的保护信息还在，迟到的版本 19 会被拒绝；保护信息被清理后，索引又像从未见过该标识，历史更新便可能以版本 19 重新创建文档。具体内部删除版本保留多久受 ES 版本与配置影响，从现有材料尚不能确认，也不应把组件默认保留期当成业务永久保证。

协议上必须建立一个可证明的不等式：删除墓碑保留期要大于“事件从产生到最后一次允许重放”的最大年龄，再加故障恢复、时钟误差和运维安全余量。这个最大年龄应同时纳入主队列保留、自动重试、死信保留、最长停机以及人工重放 SLA；死信工具在超过该期限后禁止原样重放，只能查询 MySQL 当前事实，生成带当前更高版本的写入或删除事件。清理墓碑前，还应确认所有消费者水位都越过删除事件，且允许重放的消息和归档中已不存在更低版本。

如果历史消息允许无限期保存并随时原样重放，任何有限墓碑都无法给出不复活保证，只能把删除版本保存在独立的持久版本账本中，或引入不会复用的索引纪元并在重建、重放时一起比较。现有项目尚未完整实现业务版本和墓碑，这里是使外部版本方案闭环所需的设计条件，不是现行运行结果。

**核对依据**：[索引同步边界说明](../flow-notes/06-shop-read-and-search.md)、[当前索引同步消费源码](../../../src/main/java/com/localdeals/mq/EsSyncConsumer.java)、[Elasticsearch 外部版本写入语义](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/docs-index_.html)、[RocketMQ 顺序消息说明](https://rocketmq.apache.org/docs/4.x/producer/03message2/)

### Q41｜一条同步消息包含多行，其中一行失败，应该确认还是重试

**口述回答**

如果消息的确认粒度是整条，而业务要求每一行最终应用，就不能在仍有失败行时确认，否则该行会永久丢失。当前消费者会逐行捕获异常并继续处理后续行，统计成功和失败；遍历结束后只要存在失败就抛异常，让 RocketMQ 重投整条消息。代价是本轮已成功的行也会再执行，固定文档标识使完全相同的覆盖或删除通常可重复，但无法解决旧状态覆盖新状态。永久坏行可能使整条消息反复重试并最终进入死信；当前也没有逐行检查点或自动隔离，未知操作还会被当作写入，且只按表名过滤、没有校验数据库来源。

**追问展开**

1. **追问一：整条重试会怎样影响前面已写成功的文档？永久坏行、未知操作类型与错误数据库来源如何处理？**

   **回答：** 整条重试会重复前面成功行，因而每行操作本身必须幂等，并把“重复”与“乱序”分别处理。永久缺字段或类型错误的行不会靠重试自愈，应记录原消息、行位置、原因并隔离，避免占住重试资源；未知操作应拒绝而非猜成更新，数据库和表应同时做允许列表校验。上述校验、逐行隔离是建议，现行代码只有继续处理后统一抛错。

2. **追问二：消息进入死信队列以后怎样安全重放？如何避免把已经修复的新状态再覆盖成旧内容？**

   **回答：** 死信重放前先确认根因和当前事实：保留原载荷、消费次数、失败位置及版本，修复解析或数据后，再按业务版本条件写入；若无法证明旧事件仍新鲜，可从 MySQL 当前行重新生成写入或删除墓碑，而不是原样投回主队列。重放使用专用批次、限速和审计，抽样比对索引；否则一条早期死信可能把后来已修复的文档覆盖回旧状态。

**核对依据**：[同步消息批处理源码](../../../src/main/java/com/localdeals/mq/EsSyncConsumer.java)、[消费者结果指标测试](../../../src/test/java/com/localdeals/mq/EsSyncConsumerMetricsTest.java)、[RocketMQ 重试与死信语义](https://rocketmq.apache.org/docs/4.x/consumer/02push/)

### Q42｜索引损坏或需要更换 mapping 时，怎样做完整重建

**口述回答**

当前非测试环境启动逻辑只在索引不存在时创建 mapping（映射），随后无分页读取全部商铺并按固定标识覆盖写入、强制刷新。若索引已存在，它不校验映射；数据库已删除而索引仍残留的文档也不会被清掉，全量读取期间发生的新变更还可能被旧快照覆盖。因此它是便捷初始化，不是无停机重建方案。完整重建应创建带版本的新索引，先记住增量日志水位，再导入一致范围的全量快照，追赶水位后的新增、更新和删除，校验完成后用一次原子别名切换流量；旧索引暂留，异常时切回。

**追问展开**

1. **追问一：启动时把数据库所有现有行再写一遍，能否清掉已经删除的旧文档？全量读取期间新增和更新如何衔接？**

   **回答：** 对现有索引做 upsert（存在则更新、不存在则插入）只能补当前行，无法知道哪些文档已从 MySQL 删除；必须重建到空的新索引，或另外扫描差集并删除。全量扫描期间的并发写需要用开始水位后的 binlog 重放衔接，且删除也要作为墓碑处理；只在全量结束后再开增量会留下时间缝隙。

2. **追问二：如何用新索引、增量追赶和别名切换降低停机？切换前要核对哪些数据，失败如何回退？**

   **回答：** 流程是预建并验证新 mapping，记录日志水位，分批全量导入并可重试，持续追赶增量直到延迟满足阈值；切换前核对总数、分类分布、抽样字段、删除样本、查询契约和最新水位。别名的删除旧指向与添加新指向应在一个请求中原子执行。保留旧索引和切换水位，发现错误可切回；回退期间仍要明确增量如何双写或补追，不能只说“改回别名”。

#### Q42-D1｜面试官追加深挖

**追问：** 记录增量水位后分批扫描全表，如果某条记录先被增量更新到新索引、随后又被全量旧行覆盖，最后还能靠“追赶完成”保证正确吗？请说明快照、水位、全量写入与增量应用的具体排序或版本条件。

**追问缘由：** 现有重建步骤没有展开全量与增量并行写同一文档时防止旧快照覆盖的机制。

**回答：** 不能仅靠“消费者水位已经追到最新”保证。假设全量快照里该记录是版本 5，增量版本 6 先写进新索引，消费者也把水位推进到 6；随后全量任务无条件覆盖写入版本 5。此时水位看似已追完，却不会自动再投一次版本 6，新索引最终反而是旧值。水位说明日志读到了哪里，不说明同一文档最后一次实际写入来自哪个版本。

一种安全排序是先取得与数据库一致性快照对应的起始 binlog 水位 `W0`，全量只从该快照导入；增量事件先缓存而不写新索引，等全量结束后，再把所有大于 `W0` 的事件按业务键顺序应用，追到切换水位 `Wc` 后校验并切别名。这里“快照对应水位”必须用数据库支持的备份/快照协议取得，不能在两个独立时刻随手读一个位点和开始分页。

若为了缩短追赶时间让全量与增量并行写，则两类写入都必须携带同一可比较的单调版本，并由索引端原子拒绝低版本：版本 6 先写后，迟到的全量版本 5 会失败；删除也要携带版本墓碑。另一种办法是在全量结束后从 `W0` 再完整重放一遍，而不能沿用那条已被提前推进的目标索引水位。分批扫描若不在同一快照内，还需依赖逐行业务版本与从扫描前开始的完整变更日志覆盖新增、更新和删除。现有初始化流程并没有这些完整保证。

**核对依据**：[当前索引初始化源码](../../../src/main/java/com/localdeals/init/ShopIndexInitializer.java)、[索引同步流程笔记](../flow-notes/06-shop-read-and-search.md)、[Elasticsearch 别名原子更新](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/indices-aliases.html)

### Q43｜怎样理解 ES 的近实时搜索、分页和分片

**口述回答**

ES 写入确认后，文档已进入写路径，但通常要等下一次 refresh（刷新）生成可搜索段，因此搜索是近实时而非立即可见；refresh 也不等于 fsync（刷盘）持久化，后者还涉及事务日志。频繁强制刷新会制造很多小段并增加合并、I/O 和 CPU 成本。分页方面，普通 `from + size`（起点加数量）在每个分片都要收集并排序到目标深度，再由协调节点归并，页越深内存和计算越贵。在线连续翻页更适合稳定唯一排序配合 `search_after`（游标续查），需要跨页一致视图时再结合 PIT（时间点快照）。

**追问展开**

1. **追问一：写入成功为什么可能暂时搜不到，刷新与持久化是否是一回事？频繁强制刷新会付出什么成本？**

   **回答：** “索引请求成功”与“搜索可见”之间存在刷新窗口；显式等待刷新可以缩短测试的不确定性，却把刷新成本放进写路径。refresh 让新段进入搜索视图，事务日志和刷新到磁盘负责崩溃恢复，二者目标不同。副本提高读容量和可用性，但不会消除这一可见性契约，也不能用副本数量代替持久性配置。

2. **追问二：深分页为什么昂贵？稳定排序、游标分页与一致性搜索视图怎样配合，适合替代哪类分页需求？**

   **回答：** 深分页时每个分片保留大量候选，协调节点再合并，全局第十万条并不是只读取十条。游标字段必须包含稳定总序，通常在业务排序字段后加唯一标识；客户端把上一页最后一条的排序值传入。若索引在翻页间改变，仅有游标仍可能看到漂移；PIT 固定搜索视图更适合滚动浏览或导出。随机跳到任意页仍是普通页码的优势，不能假装游标也能低成本随机跳转。

**核对依据**：[Elasticsearch 近实时搜索](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/near-real-time.html)、[Elasticsearch 刷新成本](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/indices-refresh.html)、[Elasticsearch 分页与 PIT](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/paginate-search-results.html)、[Elasticsearch 事务日志](https://www.elastic.co/guide/en/elasticsearch/reference/7.17/index-modules-translog.html)

### Q44｜MQ 的“至少一次投递”与业务“只生效一次”有什么关系

**口述回答**

至少一次只保证消息在不确定时倾向于再投，不保证消费者只看到一次。生产者发送成功但确认丢失会重发；消费者完成数据库提交却在确认前宕机会再次收到；临时异常触发重试，超过上限进入死信也只是停止自动重投。业务“只生效一次”必须靠稳定业务标识、数据库唯一约束、条件更新和已处理记录实现。项目中，秒杀消息重复时会核对同一用户、活动和订单归属，并靠主键及用户活动唯一约束避免二次扣库存；搜索同步的固定文档标识只能抵抗相同事件重复，不能抵抗乱序，这两种幂等强度不能混为一谈。

**追问展开**

1. **追问一：生产确认丢失、消费者提交后确认丢失、重试与死信分别为什么会制造重复或不确定？**

   **回答：** 生产确认丢失时生产者不知道 Broker 是否已有消息，重发可能得到两份；消费端提交后确认丢失时 Broker 不知道业务已成功，也会重投。重试把暂时错误变成后续机会，同时扩大重复窗口；死信保存最终未自动成功的消息，方便排障，但不会自动撤销已发生的副作用，也不会证明业务失败。每个外部副作用都要单独考虑去重。

2. **追问二：严格有序、消费并发、吞吐和失败重试有什么冲突？用本项目举例说明应该按什么业务键确定顺序范围。**

   **回答：** 并发消费提升吞吐，却允许同一业务键的消息交错；严格顺序通常把同键路由到同一队列并串行处理，前一条失败会阻塞其后，吞吐和可用性下降。搜索同步适合按商铺或内容标识划分顺序范围，而不是让整个主题全局串行；秒杀至少应让同一用户与同一活动/订单的状态变化共享幂等身份。当前消费者使用并发模式，未实现按业务键有序加版本的完整方案。

**核对依据**：[秒杀恢复流程笔记](../flow-notes/02-seckill.md)、[订单消费源码](../../../src/main/java/com/localdeals/mq/SeckillOrderConsumer.java)、[RocketMQ 至少一次说明](https://rocketmq.apache.org/docs/4.x/faq/)、[RocketMQ 消费与死信说明](https://rocketmq.apache.org/docs/4.x/consumer/02push/)、[RocketMQ 幂等最佳实践](https://rocketmq.apache.org/docs/4.x/bestPractice/01bestpractice/)

## 三、限流、可观测与压测（Q45～Q52）

### Q45｜登录、秒杀、领券和查询接口是否真的使用同一种限流

**口述回答**

不是。验证码发送按手机号限制短时间重复获取，验证码校验和后台登录还控制失败或尝试次数，这是防爆破语义；秒杀入口用 Redis 固定窗口，在一次脚本中同时检查活动、用户和 IP 三维请求预算；普通领券依靠资格、活动额度和数据库唯一约束，这是业务约束，不是通用流量限速。查询侧仅部分路径接入本实例信号量：详情缓存失效回源与热榜数据库回退使用数据库舱，ES 搜索及显式名称模糊查询使用搜索舱。分类、附近查询、粉丝动态等路径并未因此获得统一保护，所以不能概括为全站或领券全链路限流。

**追问展开**

1. **追问一：请按实际入口区分尝试次数控制、固定窗口、并发许可与业务额度；哪些接口尚未接入统一流控？**

   **回答：** 手机验证码默认一分钟内只发一次，错误验证码还有有限尝试预算；后台登录按账号与 IP 控制失败，并有 IP 尝试上限。秒杀默认一秒固定窗口，活动、用户、IP 三个维度由 Redis 原子准入。数据库/搜索舱是并发许可和短等待，而活动额度、单用户领券唯一性属于业务不变量。它们控制对象、时间尺度与拒绝原因都不同，不能只因都可能返回拒绝就叫同一种限流。

2. **追问二：本实例限制四个并发与全局每秒四个请求有什么不同？如何避免把“有限制措施”笼统写成“全链路限流”？**

   **回答：** 本实例四个并发表示单台应用同一时刻最多四个受保护调用；十台应用理论上可形成约四十个，而且它不限定每秒请求数。全局每秒四次需要共享计数或网关在所有实例间统一判断。准确表述应列出具体入口、资源和作用域，并说明未接入路径；“有限制措施”只证明局部防护，不能推导出统一网关、全局配额或整条调用链每一步都受保护。

### Q46｜固定窗口、滑动窗口、令牌桶和漏桶如何选择

**口述回答**

固定窗口用“时间段＋计数”判断，状态小、实现简单，适合当前秒杀入口的粗粒度准入，但相邻窗口末尾和开头可各放满一次，短时间内形成接近两倍配额的边界突发。滑动日志记录每次时间最准确但开销高，滑动计数折中精度与成本；令牌桶按平均速率补令牌并允许受控突发，适合可吸收小峰值的接口；漏桶按固定速度排出，更能平滑下游，却引入排队或丢弃。选择要从下游承载方式、允许突发和公平性出发，而不是认为某算法普遍更高级。当前项目实现的是 Redis 固定窗口，不是另外三种。

**追问展开**

1. **追问一：窗口边界会出现怎样的突发流量？秒杀活动、用户和 IP 三维预算怎样在同一次请求内一致判定？**

   **回答：** 例如每秒限 100，第一秒末尾通过 100 个、下一秒开头再通过 100 个，极短区间内就有 200 个到达下游。当前秒杀把同一次请求的活动、用户和 IP 三个计数放入一个 Lua 脚本：先读取并判断三项，只要任一超限就整体拒绝；全部可用才一起递增并设置窗口寿命，避免先扣活动配额、后发现用户超限的部分更新。

2. **追问二：被拒绝请求是否消耗其他维度配额，后续业务失败是否返还请求计数？分别对应什么产品语义？**

   **回答：** 当前被拒请求不递增任何维度；已被准入的请求则三项都计一次，即使之后库存不足或数据库异步失败也不返还。这定义的是“尝试/准入预算”，能抑制探测和重试风暴。若产品要统计“成功购买额度”，应另设由最终业务状态维护的计数；随意返还入口预算会让失败重试绕过保护，而可靠退款又需要精确请求身份和补偿协议，不能把二者混成一个计数器。

**核对依据**：[秒杀流量保护源码](../../../src/main/java/com/localdeals/service/SeckillTrafficGuard.java)、[固定窗口原子测试](../../../src/test/java/com/localdeals/service/SeckillTrafficGuardRedisIT.java)、[Redis 限流模式说明](https://redis.io/docs/latest/develop/use-cases/rate-limiter/)

### Q47｜Redis 或 ES 故障时，哪些接口继续服务，哪些应该拒绝

**口述回答**

降级取决于该依赖保存的是可重建加速数据还是正确性前提。Redis 中的登录会话、验证码状态无法核实时，受保护请求和认证应拒绝；秒杀无法原子核验流量、库存预占及归属也应失败关闭，不能“先放行再说”。店铺详情缓存只是加速层，Redis 读写失败可在本实例数据库许可范围内回源并跳过回填；热榜也可回 MySQL。这个有界回源并未覆盖所有分类、GEO（地理位置）和粉丝动态路径。ES 故障时，当前商铺和内容搜索经搜索并发舱返回服务不可用，并不会自动切换 MySQL 模糊查询。

**追问展开**

1. **追问一：认证状态不可验证、库存预占不可验证、详情缓存不可用这三种故障，为什么不能统一按“降级放行”处理？**

   **回答：** 认证状态不可验证时放行会越权；库存预占不可验证时继续下单会造成超卖、重复或无法恢复，所以宁可返回暂不可用。详情缓存失败时 MySQL 仍是权威事实，受控回源不会改变写入不变量，因此可以牺牲容量保可用。即便都是 Redis 故障，数据角色不同，附近索引或动态索引丢失还可能没有同语义重建路径，不能用一个全局“忽略 Redis”开关处理。

2. **追问二：ES 失败直接退回 MySQL 模糊查询，会给数据库和结果语义带来什么变化？当前项目是否真的自动执行这个回退？**

   **回答：** ES 的全文分词、相关性、分类过滤、地理半径与距离排序，和 MySQL 名称包含查询的结果契约不同；自动退回还会把搜索峰值直接压到数据库。若要设计回退，应限制查询范围、容量和超时，向客户端标记降级，并验证数据库索引。当前只有一个客户端显式调用的名称模糊查询入口，并非 ES 异常自动调用；此外非测试启动初始化还依赖 ES，ES 不可用甚至可能影响应用启动。

### Q48｜如何从 Prometheus 指标判断系统只是变慢，还是一致性已经出问题

**口述回答**

“变慢”首先看耗时分布、并发中任务和队列年龄，例如缓存回源、索引写入、订单持久化的 Timer（计时器），再结合错误计数增长率；“可能不一致”则看未决事件数量、最老未决年龄、隔离与死信是否持续增长，并最终执行数据库不变量对账。Prometheus 指标只能发出信号，不能凭一个缓存命中率证明事实一致。当前应用预注册有限枚举标签，计数器覆盖认证、流控和处理结果，关键计时器显式发布直方图桶，Gauge（仪表）采样待办与年龄；RocketMQ 主队列、重试和死信积压仍应从 Broker 侧观察。

**追问展开**

1. **追问一：缓存回源、接口错误、消息积压、最老未决订单年龄、死信与隔离记录各适合用什么类型指标？**

   **回答：** 缓存回源和处理耗时用直方图/计时器，接口错误、消费成功/失败、死信或隔离新增用单调计数器，当前积压量、最老未决年龄、执行中数量用仪表。消息积压既要当前深度也要最老年龄，避免低吞吐队列只看数量被忽略。数据库关系、聚合加待办增量、正式订单、库存和预占状态仍需查询事实源做等式或集合核对。

2. **追问二：为什么不适合把订单号、用户 ID 等直接作为指标标签？计数器重启、采样失败和标签基数怎样影响分析？**

   **回答：** 把用户或订单标识放进标签会为每个值创建新时间序列，内存、抓取和查询成本随业务量爆炸，应放日志或追踪，只保留有限结果枚举。计数器进程重启会归零，分析要用区间增长率并识别重置；采样失败不能写成零，否则把“未知”伪装为“没有积压”。当前采集器用 NaN（非数）表示未知并累计采样失败，可据此把观测故障与真实零值分开。

#### Q48-D1｜面试官追加深挖

**追问：** 两个实例请求量分别是100次和10000次，各自有一个P99，能不能把两个P99取平均当作集群P99？使用直方图时应先聚合什么、再算什么，桶太粗会怎样影响结论？

**追问缘由：** 原答案说明了指标类型，但没有解释多实例尾延迟的聚合与估计误差。

**回答：** 不能，连按请求量加权平均两个 P99 也不成立。分位数是对全部样本重新排序后取位置，不是可线性相加的均值；100 次请求的实例与 10000 次请求的实例权重相差百倍，而且仅知道各自 P99，已经丢失了阈值附近的分布。一个实例的极慢 1% 和另一个实例的大量临界样本如何交错，会改变集群 P99，却不会体现在“两个 P99 的平均值”中。

使用相同边界的累计直方图时，应先在同一时间窗口对各实例每个 `le` 桶的计数增量求和，同时聚合总样本数；再在聚合后的累计分布上找到达到总数 99% 的桶，并据此估算集群 P99。Prometheus 中通常是先按桶上界保留 `le` 聚合各实例的速率或增量，再调用分位数估算。预先由实例算出的分位值或 Summary（摘要）不能再汇总成集群分位数，还要正确处理进程重启造成的计数器重置。

直方图给出的本质是区间。若 98% 落在 100 毫秒以内、99.5% 落在 500 毫秒以内，真实 P99 只知道位于这个宽区间；线性插值只是估计，分布在桶内集中时误差会很大。因而桶边界应围绕 SLO 阈值和预期尾部加密，并同时报告样本量、超时和错误；桶过粗时最多判断是否可能越线，不能声称一个精确 P99。

### Q49｜接口延迟正常，但消息积压持续增加，你会怎样定位

**口述回答**

先把同步入口和异步处理拆成两条速率：比较生产受理速率、各队列消费成功速率、主队列/重试队列/死信的深度与最老消息年龄，确认是持续流入大于处理能力，还是失败重投造成假性吞吐。再按消费阶段看锁忙、临时错误、毒消息、数据库持久化耗时与错误、连接池等待、Redis/ES 延迟、重平衡和进程日志。HTTP 很快只说明请求线程完成了准入与投递，不说明异步数据库已经跟上。应先找出瓶颈资源和失败类型，再决定扩线程、扩实例、限入口或隔离坏消息，不能只看 CPU 就加消费者。

**追问展开**

1. **追问一：怎样区分生产速度过快、消费线程不足、数据库锁等待、依赖变慢和坏消息反复重试？**

   **回答：** 若生产长期高于成功消费且错误低，是容量不足；线程都忙但数据库锁等待或连接池等待高，是下游瓶颈；依赖耗时同步上升是外部服务变慢；同一消息反复出现并转移到重试队列，是业务/数据错误。主队列下降并不一定恢复，压力可能已进入重试或死信。按消息标识抽样串联接收、加锁、写库和确认日志，才能区分“没拿到任务”和“拿到后失败”。

2. **追问二：增加消费者实例一定有效吗？队列数、单用户锁、数据库连接和热点库存行会怎样限制扩容收益？**

   **回答：** 消费者扩容受订阅队列数限制：可并行分配的队列不增加，多余实例拿不到分片。即使队列足够，同一用户锁仍串行该用户消息，数据库连接数、唯一约束竞争和热点活动库存行会成为共享瓶颈；盲目扩容反而增加锁冲突和数据库压力。当前源码也未显式固定队列数和消费线程，应核对运行时 Broker 与客户端配置后再评估理论并行度。

**核对依据**：[当前业务指标定义](../../../src/main/java/com/localdeals/observability/LocalDealsMetrics.java)、[订单消费源码](../../../src/main/java/com/localdeals/mq/SeckillOrderConsumer.java)、[RocketMQ 消费扩容与队列约束](https://rocketmq.apache.org/docs/4.x/bestPractice/01bestpractice/)、[RocketMQ 重试与死信说明](https://rocketmq.apache.org/docs/4.x/consumer/02push/)

### Q50｜“1000 用户、1000 笔订单全部落库”具体怎样测出来

**口述回答**

这句话来自历史快照 `d063764` 的专用本地基线，不是本次当前快照复测。单实例应用连接隔离的 MySQL 8、Redis 6.2 和 RocketMQ 4.9.4；成功场景每轮库存 1000，JMeter 配置 1000 线程、1000 个独立用户令牌、每线程 1 次请求、5 秒爬升，秒杀流控开启且活动/IP 上限显式调到 2000。三轮均得到受理 1000、正式订单 1000、数据库与 Redis 库存归零、预占和成功状态各 1000、重复订单及主/重试/死信积压为零。5 秒内逐步启动线程，所以“全部 1000”不等于某一瞬间严格并发 1000。

**追问展开**

1. **追问一：线程数、独立用户数、请求数、启动爬升时间、库存、单实例配置和限流参数分别是多少？是否等于 1000 个请求严格同时执行？**

2. **追问二：HTTP 成功、最终订单数、重复订单、库存与消息积压怎样联合验收？历史压测源码快照与当前代码如何对应？**

### Q51｜HTTP P99 和异步订单最终落库耗时是不是同一个指标

**口述回答**

不是。历史 P99 的 64、45、61 毫秒来自三轮 JTL 中 HTTP 样本的 elapsed（请求耗时）：请求完成 Redis 准入并取得事务消息发送结果后即可响应，正式订单仍由消费者异步写 MySQL。每轮约 13 秒的 drain（排空）从整轮 JMeter 结束后开始轮询，直到预期订单、成功状态、无处理中记录以及 Broker 主/重试/死信均归零；它是整批尾部收敛时间，不是每笔订单从受理到落库的延迟样本，更不是订单最终延迟 P99。要测后者，必须用同一订单标识记录受理时间与持久化完成时间并形成分布。

**追问展开**

1. **追问一：请求响应、成功下单吞吐、总请求吞吐和积压排空时间分别如何测量？库存不足的快速拒绝会怎样改变指标？**

   **回答：** HTTP 响应耗时从 JTL 每个请求计算；入口受理吞吐是测量窗口内的受理数除以时长，总请求吞吐还包括业务拒绝。持久化成功吞吐则应按指定时间窗内正式订单的新增提交数计算，并排除重复重试，不能因最终得到 1000 单就直接套用入口 JMeter 吞吐；排空时间是在负载停止后按多项最终状态轮询。库存 100 的竞争场景有 900 次快速拒绝，总吞吐约 211 次/秒且 P99 为 26 毫秒，但只有 100 次受理和 100 笔订单，不能由更低 P99推出落库更快。

2. **追问二：为什么只做库存等于请求数的成功样本不足以说明竞争正确性？你还会加入哪些负向与重复请求样本？**

   **回答：** 库存等于请求数主要覆盖成功路径，几乎不迫使库存竞争和拒绝分支执行。历史另有库存 100、请求 1000 的样本，得到 100 次受理和 900 次库存不足，并联合核对零超卖。还应设计同一用户重复请求、同一消息重投、发送确认不确定、数据库提交后状态更新失败、毒消息和依赖超时等样本；这些属于下一步故障与幂等验证，不能虚构为本次已跑的压力结果。

#### Q51-D1｜面试官追加深挖

**追问：** 假设服务卡顿30秒，固定线程客户端等待响应期间不再发新请求，只统计已经结束的HTTP样本会怎样影响你看到的吞吐和P99？怎样设计到达速率、超时样本与未终态订单的统计，避免把积压隐藏掉？

**追问缘由：** 当前严格区分HTTP和落库延迟，但没有讨论负载生成方式及未完成样本对结果的偏差。

**回答：** 固定线程且“收到响应后才发下一次”的客户端是闭环负载。服务卡住 30 秒时，线程都在等待，新的计划请求不再到达，实际施加到服务端的到达率会自动下降；这会把本应形成的排队压力隐藏掉。若报表只纳入已经结束的 HTTP 请求，卡住或测试结束时仍未完成的样本被右删失，吞吐可能按完成样本或活跃时段被误读，P99 也只在幸存的快样本中计算，甚至看起来仍很漂亮。若恢复后慢样本最终完成，它们是否进入窗口又取决于测试收尾方式，结果不可比。

容量实验应明确目标到达率，并用开放式模型按计划时间发起请求，不因前一个响应变慢而停止；同时记录计划到达、实际发出、服务端受理、拒绝、客户端超时和最终完成的数量及墙钟时间。延迟至少包含从计划到达开始的排队等待，所有超时都作为失败或“延迟大于超时阈值”的样本单独进入错误预算，不能从 P99 数据集中静默删除；还应持续记录客户端在途数、服务端队列深度和最老任务年龄。

对异步订单，再按订单号从受理时刻追到成功、失败或明确的未知超时，固定观察和排空截止时间。截止时未终态的订单必须报告数量、比例和年龄，不能只对已落库订单算延迟。最终同时给出目标到达率下的受理率、HTTP 成功/超时分布、订单终态分布及积压曲线，才能识别协调遗漏，而不是让卡顿通过降低负载自我掩盖。

### Q52｜设计一组能验证恢复链路的故障注入实验

**口述回答**

我会用四个确定性故障点逐段验证，而不是随机停整套环境：一是在 Redis 完成精确预占、事务消息尚未明确提交时终止本地回调，验证 Broker 回查凭相同归属提交消息；二是在 MySQL 正式订单提交后、Redis 成功标记前中断，验证消息重投通过数据库唯一约束识别同一订单，只修状态而不再扣库存；三是在发券通知已被 Redis 接受、数据库发布标记更新前失败，验证持久待办仍可重试且允许重复提示；四是在对账原子认领后宕机，验证待检查成员只是被推迟、到期后可再次扫描。本次只做源码推演和历史证据核对，未实际执行这些实验。

**追问展开**

1. **追问一：分别在 Redis 预占之后、数据库提交之后、通知发布之后和对账认领之后中断，预期留下什么可检查状态？**

   **回答：** 第一处预期保留库存扣减、精确预占、处理中状态和待检查索引，数据库起初无订单，半消息回查后才可消费；第二处数据库订单和库存已提交，Redis可能仍处理中，重投后转成功且库存不回补；第三处用户可能已经在线收到通知，但待办事务因标记失败仍是待处理，重试可能再次发布，说明“发布受理”不等于只提示一次或已读；第四处原子认领会递增尝试次数、保留处理中状态，并把待检查时间移到当前时间加重试间隔，进程退出后记录不丢，下一轮到期再处理。

2. **追问二：怎样设置超时、停止条件与隔离数据，证明恢复依靠目标机制，而不是测试重置或重启顺带修好了？**

   **回答：** 每个实验用专用数据库模式、Redis 前缀、主题、消费组和运行标识，启动前检查连接与哨兵数据，隔离不确定就停止。故障点用测试钩子或闩锁精确触发，预先写明中断前后允许状态；超时按 Broker 回查/重试和对账周期设置，并以多轮无变化、进入死信/隔离或超过机制上界作为停止条件。恢复时只放开被中断组件，不清库、不重置状态、不重启整栈；先保存日志、数据库行、Redis归属和队列位点，再观察目标机制收敛，才能排除“测试重置顺带修好”。
