### Q53｜用订单标识作为 HashMap 的键，需要满足什么约定？

**口述回答**

订单标识作为键，首先应是稳定的值对象：对象相等要满足自反、对称、传递、一致，且两个相等对象必须产生相同散列值。HashMap 先用散列值定位桶，再用相等判断确认键，因此只重写其中一个方法会破坏查找语义。键参与相等性和散列计算的字段还应在放入后保持不变；最稳妥的是直接使用不可变的长整型、字符串，或只由不可变字段组成的对象。并发场景则要另外分析，正确的键约定并不会让普通 HashMap 获得线程安全性。

**追问展开**

1. **追问一：`equals` 与 `hashCode` 不一致、插入后修改键字段会造成什么问题？Java 8 的冲突链、树化和扩容分别何时发生？**

   **回答：** 若两个相等键的散列值不同，它们可能落入不同桶，造成重复记录或查不到；若插入后修改键字段，查找会按新散列定位，而元素仍留在旧桶，形成“看得见却取不出”的幽灵项。Java 8 中，默认负载因子为 0.75，插入后大小超过 `容量 × 负载因子` 才触发扩容。桶内冲突先形成链表；插入使桶内节点数达到树化门槛时，还要看表容量是否至少为 64，容量较小时优先扩容，不能背成“链表到 8 个必然树化”。

2. **追问二：在请求合并登记表里，普通 HashMap 为什么不够？换成线程安全容器后，多步“先查再放”是否自动变成原子操作？**

   **回答：** 请求合并登记表会被多个请求同时读写，普通 HashMap 既不保证可见性，也不保证结构修改安全。换成 ConcurrentHashMap 只保证单个操作的并发语义，`get` 后再 `put` 仍可能让两个线程都认为自己是首个请求。更稳妥的做法是创建候选 FutureTask，用 `putIfAbsent` 竞争登记，只有获胜者回源，其他线程等待同一个结果；收尾时用“键和同一任务实例都匹配”的条件删除，避免旧任务误删后来者。

**核对依据**：[Oracle Java 8 Object 契约](https://docs.oracle.com/javase/8/docs/api/java/lang/Object.html)、[Oracle Java 8 HashMap 文档](https://docs.oracle.com/javase/8/docs/api/java/util/HashMap.html)、[OpenJDK 8 HashMap 源码](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/HashMap.java)、[商铺读取与搜索流程中的请求合并](../flow-notes/06-shop-read-and-search.md)

### Q54｜Java 8 的 ConcurrentHashMap 如何支持并发读写？

**口述回答**

Java 8 的 ConcurrentHashMap 核心是节点数组加桶级协作，不再以 Java 7 的 Segment 分段锁作为主结构。读取通常通过易失性读沿桶链或树查找，不必取得全表锁；写入空桶时可用比较并交换（CAS）安装首节点，冲突桶上的更新再对桶首节点加锁，扩容时多个线程还能协助迁移。它因此把竞争限制在更细粒度的位置，但不是“无锁容器”：树桶、冲突更新和迁移都有同步协议，保证的是规定的并发语义，而非任意复合业务动作自动原子。

**追问展开**

1. **追问一：它与 Java 7 的分段锁说法有什么差别？`putIfAbsent`、计算后写入和普通 `get` 加 `put` 的语义有什么不同？**

   **回答：** Java 7 常用“多个 Segment，各自持锁”解释；套到 Java 8 会答错，因为 Java 8 已改为数组槽位、CAS、桶锁和转发表。`putIfAbsent` 是一个原子条件写；`compute` 可原子地围绕某个键计算和更新，但回调有约束；普通 `get` 加 `put` 是两个独立动作，间隙里其他线程可以写入。若业务含远程调用或多资源状态，即使用了原子映射方法，也仍需设计幂等和失败边界。

2. **追问二：把慢数据库查询放进原子计算回调会有什么风险？并发统计大小、遍历和弱一致性分别能保证什么？**

   **回答：** 原子计算可能阻塞同一桶上的部分更新；把慢数据库查询放进回调会扩大受影响时间，还可能因递归更新、超时或异常让行为难以推理，因此回调应保持短小且不递归修改映射。可以用短回调只登记一个 FutureTask，把慢查询放在获胜线程外部执行。并发下 `size`、聚合统计和遍历适合监控估算或弱一致视图：单个已完成键更新与随后读取有可见性关系，但跨多个键的遍历不是某一瞬间的事务快照，不能据此作精确业务裁决。

**核对依据**：[Oracle Java 8 ConcurrentHashMap 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ConcurrentHashMap.html)、[OpenJDK 8 ConcurrentHashMap 源码](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/concurrent/ConcurrentHashMap.java)、[请求合并边界](../flow-notes/06-shop-read-and-search.md)

### Q55｜为热榜或批量事件聚合选择 Java 集合，你如何决定？

**口述回答**

我会先按处理阶段选集合，而不是找一个“万能容器”。批量事件按业务标识聚合时，用 HashMap 做近似常数时间的查找和累加；若处理中始终需要按键有序，可用 TreeMap 换取对数时间操作；只求前 K 名时，用容量为 K 的小顶优先队列保留当前候选，最后再转成列表按最终规则排序。若数据本来不大或必须输出完整顺序，直接列表排序更简单。选择还要包含并发模型、空值、稳定次序和内存上限，而不只是平均复杂度。

**追问展开**

1. **追问一：HashMap、TreeMap、优先队列和排序后的列表分别适合哪一步？维护 K 个最大值的时间与空间复杂度是多少？**

   **回答：** 对 N 条输入维护 K 个最大值，遍历时每个候选至多进行一次堆调整，时间通常是 `O(N log K)`，额外空间是 `O(K)`；当 K 接近 N 时，直接排序的 `O(N log N)` 可能更清晰且常数更好。TreeMap 适合边聚合边按键范围查询，并不天然等于“按热度取前 K”；HashMap 负责合并、优先队列负责裁剪、列表负责最终展示，是常见且职责清晰的组合。

2. **追问二：为什么相同分数还需要稳定次序？比较器中直接用两个 long 相减再转 int，可能出什么错误？**

   **回答：** 同分若没有第二排序键，堆迭代、数据库分页或多实例重算的顺序可能漂移，导致翻页重复、遗漏或缓存结果频繁变化。应定义确定性的规则，例如“分数降序，业务标识降序”，并在各层保持一致。比较两个 `long` 时直接相减再转 `int` 会溢出或截断，使比较器违反反对称、传递约定，排序甚至可能抛异常；应使用 `Long.compare`，或用 `Comparator.comparingLong` 再追加稳定的平局字段。

**核对依据**：[Oracle Java 8 PriorityQueue 文档](https://docs.oracle.com/javase/8/docs/api/java/util/PriorityQueue.html)、[Oracle Java 8 Comparator 文档](https://docs.oracle.com/javase/8/docs/api/java/util/Comparator.html)、[点赞与热榜流程](../flow-notes/04-like-and-hot-rank.md)

### Q56｜共享变量加上 volatile，能保证并发操作正确吗？

**口述回答**

不能。`volatile` 主要提供可见性和特定的有序性：一个线程对易失性变量的写，对随后读到该写的线程先行发生；编译器和处理器也不能把相关访问任意重排到这条发布边界之外。它不把“读—改—写”合成一个不可分割动作，所以 `count++` 仍会丢更新。若异步重建只允许一个任务进行，仅用易失性布尔值先判断再赋值同样有竞态，应改用原子比较并交换、锁或容器的原子登记方法；`volatile` 更适合停止标志和安全发布。

**追问展开**

1. **追问一：可见性、原子性和有序性分别是什么？用 `count++` 和异步任务进行中标志举例说明。**

   **回答：** 可见性是一个线程的写能被另一个线程观察；原子性是操作不能被看见处于中间状态，也不会被竞争穿插；有序性是程序所依赖的先后关系不会被允许的重排破坏。单次易失性读写有原子和可见语义，但 `count++` 包含读、加一、写三步。任务标志的“若为假则设真”也有两步，两个线程都可能先读到假，所以要使用 `compareAndSet(false, true)`，并在任务拒绝或结束时按所有权复位。

2. **追问二：先行发生关系怎样帮助分析线程之间的数据发布？双重检查单例为什么要考虑安全发布？**

   **回答：** 先行发生（happens-before）是判断“某次写是否必须对某次读可见”的规则，例如同一线程程序次序、监视器解锁到后续加锁、易失性写到后续读，以及这些关系的传递。双重检查单例如果引用不是 `volatile`，对象分配、字段初始化、引用赋值可能表现为引用先发布，另一线程看到非空却看到未完全初始化的状态；Java 5 以后配合易失性引用，第二次检查和同步块才构成正确的安全发布方案。

#### Q56-D1｜面试官追加深挖

**追问：** 把一个包含可变 List 的对象放进 volatile 引用后，发布前的初始化和发布后继续往 List 里加元素，分别获得什么可见性保证？为什么“引用安全发布”不能直接推出“对象后续修改线程安全”？

**追问缘由：** 原回答讲安全发布，尚未限定它对后续可变状态的保护范围。

**回答：** 假设线程 A 先构造对象、向其中的 `List` 放入初始元素，最后把对象引用写入 `volatile` 字段；线程 B 随后读取该字段并确实观察到这次写。易失性写与读建立先行发生关系，A 在发布前完成的对象字段初始化和列表写入也通过传递关系对 B 可见，所以 B 不应看到一个只初始化了一半的对象。前提是对象没有在这次发布之前通过别的路径逸出。

但 A 在发布完成后再执行 `list.add`，这次普通写发生在原来的易失性写之后，并没有被那条发布边界带给 B。引用本身仍是同一个且可见，不代表列表元素、数组扩容和 `size` 的后续修改也有同步关系。多个线程并发添加还可能丢元素；读与扩容并发时也可能看到不一致结构或出现迭代异常。即使写线程添加后再次写一遍易失性引用、读线程观察到该新写，这至多补充可见性，仍不能把多个列表操作变成一个原子不变量。

如果状态是“读多写少的完整快照”，更稳妥的是每次构造新的不可变列表和对象，再整体替换易失性引用；若必须原地修改，则所有访问使用同一把锁，或选用符合操作语义的并发集合。安全发布回答的是对象首次交给其他线程时的可见性，线程安全还必须覆盖发布后的每一次读写和复合操作。

**核对依据**：[Java 语言规范 17.4 内存模型](https://docs.oracle.com/javase/specs/jls/se8/html/jls-17.html)、[Oracle Java 8 AtomicLong 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/atomic/AtomicLong.html)

### Q57｜CAS 和锁如何选择？

**口述回答**

比较并交换（CAS）适合状态小、临界区短、可以无副作用重试的更新，例如单个计数或从“空闲”切换到“处理中”。它乐观地比较旧值，匹配才写入，失败者重读并重试，不会因线程挂起而让锁持有者阻塞全局。锁更适合同时维护多个字段不变量、需要条件等待，或临界区包含不可重复的数据库和网络操作。选择不能只看“无锁更快”：低竞争时 CAS 很轻，激烈竞争会持续自旋、浪费 CPU；锁虽有调度成本，却能把等待线程停放并表达更完整的临界区。

**追问展开**

1. **追问一：比较并交换适合怎样的短操作，竞争激烈时有什么代价？ABA 问题在带状态迁移的对象中何时值得关心？**

   **回答：** CAS 的经典风险是 ABA：线程读到 A，期间状态变成 B 又回到 A，单看值仍匹配，但中间变化可能有业务含义。纯数值累加通常不关心这段历史；对象状态机、栈节点复用或“同一值但不同代次”的所有权则应加入版本戳、使用不可变新对象，或改用锁。竞争很高、重试计算昂贵、回调带副作用时也不应让 CAS 循环无限放大工作量。

2. **追问二：AtomicLong 与 LongAdder 的取舍是什么？监控统计和业务唯一序号能否用同一种计数器？**

   **回答：** AtomicLong 对单个增量提供线性化的精确序列，适合需要立即准确读取的小规模计数；LongAdder 把热点分散到多个单元，竞争下吞吐通常更好，但 `sum()` 在并发更新时不是原子快照，适合请求量、命中量等统计。业务唯一序号不仅要“数字大致增加”，还要保证不重复、持久和跨实例协调，不能用 LongAdder 生成；即便 AtomicLong 单进程唯一，重启和多实例也需要数据库、号段或专门的分布式标识方案。

**核对依据**：[Oracle Java 8 AtomicLong 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/atomic/AtomicLong.html)、[Oracle Java 8 LongAdder 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/atomic/LongAdder.html)、[Java 8 并发包概览](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/package-summary.html)

### Q58｜synchronized、ReentrantLock 和 Semaphore 各适合什么场景？

**口述回答**

`synchronized` 适合结构简单、作用域明确的互斥与条件协作，进入和退出由语言保证，异常也会自动释放监视器。ReentrantLock 同样可重入，但额外支持可中断获取、限时尝试、公平策略和多个 Condition，适合必须精细控制等待的场景，代价是必须在 `finally` 中解锁。Semaphore 表达的是最多允许多少个并发许可，例如限制同时回源数据库的请求数；它不要求释放者必须是取得许可的线程，因此不具备互斥锁的线程所有权检查。单许可的信号量也能用于互斥，但所有访问必须遵守同一许可协议，不能仅靠设置许可数量就保证业务状态安全。

**追问展开**

1. **追问一：可重入、可中断、超时、公平性和条件等待怎样影响选择？AQS 的状态与等待队列大致如何配合？**

   **回答：** 可重入避免同一线程沿调用链再次取得同一锁时自锁；可中断和超时让调用者能放弃等待；公平锁倾向按等待先后来获取，降低饥饿但会减少吞吐；多个 Condition 可把不同等待原因分组。ReentrantLock 和 Semaphore 都建立在抽象队列同步器（AQS）之上：一个整数状态表示占用或许可情况，获取失败的线程进入近似先进先出的等待队列并停放，状态释放后再唤醒合适节点竞争。

2. **追问二：一个线程可以释放另一个线程取得的信号量许可吗？这与有所有权的锁有什么不同，如何避免多释放？**

   **回答：** Semaphore 的 `release` 不校验线程所有权，因此 A 线程取得的许可可以由 B 线程释放，这适合任务移交，却也意味着多释放会把许可总数永久抬高。常见写法是先用局部布尔值记录 `acquire` 是否真正成功，只在成功后进入 `finally` 释放一次；超时、被中断、提交任务失败时分别处理。互斥锁则绑定持有者，非持有线程解锁会失败，这种所有权正是保护临界区结构的组成部分。

#### Q58-D1｜面试官追加深挖

**追问：** 使用 Condition 等待“队列非空”时，为什么 await 外必须用 while 重新检查，而不能只用 if？请按释放锁、进入等待、收到 signal、重新抢锁的顺序，解释被唤醒为何不等于条件已经归自己所有。

**追问缘由：** 现有AQS与条件等待介绍停留在状态和队列名称，缺少等待条件如何重新成立的中间步骤。

**回答：** 消费线程先持有锁，在 `while (队列为空)` 中调用 `await`。这个调用会把线程加入条件等待队列，并以原子步骤释放关联锁，然后线程停放；否则“先解锁、后入队”之间可能漏掉生产者的通知。生产者取得同一把锁、加入元素并调用 `signal` 后，被选中的等待节点只是从条件队列转移到同步等待队列，并不立刻从 `await` 返回，也没有从生产者手里接管锁。生产者仍可继续修改共享状态，直到解锁。

被通知的消费者随后还要与其他等待线程重新竞争锁，真正取得锁后 `await` 才返回。这个间隔里，另一个消费者可能先拿锁并取走刚加入的元素；一次通知也可能唤醒多个候选中的一个，而条件等待还允许无理由唤醒。因此“被唤醒”只表示可以再次竞争和检查，不表示“队列非空”这项业务条件已经专属于本线程。

若外层写成 `if`，线程恢复后会直接执行出队，可能面对再次为空的队列。写成 `while` 才会在持锁状态下重新判断：条件成立才消费，不成立就再次 `await`。相应地，生产者也应在持锁状态下先改变队列，再发通知，让重新取得锁的消费者能够看到与通知相匹配的状态变化。

**核对依据**：[Oracle Java 8 ReentrantLock 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/locks/ReentrantLock.html)、[Oracle Java 8 Semaphore 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Semaphore.html)、[OpenJDK 8 AQS 源码](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/util/concurrent/locks/AbstractQueuedSynchronizer.java)

### Q59｜线程池怎样决定创建线程、入队或拒绝？

**口述回答**

Java 8 ThreadPoolExecutor 接收任务时的顺序是：运行线程少于核心线程数，先尝试创建核心线程；否则尝试把任务放入工作队列；队列放不下时，再创建非核心线程，直至最大线程数；仍无法接纳才执行拒绝策略。这个顺序说明最大线程数只有在队列有界且已满时才会发挥扩容作用。非核心线程空闲超过保活时间通常会回收，核心线程默认不回收；参数应作为一套容量和过载策略设计，而不是彼此独立地设成很大的数字。

**追问展开**

1. **追问一：核心线程数、最大线程数、队列容量、空闲回收和拒绝策略各控制什么？无界队列为什么可能让最大线程数失去预期作用？**

   **回答：** 核心线程数是常态并发，最大线程数是队列饱和后的短时上限，队列容量吸收受控突发，保活时间回收额外线程。拒绝可以抛异常、中止最旧任务、静默丢弃，或由提交线程执行；每种都必须匹配业务契约。无界队列几乎总能接住任务，池通常只创建到核心线程数，最大线程数形同虚设；持续过载则表现为排队时间和内存不断上升，而不是及时拒绝。

2. **追问二：缓存重建任务被拒绝时，怎样处理任务进行中标志？把拒绝任务交回 HTTP 线程执行会有什么代价？**

   **回答：** 缓存重建若先设置“进行中”再提交，提交被拒绝却不复位，后续请求会永远以为已有任务。应让成功入队成为状态转换的一部分，或在拒绝和任务 `finally` 中用任务身份做条件复位，避免旧任务清掉新标志。调用者运行策略可以把压力反馈给生产者，但若生产者是 HTTP 工作线程，慢查询会直接拉高响应时间，还可能占着数据库连接或请求上下文；只有把这种降速作为明确背压契约并监控时才适合使用。

#### Q59-D1｜面试官追加深挖

**追问：** 如果通过 submit 提交 FutureTask，拒绝策略却静默丢弃，调用方拿到的 Future 会处于什么状态？线程池关闭后 CallerRunsPolicy 是否仍必然运行任务，怎样避免请求合并登记和等待者永久悬挂？

**追问缘由：** 原答案提到多种拒绝策略和清理，但未展开不抛异常也不执行任务的终态缺口。

**回答：** `submit` 会先把任务包装成 `FutureTask`，再交给线程池的 `execute`。若池已饱和，而拒绝处理器采用静默丢弃，它既不运行任务，也不抛异常；`submit` 因而仍可正常返回那个 `Future`。这个任务没有线程把它从初始状态推进到成功、异常或取消，`isDone()` 会一直为假，无超时的 `get()` 可以永久等待。调用方主动 `cancel` 才能把它转为取消终态，但取消只改变任务状态；若任务其实已经开始，能否停止还取决于中断与任务协作。

`CallerRunsPolicy` 也不是任何时候都兜底运行。线程池尚未关闭时，它通常让提交线程直接执行；池已关闭时则不会执行任务，也不保证抛出异常，同样可能留下未完成的 `Future`。提交前检查 `isShutdown()` 也封不住检查后关闭的竞态，最终必须由拒绝路径给出明确终态。

用于请求合并时，不应选无反馈的丢弃策略。可以采用抛异常的拒绝策略，捕获后把共享结果显式完成为异常，并按任务身份删除登记；或者自定义拒绝处理器，把被拒绝的 `Future` 取消。正常执行、执行异常、拒绝、关闭时退回尚未运行的队列任务，都要走统一的“完成或取消＋条件清理”逻辑，等待者自身还应有超时。关闭服务时需逐项终结仍登记的任务，不能假定放进过队列就一定有人执行。

**核对依据**：[Oracle Java 8 ThreadPoolExecutor 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ThreadPoolExecutor.html)、[商铺缓存重建流程](../flow-notes/06-shop-read-and-search.md)

### Q60｜如何确定异步线程池大小和队列容量？

**口述回答**

我不会从固定公式直接抄一个线程数，而会先拆任务类型并测量服务时间。CPU 密集任务的活动线程通常接近可用核数；数据库、网络等待型任务可有更多线程，但真正上限往往是数据库连接、下游限流和可接受等待时间。线程池、连接池和并发许可要一起预算：不能让大量工作线程同时堵在较小连接池前。队列容量则由允许吸收的突发量和最大排队时延反推，并采用有界队列、明确拒绝或降级，使过载在资源耗尽前可见。

**追问展开**

1. **追问一：CPU 密集与数据库、网络等待型任务分别受什么限制？线程池、数据库连接池和接口并发许可如何协同？**

   **回答：** 可以先用压测取得单任务 CPU 时间、等待时间和下游吞吐，再从小并发逐级增加，观察吞吐何时不再增长。若一个实例只允许少量数据库回源，线程池中可能触达数据库的并发就不应远高于可用连接，还要给同步请求和管理操作留余量；批量工作线程、每任务内部并发许可和数据库连接池共同决定真实并发。网络调用也受对端容量、客户端连接池和端到端超时约束。

2. **追问二：任务持续超时还不断入队时，怎样做背压、超时和监控？为什么仅增加线程数可能让系统更慢？**

   **回答：** 持续超时时不能继续无界入队。应限制队列，记录活动线程、队列长度与队龄、拒绝数、执行/等待耗时、连接池等待和下游错误；超过预算时在入口限流、暂停拉取、降级或快速失败，并让可重试任务保留持久身份。单纯增加线程会增加上下文切换、内存栈、连接争抢和锁竞争，使更多任务同时超时；验证要看完成吞吐和尾延迟，而不是只看“线程都忙起来了”。

#### Q60-D1｜面试官追加深挖

**追问：** 假设稳定到达速率为每秒200个任务、平均执行耗时50毫秒、允许排队不超过100毫秒，你会如何估算在途并发和队列预算？为什么不能据此直接承诺P99达标，还需要测哪些分布和下游限制？

**追问缘由：** 原回答提出按时延反推容量，但没有给出可手算的量化连接及其适用前提。

**回答：** 先按利特尔法则做一阶估算：平均到达率 `λ=200/秒`，平均执行时间 `S=0.05秒`，仅执行中的平均任务数约为 `λS=10`。允许的排队时间是 `0.1秒`，按同一到达率折算约为 `λWq=20` 个排队任务，所以可把“约 10 个执行中、约 20 个等待、总在途约 30 个”作为容量试验的起点。直观上，10 个工作线程每 50 毫秒完成一轮，20 个排队任务需要约两轮即 100 毫秒才能清完。

但 10 个线程的理论服务率恰好也是每秒 200 个，利用率已经接近 100%；只要到达或耗时有一点波动，队列就会增长。因此 20 不是保证值，生产配置还要留吞吐余量，并在队龄接近预算时背压或拒绝。利特尔法则描述长期平均在途量，不从平均数推出 P99，也假设系统大致稳定。

要判断 P99，至少要测到达间隔和突发分布、执行耗时分布及二者的相关性、队列等待分布、超时与重试放大，还要观察 CPU、垃圾回收和线程调度。下游方面需核对数据库连接余量、查询与锁等待、客户端连接池、网络时延、对端并发和限流；工作线程不能多于真正可并行的下游容量。最后应以开放到达率逐级压测，联合验收完成吞吐、队龄、P99 和拒绝率，而不是用这三个平均数直接承诺尾延迟。

### Q61｜FutureTask、CompletableFuture 和线程中断如何影响超时处理？

**口述回答**

Future 的等待超时只说明调用者在限定时间内没拿到结果，不表示任务已经停止；若调用者什么都不做，后台任务仍可能完成并产生写入。FutureTask 取消时可选择尝试中断执行线程，但中断本质是协作信号：任务要检查状态或在可中断阻塞点响应，数据库驱动、套接字和远程服务还需要各自的查询或读写超时。Java 8 的 CompletableFuture 取消主要表现为异常完成，因为它不直接控制计算线程，不能把“调用了 cancel”当成外部操作被终止的证明。

**追问展开**

1. **追问一：等待结果超时是否等于任务停止？取消、设置中断标志和真正终止外部数据库请求是什么关系？**

   **回答：** `get(timeout)` 抛出超时异常只结束本次等待。随后调用 `cancel(true)`，对于 FutureTask 是尝试设置取消状态并中断正在运行的线程；线程可能吞掉中断、处于不可中断操作，或外部请求已经到达服务端，因此仍不能推导业务没有执行。数据库访问应另设连接、套接字、语句级超时，必要时使用驱动支持的取消；写操作还必须靠幂等身份和结果查询处理“不知道是否成功”。

2. **追问二：Java 8 异步回调默认可能运行在哪个线程池？异常怎样传播，如何避免阻塞共享池或遗漏收尾清理？**

   **回答：** Java 8 的 `CompletableFuture.supplyAsync`、`runAsync` 若不传执行器，通常使用公共 ForkJoinPool；把阻塞数据库调用放入其中会挤占同进程其他异步任务，应显式使用有界专用池。异常常被包装为 ExecutionException 或 CompletionException，回调链要明确记录并传播。许可、ThreadLocal 和登记项应由实际执行任务的线程按资源所有权在 `finally` 收尾，等待者超时或取消不能提前释放仍在使用的资源；若任务在执行前就被取消或静默丢弃，还要有独立的未启动收尾路径。

**核对依据**：[Oracle Java 8 Future 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)、[Oracle Java 8 FutureTask 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/FutureTask.html)、[Oracle Java 8 CompletableFuture 文档](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/CompletableFuture.html)、[请求合并的超时边界](../flow-notes/06-shop-read-and-search.md)

### Q62｜ThreadLocal 为什么会造成内存滞留或身份串用？

**口述回答**

ThreadLocal 的值不是存在线程本地变量对象里，而是存在当前 Thread 持有的内部映射中。映射条目的键对 ThreadLocal 是弱引用，值却是强引用：外部不再引用键时，键可被回收成空，但只要长寿命线程仍存活且没有触发足够的映射清理，值仍可能被线程间接持有。在线程池中工作线程会跨请求复用，如果请求结束不删除身份，下一个任务就可能读到前一用户，既是内存滞留也是越权风险。因此身份上下文必须在请求最外层建立，并在无论成功或异常都会执行的收尾点删除。

**追问展开**

1. **追问一：线程、内部映射、弱引用键和强引用值之间是什么关系？为什么键被回收不代表值马上释放？**

   **回答：** 引用链可以概括为“线程 → 内部映射 → 条目 → 值”；条目只弱引用 ThreadLocal 键。垃圾回收清掉键不等于能越过仍然存在的线程和条目去清掉强引用值，内部映射只会在后续的 `get`、`set`、`remove` 等操作中顺带探测和清理部分陈旧条目。短命线程结束后整张映射可回收，线程池线程长期存活才更危险，尤其值持有用户对象、类加载器或大缓冲区时。

2. **追问二：线程池中的长寿命工作线程为什么需要主动 `remove`？可继承线程本地变量能否安全解决线程池中的上下文传递？**

   **回答：** Web 请求应在完成回调或最外层 `finally` 调用 `remove`，且只清理当前线程上自己建立的上下文；异步子任务应显式传入必要身份并自行清理。InheritableThreadLocal 只在线程创建时从父线程复制值，线程池线程往往早已创建，因此会得到旧值或根本没有值，也无法处理任务间隔离。若确需跨池传播，可在提交时捕获最小上下文、执行前安装、执行后恢复或删除，最好由统一任务装饰器实现。

**核对依据**：[Oracle Java 8 ThreadLocal 文档](https://docs.oracle.com/javase/8/docs/api/java/lang/ThreadLocal.html)、[OpenJDK 8 ThreadLocal 源码](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/java/lang/ThreadLocal.java)、[Oracle Java 8 InheritableThreadLocal 文档](https://docs.oracle.com/javase/8/docs/api/java/lang/InheritableThreadLocal.html)、[登录上下文清理流程](../flow-notes/01-login-and-access.md)

### Q63｜Java 8 的堆、线程栈、元空间和直接内存各保存什么，怎样排查异常？

**口述回答**

堆主要保存对象和数组，是垃圾收集的核心区域；每个线程有自己的 Java 栈，保存方法栈帧、局部变量和调用状态，线程越多总栈占用越大。Java 8 用本地内存中的元空间保存类元数据，容量不再受旧永久代固定大小约束，但错误的类加载器仍可让它持续增长。直接内存常见于 NIO 缓冲区和本地库，位于 Java 堆外，却仍计入进程和容器内存。排查要先区分 Java 抛出的具体内存错误、垃圾收集恶化，还是容器达到限制直接杀进程。

**追问展开**

1. **追问一：堆空间不足、线程数过多、类加载泄漏和直接内存耗尽的线索有何不同？容器进程被杀一定会有 Java 堆溢出异常吗？**

   **回答：** 堆不足常伴随频繁完整收集、老年代存活集持续上升和堆空间错误；线程数过多会看到大量线程、栈或无法创建本地线程；类加载泄漏表现为已加载类和元空间持续增长，常与不可卸载的类加载器有关；直接内存问题可见直接缓冲池、本地内存跟踪或进程常驻内存上升，而 Java 堆并不大。容器的内存控制组触发 OOM Kill 时，操作系统可能直接终止进程，日志里不一定出现 Java 堆溢出异常。

2. **追问二：你会怎样结合 GC 日志、线程转储和堆转储定位问题，怎样控制采集大文件对现场的影响？**

   **回答：** 我会先对齐进程、容器和 GC 时间线，再低成本取得 GC 日志、类直方图、线程数/线程转储以及直接缓冲指标；确认堆内对象异常后才生成堆转储，并结合支配树和到垃圾收集根的引用链定位持有者。堆转储可能触发明显停顿、占用接近堆大小的磁盘并包含敏感数据，应先确认磁盘和权限，在单个受控实例或故障实例采集，限制重复触发，优先保留退出时自动转储并妥善脱敏和销毁。

**核对依据**：[Java 虚拟机规范 2.5 运行时数据区](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-2.html)、[Oracle Java 8 故障诊断工具](https://docs.oracle.com/javase/8/docs/technotes/guides/troubleshoot/tooldescr006.html)、[Oracle Java 8 本地内存跟踪](https://docs.oracle.com/javase/8/docs/technotes/guides/troubleshoot/tooldescr007.html)

### Q64｜请求 P99 周期性升高，如何判断是不是 GC 导致？

**口述回答**

我会把同一时间基准上的请求 P99、吞吐、错误率、CPU、线程池队列与 GC 日志叠在一起，看尾延迟尖峰是否稳定覆盖停顿区间，并检查尖峰前的分配速率、年轻代回收频率、对象晋升、老年代占用和完整收集原因。相关性只是起点：CPU 抢占、数据库慢查询和排队也可能恰好同时发生。Java 8 实际使用的收集器必须从启动命令、运行时标志或 GC 日志确认；当前工程配置没有显式指定应用收集器，不能拿较新 JDK 的默认值或开发机猜测来回答。

**追问展开**

1. **追问一：对象分配、晋升、停顿与吞吐之间有什么关系？Java 8 使用哪种收集器需要从哪里确认？**

   **回答：** 高频分配先增加年轻代回收；存活对象晋升过快会推高老年代压力，晋升失败或元数据阈值等原因可能触发更长停顿。停顿会直接拉高在途请求延迟，过多收集也会吞噬应用吞吐，但低暂停不等于高吞吐。确认命令可查看完整启动参数和运行时 `VM.flags`，日志则要识别收集器名称、原因、各区前后容量和停顿时间；Java 8 的默认选择还受服务器类别和平台影响，不能只凭版本号断言。

2. **追问二：如果根因是无界任务队列或长时间持有的大集合，单纯调大堆是否解决问题？如何用修改前后的同负载证据验证？**

   **回答：** 无界任务队列或大集合长期持有对象时，调大堆只是延后耗尽，还可能扩大活跃集和某些停顿；根治应限制队列、建立背压、减少对象生命周期并修正所有权。验证采用相同机器和相同负载曲线，充分预热后重复修改前后实验，只改变一个主要变量，同时比较 P50/P99、完成吞吐、错误率、分配率、活跃集、各类 GC 停顿以及队列长度；若尖峰与停顿脱钩，就应继续查线程调度和下游等待。

### Q65｜Spring 声明式事务依靠什么生效，哪些调用会绕过事务？

**口述回答**

Spring 声明式事务通常由代理拦截一次方法调用：调用进入代理后，事务拦截器按属性开启或加入事务，把连接等资源绑定到当前线程，调用目标方法，再依据返回或异常提交、回滚。关键不是“方法上写了注解”这一静态事实，而是调用是否真正经过代理。目标对象内部用 `this` 自调用不会重新穿过代理，私有方法也不能按常见代理模式独立成为外部拦截入口。把事务方法拆到另一个受容器管理的组件，是为了让跨组件调用经过代理，同时也会真实改变事务传播和物理连接边界。

**追问展开**

1. **追问一：代理调用、自调用、方法可见性和异常是否向外传播如何影响事务？为什么把事务拆到另一个业务组件可能改变行为？**

   **回答：** 外部调用代理的可拦截方法才应用事务属性；自调用直接进入目标方法，新增或新建事务等声明不会生效。在本项目的 Spring 5.2 常规代理式注解事务口径下，应把事务入口设计为可被代理调用的 `public` 方法；接口代理主要拦截接口调用，类代理也不能覆盖 `final` 或私有方法。项目的单笔发券事务放在独立组件并使用“新建事务”，使批处理调用能真的暂停外层事务并开启新事务；这不是单纯调整代码风格，而是改变了每笔提交和失败隔离。

2. **追问二：默认回滚规则是什么？捕获异常后正常返回、抛受检异常和开启异步线程各应怎样分析？**

   **回答：** 默认规则是未检查异常 RuntimeException 和 Error 触发回滚，受检异常默认不回滚，除非配置 `rollbackFor`。方法捕获异常后正常返回，代理通常会提交，除非重新抛出或显式标记回滚；反过来，内部加入同一事务的方法把事务标成只能回滚，即使外层捕获，也可能最终失败。事务资源绑定在线程上，新开的异步线程不会继承调用方物理事务；等待异步结果也不会把两个线程的数据库操作合成一个原子事务。

**核对依据**：[Spring 5.2 声明式事务文档](https://docs.spring.io/spring-framework/docs/5.2.x/spring-framework-reference/data-access.html)、[Spring Boot 2.3.12 依赖版本](https://docs.spring.io/spring-boot/docs/2.3.12.RELEASE/reference/html/appendix-dependency-versions.html)、[发券事务边界](../flow-notes/03-voucher-grant.md)、[独立发放事务源码](../../../src/main/java/com/localdeals/service/VoucherGrantTransactionService.java)

### Q66｜加入事务、新建事务与嵌套事务有什么区别？

**口述回答**

`REQUIRED` 有外层事务就加入，没有才新建，因此内外共享同一物理事务，最终只能一起提交或回滚。`REQUIRES_NEW` 总是暂停外层事务并开启独立物理事务，内层可以先提交，但会额外占用连接；外层后来回滚不会撤销已经提交的内层。`NESTED` 通常在同一物理事务内建立保存点，内层失败可回滚到保存点让外层继续，但最终耐久性仍取决于外层提交。三者不能只记成“异常是否隔离”，还要结合代理是否生效、连接池容量、数据库保存点支持和调用方快照来分析。

**追问展开**

1. **追问一：内层失败后外层捕获异常，什么时候仍可能在提交时发现只能回滚？保存点能否等同独立提交？**

   **回答：** 内层 `REQUIRED` 与外层共用事务，它即使把异常抛出后被外层捕获，也可能已把共享事务标成 rollback-only；外层到提交点才收到 UnexpectedRollbackException，防止调用方误以为已提交。`REQUIRES_NEW` 的回滚标记只影响独立内层，但每个外层线程可能同时占着一个连接并等待另一个连接，池太小会互相等待。`NESTED` 的保存点只是同一事务内的局部回退，不是独立提交；外层整体回滚时，保存点之后和之前的修改都会消失。

2. **追问二：方法没有事务注解，是否意味着其数据库查询一定没有外层事务？结合批量发券解释快照和连接复用。**

   **回答：** 没有事务注解只表示该方法自身不声明新的事务属性，并不表示调用时一定无事务；若它在外层事务线程中执行，数据库查询仍会复用外层绑定的连接、隔离级别和读视图。当前批量发券先有外层批处理事务，每笔独立事务完成后，回到普通门面方法的查询仍可能处于恢复后的外层事务，在可重复读下读到旧快照。容量上也要为“外层占一条连接、内层再借一条”的并发模式留余量，不能只按工作线程数等额配置连接。

**核对依据**：[Spring 5.2 事务传播文档](https://docs.spring.io/spring-framework/docs/5.2.x/spring-framework-reference/data-access.html)、[发券传播与快照边界](../flow-notes/03-voucher-grant.md)、[MySQL 8 一致性读](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)、[批任务外层事务源码](../../../src/main/java/com/localdeals/service/VoucherBatchJobService.java)、[发放查询与异常处理源码](../../../src/main/java/com/localdeals/service/VoucherGrantService.java)

### Q67｜Spring 如何完成依赖注入、Bean 生命周期和自动配置？

**口述回答**

Spring 先读取配置并形成 Bean 定义，解析构造器依赖后实例化对象，再填充属性依赖，调用感知接口和各类后置处理器，执行初始化回调，最后还可能由后置处理器返回代理对象；容器关闭时再对已完成创建的单例执行销毁回调。依赖注入的价值是由容器组装对象和替换实现，而不是业务代码自行定位依赖。Spring Boot 自动配置则是在类路径、已有 Bean、属性等条件满足时补充默认配置，用户显式配置通常可以使其退让；最终是否启用要看实际属性源、激活的 profile 和条件评估，不能只看依赖已加入。

**追问展开**

1. **追问一：对象构造、依赖注入、初始化回调与代理生成的大致关系是什么？在启动初始化中访问 ES 失败会如何影响应用可用性？**

   **回答：** 可简化理解为“构造 → 注入 → 初始化前处理 → 初始化回调 → 初始化后处理/代理”，但个别后置处理器能提前介入，不能把它当成所有 Bean 的逐行固定实现。若启动初始化回调同步连接搜索引擎、创建索引并全量写入，而异常继续抛出，该 Bean 创建会失败，通常导致应用上下文刷新失败，整个实例不可用。应根据业务要求把外部依赖做成启动硬门槛、带超时的就绪检查，或可重试的独立初始化任务，不能悄悄吞错并宣称索引可用。

2. **追问二：循环依赖为什么不是都能解决？配置覆盖、条件装配和 profile 怎样影响你认为“已经启用”的恢复任务？**

   **回答：** 构造器循环依赖在双方实例化前就互相需要，无法靠暴露半成品解决；部分单例属性注入循环可能借助提前引用通过，但原型作用域、代理增强和初始化时调用都可能使它失败或拿到未就绪对象，因此更好的办法是拆分职责。恢复任务是否运行还取决于配置优先级、环境变量、命令行、profile 以及条件装配。本项目多项恢复工作默认关闭，所以“代码存在”不等于“当前环境已启用”，应查看启动时的有效配置和条件报告。

#### Q67-D1｜面试官追加深挖

**追问：** 如果在本Bean的初始化回调中调用标有 @Transactional 的方法，为什么不能仅凭注解认为事务已经生效？请结合代理生成时机与自调用说明，并给出一个能明确经过代理的初始化任务组织方式。

**追问缘由：** 生命周期和事务代理分别说明过，但尚未连接启动初始化调用与事务生效时点。

**回答：** `@Transactional` 通常由 Spring AOP 代理在方法调用边界开启和结束事务，不是注解一出现，目标对象内部任意调用就自动带事务。本 Bean 的初始化回调执行时，对象仍处于创建流程，初始化后处理器可能尚未返回最终代理；而回调中写 `this.事务方法()`，即使最终已有代理，也属于目标对象自调用，不经过代理拦截。因此不能仅凭方法上的注解断言事务已经生效，异常回滚和传播属性都可能没有预期语义。通过提前暴露自身代理来绕过还会引入生命周期和循环依赖问题，不适合作为默认方案。

可以把事务工作拆到另一个 Bean 的公开方法中，由专门的启动协调器在容器完成刷新后调用它。例如协调器实现 `ApplicationRunner`，或监听应用就绪事件；它注入的是事务工作 Bean 的代理，调用从协调器跨 Bean 进入公开事务方法，代理便能明确建立事务。启动是否必须等任务成功、失败是否阻断就绪、如何超时与重试，还应作为独立运行契约定义，而不是由初始化回调偶然决定。

如果任务确实必须在较早生命周期同步执行，也可在协调器中使用 `TransactionTemplate` 显式包住数据库步骤，这不依赖自调用代理。无论采用哪种方式，都应以一次故意抛错的集成验证确认数据库修改整体回滚；现有材料未给出这个特定初始化自调用已经受事务保护的证据。

**核对依据**：[Spring 5.2 容器与 Bean 生命周期](https://docs.spring.io/spring-framework/docs/5.2.x/spring-framework-reference/core.html)、[Spring Boot 2.3.12 外部化配置与自动配置](https://docs.spring.io/spring-boot/docs/2.3.12.RELEASE/reference/htmlsingle/)、[商铺搜索启动边界](../flow-notes/06-shop-read-and-search.md)、[当前应用配置](../../../src/main/resources/application.yaml)

### Q68｜可重复读和读已提交有什么区别，MVCC 怎样支持一致性读？

**口述回答**

InnoDB 的多版本并发控制（MVCC）借助事务标识和 undo 历史，让普通一致性读选择对当前读视图可见的版本，而不必给这些记录加共享锁。在 MySQL 8 的可重复读下，事务内第一次普通一致性读通常建立快照，后续普通查询复用它；读已提交则每次一致性读建立新快照，所以能看到查询开始前已提交的新数据。锁定读和更新属于当前读，要读取足以加锁或修改的最新可见版本。因此同一事务可以普通查询仍看旧快照，却通过锁定读或更新接触更新状态，两类读不能混成一句“都可重复”。

**追问展开**

1. **追问一：读视图何时建立，普通查询与锁定读分别如何读取数据？同一事务能否先读旧快照、再通过更新接触新状态？**

   **回答：** 读视图根据活跃事务范围判断某版本是否可见，若不可见就沿 undo 版本链寻找旧版本。可重复读的普通 `SELECT` 在首次一致性读时建立并复用视图；带锁查询、更新和删除要基于当前状态加锁。于是事务可以先普通查询看见余额 10，另一个事务提交为 8 后，本事务普通查询仍见 10，却用条件更新作用于当前版本 8；应用若先用快照判断、再用当前读写入，必须检查锁定结果或影响行数，不能沿用旧判断。

2. **追问二：活动锁后再查重为什么不能简单保证看到最新提交？你怎样构造两个会话的最小验证实验？**

   **回答：** 当前发券链路在事务内先普通查重，随后锁定活动记录，再做普通查重；若第一次查询已经建立可重复读快照，锁并不会自动把后一次普通查询升级为当前读。最小实验可让会话 A 开启可重复读并先查到“无权益”，会话 B 插入权益并提交；A 再做一次锁定读确认当前活动，随后普通查重仍可能为空，最终插入由唯一约束拒绝。改用读已提交重复实验，第二次普通查重可见 B。即便数据库约束防止重复，竞争者也可能先因名额耗尽返回，不能保证都直接返回已有权益。

**核对依据**：[MySQL 8 事务隔离级别](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html)、[MySQL 8 一致性读](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)、[发券并发与读视图边界](../flow-notes/03-voucher-grant.md)

### Q69｜InnoDB 行锁实际锁在哪里，什么情况下会扩大范围？

**口述回答**

InnoDB 所谓“行锁”实际落在查询扫描到的索引记录上，而不是脱离访问路径直接锁抽象业务行。锁的范围由隔离级别、查询条件、索引是否唯一、记录是否存在以及优化器采用的索引共同决定。主键或唯一索引的命中等值查询通常可缩小为记录锁；可重复读下，非唯一条件和范围扫描常使用记录与前方间隙组合的临键锁，以防扫描范围出现幻行。缺少合适索引时需要扫描许多索引记录，锁也可能覆盖大范围，所以“SQL 条件看起来只找一行”不等于只锁一行。

**追问展开**

1. **追问一：主键等值、唯一索引等值、非唯一范围扫描和缺少合适索引时，记录锁、间隙锁和临键锁如何影响并发？**

   **回答：** 已存在的主键、完整唯一键等值命中通常只需锁对应记录；查找不存在值、非唯一索引或范围条件，在可重复读下可能涉及间隙锁或临键锁。读已提交一般减少间隙保护并会更早释放不匹配记录锁，但外键检查、重复键检查等仍有例外。若优化器走全索引扫描，扫描到的记录都可能进入锁定范围。面试时应说“以执行计划和实际加锁为准”，而不是把主键、普通索引、无索引机械映射为固定锁型。

2. **追问二：发券锁活动再锁资格，其他入口反向加锁可能发生什么？如何发现死锁，并让业务重试保持幂等？**

   **回答：** 多资源事务必须约定全局加锁顺序。当前发券路径先锁活动，再锁资格；若另一入口反过来持有资格并等待活动，两条事务可能构成等待环而被数据库选择一个牺牲者。应统一顺序、缩短事务、为条件字段建合适索引，并采集死锁日志和 InnoDB 状态还原双方 SQL 与索引。死锁重试必须重跑完整事务，使用稳定业务幂等身份和唯一约束，并加入退避与次数上限，不能只重发最后一条写入。

#### Q69-D1｜面试官追加深挖

**追问：** 可重复读下，两个事务都用唯一键 SELECT FOR UPDATE 查询同一个不存在的权益，各自查空后再插入，为什么“先锁再插”仍可能出现等待或死锁？请解释不存在时锁的是哪一段、间隙锁彼此与插入意向锁如何相互作用。

**追问缘由：** 现有回答提到不存在记录和间隙锁，但没有展示查空后并发插入的具体机制。

**回答：** 唯一键对应的记录不存在时，没有现成索引记录可加普通记录锁。可重复读下，加锁查询通常会在该值应插入的位置保护索引间隙，边界是相邻的前驱与后继索引记录。间隙锁的主要作用是禁止向这段空隙插入，它们彼此可以兼容，所以事务甲、乙都可能成功取得同一段间隙保护并同时查到空；这与“已经把不存在的业务对象独占住”不是一回事。

接着甲、乙都尝试插入该唯一键。插入前需要取得插入意向锁并做唯一性检查；插入意向与另一事务持有的冲突间隙锁不兼容。于是甲保留自己的间隙锁、等待乙的保护放行，乙也保留自己的间隙锁、等待甲放行，可能形成等待环并由死锁检测选择一个事务回滚。不同具体时序下，也可能是一方先插入，另一方等待其唯一键结果，待其提交后收到重复键；实际锁型还受执行计划和索引定义影响。

所以“先查空再插入”仍要把唯一约束作为最终防线，并把死锁、锁等待超时和重复键设计成可识别结果：整个短事务回滚后按稳定幂等身份重试或读取赢家。若业务必须在插入前串行判断，可锁一个必然存在且粒度合适的父记录，例如对应用户与活动的协调行，并统一加锁顺序；不能指望对不存在唯一键的加锁查询天然选出唯一赢家。

**核对依据**：[MySQL 8 InnoDB 锁类型](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking.html)、[MySQL 8 语句加锁规则](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)、[MySQL 8 死锁处理](https://dev.mysql.com/doc/refman/8.0/en/innodb-deadlocks.html)、[发券锁顺序](../flow-notes/03-voucher-grant.md)

### Q70｜怎样为订单查询、商户列表和待处理事件扫描安排索引字段？

**口述回答**

我会从真实查询契约反推复合索引：先放稳定的等值过滤字段，再考虑范围字段与排序字段，最后评估是否附带少量返回列形成覆盖索引。例如用户在某活动下查订单，适合把用户和活动放在同一索引并按业务不变量决定是否唯一；商户列表可围绕商户、状态及稳定翻页标识设计；待处理事件扫描可围绕状态、下次执行时间和标识设计。字段顺序必须服务最常见且最昂贵的访问路径，不能用“选择性最高永远放第一”或“每列各建一个索引”替代执行计划验证。

**追问展开**

1. **追问一：最左前缀、范围条件、排序、回表与覆盖索引怎样影响选择？为什么每个字段都建索引未必更好？**

   **回答：** 联合索引能从最左前缀连续利用字段；等值列之后的第一个范围条件往往限制后续列继续用于缩小扫描，但后续列仍可能参与索引条件下推或覆盖。排序只有在过滤与索引方向满足条件时才可避免额外排序，覆盖索引可减少回表，却会增大索引和写放大。每个额外索引都会消耗空间、缓存和插入更新成本，重叠索引还会增加优化器选择负担，因此要按查询簇合并并删除无收益索引。

2. **追问二：怎样通过执行计划与实际行数发现扫描过多？深分页、大 IN 列表以及按指定 ID 顺序排序各有什么代价？**

   **回答：** 先用 `EXPLAIN` 看访问类型、候选/实际索引、估算行数、额外排序和临时表，再在可控环境用 `EXPLAIN ANALYZE` 对比实际行数、循环次数与耗时；估算和实际偏差大还要检查统计信息及数据倾斜。深 `OFFSET` 分页仍要扫描并丢弃前面的行，优先用稳定排序键做游标翻页；超大 `IN` 会增加解析、范围构造和随机访问；按输入标识指定顺序通常需要额外排序，所以当前批量回库虽能恢复搜索排名，仍要限制候选规模。

#### Q70-D1｜面试官追加深挖

**追问：** 对于 WHERE status = ? AND next_time <= ? ORDER BY next_time, id LIMIT ?，索引(status, next_time, id)为什么合适？下一页有多条相同next_time时，应怎样把上一页的(next_time, id)写成续查条件，避免只按时间翻页漏数据？

**追问缘由：** 现有索引建议较抽象，缺少范围列、稳定排序与复合游标如何共同使用的最小例子。

**回答：** 这个查询先对 `status` 做等值过滤，再对 `next_time` 做到期范围扫描，并按 `next_time, id` 取最前一批。索引 `(status, next_time, id)` 让数据库先定位一个状态的连续索引区间，再沿时间和标识的索引顺序扫描；`id` 既提供相同时间下的确定次序，也可能减少额外排序。范围列之后的标识通常不再大幅缩小最初的扫描区间，但仍可用于有序遍历、索引条件或覆盖，最终是否避免排序要用执行计划确认。

假设升序分页，第一页最后一条游标为 `(t0, i0)`，并固定本轮截止时间 `cutoff`，下一页条件应写成：

```sql
WHERE status = :status
  AND next_time <= :cutoff
  AND (next_time > :t0 OR (next_time = :t0 AND id > :i0))
ORDER BY next_time ASC, id ASC
LIMIT :batchSize
```

例如上一页止于 `10:00, 42`，下一页先接着取 `10:00` 且标识大于 42 的记录，再取更晚时间；若只写 `next_time > 10:00`，同为 `10:00` 的 43、44 就会漏掉。降序时比较符号整体反向。固定 `cutoff` 可避免翻页期间新到期记录不断改变本批范围；但若处理过程会修改状态或下次时间，仍需结合条件认领、事务边界和重复扫描保证并发安全，复合游标本身只解决稳定续查。

**核对依据**：[MySQL 8 多列索引](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)、[MySQL 8 EXPLAIN](https://dev.mysql.com/doc/refman/8.0/en/explain.html)、[MySQL 8 ORDER BY 优化](https://dev.mysql.com/doc/refman/8.0/en/order-by-optimization.html)、[商铺搜索回库顺序](../flow-notes/06-shop-read-and-search.md)

### Q71｜redo log、undo log 和 binlog 分别解决什么问题？

**口述回答**

redo log 是 InnoDB 的预写式重做日志，记录页面修改所需的信息，使已提交变更在数据页尚未刷盘时仍可在崩溃恢复中重做。undo log 保存撤销和历史版本信息，既支持事务回滚，也让多版本一致性读沿版本链读取旧数据。binlog 位于 MySQL 服务器层，记录数据库变更事件，用于复制、时间点恢复以及 Canal 一类变更订阅。三者不是互相替代：回滚主要依赖 undo，存储引擎崩溃恢复依赖 redo，跨实例传播和下游订阅依赖 binlog；业务还需确认日志保留和订阅位点。

**追问展开**

1. **追问一：事务回滚、崩溃恢复、主从复制与 Canal 订阅分别依赖哪些日志？数据库返回提交成功的耐久性与哪些配置有关？**

   **回答：** 数据库返回提交成功的耐久性还取决于刷盘配置与底层存储保证。常见强耐久基线是每次提交把 InnoDB 日志刷到持久介质，并让 binlog 每次提交同步，但具体配置、文件系统和硬件缓存都要核对；降低同步频率会用潜在数据损失换吞吐。事务回滚不会靠 binlog“反向执行”，从库复制和 Canal 也不读取应用表猜变化，而是消费已写入的 binlog 事件并维护自己的位点。

2. **追问二：为什么数据库提交与 binlog 记录需要协调？主从延迟时，从副本查不到订单为何不足以触发库存补偿？**

   **回答：** 若 redo 已认为事务提交而 binlog 没有该事务，主库恢复与复制视图会分裂；反之也会产生不可正确重放的事件。MySQL 用内部的准备与提交协调，让存储引擎状态和 binlog 在恢复后保持一致。副本存在复制延迟时，“副本暂时查不到订单”只代表观察可能陈旧，不能证明主库未提交；据此释放库存可能重复放回已售名额。本项目数据库条件扣减仍能阻止库存变负，但会产生额外准入、库存偏差和后续失败。补偿应查询权威主库，或采用经验证的一致性读取协议，并把查询超时归类为未知，而不是当成订单不存在。

#### Q71-D1｜面试官追加深挖

**追问：** 请分别分析两种宕机点：redo已prepare但binlog尚未完整持久化；binlog已完整持久化但redo最终commit记录尚未完成。恢复时根据什么决定提交或回滚，为什么只看redo里有没有commit不够？

**追问缘由：** 原答案只概述内部准备与提交协调，没有解释两阶段提交在关键崩溃窗口的裁决依据。

**回答：** 两阶段协调会用同一事务标识把 InnoDB 的准备状态与 binlog 中的完整事务关联起来。第一种宕机发生时，redo 只有 `prepare`，而 binlog 事务尚未完整落到可恢复边界；重启会忽略或截断不完整的 binlog 尾部，并发现这个准备事务没有对应的完整 binlog 提交证据，因此利用 undo 回滚它。这样主库不会保留一笔从库和变更订阅永远看不到的提交。

第二种宕机时，binlog 已完整持久化并包含该事务及其结束标识，但 redo 的最终 `commit` 记录还没完成。恢复发现 InnoDB 事务处于准备态，同时能在有效 binlog 中找到同一事务标识，就把它判定为提交并完成存储引擎提交；否则从库可能已经按 binlog 应用了一笔主库却回滚的数据。恢复过程还会结合 redo 重做应保留的页修改，并利用 undo 回滚应撤销的事务；这里不把它夸大成固定的“先裁决、后重做”阶段顺序。

所以只看 redo 有没有 `commit` 不够：第一种和第二种在 redo 中都可能只表现为已准备，真正区分它们的是 binlog 是否存在完整、可恢复且能匹配的事务。反过来，只有零散或未闭合的 binlog 字节也不能作为提交证据。上述结论还以日志确实按相应耐久配置写入稳定介质为前提；若降低 redo 或 binlog 的提交刷盘强度，断电时可保留到哪里要按实际配置和存储保证重新界定，现有材料没有给出运行环境配置值。

**核对依据**：[MySQL 8 redo log](https://dev.mysql.com/doc/refman/8.0/en/innodb-redo-log.html)、[MySQL 8 undo log](https://dev.mysql.com/doc/refman/8.0/en/innodb-undo-logs.html)、[MySQL 8 binlog](https://dev.mysql.com/doc/refman/8.0/en/binary-log.html)、[MySQL 8 binlog 耐久配置](https://dev.mysql.com/doc/refman/8.0/en/replication-options-binary-log.html)、[商铺索引同步边界](../flow-notes/06-shop-read-and-search.md)

### Q72｜使用 MyBatis-Plus 后，哪些 SQL 正确性和性能问题仍要自己负责？

**口述回答**

MyBatis-Plus 减少了单表增删改查和条件构造的样板代码，但不会替业务选择正确的事务、索引、锁、唯一约束或查询次数。生成了合法 SQL 不代表并发安全：库存、配额和状态流转仍要写成带旧状态或下限条件的更新，并检查影响行数；分页和批量查询仍需观察执行计划。动态排序只能从服务端白名单映射到列，不能把客户端片段直接拼入 SQL；空值是否忽略、是否写成 NULL 也受更新策略影响，必须通过最终 SQL 和测试确认，而不能假设框架会自动安全。

**追问展开**

1. **追问一：条件更新的影响行数为什么是业务判断的一部分？拼接排序片段、动态条件和空值字段更新各有哪些风险？**

   **回答：** 条件更新返回 1，表示当前状态满足且本次取得了转换权；返回 0 可能是库存已空、状态已变化或目标不存在，应转成明确业务结果，不能仍返回成功。动态条件若漏掉租户、商户或状态约束会扩大修改范围；客户端控制的列名、排序方向和尾部片段若直接拼接会产生注入风险；对象字段为 `null` 时，框架可能按字段或全局策略忽略更新，也可能写入空值，所以“传了空”不能替代显式清空语义。

2. **追问二：逐条补作者与点赞状态会产生怎样的查询放大？批量查询后如何恢复原始排名，又怎样处理缺失行？**

   **回答：** 列表有 N 条结果后逐条查询作者和当前用户是否点赞，可能放大为 `1 + 2N` 次访问，尾延迟和连接占用随 N 增长。应先收集去重标识，用一到数次批量查询构造映射，再按原始候选列表回填，整体保持常数次往返。数据库 `IN` 查询不保证按输入顺序返回，因此要显式重排；批量结果缺少某行时应按契约跳过、保留占位或报数据不一致，不能空指针，也不能让页内顺序错位。

**核对依据**：[MyBatis-Plus 3.4.3 源码标签](https://github.com/baomidou/mybatis-plus/tree/v3.4.3)、[MyBatis 动态 SQL 官方文档](https://mybatis.org/mybatis-3/dynamic-sql.html)、[发布与关注流查询边界](../flow-notes/05-publish-and-follow-feed.md)、[商铺批量回库流程](../flow-notes/06-shop-read-and-search.md)

## 九、HTTP、网络与接口安全（Q73～Q76）

### Q73｜客户端超时、断开或收到网关错误，能否判断服务端没有成功？

**口述回答**

不能一概而论。DNS 解析、连接池借用、TCP 建连和代理转发都可能超时，具体由哪项超时参数覆盖，要看客户端实现；建连尚未完成时，服务端也许尚未收到应用请求。读取超时和客户端断开则常发生在请求已经发送之后，服务端可能仍在执行、已经提交数据库，甚至只是在响应返回途中丢失。网关的 502、504 也只描述网关观察到的上游失败或超时，不是业务事务的否定证明。对已经发出、执行结果不确定的写请求，应使用稳定业务标识幂等重试并查询权威结果，不能凭网络错误盲目补偿。

**追问展开**

1. **追问一：连接超时、读取超时和业务处理超时分别发生在哪一段？重试写请求为什么需要业务幂等身份？**

   **回答：** 连接超时覆盖建立连接前后的网络等待；读取超时是连接已建立、请求可能已发出，但限定时间没读到响应；业务处理超时是服务端或业务编排主动规定的截止时间。三者的观察位置不同，都不能自动回滚已到达下游的动作。重试 POST 若每次生成新身份，会把同一次用户意图执行多次；应让同一意图复用幂等键，服务端原子记录键、请求摘要和最终结果，参数冲突则拒绝。

2. **追问二：200、401、403、404、409、429、500 和 503 在本项目情境下怎样区分？HTTP 成功与异步业务成功如何通过契约表达？**

   **回答：** 200 表示本次 HTTP 交互成功并按契约返回，不必然表示异步订单已落库；401 是缺失或无效身份，403 是身份有效但无权限，404 是资源不存在或按策略隐藏，409 是当前资源状态冲突，429 是请求过多，500 是未预期内部错误，503 是容量或依赖暂不可用。异步受理应返回稳定业务标识和“处理中”语义，查询接口再给出成功、明确失败或未知；不要让一个模糊的 `success=true` 同时代表消息已接纳和最终业务已提交。

**核对依据**：[RFC 9110 HTTP 语义](https://www.rfc-editor.org/rfc/rfc9110.html)、[RFC 6585 的 429 状态](https://www.rfc-editor.org/rfc/rfc6585.html)、[秒杀请求与最终状态边界](../flow-notes/02-seckill.md)、[登录与权限状态语义](../flow-notes/01-login-and-access.md)

### Q74｜一次 HTTPS 请求到达 Spring Boot 服务前大致经过哪些步骤？

**口述回答**

按常见的 HTTP/1.1 或 HTTP/2 经 TCP 的 HTTPS 路径，客户端先通过缓存或解析器完成 DNS 名称解析，得到入口地址；随后与网关或服务建立 TCP 连接，通过握手同步初始序号并确认双向通信；再进行 TLS 握手，验证证书、协商协议与密钥，形成加密通道；之后发送 HTTP 请求。请求还可能经过负载均衡、反向代理和容器网络才到应用端口。已有连接复用可省去重复 DNS、TCP 和 TLS 成本，所以延迟分析要区分首次连接与复用连接。HTTP/3 使用 QUIC，不能直接套用这条 TCP 时序。

**追问展开**

1. **追问一：DNS、TCP 建连、TLS 握手和连接复用各影响什么延迟？TCP 的可靠传输为什么不能保证业务只执行一次？**

   **回答：** DNS 受缓存命中和递归查询影响；TCP 建连至少有网络往返，丢包会增加重传；TLS 还要验证服务身份并协商会话密钥，版本和会话恢复影响往返数；连接池复用则分摊这些固定成本。TCP 保证一条连接上的字节有序、可靠交付，不理解业务事务：客户端没收到响应后重连重试，第一次请求可能已经提交，第二次仍会再次送达，所以“可靠传输”不等于“业务恰好执行一次”。

2. **追问二：大量短连接、TIME_WAIT 或连接池耗尽分别会出现什么现象？TCP 流量控制与拥塞控制有什么区别？**

   **回答：** 大量短连接会增加握手 CPU、往返延迟和套接字资源，主动关闭的一侧可能积累 TIME_WAIT，最终耗尽临时端口或连接跟踪资源；连接池耗尽则表现为获取连接等待、超时和吞吐平台期，应同时检查池内借用与目标端连接。流量控制保护接收端，主要由接收窗口限制发送者；拥塞控制保护网络路径，根据丢包或拥塞信号调整拥塞窗口。两者最终共同限制在途数据量，但解决的问题不同。

**核对依据**：[RFC 1035 域名系统](https://www.rfc-editor.org/rfc/rfc1035.html)、[RFC 9293 TCP](https://www.rfc-editor.org/rfc/rfc9293.html)、[RFC 8446 TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)、[RFC 5681 TCP 拥塞控制](https://www.rfc-editor.org/rfc/rfc5681.html)

### Q75｜代理转发头、跨域与会话凭据分别有哪些信任边界？

**口述回答**

转发 IP 头是普通请求数据，客户端可以伪造，只有请求的直接来源确实属于受控代理时才能按约定解析；否则应使用直接连接地址。当前项目也以显式可信代理名单作为这条边界。跨域资源共享（CORS）只约束浏览器是否允许脚本读取跨源响应，不会验证用户身份，非浏览器客户端也不受它保护。会话凭据才代表身份，服务端每次还要校验有效期、撤销状态和资源归属。三条边界分别解决来源推断、浏览器读取策略和业务授权，任何一条都不能替代另外两条。

**追问展开**

1. **追问一：为什么不能直接相信客户端提供的转发 IP？可信代理配置错误会怎样影响登录和秒杀 IP 限流？**

   **回答：** 若服务直接信任任意转发头，攻击者可伪造不同地址绕过登录或秒杀 IP 限流，也能污染审计；若生产代理未列入可信范围，应用又只看直接地址，所有用户可能被识别为同一个代理，形成误限流。正确做法是只信任明确网段或代理实例，限制服务端口只能由这些代理访问，按代理追加规则从可信边界解析地址链，并记录直接地址和解析结果以便审计。

2. **追问二：CORS 能否替代身份认证或商户权限校验？长期 token 放在 URL、日志或浏览器存储中分别需要考虑什么风险？**

   **回答：** 即使 CORS 只允许一个前端域名，攻击者仍可用脚本、移动客户端或服务端直接调用接口，所以身份认证和商户资源归属必须在服务端执行。长期令牌放在 URL 会进入历史、代理/服务日志和可能的 Referer；放在可被脚本读取的浏览器存储中则重点防范跨站脚本攻击。安全 Cookie 可借助 HttpOnly、Secure、SameSite 降低部分风险，却要配合跨站请求伪造防护。短期一次性连接票据应代替在 WebSocket URL 中暴露长期令牌。

#### Q75-D1｜面试官追加深挖

**追问：** 恶意页面向使用Cookie会话的接口发送一个不需要预检的跨站请求，服务端也没有返回允许跨域的响应头，这能保证写操作未执行吗？请区分浏览器发送请求与允许脚本读响应，再说明SameSite和CSRF校验各在哪一步起作用。

**追问缘由：** 现有回答指出CORS不能授权，但尚未用具体请求区分响应不可读与写入副作用。

**回答：** 不能保证。恶意页面可以提交一个浏览器认定为“简单请求”的表单，例如跨站 `POST` 且使用表单编码；这类请求不需要先发预检。若会话 Cookie 按浏览器策略被带上，服务端可能已经完成认证并提交写事务，之后才返回响应。没有允许跨域响应头，只会让恶意页面的脚本无法读取响应内容，并不会撤销已经发送的请求或服务端副作用；普通表单跳转甚至不是靠脚本读取响应来发动攻击。

`SameSite` 在浏览器准备请求、决定是否附带 Cookie 时起作用。`Strict` 通常最严格地阻止跨站携带，`Lax` 对跨站子请求和不安全方法有限制，`None` 配合 `Secure` 则允许跨站发送；具体导航例外和旧客户端行为需按目标浏览器验证。因此它能减少携带身份的跨站请求，但不能替代服务端校验，也不能修复把写操作设计成 `GET`、同站子域受控失陷等问题。

CSRF（跨站请求伪造）校验发生在请求已经到达服务端之后、任何业务写入之前。服务端应要求攻击页面无法获知且与会话绑定的令牌，或采用经过严格设计的双重提交令牌，并可结合 `Origin`/`Referer` 校验；令牌缺失或不匹配就直接拒绝，不开启业务副作用。CORS 决定响应能否交给跨源脚本，SameSite决定 Cookie 是否随请求发送，CSRF令牌决定携带 Cookie 的请求是否具有合法操作意图，三者位置和职责不同。

**核对依据**：[RFC 7239 转发信息](https://www.rfc-editor.org/rfc/rfc7239.html)、[Fetch 标准的 CORS 协议](https://fetch.spec.whatwg.org/#http-cors-protocol)、[RFC 6750 持有者令牌用法](https://www.rfc-editor.org/rfc/rfc6750.html)、[登录、可信代理与连接票据边界](../flow-notes/01-login-and-access.md)

### Q76｜WebSocket 为什么适合在线提示，却不能直接当可靠业务消息队列？

**口述回答**

WebSocket 在一次 HTTP 升级后保留双向长连接，适合低延迟地提示“订单状态可能变化”，但连接只代表某个时刻某个实例上的在线通道。浏览器掉线、服务实例重启、网络切换或发送缓冲失败时，消息可能消失；协议本身没有业务级持久存储、消费确认、重试、去重和离线补发。当前项目用本地连接表保存在线会话、以 Redis 发布订阅跨实例路由，仍属于尽力而为通知。最终订单或权益状态必须由持久化查询确认，不能把一次发送成功当成用户已看到或业务已完成。

**追问展开**

1. **追问一：握手鉴权、一次性票据、发送前重验和连接断开恢复分别解决什么问题？多实例如何找到用户所在连接？**

   **回答：** 握手鉴权和允许来源检查控制谁能建立连接。当前后台连接使用短期一次性票据，并在发送前重新验证后台会话、权限和商户范围；消费者连接使用用户令牌鉴权，不能把后台的票据与逐次重验机制泛化到所有连接。断线恢复需要客户端退避重连、重新鉴权并主动拉取权威状态。多实例下，各实例维护本地连接，再用跨实例通道把用户事件广播或路由到持有连接的实例；这解决“找到连接”，不解决离线可靠性。

2. **追问二：Redis 发布订阅没有在线接收者、消费者慢或用户短暂掉线时如何表现？若要求可靠通知，你会增加哪些持久与确认机制？**

   **回答：** Redis 发布订阅采用至多一次投递：发布时没有订阅者，消息直接丢失；订阅者短暂断线也不能补历史，消费者过慢还可能积压输出缓冲并被断开。因此可靠通知应先把事件写入持久 Outbox 或消息队列，携带稳定事件标识；消费者幂等处理、记录投递游标或用户通知箱，失败可重试，客户端用确认或最后游标补拉。即便如此，“送达设备”和“用户已读”仍是不同状态，要分别定义。

**核对依据**：[RFC 6455 WebSocket 协议](https://www.rfc-editor.org/rfc/rfc6455.html)、[Redis 发布订阅投递语义](https://redis.io/docs/latest/develop/pubsub/)、[当前在线通知链路](../flow-notes/01-login-and-access.md)、[秒杀通知边界](../flow-notes/02-seckill.md)、[连接与发送前校验源码](../../../src/main/java/com/localdeals/websocket/SeckillWebSocketHandler.java)、[连接来源与订阅配置](../../../src/main/java/com/localdeals/config/WebSocketConfig.java)

## 十、扩容与综合系统设计（Q77～Q80）

### Q77｜活动请求规模扩大一百倍，怎样定位瓶颈并逐步扩容？

**口述回答**

这是扩展设计，不是当前能力声明。我会先固定请求模型和成功比例，按入口、Redis 原子准入、消息发送、队列等待、消费、数据库提交逐段埋点，观察利用率、排队时间、吞吐和错误，找到最先饱和的资源；随后一次只改变一个容量因素并重测。无状态接口可在共享限流与幂等前提下水平扩容，消费者要有足够独立队列和无共享热点才会随实例增长。单活动库存键、数据库库存行、同一有序消息队列或全局消费锁不会因简单加机器消失，必须改数据与竞争模型。

**追问展开**

1. **追问一：入口流量、单 Redis 热点、MQ 队列、数据库热点库存行、消费锁和连接池中，哪些能水平扩容，哪些不能简单加实例？**

   **回答：** 入口实例可水平扩，但总限流不能只做各实例本地计数；Redis 集群能分散不同键，却不能拆掉单个活动热键；消息队列能按更多队列并行，但同一业务键要求局部顺序时并发受限；消费者扩容还会受数据库连接总数、热点行和分布式锁限制。数据库读可借助只读副本，库存条件更新和唯一约束仍要回到权威写节点。每一步都要看端到端完成吞吐，避免只是把积压从 HTTP 队列搬到消息队列或连接池。

2. **追问二：分段库存或分片库存怎样处理售罄判断、剩余库存汇总和跨分片补偿？如何验证没有因扩容破坏一人一单？**

   **回答：** 分段库存可把总量预分配为多个可审计分片，请求按稳定规则选片，分片空时有限次数换片；售罄要在所有分片均无可用量后确认，不能用滞后的汇总值直接裁决。调拨和补偿都应写账本，按原订单把名额退回正确分片，并处理分片之间的剩余倾斜。一人一单仍需全局业务身份和数据库唯一约束兜底。验证要混合重复用户、跨分片重试、消息重投和故障补偿，断言总成功数不超总库存且任一用户最多一笔。

#### Q77-D1｜面试官追加深挖

**追问：** 把10份库存从分片A调拨到B时，若A已扣减、B尚未增加就宕机，如何避免丢额度；若反过来先加B，又如何避免双花？请用调拨单号和中间状态说明恢复协议，以及为何“汇总剩余库存”无法替代它。

**追问缘由：** 原答案要求调拨记账，但没有展开跨分片增减非原子时的额度守恒机制。

**回答：** 需要先创建带全局唯一调拨单号的持久调拨记录，保存来源、目标、数量和单调状态。较直观的是“先冻结来源、再激活目标”：来源分片在一个本地事务中条件扣减 10 份可售库存，并写入该调拨单的“来源已预留”防重记录，二者必须同成同败。目标分片再在自己的本地事务中，以同一单号把 10 份加入可售库存并写入“已入账”持久收据。若来源扣减后宕机，恢复工作器根据调拨单重试目标事务；目标已有收据就只返回成功，没有收据才执行一次，因此额度不会因重试重复增加。

取消不能靠协调者某次“查询目标尚未入账”后直接退还来源，因为此前发出的旧入账命令可能仍在路上。协调者必须先让目标分片对同一调拨单原子落下持久的“已取消/拒绝入账”状态，使取消与入账在目标本地竞争同一状态：取消先赢，任何迟到入账都被拒绝，此时收到确定取消收据后，来源才能在本地事务中把额度退回并记录已退款；入账先赢，则不能退来源，只能完成原调拨，或另建一张反向调拨单。目标结果不确定时，额度继续保持在途，不能猜测补偿。

反过来先给目标增加可售库存，会在来源尚未扣减时造成双花。若必须先处理目标，只能先在目标事务内建立不可售的“待入账”记录，来源预留成功后再原子激活；失败则用上述取消竞争封死迟到激活。守恒关系只能在同一逻辑账本视图、每份额度恰好归属于来源可售、在途或目标已入账之一时成立。目标已经提交入账而协调状态尚未更新时，应以目标持久收据把归属判给目标，不能同时把它算作目标可售和协调者眼中的在途。跨分片汇总既不是同一时点，也没有单号、归属和防重证据，无法替代这一恢复协议。当前文档明确这是扩展设计，不能声称已经实现或演练。

**核对依据**：[秒杀流程与当前恢复边界](../flow-notes/02-seckill.md)、[RocketMQ 4.x 顺序消息](https://rocketmq.apache.org/docs/4.x/producer/03message2/)、[历史资源与流量验证](../../evidence/m5/m5c-resource-traffic-results.md)

### Q78｜加入支付、超时取消和退款后，秒杀订单状态怎样扩展？

**口述回答**

这是尚未实现的业务扩展。我会把“异步落单处理状态”和“支付业务状态”分开：前者回答消息是否已形成正式订单，后者用待支付、已支付、取消中、已取消、退款中、已退款等显式状态表达资金生命周期。每次迁移都写成“旧状态满足才更新”的原子条件，并记录版本、操作幂等身份和审计时间；创建订单、发送待支付事件仍用本地事务加 Outbox 衔接。超时任务只提出一次取消意图，真正释放库存要等状态裁决，不能把消费处理超时误当成用户支付截止时间。

**追问展开**

1. **追问一：支付回调与超时取消同时到达，如何通过状态条件、幂等身份与事务边界裁定结果？订单处理超时和支付超时为什么不能混用？**

   **回答：** 支付回调与超时取消并发时，双方竞争同一合法前置状态：支付成功者把待支付改为已支付，取消者把待支付改为取消中；只有影响一行的一方取得转换权。若支付渠道事实上已扣款但取消先取得状态，系统不能简单拒绝旧回调并留下资金，应查询渠道事实并转入退款流程；若支付先成功，取消不得释放库存。渠道交易号和回调事件号都要唯一去重，状态更新与业务事件写入同一事务，外部调用则靠重试和对账闭环。

2. **追问二：退款成功但内部状态更新失败，或库存已释放后旧支付回调到达，怎样设计对账、补偿及人工处置？**

   **回答：** 退款渠道成功但本地更新失败时，持久化的退款请求和渠道交易号让定时对账能查询外部事实，再幂等补写已退款；多次回调不能重复退款。库存已释放后收到旧支付回调，应进入“已取消但渠道已付”的异常分支，冻结自动重新占库存，优先发起原路退款并告警。对账要同时扫描长时间中间态、渠道账单和本地事件位点；超过自动重试上限进入隔离队列和人工工单，保留每次决策证据。

**核对依据**：[当前秒杀状态与未实现边界](../flow-notes/02-seckill.md)、[RocketMQ 4.x 事务消息](https://rocketmq.apache.org/docs/4.x/producer/06message5/)、[RFC 9110 幂等语义](https://www.rfc-editor.org/rfc/rfc9110.html)

### Q79｜怎样演进租户隔离、搜索与数据分片？

**口述回答**

这是面向规模增长的方案。早期可在共享库表中为商户私有资源带上租户标识，按业务唯一性的作用域设计复合约束与索引，并让后台读写贯穿商户范围；再由统一的数据访问拦截与权限测试降低漏条件风险。数据量或隔离要求提高后，可按租户分库，头部租户独立部署。平台跨商户管理要使用单独授权入口和审计身份。搜索也要区分用途：商户后台的私有数据查询必须先限定租户；消费者查找公开商铺则允许跨商户发现，按公开可见性规则过滤，不能错误地套成“只能搜自己商户”。

**追问展开**

1. **追问一：共享表加商户条件、分库与独立部署各适合什么场景？平台跨商户查询与商户自身隔离如何兼顾？**

   **回答：** 共享表成本最低，适合租户多但单租户小、隔离等级一致的阶段，风险是任一漏条件都可能越权；分库能隔离容量和故障，但增加路由、迁移、连接池及跨库事务成本；独立部署适合强合规或超大租户，运维成本最高。平台运营查询应使用显式的平台角色、受限字段和审计日志，可汇入专门分析存储；商户接口则在入口确定租户后贯穿数据库、缓存、消息和搜索，不接受客户端任意切换范围。

2. **追问二：分片后唯一约束、全局 ID、跨商户报表和搜索权限怎样实现？如何避免先查全量再在应用层过滤造成泄露或分页错误？**

   **回答：** 单库唯一约束不能天然覆盖多个分片，需让同一不变量按分片键落在同一库，或建立全局注册服务；全局标识可用带节点/时间信息的算法或数据库号段，但都要处理时钟、号段重用和容量。跨商户报表可通过 binlog/消息汇入分析仓，接受明确延迟，避免在线跨库扇出。搜索索引按规模选择共享索引加租户过滤、分组索引或独立索引，并在别名和查询层双重约束；先取全量再过滤会泄露总数、排序和分页位置。

**核对依据**：[登录与商户授权边界](../flow-notes/01-login-and-access.md)、[商铺搜索与同步边界](../flow-notes/06-shop-read-and-search.md)、[MySQL 8 多列索引](https://dev.mysql.com/doc/refman/8.0/en/multiple-column-indexes.html)

### Q80｜怎样定义上线前验收标准与持续演进路线？

**口述回答**

当前仓库还不能据此宣称生产就绪。上线门槛应先覆盖正确性、安全、可恢复和可观测：并发下不超卖、不重复授权且无越权；任何超时都能以稳定身份查询或重试；备份可恢复；关键依赖故障有明确降级；指标、日志和告警能定位积压与不一致。然后才谈吞吐扩容。路线应从可重复的单实例基线开始，补齐自动化故障注入和恢复断言，再进入多实例、真实中间件与主从切换演练；每阶段都保存版本、配置、数据集和验收结果，未跑端到端就明确写“未验证”。

**追问展开**

1. **追问一：请从已知缺口中选择三个最影响正确性或可恢复性的问题，说明修复优先级、最小改动和验证方法。**

   **回答：** 我会优先处理三个已知缺口。第一，Redis 全量丢失后无法精确恢复未决预占和隔离信息：最小防护是阻止恢复未完成时重新开放准入，建立状态盘点与处置步骤；持久预占账本涉及一致性协议调整，要作为后续独立阶段设计和演练，不能称为小修。第二，分类搜索的过滤条件被后设置的地理过滤覆盖：组合成一个布尔过滤，并用分类与坐标交叉样本验证，这是适合独立完成的小改动。第三，搜索同步缺少乱序保护且未验证完整 Canal 链路：先用乱序重放用例明确缺口，再设计单调版本和删除保护，补充从数据库提交到索引可见的端到端验证；检查点和坏事件隔离分别分步实施。

2. **追问二：你会怎样定义可用性、最终一致性延迟、数据恢复点和恢复时间目标，并把单机实验逐步推进为可重复的高可用验证？**

   **回答：** 指标必须先定义分母与观察窗口。例如候选目标可设为：有效请求月可用性 99.9%，已受理订单 99.9% 在 60 秒内到达终态；具体数字需由业务容量和成本评审后确认，不能冒充现有实测。MySQL 已确认提交的核心事实期望恢复点目标（RPO）趋近 0，必须用备份、日志和跨故障域复制证明；可重建缓存与搜索可接受更大 RPO，但要给出重建时限。恢复时间目标（RTO）按单实例、机房和数据损坏分别演练。推进时把压测与故障脚本固化，在隔离数据上执行进程终止、网络中断、积压、主从切换和备份恢复，并由业务不变量自动判定结果。

#### Q80-D1｜面试官追加深挖

**追问：** 如果系统把大量已受理订单在60秒内标成失败，“99.9%在60秒内到达终态”的目标仍可能达标，这能证明服务质量好吗？你会如何同时定义受理后的成功率、终态时延与未知超时，并防止通过快速失败美化指标？

**追问缘由：** 现有候选SLO只约束到终态时延，没有限定失败终态与成功交付的比例。

**回答：** 不能。“及时到终态”只衡量悬而未决是否被收敛，成功和失败都可进入分子；如果 10000 笔已受理订单中 9990 笔在一秒内失败，它甚至能得到 99.9% 的漂亮结果，却显然没有完成用户期待。快速失败对未受理的过载请求可以是合理保护，但不能把已经承诺受理的订单批量失败包装成良好交付。

我会按受理时刻形成固定 cohort（同期订单集合），用去重后的已受理订单数 `N` 作统一分母，并至少同时报告三组指标：一是成功交付率 `成功终态数/N`，技术失败、业务取消要按稳定原因码分开；二是从受理到终态的延迟分布及“在 60 秒内成功”“在 60 秒内明确失败”的各自比例，不能只合并二者；三是到 60 秒仍无可证明终态的未知率 `未知数/N`、最老未知年龄和后续最终去向。只有状态机真正完成裁决和必要补偿，才能标成失败，不能到时机械改状态来消除未知。

观察窗口也要防右删失：刚受理、尚未拥有完整 60 秒观察期的订单不能混入已完成 cohort 美化比例，应延迟结算或明确列为未成熟样本。上线门槛采用组合 SLO 和独立错误预算，例如成功率、未知率任一越线都失败，即使终态时延达标；看板同时展示绝对数量、原因分布和失败时延，对“失败突然变快、成功率突然下降”单独告警。具体目标数值仍需业务评审和压测确定，现有材料只提供候选目标，不能当成已经验证的生产 SLO。
