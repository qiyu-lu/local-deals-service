# 业务流程笔记提示词

这套提示词用于编写能顺着读、能自己复述的业务笔记。它以 `10-seckill.md` 的表达习惯为样本：用 Markdown 无序列表从请求带来的数据讲起，说明接下来检查什么、修改什么、交给谁继续处理。一级条目推进流程，下面的子条目在调用位置讲清方法、脚本和 SQL 的内部逻辑；复杂异常恢复、长篇原理推演与独立业务情形再放到后面。

## 怎样使用

每个新会话只需要拼接两部分：

1. 从 [01-flow-scopes.md](01-flow-scopes.md) 复制本会话对应的一个代码块。
2. 接上 [02-writing-style.md](02-writing-style.md) 的全文。

在项目目录 `/home/sd101t/IdeaProjects/hm-dianping` 中执行。选题提示词决定读什么、写哪个文件；通用提示词决定怎样讲。目标文件不存在时新建，已经生成时直接调整该文件，不需要先提交计划等待确认。

建议分成下面 5 个会话，共生成 6 份笔记：

| 会话 | 负责的业务 | 新笔记，均位于 `docs/learning/flow-notes/` |
| --- | --- | --- |
| A | 消费者登录，平台与商户后台登录、权限和资源归属，WebSocket 身份 | `01-login-and-access.md` |
| B | 秒杀请求、事务消息、消费落库、结果查询、异常恢复 | `02-seckill.md` |
| C | 活动与资格、单人领券或发券、签到奖励、批量发券、通知 | `03-voucher-grant.md` |
| D | 点赞与热榜；图片发布、关注与 Feed | `04-like-and-hot-rank.md`、`05-publish-and-follow-feed.md` |
| E | 店铺详情与缓存、附近店铺、全文搜索与索引同步 | `06-shop-read-and-search.md` |

A～D 覆盖这次提到的重点。E 用于补齐原 08 中的读取与搜索部分，可以在复习到这里时再执行。D 的两份笔记共用 Blog 相关源码，但各自讲完整流程，先完成点赞与热榜，再整理较短的发布与关注流。

这样拆有几个原因：平台账号和商户账号共用后台身份链，分开会重复阅读权限实现；四类营销入口最终共用单人发券事务，也适合放在一起比较。秒杀的消息回查、数据库落单和补偿需要互相对照，应留在同一个会话。普通资料查询、登出、分类列表等随相关主题带过，暂时不再增加会话。

跨主题只引用明确的交接结果。例如秒杀从“已取得当前用户”开始，不重复讲登录；营销从“已取得后台身份与商户范围”继续，不重写拦截器；通知的业务触发归各业务笔记，长连接如何认证归 A。各会话只写分配给自己的文件，因此可以并行执行。

## 为什么这次调整写法

`10-seckill.md` 保留了参数、判断和数据写入之间的联系，列表与缩进也让步骤和内部逻辑容易区分。讲到限流时，就应在这里说明参数怎样传给 Lua、Redis 时间怎样换成窗口编号、三个 key 怎样组成、计数怎样判断和修改，以及返回 Java 后如何继续。不能先只写“Lua 限流”，再让读者去文末查实现。

这次的两个要求是：每个关键步骤内部的执行逻辑要详细；这些逻辑默认放在该步骤发生的位置。它同样适用于 Java 方法、SQL、拦截器、消费者和后台任务。普通判断与直接业务拒绝就地说明；只有跨多轮、多执行者的复杂恢复，或完整的并发与原理推演，才有必要单独抽离。原位置仍需写明触发条件和接手者。

因此不再限制主流程只有两级列表，也不按篇幅长短机械移动内容。必要时可以增加层级，或在原位置用小标题展开一个连续子流程。读者暂时不看补充章节和源码，也应能顺着笔记说明每一步具体怎样得到结果。

同时，10 只能作为表达样本。当前源码已经能确认几处需要校正或补全的内容：

- MySQL 的订单防重是订单主键，以及 `(user_id, voucher_id)` 唯一约束；不是用户与订单号的复合唯一约束。依据是 `V2__voucher_order_constraints.sql` 和 `createVoucherOrder`。
- `seckill_check.lua` 当前仍读取并写入旧已购 Set，不能因为它承担兼容作用就说运行时可以忽略。它与精确预占分别怎样检查和写入，应在准入脚本的步骤中说明。
- `seckill_mark_success.lua` 先核对预占映射和三个归属 ID，才允许处理已有 SUCCESS 或把 PROCESSING 改为 SUCCESS；这不是只看状态的更新。
- `SeckillOrderConsumer` 对两类明确的数据库永久失败会暂停活动并尝试精确补偿，对订单号归属冲突则暂停并隔离。新笔记应明确讲出这些实际分支，不停留在“后面可能处理”。

提示词会要求执行会话重新对照当时的源码核验这些点。这套文件只提供提示词及编排方式，业务笔记的生成与调整由各执行会话完成。

## 已有笔记怎样使用新版

在原来生成笔记的会话里发送下面这段，替换目标文件路径即可，不必重新提交第一组选题：

```text
请读取 docs/learning/prompt-kit/02-writing-style.md，按新版要求调整生成的文件

保留这份笔记已有的业务范围和列表表达，直接修改这个文件，不修改提示词文件。
本次要补全各步骤内部怎样执行，并把相关逻辑放回调用发生的位置。

请沿对应源码补清关键方法、Lua、SQL 的输入、内部判断与计算、数据读写、
返回结果及调用方怎样继续。把文末原有的必要实现细节移回对应步骤，
并补上旧稿根本没有写出的关键逻辑，不能只搬回原来的摘要。

不要因为子步骤多就移到文末，不硬性限制列表只有两级。
普通条件判断和直接业务拒绝留在步骤内；复杂异常恢复、很长的原理推演
和独立业务情形可以保留在后面，调用处须交代触发条件和后续去向。

保留正确内容、独有异常和实现边界，合并移动后重复的段落。
验收标准：暂时不看文末补充和源码，也能从笔记理解每一步怎样执行，
并顺着返回结果继续读到整个流程的结果。
```

## 怎样让 AI 逐渐贴近你的表达

如果还不确定这种写法是否合适，可以先用最熟悉的秒杀校准一次，再把调整后的通用提示词交给其他会话。这样能减少所有文件都生成以后再整体重写的成本。

读完一段后，合上笔记，用自己的话写出这一段，再在原会话追加类似下面的反馈：

```text
下面是我读完后自己复述的这一段：
【粘贴我的复述】

请对照当前源码，只指出影响正确理解的遗漏或错误，并把这一段按我的表达修正。保留我的叙述顺序，用一级列表推进步骤，在子条目中就地展开内部逻辑；如果中间跳过了必要转换，就补上“拿到什么、怎样处理、结果交给谁”的连接。普通判断、方法与脚本的执行细节留在这一步，只有复杂恢复或长推演才单独展开。不要重写整份文档，也不要额外生成面试问答。
```

判断笔记是否合适，可以看自己能否接着讲出下一步、说明谁在执行，以及解释这一步失败后由谁继续。遇到卡住的地方，只让 AI 改那一段和必要的补充说明，通常比不断要求“写得更口语化”更有效。
