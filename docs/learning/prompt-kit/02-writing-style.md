# 第二组：通用写作提示词

前面已经给出本会话负责的业务与输出路径。请结合下面的要求，直接读当前项目并编写笔记。目标是让我只读笔记，就能理解整条业务以及各步骤内部怎样执行，再逐渐换成自己的话复述；不必为了弄清某个方法或脚本如何完成当前步骤而跳到文末或打开源码。

## 阅读依据与工作范围

先完整读 `docs/learning/10-seckill.md`，理解我习惯怎样描述输入、判断和后续动作。保留它用 Markdown 无序列表逐步描述、用缩进表示步骤内部逻辑的形式，同时模仿叙述顺序与用词习惯，修正事实错误、重复和过细的分点。它只是表达样本，不是正确答案；其他主题也不要硬套秒杀的锁、补偿或状态机。

随后只读 08、09 中与本主题有关的章节，用它们定位当前源码。沿实际入口追查到必要的 Service、SQL、Lua、异步任务和默认配置；相关测试按需用于理解分支。方法或注释存在，不代表主路径会调用它。旧笔记、代码注释和当前实现冲突时，以实际调用与执行逻辑为准。

本任务只编写分配给本会话的目标笔记，可以创建其父目录。目标不存在时新建；已经生成时直接在目标文件中调整，保留有用的人工表述和已经核实的内容，纠正查明的错误。保留已有业务源码、08/09/10 和其他笔记的人工改动，不修改共享 README，不操作其他会话负责的文件，不提交或推送。不启动服务、运行迁移或业务测试；不要再拆子 Agent 或额外生成规划、审计报告。完成后只简要报告修改文件和重要修正。

不要为写一条链遍历整个仓库，也不要停留在只复述旧文档。遇到关键分支就继续读到能确认结果的位置；确实无法确认的地方就地标明，不用“系统会自动处理”补齐。

## 在流程发生的位置讲清每一步

每条独立流程的标题下，用一两句交代“谁要做什么事、请求带来什么、希望得到什么结果”，随后用 Markdown 无序列表按发生顺序描述。不要把多个请求的介绍挤成一大段，也不要先放项目背景、技术选型列表、术语表或面试开场白。默认关闭的功能，要在相关流程开始前简要说明启用前提。

沿用我熟悉的表达：

“用户请求进来，带的是……；当前用户从……取得。接着根据……检查……。通过后把……写到……，这里记录的是……。随后由……拿着……继续处理。到这里请求返回……，后面的……另外执行。”

主流程统一用 `-` 列表；`*` 或 `+` 也能表达同样层级，保持全文一致即可。按下面的颗粒度组织：

- 一级条目表示一个能独立复述的流程步骤，按发生顺序排列。先交代这个动作要完成什么，再在其下展开内部执行过程，不把几个阶段塞进同一条长段落，也不用给每个步骤单独起标题。
- 二级及必要的更深层条目按实际执行顺序解释这个步骤里的输入、读取、判断、计算、写入和返回。方法内部又调用脚本或其他关键方法时，继续在当前位置展开，结束后明确回到调用方怎样处理结果。
- 层级由真实逻辑决定，不硬性限制为两级，也不因步骤长或有多个参数就移到文末。较长的连续子流程可以在当前位置用一个小标题组织，讲完再继续外层流程；只增加有实际含义的层级。
- 相邻的简单赋值、校验可以合并；不同的业务动作仍应分点。不要为了减少条目把主流程改成连续长段落，也不要只是给原来的每个长段落机械加一个 `-`。

每个条目里的话仍要自然连贯，使用“接着”“通过后”“如果……就……”把前后联系讲出来，不要只留下“参数校验”“状态更新”这种关键词。步骤数量由实际流程决定，不按面试时长或固定字数压缩，也不为了凑五步或十步合并不同请求。

重点保留这些中间连接：数据从哪里来、在哪一步变成了什么、保存在哪里、后面谁拿它作判断。例如不能只写“保存预占”，还要说明是把该券下的用户与本次订单号对应起来，后续消息才能核对是不是同一次操作。必要时给一组明确标为假设的 ID 或数据，展示前后变化。

对流程中的关键方法、Lua、SQL、拦截器、消费者和后台任务，都按实际需要讲清以下内容。这是检查遗漏的依据，不要求每个步骤机械套一遍小标题：

- 调用方传入哪些业务参数，哪些来自请求、登录上下文、配置或前一步结果，它们用于什么判断。
- 内部依次读取哪些数据，key 如何组成、使用什么数据结构，哪些字段参与接下来的比较或计算。
- 实际按什么顺序检查条件、计算中间值；条件不满足时返回什么或抛出什么，调用方因此走哪条分支。直接的业务拒绝也写在这里。
- 条件满足后依次改哪些数据，关联 ID 或映射怎样建立，状态与 TTL 如何变化，操作由哪个原子脚本、锁或数据库事务保护。
- 方法返回什么，外层如何使用返回值继续、拒绝或交给其他执行者；数据库事务在哪里提交，哪些动作发生在提交之后。

这些执行细节应随对应步骤出现。Lua 的输入、内部判断和返回值，SQL 的关键 WHERE 条件与影响行数，方法中的几次查重，都是流程本身。不能只写“调用 Lua 校验资格”“执行方法保证幂等”“更新状态”就跳到下一步，也不能把它们唯一的完整解释放在流程外的机制章节。数据结构在第一次使用时解释清楚，后续使用时说明当前读写哪部分即可。

只合并不影响理解的机械动作，例如多次简单赋值、重复日志或无关指标代码；不要逐行翻译 import、getter 和框架样板。完整程度以读者能否在当前位置说明“这一结果具体怎样得到”为准，不要求复刻全部源码。

不要把一份文档里的全部流程强行串成一次请求。同步请求返回时要收束；消息消费者、后台任务、事务回查、用户查询分别说明触发者和起点。多个入口共用一段逻辑时，只完整解释一次共同部分，再说明各入口在哪里接入。并行发生的事情不能写成固定先后。

主流程中直接写清关键事务的范围、提交点、锁保护的对象，以及成功当时究竟成立了什么。空值、库存不足、重复请求、状态不匹配等直接判断，以及当前方法如何返回或抛错，放在判断发生的位置。只有异常后还需跨多个执行者、多轮重试或较长的事实核查时，才把整段恢复过程放到后面的独立小节；当前位置仍须交代触发条件、已完成到哪里和谁接手，并链接到具体小节。不要只写“异常详见后文”。

## 哪些内容才需要放到流程之外

先判断一段内容是否在回答“当前这一步具体怎么执行、结果怎么传给下一步”。如果是，默认在当前位置讲完；篇幅长、包含 Lua 或多条 SQL 都不是抽离的充分理由。需要抽离的是复杂异常恢复、很长的并发或原理推演，以及独立的业务场景与方案比较。主流程应当能够独立读懂，不依赖文末补齐正常执行逻辑。

### 复杂机制的进一步推演

例如多个事务交错提交的完整时间线、旧热榜构建器晚到的并发推演、某种方案的替代做法和代价。这些可以放在后面；实际加锁、查重、申请 generation 和拒绝过期结果的操作，仍须先在各自执行位置讲清。

每个补充小节指出它进一步解释哪个步骤，不要复制一遍已讲过的内部操作。源码片段、返回值或状态小表如果有助于理解当前步骤，可以直接放在对应步骤下，不必统一收集到文末。正文先说中文含义，再给代码里的名字。

遇到并发问题，用两个请求或两个任务的先后顺序解释。例如先后查到相同结果之后，实际在哪一步发生竞争，最后由锁、唯一约束或条件更新中的哪一个作判断。不能只用“保证幂等”“原子操作”“最终一致性”代替执行过程。

### 出问题时，后面由谁继续

这里只展开在原步骤中难以连贯讲完的复杂恢复过程；简单拒绝、返回值分支和短的错误处理留在原步骤。每个场景先说明断点，再按时间顺序解释处理；涉及多个动作或条件分支时使用列表，简单原因可以用短段落。需要讲清：

事情断在什么位置；此前哪些修改已提交，哪些尚未确定；哪个请求、消费者或后台任务会再来；它检查什么记录后决定重试、回滚、补偿、回退、拒绝或隔离；重复执行为什么不会多产生一份结果；用户这时能查到什么。

不是每条链都具备这些恢复动作。只写当前实际存在的处理：只有日志就明确说只有日志；任务默认没开就说明开启条件；没有自动恢复就说明会留下什么状态。区分“明确没成功”“结果暂时不知道”和“不同记录的归属互相冲突”。网络超时不能直接等同于远端未执行。

异常和实现局限放在对应位置解释，不额外堆一份泛化风险清单。不把在线通知成功当成业务成功或用户已收到，不把局部事务写成所有组件一起提交和回滚。

### 放到实际业务情形里理解

挑几种对本主题最有帮助的具体情形，每种用一小段解释。它可以引用前面已经讲过的异常，但这里着重回答为何要采取这项措施，不再复制一次恢复流程。

描述到能想象的程度：谁做了什么、在哪个时间点重复或发生变化、简单处理会带来什么后果、项目里的哪一步避免或限制了这个后果、这种做法还有什么代价。

例如“同一用户因页面没有响应又点了一次”“两个用户同时争最后一个名额”“旧热榜任务比新任务更晚完成”。不要只写“高并发场景”“保障可靠性”。这些是帮助理解的假设场景，不能包装成已经发生的线上事故或已经完成的压测。

### 源码反查与必要修正

结尾给少量与关键判断对应的源码相对链接，标明相关方法、脚本或 SQL 的作用，方便从笔记跳回去。链接不必塞进每句话，也不要重新列出整个仓库目录。不要猜行号。

如果原笔记有影响理解的错误，简要写出原来怎样理解、应改成什么、依据哪处源码。新正文直接使用正确说法。10 是重点纠错对象，但不需要做错别字清单或旧文档迁移表。

实现存在、配置默认开启、测试覆盖、这次实际运行是不同结论。以源码阅读完成的笔记就如实说明阅读范围；不要照搬历史测试数字或生产性能结论，也不必附一大段通用证据声明。发现未实现的能力时，就地说明，不另起改造方案。

## 表达方式

用像我在复习代码时给自己解释的中文，可以自然出现“我这里先看……”，不必每句都用第一人称。减少“通过……实现了……保障了……”的套句，多用明确的主语和动作：入口检查、脚本写入、数据库提交、消费者重试、用户重新查询。

Outbox、principal、generation、幂等之类的概念，在第一次用到的位置解释它具体指什么、为什么当前这一步需要它。不要默认我已经理解这些概念，也不要先插一段完整的中间件教程。

下面用秒杀限流展示“进入方法、展开脚本、回到调用方”的写法。示例依据 `SeckillTrafficGuard.check` 和 `seckill_traffic_guard.lua`，用于说明叙述深度；实际笔记仍按当时源码核对：

- 入口拿到券 ID、当前用户 ID 和客户端 IP 后，调用限流方法。方法先检查流控开关，关闭时直接返回；开启时要求这三个值不为空，再准备调用 Lua。
  - Java 先组装三类计数 key 的前缀：`traffic:seckill:{券ID}:activity:`、`traffic:seckill:{券ID}:user:用户ID:`、`traffic:seckill:{券ID}:ip:IP摘要:`。IP 用 SHA-256 摘要表示；这里还没有拼接时间窗口编号。
  - 随后把三个前缀作为 KEYS，把配置中的窗口毫秒数、活动上限、用户上限和 IP 上限作为 ARGV 传给脚本。
  - 脚本先把四个参数转成数值，要求窗口至少 1000 毫秒，三个上限都大于零；不满足就返回 Redis 错误，由 Java 按限流依赖异常处理。
  - 接着读取 Redis TIME，取得秒和微秒并换算为当前毫秒时间，再计算 `向下取整(当前毫秒时间 / 窗口毫秒数)`，得到窗口编号。这样多个应用实例使用同一个时间来源。
  - 把窗口编号接到三个前缀后面，得到本窗口的实际计数 key。例如假设券 ID 为 1001、用户 ID 为 42、窗口编号为 17，该用户的 key 就是 `traffic:seckill:{1001}:user:42:17`。
  - 分别 GET 三个计数并转成数值，没有可解析的计数时按 0 参与判断，然后依次检查：
    - 活动计数已经达到上限，返回 1。
    - 活动未超限，再看用户计数，达到上限返回 2。
    - 前两项未超限，再看 IP 计数，达到上限返回 3。
    - 这三个拒绝都发生在计数写入前，因此被拒请求不会只增加其中一部分计数。
  - 全部通过后，依次给三个 key 自增，并把过期时间都设置为 `2 × 窗口毫秒数 + 1000 毫秒`，让旧窗口的数据随后自动清理；最后返回 0。
- Lua 执行结束，控制回到 Java 限流方法。返回 0 就记录通过并正常返回；1、2、3 分别记录对应超限原因，再抛出映射为 HTTP 429 的异常。Redis 调用抛错、返回空值或约定外结果时返回 503。
- 限流方法正常返回后，外层秒杀逻辑才继续生成订单号。前面三个计数记录的是入口请求量，所以后续抢券失败也不会退还这些计数。

这里已经在调用位置解释了脚本怎样得到结果，读者无需跳到“Lua 原理”一节才能继续。Java 方法、SQL、拦截器、状态更新和后台任务也用同样深度描述；不要只对 Lua 增加细节。复杂的故障恢复或多请求交错推演仍可放在后面。

保留列表带来的清晰步骤边界，合并的只是重复或机械的条目。不要额外附“30 秒版、2 分钟版、十个面试问题、术语总表”等重复版本。目标是有一份能顺着读懂内部执行逻辑的流程，后面的补充帮助深入理解，不承担填补主流程缺失步骤的职责。

默认用文字把过程讲清；只有不同执行者的交接或状态分叉用文字确实容易混淆时，才加一张简短图。图跟在相关文字后面，不能替代步骤说明，也不要为每份文件机械画图。

## 已有笔记怎样调整与检查

如果目标笔记已经生成，先保留它的业务范围、列表表达与正确内容，把原先集中放在文末的必要执行逻辑移回各自调用位置，再沿相关源码补齐旧稿根本没写出的参数、判断、计算、读写和返回处理。只调整排版或原样搬回一句摘要，都不能满足本次要求。移回后合并重复内容，保留后文独有的复杂异常、原理推演和业务情形，不需要再生成一份摘要或重组报告。

写完自行检查：

- 只读某一步及其下面的子条目，能否说明该方法收到什么、内部怎样处理、为什么得到这个结果、调用方下一步做什么。
- 如果暂时不看文末补充和源码，是否仍能从入口走完整个正常执行过程及直接业务分支；是否还有“执行某脚本”后缺少内部过程的跳跃。
- 是否把普通方法、SQL 和后台任务也讲完整，而不是只补全 Lua；是否将关键数据结构在使用位置解释清楚。
- 抽离的内容是否确实是复杂恢复、长推演或独立场景；篇幅长或有第三层列表不能单独成为抽离理由。
- 每次切换请求或执行者是否交代清楚，复杂异常是否有明确去向，源码事实是否准确，是否去除了重复而保留了独有内容。

修好这些问题后直接交付，无需另写自检报告。
