秒杀的一部分流程：

+ 输入是优惠券id和解析出来的真实ip，这个真实ip是由于可能是通过ngnix网关的原因、
+ 根据userholder 获得当前的用户id，
+ 然后根据优惠券id，用户id，客户端ip，检查相关id是否为空，不为空的话，通过一个lua脚本进行一个固定窗口的限流，同时限流三个维度：活动总请求，单用户请求量，单ip请求量；
    - lua输入的参数有配置文件横纵的时间窗口大小、整个活动在窗口内允许的总请求数、单个用户在该窗口内允许的请求数、单个ip在窗口中允许的请求数；以及活动计数、用户计数、ip计数三者各自的key前缀，各自key同时会拼接时间窗口编号；
    - 检验输入的参数有效性；
    - 获得redis服务器的时间，不使用java的时间，不用客户端时间，因为不同的机器可能有时间偏差，保证所有服务器节点使用同一个时间源，避免分布式环境下时间不一致；
    - 计算当前时间窗口，就是时间窗口桶的编号，当前时间除以时间窗口的长度，然后拼接出是三个key；
    - 读取当前窗口计数，进行限流判断，活动总请求超限，返回 1；单用户请求超限，返回 2；单 IP 请求超限，返回 3；都不会增加计数，不会出现“后面秒杀业务活动层已经扣一次，后来才发现用户层超限”的情况。
    - 如果都没有超过限度，则三个key自增，然后设置过期时间，为 2倍的时间窗口+1秒，这样为了让旧窗口的 key 自动过期，避免 Redis 内存无限增长。返回 0，表示允许通过
+ 根据上面lua脚本的不同输出，记录这个不同的情况；
+ 根据 redisIdWorker 生成一个订单id，这个 RedisWorker 是基于 Redis 的分布式全局唯一 ID 生成器，思路类似雪花算法（Snowflake），但序列号部分用 Redis 自增来实现，
+ 基于 RocketMQ 事务消息发送下单消息，根据优惠券id，用户id，预生成的订单id，返回值是int类型的
    - 根据三个id构建一个自定义类上下文，这三个id是用于后续事务执行的参数，这个类中有一个字段是作为后续进行保存事务状态的结果，根据结果来判断是提交还是回滚；
    - 根据三个id构建消息体，后续消费者受到这条消息后，会异步执行真正的下单逻辑；
    - 发送事务消息根据rocketmq提供的 方法，包含三个参数，话题topic，消息体，和自定义类的上下文，
    - 发送半消息-执行本地事务-提交或者回滚，如果本地事务没有及时上报，Broker 会回调 检查事务的方法，根据
    - 返回事务执行的结果；
+ Broker 收到半消息成功后，回调执行事务方法，重写的一个事务方法
    - 校验和解析参数，
    - 执行lua脚本，
        * 会输入6个key，和三个id，以及一个配置的阈值，用于判断处理中的订单是否过期，
        * 6个key分别是：根据优惠券id拼接的库存key，根据优惠券id拼接的已经购买的用户集合key（这个是为了兼容旧的版本），根据优惠券id拼接的活动元数据哈希key，根据优惠券id拼接的预占用户-订单的映射集合key，根据订单id拼接的单笔订单状态哈希key，处理中订单zset，得分为过期时间戳
        * 进行参数校验时间阈值是否为负数，
        * 检验活动元数据，读到状态，开始和结束时间，并判断合法性
        * 如果活动状态不为 active，直接返回 4，表示活动未开始，已结束，已下线等情况；
        * 使用redis时间判断活动时间窗，如果当前还未开始返回3，如果当前已结束返回4；
        * 检验库存如果库存不足返回1；
        * 根据优惠券id拼接的已经购买的用户集合key（这个是为了兼容旧的版本）这里就是为了兼容旧的版本，这个可以不用关注，可以忽略
        * 根据用户和订单的映射key得到哈希，判断用户id是否有，如果有说明已经重复下单过了，防止重复下单；
        * 上面检验过之后进行
            + 扣减库存，库存key自减，
            + 写预占，映射key，设置对应的优惠券的用户id为当前用户，订单id为当前订单；
            + 单笔订单状态哈希key，设置状态为processing，订单id，用户id，优惠券id，创建更新时间，失败原因为空，对账补偿次数为0
        * 然后单笔订单状态哈希去掉过期时间，只要库存和预占还在，PROCESSING 状态就不能自动消失，否则回查会查不到状态，无法裁定。等订单进入终态（成功/失败）时，再由后续逻辑设置 7 天 TTL。
        * 处理中订单zset加入当前订单，设置过期时间戳为配置中的过期时间加上当前时间；
    - 处理lua的返回结果，将结果写入上面的那个自定义的类上下文，这样主线程就能拿到这个结果返回给上层；为0则放行commit；不为0，为lua其他的返回结果，则业务拒绝rollback，其他返回值unknown
+ 当事务消息返回unknown时进行回查，或者说事务执行后Broker 长时间没有收到提交或者回滚的指令
    - arg 已经不在了，只能根据消息体本身去 Redis 查真实状态。是三个id，进行反序列化消息，
    - 检查一个zset，是一个存放被隔离的问题订单，如果根据订单号查找当前订单号在这个zset中，说明这条事务之前被对账/补偿逻辑标记为异常，直接回滚，rollback；
    - 检验预占映射，判断这个优惠券下的用户id---订单id，是否有内容，
        * 如果映射不存在或者里面的订单id和消息中的不一致，说明这次事务的预占已经失效或被别人覆盖就回滚 rollback。这一步防止重复提交、错乱提交。
    - 检查订单状态，根据订单状态哈希中读出状态，和三个id，如果读不到状态则返回unknow，稍后会查；如果三个id和消息中的对不上，返回rollback；
    - 根据订单状态进行判断，如果为processing，则返回commit，说明本地事务已经成功发起，让消息投递消费者继续推进；如果为success，返回commit，已经成功了，消息投递是幂等的，重复消费没有影响；如果为failed，返回rollback，其他返回unknown；
    - 其他返回unknown；
+ 回到这个秒杀业务入口函数，根据事务消息的返回结果返回不同的显示；



异步落库

+ 根据一个注解声明是rocketmq的消费者，topic和消费者组从配置中进行读取；
+ 消费入口进行自己实现
    - 校验消息合法性
    - 获取分布式锁，通过用户id，按照用户加锁：同一用户的消息串行处理，避免同一用户并发写订单产生竞争；不同用户互不影响，吞吐高。，如果拿不到就直接抛出异常，
    - 检查redis中的预占状态，是一个lua脚本，传入，订单状态hash的key，预占映射的key，隔离区zset，以及三个id
        * 如果订单id 是在隔离区内容直接返回4；
        * 读状态哈希，如果有任一个字段缺失返回0，
        * 如果状态哈希字段和当前id不一致返回4；
        * 如果状态是success返回2，为failed，返回3，既不是成功也不是失败还不是processing，返回0；
        * 如果是processing，再次检查预占的映射 中用户id对应的订单id是否等于当前的订单id，如果不等返回4，相等返回1，
    - 根据脚本返回，如果为2，成功，直接返回；为3，失败，直接返回；为4，预占归属不匹配，抛出异常，重试后进入mq；不上面的，同时不为1，其他状态，返回异常；为1可以继续处理
    - 为1的话写 MySQL ，插入订单-唯一键冲突，订单号唯一，用户号-订单号唯一；
        * 如果发生冲突会有以下情况：
        * 订单id已经存在并且归属相同，用户id和优惠券id一致，说明之前已经成功落库，现在mq重复投递，直接返回；
        * 如果订单id存在但是归属不同，订单id已经被占用，但属于另外的一个用户/券，这是严重的数据一致性问题，说明 ID 生成或预占逻辑出错了。
        * 订单id不存在，但是用户id和优惠券id冲突，按照用户id和优惠券id查出现有订单，抛出异常，后面可能会暂停活动，补充redis，通知用户失败等，从业务上看，这个用户在这张券上已经有一单了，当前这条消息属于“多余的预占”，回滚 Redis 让状态回到一致即可。
    - 扣减库存，抛出对应的异常，可能库存不足，和redis库存不一致可能是预热时没有同步好，或者redis和db双写不一致，后续可能暂停活动再补偿；
    - 然后数据库处理后，通过一个lua脚本进行落库成功后的状态收敛操作，将redis这笔订单processing改为success，从处理中订单中移除，并设置过期时间；
        * 对应的参数校验；
        * 得到状态，
            + 如果状态已经是succe，说明之前已经标记过，可能是重复调用，从处理订单中去掉这个订单id，对于这个状态哈希key设置过期时间，返回1；
            + 如果不是success也不是processing，返回0；
            + 如果是processing，设置哈希，状态为success，更新时间更新，删除失败原因字段，从处理列表中删除，设置过期ttl，返回1
    - 然后通知websocket，通知一下用户id，订单id，优惠券id，成功状态；
