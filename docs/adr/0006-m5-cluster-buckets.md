# ADR 0006：M5 Redis Cluster 化——库存分桶、按桶路由、主节点故障演练

- 状态：**草案**。设计与实现已完成，隔离栈全量 IT 在真实 Cluster 上通过；
  性能对比与故障演练的数字待 `scripts/bench.sh m5` 跑完后填入（计划 0 节第 7 条）。
- 关联：[V2 计划 M5](../plan/v2-high-concurrency-plan.md)、[ADR 0005](0005-m4-batch-consumption.md)、
  [M4 复测](../../benchmark/v2/m4/comparison.md)

## 背景

M4 把落库做成批量后，瓶颈变成一句可以量化的话：**一次「插入 + 扣库存」提交的上限约 80 次/s，
吞吐 ≈ 80 × 实际批大小**（M4 复测第 4 节）。那 80 次/s 是同一张券的**同一行**
`UPDATE tb_seckill_voucher SET stock = stock - n` 的行锁 + 提交代价。批量把每单一次行锁换成每批
一次，但同一张券的并发批次仍然争同一行。

Redis 侧同样是单点：一张券的库存、预占、订单状态、到期索引全都是**一个 key**，无法分片，也没有
副本可切。D5 就是这条。

M5 要同时解决两件事：把那一行变成 K 行，把 Redis 从单节点变成 3 主 3 从，并且用一次真实的
主节点宕机证明「Redis 是可丢的性能层，正确性不依赖它」。

## 决策

### 1. 桶 = `userId % K`，K 是 2 的幂且 ≤ 1024

`SeckillBucketRouter` 把一张券拆成 K 份库存。桶由**用户**决定，不是由请求决定：

- 同一用户永远落同一桶 → **判重天然原子**，一次 Lua 就能完成，不需要跨桶。
- 订单号低位带着 `userId % 1024` 的基因（M3 的 Snowflake），所以 **K 取 2 的幂时，
  桶可以从订单号单独反推**。这不是锦上添花：订单状态轮询接口只有 orderId，没有 voucherId，
  也没有 userId。
- 准入时校验订单号的基因与买家一致，不一致直接拒绝：否则它的状态 key 会落到另一个桶、另一个
  slot，之后谁也查不回来。

### 2. hash tag 是 `{sk:b<n>}`，**不带券号**

计划里写的是 `sk:{v17:b3}:stock`。实现改成 `sk:{sk:b3}:stock:17`，理由：

- 秒杀期间热的是**一张券**，它的 K 个桶已经散在 K 个 slot 上，带不带券号对热点分散没有区别。
- 带券号的代价是：任何一个 key 都必须先知道券号才能拼出来。而按 orderId 查状态时没有券号。
- 代价：不同券的同号桶落在同一个 slot。多张券同时热时会略不均，接受，写在这里。

一次 Lua 调用的所有 key 都带同一个 tag：库存、活动元数据、预占 Hash、订单状态、桶内到期索引、
用户/IP 限频窗口。所以准入仍然是**一个 RTT、一个 slot**。

### 3. 活动元数据按桶复制

准入 Lua 要读活动状态和起止时间，而它只能读本桶 slot 的 key，所以 `meta` 在每个桶各存一份。
写入点只有三处（发券、启动预热、挂起券），都改成写 K 份。券的活动窗口不会高频变化，这份冗余
是静态的。

### 4. 消费批次按桶拆成多次往返

一批消息可能来自不同桶。认领与收尾因此**按桶分组，每桶一次往返**，结果按调用方顺序拼回去。
同一个桶的消息仍然是一次往返，所以常见情况没有变慢；跨桶的批次多几次 RTT，换来每次调用都在
一个 slot 内。

落库仍然按**券**分组（一次多值 `INSERT IGNORE` + 一次 `stock - n`），因为 MySQL 的那一行是
按券的。桶不改变 DB 分组。

### 5. L1 标记桶，L2 跟随桶

- L1（售罄标记）挂在拦截器上，**跑在鉴权之前**，只有券号没有用户，因此也没有桶。它现在只有在
  **每个桶都被标记**时才本地拒绝；单个桶空了不能挡住其他桶的买家。回补一个单位只重开它自己的桶。
  pub/sub 的消息体从 `+17` 变成 `+17:3`。
- L2（本地令牌桶）跟随本桶的剩余库存，因为脚本返回的就是本桶的库存。配置里的下限仍然是
  **按券**的数字，实现里除以 K 分摊，否则拆桶会让打到 Redis 的流量翻 K 倍。

### 6. 空桶不借库存

计划里留了「桶空时向相邻桶借」的选项。M5 先实现**不借**的简单版：

- 买家自己的桶空了就是「库存不足」，哪怕别的桶还有货。
- 这是**尾部浪费**，`SeckillBucketAdmissionIT` 用一个确定的例子把它钉住（4 桶 8 库存，
  桶 0 的第三个买家被拒，而全券还剩 6 件），真实分布下的浪费量由 `scripts/bench.sh m5` 的
  bucket 扫描给出。
- 借库存要两步（扣邻桶库存、写回本桶预占），两步之间崩溃要靠幂等 token 串联 + 对账器归还，
  复杂度不小。**先量化再决定**，数字回来后在本 ADR 补结论。

### 7. 对账器按桶扫描

到期索引变成 K 个 ZSET，一轮对账把批量按桶均分，逐桶取各自的份额。天然可以多实例按桶分片并行
（M5 没有做分片调度，只是把结构准备好了）。

### 8. 两个客户端都要认识 Cluster

- Lettuce：周期 10 秒刷新拓扑 + 打开全部自适应触发（MOVED/ASK/重连）。没有这一条，主从切换后
  客户端会一直用旧拓扑，直到重启。
- Redisson（只用来做对账器的调度锁）：同样按 `spring.data.redis.cluster.nodes` 走集群模式。
- 非秒杀路径里最后一处「多 key 但没有 tag」的脚本是登录验证码（码、冷却、失败计数三个 key），
  已改为共享手机号的 tag。博客热榜脚本本来就带 tag。

### 9. 部署与演练环境

`docker/redis-cluster/docker-compose.yml` 起 3 主 3 从。六个节点**共享宿主网络**：Cluster 节点
之间用它 announce 的地址互相通信，客户端也按同一个地址跟随 MOVED。桥接网络下节点只能 announce
容器地址，而应用和压测都在宿主机上；announce `127.0.0.1` 又会让每个节点指向自己。共享宿主网络
是唯一一个「对所有人都成立」的地址。

`REDIS_MODE=cluster scripts/stack.sh up` 同时保留单节点：基准版本（`v2.0-m4`）的 key 没有 tag，
在 Cluster 上根本跑不起来，A/B 必须一边单节点、一边集群。

## 代价与边界

- **尾部浪费**：不借库存时，买家的桶空了就买不到，尽管全券还有库存。K 越大越明显。
- **不同券的同号桶共用 slot**：多张券同时热时负载会略不均。
- **元数据 K 份**：写点三处，静态冗余；如果将来活动窗口要频繁改，这里要重新考虑。
- **跨桶批次多几次 RTT**：消费端一批如果跨 m 个桶，认领与收尾各是 m 次往返而不是 1 次。
- **异步复制会丢**：主节点宕机会丢掉尚未复制的预占与扣减，promote 之后 Redis 的库存比真相多。
  正确性由 MySQL 的 `stock >= n` 条件更新兜底，超放的请求走补偿并对用户可见地失败。这正是
  演练要量化的东西（RPO 与收敛时间）。
- **Redisson 3.13.6**：版本偏旧，集群模式可用，但没有升级；升级留给需要时。
