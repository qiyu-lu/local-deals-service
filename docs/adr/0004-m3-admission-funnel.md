# ADR 0004：M3 秒杀热路径——准入漏斗、本地发号、只让成功者碰 Broker

- 状态：**草案**。设计决策已定并已实现；正式对比数字待 `scripts/bench.sh m3` 跑完后填入
  （计划 0 节第 7 条：长测由人启动，结果交回下个会话再下结论、合并、打 tag）。
- 关联：[V2 计划 M3](../plan/v2-high-concurrency-plan.md)、[M0 基线](../../benchmark/v2/m0/baseline.md)、
  [ADR 0003](0003-m2-order-lifecycle.md)

## 背景

M2 结束时，秒杀接口每个请求（其中 99% 注定失败）都要付：一次 `SeckillTrafficGuard` Lua、
一次 `RedisIdWorker` INCR、一条事务 half message、本地事务里的准入 Lua、一次 end-transaction；
登录拦截器还要再读一次 token Hash、续一次期。M0 火焰图里这几项加起来占准入端一半以上，
Broker 上 half message 数等于请求数（D1、D2）。

## 决策

### 1. 漏斗分层：每一层只放行下一层需要的量

| 层 | 位置 | 成本 | 拦什么 |
| --- | --- | --- | --- |
| L0 | nginx `limit_req`（每 token 2 r/s、每 IP 50 r/s） | 0 次应用调用 | 脚本刷单、单用户狂点 |
| L1 | `SeckillSoldOutInterceptor`，排在登录拦截器**之前** | 0 次网络 IO | 售罄后的全部请求 |
| 令牌 | `X-Seckill-Token`，HMAC 本地校验 | 0 次网络 IO | 活动开始前的请求、冒用他人/他券的请求 |
| L2 | `SeckillLocalRateLimiter`，每实例、每券的令牌桶 | 0 次网络 IO | 超过剩余库存 × 系数的请求 |
| L3 | `seckill_check.lua`，一次 RTT | 1 次 Redis | 用户/IP 限频、活动窗口、判重、扣减、写预占 |
| 发布 | 成功者一条普通消息 | 1 次 Broker | — |

- **L1 放在认证之前**：售罄答复对任何人都一样，不泄露信息；放在后面就还要付登录拦截器的
  两次 Redis 命令，“售罄后 0 网络 IO”做不到（计划没写到这一点）。代价：未登录用户在售罄后
  看到“库存不足”而不是 401。
- **L1 的失效**：Lua 报库存不足（或刚拿走最后一件）时置位，经 Redis pub/sub（`+id` / `-id`）广播；
  库存回到 Redis 的三个地方（首次补偿、关单释放、退款释放）广播清除。pub/sub 会丢、不同实例的
  消息会交错，所以已售罄的券每个实例每秒仍放 1 个探针请求去 Redis：探到库存就清标记。陈旧标记
  最多持续一个探针间隔，不依赖消息必达。
- **L2 的速率**：`max(最低速率, 剩余库存 × 系数)`，默认系数 2、最低 50/s，容量 1 秒。剩余库存来自
  L3 脚本的返回值，零额外开销；还没见过库存的券不限。它替代了原先 Redis 里的活动级限流；
  用户级 / IP 级限频并进 L3 同一个脚本。超出答 429 `SECKILL_BUSY`。
- **L3 单脚本**：返回 `{code, remainingStock}`；新增 6/7（用户/IP 限频）与 8（该 orderId 已有状态）。
  限频计数只在通过时递增，被拒的请求不占别人的名额。

### 2. 本地 Snowflake 发号

- 布局：`41 位毫秒（纪元 2025-01-01Z）| 5 位 worker | 7 位序号 | 10 位 userId % 1024`。低 10 位是
  用户的分片基因，M6 按 user_id 分片时按 order_no 也能单分片命中。每毫秒每实例 128 个号，
  即 12.8 万/秒，远高于准入吞吐。
- **与 V1 号段不相交**：V1 的号是 `(秒 − 2025-12-22) << 32 | count`，在 2^25 秒（2027-01）之前都小于 2^57；
  新纪元让 2026-02 之后签发的号全部 ≥ 2^57。M2 迁移来的旧订单号因此不可能与新号撞车；时钟早于
  这个范围时发号器直接拒绝（fail closed），而不是签出一个低号。
- **workerId**：Redis 租约（`SET NX PX`，32 个槽，每 ttl/3 续一次，默认 ttl 30 s）。实例按**自己的时钟**
  在 ttl 的 5/6 处停止发号（本地栅栏），所以续约失败期间 Redis 还没让出这个槽时，本实例已经不再发号，
  不会与接手者重叠。拿不到租约时接口答 503，和原来 INCR 失败时一样。
- 小幅时钟回拨（≤5 ms）等过去，更大的回拨拒绝发号。
- 计划原文“只在 Lua 成功后才需要”与“Lua 内写 orderId”矛盾，按计划的结论处理：本地发号零 RTT，
  仍在 Lua 之前生成；失败者只多花一次本地位运算。

### 3. 只有成功者碰 Broker：选 B（普通发送 + 对账器重投）

- A：保留事务消息，但 Lua 在 HTTP 线程先跑，成功才发 half message，本地事务只做确认。
- B：Lua 成功 → `syncSend` 一条普通消息；发送失败或进程在 Lua 与发送之间崩溃，由对账器从
  `PROCESSING` 预占**重投**。预占本身就是 outbox。
- 两个方案都要处理“Lua 成功、消息没发出去”：A 在 Lua 与 half message 之间崩溃时同样留下没有消息
  的预占，事务消息的回查只覆盖 half 与 end-tx 之间那一小段。所以 A 并不能省掉重投，只是在每个
  成功者身上多付一次 half + 一次 end-tx。
- 决策：**B**。对账器在“写库库证明无单、且未到最终期限”时重投原消息（重复无害：消费者看到 SUCCESS
  或已有订单就确认），过了最终期限才精确补偿，行为与之前一致。`SeckillOrderProducer` 不再是
  事务监听器。
- 故障证明：`SeckillRedriveIT` 用真实 Lua、Broker、消费者复现“Lua 成功、什么也没发”；
  `benchmark/v2/scripts/kill-drill.sh` 在压测中 `kill -9` 应用，`BROKER_DOWN=1` 时先杀 Broker 让发送
  失败，制造出真正没有消息的预占。
- 探索发现：只 `docker pause` Broker 再 `kill -9` 应用，**不会**丢消息——请求字节已在 Broker 的 socket
  缓冲里，恢复后照样落盘。真实的“Lua→发送”窗口只有亚毫秒，自然 kill 几乎打不中。

### 4. 删除隔离区（quarantine）

计划 M0 留给 M3：若新发号方案下 orderId 碰撞不可能发生，就删。碰撞现在进不了 Redis：
Snowflake 在租约内唯一；即使租约异常导致两个实例共用 worker，L3 脚本发现该 orderId 的状态
Hash 已存在就返回 8（不写任何东西），应用换号重试一次。状态 Hash 永远只属于一个预占——
这正是当初设隔离区所缺的证明。于是：

- 删除 `seckill_reconcile_quarantine.lua`、隔离 ZSET 与原因 Hash、四个脚本里的隔离守卫、
  对账决策 `QUARANTINED`、消费者的 orderId 冲突隔离分支、隔离积压指标。
- DB 里 orderId 属于别人（只可能来自 Redis 数据丢失后的极端情况）：与“同用户同券已有订单”一样，
  挂起券 + 精确补偿。
- 对账器遇到归属不符、预占不符、字段损坏：计数 `needs_operator`、打错误日志、推迟一个 retryDelay，
  继续留在到期积压里可见，等人处理；不再搬进另一个集合。
- 计划说连 `seckill_reconcile_defer_unresolved.lua` 一起删，但它还负责“共享用户锁忙”时的推迟，
  这把锁 M4 才拆，所以保留，只去掉隔离逻辑。

### 5. 秒杀令牌

`GET /voucher-order/seckill/{id}/token` 只在活动 ACTIVE 且在窗口内时签发
`<过期秒>.<base64url(HMAC-SHA256(secret, userId:voucherId:过期秒))>`，默认 10 分钟。下单缺令牌或
令牌不属于本人本券答 403 `SECKILL_TOKEN_INVALID`。压测时 k6 用同一密钥自己签（每个请求都是新用户，
先取令牌会让请求数翻倍），服务端照常验签，验签成本计入测量。

## 代价与边界

- L1/L2 都是每实例的：N 个实例时 L2 的总放行量是 N × 剩余库存 × 系数；这是有意的（只防洪峰，
  不做精确配额），精确判定仍在 L3。
- L2 会把“还有库存”时的一部分请求答成 429：在秒杀语义里它们本来就抢不到。
- 对账器的重投速度是瓶颈：默认 stale-after 2 分钟、每 10 秒 100 单。探索性演练里 4494 个没有消息的
  预占用了 589 秒才全部落库。正确性不受影响（预占、订单、库存三方一致），但收敛慢，M4 批量化时处理。
- Lettuce 连接池只有 10：L1 之前，售罄请求每个要 3 次 Redis 命令，池等待是 M0–M2 在 1.5 万 req/s
  附近掉请求的原因之一；L1 之后售罄请求不再碰 Redis，这个瓶颈基本消失，池大小未调。
- 压测机上 k6 只有 2 个核：M3 之后应用在 3 万 req/s 时只用约 1.3 核，剩余的丢弃主要来自压测端。
  `summary.csv` 新增 `k6_cpu_cores` 列来证明或否定这一点。
