# ADR 0007：批量消费的真正约束是「批里有几条」，不是「一次提交多快」

- 状态：**已决定**（2026-09-20）。扫描已跑完（`benchmark/v2/m6/20260920-215408-m6-consume`，
  `status=DONE`，commit `f35f34d`）。消费默认值改为 `batch-size=256`、`thread-count=4`、
  `pull-interval=50ms`、`pull-batch-size=256`；**MySQL 热点行 `tb_seckill_voucher` 不拆**，
  理由与回归条件见「决策 4」。
- 关联：[V2 计划 M6](../plan/v2-high-concurrency-plan.md)、[ADR 0005](0005-m4-batch-consumption.md)、
  [ADR 0006](0006-m5-cluster-buckets.md)、[M4 复测](../../benchmark/v2/m4/comparison.md)、
  [M5 复测](../../benchmark/v2/m5/comparison.md)、[M6 消费参数扫描](../../benchmark/v2/m6/consume-sweep.md)

## 背景

M4 把落库做成批量，量到「吞吐 ≈ 80 次提交/s × 实际批大小」，并推断慢轮是「批里只有一两条」。
**那是推断**：`LocalDealsMetrics` 没有批大小指标，`scripts/bench.sh` 不归档 actuator 快照，
`app.log` 每次 `app-start` 被覆盖。M4 把这两件事交给 M5，M5 没做，于是 M5 的落库 A/B
九轮全部落在同一条「双稳态」曲线上，读不出任何版本差异（M5 复测第 4 节）。

M4 复测结尾还写了一句「抬高 80 次/s 这个上限正是 M5 的库存分桶」。M5 收尾时已经更正：
那 80 次/s 是 MySQL `tb_seckill_voucher` **同一行**的代价，M5 分的是 Redis 的 key。
于是「拆那一行」成了一件不属于任何里程碑的工作，M6 开头把它接了过来。

## 决策

### 1. 先补仪表，再改任何东西

- `local_deals.seckill.consume.batch.size{stage=delivered|persisted}`：
  **delivered** 是 Broker 交给消费者的一批有几条，**persisted** 是「一次 INSERT + 一次扣库存」
  实际带走了几条。两者的差就是分组损耗。
- `local_deals.seckill.consume.degraded{reason=insert_skipped|stock_short}`：
  退化不再只有一条日志和一个共用的 FAILURE 计时器。`BatchPersistDegradedException` 带上原因，
  「重投撞上已存在的行」和「库存撑不住这一批」是两件事，分开数。
- `scripts/bench.sh`：每个测量轮结束前在应用还活着时抓一次 `/actuator/prometheus`；
  `stack.sh app-start` 把 `app.log` **轮转**而不是覆盖，整场的日志都随结果归档；
  `summary.csv` 增加 `batch_mean` 列，取值是该轮前后两次抓取的差，所以它只描述这一轮。

### 2. 实测结果：批大小约 1.03

M5 冒烟（`batchSize=64`，`threadCount=16`）：

| 阶段 | 批数 | 订单数 | **均值** | 最大 | 退化 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 阶梯 | 1139 | 1200 | **1.05** | 6 | 0 |
| 落库 | 2904 | 3000 | **1.03** | 4 | 0 |
| Redis 宕机轮 | 3814 | 4859 | **1.27** | **32** | 4 |

`persisted` 与 `delivered` 完全相等，退化计数为 0——**分组没有损耗，批本身就没攒起来**。

成因：16 个消费线程 × 一次提交约 12 ms ≈ 1300 次/s 的处理能力，而到达速率是 1000–2000/s。
消费者本来就跟得上，队列里永远没有第二条消息在等，RocketMQ 自然一次只交一条。
`consumeMessageBatchMaxSize` 是上界，不是目标。

宕机轮是反证：故障转移期间积压形成了，同一份代码的批大小立刻到 max 32。**同一个机制被看到两次。**

这同时解释了 M5 那个「双稳态」：一轮快还是慢，取决于那一轮有没有攒出积压。

> **2026-09-20 更正**：上面这一句被扫描推翻了。慢档与快档的批大小都在 1.2 左右，
> 翻转的是提交速率（约 400 → 约 80 次/s），不是批大小。见「实测」第 3 条。

### 3. 因此先扫消费参数，再决定拆不拆 MySQL 那一行

拆行抬高的是「提交速率」这一项；而冒烟说明当前被钉住的是「批大小」这一项。批大小为 1 时，
把一行拆成 K 行几乎买不到东西。顺序因此反过来：

1. 先把批填满——`pull-interval`（队列两次拉取之间等多久）、`pull-batch-size`、线程数。
   新增的两个配置项**默认值等于 M4 的既有行为**（0 ms / 32），不扫描就什么都不变。
2. 填满之后如果 80 次/s 重新成为约束，再拆行，届时收益是可预期的（80 × K）。

扫描场景 `scripts/bench.sh m6-consume`，组合写作 `batch:threads:pullMs:pullBatch`。

### 3.1 扫描之后：默认值改为 `256:4:50ms:256`

这是 `summary.csv` 里唯一一个让消费端在整轮内跟住 2000 单/s 的组合（2001.5 单/s、负载后
0.1 s 排空、批 12.68）。**四个旋钮整组进默认值**，因为只有这一整组被测过；拆出「只改
拉取间隔和线程数」会得到 `64:4:50:32`，而那个组合一次都没跑。有证据的是拉取间隔，
没有独立证据的是 `batch-size` 与 `pull-batch-size`（实测批封顶 32，256 从未被触到），
线程数方向对但落在噪声带内——归因逐条写在 [M6 消费参数扫描](../../benchmark/v2/m6/consume-sweep.md) 第 7 节。

### 4. MySQL 热点行 `tb_seckill_voucher`：**不拆**

决策 3 立的条件是「填满之后如果 80 次/s 重新成为约束，再拆行」。扫描的结果是这个条件
**没有成立，而且它的前提本身是错的**：

1. **80 次/s 不是那一行的能力，是双稳态的慢档。** 同一轮里，批大小按 1.20 折算，
   `b64t16i0p32` 前 17 秒跑在约 394 次提交/s，随后 21 秒掉到约 73 次/s；当前默认那一轮
   前 21 秒是约 427 次/s。拆行是为了把 80 乘 K，而这个被拆的数字高估了自己 5 倍。
2. **当前的约束是到达速率，不是提交速率。** 新默认值下那一行每秒只被要求约 150 次提交
   （2001.5 ÷ 12.68），而它已经被看到能做约 400 次。消费端整轮跟住了发压速率，
   本次场景（2000 req/s）根本没有把它逼到上限。
3. **减少消费线程没有让那一行更难受。** 赢的组合是四线程——比 M4 的 16、M5 的 16 都少，
   每次提交带走 12.68 单。同一行上的并发反而下降了。

**回归条件**：当某一次实测同时满足——提供的到达速率远高于 2000/s、`drain_s_after_load`
重新大于 0、且 `persist_orders_per_s ÷ batch_mean` 不再随负载上升而上升（提交速率封顶）——
拆行的收益才是可预期的（封顶值 × K）。这件事挂在 M8 那一晚的高速率落库轮上。

> **2026-09-21 更正（M8 长测）**：回归条件三条同时成立了。`m8-scale` 的落库轮以 2 万/s 灌入、
> 负载后仍要排空 3.4–7.6 s，而提交次数/s 在 1/2/3 个实例下都是 70–115、没有趋势
> （`benchmark/v2/m8/20260921-042503-m8-scale/`）。所以「不拆」的前提——约束是到达速率——
> 已不成立；上面第 1 条看到的约 400 次/s 在多实例持续负载下也没有再出现。本决策当时是对的，
> 现在由 [ADR 0009](0009-m8-multi-instance.md)「实测」第 3 条取代：那一行是写路径水平扩展的实测上限，
> 拆不拆是 M8 之后待定的事。

## 代价与边界

- **`pull-interval` 拿延迟换吞吐**：等待积压意味着每条消息多等最多一个 pull 间隔才落库。
  秒杀的落库是异步的（用户看到的是准入结果），所以这笔交易大概率划算，但它**是一笔交易**，
  扫描要同时看 `drain_s_after_load`，不能只看 `persist_orders_per_s`。
  **实测下来这笔交易的价码是：默认每条订单多等最多 50 ms 才落库。** 买到的是同一轮里
  批大小 2.16 → 12.68、排空 11.6/30.7 s → 0.1 s。准入端没有被波及——赢的那一轮 HTTP
  p99 21.7 ms、max 62.3 ms，与其余各轮同档（p99 11.6–71.5 ms）。
  代价真正会被看见的地方是「下单后多久能查到订单」和对账器的到期判定：
  `reconciliation.stale-after` 必须远大于一个 pull 间隔，默认 2 分钟对 50 ms 有三个数量级的
  余量，但把 `pull-interval` 调到上限 1000 ms 时要重新看这一条。
- **`batch-size` 256 目前是一个够不着的上界**：实测 delivered 批从未超过 32，所以它和
  `pull-batch-size` 一样没有被触到。如果将来那个 32 的上界被抬高（它来自 Broker 侧，
  本次没有去读 Broker 的运行配置），一次事务会带走多达 256 单并在热点行上持锁更久——
  那时要重新量，而不是假设更大的批一定更好。
- **`batch_mean` 是每轮的差值**，不是瞬时分布；某一轮内部的快慢切换仍然只能从 `.prom`
  的直方图桶里看。
- **对照组基线的环境假设变了**：`v2.0-m5` 是集群构建，不能再按「基线一律跑单节点」处理，
  否则准入脚本读不到元数据、整轮 503。`S_BASELINE_BUCKETS` 现在显式表达这件事。
- **拆 MySQL 热点行的设计尚未定稿**。若将来要做，真正让它生效的前提是消费批次尽量来自
  同一个桶（否则一个事务要持有 K 个行锁，竞争更糟），也就是生产端按桶选队列——
  那是一笔比「加一张表」大得多的改动，不应该在没有数据支持时就先做。

四件必须一起读的事：

1. **精度**：第 2、3 行是同一个 jar、同一组参数、相隔两分钟的两轮，吞吐差 2.18 倍而
   `batch_mean` 只差 0.5%。**这张表里任何小于约 2.2 倍的单轮差异都读不出来**，线程数那三行
   （550.0 / 1023.3 / 767.1）因此不构成结论。
2. **决策 2 的核心结论在 2 万单上站住了**：七份 `.prom` 里 `stage=persisted` 与
   `stage=delivered` 的 `_count`、`_sum` **完全相等**，两个 `consume_degraded_total` 全部为 0。
   分组依然没有损耗。
3. **决策 2 的一句推断被推翻**：本文原写「A 段 = 批里只有一两条」。实测是 A 段与 B 段的批
   大小都在 1.2 左右，**翻转的是提交速率（约 400 → 约 80 次/s），不是批大小**。
   为什么翻转，本次仪表仍然答不出来。
4. **2001.5 单/s 是下限不是上限**：`drain_s_after_load = 0.1 s` 说明负载停止时已经落完，
   这个数字等于场景的发压速率 2000 req/s。**本场景测不出任何高于 2000 单/s 的东西**，
   要量上限需要更高的 `S_DRAIN_RATE`，已挂到 M8 那一晚。同理，赢的那一轮只持续 10.5 秒，
   而 `b64t4i20p128` 在第 8 秒从约 2000 单/s 掉到 390——**新默认值在更长负载下会不会也掉
   下去，本次没有被检验**。
