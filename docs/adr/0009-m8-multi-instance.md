# ADR 0009：M8 多实例全链路——一个 trace、三个实例、一条过夜命令

- 状态：**已接受（实现与场景脚本）**（2026-09-21）。长测由人手动启动，数字见「实测」一节，
  跑完前该节留空。
- 关联：[V2 计划 M8](../plan/v2-high-concurrency-plan.md)、[ADR 0006](0006-m5-cluster-buckets.md)、
  [ADR 0008](0008-m6-order-sharding.md)

## 背景

M0–M6 的全部证据来自**一个实例**。诊断表里的 D8 说的就是这件事：多实例调度、故障转移都没有
验证过。M5 补了一半——Redis 主节点宕机演练——但它得到的结论反而让另外半件事更悬：

- **实测 RPO = 0**。主节点死掉时它负责的 slot 直接不可写，买家收到 503 而不是一个假的成功，
  丢失窗口只有不到 1 ms 的复制延迟。于是「Redis 超放 → MySQL `stock >= n` 兜底」这条整个设计
  赖以成立的最后防线，**至今没有被真实触发过一次**。
- 「多实例」这三个字在 M6 之前只是一个断言。

M8 只做三件事，其余（虚拟线程对比、Grafana 看板）在 2026-09-21 砍掉：把一个请求从 nginx 一路
标到订单行；把三个实例真的跑起来并量它加不加吞吐；把那条从没触发过的防线逼出来。

## 决策

### 1. 一个 trace 贯穿 HTTP → MQ → DB，三跳三种机制

- **HTTP**：`TraceIdFilter` 排在所有过滤器和拦截器之前——被 L1 售罄标记挡掉的请求，正是最值得
  查的那一类。id 进 MDC，再由 `logging.pattern.level` 的 `%X{traceId}` 进入**每一行**日志，
  而不是一个参数一个参数地传；同时写回响应头，调用方能拿着它来问。
- **不合法的头换掉，不修补**。它会进入这个请求的每一行日志，所以能往里写换行的人就能伪造日志行。
  修补过的 id 仍然来自调用方，而且和发送方记下的对不上，所以直接换一个新的。
- **MQ**：消息体带 `traceId`。对账器重投的消息已经带着原请求的 id，那个更真，不覆盖。
- **DB**：`trade_order.trace_id` 列。**为什么不是 SQL 注释**：一个消费批次把 N 个买家合成一条
  INSERT，语句根本没有单一的 trace；而且每请求不同的注释会让预编译语句的文本每次都不一样，
  等于在热路径上扔掉语句缓存。列不会：它是那条本来就要执行的 INSERT 多写的一个字段，而且比
  日志轮转活得久。
- 关单的定时消息也带着买家的 trace，所以一小时后那句 `Unpaid order closed` 会和当初那次请求
  连在一起——写在三个实例中的哪一个都行。
- 消费线程是池化的：每条消息用自己的 trace 进出，用完把线程还成原样，批次本身不属于任何 trace。

### 2. nginx + N 个实例，每个实例独占自己的核

- `INSTANCE=n` 让第 n 个实例用 `APP_PORT+n-1`、自己的 pid 与日志。**实例 1 的文件名一个字都
  没改**，所以 M3–M6 的场景仍然找得到它们。
- **扩展曲线给每个实例自己的 cpuset，而不是切分一份固定预算**。三个实例分同一份 8 核只能测出
  「多开进程的开销」，测不出扩展性。代价见下。
- nginx 用 host network：上游就是宿主机进程，走桥接等于给每一个被测请求加一层 NAT。
- **不开 `limit_req`**。目标架构图里有它，但压测前面摆一个限流器，测的就是限流器；要测的漏斗
  在应用里。
- nginx 在调用方没带头时用 `$request_id` 生成 `X-Trace-Id`，所以边缘日志和应用日志共用一个 id。

### 3. 压测脚本自己扮演支付渠道

mock 渠道把支付登记在**进程内存**里，收银台因此只在下单的那个实例上有效。这不是缺陷而是它的
定位：真实渠道是外部系统。所以全链路脚本走 API 预支付，然后自己按 `PaymentSigner` 的规范签名
发 `/payment/callback`——那才是多实例下必须站得住的端点：签名校验、重复投递、乱序、按支付单行
幂等。**mock 渠道的内存态不改**，作为已知边界写在下面。

### 4. 发现并修掉：附属表主键的第二个 Snowflake

这是全链路冒烟第一次跑就抓到的东西，1000 单里 24 次：

```text
Duplicate entry '1308608633747013633' for key 'order_state_log_3.PRIMARY'
```

这个应用里有**两个 Snowflake**。订单号那个的 workerId 来自 Redis 租约（`WorkerIdLease`），
两个实例不可能拿到同一个。M6 给附属表主键用的是 ShardingSphere 的 SNOWFLAKE（因为
AUTO_INCREMENT 在每张物理表各自从头数），它的 workerId **从自己的 props 读，默认 0**。两个
实例都是 0，于是同一毫秒铸出同一个 id。一个实例永远看不到这件事——所以此前每一次测试、每一次
压测都是绿的。

修法：`sharding.yaml` 里放占位符，`ShardingWorkerId` 在解析前填掉，启动时打日志。号从
`local-deals.sharding.worker-id` 取，没配就取 `server.port % 1024`。

**为什么不复用已有的 Redis 租约**（一个机制显然比两个好）：分片数据源要跑 Flyway 迁移，
从 Redis 取号意味着 Redis 一挂就没有任何数据库能迁移。端口对这个项目部署的形态（同一台机器上
几个实例）已经够用——一台机器不可能把同一个端口给两个实例。跨机端口会重复，那时必须显式配。

### 5. 一条命令跑完四个场景，互不牵连

`scripts/bench.sh m8` 依次跑 `m6`（M6 欠的分片同场对照）、`m8-fullchain`、`m8-scale`、
`m8-window`。每个场景是**独立进程 + 独立 stack + 独立结果目录 + 独立 status**：失败记进
`scenarios.csv`，下一个照跑。一条过夜命令的意义就在于第四个场景不该取决于第一个的运气。
suite 替所有子场景持有那把场景锁，子进程被告知不要再抢；jar 按 commit 缓存，四个场景只打一次包。

### 6. 复制空窗：先让副本睡着，再杀主

M5 之所以 RPO = 0，不是运气而是机制：主节点一死，它的 slot 直接不可写。要逼出「Redis 超放」，
必须先造出空窗。`DEBUG SLEEP n` 让副本**停止应用复制流**但连接还在，几秒后杀主，被提升的副本
就带着几秒前的世界观回来——它相信已经卖掉的库存还在，于是放进比真实库存更多的买家。这时挡在
超卖前面的只剩 MySQL 的 `stock = stock - n WHERE stock >= n`。

量化的四个数：`stock_short_degraded`（条件更新拒掉整批的次数，也就是那条防线真的开火了几次）、
`lost_admissions`（被告知抢到却没有订单的人数）、`stock_gap`（Redis 相信的库存减去真实库存）、
`oversold`。

**造这个空窗花了四次才对，三次失败各自说明一件事**，都写进了脚本的注释：

1. **杀晚了**。第一次在库存卖光之后才杀主节点（`stock_at_kill=0`），被提升的副本回来时本来就
   没有东西可信。一整行 0 读起来像「防线成立」，其实是「什么都没测」。所以结果行里加了
   `window_effective`，让一次时机不对的运行自己说出来。
2. **`DEBUG SLEEP` 根本造不出空窗**。它只让副本停止**应用**复制流，字节早已在它的 socket 缓冲区里；
   醒来以后一条不落地应用，RPO 仍然是 0。要真丢，主节点必须停止**发送**——先让副本睡着
   （睡着的副本无法重连），再从主节点这边 `CLIENT KILL TYPE replica` 把链路切断。
3. **买家不能比库存少**。切断链路之后确实量到了空窗（`stock_gap=758`、6 个人被告知抢到却没有订单），
   但 `stock_short_degraded` 还是 0——同一行里 1787 件根本没卖出去。复活的库存没人来抢，
   条件更新自然没有东西可拒。所以空窗轮必须**买家多于库存**（`DRILL_TAIL_S`）。

三件事同时成立之后，冒烟里第一次看见这条防线开火：4000 库存，Redis 放进 **4697** 人，
MySQL 只建了 **4000** 单，条件更新拒掉 **86** 个批次，**超卖 0**，697 个人拿到了假的成功。
（冒烟数字，只用于确认机制成立；正式数字见「实测」。）

## 代价与边界

- **单机 16 vCPU 的分核**：三个实例各 2 个、nginx 2 个、依赖 4 个、k6 4 个。所以扩展曲线是
  「每实例 2 核」的曲线，不是「每实例 8 核」的；M3 的天花板数字不能直接拿来比。
- Redis Cluster、Broker、两个订单库、nginx 和 k6 本身都是**共享的**。曲线一旦不线性，先看它们
  ——`edge.csv` 里有 nginx 的核数，`summary.csv` 里有 k6 的。
- mock 渠道的内存态没有改（决策 3）。多实例下它的收银台仍然只在下单那个实例上有效。
- ShardingSphere 的 workerId 跨机部署必须显式配置（决策 4）。
- traceId 的覆盖面：HTTP 是全量的；**MQ → DB 这一跳只做了秒杀链与关单链**。支付回调、营销发放
  的消息没有接，因为它们不跨实例交付一笔订单的所有权。
- `DEBUG SLEEP` 期间副本也无法参与选举，所以转移时间会比 M5 那两次长——这是制造空窗的代价，
  不是回归。
