# 深挖问答：后台、营销与读路径

> 《[项目深挖问答](project-deep-dive.md)》的一部分：第 8、9、10 节，13 题。
> 事实标准与全书一致：机制来自代码，数字原样抄自 [压测报告](../benchmark-report.md) 或[主计划](../plan/v2-high-concurrency-plan.md)进度表，没做的直接说没做。

## 8. 商户后台与权限

### Q8.1 后台权限怎么做的？怎么保证商户 A 看不到商户 B 的数据？  〔常见｜追问链：后台权限怎么做的 → RBAC 几张表 → 多租户隔离靠什么 → 漏写一个查询条件会怎样 → 为什么不用框架自动注入租户条件〕
**答**：权限是标准 RBAC 四张表（角色、权限点、账号-角色、角色-权限），落到接口上靠一个权限注解 `@RequireAdminPermission`，由后台授权拦截器检查；**没有注解就是 403**，是白名单准入而不是默认放行。但注解只能回答「这个接口你能不能调」，回答不了「这一行是不是你的」，所以跨商户隔离是第三层：每个服务方法自己按主体的范围类型加商户条件。两层是分开的，缺一不可。

**展开**：
- 三道关，详见笔记 02 第三节 3.2：会话拦截器只认人不拒绝 → 授权拦截器判断权限点 → 服务方法里做行级隔离。
- 权限点是「模块:动作」的字符串，内置三个角色：平台、商户主账号、商户员工。核销权限三个角色都有（店员站柜台就是干这个的），审计查看只给平台和主账号——见迁移 `V15__admin_audit_and_coupon_permissions.sql` 里那两条按角色码插授权的 SQL。
- 授权拦截器的取注解顺序是「先方法、后类，两处都没有就 403」。证据：`AdminAuthorizationInterceptorTest#authenticatedRequestWithoutExplicitAnnotationIsDeniedByDefault`，以及走真实拦截器链的 `AdminMvcSecurityTest#actualInterceptorChainRequiresCurrentAdminPermission`。
- 行级隔离有固定写法：列表查询商户账号强制加 `merchant_id = 自己`；单条读取按（主键，商户 id）查，**查不到一律 404**，不存在和不属于你返回同一个东西，不给跨商户探测留信号；更新先按（主键，商户 id）`FOR UPDATE` 锁行，`UPDATE` 的 `WHERE` 里**再带一次**商户 id，影响行数不为 1 当 404。锁一次、条件再带一次，是为了不依赖「读的时候属于我、写的时候还属于我」。
- 仅平台能做的动作（列商户、建商户、把历史商铺分配给商户）在服务里再显式判断一次范围类型，和权限点注解构成双保险。
- 商铺归属只许「认领」不许「换绑」：目标必须还挂在迁移预置的「历史待分配」商户下，更新以「当前商户 id 仍是原来那个」为条件，两个人同时认领只有一个成。
- 证据：`AdminRbacIT#merchantScopeIsEnforcedByTheSameVoucherQueryThatReturnsRows`——用同一个查询、换一个商户主体跑，能返回行的那条 SQL 在换人之后返回空。
- **本项目没做**：没有 MyBatis 拦截器自动往 SQL 里注入租户条件，也没有数据库的行级安全策略，更没有「所有后台查询必须带商户条件」的静态检查。**会怎么做**：成熟方案是写一个 SQL 解析层的租户插件（比如 MyBatis-Plus 的多租户插件），在 SQL 被执行前把 `merchant_id = ?` 挂到每个 `WHERE` 上，再配一份白名单表说明哪些表不参与。代价有三条：一是所有 SQL 都要能被解析器正确改写，复杂子查询和 `UNION` 容易被改错或漏改；二是隔离变成隐式的，读代码看不见条件，出问题排查更难；三是平台账号的「全通」要开后门，后门本身就是新的越权入口。我当前的取舍是把隔离写成显式且可读的代码，靠写法统一和集成测试兜住，弱点就是新写一个查询全靠人记得——这是这套设计里真实的弱点，我不回避。

**可能的追问**：→ Q8.2（改完权限已登录的人怎么办）；→ Q8.3（审计怎么保证不漏）；→ 「平台账号能核销任何商户的券吗」；→ 「商户后台按商户翻订单怎么查，分片了吧」（是跨 8 张表广播归并，详见第 08 章）。

**别踩**：
- 不要把「权限注解」说成「解决了多租户隔离」——它只管接口，行级隔离是另写的，说混了一追就穿。
- 不要说成「用了 Spring Security」——这里是两个自写的拦截器加一个注解，没有引 Security。
- 不要吹「租户隔离自动化、不可能漏」——本项目恰恰是手写的，主动说出这个弱点比被问出来强。
- 单条越权访问返回的是 404 不是 403，说反了就把「不给探测信号」这个设计意图讲丢了。

### Q8.2 改了权限之后，已经登录的人怎么立刻失效？  〔常见｜追问链：token 怎么存的 → 改密码/停用怎么踢人 → JWT 能撤销吗 → 黑名单要多大 → 缓存了权限还能立刻失效吗 → 长连接怎么办〕
**答**：会话是 Redis 里一个不透明令牌的键，值不是单纯的账号 id，而是「账号 id:签发时的认证版本号」。改密码和停用账号时对账号表做一条带版本号 CAS 的更新，把版本号加一，所有在途会话里记的那个数就都旧了；下一次请求走到会话拦截器，版本号比对不上，会话键被删、按未登录处理。不需要遍历 Redis，也不需要黑名单。

**展开**：
- 「权限改了要立刻生效」这件事在本项目其实有两个层次：
  1. **权限点的变更**是立刻生效的，因为**每个后台请求都重新查库**拿账号、角色码、权限点，压根没有缓存。证据：`AdminSessionServiceTest#everyResolutionReloadsAccountAndCurrentPermissionsFromDatabase`。
  2. **要把人整个踢下线**（改密、停用账号、停用商户）才走认证版本号那一刀。
- 为什么不把令牌落库做会话表：那要每次请求多写一次续期；版本号是账号表上一个整数，改密和停用本来就要写这一行，加一不花额外的写。撤销是「懒失效」——下一次请求自己发现对不上。
- 版本号的更新必须是 CAS：`SET 口令哈希 = 新值, auth_version = auth_version + 1 WHERE id = ? AND auth_version = 读到的值 AND status = 1`，影响行数不是 1 返回 409 让对方重来。直接 `+1` 的话两个并发操作都会成功，但其中一个是基于已经过期的账号状态做的判断。停用账号那条 CAS 商户账号还在 `WHERE` 里额外带商户 id。
- 停用商户主体等于一次性停掉它名下所有账号——资格检查里会查商户主体是否启用，不用逐个改账号。证据：`AdminSessionServiceTest#disabledMerchantRevokesExistingMerchantSession`、`#disabledAccountRevokesExistingRedisTokenImmediately`、`#credentialVersionChangeRevokesAnOtherwiseValidToken`。
- **长连接**：后台实时推送的 WebSocket 会话里存着签发它的令牌，每次推送前对每个本地会话重新解析一次主体，核对账号 id、实时订单权限、范围类型和商户 id，任何一条不符就摘掉会话并以「违反策略」关闭。所以那一刀对已连上的连接同样生效，生效时机是「下一条要推给它的消息」。详见笔记 02 第三节 3.5。
- **诚实的边界**：这不是「立刻」，是「下一次请求时」。而且粒度是整个账号，做不到「只踢掉某一台设备」。按 30 分钟会话 TTL 算，最坏情况是一个已停用账号的令牌在它下次发请求之前一直躺着——但它躺着不发请求也做不了任何事。
- **本项目没做**：没有主动推送式的撤销（比如发一条撤销事件让各实例清本地缓存），也没有令牌黑名单。**会怎么做**：如果哪天为了省掉每请求 3–4 次库查而给权限加缓存，就必须配一条撤销广播：改密/停用时往 Redis 发布订阅或消息里投一条「账号 X 版本到 N」，各实例收到就清掉本地条目。代价是广播本身不可靠（实例刚启动、订阅断开时会漏），所以还得给缓存配一个很短的 TTL 做兜底，撤销延迟就变成「广播延迟或缓存 TTL 取小」而不是零。也就是说**加缓存是要用撤销的确定性去换的**，后台 QPS 低，我没换。

**可能的追问**：→ 「那你为什么不用 JWT」；→ 「每个请求查 3–4 次库不慢吗」；→ Q8.1（权限点本身怎么判）；→ 「WebSocket 握手怎么带令牌」（一次性 30 秒票据，详见笔记 02 第三节 3.5）。

**别踩**：
- 别说「改了权限立刻失效，因为我存的是 Redis」——存 Redis 只解决「删一个令牌」，解决不了「一个账号有多个令牌、令牌不落库没法枚举」，版本号才是答案。
- 别把它说成「立刻」。它是懒失效，下一次请求才发现。这句要主动补，否则被追一句「那他不发请求呢」就被动。
- 别吹「无缓存所以性能没问题」，反过来讲：每个后台请求一次 Redis 读加三到四次库查，没有任何缓存，这是「能立刻撤销」的直接代价，后台 QPS 低所以可以接受。
- 别说 JWT「加个黑名单就等价了」——黑名单的规模和过期策略是新问题，而且 JWT 里缓存的权限本身也会过期。

### Q8.3 后台操作审计怎么做的？为什么不逐个接口加注解？  〔偶见｜追问链：审计怎么落 → 切点挂在哪 → 漏接口怎么办 → 审计和业务同一个事务吗 → 审计写失败怎么办 → 有没有记不该记的东西〕
**答**：一张表加一个切面。关键是切点不是挂在某个「审计注解」上，而是挂在**权限注解**上——`@Around("@annotation(permission)")`，`permission` 就是 `RequireAdminPermission`。所以所有方法级带权限注解的非 GET 后台接口自动被记录，新接口漏不掉。显式的 `@AdminAudit` 退化成可选项，只用来起一个稳定的动作名和挑出业务目标。这一条是 M2 执行时相对计划的偏差，计划里写的是「一张表 + 一个切面」，落地时把覆盖面绑到了权限注解上。

**展开**：
- 为什么是权限注解：**覆盖范围和「受保护的后台写接口」这个集合天然一致**。逐个加审计注解的做法要靠人记得，而人一定会忘；挂在权限注解上，漏了注解的接口本来就进不来（Q8.1 的 fail-closed），所以「能调到的写接口」和「被审计的接口」是同一个集合。
- 切面跑在处理器内部、授权拦截器之后，所以主体一定已经在线程局部变量里。
- 记什么：动作名默认是「HTTP 方法 + **路由模板**」，用模板不用实际 URI，这样同一个接口的动作名稳定、可聚合；目标 id 默认取路径变量按名排序拼成「名=值」，超 255 字符截断；显式注解里可以写一段 SpEL 对返回值求值——核销链路就是用它记券号而**故意不记核销码**（核销码是用户手里的秘密，不能因为审计反而泄露，详见第 07 章）。SpEL 只在成功返回时求值，求值抛异常只打日志、退回路径变量。
- 三个分支都记：抛异常记失败（错误码取业务异常自带的码，取不到用异常类名，异常照常往外抛）、返回体标着不成功也记失败、正常返回记成功。证据：`AdminAuditAspectTest` 的 `aSuccessfulWriteIsRecordedWithWhoWhatWhichAndWhere` / `aRejectedWriteIsRecordedAsFailureAndStillThrown` / `aFailedResultBodyIsAFailureToo` / `readsAreNotAudited` / `anExplicitActionAndResultTargetOverrideTheDefaults`。
- 两个刻意的取舍：
  - 审计行走 `REQUIRES_NEW` **独立事务**。放进业务事务看着更严谨，实际后果是失败的业务事务回滚时会把那行「失败审计」一起带走——最该留的记录反而没有。
  - 写审计失败只打 error 日志**不往外抛**：操作已经真实发生了，不能因为审计写不进去就把一次成功的操作报成失败。证据：`AdminAuditAspectTest#anAuditStoreOutageDoesNotBreakTheOperation`。
- IP 不是直接取远端地址：只有直连对端落在配置的可信代理网段里时才认转发头的第一跳，否则用直连地址。不然任何人都能伪造审计里的 IP。
- 查询侧要 `audit:read` 权限点，平台看全部，商户强制按自己的商户 id 过滤，主键倒序，每页上限 100 条；表上的索引就是按（商户 id，主键）和（账号 id，主键）建的，正好服务这一种查法。
- **已知缺口，会主动说**：切点只匹配**方法上**的权限注解，而登录、登出、改密码、查自己这几个接口的注解写在控制器类上，所以**「谁在什么时候改了自己的密码」目前没有审计行**，只有认证指标里的成功/失败计数。反过来领票接口是 POST 且有方法级注解，页面每次重连都写一行，属于噪音。两头都不理想，是同一个切点选择带来的。
- **本项目没做**：审计只增不删，没有归档或分区；查询只支持按商户过滤加主键倒序翻页，没有按动作名、时间范围、操作人筛的接口；也没有把审计投成消息。**会怎么做**：要做到「审计不丢」，正路是业务事务里写一张发件箱表（本项目点赞链路就是这个形态，详见第 10 章），再异步投出去落到审计存储；要做查询和留存，正路是按月分区或定期归档到对象存储加 ES。代价分别是：发件箱把审计重新拉回业务事务，业务事务回滚时那行仍然会丢（除非失败路径单独补一条），且多一张表和一个投递 worker；ES 那条路要多维护一套索引和回填，而本项目已经决定不引 ES 读模型了。后台写操作量很小，我认为当前的「独立事务 + 失败只打日志」是够用的权衡。

**可能的追问**：→ 「切点挂在权限注解上，那类级注解的接口怎么办」（就是上面那个缺口）；→ 「审计要不要保证不丢」；→ Q8.1（权限注解为什么是 fail-closed）；→ 「核销的审计里记了什么」（记券号不记核销码，第 07 章）。

**别踩**：
- 别说「所有后台接口都有审计」。是「所有**方法级**带权限注解的非 GET 接口」，登录改密那几个类级注解的接口确实没有。这个缺口自己说出来，比面试官翻代码翻出来强得多。
- 别把审计说成强一致的「操作与审计同生共死」——本项目是独立事务且失败只打日志，是明确允许丢的。
- 别说「GET 都不记」——带了显式 `@AdminAudit` 的 GET 也会被记，留给「查询本身就敏感」的接口。
- 别说客户端 IP 就是 `X-Forwarded-For`，那等于承认审计里的 IP 可伪造。

## 9. 营销、Outbox、通知

### Q9.1 营销发放怎么保证不重复发、额度不超？  〔常见｜追问链：怎么保证一人一张 → 额度会不会超发 → 并发下先查再发的窗口怎么关 → 运营改规则时正在发的怎么办〕

**答**：两件事分别由两个数据库约束兜底，不靠应用层判断。不重复发靠发放流水表上（活动 id，用户 id，幂等键）的唯一键，幂等键是服务端算的，客户端传什么都被覆盖；额度不超发靠一条带 `granted_count < quota_total` 条件的自增 UPDATE，影响行数不是 1 就失败。应用里那些「先查一次有没有发过」「先看一眼额度满没满」都只是省一次写和给更准的错误码，删掉它们正确性不变。

**展开**：
- **幂等边界**：普通领取和后台发放共用一个固定串（这个活动每人一辈子一次），签到奖励是「任务奖励 + 每日签到 + 业务日期」拼的串（每人每天一次）。迁移 `V10` 先把存量行回填成固定串 `ONCE`，再把列改成非空，最后才把唯一键从（活动，用户）换成（活动，用户，幂等键）——顺序不能反。这样两种语义共用同一张表、同一套额度逻辑，发放门面里不需要为任务奖励分叉。
- **额度**：`incrementGrantCount` 的 WHERE 里同时钉住活动 id、商户 id、券 id、规则版本、状态 ACTIVE、时间窗、以及 `granted_count < quota_total`。超发在 SQL 这一层就不可能发生。更新失败之后那段「逐条分类是版本变了还是时间窗过了还是额度满了」只影响错误码精度。
- **并发窗口**：门面先查一次是快路径（批量重跑时绝大多数条目走这条，连活动行的锁都不碰）；查不到才进内层事务，`SELECT ... FOR UPDATE` 锁住活动行之后**必须再查一次流水**——等锁这段时间里另一个请求完全可能已经发完提交了。完整流程详见笔记 09 第三节 3.3。
- **撞键回查**：万一两个请求同时挤过了复查，后提交的会撞唯一键，异常抛出内层事务把它那次额度自增一起回滚，门面**在事务外**再查一次，查到就返回幂等命中。门面故意不开事务就是为了这个顺序。
- **规则并发**：活动行上有规则版本号，每次定义变更和状态变更都加一；所有写都要求调用方带「我看到的版本」，不一致直接报「规则已变化」。改额度的 UPDATE 里还带「新额度不小于已发放数」，运营不可能把额度改到比已发数还小。
- **证据**：`MarketingGrantConcurrencyIT` 里四条：同一用户 100 个并发领取只产出 1 条流水且计数只加 1；100 个用户抢额度 10，恰好 10 个赢；用户领取与后台发放对同一个人打架仍然只有 1 条流水；带旧规则版本的请求对流水和额度都没有副作用。

**可能的追问**：→ Q9.2（同一个事务里还写了什么）；→ 「拿到锁之后为什么还要再查一遍」；→ 「已经有条件 UPDATE 了，前面那次读额度是不是多余的」；→ 「批量 Job 跑到一半运营改活动会怎样」（Job 上抄了一份规则版本，剩下的条目会整齐停在「规则已变化」）。

**别踩**：
- 不要说「用 Redis 分布式锁保证不重复发」——这条链路里没有 Redis 锁，幂等靠唯一键、串行靠数据库行锁。
- 不要说「先查一次保证了不重复」。第一次查没有任何锁，它只是快路径；真正的保证是唯一键。
- 不要把「发放流水」和「券资产」说成一张表。流水是「谁在哪个活动上拿到过什么」的记录，券是用户手里那张可核销的资产，详见笔记 07。
- 别说额度自增是「乐观锁」就完了——它没有版本号自增语义，是一条带业务条件的原地自增，说清 WHERE 里有什么更值钱。

### Q9.2 通知为什么要先落库再推？直接推不行吗？这就是本地消息表吗？  〔高频｜追问链：发券成功怎么通知用户 → 为什么不在事务里直接推 → 那和本地消息表/Outbox 什么关系 → 消息推失败了怎么办 → 这张表会不会无限涨〕

**答**：因为 Redis 的推送没法参与数据库事务。提交前推，事务回滚就成了假通知；提交后推，进程在这中间挂掉这条通知就永远没有了，而且没有重试、没有退避、没有可观测的积压。所以通知那一行是和发放流水、券资产在**同一个事务**里写进去的，一个后台 worker 再把它搬出去。形态上确实就是本地消息表/Outbox，但语义比典型的本地消息表弱一档：它要的是「至少试着送一次，送不到也不要紧」，真相永远是数据库里那条发放记录。

**展开**：
- **写入**：内层事务里 `insertPending` 落一行 PENDING、attempts=0、next_attempt_time=当前时间，表上（grant_id）是唯一键——一条发放最多一条通知。额度、流水、通知、券四件事同生共死。
- **投递**：worker 是定时任务，启动后 5 秒开始、每轮结束后 1 秒再来（`local-deals.voucher-batch.initial-delay=5s` / `fixed-delay=1s`），单批 50 条（`notification-batch-size`，上限 500），可以用 `notification-worker-enabled` 整体关掉。取批的语句是「状态 PENDING 且 next_attempt_time 已到」，按（next_attempt_time，主键）排序取前缀并 `FOR UPDATE`，顺便 JOIN 出活动 id 和券 id。
- **失败**：往用户专属 Redis 频道 publish 抛异常就走退避：attempts 加一（封顶 10），下次尝试时间 = 现在 + `2^(attempts-1)` 秒、封顶 5 分钟，记下错误原因 `REDIS_PUBLISH_FAILED`，**行仍然是 PENDING**，下一轮还会被取到。成功才条件更新成 PUBLISHED（条件里带「仍是 PENDING」）。
- **和第 10 章那个 Outbox 的区别（很好用的一句话）**：点赞那个要的是「恰好生效一次」，消费者在同一个事务里既改聚合列又打已处理标记；这个要的是「至少送达一次、送不到也不要紧」，消费者是把消息扇出到会话，投递本身尽力而为。
- **和 RocketMQ 的取舍**：项目里秒杀链路用了 RocketMQ（详见笔记 05）。这里的通知不是必须送达的业务事件，用 Redis 发布订阅做一次机会性扇出成本最低，持久性那一半已经被 Outbox 解决掉了。
- **证据**：`VoucherGrantNotificationOutboxServiceTest` 三条——Redis 失败后行仍是 PENDING 且重试元数据被正确封顶；一次被接受的 publish 只把那一行标成 PUBLISHED；数据库标记失败不会被误报成 Redis 失败。`M6cRedisRecoveryIT` 把 Redis 容器停掉：Job 不回滚，Redis 恢复后那条持久的 PENDING 行被补发出去。
- **本项目没做：已发布行的归档清理。** 现在没有任何清理任务碰这张表，PUBLISHED 的行会一直留着（对照：点赞事件表是有清理任务的，每秒一次、每次最多 5 批 × 2000 行、只删处理时间超过 1 天的已处理行）。**会怎么做**：照搬点赞那套有界删除——按（状态，published_at）建索引，定时删「已发布且早于保留期」的行，每批限行数、删不满一批就提前结束。代价是通知记录失去长期可查性（要留证据就得先归档到冷表或对象存储再删），以及多一个会和投递 worker 抢同一张表锁的定时任务。
- **本项目没做：死信与告警。** attempts 封顶 10 只封了退避时长，**没有封重试本身**——到上限之后仍然按 5 分钟一轮无限重试，没有终止状态、没有到达阈值的告警。现在只有一个只读采样器定期数待发条数和最老那条待发的年龄写成仪表。**会怎么做**：加一个 FAILED 终态 + 死信表，超过阈值转死信并告警；代价是需要人工重放入口，且对「Redis 长时间不可用」这种全局故障会一次性把大批行推进死信。

**可能的追问**：→ Q9.3（推出去之后怎么找到用户所在实例）；→ 「多实例下同一条通知会不会推两遍」（取批用 `FOR UPDATE`、标记带条件，真正的风险是「publish 成功但标记前进程挂了」，所以推送必须幂等，前端用 eventId 去重）；→ 「worker 在事务里做 Redis 网络 IO 有什么问题」。

**别踩**：
- 不要把它说成「RocketMQ 事务消息的替代方案」然后展开讲半消息——这条链路根本没有 MQ，讲错了会被当场拆穿。
- 不要说「Outbox 保证通知一定送达用户」。它只保证「消息一定会被交给 Redis 至少一次」，用户没开页面这条消息就是丢的。
- 不要说取批用了 `SKIP LOCKED`——**没有**。多实例部署时其它实例会阻塞在锁等待上，实际是串行推进，这是已知边界，主动说出来比被挖出来好。
- 别把退避说成「指数退避 + 抖动」，代码里没有抖动。

### Q9.3 WebSocket 多实例怎么扇出？用户不在线怎么办？  〔常见｜追问链：怎么知道用户连在哪台机器上 → 要不要维护一张路由表 → 用户不在线消息怎么办 → 用户登出了连接还在怎么办 → 前端怎么保证不漏〕

**答**：不维护路由表。每个应用实例启动时都按模式订阅这一族用户频道（`ws:voucher-grant:<userId>`），发券的实例只管往用户那个频道 publish，所有实例都收到，只有真正持有那条连接的实例发得出去，其余实例在本地会话表里查不到人就直接返回「没发出去」。用户不在线这条消息就是丢的——这不要紧，因为事实在数据库里那条发放记录，前端的兜底是断线时降级轮询「我的发放记录」。

**展开**：
- **扇出**：`WebSocketConfig` 里注册的监听器用 `PatternTopic("ws:voucher-grant:[0-9]*")`，收到后从频道名解析出 userId，交给本实例的 `SeckillWebSocketHandler#sendToUser`。会话注册表就是一个进程内的 `Map<userId, session>`。代价是每条消息会被每个实例都收到一遍，实例数多了是纯浪费；好处是完全没有「用户在哪台机器」这份需要维护正确的状态。
- **负载**：payload 里 id 全部转成字符串，因为它们超出 JavaScript 安全整数范围；带一个 eventId 给前端去重。
- **连接与鉴权**：握手时按查询参数里的 token 验出会话，验的是和 HTTP 请求同一份登录态；**每次发送之前还要再验一次 token 仍然有效**（不刷新有效期），用户登出或 token 过期，已建立的连接会在下一次推送时被关掉，而不是一直活到超时。同一个用户再连一次会顶掉旧连接。每条会话套了 `ConcurrentWebSocketSessionDecorator`，发送超时 10 秒、缓冲上限 256 KB，防止一个卡住的客户端拖住推送线程。
- **前端兜底**：WebSocket 断开或建不起来就降级轮询，每 2 秒一次、最多 10 次、总时长 30 秒，连上就停。收到推送先用 eventId 去重，再**重新拉一次列表**——页面上的券一律来自那次重新拉取，推送里被直接用掉的只有提示框那句文案。所以推送在这条链路里基本只是一个「你该刷新了」的信号。详见笔记 09 第三节 3.5。
- **本项目没做：离线补偿。** 没有未读表、没有已读状态、没有登录后补推，也没有 APNs/FCM 这类离线通道；前端的去重集合在内存里，刷新页面之后同一条事件会再提示一次。**会怎么做**：把「通知」本身做成一份用户可查的持久列表（一张站内信表 + 未读计数），推送只是它的实时通道，用户上线时先拉未读；真要触达离线用户再接第三方推送通道。代价是多一份需要维护已读状态的数据、多一次登录时的读放大，以及第三方通道自己的送达不确定性——而本项目的场景里「进券包看一眼」已经够用，所以是明确选择不做，不是遗漏。
- **本项目没做：后台侧的发放通知。** 运营看批量 Job 进度只能刷新列表页，实时频道目前只服务秒杀订单事件。

**可能的追问**：→ Q9.2（消息是谁 publish 的、失败了怎么办）；→ 「为什么不用 STOMP / 消息代理」；→ 「为什么不用长轮询或 SSE」；→ 「实例很多的时候每条消息被所有实例收到会不会有问题」。

**别踩**：
- 不要说「用 Redis 存了用户和实例的映射然后定向投递」——本项目就是广播式扇出，说成定向是编的。
- 不要说「WebSocket 保证消息可靠送达」。「已发布」只表示消息交给了 Redis。
- 不要说离线消息会被补发——没做，直接说没做，然后讲会怎么做。
- 讲鉴权时别漏掉「每次发送前复验 token」这一条，它是这个实现里最容易被追问也最容易加分的点。

### Q9.4 点赞为什么要先写一行事实再异步合并计数？直接 `update` 计数不行吗？  〔常见｜追问链：点赞怎么存 → 为什么不直接加计数 → 异步会不会重复加 → worker 崩在中间怎么办 → 用户看到的数不准怎么办〕

**答**：直接 `UPDATE 笔记 SET liked = liked + 1` 会把同一条热点笔记的所有点赞串行在一把行锁上，而且这把锁是在用户请求的事务里持有的。改成先写事实之后，在线请求只碰两张各自独立的行——一条「谁赞了哪条笔记」的关系行和一条「+1/-1」的事件行，同事务提交；计数列由一个后台 worker 把一批事件按笔记合并后再改，单批 500 条如果全打在同一条热点笔记上，合并后只发出 1 条更新。代价是展示的总数有秒级延迟。

**展开**：
- **写入侧**：关系表用（笔记 id，用户 id）联合主键，这就是天然幂等键，重复点赞撞主键、捕获后返回「未改变」且**不写事件行**；取消点赞删到 0 行同理。只有状态真的变了才插事件行，插入影响行数不等于 1 就抛异常回滚——「一次状态改变」与「一条事件」严格配对。
- **投影 worker**：启动后延迟 5 秒，每轮结束 200 毫秒再跑，单批 500（`local-deals.blog-like.*`）。先抢一把不等待的 Redis 锁，抢不到就这轮不干活，**抢锁时 Redis 抛异常也继续往下走**——这把锁只减少多实例空转，真正的互斥是数据库的 `FOR UPDATE`。
- **恰好生效一次**：计数更新与「已处理」标记在同一个事务里提交。提交前崩整批回滚下次重放，提交后崩这批已带标记、标记语句条件里又带「处理时间为空」且要求标记行数等于本批行数，不可能再加一遍。注意这里的「恰好一次」说的是**增量落到计数列恰好一次**，不是事件行只被读一次。
- **细节里两个容易被追问的点**：计数列是无符号的，所以更新写成 `CAST(liked AS SIGNED) + ? WHERE ... AND CAST(liked AS SIGNED) + ? >= 0`，直接减会在下溢时报错而不是被守卫挡住；而且是一条一条发、没用 JDBC 批量更新，因为批量更新允许驱动返回「成功但不知道行数」，那条安全断言就形同虚设。
- **用户感知**：用户对**自己**的点赞状态没有延迟，「我赞过吗」是直接查关系表的；有延迟的是展示总数和热榜排序（热榜还要再叠一层最多 30 秒的刷新间隔）。这是有意识的取舍：点赞数不是钱。
- **证据**：`BlogLikeReliabilityIT` 里几条——重复的期望态命令只产出一条增量；并发点赞只创建一条关系行和一条事件行；事件行插入失败会回滚关系行的改动；已处理标记失败会回滚聚合更新并保持可重放；两个并发批处理消费者对同一条事件恰好应用一次。
- **本项目没做：计数对账。** 计数列与关系表行数是否严格相等，目前只由「事件与状态改变严格配对」这一条断言保证，**没有周期性对账器去重新数一遍**，出了偏差只能人工重算。**会怎么做**：低峰期按笔记分段 `COUNT(*)` 关系表与计数列比对、只修差异行并留审计记录。代价是对账查询本身在大表上很贵，要分段限速；而且和投影 worker 有写冲突，得在「无未处理事件」的窗口里做。
- **本项目没做：这条链路的压测。** 压测报告里没有点赞与热榜的数据，所以「省掉多少热点行锁」只能讲机制、不能报数字。

**可能的追问**：→ Q9.2（和通知 Outbox 什么区别）；→ 「一条坏事件会怎样」（守卫条件让更新影响 0 行时整批抛异常回滚并**无限重试同一批**，没有死信、没有跳过、没有重试上限——这是有意选的「宁可卡住也不丢改动」，但它确实会卡住）；→ 「吞吐上限在哪」（定时任务 + 一把全局锁，同一时刻整个集群只有一批在跑，没有按笔记 id 分片并行）；→ 热榜怎么读、怎么降级（详见笔记 10 第三节 3.4 / 3.5）。

**别踩**：
- 不要说「点赞用 Redis Set 存」。早期的 Redis 点赞集合和灰度双路径已经在后续迁移里删掉了，现在关系表就是真相源，计数列就是它的异步投影，没有第二种含义。
- 不要说「异步所以可能丢」。丢不了——事实和事件同事务提交，worker 失败就重放；会「不准」的只有延迟期间的展示值。
- 不要把这里的「恰好一次」说成消息队列那种端到端 exactly-once。它成立的前提有三条：写入侧严格配对、取批 `FOR UPDATE`、标记语句带条件且校验行数，缺一不可。
- 不要为了显得高级说「用 MQ 做的 Outbox」。这里就是一张数据库表，理由是「事实与事件必须同一个事务提交」，而消费者本来就在同一个库里改一列。

## 10. 缓存与搜索

> 涉及的角色名：通用缓存组件（`CacheClient`）、单飞加载器、读隔离舱 / 搜索隔离舱。

### Q10.1 缓存穿透 / 击穿 / 雪崩你分别用了什么？为什么不是另一种？  〔高频｜追问链：三兄弟分别怎么解 → 为什么不用布隆过滤器 → 空值也要 TTL 吗 → 击穿为什么不用分布式锁 → 雪崩你加随机 TTL 了吗〕

**答**：穿透用的是**空值占位 + TTL**，不是布隆过滤器；击穿用的是**进程内单飞加载**，不是分布式互斥锁，也没有逻辑过期；雪崩这一块我**没有做 TTL 随机化**，真正兜住雪崩的是**读隔离舱**——它直接给数据库回源立了一个并发硬上限，不管上游是因为雪崩、热点还是坏值修复涌过来的。这三条都在同一个通用缓存组件里，店铺详情和店铺类型列表复用同一套。详见笔记 03 第三节。

**展开**：

- **穿透 = 空值占位**。查不到就写一个约定的占位串 `_NULL_PLACEHOLDER_`，TTL 30 秒；下次命中占位串直接返回 null，**一次数据库都不查**。空值 TTL 由配置单独控制，而且启动时校验它**不得长于**正常值 TTL（`BoundedCacheProperties` 的 `@PostConstruct`），配错直接起不来——否则新建的店铺会有一段明显的不可见期。证据：`CacheClientTest.returnsExactEmptyPlaceholderWithoutDatabaseFallback`、`missUsesPositiveAndNegativeTtls`，以及 `ShopServiceIT` 里「不存在的 id 回源一次后写入短 TTL 占位」。
- **布隆过滤器我确实做过，后来删了**。V1 里有一个 Guava 的进程内 `ShopBloomFilter`，启动时把全量店铺 id 灌进去，查询前先问一句。删掉的原因很具体：它是**进程内**的，多实例部署时 A 实例新建的店铺不在 B 实例的过滤器里，会产生**假否定**——把真实存在的店铺判成不存在，这比穿透严重得多。真要用得换成 Redis 里的共享位图（或 RedisBloom），代价是每次查询多一次网络往返、而且**不支持删除**（要么用计数布隆，要么定期重建）。对这个场景来说，空值占位已经把「同一个乱猜 id 的重复请求」挡住了，布隆过滤器多挡的只是「大量**互不相同**的乱猜 id」，收益撑不起那套复杂度。
- **击穿 = 单飞**。以「缓存资源 + 具体键」为单位，本进程内只让 leader 真正加载，其余 follower 等结果，最多等 750 毫秒。为什么不是分布式锁：锁要处理加锁、续期、超时、持锁进程崩溃一整套，而击穿的痛点「同一瞬间几百个线程压到库上」绝大部分本来就发生在同一个进程内。代价我认：**N 个实例就是 N 次回源**，而不是 1 次；这个量级完全扛得住。证据：`SingleFlightLoaderTest.thirtyTwoOverlappingRequestsExecuteOneCallback`（32 个重叠请求只执行一次回调）、`twentyFollowersHonorConfigured750MillisWithoutStartingAnotherLeader`。
- **雪崩这块我要说实话**：代码里**没有 TTL 随机化**，店铺详情固定 30 秒、类型列表固定 100 分钟。缓存层本身是 Redis Cluster 3 主 3 从，整体不可用这一层靠的是「读 Redis 抛异常就当没有缓存、直接回源并打上不回写的标记」，再由读隔离舱（许可 4、最多等 20 毫秒、拿不到直接 429）保证回源量有上界。**会怎么做**：给正值 TTL 加一个百分之十几的抖动，或者按 key 的 hash 打散——很便宜，只是这个项目里同一类 key 的写入时间本来就是被请求随机打散的，不像「启动时批量预热」那种会整齐到期的场景，所以一直没加。

- **还有一条和「空值」正好撞在一起的坑，值得单独讲**：类型列表是整个列表存一个 key，所以「空数组」是合法结果、要直接返回。而 Hutool 5.8 解析 JSON 数组时**默认丢掉 null 元素**——一个被写坏成 `[null]` 的值会被解析成空数组，然后被当成「合法的空命中」直接返回，**这个 key 就永远修不回来了**（它不是未命中，不会触发回源）。修法是解析时显式 `setIgnoreNullValue(false)` 把 null 保留下来，再让校验函数把它判成坏值触发回源覆盖写。校验的内容是：每个元素非 null、id 非 null 且为正、且互不重复。证据：`ShopTypeServiceImplTest.nullNonPositiveAndDuplicateIdsAreBadAndRepaired`，用例里的输入就是 `"[null]"`。这条是 M1 执行时发现的偏差之一（ADR 0002）。单对象那边对应的是另一道校验：请求的 id 必须等于反序列化出来的对象里的 id，防的是 key 被写脏或前缀撞了把 A 的数据返回给 B。
- **多级缓存（本地 Caffeine 一级 + Redis 二级）本项目没做，而且是主动砍的**。计划里原本是 M7，2026-09-21 决定不做，写在进度表里的理由是：「Caffeine+Redis 两级缓存是八股密度最高、区分度最低的一块」；压测报告的「没做」清单里也列着「多级缓存（M7 砍）」。**会怎么做**：本地放一份短 TTL 的副本，失效经 Canal → MQ 广播到各实例。**代价要说清**：本地副本没有任何办法做到和 Redis 同时失效，广播有延迟、还可能漏，等于引入了一个「各实例各自看到不同旧值」的新一致性层级；而且本项目的读压力从来不是瓶颈——瓶颈线一路从 Broker 移到库存那一行（详见笔记 00 第五节），多加一级缓存改善不了它。

**可能的追问**：→ Q10.2（逻辑过期）；→ Q10.3（拿不到重建权的线程）；→ 「Redis 整个挂了这个接口还能用吗」（能，走回源 + 隔离舱限流，见笔记 03 第三节第一小节的 Redis 异常分支）。

**别踩**：
- 别把「布隆过滤器」说成现在还在用——代码里没有，只有一条 V1 留下的测试注释。被翻代码会当场穿帮。
- 别说「我加了随机 TTL 防雪崩」。没加就是没加。
- 别说「空值缓存永久」——空值必须有 TTL，而且不能比正值长，这一条是写在启动校验里的。
- 别把三兄弟说成三套独立机制：这里是一个组件里的三条分支，穿透和击穿共用同一条回源路径。
- 别顺嘴说「我还做了本地 + Redis 的多级缓存」。没做，而且是**主动砍掉**的，理由要能说出口。

### Q10.2 逻辑过期返回旧数据用户能接受吗？异步重建线程挂了会不会永远是旧数据？  〔常见｜追问链：逻辑过期怎么实现 → 返回旧值能接受吗 → 重建线程挂了怎么办 → 值永不过期内存怎么办 → 那你为什么不用〕

**答**：先把事实说清楚——**这个项目现在没有逻辑过期**。V1 的缓存组件里写过一版（值不设 TTL、把过期时间塞在值里、发现过期就丢给线程池异步重建、期间返回旧值），但它**没有任何调用方**，真正跑在读路径上的一直只有「空值占位 + 单飞 + 隔离舱」。V2 第一步清理就把这些没有调用方的教程残留删掉了，连同一个自研的 SETNX 锁。所以这道题我能回答的是「它的坑在哪、以及我为什么即使重做也不会加回来」。

**展开**：

- **返回旧数据能不能接受，取决于业务**。秒杀库存这种绝对不行；店铺资料这种「名称、地址、营业时间」其实可以接受几十秒的陈旧——但正因为可以接受，直接用一个 30 秒 TTL 就够了，没必要为了省那一次回源引入逻辑过期。逻辑过期真正的适用场景是「回源特别贵（几百毫秒到秒级）且绝对不能有一次慢请求」的超热点，店铺详情是主键查一行，不是这种场景。
- **重建线程挂了会不会永远是旧数据——会**。这是逻辑过期最容易被问死的地方：值本身**没有 TTL**，如果异步重建任务抛异常、或者重建线程池的队列满了被拒、或者进程在「已把标记置为重建中、还没重建完」的瞬间被 kill，那个「重建中」的标记如果不带过期时间，这个 key 就永远卡在旧值上，没有任何机制能自愈。所以工程上必须配三件套：重建标记本身带 TTL（相当于锁的租约）、重建任务 catch 住所有异常并在 finally 里释放标记、以及一个「逻辑过期时间超出阈值 N 倍」的兜底告警或强制同步重建。这三件事加起来，复杂度已经不比分布式锁低了。
- **另一个代价是冷数据永不淘汰**。值不设 TTL 就意味着只能靠 Redis 的淘汰策略来收内存，而一旦内存吃紧触发 LRU 把它淘汰掉，逻辑过期承诺的「永远有旧值可返回」就不成立了——这时候退化成普通的缓存未命中，还不如一开始就用 TTL。
- **所以我的结论是**：逻辑过期是用「重建期间返回旧值」换「并发回源」，而并发回源这件事**单飞已经解决了**（32 个重叠请求只回源一次，有测试），我没必要为一个已解决的问题再付一次「值永不过期 + 重建线程可靠性」的代价。

**可能的追问**：→ Q10.3；→ 「那你怎么保证首次加载不会让用户等很久」（隔离舱里的回源有耗时打点，follower 最多等 750 毫秒，超时是 503 而不是无限等）。

**别踩**：
- 别为了显得「做得多」而把逻辑过期说成自己在用。面试官一 grep 代码就没了，而且笔记 03 第五节和「已知边界」都白纸黑字写了没有。
- 别只说「异步重建挂了有 TTL 兜底」——逻辑过期的值**本来就没有 TTL**，这正是它区别于普通缓存的地方；有 TTL 兜底的是「重建标记」，两个东西不要混。
- 别把逻辑过期和「缓存预热」混为一谈。

### Q10.3 拿不到重建锁的线程做什么？会不会把线程全阻塞住？  〔常见｜追问链：怎么互斥 → 拿不到的线程干什么 → 等多久 → 等的时候占着 Tomcat 线程吗 → 超时了会不会又去打库 → 多实例呢〕

**答**：这里没有「锁」，是单飞：第一个到的线程是 leader，在**自己的请求线程上**执行加载；同一时刻同一个 key 的其他线程是 follower，直接在 leader 的 `FutureTask` 上等结果，**最多等 750 毫秒**，等不到就抛 503（数据暂不可用）。follower 既不排队重试、也不会自己去回源。会不会把线程阻塞住——**会占住，但是有确定上界**：任何一个 follower 最坏就是 750 毫秒后带着 503 退出，不会无限期堆积。

**展开**：

- **等待上界是配置死的**：`read.shared-load-wait` 默认 750 毫秒，而且配置类在启动时校验它必须落在 100 毫秒到 2 秒之间，不允许配成一个夸张的值。leader 做完无论成败都把这个 key 从在途表里摘掉，失败的异常会原样传播给所有 follower（不会出现「leader 挂了 follower 干等」）。
- **关键的一条：follower 超时之后不会转而自己去打库**。这是我专门写测试钉住的行为——`CacheClientTest.timedOutFollowerDoesNotAcquireDbPermitOrStartASecondFallback`、`SingleFlightLoaderTest.followerTimeoutDoesNotCancelLeaderRemoveEntryOrStartSecondLoad`：超时的 follower 不去抢数据库读的信号量许可、也不会启动第二次回源，leader 那次加载也不会被取消。如果不钉这一条，「超时」反而会变成放大回源的开关。
- **线程被占住这件事的真实上界**：容器线程池用的是 Spring Boot 默认配置（没有开虚拟线程，M8 把虚拟线程对比实验砍掉了）。极端情况是大量请求打同一个热 key，它们会各自占一个容器线程等最多 750 毫秒。这确实是一个可以被攻击的点，但它换来的是「数据库前面只有 4 个并发」——**宁可让请求线程等一小会儿或快速失败，也不能让几百个连接压到连接池上，把下单这类写请求一起拖死**。
- **隔离舱是第二层，而且刻意不排队**：leader 真正查库前要拿数据库读的信号量许可，许可总数 4、最多等 20 毫秒，拿不到直接 429（读请求过多）。许可这么小、等待这么短是故意的——一旦允许排队，队列本身就成了新的延迟来源，压力反而被藏起来看不见。搜索走的是**另一个独立的舱**（同样 4 个许可、20 毫秒），ES 被打爆不会连累详情页回源。
- **多实例的代价我认**：单飞是进程内的，N 个实例同一时刻就是 N 次回源，不是 1 次。要做到全局一次就得上分布式锁（或者让某一个实例负责预热），那套东西的复杂度我在 Q10.1 里说过，这个规模不值得。

**可能的追问**：→ Q10.1（为什么不用分布式锁）；→ 「429 和 503 怎么分的」（拿不到许可是 429，舱内未知运行时异常统一换成 503，已经带明确状态码的异常原样向上抛）。

**别踩**：
- 别说「拿不到锁就自旋重试 / sleep 50 毫秒再查一次缓存」——那是教程版的写法，本项目不是这么做的，而且自旋重试恰恰是把线程占住更久的做法。
- 别说「follower 不占线程」。它是同步 `Future.get`，实打实占着一个请求线程，只是有上界。说成不占反而不可信。
- 别把「隔离舱 4 个许可」说成「最多 4 个并发请求」——那是**同时回源查库**的并发上限，缓存命中的请求根本不进这个舱。

### Q10.4 缓存和数据库的一致性怎么保证？为什么没上 binlog 订阅？  〔高频｜追问链：先删缓存还是先写库 → 延迟双删做了吗 → 删失败怎么办 → 为什么不订阅 binlog → binlog 刷缓存有什么坑〕

**答**：写侧是**先写库、事务提交后再删缓存**，而且删除动作注册成 afterCommit 回调，不在事务里做；删除失败**不重试、不抛异常**，靠 30 秒 TTL 兜底。没做延迟双删。这条链路的一致性目标明确就是「最终一致 + 窗口有上界」。至于 binlog 订阅——**这个项目里 Canal → MQ 这条链路是有的，但只接到了 Elasticsearch 索引，没有接到缓存失效上**，这是有意的取舍，不是不知道。

**展开**：

- **为什么是「提交后删」而不是「先删缓存再写库」**：先删再写的窗口里，一个并发读会把**旧值**重新加载回缓存，而这份旧值带的是完整的 30 秒 TTL——等于用一次删除换来了 30 秒的脏数据。放在提交后删，最坏只是「提交到删除之间」那一小段读到旧值，这段远短于 TTL。至于延迟双删，它是在「先删再写」的前提下打的补丁，我既然选了提交后删，就没必要再引入一个「延迟多久」这种拍脑袋的参数。
- **afterCommit 这一步还加了一个断言**：注册前先确认当前确实处于事务同步中，否则直接抛异常——防止哪天有人把写方法的 `@Transactional` 漏掉，导致缓存动作在无事务的情况下静默执行。
- **失败就是失败，不补救**：事务已经提交了，这时候抛异常没有任何补救作用，只会让一次成功的写对调用方显示成失败。所以三个动作（删详情缓存、从旧类型的 GEO 集合移除、加进当前类型的 GEO 集合）各自 try/catch 不外抛。**代价要说清**：详情缓存有 30 秒 TTL 兜底，**GEO 集合没有这个兜底**——写 Redis 失败就会在集合里留下错误的坐标或幽灵成员，没有定时任务纠正，只能等下一次对这家店的写或者重新灌库。而且这两个 GEO 动作**只在失败时打一条错误日志、没有指标**，监控上看不出来。这是我这条链路上最真实的一个缺口。
- **证据**：`BoundedCacheMySqlRedisIT.committedAdminUpdateEvictsTheExactDetailKey`（提交后精确删掉那一个 key）和 `rolledBackAdminUpdateLeavesThePreexistingCacheUntouched`（回滚时一个字节都不动缓存）——后面这条正是「不会出现缓存已删、事务回滚」的那个断言。
- **为什么 binlog 订阅接了 ES 却没接缓存**：ES 索引没有 TTL 这种自愈手段，不订阅 binlog 就只能靠每次启动的全量重灌，运行期会一直停在旧数据上，所以它**必须**有一条变更流；而详情缓存 30 秒就自己过期了，用 binlog 换来的只是把「最多 30 秒陈旧」缩短到「最多几百毫秒陈旧」，对店铺资料这个场景收益很小。
- **如果要接，我会怎么做、坑在哪**：Canal 消息里已经带了表名、操作类型和变更后的行，缓存这边订阅同一个主题，按主键拼出 key 执行 DEL（**删除而不是回写**——回写会因为消息乱序把旧值盖到新值上，而删除是幂等的、天然抗乱序和重复投递）。坑有三个：一是延迟，binlog → Canal → MQ → 消费这几跳之间仍然是旧值，所以它只是缩短窗口、不是消除窗口，任何「binlog 订阅=强一致」的说法都是错的；二是消费挂了就等于失效没了，必须保留 TTL 作为最后兜底，不能因为上了 binlog 就把 TTL 去掉；三是多了一个必须自己运维的组件——这个项目里 Canal 没起来的时候，搜索接口**不报错，只返回旧结果，而且没有对这个延迟的监控告警**，同样的失败模式会原样复制到缓存上。
- 顺带说一句：ES 那条链路之所以敢「失败就抛异常让 MQ 重投」，是因为写入是**按文档 id 覆盖写**、删除是按 id 删，重复消费天然幂等，不需要额外的消费去重表。详见笔记 03 第三节第五小节。

**可能的追问**：→ 「那 GEO 集合漂了你怎么发现」（发现不了，只有日志，已知边界）；→ 「ES 和库不一致会不会返回错数据」（不会返回错字段，因为只从 ES 取 id 和顺序，字段一律回数据库查——见 Q10.6）。

**别踩**：
- 别说「保证强一致」。这里是最终一致，而且我能说清窗口的上界是 30 秒。
- 别把延迟双删说成万能：它解决的是「先删再写」自己制造的问题，而且「延迟多久」根本没法算准。
- 别说「binlog 订阅之后就不需要 TTL 了」——消费一挂就没有任何兜底。
- 别说本项目「没有 binlog 链路」。有，而且是主力（ES 同步靠它），只是没用在缓存上。

### Q10.5 附近的店铺怎么实现的？GEO 底层是什么结构？分页怎么做？  〔常见｜追问链：GEO 命令用了哪些 → 底层是什么 → 精度怎么来的 → 分页怎么分 → 深翻页会怎样 → Redis 重启集合没了怎么办〕

**答**：用 Redis 的 GEO，**每个店铺类型一个集合**，成员是店铺 id、坐标是店铺经纬度；查询时以用户坐标为圆心搜 5000 米、带距离。底层就是 zset：GEO 把经纬度用 GeoHash 编码成一个 52 位整数当作 score，所以 `GEOADD` 本质是 `ZADD`。分页这块要老实说——Redis 的半径搜索**只能限制返回条数、不能跳过前 N 条**，所以我传的 limit 是「当前页的结束下标」（页码 × 5），拿回来之后在应用里跳过前面的部分。详见笔记 03 第三节第三小节。

**展开**：

- **为什么按类型分集合而不是全站一个**：查询永远带着类型，分开之后半径搜索的候选集小得多；代价是店铺改类型时要「从旧集合移除 + 加进新集合」两次往返（而且我不判断类型有没有真变，只要是修改就无条件先移再加——判错一次就会在旧集合里留下幽灵成员）。
- **底层结构**：有序集合 + GeoHash。把二维经纬度用 Z 阶曲线交错编码成一维整数，相近的点编码前缀相同，于是范围查询就变成 zset 上的若干段 score 区间扫描。这也解释了它的两个特性：一是精度有限（编码到 52 位，米级误差），二是圆形搜索实际上是「先按 GeoHash 格子取候选，再逐个算真实距离过滤」，所以候选集大的时候是有真实计算开销的——这正是我按类型分集合的直接理由。
- **Redis 只出 id 和距离，字段回数据库取**：拿到 id 列表后回库查整行，SQL 末尾拼一段按给定 id 顺序排序的子句——`IN` 查询本身不保证顺序，不强制排序的话距离排序就白做了；最后把距离按 id 回填到实体上一个**不落库的距离字段**返回。
- **深翻页的放大我承认**：页大小固定 5，第 10 页就要从 Redis 取回 50 条再扔掉 45 条，页码越深拿回来的越多。**会怎么做**：改成游标式——用上一页最后一条的距离作为下界继续往外搜（`GEOSEARCH` 本身不支持距离下界，所以实际做法是在应用侧维护「上次的距离 + 已返回的 id 集合」，或者干脆用 `ZRANGEBYSCORE` 在 GeoHash score 上自己分页）。代价是不能跳页、只能一页页往下翻，产品上得接受「上一页/下一页」而不是页码。这个项目里**没有做**，就是取满再跳过。
- **Redis 重启集合是空的，这条我做了降级**：搜索结果为空或为 null 就**降级回数据库**按类型分页返回，只是丢掉距离和距离排序，接口不报错。但恢复距离排序需要人工重新灌一次集合，**没有自动重建**。另外半径 5000 米是**写死在代码里**的，搜索接口那边可以传但默认也是 5000。
- 还有两条路根本不走 Redis：排序方式是「评论数」或「评分」时直接走数据库分页（和位置无关）；前端没传坐标时也走数据库。

**可能的追问**：→ Q10.6（ES 那边的深分页）；→ Q10.4（改店铺之后 GEO 怎么同步、失败了怎么办）。

**别踩**：
- 别说「GEO 是一种独立的数据结构」——它就是 zset，能被 `ZSCORE`、`ZREM` 直接操作，这一点面试官经常拿来验你是不是真看过。
- 别说「GEO 支持 offset 分页」。`GEOSEARCH` 的 `COUNT` 只是限制条数，没有 offset，这正是本项目「取满再跳过」的原因。
- 别把降级说成「无损」——降级之后距离字段和距离排序都没了。
- 别声称 GEO 是精确距离：格子编码有误差，米级的事不要打包票。

### Q10.6 ES 深分页为什么慢？`search_after` 的排序字段怎么选、有相同值怎么办？  〔高频｜追问链：from/size 为什么慢 → max_result_window 是多少 → scroll / search_after / PIT 区别 → 排序字段怎么选 → 有重复值怎么办 → 你项目里用了吗〕

**答**：先说结论——**这个项目的搜索用的是 from / size，没有实现 `search_after`**，页大小固定 5。深分页慢的根因是：每个分片都得把前 `from + size` 条取出来排序交给协调节点，协调节点再对 `分片数 × (from + size)` 条做一次归并，**每一页的代价随页码线性增长，而且内存开销也随之增长**，所以 ES 默认用 `index.max_result_window`（默认 10000）把 `from + size` 卡死。`search_after` 的思路是把「跳过 N 条」换成「从某个排序值之后开始」，让每页代价固定。

**展开**：

- **from / size 为什么贵**：它不是「跳过」，是「取出来再扔掉」。10 个分片翻到第 1000 页（from=10000, size=10），协调节点要收上来 10×10010 条排序值做归并，只为了吐出 10 条。这也是 `max_result_window` 存在的理由——它保护的是协调节点的内存，不是限制业务。
- **三个方案的取舍**：`scroll` 会固化一个搜索上下文（快照），适合离线全量导出，**不适合在线翻页**，因为上下文常驻内存且看不到新数据；`search_after` 是无状态游标，适合用户一页页往下翻，但**不能跳页**；生产上正规做法是 `search_after` + **PIT（point in time）**，PIT 提供一个轻量快照保证翻页期间的结果集稳定，否则翻页中途有文档写入会出现漏条或重复。
- **排序字段怎么选**：必须是**有 doc_values、全局可比、且组合起来唯一**的一组字段。业务排序字段（这个项目里可用的是评分、销量、人均价格、距离）几乎一定有重复值，所以**必须追加一个 tiebreaker**。
- **有相同值怎么办——这就是 tiebreaker 的整个意义**：如果排序键不唯一，游标定位就是模糊的，同一个排序值的文档可能被跳过或重复返回。做法是在排序数组末尾追加一个唯一字段，游标就是「上一页最后一条的完整排序值数组」。具体到这个项目：搜索文档里目前只有 `@Id` 映射成文档 id，**`_id` 默认没有 doc_values，不建议拿来排序**；真要上 `search_after`，要么给文档加一个独立的数值 id 字段（长整型、有 doc_values）当 tiebreaker，要么开 PIT 之后用 `_shard_doc` —— 后者是 ES 7.12 之后专门为这个场景提供的、最便宜的全局唯一 tiebreaker。距离排序也一样：`geo_distance` 排序值是浮点米数，同一栋楼里的两家店完全可能相等，照样需要 tiebreaker。
- **这个项目为什么没做**：页大小 5、能翻到的页数很浅，深分页在当前场景不是真问题；而且真正花力气的地方在写路径。被问到我直接说没做，但能说清它解决什么、以及为什么不能拿 `_id` 当 tiebreaker——这比硬说自己做了有用。
- **顺带说一个真做了的取舍**：命中之后我**只取文档 id**，再用这批 id 回数据库查整行并拼保序子句。理由是索引里只放过滤和排序字段（图片、营业时间这些展示字段没放），而且索引是 binlog 异步同步的、可能比库旧——**让索引负责排序和筛选，让数据库负责字段的真实值**。这条设计和 `search_after` 是兼容的：换成游标翻页时，回表那一步一个字都不用改。
- **搜索这条路上真正做了的保护**：整个查询体被放进**搜索隔离舱**（许可 4、最多等 20 毫秒，拿不到 429），它和数据库读那个舱是两个独立的舱；ES 客户端自己还有超时——连接 500 毫秒、socket 1 秒，所以一个慢查询最多占住一个许可 1 秒。
- **这条路上修过一个真实缺陷**（ADR 0002 / 计划文档「M1 执行时发现的计划偏差」）：「类型 + 距离」一起搜时**类型过滤被丢掉了**，原因是 builder 只保留一个 filter，我分两次 `withFilter` 把前一次覆盖掉了；修法是把所有过滤条件合进同一个 bool 再设置进去。集成测试里专门放了一家「同样是火锅、同样在 5 公里内、但 typeId 不同」的店来钉住这个行为。

**可能的追问**：→ Q10.4（索引和库的一致性）；→ 「为什么不直接返回 ES 里的文档」（上面第 6 条）；→ 「ES 挂了搜索接口什么表现」（舱内未知运行时异常统一换成 503「搜索暂不可用」，带明确状态码的异常原样抛）。

**别踩**：
- 别说自己实现了 `search_after`。仓库里那个 `ShopSearchAfterIT` 是「修复**之后**的测试」，名字里的 after 不是 ES 的 `search_after`，这个很容易被误读，最好主动澄清。
- 别只说「加个唯一字段就行」而说不出为什么 `_id` 不合适（没有 doc_values）。
- 别把 `scroll` 说成在线翻页方案。
- 别说「`search_after` 能解决跳页」——它恰恰不能跳页，这是它的固有代价。
- 别把 `max_result_window` 说成「ES 最多只能查一万条」——它限的是单次 `from + size`，不是数据量上限。
