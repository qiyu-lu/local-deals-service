## 1. 秒杀准入

> 本节的流程细节不重抄，详见笔记 04 第三节；数字凡标「压测报告」的抄自 `docs/benchmark-report.md`，

### Q1.1 一次秒杀请求从进来到返回走了哪几层？每层挡掉什么？  〔高频｜追问链：讲讲你的秒杀流程 → 每层挡掉什么 → 为什么这么排 → 哪一层保证不超卖〕

**答**：五层漏斗，越靠前越便宜。边缘限流（nginx）→ 进程内售罄标记 → 秒杀令牌验签 → 进程内令牌桶 → 一次 Redis Lua。前四层都是 0 次网络 IO，只有最后一层碰 Redis，而且是一次往返。成功者才发一条普通消息，返回订单号，数据库这时还没有订单。整条链路的设计目标是「让注定失败的那 99% 尽可能便宜地失败」。

**展开**：

- L0 边缘限流：nginx `limit_req`，按 `$http_authorization` 每 2 r/s（burst 2）、按客户端地址每 50 r/s（burst 100），只挂在下单这一个 location 上，领令牌和查单不受限。挡脚本刷单和单用户狂点，超出 429，一个字节不进应用。
- L1 售罄标记：拦截器 `order(-1)`，排在登录拦截器之前，只管这条路径的 POST。**只有 K 个桶全被标记时**才本地回「库存不足」（HTTP 200 + 业务失败码），不查 token、不读 Redis。
- 令牌层：登录拦截器给出用户 id 后，控制器验 `X-Seckill-Token` 的 HMAC，不过就 403。纯本地计算。
- L2 本地令牌桶：按（券，桶）一个桶，速率跟着「上一次脚本报回来的本桶剩余库存 × 系数」走，取不到令牌 429。
- L3 准入脚本：七个 key 同一个 hash tag，一次往返里做完限频、活动窗口、判重、库存、订单号占用检查，全过了才扣库存 + 写预占 + 写「处理中」状态 + 入到期索引，返回 `{结果码, 剩余库存}`。
- 证据：压测报告第 2 节 M3 行——准入拐点 5k → **20 000 req/s**（p99 83 ms），天花板 13.2k → ≥26.2k，10k 档 p99 128 → 33 ms、应用 CPU 3.04 → 0.60 核，半消息从「等于请求数」变成 0。每档 `accepted = stock`，无超卖。

**可能的追问**：→ Q1.2（标记怎么同步）；→ Q1.5（为什么挤进一个 Lua）；→ 「拐点是怎么定义的」（p99 < 100 ms 且丢弃 < 1% 的最高档，详见笔记 12）。

**别踩**：不要说「前面几层保证了不超卖」。前四层全是**可丢的准入层**，它们放行多少都不影响正确性；唯一的判定点是 L3 脚本里「读库存和扣库存在同一个原子区间」，而最后一道防线还在数据库的条件更新上（见 Q1.8、Q1.5）。也不要把 L1 说成「售罄后 100% 不碰 Redis」——每个实例每秒仍有一个探针请求会去 Redis。

### Q1.2 进程内的售罄标记，一个实例学到了别的实例怎么知道？  〔常见｜追问链：本地缓存怎么同步 → pub/sub 丢了怎么办 → 为什么不用一致性协议〕

**答**：靠 Redis 的一个 pub/sub 频道广播，消息体是「+券号:桶号」/「-券号:桶号」。但这条广播只是**加速手段，正确性不依赖它**：每个实例对一张全桶标记的券每秒仍放一个探针请求去 Redis 问真话，所以陈旧标记最多活一个探针间隔（默认 1 秒）。我没有做任何一致性协议。

**展开**：

- 某实例第一次把某个（券，桶）标记为售罄时广播 `+`；库存回到桶里的三个地方（消费侧首次补偿、关单释放、退款释放）广播 `-`。发送失败只记一条 warn 日志，本地标记照样生效。
- 订阅侧对格式不合法的消息直接忽略并 warn，不会因为一条脏消息挂掉。
- 为什么敢这么松：一个实例的标记只影响**它自己**的本地拒绝，不会传染成全局的错误状态；而全桶标记下的探针保证它会被纠正。用 Raft/版本号那一套的代价远大于「最多错 1 秒的本地拒绝」。
- 证据：`SeckillSoldOutRegistryTest` 钉住了三条——`oneEmptyBucketMustNotRejectTheOtherBuyers`、`everyBucketEmptyIsAnsweredLocallyAndEachBucketIsBroadcastOnce`、`aFailedBroadcastStillFlagsLocally`（广播失败仍然本地置位）；`SeckillSoldOutRegistryIT` 在真实 Redis 上跑同一组行为。

**可能的追问**：→ Q1.3（标记错了怎么办）；→ 「pub/sub 消息交错了呢」（不同实例的 `+`/`-` 可能乱序到达，同样由探针兜底，不保证任意时刻各实例标记一致）。

**别踩**：不要把 pub/sub 说成「可靠广播」。Redis 的 pub/sub 没有持久化、没有 ack，订阅者断线期间的消息直接丢。也不要说「广播保证了各实例视图一致」——本项目明确接受不一致。

### Q1.3 标记错了（实际还有货却被标成售罄）怎么自愈？  〔常见｜追问链：本地缓存怎么同步 → 标记错了怎么办 → 自愈要多久 → 为什么不直接设 TTL〕

**答**：靠探针自愈。即使某张券的 K 个桶全被标记，每个实例**每个探针间隔（默认 1 秒）仍放一个请求**穿过 L1 去 Redis；如果脚本回来说「成功」而本桶此前被标记过，说明标记是陈旧的，立刻清标记并广播 `-`。所以陈旧标记的寿命上界就是一个探针间隔，不依赖广播必达。

**展开**：

- 探针的选人方式是一次 CAS：`nextProbe.compareAndSet(due, now + interval)`，推成功的那**一个**请求继续往下走，其余仍然本地拒绝。用 CAS 而不是加锁，是因为这行代码在售罄后是全链路最热的一行。
- 清标记的三类真实来源：消费侧发现数据库库存不足做首次补偿、关单/退款把库存还回买家自己的桶、以及上面这个探针。前两类是「库存真的回来了」，第三类是「标记本来就错了」。
- 标记是按桶清的：一个单位还回来只重开它自己那个桶，不会把整张券的标记抹掉。
- 证据：`SeckillSoldOutRegistryTest#oneProbePerIntervalReachesRedisSoAStaleFlagHeals` 和 `#oneReturnedUnitReopensItsOwnBucketOnly`。

**为什么不直接给标记设 TTL**：TTL 到期是「无条件放开一段时间」，售罄后会周期性地放一大批请求砸 Redis；探针是「恒定每实例每秒一个」，成本固定，而且探针本身就是一次正常的下单请求，探到有货的那个人是真的买到了，不浪费。

**可能的追问**：→ 「N 个实例就是 N 个探针」（是，L1 的探针也是每实例每秒一个，写在笔记 04 已知边界里）；→ Q1.4。

**别踩**：不要说「自愈时间是 1 秒」就完了——准确说法是「上界是一个探针间隔，且是每实例独立计时的」。也不要说探针是一个后台定时任务，它不是，它就是被选中的那个真实用户请求。

### Q1.4 本地令牌桶的速率按什么定？多实例下阈值怎么分？  〔常见｜追问链：限流用什么算法 → 阈值怎么定 → 多实例怎么分 → 为什么不用分布式限流〕

**答**：速率是 `max(每桶下限, 本桶剩余库存 × 系数)`，系数默认 2，容量等于速率（一秒的突发量）。「本桶剩余库存」是上一次准入脚本的返回值，**零额外开销**。多实例**不分摊**：每个实例各自一份，N 个实例的总放行量就是 N 倍——这是有意的，L2 只防洪峰，不做精确配额。

**展开**：

- 配置里的下限写的是**按券**的每秒 50，实现里除以桶数 K 分摊（至少 1）。不除的话，一张券拆成 K 个桶会让打到 Redis 的兜底流量翻 K 倍。
- 还没见过库存的（券，桶）**不限流**，直接放行——否则活动刚开始时所有人都被挡住，谁也拿不到第一个剩余库存值。
- 速率是跟着库存往下掉的：卖到只剩 10 件时速率就是 20/s，比剩余库存多得多的请求在秒杀语义里本来也抢不到，把它们 429 掉比让它们去挤 Redis 划算。
- 证据：`SeckillLocalRateLimiterTest` 钉住了 `permitsFollowTheRemainingStockTimesTheFactor`、`aShrinkingStockShrinksTheBucketImmediately`（库存变小时立刻收紧，不等下一个窗口）、`theRateNeverDropsBelowTheFloorSharedOutOverTheBuckets`、`bucketsOfOneVoucherAreIndependent`。

**为什么不用分布式限流**：分布式限流每次判定至少一次网络往返，而 L2 存在的全部意义就是「不付这次往返」。精确判定我已经有了，就是 L3 那一次 Lua。

**可能的追问**：→ Q1.10（分桶后阈值怎么变的）；→ 「令牌桶和漏桶的区别」（L0 的 nginx `limit_req` 是漏桶 + burst，L2 是令牌桶；令牌桶允许攒突发，漏桶匀速出）。

**别踩**：不要说「L2 保证了打到 Redis 的流量不超过 X」——它是每实例的，N 个实例就是 N 倍，说成精确配额会被当场拆穿。也不要说 L2 保证「有库存的人一定能买到」：它会把一部分「还有库存时」的请求也 429 掉。

### Q1.5 为什么限频、活动校验、判重、扣减、写预占要放在一个 Lua 里？拆开会怎样？  〔高频｜追问链：怎么保证不超卖 → 为什么用 Lua → 拆成多条命令行不行 → 用 WATCH 呢 → Lua 是原子的但持久吗〕

**答**：因为「查到有库存」和「扣掉库存并记下是谁」之间不能被别人插进来，否则要么超卖、要么一个人抢到两件。Redis 执行 Lua 是单线程串行的，天然就是这个原子区间。顺带一个好处：十几条命令压成一次往返。拆开就得引入分布式锁或者 WATCH 重试——前者更慢，后者在秒杀这种极高冲突下几乎必然重试到底。

**展开**：

- 脚本内部是有顺序的：参数自检 → 取 Redis 服务器时间 → 限频 → 活动窗口 → 库存 → 判重 → 订单号占用 → 才开始写。顺序不是随意排的：**先判再写**，除了「通过了限频的请求会记一次计数」之外，任何一个分支返回时都没有写入过；被限频拒掉的请求连计数都不递增，不占别人的名额。详见笔记 04 第三节。
- 取 Redis 自己的 `TIME` 而不是 Java 传时间戳，是因为多个应用实例的本地时钟不一定一致，活动起止的判定必须有唯一时钟。
- 七个 key 共享 hash tag `{sk:b<n>}`，所以在 Cluster 上仍然是**一个 slot、一个 RTT**（见 Q1.11）。
- 证据：`SeckillLuaScriptContractTest` 和 `SeckillAdmissionScriptIT` 把每个返回码和「返回前不写任何东西」的性质逐条钉住；压测报告 M3/M5 两行里每一档都是 `accepted = stock`，无超卖。

**拆开的具体代价**：分成 GET 库存 → 判重 → DECR 三次命令，要么三次 RTT（延迟三倍），要么用 MULTI（MULTI 不能根据中间结果分支）；用 WATCH + 重试在一千件库存、三万请求的场景下会把大部分请求变成重试风暴；用 Redisson 锁则是每请求至少两次 RTT 加上锁竞争。

**别踩**：**Lua 原子 ≠ 数据不会丢**。这个脚本的原子性只覆盖「要么全做要么全不做」，不覆盖主从复制——主节点挂掉时尚未复制的扣减和预占会丢，切换后 Redis 的库存比真相多（见 Q1.8 结尾和压测报告第 3 节第 8 条）。也不要说「Lua 保证了最终不超卖」——最终防线是数据库的 `stock >= n` 条件更新。

### Q1.6 Lua 执行期间 Redis 阻塞吗？脚本写长了有什么风险？  〔常见｜追问链：为什么用 Lua → Lua 会阻塞吗 → 脚本超时了怎么办 → 你的脚本多长〕

**答**：会阻塞。Redis 执行脚本的那条命令线程是串行的，脚本跑多久，其它客户端的命令就排多久——这正是它原子的原因，也正是它的风险。所以我的准入脚本被刻意压得很短：没有循环、没有 `KEYS`/`SCAN`、没有跨 slot 访问，全部是常数条 O(1) 命令（大致十几条：一次 TIME、两次 GET + 两次 INCR/PEXPIRE、一次 HMGET、一次 GET、一次 HEXISTS、一次 EXISTS、然后 DECR/HSET/HSET/PERSIST/ZADD）。

**展开**：

- 脚本写长的真实风险有三个：一是阻塞整个实例（Redis 的慢查询在这里是全局停顿）；二是超过 `busy-reply-threshold` 后 Redis 开始对其它客户端回 BUSY，而这时候**只有还没做过写操作的脚本能被 `SCRIPT KILL` 掉**，一旦它已经写过，就只剩 `SHUTDOWN NOSAVE` 这种把数据搞丢的手段；三是脚本里做非确定性操作在老版本上会影响复制（现在默认是效果复制，脚本里调 `TIME` 是安全的，我依赖的就是这一点）。
- 我的规避方式就是「短 + 无循环 + 单 slot」：单 slot 是硬要求，Cluster 下跨 slot 的脚本根本不让执行；无循环保证执行时间与数据量无关，不会因为某个 hash 变大而变慢。
- 间接证据：压测报告 M5 行里，10k/20k 档 Redis 的 CPU 分别只有 0.02 / 0.03 核（Cluster 六节点之和），M3 行里 Redis CPU 从 0.38–0.42 降到 0.01–0.02 核。脚本不是瓶颈。
- **本项目没做**：我没有单独采集脚本执行耗时的分布，也没有配 `lua-time-limit` 的告警。要做的话会是两件事——在 Redis 侧开慢日志（`slowlog-log-slower-than` 调低）把长尾脚本捞出来，在应用侧给这次 `execute` 加一个 timer 指标按分位数看。代价是慢日志本身要人去看，指标要多一次计时开销（很小）。这两样都是假设方案，没有实测数字。

**可能的追问**：→ 「那批量消费的脚本呢」（那一侧按桶分组、每桶一次往返，详见笔记 05）；→ 「Redis 7 的 function 呢」（没用，脚本用 `DefaultRedisScript` 加载，走 EVALSHA）。

**别踩**：不要说「Lua 不阻塞 Redis」或者「Redis 是多线程所以没关系」——Redis 6 之后的多线程只用在网络 IO，命令执行仍是单线程。也不要说「超时了 Redis 会自动回滚脚本」——Redis 没有脚本回滚，写过一半的脚本被杀不掉就是这个原因。

### Q1.7 一人一单在准入层怎么做的？和数据库唯一索引是什么关系？  〔高频｜追问链：一人一单怎么做 → 高并发下同一个人并发下单呢 → 数据库那一层还需要唯一索引吗 → 分库分表之后唯一索引还有用吗〕

**答**：准入层是一个预占 Hash：key 是（桶，券），field 是用户 id，value 是订单号。脚本在扣库存前先 `HEXISTS` 这个 field，存在就返回「重复购买」。因为桶是按 `userId % K` 切的，**同一个人永远落同一个桶**，判重天然只看一个 key、天然在同一个原子区间里。数据库那边还有一个唯一键 `(user_id, voucher_id, active_flag)`，它不是重复保险，而是**Redis 数据真的丢了以后的最后一道约束**。

**展开**：

- 预占 Hash 是一物两用：既是判重依据，也是「这个订单号归谁」的归属证据，后面消费、补偿、对账都要拿它对账（详见笔记 05）。
- 同一个人并发下单：两个请求都进到 L3，Redis 串行执行两个脚本，第二个必然看到 `HEXISTS = 1`，返回重复购买。不需要任何锁。
- 数据库侧：落库是 `INSERT IGNORE`，唯一键冲突时不报错、计一个 `duplicate` 指标；`active_flag` 参与唯一键是为了让关单/退款之后这个人还能再买（详见笔记 06）。分库分表后订单表按 `user_id` 分片，`(user_id, ...)` 的唯一键**片内即全局**，因为同一个用户的所有订单必然在同一个分片上——这也是订单号低位嵌用户基因的动机之一（详见笔记 08）。
- 证据：`SeckillLuaScriptContractTest` 覆盖返回码 2；`SeckillBucketAdmissionIT#oneBuyerOnlyEverTouchesTheirOwnBucket` 钉住「一个买家只碰自己的桶」。

**可能的追问**：→ Q1.9（为什么按用户切桶）；→ 「唯一索引冲突了这一单怎么办」（消费侧当幂等处理，详见笔记 05）。

**别踩**：不要说「有了 Redis 判重就不需要唯一索引了」，也不要反过来说「唯一索引才是真正的一人一单，Redis 只是挡一下」。准确说法是：正常路径上判重在 Redis 完成，唯一索引在 Redis 数据丢失的极端路径上才会真正生效。另外别说「用分布式锁做一人一单」——本项目下单路径上没有任何分布式锁（见 Q1.8）。

### Q1.8 为什么不用 Redisson 分布式锁？教程里那把锁去哪了？  〔高频｜追问链：一人一单怎么做 → 用锁吗 → Redisson 的看门狗了解吗 → 锁的性能开销有多大 → 你怎么知道不用锁是对的〕

**答**：下单准入路径上**从来没有分布式锁**，一人一单和扣库存都在同一个 Lua 的原子区间里完成，锁是多余的。教程版把 Redisson 锁放在消费落库那一侧，我这里也曾经有过（每条消息一把），M4 把它换成了「Redis 内状态认领」的 CAS + 租约。换掉它的理由不是「锁慢」——恰恰相反，M0 的火焰图里 `lock/unlock` 只占消费线程 wall 时间的 **0.2%**（`benchmark/v2/m0/baseline.md` 第 4.2 节），因为锁按订单/用户粒度，根本没有竞争。

**展开**：

- 这 0.2% 是个很有意思的点：计划里我原本把「每消息 Redisson 锁」列为瓶颈（D3），实测把它证伪了。同一张火焰图里真正的大头是 `tb_seckill_voucher` 那一行的行锁等待 44.7% 和连接池等待 49.5%。**先测再改**，这是我从这件事上拿到的最直接的教训。
- 那锁为什么还是被换掉了？不是为了性能，是为了**语义**：锁只能保证互斥，不能表达「这一批被谁领走了、租约什么时候过期」。换成状态认领之后，对账器能从状态本身判断「有人在处理」还是「租约过期该我接管」，而不是去抢一把看不出所有者的锁。批量化之后一把锁也锁不住一个跨多单的批次。
- 现在 Redisson 在秒杀链路上只剩一处：对账器的**每单调度锁**，用来让多个对账实例不同时处理同一单。它在冷路径上，每 10 秒一轮、每轮 100 单，不在热路径上。
- 关于看门狗：Redisson 的默认续期看门狗在「客户端卡住但没死」时会一直续期，锁形同虚设；我的发号器租约反过来做——**本地栅栏只信任 ttl 的 5/6，到点自己停**（见 Q1.14），这是 fail-closed 而不是 fail-open。

**可能的追问**：→ Q1.14（租约与栅栏）；→ 「锁的主从切换问题/RedLock」（Redisson 的锁在主从异步复制下切换会丢，我没有用它承担正确性，所以不受这个影响）。

**别踩**：不要说「Redisson 锁性能差所以我去掉了」——我的实测数字正好否定这句话，说出来反而是送人头。正确的表达是「它不是瓶颈，但它表达不了我需要的语义」。也别说「现在完全没用 Redisson」，对账器调度锁还在。

### Q1.9 库存为什么要分桶？桶数怎么定？某个桶空了别的桶还有货怎么办？  〔常见｜追问链：热点 key 怎么办 → 怎么分 → 桶数怎么定 → 分桶带来什么新问题〕

**答**：分桶是为了解掉 Redis 侧的单点：不分桶时，一张券的库存、预占、订单状态、到期索引全都是**一个 key**，在 Cluster 上只能落一个 slot，没法分片。分成 K 份之后这张券的流量散在 K 个 slot 上。桶号是 `userId % K`，K 必须是 2 的幂且 ≤ 1024，默认 16。某个桶空了、别的桶还有货时，这个买家就是「库存不足」——**本项目明确选择不借库存**。

**展开**：

- 为什么按用户切而不是按请求随机切：按用户切换来两个硬性质——（1）同一个人永远落同一个桶，判重只看一个 key（Q1.7）；（2）订单号低位带 `userId % 1024` 的基因，K 取 2 的幂时**桶可以从订单号单独反推**，而查单接口手里只有订单号，没有用户也没有券。按请求随机切的话，判重要扫 K 个桶，查单要扫 K 个 slot。
- K 的上界 1024 不是拍的：基因只有 10 位，K 超过 1024 就反推不回来了，`SeckillBucketRouter` 的构造函数直接拒绝。
- 库存怎么分：`总库存 / K`，前 `总库存 % K` 个桶多一件。K 份加起来精确等于总库存，彼此相差最多一件，不会凭空多也不会少。
- 不借库存的代价叫**尾部浪费**，`SeckillBucketAdmissionIT#aBuyerWhoseBucketIsEmptyIsRefusedWhileTheVoucherStillHasStock` 用一个确定的例子把它钉住（4 桶 8 库存，桶 0 的第三个买家被拒而全券还剩 6 件）。
- 但实测的浪费量是 **0**：M5 长测里每一档 `accepted` 都精确等于库存，K = 1/8/16/64 都一样。原因很直接——秒杀场景下需求远大于库存，每个桶都会被买空；浪费只在「需求与库存量级相当且分布不均」时才出现，那是日常领券不是秒杀。
- **借库存本项目没做**。要做的话是两步：扣邻桶库存、写回本桶预占；两步之间崩溃要靠一个幂等 token 把两步串起来，再由对账器把悬空的那一件归还。代价是热路径上多一次跨 slot 操作（跨 slot 就不能在一个 Lua 里做了，这是最大的代价），以及对账器要多认识一种状态。所以结论是「先量化再决定」，量出来是 0，就不做——真需要时更简单的做法是直接调小 K。

**可能的追问**：→ Q1.10（分桶后限流阈值）；→ Q1.11（hash tag）；→ 「MySQL 那一行也分桶了吗」（**没有**，`tb_seckill_voucher` 仍是一张券一行，这正是写路径水平扩展的上限，压测报告第 3 节第 7 条实测：1/2/3 实例的提交次数都在 70–115 之间，与实例数无关）。

**别踩**：不要说「分桶把库存那一行的瓶颈解决了」——分桶分的是 Redis 的 key，不是数据库的行，M4 复测里那句话是错的、ADR 0006 专门更正过。也不要说「尾部浪费不存在」，正确说法是「在秒杀的负载形态下实测为 0，但这个洞是真的」。

### Q1.10 分桶之后限流阈值怎么变的？你观察到什么副作用？  〔常见/坑题｜追问链：分桶带来什么新问题 → 限流阈值怎么跟着变 → 数字上看到了吗 → 这算回退吗〕

**答**：两个本地层都跟着桶走了。L2 的速率改成跟随**本桶**剩余库存，配置里按券的下限在实现里除以 K 分摊；L1 改成「每个桶都被标记时才本地拒绝」。副作用在数字上很明显：M5 复测里 20k 档的 `http_429` 从 **21 涨到 1480**。

**展开**：

- 为什么下限要除以 K：下限是兜底速率（默认按券 50/s）。如果不除，16 个桶各自按 50/s 兜底，快卖完时打到 Redis 的兜底流量就是原来的 16 倍——拆桶的目的是分散，不是放大。
- 429 涨了 70 倍的机理：16 个桶各自独立限流，每个桶的速率是「本桶剩余库存 × 2」和「50/16」取大。同样 1000 件库存、同样的到达速率，分成 16 份之后每一份的速率上限都小得多，合起来比单桶更早开始丢。
- 这**不是回退**，而是设计里写明的行为：被 429 的请求本来就抢不到 1000 件库存里的任何一件。同一场 M5 复测里两档都是 `accepted = stock = 1000`、无超卖、`half_msgs` 恒 0，达成速率 10k 档 −0.1%、20k 档 −1.7%（压测报告 M5 行）。
- 我没有为此调参数。要调的话方向是把 `stockFactor`（默认 2）调大，让速率跟库存的跟随更宽松；代价是打到 Redis 的流量变多。这是一个纯粹的取舍旋钮，我没有实测过不同系数下的曲线。

**可能的追问**：→ 「p99 也涨了吧」（涨了，+28~45 ms，但那一项**不是干净对照**：Cluster 的六个节点共享对照组里一个 Redis 独占的两个核，我在复测里写明了）；→ Q1.4。

**别踩**：不要把这个 429 的上涨说成「优化带来的收益」或者遮掉不说。也不要把 p99 的上升说成「Cluster 就是更慢」——这一场的核分配不干净，我只能说「方向可以解释」，不能下结论。

### Q1.11 hash tag 怎么选的？为什么不把券号放进 tag？代价是什么？  〔坑题｜追问链：Cluster 上多 key 操作怎么办 → tag 怎么设计 → 为什么不带券号 → 那热点怎么办〕

**答**：tag 是 `{sk:b<n>}`，**只有桶号，不带券号**，完整 key 形如 `sk:{sk:b3}:stock:17`。计划里原本写的是 `sk:{v17:b3}`，实现时改掉了。理由只有一个：按订单号查状态时**手里没有券号**——订单状态轮询接口只有 orderId，既没有 voucherId 也没有 userId，tag 里带券号会让这个 key 根本拼不出来。

**展开**：

- 一次准入脚本的七个 key（库存、活动元数据、预占、订单状态、桶内到期索引、用户限频窗口、IP 限频窗口）全部带同一个 tag，所以在 Cluster 上是**一个 slot、一个 RTT**。Cluster 对跨 slot 的多 key 命令和脚本是直接拒绝的，这不是优化问题，是能不能跑的问题。
- 热点分散上带不带券号没有区别：秒杀期间热的本来就是**一张券**，它的 K 个桶已经散在 K 个 slot 上了。带券号只能顺带把冷券也散开，而冷券本来就不需要散。
- 代价我写在边界里了：**不同券的同号桶会落在同一个 slot**，多张券同时热的时候负载会略不均。认了。
- 推不回去的那半边怎么解决：`SeckillBucketRouter#bucketOfOrder(orderNo)` 直接 `orderNo & mask`，再拼 `statusKeyOfOrder`。这就是 Q1.13 里订单号低位嵌基因的第二个用处。
- 证据：`SeckillBucketRouterTest`；M5 那一场的隔离栈全量 IT 在真实 3 主 3 从 Cluster 上 579 个全绿（ADR 0006）。

**可能的追问**：→ Q1.13（基因）；→ 「非秒杀路径上还有跨 slot 的脚本吗」（改 Cluster 时排查过，最后一处是登录验证码的三个 key，改成共享手机号的 tag；博客热榜脚本本来就带 tag）。

**别踩**：不要说「加 hash tag 是为了性能」——首要原因是 Cluster 下多 key 脚本的硬约束。也不要说「tag 带券号能解决热点」，在本项目的负载形态下它什么也解决不了，还要付出 key 拼不出来的代价。

### Q1.12 秒杀令牌是干什么用的？没有它会怎样？  〔常见｜追问链：怎么防脚本刷 → 令牌怎么生成 → 令牌存哪 → 能撤销吗〕

**答**：它是一张短期有效、绑定「本人 + 本券」的准入凭证，格式是 `<过期秒>.<base64url(HMAC-SHA256(密钥, "用户id:券id:过期秒"))>`，默认 10 分钟。作用是把两类请求在**零网络 IO** 的前提下挡掉：活动开始前就来的请求，和冒用他人/他券的重放请求。它**不落 Redis**——落了就等于在下单路径上多一次读，而下单时我只要用同一个密钥重算一遍签名就能验。

**展开**：

- 签发接口是 `GET /voucher-order/seckill/{id}/token`，只在活动 ACTIVE 且在窗口内才签；下单时带 `X-Seckill-Token` 头，控制器验签，不过就 403。
- 验签用的用户 id 来自当前会话、券 id 来自路径，所以别人的令牌、别的券的令牌都验不过，令牌也没法在券之间串用。
- 签名比较用 `MessageDigest.isEqual`（常量时间），不用 `String.equals`，避免时序侧信道。
- 是否强制可配（`token.required`），默认强制。
- 代价写在边界里：**签出去就撤不回来**。活动被挂起之后，已经签出的令牌仍然验得过，最长可能比活动结束多活一个有效期；真正拦住它的是下单脚本里的活动状态检查（返回码 4）。这是「不落 Redis」这个选择的直接后果，我接受它。
- 证据：`SeckillTokenServiceTest`。
- 压测时的处理必须声明：k6 用同一个密钥自己签（每个请求都是新用户，先去取令牌会让请求数翻倍），**服务端照常验签，验签成本计入测量**。

**可能的追问**：→ 「要撤销怎么办」（**本项目没做**。业界做法是加一个版本号/代次：把券的 token 版本存在活动元数据里，签名里带上版本，挂起时把版本加一，所有旧令牌一次性失效。代价是验签从「纯本地」变成「要知道当前版本」——要么接受一次 Redis 读，要么在本地缓存版本、接受秒级的延迟。这是假设方案，没有实测）；→ Q1.1。

**别踩**：不要说「令牌保证了防刷」——防脚本刷的主力是 L0 的 nginx 限流和 L3 脚本里的按用户/按 IP 限频，令牌管的是「是不是本人本券、活动有没有开始」。也不要说「令牌是一次性的」，它在有效期内可以反复用，防重复购买的是预占 Hash。

### Q1.13 订单号怎么生成的？为什么本地发号而不是 Redis incr？  〔高频｜追问链：分布式 ID 怎么生成 → 为什么不用 UUID → 为什么不用 Redis incr → 雪花的时钟回拨怎么办 → 分库分表之后怎么按订单号查〕

**答**：本地 Snowflake，布局是「最高位 0 | 41 位毫秒（纪元 2025-01-01Z）| 5 位实例编号 | 7 位序号 | 10 位用户基因」。不用 Redis `INCR` 的直接原因是**它是一次网络往返，而且每个请求都要付**——包括那 99% 注定失败的。本地发号是纯位运算，失败者只多花这一点点。第二个原因更结构性：Redis 自增给不出我要的那 10 位基因。

**展开**：

- 低 10 位是 `userId % 1024`，于是 `order_no % 2^k == user_id % 2^k`（k ≤ 10）。两个用处：（1）订单表按 `user_id` 分片，按 order_no 查也能**单分片命中**，不用广播（详见笔记 08）；（2）桶号可以从订单号单独反推（Q1.11）。
- 每毫秒每实例 128 个号（7 位序号），即 12.8 万/秒，远高于准入吞吐；序号用满就自旋等到下一毫秒。
- **纪元选择是为了和 V1 的号段不相交**：V1 的号是 `(秒 − 2025-12-22) << 32 | count`，全部小于 2^57；新纪元让 2026-02 之后签发的号全部 ≥ 2^57。所以 M2 迁移来的历史订单号不可能与新号撞车。发号时会检查毫秒差落在 `[2^57 对应的下界, 不溢出符号位的上界]` 里，超出直接拒绝发号——**宁可失败也不签出一个可能撞车的低号**。
- 不用 UUID：128 位、无序、做主键会让 InnoDB 聚簇索引页分裂，而且带不了基因。
- 证据：`SnowflakeOrderIdGeneratorTest` 里的 `idsAreUniqueUnderConcurrencyWithZeroNetworkCalls`、`lowTenBitsCarryTheUserGeneSoAnOrderRoutesLikeItsUser`、`everyNewIdIsAboveEveryV1RedisIdSoTheTwoRangesNeverMeet`、`sequenceOverflowWaitsForTheNextMillisecond`。
- 另外准入服务在调脚本前会**校验订单号的基因与买家一致**，不一致直接抛错——否则这个订单的状态 key 会落到另一个桶、另一个 slot，之后按订单号谁也查不回来。

**可能的追问**：→ Q1.14（实例编号与时钟回拨）；→ 「为什么不用美团 Leaf/百度 UidGenerator」（号段模式仍然要定期取号段、要一张号段表，而我需要的基因位它们的默认布局里没有；自己实现 60 行、能钉住测试，我认为这里不值得引依赖）。

**别踩**：不要说「Snowflake 保证全局唯一」就收口——它的唯一性完全依赖「实例编号不重复」和「时钟不回拨」，这两条都要自己保证（Q1.14）。也不要说「发号失败不影响用户」——发号抛异常时整条请求答 503，这是有意的 fail-closed。

### Q1.14 发号器的实例编号怎么分配？多实例撞号、时钟回拨怎么办？  〔高频｜追问链：Snowflake 的 workerId 哪来的 → K8s 弹性扩缩呢 → 租约续不上怎么办 → 时钟回拨怎么办 → 回拨很久怎么办〕

**答**：从 Redis 抢一个租约：对 `order-id:worker:<0..31>` 逐个做 `SET NX PX`（值是本进程随机 token，ttl 默认 30 秒），抢到就用；之后每 ttl/3（10 秒）用一个「比对 token 相同才 PEXPIRE」的小 Lua 续期。关键不是续期，而是**本地栅栏**：每次续期成功时记下「有效到 = 发起续期的时刻 + ttl − ttl/6」，只信任 ttl 的 5/6；发号前先看本地时钟过没过这个点，过了就抛错。时钟回拨 ≤ 5 ms 等过去，更大的回拨直接拒绝发号。

**展开**：

- 为什么栅栏是这套方案的核心：Redis 那边 ttl 到期才会让出槽位，而我在 5/6 处就已经停止发号了，中间留出 ttl/6 的安全余量。于是**续不上的那段时间里，Redis 还没让出槽，本实例已经不再发号**，接手者与本实例在时间上不会重叠。这是 fail-closed，和 Redisson 看门狗那种「客户端卡住还一直续期」的 fail-open 正好相反。
- 续期时 Redis 抛异常（网络问题）**不放弃槽位**，由栅栏决定什么时候停——因为这时我并不知道 Redis 是不是真的丢了我的 key，贸然重抢反而可能一个进程占两个槽。
- 续期返回不是成功（说明 key 被别人接手了）：立刻把本地编号作废，重走一遍抢占。
- 32 个槽全被占：打错误日志，在抢到之前下单接口一律 503；续期调度每 10 秒还会再试一次抢占。这是明确的边界——**超过 32 个实例就抢不到租约**，当前规模够用。
- 进程正常退出时用「token 相同才 DEL」的小 Lua 主动释放，删不掉也无所谓，它自己会过期。
- 时钟回拨：≤ 5 ms 自旋等过去（对应 NTP 的小步调整）；更大的直接 `IllegalStateException`，整条请求 503。不等、不借用未来时间戳，因为等一分钟就是把一分钟的请求全部挂住。
- 证据：`WorkerIdLeaseTest#stopsIssuingBeforeRedisCouldHaveExpiredTheKeyWhenRenewalsFail`、`#aStolenKeyDropsTheSlotAndTakesAnotherOne`、`#aSuccessfulRenewalExtendsTheFence`，以及真实 Redis 上的 `WorkerIdLeaseIT`；回拨行为由 `SnowflakeOrderIdGeneratorTest#smallClockRollbackWaitsAndLargeRollbackFailsClosed` 钉住。
- 还有一道**脚本级的兜底**：万一租约异常导致两个实例短暂共用同一个编号、签出同一个号，准入脚本发现这个订单号的状态 key 已存在就返回码 8，**不动库存、预占和订单状态**，应用换一个号再调一次；第二次仍冲突才答 503。正因为有了这个证明（状态 Hash 永远只属于一个预占），我才把早期版本里的「订单号隔离区」整块删掉了。

**可能的追问**：→ Q1.8（和 Redisson 看门狗的对比）；→ 「为什么是 5/6 不是别的」（ttl/6 的余量对应 ttl 30 s 时的 5 s，比续期周期 10 s 小一档；这是个拍的数，但方向必须是「本地先停」）；→ 「重试会不会重复扣库存」（不会，第一次脚本什么也没写；代价是这个用户在本窗口多花一次限频配额）。

**别踩**：不要说「租约保证了不会撞号」——保证不撞的是**本地栅栏 + 脚本返回码 8** 这两道，租约本身在网络分区下给不了这个保证。也不要说「时钟回拨我会等」——只等 5 ms，超过就拒绝。

### Q1.15 预占成功但消息没发出去，这一单怎么办？  〔高频｜追问链：异步下单消息丢了怎么办 → 为什么不用事务消息 → 对账器怎么发现的 → 多久能收敛 → 用户这段时间看到什么〕

**答**：这一单留在 Redis 里，状态是「处理中」，由对账器重投。**预占本身就是 outbox**——它在脚本里和扣库存原子地一起写下，所以只要预占在，这一单就丢不了。发送失败在应用里只记日志和指标，**不影响给用户的答复**：订单号照样返回，前端拿它去轮询。

**展开**：

- 覆盖的三种情况是同一种：`syncSend` 抛错（Broker 没确认存下）、进程在脚本成功与发送之间被杀、以及脚本跑完但回包丢了（这一种在 Java 侧还有一层兜底——按订单号去读状态，若存在且订单号/用户/券三者都对得上、状态是处理中或已成功，就按成功继续）。
- 对账器的发现方式：脚本写预占时把订单号按「当前时间 + stale-after（默认 2 分钟）」放进本桶的到期索引 ZSET；对账器定期（默认每 10 秒、每轮 100 单）扫到期的，查到数据库无单且未到最终期限（默认 15 分钟）就**重投原消息**。重复无害：消费者看到已成功或已有订单就直接确认。过了最终期限才走精确补偿。详见笔记 05。
- **为什么不用事务消息**：事务消息只覆盖「半消息发出」到「提交」这一小段。我的准入成功点在 Redis 脚本里，在「脚本成功」到「半消息发出」之间崩溃，同样留下一条没有消息的预占——所以事务消息**并不能省掉重投**，只是在每个成功者身上多付一次半消息加一次提交，还要在每个失败者身上也付一次。既然重投必须有，不如让预占直接当 outbox。数字上：压测报告 M3 行，half message 从「等于请求数」变成 **0**。
- 证据：`SeckillRedriveIT#anAdmittedOrderWhoseMessageWasNeverSentStillReachesMySql`，用真实 Lua、真实 Broker、真实消费者复现「脚本成功、什么也没发」；演练侧 `benchmark/v2/scripts/kill-drill.sh` 在压测中 `kill -9` 应用，`BROKER_DOWN=1` 时先杀 Broker 让发送真的失败。压测报告 M3 行：`kill -9` ×2 与「先杀 Broker」三方一致收敛（M3 复测的明细是 4249 个无消息预占全部重投落库、收敛 574.2 s）。
- 一个诚实的副产品：只 `docker pause` Broker 再 `kill -9` 应用**不会**丢消息——请求字节已经在 Broker 的 socket 缓冲里，恢复后照样落盘。真实的「脚本→发送」窗口只有亚毫秒，自然 kill 几乎打不中，所以演练必须先把 Broker 杀掉才造得出这个场景。
- 已知的短板：**重投速度是瓶颈**。默认 stale-after 2 分钟、每 10 秒 100 单，上面那 574.2 s 就是这个参数决定的。正确性不受影响（预占、订单、库存三方一致），但收敛慢。

**可能的追问**：→ 「用户这两分钟看到什么」（轮询查单返回「处理中」，详见笔记 05/06）；→ 「重投会不会重复建单」（不会，消费侧 `INSERT IGNORE` + 状态机条件更新，详见笔记 05）；→ Q1.8。

**别踩**：不要说「用了事务消息就不会丢」——这正是本项目要反驳的那句话，前面那段推理是这题最值钱的部分。也不要说「消息丢了对账器马上就能补」——默认要等 stale-after 2 分钟才进对账视野，收敛是分钟级的，说快了会被追问参数当场露馅。

### Q2.1 为什么要引入 MQ？同步写库不行吗？引入之后多了哪些新问题？  〔高频｜追问链：为什么要异步 → 同步写库慢在哪 → 异步之后用户怎么知道结果 → 消息丢了/重了怎么办〕

**答**：不是为了「解耦」这种正确的废话，是因为秒杀的两端速率差了两个数量级。准入端一次请求只在 Redis 里跑一个脚本，实测 20k req/s 还没到拐点；而落库端每建一单都要更新同一张券的同一行库存，实测提交速率上限就在 70–115 次/s 那一档。中间不放一层缓冲，请求线程就会全部堵在那一行的行锁上。引入 MQ 之后新问题是三个：消息可能丢、可能重、用户拿不到同步结果。

**展开**：
- **同步写库的代价是量过的**：M0 基线落库 123 / 264 / 478 单/s（中位 264），火焰图里 44.7% 的时间花在 `tb_seckill_voucher` 那一行的行锁上、49.5% 在连接池等待——连接被行锁等待占住了，所以这两个数是同一件事的两面。
- **异步换来的是准入端可以只做一件便宜的事**：一次 Lua、一条预占、一条普通消息。M3 之后准入侧拐点到 20k req/s，此后每个里程碑的准入数字只用来证明没回退。
- **新问题各自的答案**：丢 → 预占即发件箱 + 对账器重驱动（Q2.4）；重 → 主键/唯一键 + 认领脚本的幂等分支（Q2.5）；查不到 → 订单状态查询接口先读 Redis 预占状态（Q2.15）。
- 代价要诚实说：落库从「下单即可见」变成「中位 5.2 s、p99 15.7 s、最大 16.0 s 才可见」（全链路场景）。

**可能的追问**：→ Q2.2（为什么不是事务消息）；→ Q2.15（用户查不到订单）；→「那为什么不干脆同步写 Redis 之后直接返回成功、后台慢慢写？」（这正是本项目做的，MQ 只是那个「后台」的调度器）

**别踩**：别说「引入 MQ 提升了吞吐」这种笼统话。本项目里 MQ **没有**提升落库吞吐，落库吞吐的上限至今还是那一行；MQ 提升的是**准入吞吐**和**削峰能力**。这两件事分开说，面试官一听就知道你量过。

### Q2.2 你用的是事务消息还是普通消息？为什么不是事务消息？  〔高频｜追问链：怎么保证「预占写了消息一定发」→ 用没用事务消息 → 半消息的代价 → 那你靠什么兜底〕

**答**：普通同步消息，`syncSend` 之后检查 `SEND_OK`，不是 `SEND_OK` 就抛异常。不用事务消息，因为 Redis 里那条「处理中」的预占本身就是发件箱——它带到期时间、进了处理中索引、能被对账器扫到，消息没发出去对账器会再发一遍。

**展开**：
- **半消息的代价在这个项目里有具体数字**：M0 的形态是每个请求——包括 99% 注定失败的——都先发一条事务半消息，15k 档 Broker 先被压住、成了天花板。M3 把准入漏斗做完之后，报告里记的是 **half message 从「等于请求数」变成 0**。这条是我最喜欢举的例子：事务消息的成本不在提交阶段，在**它让每一个注定失败的请求都写了一次 Broker**。
- 事务消息本来要解决的是「本地事务与发消息的原子性」。而这里的「本地事务」是 Redis 的一次 Lua——它本身原子，缺的只是「发送」这一跳的可靠性，而这一跳已经有一个比半消息便宜得多的补偿者（对账器）。
- 后来每一轮压测的验收项里都带着 `half_msgs = 0`：M6 扫描八轮全部 `accepted = 20000`、`order_msgs = 20000`、`half_msgs = 0`。

**可能的追问**：→ Q2.3（凭什么算 outbox）；→ Q2.4（消息丢了怎么办）；→「事务消息的 back-check 回查你了解吗？」（了解，就是本项目里对账器做的那件事，只是回查的发起方从 Broker 变成了我自己的定时任务）

**别踩**：别说「事务消息性能差所以不用」——那是印象派。要说清楚**差在哪一段**：本项目的形态是 99% 的请求注定失败，半消息让这 99% 也付了一次 Broker 写入的代价，所以拐点被 Broker 卡住。换一个「大部分请求都成功」的场景，这个论证就不成立了。

### Q2.3 Redis 里的预占凭什么算 outbox？和本地消息表比差在哪？  〔高频｜追问链：预占即发件箱 → Redis 挂了发件箱不就没了 → 和本地消息表比 → 你为什么能接受这个差距〕

**答**：算 outbox 要满足三件事——是持久的事实、能被扫出来、能据此重建消息。预占三件都占：状态哈希里存了订单号 / 用户 / 券，处理中索引是一个按到期时间排序的有序集合，对账器按分数取到期成员就能把消息原样重建出来发一遍。和本地消息表比，差的就一样：**持久性**。Redis 主节点挂了没同步出去的那条预占就没了，而本地消息表和订单在同一个库里、同一个事务里。

**展开**：
- 预占的「可扫描」是设计出来的：准入写进处理中索引时分数是「现在 + 2 分钟」（`stale-after`），两分钟后对账器才会看它一眼（详见笔记 05 第三节）。
- **丢了预占会怎样，我演练过**：M8 的复制空窗演练——先让副本睡着、再从主节点 `CLIENT KILL TYPE replica` 切断链路，让主节点在空窗里继续接单然后杀掉。两晚四轮，Redis 最多多放了 10.3% 的人，而 **MySQL 每一轮都恰好建了 30000 单、超卖恒为 0**。多出来的人在两处被挡：消费者认领时发现状态哈希不在（判「状态缺失」→ 重投 → 最终进死信队列），或者复活的库存被重新卖掉、批次走到数据库被 `stock >= n` 拒绝（第二轮 337 次）。
- 所以这个取舍的真实形状是：**本地消息表把「不丢」做到 RPO=0，代价是每一个赢家都要先写一次库；预占把这一跳挪到 Redis，代价是主节点故障窗口内可能丢预占，但丢了不会超卖、只会有人白高兴一场。** 秒杀场景我选后者。
- 补一句边界：丢失预占的那几条消息最后进的是死信队列，**没有做死信告警和自动归档**，只有日志和计数。

**可能的追问**：→ Q2.4；→ Q2.13（kill -9 收敛）；→「那用户白高兴一场你怎么交代？」（订单状态查询接口会告诉他失败，详见 Q2.15）

**别踩**：别把「预占即发件箱」说成「和本地消息表等价」。它在可靠性上是**弱一档**的，这一点要主动说出来，然后拿演练数字说明弱在哪里、后果被什么兜住。主动承认这一档，比强行论证等价可信得多。

### Q2.4 消息丢了怎么办？你怎么证明没丢？  〔高频｜追问链：发送失败怎么办 → 发送成功但 Broker 没落盘 → 消费端丢 → 你怎么证明〕

**答**：分三段看。发送段：同步发 + 校验 `SEND_OK`，失败抛异常，但**即使失败也不用当场重试**，因为预占已经在处理中索引里，两分钟后对账器会问一次写库、发现订单不存在就把消息重新发一遍。消费段：只有整批全部办完才返回 `CONSUME_SUCCESS`，任何一条没办完整批 `RECONSUME_LATER`。证明靠演练的三条一致性判据，不是靠推理。

**展开**：
- **重驱动的边界写在配置里**：年龄 < `final-timeout`（15 分钟）就重发；重发失败也不要紧，索引分数已经推后 1 分钟（`retry-delay`），下一轮再来。超过 15 分钟且补偿开关打开，才做精确补偿把名额还回去；开关关着就只告警，**绝不擅自还库存**。
- **证明的方式是演练后的三条判据同时成立**：预占数 = 订单数、Redis 库存 = 数据库库存、没有残留的处理中状态。M4 复测记的是 `kill -9` 收敛 102.8 → 44.7 s；「先杀 Broker」这一类是 574.2 → 572.1 s（没有改善，原因见 Q2.12）。
- **Broker 侧我没做的**：没有做多副本切换演练，没有去读 Broker 的刷盘配置、也没有改成同步刷盘 / 同步双写。所以严格说，「Broker 收了但没落盘就宕机」这一类丢失，我这边**不是靠 Broker 保证的，是靠对账器兜住的**——预占还在，订单不存在，15 分钟内一直重发。
- **业界成熟做法（本项目没做）**：发送端加一个本地重试队列 + 消息轨迹（RocketMQ 的 trace），Broker 侧同步刷盘 + Dledger 多副本。代价是写入延迟上升、以及多一套要运维的组件；在这个单机压测环境里我没有条件验证它，所以没做。

**可能的追问**：→ Q2.12（对账器的判定条件）；→ Q2.13（收敛时间）；→「你重发会不会重复建单？」→ Q2.5

**别踩**：别说「我加了重试所以不会丢」。要说清楚**谁是最后那个负责人**——本项目是对账器，不是发送方的重试。也别把 `syncSend` 说成「保证不丢」：它只保证 Broker 应答了，没覆盖 Broker 落盘前宕机。

### Q2.5 重复消费怎么办？幂等键是什么？  〔高频｜追问链：什么时候会重复 → 幂等键是什么 → 数据库层怎么挡 → 扣库存会不会扣两次〕

**答**：幂等键是**订单号**，它是分片订单表的主键；另外还有一个 `(user_id, voucher_id, active_flag)` 的唯一键挡住「同一个人同一张券两张活跃单」。重复消费有三道挡：认领脚本的幂等分支（已成功 / 已失败直接确认）、`INSERT IGNORE`、以及退化后单条路径撞主键冲突时的回查判定。扣库存不会扣两次——判重放之后**明确不再扣库存**。

**展开**：
- **重复的来源有三种**：整批重投（一批里有一条没办完就整批重投）、对账器的重驱动、Broker 自身的重投。三种走的是同一套幂等。
- **第一道在 Redis**：批量认领脚本对每条消息返回一个决策，已成功 / 已失败直接算办完（幂等确认），根本不会进数据库。所以整批重投时，第二遍绝大多数消息在这一步就被跳过了。
- **第二道在数据库**：多值 `INSERT IGNORE`，重投撞上已存在的行时是空操作而不是整批失败。但注意——**插入行数 ≠ 组内条数就整组回滚退化**（原因见 Q2.8）。
- **第三道在退化后的单条路径**：撞主键冲突时按订单号回查，查到的就是同一个用户同一张券 → 判为重放，直接返回且**不再扣库存**；订单号被别人占了、或者这个人这张券已有活跃订单 → 是真冲突，按永久失败处理（先挂起券再精确补偿，详见笔记 05 第三节）。
- 订单号是**发号器**本地雪花发的，低位嵌了用户 id 基因，所以它同时是分片键的来源（详见笔记 08）。

**可能的追问**：→ Q2.8；→ Q2.11（认领租约怎么防并发重复）；→「唯一键里那个 `active_flag` 是干什么的？」（生成列：CLOSED/REFUNDED 置 NULL，让关单后能再买，详见笔记 06）

**别踩**：别说「用 Redis 判重就够了」。Redis 的预占是**准入层**的判重，它允许丢；真正不可逾越的那道是数据库的主键和唯一键。这两层的地位不一样，说反了是硬伤。

### Q2.6 批量消费具体怎么批的？一批做了哪几件事？  〔高频｜追问链：一批做了什么 → 为什么要认领 → 事务边界在哪 → 一批里有一条失败怎么办〕

**答**：一批三步：**一次 Redis 往返认领整批 → 按券分组、每组一个事务（一条多值 `INSERT IGNORE` + 一次 `stock - n`）→ 一次 Redis 往返收尾**。核心是第二步：把「每单一次行锁」变成「每批每券一次行锁」。整批要么全部办完确认，要么整批重投。

**展开**：
- 完整流程详见笔记 05 第三节 3.1，口述时我只强调三处设计点：
  - **认领按桶拆、落库按券分组**，这两个维度不一样：一个 Lua 脚本只能读自己槽里的键，所以认领和收尾按买家所在的库存桶拆、每桶一次往返；而库存那一行是按券的，所以事务按券分组。
  - **事务边界是「一个券组」**，不是「一批」。一批里有两张券就是两个事务，一个组退化不影响另一个组。
  - **收尾之后的两件对外的事都不在关键路径上**：关单的延迟定时消息是异步发的，通知是整批一次管道发出去的——同步发会在消费线程上每单多一次 Broker 往返，那正是把数据库批量化之后剩下的那块开销。
- **效果**：M4 里程碑 156.3 → 319.1 单/s（最好一轮 945.2）；同一版本把批大小关成 1（`1:16`）是 168.7 单/s，和基线同档——**这一行是证明提速只来自批量的对照组**。M6 补上消费参数之后里程碑中位是 982.7 → 2088.9 单/s。

**可能的追问**：→ Q2.7（为什么不用框架的批量）；→ Q2.8；→「为什么不做部分确认？」（`setAckIndex` 只能确认一个前缀，而一批里的完成情况是乱序的）

**别踩**：别把「批量」说成「攒够 N 条再提交」——本项目**没有自己攒批**，批是 Broker 一次投递给消费者的那一批，大小由拉取间隔和到达节奏决定（这正是 Q2.9 的坑）。说成自己攒批，下一问就露馅。

### Q2.7 rocketmq-spring 不是有 consumeMessageBatchMaxSize 吗，为什么要自己持有消费者？  〔坑｜追问链：为什么不用注解 → 那个参数不是能批量吗 → 你怎么发现的 → 自己持有多了哪些事要管〕

**答**：因为 `rocketmq-spring` 的监听容器拿到一批之后是**逐条**喂给 `RocketMQListener` 的。那个参数只决定「一次 consume 调用取几条消息」，但容器在里面开了个 for 循环，所以不管调多大，业务代码看到的永远是一条，没有任何一段工作真的变成批量。要拿到整批，只能自己建 `DefaultMQPushConsumer`、注册 `MessageListenerConcurrently`，把整个 `List<MessageExt>` 交给批处理器。

**展开**：
- 这是 M4 执行时才发现的计划偏差——计划里原本写的就是「调大 `consumeMessageBatchMaxSize`」，读了容器的实现才发现不成立，记在 ADR 0005 决策 1 和计划第 5 节的「M4 执行时发现的计划偏差」里。
- **自己持有之后多管的几件事**（都在启动参数里）：
  - `pullBatchSize` 必须 ≥ `consumeMessageBatchMaxSize`，否则批永远填不满——代码里是 `Math.max(pullBatchSize, batchSize)` 兜着；
  - 消费线程数要 ≤ 数据库连接池，否则消费线程会在等连接；
  - **没有位点时从最早的位点开始消费**，而不是默认的最新位点。全新部署如果在主题还没建出来时就接了单，默认行为会跳过最早那几条；已有位点仍然以位点为准。
  - 消息体解析不了的占位成 null 带下去，由批处理器计数并**直接丢弃**——重投只会让它更晚进死信队列。
  - 老的 `@RocketMQMessageListener` 开关对它无效，换成了 `local-deals.seckill.consume.enabled`，测试 profile 默认关闭（缓存的 ApplicationContext 不该去和真实 Broker 抢消息）。

**可能的追问**：→ Q2.10（这些参数怎么定的）；→「那批量消费的顺序性呢？」（并发消费，本来就不保证顺序，业务上也不需要——每条消息是独立的一单）

**别踩**：别把这条说成「框架有 bug」。它不是 bug，是 `RocketMQListener` 的接口签名本来就是单条的；容器只能逐条喂。说成 bug 会显得没读代码。

### Q2.8 批量插入用 INSERT IGNORE，它不告诉你忽略了哪几行，扣库存的数量怎么算准？  〔坑｜追问链：批量插入怎么写的 → IGNORE 会吞掉什么 → n 不准会怎样 → 那你怎么办〕

**答**：算不准就**不算**。代码里比较实际插入行数和组内消息数，不相等就抛退化异常、**整组回滚**，再用保留下来的单条路径逐条重放。因为 `IGNORE` 只告诉你插了几行、不告诉你是哪几行被忽略，而下一步 `stock = stock - n` 必须用精确的 n——n 多扣一个就是少卖一张，少扣一个就是超卖。

**展开**：
- 两个触发条件在代码里是**分开计数**的（`consume_degraded{reason=insert_skipped|stock_short}`）：
  - `insert_skipped`：重投撞上了已存在的行，或者券 / 店铺的行不见了（按券读快照时就发现券为 null 也走这一条）；
  - `stock_short`：`stock = stock - n WHERE stock >= n` 影响行数不是 1，也就是数据库里剩的量撑不住这一批。
- **`stock >= n` 这个条件更新是超卖的最后一道闸**：复制空窗演练里 Redis 因为主节点故障多放了人，第二轮有 337 次批次走到数据库被它拒绝，四轮超卖恒为 0。
- 退化路径本身是 M2/M3 时期的老实现，分类、补偿、挂起券的规则一条没改，只是不再是默认路径（详见笔记 05 第三节 3.2）。
- **代价写在 ADR 0005 的「代价与边界」里**：整组回滚再逐条重放，重投多的场景下这条路径明显更慢，换来的是 n 一定正确。正常秒杀里被忽略的行只来自重投，占比极低——M6 扫描七份指标快照里 `stage=persisted` 与 `stage=delivered` 的 count、sum 完全相等，两个退化计数器全部为 0。

**可能的追问**：→ Q2.5；→「为什么不用 `ON DUPLICATE KEY UPDATE` 或者逐行判断返回值？」；→「为什么不先 SELECT 一遍看哪些已存在？」（多一次跨分片查询，而且仍然有并发窗口，不如让唯一键判定）

**别踩**：别说「`INSERT IGNORE` 保证幂等所以没问题」。`IGNORE` 只解决「不报错」，不解决「数量对不对」，本题问的恰恰是后者。另外别把退化说成「异常路径无所谓」——它是正确性的一部分，而且它的计数器是判断落库侧健康的一个指标。

### Q2.9 批量落库上线后只翻了一倍、离目标 3000 单/s 差很远，你是怎么定位真正原因的？  〔坑｜追问链：达标了吗 → 为什么没达标 → 你当时的推断是什么 → 后来被推翻了吗〕

**答**：没达标，M4 的验收目标是 ≥3000 单/s，实测中位 319.1 单/s（三轮里最好的一轮 945.2），参数扫描里最好的那个组合是 1056.2——我把「未达成」原样写在 ADR 的状态栏里了。定位过程分两步：先把落库采样拆成每秒速率，发现吞吐 ≈ 提交速率 × 实际批大小；再补上批大小指标，测到实际批大小只有 **1.03**——批根本没攒起来，「一次消费最多多少条」是上界不是目标。

**展开**：
- **第一步（M4）**：三个版本的每秒速率只出现三种状态：约 80 单/s、约 450 单/s、2000–9200 单/s。关掉批量的 `1:16` 整轮稳在 81 单/s，基线 p50 是 84 单/s，于是结论是「一次『插入 + 扣库存』提交的速率上限约 80 次/s」，而批量峰值 ≈ 80 × 30–110。**批量没有让提交更快，只是让一次提交带走整批。**
- **第二步（M6 开头补仪表）**：当时「批为什么攒不满」只有推断没有证据——指标里没有批大小的分布、压测脚本不归档 actuator 快照、`app.log` 每次启动被覆盖。M6 先补了三件事（批大小 `DistributionSummary` 分 delivered/persisted 两个 stage、退化计数分原因、脚本按阶段归档），然后才量：落库阶段 2904 批 / 3000 单，**均值 1.03**，最大 4；`persisted` 与 `delivered` 完全相等、退化为 0——**分组没有损耗，批本身就没攒起来**。
- **成因**：16 个消费线程 × 一次提交约 12 ms ≈ 1300 次/s 的处理能力，而到达速率是 1000–2000/s。消费者本来就跟得上，队列里永远没有第二条消息在等，RocketMQ 自然一次只交一条。反证也有：同一份代码在 Redis 宕机轮里批大小立刻到最大值 32——**积压一形成，批就满了**。
- **后来有一句推断被自己推翻了**：M6 的 ADR 原本写「慢档是因为批里只有一两条」，扫描结果是慢档和快档的批大小都在 1.2 左右，**翻转的是提交速率（约 400 → 约 80 次/s）**，为什么翻转，这次的仪表答不出来。这条更正我留在 ADR 0007 里没有删。
- 注意口径：1.03 这个数来自 M5 的**冒烟**，冒烟只用于定位瓶颈方向、不作吞吐结论；2 万单的正式扫描里这个结论重新验过一遍（第 2 条）。

**可能的追问**：→ Q2.10（那后来怎么把批填满的）；→ Q2.14（积压反而让批变大，那是不是积压更好）；→「3000 这个目标现在达到了吗？」（单实例没有：M8 三实例中位 3026 单/s，但那是三倍 CPU 换来的，见 Q2.14）

**别踩**：这题最容易说大。千万别把「最好一轮 945.2 / 扫描最优 1056.2」拿出来当成绩报——要先说中位 319、目标未达成，再讲定位过程。**这一题的价值就在于承认没达标**；一旦包装，后面所有数字都不可信了。另外别把 1.03 说成「正式压测结论」，它是冒烟里量到的方向。

### Q2.10 消费参数（拉取间隔 / 线程数 / 批大小）是怎么定的？为什么线程从 16 加到 32 反而更慢？  〔坑｜追问链：默认值怎么来的 → 每个旋钮各自的证据 → 线程加了为什么更慢 → 你敢不敢只改一个旋钮〕

**答**：跑了一轮参数扫描，最后 `batch-size=256 / thread-count=4 / pull-interval=50ms / pull-batch-size=256` **四个旋钮整组进默认值**，因为只有这一整组被完整测过。有干净单旋钮证据的只有拉取间隔：同一轮里批大小 2.16（0 ms）→ 12.68（50 ms），换成这组参数后 2001.5 单/s、负载停止后 0.1 s 排空。线程数方向对但落在噪声带里，批大小和拉取批大小实测**从未被触到**。

**展开**：
- **线程从 16 到 32 更慢**：M4 量到 16 线程 860–904 单/s、32 线程 319–337 单/s，当时的解释是「多开的线程只是更多人去抢同一行的行锁」。这个解释方向我现在仍然认，但要加一句限定——M6 的扫描做了一次**精度校准**：同一个 jar、同一组参数、相隔两分钟的两轮，吞吐差 2.18 倍而批大小只差 0.5%，所以**这台机器上小于约 2.2 倍的单轮差异读不出结论**。16 vs 32 的差是 2.7 倍，刚好越过这条线，所以我说「方向可信、不是精确结论」。最终的默认线程数是 4，比 M4 的 16 更少。
- **为什么不拆出「只改拉取间隔」的组合**：那会得到一个从来没跑过的配置。参数组合之间不可加，交付一个没跑过的默认值是给自己埋雷。
- **50 ms 是一笔明确的交易**：每条订单多等最多一个拉取间隔才落库，买到的是批大小和排空时间（同一轮里排空 11.6 / 30.7 s → 0.1 s）。准入端没被波及：赢的那一轮 HTTP p99 21.7 ms、max 62.3 ms，和其余各轮同档。
- **这个间隔有个必须守住的约束**：它必须远小于对账器的过期判定窗口（2 分钟对 50 ms 有三个数量级余量）。把拉取间隔调到上限 1000 ms 时要重新看这一条。
- **256 是一个够不着的上界**：实测交付的批从未超过 32，真正封顶的是 Broker 侧的一个更小的值，而且我**没有去读 Broker 的运行配置**。如果将来那个上界被抬高，一次事务会带走多达 256 单、在热点行上持锁更久，那时要重新量而不是假定更大的批一定更好。

**可能的追问**：→ Q2.9；→ Q2.15（50 ms 对用户可见时间的影响）；→「那 2001.5 单/s 是上限吗？」（不是，是下限——排空 0.1 s 说明负载停止时已经落完，这个数等于场景的发压速率 2000 req/s，**本场景测不出高于 2000 单/s 的东西**）

**别踩**：最容易踩的是把参数扫描的每一行都当成结论。要主动把噪声带说出来（2.2 倍以内读不出），并且明确哪几个旋钮**没有**独立证据。另外别说「2001.5 单/s 是我调优后的性能」——那是压测场景的发压上限，不是系统上限。

### Q2.11 认领租约是干什么的？消费者领了批次就崩了怎么办？  〔常见｜追问链：批量落库时对账器会不会来捣乱 → 怎么互斥 → 为什么不用分布式锁 → 崩了怎么办〕

**答**：认领租约就是「这一批我正在落库」这件事的表达方式。实现上**没有新增状态值**，而是在原来的订单状态哈希上加了两个字段——认领者令牌和认领到期时间，租约默认 30 秒。对账器读的是同样两个字段，看见别人的租约没过期就直接返回「不到期」，**所以不可能在消费者落库过程中把同一单补偿掉**。消费者崩了，租约自然过期，对账器或另一个实例照常接手。

**展开**：
- **为什么不用分布式锁**：M4 之前每条消息要取一把 Redisson 锁，至少两次额外往返。火焰图里它只占 0.2%——**不是瓶颈**，但每条消息都要白花这两次往返。改成状态哈希上的两个字段之后，认领和落库共用同一次 Redis 往返，而且和对账器读的是同一套字段，语义一致。对账器自己的调度锁保留了，因为它只作用在少量到期订单上。
- **对外契约不变**：对外状态仍然是「处理中」，查询接口、DTO、前端轮询都没动。这一点计划里没写，是实现时的取舍。
- **可重入**：认领者令牌是**每个 JVM 一个**的随机串，所以同一个进程重投自己的批次时是直接续租，不会被自己挡住；而进程崩掉之后，它的令牌不会再出现，租约只会自然过期。
- **两个 ZADD 修饰是这里最容易被追到底的细节**：推后到期分数时用了 `XX`（只更新已存在的成员，一条迟到的认领不会把已经收尾的订单重新放回到期索引）和 `GT`（只允许把分数改大，一个比 2 分钟判定窗口短的 30 秒租约不会把到期时间往前拉、给对账器送去一堆它只能拒绝的订单）。
- **崩溃的代价是明确的**：ADR 0005 的边界里写着——消费者崩溃后，它认领过的那一批要等 30 秒租约过期才会被接手。重投可能落到别的实例上，新实例也要等这 30 秒才能认领成功。这是崩溃恢复的延迟代价。

**可能的追问**：→ Q2.12（对账器怎么看这两个字段）；→ Q2.13；→「租约到期但消费者其实还活着（GC 停顿）怎么办？」（会出现对账器和消费者同时动一单——但两边最终都要过数据库的主键和 `stock >= n`，不会超卖；这属于我承认的一个窗口，不是被证明不可能的）

**别踩**：别把认领租约说成「分布式锁」。它没有 fencing token、没有严格互斥保证，只是一个**协作性的意向标记**；真正的正确性仍然由数据库的唯一键和条件更新保证。说成锁，上面那个 GC 停顿的追问就没法答。

### Q2.12 对账器多久扫一次？怎么判断一条预占卡住了？重驱动和补偿分别在什么条件下走？  〔高频｜追问链：谁来兜底 → 多久一次 → 怎么判定卡住 → 什么时候敢还库存〕

**答**：启动 30 秒后开始，每轮结束 10 秒后再跑一轮，一轮最多 100 单。判定「卡住」看的是处理中索引里的分数：准入写进去时分数是「现在 + 2 分钟」，分数 ≤ Redis 服务器时间就算到期。到期之后先认领、再**拿着这一单去问写库**，按数据库的事实分四种答案处理——完全一致就修成成功；订单不存在且年龄 < 15 分钟就**重发消息**；到了 15 分钟硬期限且补偿开关打开才补偿；数据库里另有一单冲突则先挂起券再补偿。

**展开**：
- 完整的一轮详见笔记 05 第三节 3.3。口述时我会强调三处：
  - **只读不删**：取到期列表时不从索引里删，自己中途崩了证据还在。
  - **先锁再读属主字段**：每一单先取一把这一单的调度锁，拿不到就让给别人；赢的那个实例在这一单上是唯一负责人。
  - **fail-closed 是贯穿的**：扫描失败整轮跳过；问写库失败什么都不做（在不知道数据库事实的情况下补偿等于凭空还库存）；单个订单出异常不影响这一轮剩下的。
- **补偿开关是独立于对账器开关的**：`compensation-enabled` 关着时对账器照常跑、照常重驱动，只是**绝不还库存**，只记告警。线上出事时这是我最想有的那个开关。
- **认领时会 `PERSIST` 状态哈希**，免得证据被 7 天留存 TTL 抹掉；同时把尝试次数加一，供人判断这一单被看过几次。
- **需要人介入的三类**（归属不符、预占不符、字段损坏）一律不自动处理：延后 1 分钟、计数、打错误日志，让它在到期列表和日志里反复出现直到有人修。字段损坏时连桶都还能从订单号的基因里还原出来，但没有可信的用户 id 和券 id 就拼不出认领脚本要校验的那份精确归属，任何自动动作都是瞎猜。
- **已知边界**：对账器的重驱动**没有批量化**，仍是每 10 秒最多 100 单。所以 M4 的「先杀 Broker」演练收敛 574.2 → 572.1 s，批量落库一点没帮上忙——这是 ADR 0005 里预告过、复测里被证实的一条。

**可能的追问**：→ Q2.13；→ Q2.11；→「100 单 / 10 秒够吗？」（10 单/s 的重驱动速率，面对几千条积压就是几分钟——这正是「先杀 Broker」572 s 的来源，批量重驱动是没做的事）

**别踩**：别说「对账器保证最终一致」就收。要说清楚**它凭什么敢动**——凭的是「问写库」这一步；任何一个动作的前提都是数据库给了确定的答案。以及别忘了说 15 分钟硬期限之前**只重发不补偿**，很多人这里会说成「超时就还库存」，那是会错还的。

### Q2.13 进程被 kill -9，多久能收敛？你演练过吗，数字是多少？  〔高频｜追问链：演练过吗 → 杀在哪个位置 → 判据是什么 → 数字多少 → 为什么不同场景差这么多〕

**答**：演练过，是压测脚本里固定的场景。判据是三条同时成立：预占数 = 订单数、Redis 库存 = 数据库库存、没有残留的处理中状态。数字：`kill -9` 场景批量消费上线前后是 **102.8 → 44.7 s**；「先杀 Broker」场景是 574.2 → 572.1 s（没有改善）；复制空窗那四轮是 **150–308 s**。

**展开**：
- **杀在链路的不同位置靠的机制不同**（详见笔记 05 第三节 3.4），面试时我按三段说：
  - 写完预占、还没发消息就死 → 消息根本不存在，但处理中索引里有它，两分钟后对账器扫到、问写库发现订单不存在、年龄没到 15 分钟 → **重发消息**。这就是「预占即发件箱」的含义。
  - 认领之后、插入之前死 → 数据库什么都没写，消息没确认，Broker 重投；新实例要等 30 秒租约过期才能认领成功。
  - 插入提交了、收尾之前死 → 订单已在库里，Redis 还是处理中。消息重投 → 认领通过 → 多值插入影响行数 0 ≠ 组内条数 → 整组退化 → 单条撞主键冲突 → 回查是同一个人同一张券 → 判重放、**不再扣库存** → 置成功。就算消息彻底丢了，对账器也会走到同一个结果（写库答「完全一致」，直接修成成功）。
- **为什么「先杀 Broker」慢十几倍**：那个场景积压的是**几千条没有消息的预占**，只能靠对账器一条条重驱动，而重驱动是每 10 秒 100 单、没有批量化。`kill -9` 场景积压的多数是 Broker 里还在的消息，重投是批量的。这两个数字不是同一件事，不能混着说。
- **复制空窗的 150–308 s** 是最慢的一档，因为那一轮同时要收敛「丢失预占的消息进死信」和「复活的库存被重新卖掉的批次被拒」两条路径。

**可能的追问**：→ Q2.12；→ Q2.11（30 秒租约）；→「44.7 s 里哪一段最长？」（这个我没有拆到段，只有端到端的收敛时间——拆段需要每一步的时间戳埋点，没做）

**别踩**：别拿 44.7 s 这一个数去代表「所有故障的收敛时间」。三个场景的数字差一个数量级，混用是最容易被抓的。也别说「收敛时间是我优化出来的」——44.7 s 是批量消费的副产品，而 572 s 那个**根本没改善**，这一点要一起说。

### Q2.14 消息积压了怎么办？你怎么观测积压？  〔高频｜追问链：怎么知道积压了 → 积压了怎么处理 → 加实例行不行 → 加了为什么没用〕

**答**：观测上做了两件事：**采样器**按 30 秒一轮把「处理中索引里的待办数和最老一条超期多久」写成仪表（各桶之和 / 各桶最大值），以及消费侧的批大小指标（分 delivered / persisted 两个 stage）和退化计数。处理上，这个项目的形态比较特殊——**积压本身会让批变大、吞吐自动上去**，所以轻度积压是自愈的；但重度积压我**没有**自动扩容手段，而且实测**加实例不管用**。

**展开**：
- **积压怎么被看见**：采样器每个桶跑一个只读 Lua，第一件事是取 **Redis 服务端时间**而不是应用传进来的时间戳（多实例时钟不一定一致，用服务端时间才能让「到期」这个判断在所有采样者眼里是同一个基准），然后一次区间计数得出已到期的预占数、再取分数最小的成员算出最老一条超期多久。失败时**把仪表置成 NaN 并给失败计数加一**，而不是保留上一轮的值——保留旧值会让一个已经瞎了的仪表看起来一切正常。
- **积压自愈的证据**：M5 冒烟里 Redis 宕机轮的批大小立刻到最大值 32（平均 1.27），而正常轮只有 1.03。同一个机制被看到两次。M6 换参数之后，里程碑记的负载停止时的积压是 10.7 / 55.8 / 16.1 s → **0.1 / 0.1 / 0.1 s**。
- **加实例实测不管用**：M8 量过 1 / 2 / 3 实例的落库中位是 2415 / 2435 / 3026 单/s，应用 CPU 1.41 → 2.7 → 4.0 核，而 **MySQL 只用了 0.24 核**。折算的提交次数/s 在 70–115 之间且**与实例数没有关系**——瓶颈是每批都要更新的同一行券库存，行锁不因为多了两个进程而变快。所以「积压了就加消费者」这个标准答案在这个项目里是**被实测否定**的。
- **本项目没做、业界会怎么做**：
  - **Broker 侧的 consumer lag 监控和告警**——没做。我的积压观测看的是「处理中索引」，那是业务侧的积压，不是 Broker 队列的堆积深度；两者形状相近但不是一个东西。要做就是抓 broker 的 `diff` 指标进监控，代价只是一套采集。
  - **告警**——没做。仪表存在，但没有任何阈值会主动通知人，NaN 也只是一个值，没人盯就没人知道。
  - **积压时临时扩队列 + 转发消费**（经典做法：新建一个多队列的主题，用一个只做转发的消费者把积压打散）——没做，而且在这个项目里**做了也没用**，因为瓶颈不在消费并发度而在那一行。
  - **真正有数据支撑的下一步是拆那一行**（按券分桶扣减 + 定期合并，或把库存从 MySQL 移走）。M6 当时写下的回归条件是「到达速率远高于 2000/s、负载后排空重新大于 0、提交速率封顶」，M8 那一轮三条**同时成立**了，所以拆行的收益从推断变成了可预期的。设计尚未定稿，前提是消费批次尽量来自同一个桶，否则一个事务要持有 K 把行锁，竞争更糟。

**可能的追问**：→ Q2.9；→ Q2.10；→「那你线上怎么发现积压？」（老实说：靠人看指标端点，没有告警——这是已知的缺口）

**别踩**：别背「积压了就加机器 / 加线程 / 扩队列」这套标准答案。这题在本项目里的正确回答恰恰是**这套办法不管用，并且我有数字**。这是最容易和别人拉开差距的一题，用标准答案反而浪费了。

### Q2.15 用户抢到了但订单还没落库，他去查订单查不到怎么办？落库要多久？  〔高频｜追问链：异步之后用户看到什么 → 查订单查不到怎么办 → 要等多久 → 等不及走了怎么办〕

**答**：查得到。准入成功时返回的是订单号，订单状态查询接口**先读 Redis 里的预占状态**——处理中就明确告诉他「抢到了，正在生成订单」，成功就返回库里的订单，失败就返回失败原因。落库的可见时间实测是中位 **5.2 s、p99 15.7 s、最大 16.0 s**（M8 全链路场景）。

**展开**：
- **查询接口做了两件额外的事**（代码里能看到）：
  - 先校验归属，`userId` 对不上直接答「订单不存在或无权查看」，不泄露别人的订单；
  - 状态是处理中时**再去数据库查一次**，如果订单其实已经落库了（收尾还没跑到 / 收尾丢了），就**顺手把 Redis 状态修成成功**（best-effort）再返回数据库的状态。这条是一个「读路径上的顺手对账」。
  - Redis 查不到或者查失败时，会退回到直接查数据库。
- **5.2 s 这个数要拆开看**：它不全是消费延迟。全链路场景里是 2 万单在很短时间内灌入，中位 5.2 s 里包含排队时间；正常流量下一条消息的延迟主要是一个拉取间隔（50 ms）加一次批事务。**这一点我会主动说清楚，因为 5.2 s 听起来比实际难看。**
- **有人等不及**：全链路场景里 **214 个赢家在 30 s 内没等到订单可见就放弃了付款**。他们的订单**都落了库**——那是压测脚本模拟买家耐心的上限，不是丢单。这个数我留在报告里没删，因为它说明「落库可见时间」是一个真实的产品问题，不只是技术指标。
- **本项目没做、业界会怎么做**：下单成功时**直接把订单摘要写进 Redis 预占里返回给前端**（金额、券名、支付截止时间），让「待支付页」根本不依赖数据库；或者走 WebSocket / 长轮询推送落库完成事件（项目里通知有了，但它是**尽力而为**的——管道发布失败只记日志，权威来源仍然是这个查询接口）。代价是预占的体积变大、以及要维护两份订单摘要的一致性。

**可能的追问**：→ Q2.10（50 ms 拉取间隔对这个数的影响）；→ Q2.4（要是订单永远落不了库呢 → 15 分钟硬期限后补偿，状态会变成失败并写明原因）；→「为什么不同步返回订单？」→ Q2.1

**别踩**：别说「用户轮询几次就有了」。要说清楚**中间态是有明确语义的**——处理中不是「查不到」，是一个正经状态。另外别把 5.2 s 说成「落库耗时」，它是**灌满 2 万单的场景下的可见时间**，两者不是一回事；含糊其辞会被追问到下不来台。
