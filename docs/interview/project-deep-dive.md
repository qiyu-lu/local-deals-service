## 0. 开场

### Q0.1 三分钟介绍一下这个项目  〔高频｜追问链：介绍 → 你负责哪部分 → 最难的地方 → 数字哪来的〕

**答**：这是一个本地生活的商户券营销与交易平台，闭环是商户建活动、用户抢或领或买、券进到用户资产、到店核销、最后退款或过期。技术上最难的一段是秒杀：一瞬间十万人抢一千件，99% 的请求注定失败，所以整个设计就围绕两件事——让注定失败的请求尽早、尽便宜地死掉，让抢到的那一小部分可靠地落到账上。我可以按准入、落库、可靠性、没做的四段讲。

**展开**：

三分钟版（成段，照着说）——

> 这是一个本地生活的商户券营销与交易平台，业务闭环是商户建活动、用户抢或领或买、券进到用户的资产里、到店核销、最后要么退款要么过期。五个发券来源——秒杀购买、用户领取、后台发放、签到奖励、批量发放——最后都落成同一种券资产，核销、过期、退款只操作这一张表。技术上最难的一段是秒杀，一瞬间十万人抢一千件，百分之九十九的请求注定失败，但每一个都得被处理，所以设计就是围绕「让注定失败的尽早尽便宜地死掉」和「让抢到的可靠落账」这两件事展开的。
>
> 先说准入这一半。一个下单请求进来，最外面是入口代理，进到应用里是三层漏斗。第一层是进程内的售罄标记，命中就直接回「没了」，一次网络请求都不发；这个标记是准入脚本返回售罄的时候置上的，再通过发布订阅广播给其他实例，库存被归还的时候清掉。第二层是本地令牌桶，按这张券在本实例分到的剩余库存定速，把明显超出的量挡在进程内。第三层才真正碰缓存，用一个脚本一次做完五件事：限频、活动在不在卖、这个人是不是买过、扣库存、写预占。之所以必须合成一个脚本，是因为「检查」和「扣减」之间不能被另一个并发请求插进去。订单号是本地发的雪花号，不依赖缓存，低位嵌了用户 id 的基因，后面分库分表要用。最关键的一句是：只有这一步成功的人才会发一条消息。改造前是每个请求都先发一条事务半消息，所以 99% 的请求都在打 Broker，Broker 先被打垮；改完之后半消息从「等于请求数」变成零，十千档的应用 CPU 从三点零四核降到零点六核，准入拐点从五千抬到两万。
>
> 再说落库这一半。抢到的人只是在缓存里有一条预占，订单还没建。消费者是自己写的批量消费者，拿到一批消息之后分三步：先按桶一次往返把这批认领下来，带一个三十秒的租约，这样别的实例和对账器不会同时处理它们；然后按券分组，一个事务里做一次多值插入加一次条件扣减，插入用忽略重复的写法所以重复消费不会重复建单，扣减带着「库存大于等于本批数量」的条件，这是最后一道防线；最后再按桶一次往返把状态置成功、清掉认领、移出到期索引。整批要么一起确认要么一起重投，不做部分确认，因为幂等已经保证了重投是安全的。这么改之后落库从一百五十几涨到单实例中位两千零八十八，三实例三千零二十六。中间有个插曲很值得讲：一开始只是改成批量提交，吞吐翻倍但离目标还远，补上仪表才发现批大小实测只有一点零三——消费线程本来就跟得上，队列里根本没有第二条消息在等，所谓批量一直没真的生效。后来把拉取间隔调上去把批攒起来，批大小才从二点一六变成十二点六八。
>
> 可靠性这块我做了三次故障演练。应用直接 kill -9，收敛时间从一百零二点八秒降到四十四点七秒；缓存主节点宕机两次，丢失预占零、超卖零，代价是大约一点二六万个 503；最有意思的是第三次，我故意制造了一个复制空窗——先让从节点睡着、再从主节点上切断复制链路，让主节点在这个窗口里继续接单然后杀掉它，这样才真的把最后一道防线逼出来。结果是缓存最多多放了百分之十点三的人，但数据库每一轮都恰好建了三万单、超卖恒为零，收敛靠对账器，需要一百五十到三百零八秒。这也是我敢说「缓存是可丢的准入层、数据库的条件更新才是最后防线」的底气——不是设计文档上这么写的，是演练逼出来的。
>
> 最后说没做的。写路径的水平扩展上限是秒杀库存的那一行：三个实例烧掉三倍 CPU 只多落了约百分之二十五的单，提交次数每秒七十到一百一十五，和实例数没有关系。这一行我明确没有拆，测实了、知道怎么拆、写了回归条件。准入侧的扩展曲线在这台机器上测不出来，因为压测客户端自己先满了，所以我不会说「水平扩展提升了准入吞吐」。支付是 mock 渠道，多机房、消息多副本切换、数据库主从切换都没做。

一分钟精简版（时间紧或面试官打断时用）——

> 本地生活的券营销与交易平台，核心是秒杀到核销这条闭环。难点是一瞬间人远多于货，所以请求分三层拦：进程内的售罄标记、本地令牌桶，最后才是一次缓存脚本把限频、判重、扣库存、写预占一次做完，只有成功的人才发消息。抢到之后不是同步建单，而是批量消费者一批一个事务，插入用忽略重复保证幂等，扣减带条件所以超卖不可能发生，崩了有对账器重驱动。结果是准入拐点五千到两万、半消息从等于请求数变成零、落库从一百五十几到两千多。做了三次故障演练，复制空窗那次把最后一道防线真的逼了出来：缓存多放了百分之十的人，数据库一单都没多建。写路径的上限是库存那一行，我测实了但没拆，原因可以展开讲。

节奏建议：准入 50 秒、落库 50 秒、演练 40 秒、边界 20 秒。最后那句「没做的」一定要自己说出来，它换来的是面试官的信任，而且会把话题引到我准备最充分的区域。

**可能的追问**：→ Q0.2（是不是教程）；→ Q0.3（最大难点）；→ Q0.5（数字哪来的）；→ 笔记 04 的三层漏斗、笔记 05 的批量落库与对账器、笔记 12 的三次演练。

**别踩**：
- 不要把「缓存保证不超卖」说出口——本项目结论恰恰相反：缓存是允许丢的准入层，数据库那条带 `stock >= n` 的条件更新才是最后防线，复制空窗演练里缓存确实多放了 10.3% 的人。
- 不要在开场报一串数字。只报四个：拐点 5k→20k、半消息→0、落库 156.3→2088.9、复制空窗超卖恒为 0。其余等被问。
- 不要说「支撑万级并发」然后停住。要带上口径：单机 16C/30G、k6 开环、拐点定义是 p99 < 100 ms 且丢弃 < 1%。
- 不要把业务定位说成「点评 App 的后端」。这是券的营销与交易平台，券是中心概念；说成点评会被问去查探店笔记那条链，那不是强项。

### Q0.2 你这个是不是黑马点评？和教程版比你改了什么？  〔高频｜追问链：是不是教程 → 改了什么 → 为什么要改 → 不改会出什么问题 → 改完怎么证明有效〕

**答**：业务原型确实来自黑马点评，这一点我写在仓库 README 的最后一行，不藏。但现在跑的是我重写过的版本：教程版是「一次 Lua 判库存和一人一单 + 阻塞队列/消息异步下单 + 分布式锁」，我改的是三件事——把 99% 注定失败的请求拦在发消息之前、把落库从每单一次提交改成每批一次提交、把「超卖不可能」这句话的责任从缓存挪到数据库的条件更新上。每一件我都有改造前后同场对照的数字和一次故障演练。

**展开**：

- **定位差异**：教程是「点评 App」，我把它重新定位成本地生活的商户券营销与交易平台，补出了教程没有的下半场——订单状态机、支付与退款、券资产与核销、过期，以及商户后台的 RBAC 与数据隔离。教程版是「建单即成交」，没有订单生命周期；迁移旧数据时那 14.2 万单是当成 `PAID` 并补券迁过来的。
- **改动一：漏斗放在发消息之前（为什么要改）**。教程版和我的 M0 基线一样，每个请求不管成不成都要跟消息中间件打一次交道——基线里是每个请求一条事务半消息。不改的后果是量出来的：15k 档 Broker 先流控，火焰图里 44.7% 花在库存那一行的行锁上、49.5% 在连接池等待。改完的证据：半消息从「等于请求数」变成 0，10k 档应用 CPU 3.04 核 → 0.60 核，拐点 5k → 20k req/s（p99 83 ms），天花板 13.2k → ≥26.2k。
- **改动二：批量落库**。教程是一条消息建一个单、一次提交。我改成自建批量消费者：认领（带 30 秒租约）→ 按券分组、一个事务里一次多值插入加一次条件扣减 → 收尾。落库单实例中位从 156.3 涨到 2088.9 单/s，负载停止后的积压从 10.7 / 55.8 / 16.1 秒降到 0.1 / 0.1 / 0.1 秒。
- **改动三：防线换位置**。教程里超卖的责任在 Redis 的 Lua 上。我把它挪到数据库：`UPDATE tb_seckill_voucher SET stock = stock - n WHERE voucher_id = ? AND stock >= n`，影响 0 行就整批回滚、退化为逐条重放。这不是设计洁癖，是复制空窗演练逼出来的——缓存多放了 10.3% 的人，其中一轮有 337 次被这个条件更新拒批，数据库每轮仍然恰好建 30000 单、超卖恒为 0。
- **关于分布式锁**：教程用 Redisson 锁做一人一单，我这里判重是准入脚本里的一步，数据库上还有一条限购唯一键兜底（`uk(user_id, voucher_id, active_flag)`，关单和退款后生成列为 NULL，所以可以再买）。顺带说一个反直觉的数据：M0 火焰图里 Redisson 锁只占 0.2%——所以「去掉锁提升了多少性能」这种话我不会说，真正的开销在热点行锁和连接池等待。
- **还补了教程没有的几块**：订单分 2 库 × 4 表并用基因法让按订单号查和按用户查同片、Redis Cluster 与库存分桶、traceId 从入口代理到数据库、批大小/积压/提交速率的仪表，以及三次故障演练。

**可能的追问**：→ Q0.3（最大难点）；→ Q0.5（数字怎么来的）；→ 「为什么不直接用 Redisson 锁就够了」（去笔记 04 准入脚本 + 笔记 06 限购唯一键）；→ 「异步下单用户查不到订单怎么办」（去笔记 05；全链路里落库可见中位 5.2 s、p99 15.7 s，压测脚本里有 214 个买家在 30 s 内没等到就放弃付款，但他们的订单都落了库）。

**别踩**：
- 别否认出身。说「不是黑马点评」而 README 里写着「业务原型源自黑马点评教程」，一旦被对照代码仓库就全盘失信。正确说法是「原型是它，跑的东西是我重写的，差异我能逐条给数字」。
- 别说「我去掉了分布式锁所以快了」——本项目的火焰图证据是锁只占 0.2%。
- 别把「事务消息换成普通消息」说成「保证了消息不丢」。换掉半消息省的是 99% 无效请求对 Broker 的压力；不丢单靠的是预占 + 对账器 + 幂等插入，不是消息本身。
- 别说改动三是「设计时就想到的」。诚实的版本是：M5 我预期主从切换会丢预占、逼出数据库防线，结果实测 RPO = 0 没复现，M8 才靠人为制造复制空窗做到。这段「预期被证伪」本身是加分项。

### Q0.3 这个项目最大的难点是什么？  〔高频｜追问链：难点是什么 → 你当时怎么想的 → 怎么发现想错了 → 最后怎么改 → 改完怎么验收〕

**答**：最大的难点不是写出那套设计，是**证明它在故障下真的成立**。具体那件事是：我一直说「缓存可丢、数据库的条件更新才是最后防线」，但整整一个里程碑我都拿不出证据——因为故障演练做出来的结果是零丢失，那条防线根本没被触发过。最后是靠人为制造一个复制空窗才把它逼出来的。

**展开**：

- **当时的错误假设**：M5 我写在计划里的预期是「Redis 主从切换 → 丢预占 → Redis 超放 → MySQL 条件更新兜底」，三步一条龙，我以为杀个主节点就能看到。
- **怎么证伪**：真杀了两次主节点，结果是丢失预占 0、库存差 0、超卖 0，转移 5.2 / 7.8 秒、恢复 7.3 / 9.4 秒。原因我当时没想到：故障转移期间那些槽位直接不可写，买家收到的是 503 而不是一个假的成功——代价是约 1.26 万个 503（占 42% 的请求），但真实丢失窗口只有不到 1 毫秒的复制延迟。也就是说 RPO ≈ 0，防线压根没机会被触发。这条我在计划里明确记成了「需要改正的预期」，没有粉饰。
- **怎么改**：既然自然故障逼不出来，就人为造一个数据缺口——先让从节点睡着、再从主节点上 `CLIENT KILL TYPE replica` 切断复制链路，让主节点在这个空窗里继续接单，然后杀掉它。这样从节点被提上来时，手里的库存是「空窗开始那一刻」的旧值，缓存必然多放人。
- **结果（两晚四轮）**：Redis 放进 30124 / 33096 / 33104 / 33101 人，最多多放 10.3%；MySQL 每一轮都恰好建 30000 单，超卖恒为 0。多出来的人在两条路径之一被挡下：预占随主节点一起死了，消费者认领时发现状态不在；或者复活的库存被重新卖掉、批次走到数据库才被 `stock >= n` 拒绝（第二轮拒批 337 次）。两条路径通向同一个结果，区别只在于复活的库存有没有在丢失预占的消息被处理之前被抢走。收敛需要 150–308 秒，靠对账器。
- **这件事为什么算「最大难点」**：它是唯一一件「设计说得通、代码写得出、但差点没有证据」的事。而正是这次演练，把「各层职责」从一句口号变成了一条可以在面试里被反复追问的结论。演练与判定口径详见笔记 12 第三节。

**可能的追问**：→ 「那 150–308 秒里用户看到什么」（笔记 05 对账器）；→ 「多放的人最后怎么被通知失败」；→ 「为什么不干脆把库存放数据库同步扣」（笔记 04 第一节的取舍）；→ 「复制空窗是人造的，真实生产会这样吗」（答：会，主从异步复制 + 主节点故障就是这个形状，我只是把窗口放大到可观测）。

**别踩**：
- 别把「难点」答成「高并发」「分布式事务」这种词。这类答案面试官一天听二十遍，而且接下来一定会被追到具体场景。
- 别把复制空窗说成「我们遇到的线上故障」。它是我人为制造的演练，说清楚是人造的反而更有分量。
- 别说「所以缓存挂了也完全没影响」。有影响：两次主节点宕机演练里有约 1.26 万个 503，复制空窗那次收敛要 150–308 秒。代价要一起说。
- 别把「超卖恒为 0」扩大成「任何故障下都不会出错」。同一批次横跨两个订单库时用的是 LOCAL 事务不是 XA，崩在两次提交之间会**少卖**（不会超卖），而且这个窗口**没有做故障注入验证**，这一条目前是推理不是实测。

### Q0.4 最有成就感的一次优化是什么？  〔高频｜追问链：哪一次 → 怎么定位的 → 为什么之前没发现 → 改了什么 → 提升多少 → 代价是什么〕

**答**：把落库从 156.3 单/s 做到单实例中位 2088.9 单/s 的那条线。最有成就感的不是数字本身，是中间那个反转：我改成批量提交之后吞吐只翻了一倍，离目标还很远，补上仪表才发现**批大小实测只有 1.03**——我以为自己做了批量，实际上每一批只有一条消息，「批量」从头到尾没有生效。

**展开**：

- **第一步（改对了方向但没到位）**：把落库从「每单一次提交」改成「每批一次提交」，中位 156.3 → 319.1 单/s（最好轮 945.2），目标 ≥3000 单/s 没达成。同一版本把批量关掉是 168.7 单/s，和基线同档——这证明提速确实只来自批量。同时量到一次提交的上限大约 80 次/s，也就是吞吐 ≈ 80 × 实际批大小。
- **为什么之前没发现**：那时候根本没有批大小这个指标，只有吞吐。我在里程碑收尾时把「批大小分布 + 退化计数」写成了遗留项，并且明确写了一句话：在补上仪表之前，落库吞吐的 A/B 结论一律不可信。
- **第二步（仪表说话）**：补上 `consume.batch.size` 之后一量，均值 1.03。原因很反直觉——消费线程本来就跟得上到达速率，拉取间隔是 0 就一直连续拉，队列里永远没有第二条消息在等。批量消费的前提是「队列里有东西可批」，而我的消费者太勤快了。
- **第三步（单旋钮扫描）**：拉取间隔是这次扫描里唯一有干净单旋钮证据的一项。2000 单/s 下批大小：0 ms → 2.16，10 ms → 3.90，20 ms → 6.53，50 ms → 12.68。换成 `256:4:50ms:256` 这一组后是 2001.5 单/s，而且那是场景发压速率的上限、不是系统的上限。最终单实例中位 2088.9 单/s，负载停止时的积压从 10.7 / 55.8 / 16.1 秒降到 0.1 / 0.1 / 0.1 秒。
- **代价（一定要主动说）**：每单最多多等一个拉取间隔才落库。这是延迟换吞吐，在秒杀这个场景里可以接受，因为用户等的是「抢到了」的回执（准入那一步就有了），不是订单行。另外那四个参数是一起测出来的一组，我是整组上线的，不会单独吹某一个。
- **这条线还给了一个更值钱的副产品**：加实例之后发现提交次数/s 恒在 70–115、与实例数无关，说明上限就是每批都要更新的同一行库存。这一行我**明确没有拆**，见 Q0.1 的边界那段。

**可能的追问**：→ Q0.3；→ 「拉取间隔加大了延迟，用户会不会看不到订单」（笔记 05；全链路可见中位 5.2 s、p99 15.7 s）；→ 「为什么不加消费线程」（M4 实测：16 → 32 线程反而更慢，更多线程抢同一行）；→ 「那一行你打算怎么拆」（按券分桶扣减 + 定期合并，或把库存移出数据库；回归条件写在计划里）。

**别踩**：
- 别说「我把吞吐提升了 13 倍」。要带口径：单机、中位数、156.3 → 2088.9 单/s、这是那台机器上的数。也不要自己乘出「三实例比基线快 N 倍」这种没在报告里出现过的数。
- 别把 2088.9 和 3026 混着说。2088.9 是单实例中位（M6），3026 是三实例中位（M8），而且三实例那条线的结论是「不扩展」，不是「扩展得好」。
- 别隐瞒 ≥3000 单/s 这个目标在单实例上没达成。主动说出来，再解释原因是库存那一行，这比含糊过去强得多。
- 别把「批大小 1.03」轻描淡写成小 bug。它的意义是：**没有仪表的性能结论都是猜的**——这才是这段故事真正的价值。

### Q0.5 这个项目上线了吗？有真实用户吗？没上线的话你的数字哪来的？  〔高频｜诚实题｜追问链：上线没 → 有没有真实用户 → 数字哪来的 → 测试环境和生产差多少 → 这些数能代表生产吗〕

**答**：没有上线，没有真实用户，支付是 mock 渠道，不涉及真实资金、对账文件和风控。所有数字都来自我自己在一台 16C/30G 的机器上用 k6 开环压测跑出来的，每一次运行都有可追溯的结果目录、commit 和参数清单。我的结论是「这是这台机器上的拐点和扩展趋势」，不是「生产容量」——这条我写在 README 的已知边界第一行。

**展开**：

- **怎么保证这些数字不是随手跑出来的**：压测是一条命令的无人值守入口（`scripts/bench.sh <场景>`），结果写进带时间戳的目录，里面有 `status`（`RUNNING` / `DONE` / `FAILED: 阶段: 原因`，不是 DONE 就不分析）和 `manifest.json`（commit、场景参数、分核方式、JVM 参数、机器型号、开跑和收尾时的 loadavg、同时在跑的其他容器）。启动前的 preflight 会拒绝好几类情况（端口被占、磁盘不足、没有 JDK 21、docker 不可用），其中最重要的一条是**工作区有未提交改动就不让跑**——结果必须对得上一个 commit。每个阶段有超时，第一个失败就停下并拆掉自己的栈。
- **为什么是开环不是闭环**：V1 的证据是 JMeter 1000 线程 / 5 秒 ramp-up 得到的 208 req/s，那是发压速率不是系统容量——线程发完一个要等响应才发下一个，系统越慢压力越小，永远测不出拐点。V2 全部用 k6 的 `constant-arrival-rate`，请求按目标速率到达，跟不上就表现为延迟上升和 `dropped_iterations`。「拐点」在报告里固定指 **p99 < 100 ms 且丢弃 < 1% 的最高档**。
- **公平性**：被测系统、依赖、压测客户端按物理核分开绑（不分核就是三方互偷 CPU）；每次测量前以 500 req/s 预热 30 秒且不记入结果；10 万个预生成 token 轮转，所以每个请求是不同用户，首秒售罄、其余 99% 注定失败——这正是秒杀的形态。跨天的数字不直接相减，A/B 一律是同一场次里用上一个 tag 的 jar 和当前 jar 各跑一遍，因为这台机器不同时段快慢能差 10%。
- **配置偏离（我会主动交代）**：压测时把每 IP 限流调到 10 万，因为所有请求来自 127.0.0.1，不调的话 99% 会在最外层 429，测到的只是限流器；每用户限流保持默认。多实例场景下入口代理不开 `limit_req`，同一个理由。
- **这些数能代表生产吗——不能，我说得很清楚**：单机测的是这台机器上的拐点和扩展趋势；「万级」的论证方式是单实例实测值 × 已验证的水平扩展性 + 各层无共享瓶颈的设计说明。而且多实例那条曲线里 Redis Cluster、Broker、两个订单库、入口代理和压测客户端本身都是**共享的**。准入侧的扩展曲线干脆测不出来：1/2/3 实例在 30k 档都是约 25.5k req/s，因为 k6 自己吃满了 3.52–3.58 核，而三个实例加起来只用了 1.26 核——**客户端先满**，任何「水平扩展提升了准入吞吐」的说法都不能从这份数据得出，要量得换多机压测。
- **如果要真的上线，我会怎么补（这部分本项目没做，是方案不是经历）**：本项目没做灰度与容量验证这一套。业界成熟做法是先做影子流量或线上小流量灰度拿到真实请求分布，再用全链路压测（带压测标识、影子表）在生产环境上量容量，同时配好 SLO 与自动回滚。代价是要在每条链路上贯穿压测标识、要一套影子数据隔离、要和上下游约定，工程量比我这套离线压测大一个量级，单人做不完，所以我没做。

**可能的追问**：→ Q0.1（数字总表）；→ 「那你怎么敢写万级并发」（上面第五条，口径要一字不差）；→ 「p99 为什么用 100 ms 做线」；→ 笔记 12 第一节「方法与采信」与第六至九节「动手」。

**别踩**：
- 千万别暗示上线过、别说「线上跑得挺稳」。没有真实用户就是没有；这一题面试官问的就是诚信。
- 别把冒烟运行的数字拿来当结论——报告里明确写了冒烟数字不进正文，我也别在嘴上破这条规矩。
- 别把「25.5k req/s」说成系统能力。那是 k6 的天花板。
- 别忘了交代限流的配置偏离。被面试官自己发现「你把 IP 限流关了」比自己说出来难看得多。
- 别用「测试环境比生产差，所以生产只会更好」这种话圆场。方向不一定：生产有网络、多机房、真实数据分布和邻居噪声，比这台单机的共享依赖更复杂。
