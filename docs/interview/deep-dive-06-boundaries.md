# 深挖问答：没做的与如何扩展

> 《[项目深挖问答](project-deep-dive.md)》的一部分：第 12 节，8 题。
> 事实标准与全书一致：机制来自代码，数字原样抄自 [压测报告](../benchmark-report.md) 或[主计划](../plan/v2-high-concurrency-plan.md)进度表，没做的直接说没做。

## 12. 没做的 / 如果重来 / 如何扩展

> 这一节是整份文档的诚实基准。每一道「没做」的题，先说「本项目没做」，再说「业界会怎么做、代价是什么」。
> 凡是本项目没有实测过的，一律标成推理。

### Q12.1 库存那一行你已经测实了是写路径的上限，为什么没拆？  〔坑｜追问链：你的写路径瓶颈在哪 → 怎么知道是那一行 → 为什么不拆 → 要拆你会怎么拆 → 拆完谁来保证不超卖〕

**答**：先说结论：**这一行我明确没有拆**，不是没看见，是看见了、测实了、写好了回归条件之后选择先不动。
证据是 M8 那一晚的落库轮：1/2/3 个实例烧掉三倍 CPU 只多落了约 25% 的单，提交次数/s 恒在 70–115、与实例数没有关系，
而 MySQL 只用了 0.24 核。瓶颈就是每个批次都要更新的同一行 `tb_seckill_voucher.stock`，行锁不会因为多了两个进程而变快。
不拆的理由是：当前目标场景下够用，而拆它会动到「数据库的条件更新是最后防线」这句话本身。

**展开**：

- **这一行是怎么被钉死的**。M4 时的说法是「吞吐 ≈ 80 次提交/s × 批大小」，那时还只是推断。M6 补仪表后发现
  80 次/s 是双稳态的慢档不是那一行的能力（同一轮里量到过约 394 次/s 与约 73 次/s 两段），所以 ADR 0007 决策 4
  写的是「不拆」，并留下三条回归条件：到达速率远高于 2000/s、`drain_s_after_load` 重新大于 0、
  `persist_orders_per_s ÷ batch_mean` 不再随负载上升。M8 这三条**同时成立**（2 万/s 灌入、排空 3.4–7.6 s、
  提交 70–115 无趋势），所以「那一行是写路径水平扩展的上限」从推断变成了实测。
- **要拆会怎么拆（业界成熟做法，本项目没做）**。两条路：
  1. **按券分桶扣减 + 定期合并**：把 `stock` 一行拆成 K 行（或 K 个子记录），落库时按桶更新自己那一行，
     后台定时把空桶与富余桶合并 / 归集。好处是热点行的并发被除以 K。
  2. **把库存从 MySQL 移走**，让 Redis 或一个独立的库存服务做权威，MySQL 只留流水。
- **代价和新问题，这是比「怎么拆」更该讲的一半**：
  - 第 1 条会把「一条 `stock >= n` 的条件更新 = 全局不超卖」变成「K 条局部条件更新」，
    最后防线从一个不变量变成 K 个不变量加一个合并任务，**合并任务本身成了新的正确性来源**。
  - 第 1 条还会继承 Redis 那一侧已经存在的**尾部浪费**问题：这个项目在 Redis 上已经分桶了，
    而且明确选择「空桶不借库存」——买家的桶空了就是没货，哪怕整券还有（详见笔记 04 第五节的边界）。
    MySQL 侧分桶会把同样的问题复制一遍，还多一个「合并与扣减之间的窗口」。
  - 第 2 条直接和本项目的分层定位冲突：缓存现在是**允许丢的准入层**，复制空窗那次它最多多放了 10.3% 的人。
    把权威搬上去，就得先给它持久化与故障切换的保证，等于把一个已验证的结论推翻重做。
- **为什么判断现在不值得拆**：目标场景（一张券几千到几万件、秒级售罄）里,落库侧的绝对值已经是单实例中位
  2088.9 单/s、3 实例中位 3026 单/s；而拆行换来的收益是「封顶值 × K」这种要重新测一轮才知道的东西，
  却要先牺牲一个已经被演练验证过的最后防线。**先把它写进边界，比多做一个分桶更值得讲。**

**可能的追问**：→ Q12.8；→ 「那你怎么保证以后想拆的时候还拆得动」（回归条件写在 ADR 0007 决策 4，M8 的更正段落里已勾掉）；
→ 「为什么不把库存表做成广播表」（详见笔记 08 第五节：写热点做广播表要 2PC 才能自洽）

**别踩**：
- 不要说「分桶之后就不会超卖了」。恰恰相反，分桶是**削弱**了最后防线的原子性，需要补合并任务来还债。
- 不要把「Redis 已经分桶了」说成「MySQL 也分桶了」。**Redis 的分桶是 M5 做的，MySQL 那一行没动过。**
- 不要报「拆完能到多少」的数字——没测过，一个数都没有。

### Q12.2 准入侧的扩展曲线为什么测不出来？要怎么才测得出？  〔高频｜追问链：加实例吞吐涨了多少 → 曲线线性吗 → 为什么不线性 → 你怎么排除是系统的问题 → 那这组数还有什么用〕

**答**：**这条曲线我没测出来，而且原因不在系统，在压测客户端。** 1/2/3 个实例在 30k 档分别是
25498 / 25573.6 / 25625.1 req/s，三条线重合。CPU 说明了一切：k6 在自己的 4 个 vCPU 上吃到 3.52–3.58 核，
而三个实例加起来只用了 1.26 核（各 2 核、共 6 核），nginx 用 0.59 核（共 2 核）。**客户端先满**。
所以这组数只能用来证明「加实例没有引入回退」，**不能**用来论证水平扩展提升了准入吞吐。

**展开**：

- **为什么会这样**：M3 之后一次准入几乎不花钱（10k 档应用 CPU 从 3.04 核降到 0.60 核，事务半消息从等于请求数变成 0），
  所以在一台机器上，发压的成本反而高于处理的成本。瓶颈被推到了测量仪器上。
- **怎么区分「系统满了」和「客户端满了」**：报告里 `k6_cpu_cores` 这一列就是为这件事存在的——
  它满了，阶梯就到顶了，与被测系统无关；`edge.csv` 里还有 nginx 的核数，曲线不线性时先看这两列。
  这次三个实例的应用 CPU 不涨、k6 的涨满，方向是反的，结论没有歧义。
- **要怎么才测得出**：换**多机压测**——把压力源放到被测机之外的若干台机器上，用分布式发压（多 k6 实例 + 汇总，
  或 Locust/Gatling 的 master-worker）。本项目**没做**，因为只有一台 16C/30G 的机器。
- **新问题（如果真要做）**：多机之后网络成了新的共享资源，时钟对齐、各 worker 的到达速率汇总、
  结果合并的口径都得重新定；而且被测侧的 Redis Cluster、Broker、两个订单库、nginx **仍然是共享的**，
  曲线不线性时还得先排除它们。换句话说，换多机只解决「客户端先满」这一个问题，不解决共享依赖。
- 更底层的一条边界：**单机测得的是这台机器上的拐点和扩展趋势，不是生产容量。**「万级」的论证方式是
  单实例实测值 × 已验证的水平扩展性 + 各层无共享瓶颈的设计说明，不是把某个数乘以实例数。

**可能的追问**：→ Q12.1（落库侧能测，答案是不扩展）；→ 「那你简历上的数是哪个」（单实例数字 + 口径，见笔记 12 第一节）；
→ 「为什么不干脆把 k6 多给几个核」（会挤掉被测系统的核，分核表在笔记 12 第一节）

**别踩**：
- 千万不要说「三个实例的准入吞吐是 25.5k」。这句话字面成立、含义完全错，**25.5k 是 k6 的上限不是应用的**。
- 不要因为「测不出来」就绕开这组数据。主动说出「客户端先满」这四个字，是这道题唯一的得分点。
- 不要拿 M3 的天花板（≥26.2k）和 M8 的 25.5k 比——M0–M6 是一个实例 8 核，M8 是每实例 2 核，口径不同。

### Q12.3 MySQL 主从、RocketMQ 多副本切换、多机房你做了吗？  〔高频｜追问链：你的存储是单点吗 → MySQL 挂了怎么办 → Broker 挂了怎么办 → 异地多活怎么做 → 那你做过哪些演练〕

**答**：**这三件都没做。** MySQL 是单实例（两个 schema 当两个库），RocketMQ 是单 Broker，没有多机房。
我做过的故障演练是三类：应用 `kill -9`（收敛 102.8 s → 44.7 s）、Redis 主节点宕机 ×2（丢失预占 0、超卖 0，
代价约 1.26 万个 503）、以及复制空窗后杀主（两晚四轮，缓存最多多放 10.3%，MySQL 每轮恰好建 30000 单、超卖恒为 0）。
存储和消息中间件自身的切换，**一次都没演练过**。

**展开**：

- **MySQL 主从切换（没做，会怎么做）**：一主一从半同步复制 + MHA/Orchestrator 或云厂商托管的自动故障转移，
  应用侧用 VIP 或代理层（ProxySQL/MySQL Router）承接地址变更。
  代价与新问题：半同步会把写延迟抬上去，而写延迟正好落在落库这条热路径上；切换期间连接池要能识别只读/不可写；
  异步复制则有 RPO > 0，对我这个系统意味着「已建的订单可能在切换后消失」——**那比 Redis 丢预占严重得多**，
  因为 MySQL 是最后防线，它丢数据没有第二道兜底。
- **RocketMQ 多副本（没做，会怎么做）**：DLedger（Raft）多副本自动选主，或主备 + 同步双写。
  代价：同步刷盘 + 同步复制会显著抬高发送延迟；Raft 需要至少三节点，单机压测环境根本装不下，
  而我坚持压测环境和被测配置要对应得上一个 commit（preflight 会拒绝有未提交改动的工作区）。
  现在 Broker 挂掉的后果是可说的：秒杀链路上成功者的消息发不出去，预占还在 Redis 里，由对账器重驱动；
  关单主路依赖定时消息，Broker 长时间不可用时全部关单压到兜底扫描器上，单轮 200 条、每 10 秒一轮，
  积压订单的关闭会被拉长（详见笔记 06 第六节）。
- **多机房（没做，会怎么做）**：同城双活一般是单元化 + 按用户维度路由，跨城做冷备或异步复制；
  秒杀这种强写热点通常**不做双活写**，而是把库存这类不变量锁在一个单元里。
  代价：单元化要求分片键和路由键能贯穿全链路——我的订单号里已经嵌了用户基因、分片键是用户 id，
  这一点是顺路的；但缓存的桶、Broker 的队列、发号器的实例编号租约全都要重新按单元划分，是一个子系统的工作量。
- 顺带一条相关的、**已经踩到过的**单点：分片附属表主键的 Snowflake workerId 默认取 `server.port % 1024`，
  跨机部署端口会重复——M8 全链路第一次跑 1000 单就撞了 24 次。现在必须显式配 `local-deals.sharding.worker-id`（ADR 0009）。
  这说明「多机房」不是加机器，是每一个隐含「本机唯一」的假设都要重查一遍。

**可能的追问**：→ Q12.5（跨库事务）；→ 「那你凭什么说系统可用」（答：可用性没做，做的是**正确性**的兜底，见 Q12.8）；
→ 「Redis 的切换你演练了吗」（演练了两次宕机 + 四轮复制空窗，详见笔记 12 第十节）

**别踩**：
- 不要把「Redis 主节点宕机演练」说成「做过主从切换演练」。演练的是宕机与恢复过程中的正确性，
  而且第一次的结论是**兜底防线根本没上场**（RPO 实测为 0：主节点一死 slot 直接不可写，买家收到 503 而不是假的成功）。
- 不要说「上了多副本就不丢消息」。同步复制换的是延迟，而且本项目的可靠性不靠消息不丢，靠预占 + 对账器 + `INSERT IGNORE`。
- 不要顺嘴说「日终对账我也有」——那是 M6b，2026-09-21 决定**砍掉**，没做。

### Q12.4 接真实支付渠道会多出哪些问题？  〔常见｜追问链：你的支付是怎么做的 → 回调怎么防伪 → 重复回调怎么办 → 是真渠道吗 → 真渠道会多什么〕

**答**：**本项目的支付是 mock 渠道，没有真实资金、没有对账文件、没有风控。** mock 渠道在进程内存里记支付单，
按 HMAC-SHA256 签名发回调，至少一次投递（按配置重复若干份）、失败指数退避重试、每次投递带随机抖动所以**不保证顺序**——
这三件事（异步、重复、乱序）是真渠道最常见的形态，我的验签、幂等、状态机都是按它们设计的。
但「像」不等于「是」，真渠道至少多出四类问题。

**展开**：

- **现在做到了什么**：回调按规范字段排序拼成 canonical form 做 HMAC-SHA256，验签用常量时间比较（不泄漏前缀匹配长度）；
  幂等按支付单号 / 退款单号那一行判，不依赖渠道流水号；乱序与重复由订单状态机的条件迁移吸收（五类竞态详见笔记 06）。
  M8 全链路里由压测脚本扮演渠道，自己按签名规范直接发 `/payment/callback`——因为**多实例下真正必须站得住的端点是回调**。
- **真渠道会多出来的（本项目都没做）**：
  1. **对账文件**。渠道 T+1 下发账单，必须逐笔与本地支付流水核对，产出差异单（有支付无订单、金额不一致、
     已关单却已支付未退款、重复支付）。这正是计划里的 M6b，**2026-09-21 决定砍掉**，理由是它是这个项目里
     第二个「对账」（秒杀预占对账器已经有了），面试增量小。会怎么做：按商户 + 业务日幂等可重跑的批任务，
     分片环境下按分片并行扫描。代价：它自己成了一个需要被监控的批系统，差异单还需要人工处置流程。
  2. **主动查单（补偿查询）**。回调可能永远不来，真实接法一定要有「按支付单号去渠道查一次」的反向通道。
     我这边没有——mock 渠道只推不拉。没有它，回调彻底丢失时这笔订单只能被关单兜底关掉，
     而渠道那边钱已经扣了，就是一笔差错。
  3. **资金安全与风控**：证书 / 密钥轮转（我的回调密钥有开发默认值，生产必须用环境变量覆盖）、
     金额与币种的独立校验（现在金额异常的支付**只记录成「异常」等人工，没有自动退款、也没有告警通道**）、
     重复支付的退款流程、渠道限流与降级。
  4. **网络与时序**：真渠道回调来自公网，要做 IP 白名单、重放窗口（时间戳 + nonce）、超时与退款的最终态查询。
     mock 渠道跑在进程内，这些一条都用不上。
- **mock 渠道自己的边界**：状态在进程内存里，用户在 A 实例预下单、在 B 实例点付款会找不到支付单；
  重启会忘掉未支付的支付单（预下单会重新登记）。真实渠道没有这个问题，多实例验证时把收银台固定到一个实例。

**可能的追问**：→ 「回调和关单同时到怎么办」（笔记 06 五类竞态，两种交错都跑到过）；
→ 「为什么不做对账」（上面第 1 条，是主动砍的，理由要说得出）

**别踩**：
- 不要把 mock 渠道说成「模拟了真实支付」。它模拟的是**交付语义**（异步 / 至少一次 / 乱序 / 退避重试），不是资金语义。
- 不要说「我做了支付对账」。秒杀预占那个对账器和支付对账是两件事，混说一次就全盘失分。
- 不要说「签名保证了安全」。没有重放窗口和 IP 白名单，签名只解决防伪不解决重放。

### Q12.5 跨两个库的事务崩在两次提交之间，你说结果是「有界的少卖而不是超卖」——这是实测还是推理？  〔坑｜追问链：分片之后事务怎么办 → 用 XA 吗 → 不用 XA 崩了会怎样 → 你测过吗 → 那这句话凭什么成立〕

**答**：**这是推理，不是实测；故障注入我没有做。** 我不会把它说成实测。
能拿出来的证据只有两条：一条集成测试用**物理连接**分别去数，证明了一个批次确实横跨两个库
（8 个不同槽位的买家，第一个库 4 行、第二个库 4 行，库存只扣一次）——非原子窗口的存在是这条测试的推论；
以及机制上的推导：没提交的那半批订单仍持有 Redis 预占，对账器发现库里没单会重投，`INSERT IGNORE` 让重放幂等，
但这一批的库存已经扣过一次、重放会再扣一次，所以库存**比真实值更低**——方向是安全的（宁可少卖），量级被批大小限住。
**那个窗口有多宽，我没有量过。**

**展开**：

- **为什么选 LOCAL 不选 XA**：中间件默认的 LOCAL 事务逐个物理连接提交，不保证跨库原子。选它是因为
  2PC 的额外往返和锁持有时间正好落在落库这条热路径上，而原子性并不是这条链路正确性的唯一来源——
  预占 + 对账器重驱动 + `INSERT IGNORE` + `stock >= n` 条件更新，这四件事合起来才是。
  **XA 的代价我也没有实测，所以我不报数字。**
- **这句话成立的条件**（说出来比说结论更重要）：① 重放必须幂等（靠订单表的唯一键与 `INSERT IGNORE`）；
  ② 预占必须还在（预占随 Redis 主节点死掉的情况另有一条路径，见复制空窗那次演练）；
  ③ 「多扣的那一次库存」**补不回来**——重投能补回订单，补不回这一次多扣。
  所以准确的说法是「有界的少卖」，不是「没有影响」。
- **要把它变成实测该怎么做（没做）**：在两次物理提交之间插一个可控的故障点——
  用字节码增强 / 代理层注入，或者干脆在测试用的数据源包装类里按开关抛异常/杀进程，
  然后断言：订单数 < 批大小、库存被多扣一次、对账器收敛之后订单数恢复、超卖仍为 0。
  代价是要为测试在生产路径上留一个注入点，或者引入 Byteman/Chaos 这类工具，
  以及「进程恰好死在那个窗口」这件事很难稳定复现，可能要把窗口人为拉宽——**拉宽之后测到的就不是真实窗口的概率了**，
  只能证明后果的方向，证明不了量级。
- 流程细节不重抄，详见笔记 08 第 3.3 节与第 4.3 节。

**可能的追问**：→ Q12.3（MySQL 单点）；→ 「那你为什么敢用 LOCAL」（笔记 08 第五节那一问）；
→ 「分片之后还有哪些查询是广播」（三个取单行 + 商户后台分页，见 Q12.8）

**别踩**：
- **绝对不要把它说成实测**。这题就是专门来抓这个的：面试官一句「你注入过故障吗」就能验证。
- 不要说「少卖没影响」。多扣的那一次库存补不回来，活动结束前会少卖掉这么多件。
- 不要说「上 XA 就好了」。XA 的代价这个项目没测过，而且 XA 也只把窗口收窄到 commit 阶段，不是消灭它。

### Q12.6 traceId 哪些链路没覆盖？为什么没补齐？  〔偶见｜追问链：你怎么排查一个请求 → 多实例怎么对上 → 消息那一跳怎么串 → 哪些没串 → 为什么不上链路追踪系统〕

**答**：HTTP 是全量覆盖的（从 nginx 的 `$request_id` 进来，一路到 `trade_order.trace_id`）；
**消息 → 数据库这一跳只接了秒杀链与关单链**，支付回调链和营销发放链的消息**没有携带 traceId**。
另外**批量落库路径的日志行不带 trace**——订单行上有 id，但处理那一批时打的日志不属于任何一个 trace。
还有：对账器重建的订单没有 id，迁移之前的订单也没有，所以那一列可空。

**展开**：

- **为什么这么选**：接上的那两条链有一个共同点——它们**跨实例交付一笔订单的所有权**（准入在 A 实例、
  落库可能在 B 实例；关单同理）。支付回调和营销发放不跨实例交付所有权，一个 traceId 在那里能省下的排查时间少得多。
  所以这是取舍不是遗漏，被问到时我说的就是这个标准。
- **批量那一侧为什么空**：批次是多条消息合成的一个单位，**它不属于任何一个 trace**——
  要么给批次一个新 id 并记录「它由哪 N 个 trace 合成」，要么退化成逐条。现在的实现是只有退化到单条时才写线程上下文。
  代价很具体：整批级别的日志只能靠券 id、批大小和时间去对；逐条级别至少还带订单号，可以从订单号反查回那一行的 id。
- **业界成熟方案（本项目没做）**：OpenTelemetry + Jaeger/SkyWalking，用 W3C `traceparent` 在 HTTP 头和
  MQ 消息属性上传播，span 描述每一跳的父子关系与耗时。
  代价与新问题：Agent 或 SDK 的接入成本、采样策略（全采样会把存储打满、抽样会漏掉你正要查的那一条）、
  多一套需要自己维护的后端服务；对一个单体 + 三实例的规模，收益不足以抵掉这些。
  **我现在只有一个 id，没有 span、没有父子关系、没有跨服务耗时拓扑**，「这一跳花了多久」靠同一个 id 的日志行时间戳去减。
- **还有一条相关的边界**：日志没有集中收集，多实例时是逐个实例的日志文件，按 id 查要一个文件一个文件地查。
  指标以抓取端点暴露，**没有看板也没有告警**（看板在 M8 被砍）——积压仪表存在，但没有任何阈值会主动通知人。

**可能的追问**：→ 「那你线上怎么定位一个慢请求」（笔记 12 第九节，且那一节的命令链大部分没在本项目执行过，已逐条标注）；
→ Q12.8

**别踩**：
- 不要说「我做了全链路追踪」。**只有一个 id，不是分布式追踪系统**，这两个词差得很远。
- 不要说「所有链路都串起来了」。四条链里接了两条，而且最重要的批量落库路径的日志行恰恰是空的。

### Q12.7 全链路压测里有 214 个赢家在 30 s 内没等到订单就放弃付款，这是丢单吗？  〔常见｜追问链：异步下单用户查不到订单怎么办 → 你测到过吗 → 那 214 个人是不是丢了 → 多久能看到 → 业务上怎么办〕

**答**：**不是丢单。他们的订单都落了库。** 那 30 s 是压测脚本给虚拟买家设的**耐心上限**，
脚本里叫 `never_persisted`，超过这个时间就不再轮询、直接走人。运行结束后核对的结果是：
在册订单 1000 = 库存，零超卖、零重复买家、Redis 与 DB 库存归零、零残留处理中。
落库可见时间中位 5.2 s、p99 15.7 s、最大 16.0 s。

**展开**：

- **为什么会有肉眼可见的延迟**：准入的终点是「Redis 里有一条预占」，不是「数据库里有一张订单」。
  订单由批量消费者异步建，中间还隔着一个为了攒批而调大的拉取间隔（批大小均值从 2.16 涨到 12.68 就是这么来的）。
  **延迟是异步落库这个选择的标价**，不是 bug。
- **这个延迟在业务上怎么处理（本项目做到哪一步）**：现在做到的是「预占存在即可查」——
  用户拿到订单号是同步返回的（本地发号器，不依赖缓存），查询时预占哈希里有归属证据。
  **没做**的是：前端的排队页 / 长轮询 / 服务端推送「你的订单已生成」。真实电商通常给一个明确的
  「排队中，预计 x 秒」页面，而不是让用户自己刷。
- **要把这个数压下去该怎么做**：拉取间隔调小（代价是批攒不起来，落库吞吐掉回去——这是 M6 那一轮实测的权衡）、
  或者给「赢家」单独开一条快通道。都没做，因为当前场景下 p99 15.7 s 可接受，而攒批换来的是 2088.9 单/s。
- 报告里把这条单独列成边界，就是为了避免自己把它读成丢单——**`never_persisted` 这个字段名本身容易误导**。

**可能的追问**：→ 「那用户点付款的时候订单还没有呢」（预占 + 订单号已返回，收银台的边界见 Q12.4）；
→ 「p99 15.7 s 能接受吗」（答：当前目标场景可接受，压下去的办法和代价见上）

**别踩**：
- 不要含糊地说「有 214 个用户没拿到订单」——这是把自己的诚实标注读成事故。要说「订单都落了库，是脚本的耐心上限」。
- 不要拿 30 s 和 16.0 s 做任何新的算术（比如推一个「成功率」）。**报告里的数只抄不算。**
- 不要说「异步落库对用户无感」。中位 5.2 s 就是有感的，坦白讲清楚比粉饰强。

### Q12.8 如果重来你会怎么改？现在这套设计最脆弱的一环在哪？  〔高频｜追问链：这个项目你最满意哪里 → 最不满意哪里 → 重来会怎么改 → 最脆弱的一环 → 怎么补〕

**答**：最脆弱的一环不是秒杀那条热路径——那条被三次演练逼过了。最脆弱的是**收敛依赖单一组件：对账器**。
复制空窗那四轮，正确性守住了（MySQL 每轮恰好 30000 单、超卖恒为 0），但**收敛需要 150–308 s，全靠对账器**，
而对账器自己没有批量化，也没有任何告警会告诉我它卡住了。如果重来，我会按这个顺序改三件事：
先给对账器批量化与自监控，再补跨库事务的故障注入，最后才动库存那一行。

**展开**：

- **重来会改的三件事，按优先级**：
  1. **对账器批量化 + 自监控**。现在它是收敛时间的唯一决定因素（复制空窗那几轮 150–308 s，
     比普通两轮长得多，原因就是它没有批量化，这个代价我是认的）。而且积压仪表有、**告警没有**。
  2. **给跨库事务补故障注入**（Q12.5），把「有界的少卖」从推理变成实测。这是全文里我最不舒服的一条推理。
  3. **然后才是库存那一行**（Q12.1）。它已经测实、有回归条件、知道怎么拆，反而是最不慌的一条。
- **还会更早做的一件事：先上仪表再改东西**。M4 把落库改成批量，吞吐翻倍但离目标远；
  补上批大小仪表才发现批大小实测只有 1.03——「批量」压根没生效，消费线程本来就跟得上，队列里没有第二条消息在等。
  代价是 M4 与 M5 期间的落库 A/B 结论在补仪表之前**一律不可信**，这是白烧的两个里程碑。
  这条教训比任何一个数字都值钱：**先有度量再有优化**。
- **主动交代的其余边界**（不等被挖）：
  - 落库侧的**双稳态成因至今没有量出来**：知道翻转的是提交速率（约 394 → 约 73 次/s）而不是批大小，为什么翻转，仪表还不够。
  - 消费参数是**一组四项一起改的**，只有拉取间隔有干净的单旋钮证据；线程数那几行的差异全落在噪声带里，
    **不能据此说 4 线程优于 16 线程**。
  - **商户后台按商户 id 分页是跨 8 张表的广播归并**：结果正确，不扩展，分页越深越贵，**明确不修**。
    要修需要一条独立读路径（binlog 订阅 → MQ → 搜索引擎里的订单读模型），那是另一个子系统。
  - **分片附属表主键的 workerId 跨机部署必须显式配**，默认取 `server.port % 1024`（ADR 0009）。
  - **主动砍掉的两项**：M6b 日终对账（项目里第二个「对账」，面试增量小）、M7 多级缓存
    （Caffeine + Redis 两级缓存是八股密度最高、区分度最低的一块）。两项都**没做**，不是没做完。
  - 测试侧：没有 failsafe，集成测试靠命名约定 + `-Dtest` 点名跑，忘了点名就等于没跑；
    CI 只覆盖 MySQL 和 Redis 两种容器，需要真消息中间件或真搜索引擎的六个 IT 在 CI 里被排除，
    **「CI 绿」不等于「全部集成测试绿」**；竞态用例的「两种交错都出现过」靠时延先手争取，不是形式化保证。
- **最满意的一句话**：分层定位是被演练逼出来的，不是设计文档里写的——缓存是允许丢的准入层，
  数据库的条件更新才是最后防线。第一次 Redis 宕机演练里这道防线**根本没上场**（RPO 实测 0），
  我做了四次才把空窗造对（睡副本不够，必须从主节点那一侧掐断复制连接），才第一次看见它开火。

**可能的追问**：→ Q12.1；→ Q12.5；→ 「那你觉得这个项目和黑马点评的差别在哪」（总览第五节整条瓶颈迁移线）

**别踩**：
- 不要把「最脆弱的一环」答成「Redis 挂了」。Redis 挂过两轮加四轮空窗，正确性一次没破——**答它等于没读自己的报告**。
- 不要把砍掉的 M6b / M7 说成「时间不够没做完」。是 2026-09-21 主动砍的，理由要说得出口，这比做了更能体现判断力。
- 不要在这题里堆新数字。这一题的说服力来自承认，不来自补充。
