## 3. 订单闭环：支付 / 关单 / 退款竞态

> 本节机制全部对应笔记 06、ADR 0003。流程细节不重抄，需要展开时看笔记 06 第三节。
> 角色名按 00 总览的角色名表：订单状态机、兜底扫描器、支付渠道（mock）、预占、发券组件、券资产。

### Q3.1 订单有哪些状态？哪些流转是非法的，怎么拦住？  〔高频｜追问链：状态有哪些 → 非法流转怎么拦 → 谁能改状态 → 并发下还成立吗〕

**答**：六个状态：待支付、已支付、已核销、已关闭、退款中、已退款。合法迁移只有五条边——支付、关单、核销、申请退款、退款成功，**每条边的源状态唯一**。所以「非法流转」不是靠 if 判断拦的，而是根本写不出来：一次流转就是一条带源状态的条件更新，源状态对不上就影响 0 行。

**展开**：
- 五条边写死在事件枚举里（`OrderEvent`：PAY、CLOSE、VERIFY、REFUND_APPLY、REFUND_SUCCESS），每个事件自带 from / to 两个字段，另外两个标记是「是否要求已过截止时间」（只有关单）和「是否回补库存」（关单、退款成功）。
- 全仓库只有订单状态机这一个组件调那条更新语句（`TradeOrderMapper.transition`），订单实体里 status **连 setter 都没有**。还有一个源码扫描测试（`OrderStatusWriteContractTest`）守住两条约束：只有状态机这个文件调那个方法，也只有映射层这一个文件里出现「UPDATE 订单表且在 WHERE 之前写 status 列」的语句。
- 所以「已核销的订单被退款」「已关闭的订单被支付」这类非法流转在运行时表现为 CAS 影响 0 行，各调用方自己决定怎么收场（见 Q3.5）。
- 证据：`PaymentRefundIT` 里「已核销再退款」被拒、「退款中再退款」被拒都是断言过的；5 类竞态 IT 全绿（见进度表 M2 行）。

**可能的追问**：→ Q3.2（0 行算成功还是失败）；→ Q3.5（两条边同时打）；→「为什么不做成通用状态机框架」——这里只有 5 条边，一张枚举表比框架清楚。

**别踩**：
- 不要说「用了状态模式 / 状态机框架」，本项目就是一个枚举 + 一条 SQL，说大了对方一翻代码就穿帮。
- 不要说「有订单过期状态」。**没有**：已支付但券过期的订单一直停在已支付，只有券变成已过期，「过期自动退款」没做（ADR 0003 代价段写明）。
- 不要把「券的状态」和「订单的状态」混着说，券有可用/已用/已过期/已退/冻结五个状态，是另一套（详见笔记 07）。

### Q3.2 状态流转的并发安全靠什么？条件更新影响 0 行时你当成功还是失败？  〔高频｜追问链：靠什么保证并发安全 → 0 行怎么处理 → 为什么不用版本号乐观锁 → 为什么不用分布式锁〕

**答**：靠一条 `UPDATE ... SET status=目标 WHERE order_no=? AND status=源状态`，InnoDB 的行锁把并发的竞争者排成先后，后到的那个看到的已经是改完的状态，必然 0 行。**0 行一律当「本次调用失败、我是并发失败方」**，绝不当成功——因为赢家的副作用（回补库存、发券、生成退款单）只允许发生一次，谁赢了谁做。

**展开**：
- 判定只有这一处，返回布尔：影响 1 行返回 true 并在同一事务里写一行状态流转审计；0 行直接返回 false，不写审计。
- 方法上是 `Propagation.MANDATORY`，**必须由调用方开事务**，因为赢家的副作用要和这次流转同生共死。
- 「0 行」在不同链路上含义不同，所以每个调用方拿到 false 之后**再读一次订单**判断原因，而不是笼统报错：关单服务分成「未找到 / 已关闭过 / 还没到期 / 支付赢了无事可做」四种（各打一个计数器）；支付回调分成「关单后到账 / 重复支付」两种；退款申请拿到 false 反而是异常——它已经先 `FOR UPDATE` 锁了订单行，理论上必胜。
- 为什么不用版本号乐观锁：源状态唯一，**状态本身就是版本**，再加一个版本号是冗余。版本号字段我保留了，每次流转 +1，但只给审计和排查用，不参与并发控制。
- 为什么不用分布式锁：这是单行竞争，InnoDB 行锁已经够了，引 Redisson 等于给一个已解决的问题加一个会挂的依赖；而且收敛成一条语句才能用源码扫描测试守住「只有状态机能改状态」。

**可能的追问**：→ Q3.5；→「关单那条边的时间怎么判断」（见 Q3.3）；→「如果状态机被绕过直接改 status 呢」——源码扫描测试拦。

**别踩**：
- 别说「0 行说明出错了要重试」。大部分 0 行是**正常的竞态结果**，重试反而会把已经定好的胜负搅乱；只有关单里「还没到期」这一种 false 才抛异常求重投。
- 别说「加了乐观锁」。有 version 列但它不参与并发控制，这是两回事，说错了对方追问「那你 WHERE 里带 version 吗」就接不住。
- 别扯「用了 MySQL 的 Serializable 隔离级别」。默认 RR，靠的是当前读的行锁。

### Q3.3 超时未支付怎么关单？定时消息还是扫表？为什么？  〔高频｜追问链：怎么关 → 为什么不用纯扫表 / 不用 Redis 过期事件 → 时钟偏差怎么办 → 消息丢了呢〕

**答**：主路是 **RocketMQ 5 的任意时刻定时消息**，兜底是**定时扫表**，两条路并存。秒杀消息的消费者在订单落库成功后投一条定时消息，投递时刻 = 当前时刻 + 支付超时 + 1 秒；默认支付超时 15 分钟。到点消息回来调关单服务，走那条带「必须已过截止时间」的条件更新。

**展开**：
- 为什么不用 4.x 的 18 级延迟消息：15 分钟这类业务超时不在固定档位上，要么改延迟等级要么二次投递；5.x 的定时消息（Broker 开 `timerWheelEnable`，升到 5.3.2）可以直接指定时刻。
- 为什么不只扫表：扫表的延迟下限就是扫描周期，而且是对订单表的周期性范围查询，订单量大了之后这条路的成本和延迟都不划算。定时消息让 99% 的订单在到点那一刻就被关掉。
- 为什么还要扫表：消息会丢、Broker 会挂、投递是**尽力而为**的（发送失败只记一行 warn，订单已经提交了，不会因为发消息失败而回滚）。
- **时钟**：截止时间是插入订单时由 MySQL 算的（`NOW(3) + 超时秒数`），关单的判断也是 MySQL 的 `expire_at <= NOW(3)`。参与这件事的有三个时钟（应用 / Broker / 数据库），全部收到数据库这一个时钟上之后，偏差只剩「定时消息早到一点」这一种表现，早到的结果是 CAS 影响 0 行、消费者主动抛异常让 Broker 按退避重投，**绝不会误关一笔正在付款的订单**。投递时刻多加的那 1 秒就是为了少走这一轮白重投。
- 证据：`OrderCloseTimerIT` 连真实 Broker，把支付超时配成 3 秒，断言订单确实是被定时消息关掉的、**关闭时刻不早于 3 秒**、且库存已回补；HTTP 端到端冒烟里「未支付 20 秒后 23 秒内关单 → 同一用户再买」也走通了，结束时 MySQL 与 Redis 库存一致（均为 3）。

**可能的追问**：→ Q3.4（消息丢了）；→「Broker 挂了全部关单怎么办」（见 Q3.4 别踩）；→「为什么不用 Redis key 过期事件」。

**别踩**：
- 别说「用 Redis 的 key 过期通知关单」——本项目没用，而且过期事件是不可靠投递、不保证及时，说了会被追着打。
- 别说「定时消息保证一定送达」。本项目的立场恰恰是「消息可能丢，所以必须有兜底扫描」，这才是加分项。
- 别把这一秒说成「随便加的缓冲」，要说清楚它对应的是应用时钟与数据库时钟的偏差方向。
- 现在定时消息在消费线程里**逐单**投递（批量消费路径已改成异步发送带回调，但仍是一单一条消息，没有批量投递）——被问到优化点就直说这是已知待办。

### Q3.4 定时消息丢了怎么办？兜底扫描多久跑一次、走什么索引、多实例会不会重复关？  〔高频｜追问链：消息丢了怎么办 → 扫描频率与批大小 → 走什么索引 → 多实例会不会重复 → 要不要分布式锁/选主〕

**答**：丢了就由兜底扫描器捡。它每个实例都在跑，**不选主、不加分布式锁**，因为关单是条件更新、Redis 释放脚本是幂等的，多实例并发扫是安全的。启动后 20 秒开始，每轮跑完隔 10 秒跑下一轮，每类每轮最多取 200 条。

**展开**：
- 一轮扫三件事（详见笔记 06 第三节 3.4）：① 待支付且超过截止时间 **30 秒以上**的订单，逐个走关单服务；② 「Redis 预占待释放」标记为 1 且更新时间在 **10 秒**以前的订单，重放一次 Redis 释放；③ 处于处理中、更新时间在 **1 分钟**以前的退款单，向渠道再请求一次（渠道按退款单号幂等）。第三步整体套 try-catch，失败不影响前两步；第一步单条失败只记 error，下一轮再来。
- **索引**：第一件事走 `idx(status, expire_at)`（建表时就是为它建的），按 `expire_at` 排序取前 200；第二件事走 `release_pending` 上的单列索引（这个标记只在待释放时是 1、清空时写成 NULL，所以索引里基本没有行，扫起来很便宜）；第三件事走退款流水表的 `idx(status, update_time)`。
- **那 30 秒宽限**是关键设计：定时消息才是主路，让两条路径尽量不撞；真撞上了也安全——同一条 CAS 只有一个赢家。
- **多实例**：两个实例同一秒扫到同一批 200 条，两边都去关同一笔订单，结果必然是一个 CLOSED 一个 ALREADY_CLOSED，库存只回补一次。代价是**重复劳动**：N 个实例会各自扫一遍同样的行，这是有意接受的——正确性不依赖协调，比引一把分布式锁简单。真要省这份开销，业界做法是 ShedLock 之类的「一次只有一个实例执行」或者按分片键把扫描任务切给不同实例；本项目没做。
- 证据：兜底扫描单独有两个 IT——一个把定时消息丢掉、只靠扫描把订单关掉；另一个把待释放标记置 1、更新时间回拨一分钟并模拟 Redis 当时没写成，跑一轮扫描断言标记清空、Redis 恢复，**再跑一轮不会多加一个库存单位**。

**可能的追问**：→ Q3.11（回补两次会不会超卖）；→「200 条扫不完怎么办」；→ Q3.2。

**别踩**：
- 别吹「兜底扫描零延迟」。**已知边界**：Broker 长时间不可用时全部关单压到扫描上，单轮 200 条、每 10 秒一轮，积压订单的关闭会被明显拉长——这一条要主动说，是加分不是减分。
- 别说「加了分布式锁防重复扫描」，没加，说了就是假的。
- 别把 30 秒宽限说成「怕关早了」，关早了有 SQL 里的过期条件挡着；宽限是为了**减少两条路径的无谓碰撞**。

### Q3.5 支付回调和超时关单同时到了怎么办？输的那一方怎么收场？  〔高频｜追问链：谁赢 → 输的一方钱怎么办 → 自动退款要不要回补库存 → 重复支付走同一条路吗〕

**答**：两者都要把同一行订单从「待支付」改走，InnoDB 行锁把它们串起来，CAS 只有一个赢家。**关键不是谁赢，是输的那一方必须有交代**：关单赢了，支付回调这边发现自己 CAS 输了，钱已经在我们手里，就在同一个事务里生成一张**自动退款单**（单号 `RA` + 支付单号），事务提交之后向渠道发起退款；支付赢了，关单那边读到订单已是已支付，判「支付赢了，无事可做」，直接结束。

**展开**：
- 支付回调输的时候会再读一次订单定原因：已关闭 → 记「关单后到账」，否则 → 记「重复支付」（同一订单两笔支付都成功，走同一条自动退款的路）。两种都返回「自动退款」。
- **自动退款单不推订单状态、不回补库存**。原因：订单已经是关闭态，库存在关单那一方已经补过了；再推一次状态或再补一次库存都是错的。所以退款回调里有个分支——只有「用户申请」类型的退款才继续推订单（退款中→已退款、券冻结→已退、回补库存），自动退款单到「退款成功」就结束。
- 注意两件事是**解耦**的：支付流水行锁负责「同一笔钱只入账一次」，订单的 CAS 负责「这笔钱要么买到订单、要么被退回去」。前者的赢家不一定是后者的赢家。
- 证据：`PaymentRefundIT` 跑 20 轮，最终记录是**支付胜 5 / 关单胜 15，每轮恰好一方胜**；关单胜的那些轮断言自动退款单 1 笔、券 0 张、库存比开始时多 1；支付胜的轮断言券 1 张、自动退款单 0 张、库存不变（见 ADR 0003 结果表）。

**可能的追问**：→ Q3.6（怎么复现的）；→ Q3.11（库存回补）；→「自动退款失败了呢」（兜底扫描每轮重捞超过 1 分钟未确认的退款单）。

**别踩**：
- 别说「支付回调一定会赢，因为用户都付钱了」。实测 20 轮里关单赢了 15 轮，赢家取决于谁先拿到行锁，没有优先级。
- 别说「关单赢了就把钱退给用户然后订单改成已退款」。订单停在**已关闭**，不进退款态；自动退款只动退款流水。
- 别说「先查状态再更新」来避免竞态——查完到更新之间就是竞态窗口，本项目就是靠把判断塞进 WHERE 消掉这个窗口的。

### Q3.6 这个并发你怎么复现的？写测试了吗，两种交错都跑到了吗？  〔常见｜追问链：怎么知道真并发了 → 只跑到一种交错怎么办 → 断言断的是什么 → 稳定吗〕

**答**：写了，5 类竞态各一组集成测试，连真实 MySQL / Redis / RocketMQ 的隔离栈。而且这里有个我自己踩过的坑值得讲：**一开始两个竞态循环里总是同一方赢**（关单 20/20、退款 10/10），测试是绿的，但只验证了一半交错——等于另一半分支从没跑过。

**展开**：
- 复现手段：一个闩锁把 N 个线程同时放出。竞态 1 是 20 轮，每轮换一个买家、新建订单并预下单，先把截止时间改到过去，再让支付回调和关单两个线程同时出发。
- 修法：**给一方固定的 20 ms 先手**，把轮次切成三段——前 10 轮完全同时，中间 5 轮让关单晚 20 ms（支付先手），最后 5 轮让支付晚 20 ms（关单先手）；最后断言**两种赢家都出现过**（`paidWins` 和 `closeWins` 都 > 0）。核销 vs 退款那 10 轮同样按「0 延迟 / 各自先手 20 ms」三段编排。这样不管这台机器上的自然赢家是谁，两种交错都必然被跑到。
- 断言方式是**按最终状态分支断言**，不是断言某一方赢：读出订单最终状态，已支付就要求两个返回值恰好是「支付成功」和「支付赢了无事可做」、券 1 张、自动退款单 0 张、库存不变；已关闭就要求是「自动退款」和「已关闭」、券 0 张、自动退款单 1 张、库存 +1。所以这个测试对赢家是谁不敏感，只对「结果自洽」敏感。
- 稳定性：改完之后**连续 3 次运行结果一致**；最终记录支付/关单 20 轮是支付胜 5、关单胜 15，核销/退款 10 轮是核销胜 3、退款胜 7。
- 其余几类：竞态 2 是同一条已签名的回调 10 个线程同时打进来；竞态 3 是 10 个线程同时关单**再额外让关单消费者收一次重投**（共 11 次）；竞态 4 是 10 个线程同时申请退款。

**可能的追问**：→ Q3.5；→「为什么不用 JCStress / 字节码插桩」；→「20 ms 先手会不会让测试变成串行」（会，那一段本来就是为了测串行那种交错）。

**别踩**：
- 别只说「我写了并发测试，绿的」。面试官真正想听的是**你怎么知道两种交错都跑到了**——把「一开始 20/20 一边倒」这段讲出来，比任何断言都有说服力。
- 别把 20 ms 说成「随机延迟」，是固定的先手，随机的话就没法断言必然覆盖。
- 数字别改：20 轮 5/15、10 轮 3/7，不要说成「差不多一半一半」。

### Q3.7 支付回调怎么做幂等？幂等键取什么？  〔高频｜追问链：幂等键取什么 → 为什么不用唯一索引/Redis setnx → 重复回调怎么答复 → 查不到支付单怎么办〕

**答**：幂等键是**我方支付单号**，幂等闸门是 `SELECT ... FOR UPDATE` 锁住的那一行支付流水。重复回调全部在这行上排队，第一个把状态从「等待中」改成「成功」并提交，后面的看到状态已经不是等待中，直接返回「重复」结束。

**展开**：
- 支付单号是 `订单号-序号`（序号 = 该订单已有支付流水条数 + 1），**由来源确定**，不需要发号服务；单号上有唯一键，重复生成会撞键而不是产生第二张。渠道流水号上另有唯一键，是第二道闸门。
- 只在「等待中 → 成功」这一次状态变化上做事（发券、推订单），这条更新语句自己也带「当前仍是等待中」的条件。
- 几个分支的答复要想清楚，因为**任何非 2xx 都会让渠道继续重试**：
  - 支付单不存在 → 抛 404，故意让渠道重试。因为很可能用户刚在另一个实例预下单、事务还没提交（回调跑到本地事务前面是真实存在的情况）。
  - 状态不是等待中 → 返回「重复」，上层回 2xx，结束；顺带比对渠道流水号，不一致说明同一张支付单被渠道认了两笔钱，记 error。
  - 金额不符 → 把流水置成「异常」，**永不入账**，也不碰订单状态，留人工。
- 发券这一步还有第二层幂等：券号 = `P` + 订单号且有唯一键，就算这段逻辑被重放也只有一张券。
- 证据：同一条已签名通知 10 个线程并发，断言「支付成功」恰好 1 次、其余 9 次全是「重复」，成功的支付流水 1 条、券 1 张、支付事件的状态审计恰好 1 行、退款单 0 条（ADR 0003：1 PAID + 9 DUPLICATE）。

**可能的追问**：→ Q3.5（入账成功但订单 CAS 输了）；→ Q3.8（乱序）；→「为什么不用 Redis 做幂等」——幂等结果必须和入账在同一个事务里，放 Redis 就要处理「Redis 记了但数据库回滚」。

**别踩**：
- 别说「用 Redis setnx 做回调幂等」，本项目没有，而且这题的正确答案本来就是「落库的行本身就是幂等表」。
- 别说「重复回调直接忽略」。要说清返回什么状态码，因为非 2xx = 让渠道继续重试，答错方向会造成无限重投或者真丢消息。
- 别把「支付流水幂等」和「订单状态幂等」混成一件事讲（见 Q3.5）。
- 金额不符这条别说成「自动退款」——本项目只记「异常」等人工，**既没有自动退款也没有告警通道**，这是已知边界。

### Q3.8 回调乱序（支付成功和退款通知反过来到）怎么办？  〔高频｜追问链：乱序会不会错 → 怎么排序 → 用版本号/时间戳吗 → 本地事务还没提交回调就来了呢〕

**答**：本项目**不给回调排序**，靠的是「每个回调只在一个确定的前置状态上生效，前置不成立就用非 2xx 把它顶回去让渠道重试」。退款通知早于支付通知到达时，退款单这一行还不存在 → 抛 404 → 渠道按指数退避重投，等支付那边提交出退款单之后自然就处理了。乱序因此被**转成了延迟**，而不是错误。

**展开**：
- 三种乱序 / 早到的情形和各自的兜底：
  1. 支付回调早于预下单事务提交 → 支付单查不到 → 404 → 渠道重试。
  2. 退款回调早于退款单落库 → 退款单查不到 → 404 → 渠道重试。
  3. 同一笔的多次投递乱序到达 → 内容相同，第一个赢，其余看到状态已变返回「重复」（见 Q3.7）。
- 更强的保证来自**状态机本身**：退款成功这条边的源状态是「退款中」，而「退款中」只可能由用户申请退款那一步写出来，所以哪怕退款回调抢先到了、退款单恰好存在，订单也不可能被从「待支付」直接推到「已退款」。退款回调里那条 CAS 如果失败会直接抛异常（非 2xx），让渠道重投而不是默默吞掉。
- mock 渠道就是照着这个场景造的：每条通知固定投递 2 次、最多重试 8 次、初始退避 1 秒指数增长（上限 60 秒），**每次投递前加 0 到 300 毫秒随机抖动制造乱序**。所以「重复回调」「乱序回调」「回调先于本地事务提交」在本地是稳定复现的，不是上线后靠日志猜。
- **本项目没做的**：回调消息里没有时间戳/序列号，我也没有维护「最新处理的通知版本」。业界成熟做法是回调体带渠道侧的通知序号或业务时间戳，落一张通知表按 (业务单号, 通知类型) 唯一，乱序时**丢弃比当前状态更旧的通知**；再强一点的是「回调只当触发器，收到就反查渠道的权威状态」（主动查单）。代价是多一张通知表 + 多一次出网查询，且查单接口本身也要限频重试。

**可能的追问**：→ Q3.7；→ Q3.10（没接真渠道怎么证明）；→「退避重试期间用户看不到订单已支付怎么办」。

**别踩**：
- 别说「用 RocketMQ 顺序消息保证回调有序」——回调是渠道的 HTTP 调用，进不了你的顺序消息，中间转一手也只是把乱序挪个位置。
- 别说「靠数据库时间戳比大小排序」，本项目没有这段逻辑。
- 404 那一支要说清是**故意的**：把「我还没准备好」表达成让渠道重试，而不是错误。但也要承认代价：真正不存在的支付单会被渠道重试到上限（8 次）才停。

### Q3.9 回调签名怎么验？会不会被伪造回调刷单？  〔常见｜追问链：怎么验签 → 为什么常量时间比较 → 能不能重放 → 密钥怎么管 → 真渠道会怎么做〕

**答**：对除签名外的全部字段**按字段名排序**拼成 `k1=v1&k2=v2...`，用共享密钥做 HMAC-SHA256，和来签做**常量时间比较**，验不过返回 401。所以伪造回调的前提是拿到密钥。但这套防护有明确的短板，我直说：**没有时间戳 + nonce，没有 IP 白名单，也没有主动查单**。

**展开**：
- 常量时间比较（`MessageDigest.isEqual`）是为了不泄露「前多少个字符对上了」，否则攻击者可以逐字节爆破签名。
- 这个接口不靠登录态鉴权，只靠签名——这是回调接口的常态，所以签名之外的每一步都得当成不可信输入：金额要和我方支付单的应付金额比对（不符记「异常」，永不入账），订单状态由 CAS 决定，不由回调内容决定。
- **重放**：本项目的签名不含时间戳/随机串，同一条合法回调可以无限重放。之所以不致命，是因为重放会被 Q3.7 的幂等闸门吃掉（第一次之后都返回「重复」）——但这是**幂等在兜底，不是签名在防**，两件事要分清。
- **本项目没做、业界会怎么做**：
  - 签名字段里加 `timestamp` + `nonce`，服务端拒绝时间窗外的请求，并把 nonce 放进一个短 TTL 的 Redis 集合去重 —— 代价是多一个 Redis 依赖在回调路径上，且要处理时钟偏差和 Redis 不可用时是放行还是拒绝。
  - 换成**非对称签名**（渠道私钥签、我方用渠道公钥验，如微信支付的 SHA256-RSA）：密钥泄露不再等于可以伪造回调，只影响我方发出去的请求 —— 代价是证书轮换与平台证书下载的一整套流程。
  - **主动查单**：回调只当「去查一下」的触发器，金额和状态一律以反查渠道的结果为准 —— 这是最彻底的一条，能同时解决伪造和乱序；代价是每笔多一次出网调用和它自己的重试/超时策略。本项目的渠道接口只有「登记支付」和「发起退款」两个方法，**没有查单接口**。
  - 网关层 IP 白名单 —— 便宜，但对内网横向移动无效，只能算纵深防御的一层。
- **密钥管理的真实状态**：回调密钥有开发默认值（配置里 `LOCAL_DEALS_PAYMENT_CALLBACK_SECRET` 有 fallback），生产必须用环境变量覆盖；配置类里做了「至少 16 个字符」的启动校验。没有做密钥轮换。

**可能的追问**：→ Q3.7；→ Q3.10；→「HMAC 和 RSA 签名的区别」。

**别踩**：
- 别吹「签名保证了回调不可伪造」。共享密钥的对称签名，泄露即可伪造；说清楚「幂等和金额比对是第二道防线」才是完整回答。
- 别说「做了防重放」，没做。
- 别忘了提**开发默认密钥**这个已知边界——主动说出来比被问出来好。

### Q3.10 你没接真支付，这套回调逻辑怎么证明是对的？  〔常见｜诚实题｜追问链：怎么证明 → mock 渠道做了什么 → 哪些场景证明不了 → 真接的话要改什么〕

**答**：证明不了「和某个真实渠道的协议对得上」，这个我认。我能证明的是**在真实渠道的那几条难缠语义下我的处理是自洽的**——所以我没把 mock 做成「调一下就返回成功」，而是照着真渠道的行为把它做难：至少一次投递、非 2xx 指数退避、没有顺序保证。

**展开**：
- mock 渠道的具体参数（都在配置里，可调）：每条通知固定投递 **2 次**、最多重试 **8 次**、初始退避 **1 秒**指数增长（上限 60 秒）、每次投递前加 **0 到 300 毫秒**随机抖动。这样「重复回调」「乱序回调」「回调先于本地事务提交」在本地稳定复现。
- 在这套语义上跑的证据：竞态 2（同一通知 10 并发 → 1 次成功 + 9 次重复，1 条成功流水、1 张券、1 行支付审计）、竞态 1（20 轮 → 支付胜 5 / 关单胜 15，每轮恰一方胜）、竞态 4（10 并发申请退款 → 只生成 1 笔退款单，向渠道的退款请求恰好发了 1 次）。另有 HTTP 端到端冒烟：真实应用 + mock 渠道走 HTTP 回调，跑通「下单→支付→核销→审计」「下单→支付→退款」「未支付 20 秒后 23 秒内关单→同一用户再买」，结束时 MySQL 与 Redis 库存一致（均为 3）。
- **证明不了的，我会主动列**：真实渠道的字段与签名规范（我的签名串是我自己定的）、证书/密钥轮换、渠道侧的查单与**对账文件**、部分退款与手续费、资金差错处理、风控。ADR 0003 和计划的诚实边界里都写了「支付为 mock 渠道，不涉及真实资金、对账文件、风控」。
- **还有一个已知边界**：mock 渠道的状态在**进程内存**里，用户在 A 实例预下单、在 B 实例点付款会找不到支付单；真实渠道没有这个问题，多实例验证时我把 mock 渠道固定到一个实例，压测脚本则是自己按签名规范直接发回调。
- 真要接真渠道，改动面是「换一个 `PaymentChannel` 实现 + 换一个签名器 + 加查单」，订单状态机、幂等闸门、竞态处理这三块不用动——这也是把渠道抽成接口的意义。

**可能的追问**：→ Q3.9；→「日终对账怎么做」（本项目**没做**，计划里的对账是可选项 M6b，没执行）；→ Q3.8。

**别踩**：
- 别为了好听说「用的是支付宝沙箱」。这题问的就是诚实，编一句全盘皆输。
- 别说「mock 渠道和真渠道行为一致」，只能说「模拟了至少一次投递、退避重试、乱序这三条语义」。
- 别漏掉「没做对账」。交易系统面试里对账是高频追问，主动说「日终对账在计划里是可选里程碑，没做；要做的话是按商户按日汇总订单/支付/退款/核销，再逐笔比对出差异单（有支付无订单、金额不一致、已关单却已支付未退款）」，比支吾强得多。

### Q3.11 关单之后库存怎么回补？回补两次会不会超卖？Redis 和 DB 谁先回补？  〔高频｜追问链：谁负责回补 → 会不会补两次 → Redis 和 DB 的先后 → 中间那段窗口怎么办 → Redis 挂了呢〕

**答**：回补被**拆成两半**：数据库那半（秒杀库存表 `stock + 1`）和 CAS 在同一个事务里，Redis 那半在**事务提交之后**执行。补两次不会超卖，因为两边各有自己的一次性条件：数据库那半只有赢了 CAS 的那一方会走到，Redis 那半由一段以「预占仍指向本订单」为条件的 Lua 保证重放是空操作。

**展开**：
- 顺序为什么是「DB 先、Redis 后」：Redis 不参与数据库事务。放进事务里的话，事务回滚了 Redis 改不回来，就凭空多出一个库存单位（这才是真超卖）。放到提交之后，最坏情况是 Redis 那半没做成，表现为**少卖**（数据库有货但准入层不放人），是安全方向。
- 中间那段不一致窗口是**显式记录**的：那条状态更新语句在回补边上顺手把订单的「Redis 预占待释放」标记写成 1，释放成功才清空（清空语句带「标记当前仍是 1」的条件）。释放整体 try-catch，抛异常只记 warn 并保留标记，由兜底扫描器每轮重捞（标记为 1 且更新时间在 10 秒以前）。
- 释放脚本（`lua/seckill_release.lua`，参数是用户 id 和订单号）：先取预占哈希里这个用户的值，**不等于本订单号直接返回 0**；相等才删预占，并且**只在库存计数键存在时**才 `INCR`——键不存在说明这场活动没预热或已被清掉，凭空建键会放出没人配置过的库存。释放成功还会清掉该桶的售罄标记并广播让其他实例也清（详见笔记 05）。
- **它为什么不需要幂等标记**：幂等键就是「订单号」这个业务事实本身。预占指向本订单号只在本订单被释放之前成立，释放后这个字段就没了；用户再次下单写进去的是一个新订单号，所以任何重放读到的要么是空、要么是别的订单号，一律返回 0。
- 另外要还回**买家自己那个库存桶**（桶 = 用户 id % K），不能还到别的桶去，否则那个桶凭空多一个、这个桶永远少一个。
- 证据：竞态 3——10 个线程同时关单再加一次消费者重投（共 11 次），断言「已关闭」恰好 1 次、其余都是「已关闭过」，MySQL 库存和 Redis 库存都回到初值、预占哈希里该用户的字段没了、待释放标记为空、关单事件的状态审计恰好 1 行。兜底扫描那个测试还专门断言**再跑一轮不会多加一个库存单位**。

**可能的追问**：→ Q3.13（一人一单标记）；→「Redis 释放和数据库不一致能持续多久」（下一轮扫描，10 秒级）；→ 笔记 05 的准入层为什么允许丢。

**别踩**：
- 别说「Redis 和 DB 用分布式事务保证一致」。没有，也不该有；本项目是「同事务的那半 + 提交后那半 + 一个标记 + 一个扫描」的最终一致。
- 别把顺序说反。**先 Redis 后 DB 是错的方向**：Redis 补了、事务回滚，就是凭空多库存。
- 别说「回补靠 Redis 的计数就够了」。准入层是纯 Redis 的、允许丢；数据库的条件更新才是不超卖的最后防线（对照笔记 05）。
- 「退款也回补库存」是一个**业务选择**，不是必然：活动已结束时回补的库存不会再卖出去，无害；要改成不回补，只需把退款成功这条边的「回补库存」标记改成 false。

### Q3.12 退款怎么做幂等？退款和核销同时发生呢？  〔常见｜追问链：退款幂等键 → 并发申请怎么办 → 和核销撞了谁赢 → 会不会死锁 → 输的一方脏数据怎么办〕

**答**：退款的幂等键是**确定性退款单号**：用户申请是 `RU` + 订单号，自动退款是 `RA` + 支付单号，单号上有唯一键，同一笔订单再申请一次会撞唯一键而不是退两次钱。并发申请则更早就被挡住了——退款申请的源状态是「已支付」，第二个请求拿到订单行锁时读到的已经是「退款中」，直接拒。

**展开**：
- 退款申请这条链路（详见笔记 06 第三节 3.6）：`FOR UPDATE` 锁订单行 → 校验状态是已支付 → 状态机推到退款中 → 同事务把券从「可用」改成「冻结」（改不动再试「已过期 → 冻结」，过期未用的券允许退款）→ 取第一笔成功的支付流水 → 生成退款单 → **提交之后**才向渠道发起退款请求（请求前把请求次数 +1）。请求失败只记 warn，兜底扫描每轮重捞超过 1 分钟未确认的退款单再请求，渠道按退款单号幂等，多请求几次没有副作用。
- 退款回调侧的幂等和支付回调同构：按退款单号 `FOR UPDATE` 锁退款流水行，已经是成功就返回「重复」，金额不符抛异常让渠道重试。
- **和核销的竞态**：核销是「已支付 → 已核销」，退款申请是「已支付 → 退款中」，**源状态相同**，所以天然只有一方能成。不死锁的原因是**锁顺序一致**：两边都先拿订单行锁、再动券行（退款是显式 `FOR UPDATE`，核销靠那条状态条件更新本身拿的锁）。输家整个事务回滚，包括已经改过的券状态——核销输时是 CAS 影响 0 行，退款输时是拿到行锁后读出的状态已经不是已支付。
- 一个写测试时抓到的细节：核销失败方重读券状态要用 `FOR UPDATE`，否则在 RR 隔离级别下普通读会读到事务快照里的「可用」，把「已核销」误报成「已过期」（ADR 0003 记了这条）。
- 证据：10 个线程同时申请退款，只有 1 个拿到退款单号、其余 9 个都是「退款处理中」，退款单 1 条、券已冻结、向渠道的退款请求恰好发了 1 次，之后再去核销会被拒。核销 vs 退款另有 10 轮对撞（同样三段编排），**核销胜 3 / 退款胜 7，无双赢**。

**可能的追问**：→ Q3.5（自动退款不推订单）；→ Q3.11（退款也回补库存）；→「为什么冻结而不是直接作废券」。

**别踩**：
- 别说「退款加了分布式锁」。是订单行的 `FOR UPDATE` + 退款单号唯一键。
- 别说「已核销的券也能退」。本项目已核销直接拒；能退的是**已过期未核销**的券（冻结时接受已过期）。
- 别说「冻结就是作废」。冻结是因为渠道还没确认退款成功，退款失败的话券还要能回去；但冻结之后门店已经核销不了。
- 别漏掉**部分退款没做**——只有整单退。

### Q3.13 一人一单的标记在关单/退款之后要不要清掉？清了会不会被刷？  〔常见｜追问链：标记存在哪 → 关单后要不要清 → 数据库侧怎么放开 → 清了会不会被刷单 → 为什么不删订单〕

**答**：要清，而且**必须两侧同时放开**。一人一单在本项目是两处：Redis 预占哈希里「用户 id → 订单号」这个字段（准入层判重看的就是它），和数据库订单表上的唯一键。关单/退款时 Redis 那边由释放脚本删掉字段，数据库那边靠**生成列**自动退出唯一键。缺一边就会出现「数据库允许但抢不到」或者「抢得到但落库撞唯一键」。

**展开**：
- 数据库侧：订单表上有个生成列，状态是已关闭或已退款时算出来是 NULL，否则是 1；唯一键建在（用户 id，券 id，生成列）上（`uk_trade_order_user_voucher_active`）。MySQL 的唯一索引允许任意多个 NULL，所以**进行中的订单对一个用户一张券仍然唯一**，而关闭和退款的订单自动退出这个约束。应用层零判断，一条 DDL 解决。
- 为什么不删旧订单：删了就丢掉「他确实抢到过又放弃了」这段事实，风控和客服都要；而且删除和并发的支付回调之间还要再设计一次竞态。代价是这个唯一键的语义藏在表结构里，读代码看不出来，得靠注释和测试说明。
- 分片之后仍然有效：订单按用户 id 分片，同一个用户的全部订单落在同一张物理表，所以这个片内唯一键的语义不变——这正是分片键选用户 id 的原因之一（详见笔记 08）。
- **会不会被刷**：清掉之后这个用户确实可以再抢一次，但他**每次只能占一个名额**（进行中的订单唯一），而且每一轮都要真的等到 15 分钟超时关单才能再来。所以最坏情况是「占坑 15 分钟 → 放弃 → 再占」，这属于薅名额而不是超卖；库存在数据库侧的条件更新面前始终是准的。真要防这种人，业界做法是给「取消次数」设风控阈值（一天内关单 N 次就拒绝下单）或者缩短支付超时；**本项目两个都没做**，代价分别是要维护一份用户维度的行为计数（Redis 计数器 + 每日重置），以及缩短超时会误伤慢支付的真实用户。
- 证据：竞态 5 分两半——Redis 那半走真实准入：买一单、再抢一次得到「重复」、关单、再买成功，断言两边库存都只被扣了一次；数据库那半用状态机关单再插一单，断言状态审计正好是「创建」和「关单」两行，而且此时再插第三单仍会被唯一键挡住。HTTP 端到端冒烟也覆盖了「20 秒超时 23 秒内关单 → 同一用户再买」。

**可能的追问**：→ Q3.11（释放脚本）；→ 笔记 08（分片后唯一键）；→「为什么不用 Redis 的 set 存已购用户」——那就要额外解决「什么时候删」和「Redis 丢了怎么办」，而预占哈希本来就要维护一份。

**别踩**：
- 别说「一人一单靠 Redis 的 SISMEMBER 判重」。本项目判重看的是**预占哈希里有没有这个用户的字段**，判重和预占是同一份数据，这正是它能被释放脚本一次性清掉的原因。
- 别说「关单后把订单删掉就能再买」。
- 别把生成列说成「唯一索引忽略 NULL 的 trick」就完了，要说清楚它是 `status IN (已关闭, 已退款) 时为 NULL`，也就是「终态自动退出约束」。
- 别忘了强调**两侧必须同时放开**——只答一侧是这题最常见的漏答。

## 4. 券资产与核销

### Q4.1 券资产有几个来源？为什么要统一成一个发券出口？  〔常见｜追问链：券从哪来 → 为什么不让发放流水当券 → 发券怎么幂等 → 发券和订单是一个事务吗〕

**答**：业务上有五个来源——秒杀购买、用户领取、后台发放、签到奖励、批量发放；代码上收敛成两条入口：支付回调（购买）和营销的发放内层事务（后四个），两条最后都调同一个发券组件，落到同一张券资产表。之所以要统一，是因为下游有三条逻辑——核销、过期、退款冻结——只认这一张表；每多一种「券」，这三条就要各写一遍。

**展开**：

- 手段：发券组件是唯一出口，按来源拼出确定性券号（购买券是 `P` 加订单号，发放券是 `G` 加发放流水 id），券号上有唯一键，这个唯一键本身就是幂等键，不额外要发号服务。
- 为什么不「先查再插」：查和插之间有窗口，两个并发的支付回调可能都查到没有、都去插。改成直接插、撞唯一键之后按券号回查，把并发判给数据库；回查到了就把已有的那张原样返回，上游看到的永远是成功。
- 撞唯一键有两种可能，所以回查是必须的：查得到＝券号撞了＝同一来源重复发券，走幂等；查不到＝随机核销码撞了，重抽一个码再插，最多 3 次（`MAX_CODE_ATTEMPTS`），三次都撞就抛异常——那时更可能是随机源坏了，继续重试不如失败。
- 事务边界：发券永远跑在调用方的事务里。购买侧是订单 CAS `PAID` 成功之后同事务发券；营销侧是活动额度扣减、发放流水写入、通知 Outbox 写入之后最后一步发券。发券失败就连带回滚，宁可上游重试，不能钱收了券没出。
- 有效期不 JOIN：券资产表按用户 id 分片、券模板表不分片，一条语句跨不了两边，所以先读一次券模板快照（拿门店 id 和有效天数），再用纯 VALUES 插入，`valid_from = NOW(3)`、`valid_to = NOW(3) + INTERVAL 有效天数 DAY`，全部走数据库时钟。
- 证据：`CouponVerifyIT` 里「一张已支付订单恰好一张购买券、有效期等于券模板天数」和「发放产出一张发放券」两条；ADR 0003 记的旧表迁移是 142 000 单、142 000 张券。流程细节详见笔记 07 第三节 3.1。

**可能的追问**：→ Q4.2；→「为什么不让发放流水表本身当券？」（发放流水是营销域的凭证，不分片，记幂等键和额度；券资产是用户侧的资产，按用户分片，记有效期和核销码——生命周期和访问模式都不一样）；→「G 开头的券号没有基因，按券号查会怎样？」（广播，详见笔记 08）

**别踩**：
- 别说「发券组件声明了 `MANDATORY` 传播所以一定在调用方事务里」——它**没有声明任何事务传播**，原子性靠两个调用点各自开了事务。这是已知边界，主动说出来比被挖出来好。
- 别把「五个来源」说成五段发券代码：营销那四个是在同一个发放事务方法里收敛的，实际调用点只有两处。
- 别说唯一键能跨片保证券号唯一——券号带基因的购买券确实落单片，但唯一约束本身是片内的（见 Q4.3 / Q4.4 的同类问题）。

### Q4.2 核销怎么保证只能核销一次？商户 A 能不能核销商户 B 的券？  〔高频｜追问链：怎么只能核销一次 → 和退款同时来呢 → 会不会死锁 → 失败了怎么知道是哪种失败 → 跨商户能核销吗〕

**答**：只核销一次靠两处条件更新，不靠锁服务：购买券先把订单从已支付 CAS 成已核销，再把券从「可用」CAS 成「已核销」；任意一处影响 0 行就整个事务回滚。商户 A 核销不了商户 B 的券——券上快照了商户 id，不匹配就拒；而且拒的时候返回的错和「码不存在」**完全一样**。平台级账号是例外，它可以核销任何商户的券，这条归属判断对它是跳过的。

**展开**：

- 券侧那条更新的条件是：主键 + 用户 id + 状态仍是 `AVAILABLE` + `valid_from <= NOW(3) AND valid_to > NOW(3)`。用户 id 必须带，它是分片键，不带这条更新会在八张表上各上一行锁（分片中间件对不带分片键的 `FOR UPDATE` **不报错**，只是默默锁八行，这是最危险的一类）。
- 时间窗口写在更新条件里，意味着**过期判定不依赖定时任务**：任务一次不跑，过期券也核销不掉（见 Q4.4）。
- 和退款的互斥：两条链路的加锁顺序一样，都是先订单行、后券行（核销 `PAID→USED` + 券 `AVAILABLE→USED`，退款 `PAID→REFUNDING` + 券 `→FROZEN`），所以只会互相排队、不会循环等待。真正让它们互斥的是订单行那一次 CAS，券上的 CAS 是第二道保险——也是发放券唯一的那道，因为发放券没有订单。
- 失败后的错误分类：重读券状态用的是 `FOR UPDATE` 加锁读，不是普通读。事务跑在可重复读下，普通读看到的是事务开始时的快照（券还是「可用」），会把「刚被另一个店员核销掉」误报成「券已过期」。这个 bug 是写并发测试时抓出来的。
- 跨商户：券不存在和别家商户的券抛的是**同一个** 404「券码无效」。如果两者返回不同的错，商户就能拿自己的后台当预言机，扫码空间判断哪些码是别家的真券——防枚举就白做了。
- 证据：`CouponVerifyIT` 的「同一个码并发核销恰好一个赢」和「别家商户的码和未知码长得一模一样」两条；ADR 0003 记的竞态 4——10 并发退款申请只生成 1 笔，已核销拒退，核销胜 3 / 退款胜 7，无双赢。流程详见笔记 07 第三节 3.2。

**可能的追问**：→ Q4.5；→「订单已核销但券还可用会不会出现？」（不会，券侧 CAS 失败会回滚掉订单那次流转，两者原子）；→「为什么不用 Redisson 按券加锁？」（状态字段本身就是 CAS 条件，InnoDB 行锁已经串行化竞争者，加一层分布式锁只是多一个可用性依赖，详见笔记 06）

**别踩**：
- 别说「限频保证不会被重复核销」——限频只防枚举，和「一次性」没关系。一次性是数据库那两条条件更新给的。
- 别说「平台账号也受商户隔离」——**没有**，平台账号可以核销任何商户的券，目前只靠后台权限点控制。
- 别把 `FOR UPDATE` 说成是为了「防止并发」——它在这里是为了**读到最新已提交版本以便报对错误码**，并发本身已经被 CAS 挡住了。
- 别说核销这条链路是高并发路径，它是柜台低频操作，按码查甚至是八片广播。

### Q4.3 核销码会不会被枚举？你怎么防的？  〔常见｜追问链：码怎么生成 → 长度够吗 → 限频怎么做的 → Redis 挂了限频还在吗 → 商户账号泄漏了怎么办〕

**答**：码是 16 位 Crockford base32、安全随机源生成，32 个字符正好 5 bit，所以是 80 bit 随机空间。外部硬猜没有指望。真正要防的其实不是外部暴力破解，而是**某个商户后台账号泄漏后被拿去当枚举工具**，所以防线有三层：80 bit 随机、每商户每分钟 120 次的尝试上限、以及「未知码和别家的码返回同一个错」。

**展开**：

- 字母表去掉了 I、L、O、U：这个码要在门店被念出来、被人肉敲进去，去掉形近字符能少很多输错。这是可用性选择，不是安全选择。
- 限频是一个 Lua 脚本（`lua/coupon_verify_rate.lua`）：键是「商户标识 + 当前分钟序号」，脚本先 `INCR`，发现结果是 1（说明这个分钟桶刚建）就顺手 `EXPIRE` 120 秒。自增和设过期必须在一个脚本里，否则两条命令之间进程挂掉会留下一个永不过期的计数键。脚本返回本分钟累计次数，超过上限抛 429；上限是配置项、默认 120，和那个写死的 120 秒 TTL 没有关系（数字撞脸而已）。
- 限频在控制器里、进业务之前调用，所以被限住的请求根本不会发起那次八片广播查询。
- **Redis 抛异常时放行（fail open）**，只打一条告警。这是明确的取舍：核销失败意味着顾客站在柜台前用不了券，是直接的业务中断；而限频只是纵深防御的一层，80 bit 随机码不是能扫出来的，归属判断那一层也还在。
- 入参先去空白、转大写，再过 16 位定长格式正则，格式不合直接当「查不到」，不去查库。
- 审计切面记券号，**不记核销码**——码是秘密，不该落到审计表里。

**可能的追问**：→「限频是滑动窗口吗？」（不是，固定窗口；跨窗口边界最坏能放过接近两倍配额。对枚举防护够用，但别说成精确限流）；→ Q4.2 的「同一个错」那一点；→「为什么不把用户分片基因嵌进码里省掉广播？」（会泄漏「这两张券是不是同一个用户的」，也让码更长；当前量级不值得换）

**别踩**：
- 别说「限频是安全底线」——它是 fail open 的，Redis 一抖就整个失效。底线是 80 bit 随机加归属判断。
- 别忽略两个自己知道的洞：**平台级账号共用一个全局限频桶**（不按商户分，多个平台账号共享配额，结合「平台账号可核销任何商户的券」，泄漏一个平台账号比泄漏一个商户账号后果大）；**格式正则比生成字母表宽**（正则是 16 位数字加大写字母，生成时去掉了 I/L/O/U，所以含这四个字母的码仍会通过格式校验、白白发起一次广播查询——不影响正确性，是一次能省掉的查询）。
- 别算「80 bit 配 120 次/分钟要多少年才能撞到」这种数——真被追问就说「这个数我没算，量级上不可行」，不要临场乘除编一个数字出来。

### Q4.4 券的过期任务怎么跑？分表之后 `UPDATE ... LIMIT` 为什么不能用了？  〔坑｜追问链：过期怎么实现 → 任务不跑会怎样 → 为什么不一条 UPDATE 搞定 → 多实例重复跑呢 → 怎么知道扫干净了〕

**答**：过期是双保险。真正管用的是核销那条更新里自带的时间窗口条件，所以定时任务一次都不跑，过期券也核销不掉；任务只是把状态字段**追认**成「已过期」，让按状态的查询能走索引。任务本身是固定延迟：启动后延迟 30 秒，之后每轮结束再等 60 秒，每轮最多 20 批、每批 500 条。`UPDATE ... LIMIT` 不能用，是因为分片中间件会拒绝路由到多个节点的带 LIMIT 的更新——那个 LIMIT 会在每个节点各生效一次。

**展开**：

- 计划的 M6 偏差记录里原话就是这个坑：`UPDATE ... LIMIT`（limit 会按节点生效，「最多过期 200 张」会变成 1600 张）——那句话里的 200 是记录时的举例，代码现在是每批 500，所以实际形状是「每张物理表各 500 张，八倍」（第 6 节 Q6.6 用的是代码的口径）。它和另外三类被拒 SQL（插分片表时 JOIN 单表、多表 `DELETE ... JOIN`、不带分片键的 `SELECT ... FOR UPDATE`）是同一批发现，其中不带分片键的加锁读最危险，因为它**不报错**，只是在八张表上各锁一行。
- 改法：每批先查一次——状态仍为可用且失效时间已过，按失效时间排序取前 N，**只取主键和用户 id 两列**；这条查询是广播归并的，走（状态，失效时间）索引。然后逐行条件更新：主键 + 用户 id + 状态仍是可用 + 失效时间已过 → 置为已过期。
- 先查再更新有个额外好处：读出来的每一行都自带用户 id，也就是分片键，所以每条更新只打一片。代价是一批要发 N 条语句，但这是后台任务，不在用户请求路径上。
- 幂等：状态本身就是 CAS 条件，多实例同时扫、或者上一轮跑到一半挂掉，重复执行只会影响 0 行，绝不会把已核销的券误伤成已过期。
- 一批的这些更新在同一个事务里提交；某一批**实际改动的行数**不到 500 就结束本轮。
- 证据：`CouponVerifyIT` 里「过期券被拒绝核销，且过期任务把它标成 EXPIRED」那条。流程详见笔记 07 第三节 3.3。

**可能的追问**：→「怎么保证只有一个实例在扫？」；→「顺带说说 `uk(verify_code)`」（分片之后这条唯一键收窄为**片内唯一**，跨片撞码数据库拦不住，靠的是 80 bit 随机空间；真撞了按码查会在两片各返回一行，当前代码没有处理这种情况。对比之下 `uk(user_id, voucher_id, active_flag)` 语义不变，因为一个用户的行永远在同一张表里——这正是分片键选 `user_id` 的原因。详见笔记 08）

**别踩**：
- **没做分布式互斥**：多实例部署时每个实例都跑自己的那一份，靠 CAS 保证不出错，但重复的扫描查询是实打实的浪费。没接选主也没接分布式锁。会怎么做：给这个任务加一把带租约的分布式锁（Redis 或数据库行），或者接一个调度框架做选主；代价是多一个可用性依赖——锁服务抖了任务就停摆，而现在的版本最坏只是多扫几遍。这是假设方案，本项目没写。
- **判「扫干净了」用的是改动行数，不是捞出来的行数**：多实例同时扫时，只要一批里有几行的 CAS 被别的实例抢先改掉，本轮就会提前结束，剩下的积压留到下一轮。正确性没问题，清理会慢一点。
- 别说「过期任务保证券不能被使用」——它只是追认状态；保证在核销那条 SQL 的时间条件里。
- 别把「每轮最多 20 批 × 500 条」当成吞吐数据往上报，它是限流上限，不是实测速率。

### Q4.5 已核销的券又来退款怎么办？  〔常见｜追问链：核销和退款同时来谁赢 → 已核销还能退吗 → 过期的券能退吗 → 退款失败了券卡在哪 → 退款要不要回补库存〕

**答**：退不了，直接 409，整个退款事务回滚、订单退回已支付。机制是：退款申请在同一事务里先把订单从已支付推到退款中，然后按券号把券从「可用」改成「冻结中」；改不动就再试一次把「已过期」改成「冻结中」；两次都改不动说明券已经是「已核销」，抛冲突。允许已过期的券退款是业务选择——券没用掉，钱应该能退。

**展开**：

- 和核销的互斥是双向的：加锁顺序一致（订单行在前、券行在后），谁先提交谁赢，另一方的条件更新影响 0 行然后报冲突。核销赢了，退款就申请不下去；退款赢了，核销那边订单 CAS 就推不动。
- 冻结那条更新是按券号定位的，购买券的券号里带订单号基因，能路由到单片，不是广播。
- 渠道确认退款成功的回调里，订单从退款中推到已退款，券从「冻结中」改成「已退款」，库存单位归还（和超时关单共用同一条归还路径）。
- 证据：ADR 0003 的竞态 4，`PaymentRefundIT`——10 并发退款申请只生成 1 笔退款；已核销拒退；核销胜 3 / 退款胜 7，无双赢。流程详见笔记 07 第三节 3.4 与笔记 06。

**可能的追问**：→「渠道退款一直不成功，券怎么办？」；→「过期的已支付订单会自动退吗？」；→「退款回补的库存活动已经结束了怎么办？」（回补了也卖不出去，无害；若要改成不回补，只需把退款成功那条边的「释放库存」标志改掉）

**别踩**：
- **冻结中没有回滚路径**——这是本项目明确没做的一条：退款申请成功后券就是冻结中，如果渠道那边退款一直不成功，只有重试，没有把券从冻结中改回可用的代码。也就是一次退款申请就永久让这张券不可核销。会怎么做：给冻结加一个超时反向状态机（比如退款流水停在中间态超过 N 分钟就把券从冻结中改回可用），或者由一个补偿任务按退款流水状态反推券状态；代价是要小心和渠道的异步回调抢，反向流转本身也必须是带源状态的 CAS，否则会把刚退成功的券放回可用。这是假设方案，代码里没有。
- **退款成功回调里把券从「冻结中」改成「已退款」那条更新，影响行数没有检查**：如果券当时不在冻结中，退款流水和订单照样推进，券会停在原状态，也没有告警。这是已知边界，别说成「全链路状态一致」。
- **过期的已支付订单不会自动退款**：券会被标成已过期，但订单状态机里没有「过期」这一态，订单会一直停在已支付。「过期自动退」没做。
- 别说「退款和核销靠分布式事务保证互斥」——没有分布式事务，就是同库的两次条件更新加一致的加锁顺序。
