## 7. 压测方法、数字来源、Linux 命令

> 本节所有数字原样抄自 `docs/benchmark-report.md` 与笔记 12；所有命令都能在
> `scripts/bench.sh`、`scripts/stack.sh`、`benchmark/v2/scripts/` 里 grep 到出处。

### Q7.1 你这些 QPS 是怎么测出来的？什么机器、什么工具、压测机和应用在同一台机器上吗？  〔高频｜必问：数字怎么来的 → 压测机在哪 → 拐点怎么定义 → 那你这数是不是客户端上限〕

**答**：单机压测，压测客户端和被测应用在同一台机器上，但三方分核隔开了。机器是 8C/16T（`nproc` 16）、
30 GB 内存、内核 5.15.0-134，工具是容器里的 k6 2.2.0，全部用 `constant-arrival-rate` 开环模型。
入口只有一条命令 `scripts/bench.sh <场景>`，无人值守跑完，结果目录里有 `status` / `manifest.json` /
`summary.csv`。我必须先声明：**同机压测是这份数据最大的已知缺陷**，M8 的准入数字就是被客户端卡住的。

**展开**：
- 工具与模型：`docker run --rm --network host --cpuset-cpus 6-7,14-15 --user 1000:1000 ... grafana/k6:2.2.0 run --quiet -e RATE=20000 -e DURATION=30s ... --summary-export /out/step-....json /scripts/seckill.js`。
  `--network host` 是因为被测应用和 nginx 都是宿主机进程，走桥接等于在测 docker 的 NAT。
- 分核（见 Q7.2）：应用 `0-3,8-11`、依赖容器 `4-5,12-13`、k6 `6-7,14-15`；M8 每实例各一对
  `0,8` / `1,9` / `2,10`，nginx `3,11`。
- 机器信息是脚本自己记进 `manifest.json` 的：`nproc`、`free -g | awk 'NR==2 {print $2" GB"}'`、
  `uname -r`、`cat /proc/loadavg`、以及当时还有哪些别的容器在跑。**诚实一点：CPU 型号那一列在
  manifest 里是空的**——`lscpu | sed -n 's/^Model name: *//p'` 在这台机器上没取到值，我只能说 16 个逻辑核。
- 这台机器上还跑着别的项目的未绑核容器，`load_at_start` 常年在 5~8，这是背景噪声，所以跨天数字不相减（Q7.8）。
- 场景参数也是写死在脚本里的，例如正式 m3 的阶梯是 `500 1000 2000 5000 10000 15000 20000 25000 30000` 九档、每档 30 s、每档一张新券库存 1000。

**可能的追问**：→ Q7.2（为什么分核）；→ Q7.6（那 25.5k 是谁的上限）；→ 「为什么不用 JMeter」见 Q7.3。

**别踩**：不要说「压测机独立部署」——不是，是同机分核，被问一句就穿帮。也不要把单机拐点说成生产容量：
报告里写的是「单机测得的是这台机器上的拐点和扩展趋势，不是生产容量」，「万级」只能论证成
「单实例实测值 × 已验证的水平扩展性 + 无共享瓶颈的设计说明」。

### Q7.2 为什么要分核（`taskset -c`）？不分核会怎样？  〔常见｜追问链：分核 → taskset 和 cgroup cpuset 区别 → 为什么核号成对 → 多实例为什么每实例独占核〕

**答**：一台机器上同时跑被测应用、依赖容器和压测客户端，不分核三方互相偷 CPU，
结果是「应用变慢」和「压测客户端自己跑不动了」在数字上完全分不开，拐点是假的。
分核之后 `summary.csv` 里连 k6 自己用了几个核都是一列，这一列满了这一档就要打折看。

**展开**：
- 宿主机进程用 `taskset -c 0-3,8-11 ~/.jdks/temurin-21.0.12.1/bin/java -Xms2g -Xmx2g -jar current.jar`，
  写在命令前面，让进程一出生就带着亲和性掩码；容器用 `docker update --cpuset-cpus 4-5,12-13 ld-m3bench-mysql`，
  改的是已经在跑的容器的 cgroup，不用重建。
- `taskset` 设的是进程亲和性掩码，进程自己可以改回去；cgroup 的 cpuset 是外部强加的上界。所以宿主机进程用前者、容器用后者。
- 核号成对是因为开了超线程：`n` 与 `n+8` 是同一个物理核的两个逻辑核，按物理核分配才不会让两份负载在同一个物理核上互相拖。
- M8 给每个实例**独占**一对核，而不是把 8 核切成三份：切固定预算测出来的只是多开进程的开销，测不出扩展性。
  代价必须跟着说——**M8 的曲线是「每实例 2 核」的曲线，不能和 M0–M6 的「一个实例 8 核」直接比**。

**可能的追问**：→ Q7.6；→ 「`docker update` 和重建容器有什么区别？」；→ 「绑核会不会让 NUMA 更糟？」（这台机器单路，我没测过 NUMA，直说没测）。

**别踩**：别说「分核提升了性能」——分核不提升性能，它只让数字可归因；也别把 `taskset` 说成隔离，它只是亲和性，不限额。

### Q7.3 开环压测和闭环压测的区别？你为什么选开环？  〔常见｜追问链：JMeter 结果 → 闭环为什么测不出过载 → dropped_iterations 是什么 → 拐点定义〕

**答**：闭环是固定并发，线程发完一个请求要等响应才发下一个——系统越慢我压得越轻，
所以永远测不出拐点、也永远不会过载，延迟曲线被系统自己压平了。开环是固定到达速率，
请求按我指定的速率到达、与系统回得快不快无关。**到达速率是自变量、响应是因变量，拐点才有定义。**

**展开**：
- 反面证据就在这个项目里：V1 的那个数是 JMeter 1000 线程 / 5 s ramp-up 得到的 **208 req/s**。
  那是发压速率不是系统容量。V2 全换成 k6 的 `constant-arrival-rate`。
- 开环下系统跟不上表现为两件事：延迟上升、以及客户端到点了却没有空闲 VU 去发，被记成 `dropped_iterations`。
- 所以口径固定为：**拐点 = p99 < 100 ms 且丢弃 < 1% 的最高一档**（Q7.5）。
- 不是工具问题是模型问题——JMeter 也有到达速率模式，我换 k6 是因为它容器化、`--summary-export` 出 JSON 好取数。

**可能的追问**：→ Q7.4（`dropped_iterations` 大了怎么办）；→ Q7.5。

**别踩**：不要把 `dropped_iterations` 说成「系统拒绝了请求」——它是**客户端没发出去**，恰恰说明这一档的
`achieved_rps` 是客户端上限不是服务端的。这两者说反，整套方法论就垮了。

### Q7.4 一次运行怎么判断可不可信？预热、时长、排空你分别看什么？  〔高频｜追问链：一次运行可信吗 → 预热做了什么 → 怎么防止把脏代码的结果当数 → 失败了环境怎么办〕

**答**：我的默认立场是「一次运行不可信」，要过四道关卡才采信。开跑前 preflight 五件事任一不满足直接拒绝；
跑完先看 `status` 是不是 `DONE`；再看 k6 的丢弃数、实际到达率和 k6 自己吃了几个核；
最后看 `manifest.json` 里的 loadavg 和同时在跑的容器。**冒烟运行的数字永远不进结论。**

**展开**：
- preflight（`scripts/bench.sh` 里逐条能 grep 到）：
  - 工作区必须干净——`git status --porcelain -uall -- . ':(exclude)benchmark/v2/*/[0-9]*-*/' ...`，
    输出为空才算干净，因为每一行结果都要对应得上一个 commit；冒烟才能用 `ALLOW_DIRTY=1` 放行，脏文件清单记进 manifest。
  - 端口：`ss -ltn "( sport = :24083 )" | grep -q LISTEN` 七个端口逐个查（Q7.14）。
  - 磁盘：`df -Pk <目录> | awk 'NR==2 {print int($4/1024/1024)}'`，不足 15 GB 拒绝——Broker 的 commitlog 和 ES 数据都落本地，
    ES 8.x 到 90% 水位就停止分配分片，表现是「ES 起来了但分片一直不分配」，很难查。
  - JDK 21 存在、`docker info` 连得上（「装了」和「daemon 连得上」是两回事）。
  - 一把文件锁：`exec 9>benchmark/v2/run/.scenario.lock` + `flock -n 9`，同时只允许一个场景在跑。
- 预热：每次测量前先以 **500 req/s 跑 30 s**（脚本里 `S_WARMUP_RATE=500; S_WARMUP_DURATION=30s`），输出丢进 `raw/warmup/`，
  不进 `summary.csv`。没有它，第一档同时也是 JIT 第一次编译热点、连接池第一次建连、Tomcat 线程池第一次扩容的那一刻。
- 时长：正式阶梯每档 30 s；每档一张全新的券，断言「成功人数 = 库存」。
- 排空：一次把整批库存高速放进队列再量 MySQL 追上来要多久，取「已接收订单从 10% 到 90% 之间的斜率」，甩掉两头的爬坡与收尾；
  另一个更硬的口径是「负载停止时还剩多少积压」。
- 失败处理：每个阶段套 `timeout --kill-after=30 1500 ...`，`124` 记成超时、`137`（128+9）也是；
  清理挂在 `trap ... EXIT` 上，成功失败还是被中断都会拆掉自己起的栈——**但锁是确认拿到之后才装 trap 的**，
  否则一次被拒绝的启动会去拆正在跑的那一场的容器。

**可能的追问**：→ Q7.8（同场对照）；→ Q7.11（一次运行的完整阶段）。

**别踩**：别说「跑了三轮取平均」就完事——落库侧有双稳态（同一次运行里同一行被量到约 394 次提交/s 与约 73 次提交/s 两段），
平均掩盖问题；这里取的是中位，或者依赖批大小均值这种同配置两轮几乎不动的指标。

### Q7.5 你报的「拐点」是怎么定义的？为什么报拐点而不是峰值？  〔高频｜追问链：拐点定义 → 为什么不报峰值 → 天花板你也测了吗 → 拐点和 SLA 的关系〕

**答**：拐点固定指 **p99 < 100 ms 且丢弃 < 1% 的最高一档**。报拐点是因为峰值那一档往往已经是
「延迟爆了、还在硬撑」的状态，对用户没有意义；拐点是「还能对外承诺的量」。天花板我也一起报，
但它只说明余量，不当容量用。

**展开**：
- M0：拐点 ≈1 万 req/s（p99 63 ms），天花板 15.9k，15k 时是 Broker 先流控。
- M3：同场对照里拐点 **5k → 20k**（p99 83 ms），天花板 13.2k → ≥26.2k。
- 「≥26.2k」这个写法本身就是诚实的产物：那一档还没把系统压垮，我只能说不低于这个数。
- 两个数各有用途：拐点给承诺，天花板给余量。M1 升级 JDK/框架那一轮就是典型——天花板 14.5k → 17.5k、
  10k 档 p99 73.7 → 51.8 ms、CPU −20%，但**拐点仍是约 1 万**，换来的是余量不是拐点。

**可能的追问**：→ Q7.8；→ 「p99 为什么不是 p999？」（这台机器的样本量与噪声支撑不住 p999，我没报）。

**别踩**：M3 的「5k → 20k」里的 5k 是**同场对照组（上一个 tag 的 jar）那一轮**测到的，和 M0 那天单独测到的
「约 1 万」不是同一场，按口径两者不能相减，也不该并排读成「拐点退回去了」。这句话要主动说，不然面试官自己翻出来会很难看。

### Q7.6 准入侧 1/2/3 实例数字几乎一样，是不是说明你的系统不能水平扩展？  〔坑｜追问链：曲线重合 → 是系统的问题吗 → 你怎么证明是客户端 → 那怎么才能测出来〕

**答**：不是，这条曲线**测不出扩展性，而且原因不在系统**：压测客户端先满了。
1/2/3 个实例在 30k 档分别是 **25498 / 25573.6 / 25625.1 req/s**，三条线重合；
同一行的 CPU 列说明一切——**k6 在自己的 4 个 vCPU 上吃到 3.52–3.58 核**，而三个实例加起来只用了 1.26 核
（各自 2 核共 6 核），nginx 只用了 0.59 核（共 2 核）。M3 之后一次准入几乎不花钱，所以这个数是由客户端决定的。

**展开**：
- 「客户端 CPU 也是一列」这个设计就是为这一刻准备的：`k6_cpu_cores` 取的是 k6 容器自己的 cgroup 累计量，
  由一个后台采样子进程每 0.5 秒写一次文件（容器一退出文件就没了）。
- 所以我在报告的「已知边界」里写死了一句：**任何「水平扩展提升了准入吞吐」的说法都不能从这份数据得出。**
- 要真测准入侧的扩展曲线，得换多机压测：把 k6 放到另外几台机器上，被测应用独占本机；
  这是业界的标准做法（分布式压测，多个 load generator + 一个汇总），**本项目没做**，代价是我现在没有准入侧的扩展曲线。
- 能测的那一半我测了：落库侧客户端卡不住（单子先全部进队列），答案见 Q7.7。

**可能的追问**：→ Q7.7；→ 「你怎么知道不是 nginx 的问题？」——`edge.csv` 里 nginx 只用 0.59 核（共 2 核），曲线不线性时先看它。

**别踩**：千万别顺着面试官说「三条线重合说明我的系统扩展性好/差」。两个方向都是错的：这份数据对扩展性
**没有判别力**。主动承认一个测不出来的实验，比硬解释强得多。

### Q7.7 落库侧三个实例烧了三倍 CPU 只多落约 25% 的单，瓶颈在哪？你怎么证明的？  〔坑｜追问链：为什么不扩展 → 瓶颈在哪一层 → 怎么排除 MySQL 整体 → 为什么不拆那一行〕

**答**：瓶颈是**那张券库存表的同一行**（`tb_seckill_voucher.stock`），每个批次落库都要更新它。
1/2/3 实例的落库中位是 2415 / 2435 / 3026 单/s，应用 CPU 1.41 → 2.7 → 4.0 核，而 **MySQL 只用了 0.24 核（共 4 核）**——
CPU 没打满说明卡的不是 MySQL 的算力，是那一行的行锁。行锁不会因为多了两个进程而变快。

**展开**：
- 关键证据是一个折算量：**落库速率 ÷ 批大小 = 提交次数/s**，实测在 **70–115 之间，与实例数没有关系**。
  报告里那张表逐轮列了：1 实例 2246.2 / 2583.9 单/s、批 27.3 / 29.0、提交 82 / 89；2 实例提交 90 / 71；3 实例提交 86 / 115。
- 这个结论不是事后找补：M6 就把回归条件写死了——「到达速率远高于 2000/s、负载后积压重新大于 0、
  且落库速率 ÷ 批大小不再随负载上升」。M8 这一轮**三条同时成立**（2 万/s、3.4–7.6 s、70–115 无趋势），
  所以「那一行是写路径水平扩展的上限」从推断变成实测。
- 同一个结论在更早的里程碑还有独立旁证：M0 的火焰图里消费线程 **44.7% 花在那一行的行锁上、49.5% 在连接池等待**。
- 结论的另一半也要说：**这一条已测实、尚未修**。怎么修有方案——按券分桶扣减 + 定期合并，或者把库存从 MySQL 移走；
  代价是一个批次要尽量来自同一个桶，否则一个事务持 K 个行锁、竞争更糟，那是比加一张表大得多的改动。

**可能的追问**：→ 「那 80 次/s 是上限吗？」——不是，同一次运行里同一行被量到过约 394 次/s，M4 时写的
「一次提交上限约 80 次/s」这个前提本身是错的，80 是双稳态的慢档；→ Q7.10（火焰图）。

**别踩**：别说「MySQL 是瓶颈」——太粗，会被追着问「MySQL 哪一层、CPU 还是 IO 还是锁」，而我有数据：CPU 0.24 核，
所以是锁不是算力。也别说「加机器就能扩」——这份数据恰好证明写路径加实例只加 CPU、不加吞吐。

### Q7.8 优化前后各是多少？你怎么排除机器波动？  〔高频｜追问链：前后对比 → 同场对照怎么做 → 基线包哪来的 → 差异在噪声里怎么办〕

**答**：全部用**同场对照**：同一次运行里、同一台机器、同一份分核、同一组参数，用上一个 tag 的 jar 和当前 jar 各跑一遍。
**跨天的数字我不相减**——这台机器不同时段快慢能差 10%，还跑着别的项目的未绑核容器。

**展开**：
- 基线包的做法：`git worktree add --detach benchmark/v2/run/m3bench/baseline-src v2.0-m5` 在另一个目录再检出一份工作区，
  共用同一个 `.git`、游离 HEAD 不建分支；然后
  `JAVA_HOME=~/.jdks/temurin-21.0.12.1 mvn -q package -DskipTests` 打包。
  **显式指定 `JAVA_HOME` 是为了保证基线和当前用同一个 JDK**，否则比的就不只是代码了；跑完 `git worktree remove --force` 掉。
  每个 commit 的 jar 会缓存并记下 commit，一夜四个场景不会把同样两个构建打四遍。
- 几组同场对照的结果（原样）：
  - M2 落库 189.4 vs 177.5，区间重叠，新增开销 < 2%——这一格的意义是「加了这么多业务没有变慢」。
  - M3 10k 档 p99 128 → 33 ms、应用 CPU 3.04 → 0.60 核、半消息从「等于请求数」变成 0。
  - M6 准入 10k 档 9936.5 → 9961.7 req/s（p99 68.3 → 58.6），20k 档 19725.1 → 19721.5（p99 87.3 → 101.0），无退化；
    落库中位 982.7 → 2088.9 单/s，积压 10.7 / 55.8 / 16.1 s → 0.1 / 0.1 / 0.1 s。
- 差异落在噪声里就如实写：**M5 的落库 A/B 写的是「无可测变化，而且这次量不出来」，不是「没有提升」**——
  九轮平均被双稳态决定，基线和 M5 混在同一条曲线上。这两句话在面试里完全不是一回事。

**可能的追问**：→ Q7.4；→ 「为什么不跑十轮取均值？」——落库侧双稳态下均值无意义，见 Q7.4「别踩」。

**别踩**：不要把 M0 那天的数字和 M3 那一场的对照组混着减（见 Q7.5「别踩」）。也不要报「提升了 N 倍」而不说口径——
M4 的 156.3 → 319.1 单/s 旁边必须跟着「目标 ≥3000 未达成」。

### Q7.9 压测里怎么核对没有超卖？对账是怎么做的、用了哪几条 SQL？  〔常见｜追问链：怎么验证正确性 → 用什么查 → 为什么不用应用自己的接口 → 分了表怎么数〕

**答**：每一轮压测的验收条件不是吞吐而是对账，而且对账**全部用宿主机的 `mysql` / `redis-cli` 命令行直查，
绕开应用自己的分库分表路由**——用被测系统自己的代码去证明被测系统对，是循环论证。

**展开**：
- 查券上剩余库存：
  `mysql -h 127.0.0.1 -P 24306 -u root -p'...' -N -B local_deals -e "SELECT stock FROM tb_seckill_voucher WHERE voucher_id = 42"`。
  `-N` 不打表头、`-B` batch 模式用 tab 分隔不画边框，合起来就是「给脚本读的格式」；`-p` 和密码之间不能有空格。
- 数订单要跨**两个库各四张表**共八张 `UNION ALL`，表名带库名限定：
  `SELECT COALESCE(SUM(c),0) FROM (SELECT COUNT(*) AS c FROM \`local_deals\`.\`trade_order_0\` WHERE voucher_id=42 UNION ALL ... ) counted`。
  表名不是写死的，先从 `information_schema.tables` 按「两个库、表名是逻辑名或逻辑名加下划线数字」查出来——
  这样同一条命令也能数分表前那个基线构建的单张逻辑表。
- 全链路那一条一句 SQL 出五个数：
  `SELECT COUNT(*), SUM(status NOT IN ('CLOSED','REFUNDED')), SUM(status='CLOSED'), SUM(status='PAID'), COUNT(DISTINCT IF(status NOT IN ('CLOSED','REFUNDED'), user_id, NULL)) FROM (<八张表 UNION ALL>) o`。
  `SUM(布尔)` 是 MySQL 数条件行的惯用法；`COUNT(DISTINCT IF(cond, user_id, NULL))` 数去重买家（`COUNT DISTINCT` 不数 NULL）。
- 判据：**在册订单数 == 上架库存**（既没超卖也没少卖）、**在册订单数 − 去重买家数 == 0**（没人买到两张）、
  关单数与已付数比例对得上、Redis 各桶库存求和 == 0、DB 库存 == 0、残留预占 == 0、残留处理中 == 0。
- Redis 侧按桶逐个查再相加：`redis-cli -c -h 127.0.0.1 -p 21001 -a ... GET "sk:{sk:b3}:stock:42"`。
  `{}` 是 hash tag，Cluster 只对花括号内的部分算 slot，所以同一个桶的库存、预占、处理中索引必然同节点。
- 实战结果：全链路那一轮成功单 **1000 = 库存**，249 件因超时关单回补**并被第二波全新买家再次抢完**
  （这一步才证明回补是真的、不只是改了个状态），三个实例各接 422 / 424 / 403，零超卖零重复零残留。

**可能的追问**：→ Q7.12（演练里的对账）；→ 「为什么不用 `--json`？」——要的是能直接参与 shell 算术的裸标量。

**别踩**：别说「Redis 保证不超卖」。这个项目的结论恰恰相反：Redis 是允许丢的准入层，复制空窗那四轮里
Redis 最多多放了 10.3% 的人，**MySQL 每一轮都恰好建了 30000 单、超卖恒为 0**——最后防线是数据库的条件更新。

### Q7.10 火焰图你怎么采的、怎么读的？看到了什么？  〔常见｜追问链：怎么定位 CPU 热点 → 用什么工具 → 火焰图横轴是什么 → 和 jstack 区别〕

**答**：用 async-profiler，入口是 `scripts/bench.sh profile 30 seckill-hot`，内部执行
`asprof -d 30 -e itimer -f raw/seckill-hot.html <pid>`。**`-e itimer` 而不是默认的 `cpu`，
是因为这台机器 `perf_event_paranoid` 大于 1，拿不到 perf 硬件事件的权限**，只能退到基于定时器信号的采样。
最有价值的一次是 M0：消费线程 **44.7% 花在券库存那一行的行锁上、49.5% 在连接池等待**。

**展开**：
- 参数：`-d 30` 采 30 秒、`-f xxx.html` 直接出可交互火焰图、最后一个参数是目标 JVM 的 pid。
- 另一个常用事件是 `-e wall`（墙钟采样），能看见**阻塞中的线程**——「接口慢但 CPU 不高」时要看的恰恰是它们，
  CPU 采样根本看不见在等锁、等 IO 的线程。
- 怎么读：**横轴不是时间、是样本数占比**，格子越宽表示采样时越经常「正在执行它或它的子调用」；
  纵轴是调用栈深度，向上是被调用方。看法是从底往上找第一个「宽得不合理」的格子，那是热点入口；
  顶上那片同宽的平顶是真正在烧 CPU 的叶子方法。
- 和 `top -H` + `jstack` 的区别：后者是手动稀疏采样、还会 safepoint 暂停；async-profiler 高频采样、
  支持 wall / alloc / lock 多种事件，开销小得多。**`top -H` / `printf '%x'` / `jstack` 这条链是通用做法，本项目未实际用到**——
  这台机器上的问题是用火焰图 + actuator 指标 + CSV 列定位的。

**可能的追问**：→ Q7.7（那一行）；→ 「火焰图里看到连接池等待，你怎么改的？」（M4 的批量落库把每单一次提交变成每批一次，详见笔记 05）。

**别踩**：别把火焰图横轴说成时间轴，这是最常见的翻车点。也别声称自己用 `jstack` 抓过热点线程——这个项目没有，说了会被追细节。

### Q7.11 一次 `bench.sh` 运行从头到尾发生了什么？每个阶段对应哪些命令？  〔常见｜追问链：流程 → 为什么要隔离栈 → 结果目录怎么读 → 卡住了怎么办〕

**答**：骨架是一条：**启动前检查 → 起隔离栈 → 分核 → 打包 → 预热 → 阶梯/排空 → 采集 → 演练 → 对账 → 清理**。
整场无人值守，所以第一件事是挂后台：`nohup scripts/bench.sh m8 > /tmp/m8-bench.out 2>&1 &`。

**展开**（每阶段一条代表命令，细节见笔记 12 第八节）：
- 检查：见 Q7.4 的五件事 + `flock`。
- 起栈：`docker compose --project-name ld-m3bench --project-directory . --env-file /dev/null --file docker-compose.yml up -d mysql redis namesrv broker elasticsearch`。
  `--project-name` 是隔离的根（删的时候只删这个 project）；**`--env-file /dev/null` 是明确不读 `.env`**，
  否则开发栈的配置会悄悄污染这套栈的端口和密码，这种污染极难发现。这条 `up` 外面包了三次重试，
  因为 docker 偶尔拒绝把容器挂到刚建的 bridge 网络上（`bridge port not forwarding after 200ms`）。
  集群模式另起一套 project，用 `redis-cli ... --cluster create <六个地址> --cluster-replicas 1 --cluster-yes` 成环，
  再轮询 `CLUSTER INFO` 里的 `cluster_state:ok`。topic 和消费组显式建：
  `docker exec ld-m3bench-broker sh mqadmin updateTopic -n namesrv:9876 -c ld-m3bench -t seckill-order-topic`——
  显式建是为了让队列数确定，自动创建出来的队列数会影响消费并行度，而那正是被测量的东西。
- 分核、打包、预热：见 Q7.2、Q7.8、Q7.4。
- 阶梯 / 排空：见 Q7.1、Q7.3。
- 采集：**不是 `docker stats`**，而是前后各读一次累计量再相减。应用读 `awk '{print $14+$15}' /proc/12345/stat`
  （第 14、15 字段是 utime/stime，配 `getconf CLK_TCK` 换成秒，多实例时把各 pid 相加）；
  容器读 `/sys/fs/cgroup/cpu,cpuacct/docker/<完整 Id>/cpuacct.usage`（纳秒累计，容器 Id 用 `docker inspect -f '{{.Id}}'` 取）。
  核数 = (后 − 前) / 1e9 / 墙钟秒。**已知代价：平均核数会掩盖尖峰。**
  每轮结束前还要趁应用活着抓一次 `curl -fsS --max-time 20 http://127.0.0.1:24184/actuator/prometheus -o raw/....prom`——
  批大小分布和退化计数只活在进程内存里，应用一停就没了（M4/M5 就是吃了没仪表的亏）。
- 演练与对账：Q7.12、Q7.9。
- 清理：`trap ... EXIT` 里归档日志、停应用、`docker unpause` 可能还暂停着的 broker、拆栈和 volume、删 worktree、把 `status` 从 `RUNNING` 改成终态。
- 每阶段超时：`timeout --kill-after=30 1500 scripts/bench.sh _phase drain_round current`（先 TERM，30 秒不死补 KILL）。
  因为 `timeout` 只能跑外部命令不能跑 shell 函数，脚本是重新 exec 自己带一个内部子命令来执行那个函数的。
- 结果目录读法：`status`（不是 `DONE` 就不分析）→ `manifest.json` → `summary.csv` → `run.log` / `raw/`。

**可能的追问**：→ Q7.13（`nohup` 各部分什么意思）；→ 「为什么不用 `&` + `sleep` + `kill` 自己实现超时？」——`timeout`
已经处理好进程组、信号转发和退出码语义，自己写的在被测进程 fork 了子进程时几乎一定会漏杀。

**别踩**：别说「用 `docker stats` 采的 CPU」——这个项目没有用它采数（只在肉眼看实时负载时用）；说错了下一问「那你怎么拿到窗口内的精确用量」就接不住。

### Q7.12 `kill` 和 `kill -9` 的区别？演练为什么必须用 -9？  〔高频｜追问链：信号区别 → 为什么演练要 -9 → 那你日常怎么停服 → docker kill/stop 呢 → 收敛怎么判定〕

**答**：`kill` 默认发 `SIGTERM`(15)，**可以被捕获**——JVM 会跑关闭钩子、Spring 会优雅停机（连接排空、消费者反注册、线程池 shutdown）；
`kill -9` 发 `SIGKILL`，**内核直接回收进程，不能被捕获也不能被忽略**，一行钩子都不跑。
演练必须用 -9，因为我要模拟断电 / OOM killer / 容器被强杀这类**没有机会收尾**的崩溃；
用普通 `kill` 的话优雅停机会把半截状态收干净，验证的就成了优雅停机而不是崩溃恢复，恰好把最想验的那条路径绕过去。

**展开**：
- 演练怎么敲：`benchmark/v2/scripts/kill-drill.sh 20000 2000 6`（三个位置参数是「库存、到达率、第几秒动手」），
  里面是 `kill -9 "$(cat benchmark/v2/run/m3bench/app.pid)"`。第 6 秒下手是挑在售罄之前，让它死的时候手里正好攥着上万条预占。
- 收敛是一个**可判定的谓词**，不是肉眼看曲线：重启后每两秒轮询一次，直到**预占数等于订单数且处理中索引为空**（详见笔记 05 的对账器）。
  结果：M3 两轮 102.8 / 102.7 s、M4 批量化后 44.7 s、M5 上 Cluster 后 56.8 s，三个版本都是预占 = 订单、Redis 库存 = DB 库存、无残留处理中。
- 变体 `BROKER_DOWN=1` 先在第 4 秒 `docker kill` 掉 broker 再杀应用，造出「准入脚本已经成功、消息却从没进 Broker」的预占——
  正是对账器必须重投的那一类。M3 那一轮重投了 4249 单、三方一致收敛，代价 574.2 s；M4 是 572.1 s，
  **因为对账器本身没有批量化**，与预期一致。
- 日常停服是另一条路，形状正好相反：`scripts/stack.sh app-stop` 先 `kill`（TERM），然后每秒轮询最多 30 次等它自己退，
  仍然活着才 `kill -9` 兜底。
- `docker kill` 和 `docker stop` 的关系与此完全对应：`kill` 直接 SIGKILL，`stop` 先 SIGTERM 再等宽限期。演练要前者。
- 顺带一条：`flock` 的锁挂在打开的文件上，**进程被 `kill -9` 内核也会释放**，这正是它比写 pid 文件可靠的地方。

**可能的追问**：→ 「SIGKILL 和 SIGSTOP 有什么共同点？」（都不能被捕获/忽略）；→ Q7.9（演练后怎么对账）。

**别踩**：别说「kill -9 是强制杀进程所以更好用」——日常停服用 -9 会丢掉优雅停机，消费者不反注册、连接不排空，
反而制造脏局面。要讲清楚这是**两个场景两种用法**。

### Q7.13 怎么后台跑一个长任务、不怕终端断开？  〔常见｜追问链：nohup 各部分 → 2>&1 顺序 → 和 setsid/tmux 区别 → 怎么看进度〕

**答**：项目里真实用的是 `nohup scripts/bench.sh m8 > /tmp/m8-bench.out 2>&1 &`，一整夜四个场景挂在后台。
四个部分各管一件事，缺一不可。

**展开**：
- `nohup` —— 让进程忽略 `SIGHUP`。终端关掉或 ssh 断开时内核会给前台进程组发 HUP，默认动作是终止。
- `> /tmp/m8-bench.out` —— 重定向 stdout。**不重定向的话，终端一没，写 stdout 会拿到 `SIGPIPE` 或 EIO，照样死。**
- `2>&1` —— 把 stderr 复制到「stdout 当前指向的地方」。**顺序关键**：必须写在 `>` 后面；写成 `2>&1 > file` 的话 stderr 还留在终端上。
- `&` —— 放进后台作业。
- 区别：`nohup &` 只解决 HUP 和输出两件事，进程仍在原会话里；要彻底脱离会话用 `setsid`；要能回去交互用 `tmux`；
  要当服务管用 `systemd-run`。这里不需要交互，所以用最轻的那个。
- 看进度：`/tmp/m8-bench.out` 只是 stdout 的兜底，真正的过程日志在结果目录的 `run.log` 里，我用
  `tail -f benchmark/v2/m8/<目录>/run.log` 或 `less` 看（`less` 里 `/` 搜索、`G` 跳末尾、`Shift+F` 等效 follow 且能 Ctrl+C 退回浏览）。
  **诚实标注：`tail -f` 和 `less` 是我人工敲的，不在脚本里；脚本里用的是 `tail -1` 取子命令最后一行和 `grep`。**

**可能的追问**：→ 「`tail -f` 和 `tail -F` 区别？」（`-F` 能跟上文件被轮转）；→ Q7.11。

**别踩**：别把 `nohup` 说成「让进程在后台跑」——放到后台的是 `&`，`nohup` 只管 HUP 和默认输出重定向。这题考的就是这个区分度。

### Q7.14 端口被占了怎么看？`ss` 和 `netstat` / `lsof -i` 有什么区别？  〔常见｜追问链：怎么查端口 → ss 为什么快 → 怎么知道是谁占的 → 临时端口段是什么〕

**答**：脚本 preflight 里用的是 `ss -ltn "( sport = :24083 )" | grep -q LISTEN`，对 MySQL / Redis / NameServer /
Broker / ES / 应用 / management 七个端口逐个查，命中就直接拒绝启动。`-l` 只看 listening、`-t` 只看 TCP、
`-n` 不做端口名和主机名反解（快，且输出稳定好 grep）；括号里是 ss 自己的过滤表达式，`sport` 是源端口。

**展开**：
- `ss` vs `netstat`：`ss` 直接读内核的 netlink（`sock_diag`），`netstat` 是去遍历 `/proc/net/*` 文本，连接一多慢一个数量级；
  而且 `netstat` 在新发行版上已经不默认装了。
- `lsof -i` 强在反查「哪个进程持有这个 fd」，但它要扫全部进程的 fd 表，更慢。**分工**：查端口占用用 `ss`，查「谁占的」用 `lsof -i :端口` 或 `ss -ltnp`（`-p` 要权限）。
- 这个项目真被这件事坑过，值得讲：**整套栈的端口全压在 32768 以下**，因为这台机器的临时端口段是 32768–60999，
  一次压测在里面占着上百条连接；某次运行把一个本该监听的端口拿去当出方向源端口，下一个进程就 bind 不上了。
  **M8 的冒烟因此丢了四个场景里的两个**，报错看起来像「多实例有问题」，其实完全不是。
  另外 Redis 6.2 的集群总线固定在客户端端口 +10000 且只有「宣告值」可配，所以客户端基数还必须小于 22768。
- `app-stop` 之后也会逐个等端口释放（每秒轮询最多 60 次），而不是让 Tomcat 自己去发现问题再把整个阶段拖垮。

**可能的追问**：→ 「TIME_WAIT 太多怎么办？」——`ss -s` 看各状态汇总，`timewait` 巨大通常是短连接没复用；
**这条是通用做法、本项目未实际用到**，项目里对应的事实是 nginx 到上游用 keepalive 长连接
（`keepalive 512`、`keepalive_requests 100000`、`proxy_set_header Connection ""`、`proxy_http_version 1.1`），
理由写在配置旁边：不这么做测出来的是 TIME_WAIT 的性能而不是应用的。

**别踩**：别把 `ss -ltn` 说成能直接看出「谁占了端口」——不加 `-p` 看不到进程。也别说 `netstat` 和 `ss` 只是别名，
数据来源不同是这题的考点。

### Q7.15 三层测试各怎么跑？并发竞态的集成测试你是怎么制造出两种交错的？  〔常见｜追问链：三层怎么分 → mvn test 会跑 IT 吗 → 并发测试不 flaky 吗 → 怎么保证两种顺序都测到〕

**答**：三层是单元/切片、集成（IT）、压测/演练，成本差两个数量级，写代码时的循环永远在第一层。
仓库里现在有 **104 个 `*Test` 和 47 个 `*IT`**。竞态用例的核心技巧是：
**确定性的一半 + 闩锁并发的一半，再把「先手时延」编进 20 轮循环，最后断言两种赢法都至少出现过一次。**

**展开**：
- 第一层：`mvn -o test`（`-o` 离线）。这里有个容易答错的点：`pom.xml` 里**没有**任何 surefire / failsafe 配置，
  surefire 的默认包含规则是 `Test*` / `*Test` / `*Tests` / `*TestCase`，**`*IT` 不在里面**（那是 failsafe 的规则，本项目没引）。
  所以 `mvn test` 一个 IT 都不会起；47 个 IT **只能靠 `-Dtest=` 点名**。
- 第二层两套依赖：`LOCAL_DEALS_IT_CONTAINERS=true` 时一个 `ApplicationContextInitializer` 起 MySQL 8 与 Redis 6.2 容器
  （每个 JVM 只起一次、所有上下文共享，测试树里没有一个 `@Testcontainers` 注解）；不设开关就连 `scripts/stack.sh up` 起的隔离栈。
  本机完整顺序：`scripts/stack.sh up` → `eval "$(scripts/stack.sh env)"` → `scripts/stack.sh it '*IT'`，
  集群相关的要带 `REDIS_MODE=cluster`（`it` 只认这一次调用上的变量，忘了带就还是连单节点，最容易踩）。
  CI 里是 `mvn -B test -DfailIfNoTests=false -Dtest='*IT,!SeckillWithRocketMQIT,!...'`——需要真 Broker 或真 ES 的六个类被排除，
  所以**「CI 绿」不等于「全部 IT 绿」**，它们只能本机补跑。另有 19 个 IT 用 `@EnabledIfEnvironmentVariable` 门控，
  没有任何脚本替你设，跑就得自己带变量。
- 第三层：`scripts/bench.sh <场景>`，见 Q7.11。
- 竞态怎么造两种交错：
  1. **先手那一半（确定性）**：把顺序钉死——先让订单过期、先把关单执行完，再投递支付回调，断言返回是「自动退款」
     而不是「支付成功」，且订单仍是关闭态、没发券、退款记录恰好一条、库存已还回。这一半百分之百可复现。
  2. **闩锁那一半（真并发）**：一个计数为 1 的 `CountDownLatch` 当发令枪，任务进池后先 `start.await()` 停住，
     主线程等全部提交完再 `countDown()`；有的用例还加一道 `ready` 闩确认线程都到位，把线程创建开销也排除掉。
     断言是「恰好一个赢」：同一用户同一券八个线程并发下单，一个成功、七个拿到预占冲突、库存只少 1。
  3. **关键的第三步**：光靠闩锁，在某台机器上可能总是同一方赢，另一种交错从来没测到而测试还是绿的。
     所以把**先手时延编进循环**——同一场景跑 20 轮，前 10 轮同时起跑，第 11–15 轮给一方 20 毫秒先手，
     第 16–20 轮把先手让给另一方，每轮按最终状态判定谁赢并断言那一方的完整后果，**最后断言两种赢法都至少出现过一次**。
     这样「这台机器上另一种交错从没发生」会让测试变红，而不是悄悄变成只测了一半的绿。
  4. 还有第四种机制：用额外两道闩**把一方钉死在临界区里**（被测代码进临界区时倒数一道，主线程验证完再倒数另一道放它走），
     于是可以在领跑者还没出来的窗口里断言其余三十一个线程确实是以跟随者身份共享结果；也可以在这个窗口里让一个跟随者超时或被中断，
     证明它不会取消领跑者、不会删在途记录、不会另起一次加载。纯闩锁做不到这种「窗口内断言」。
  5. 测试 profile 把后台的批量消费者、扫描任务、点赞投影 worker 全关掉——否则断言那一刻是谁写的数据说不清，竞态用例会变成随机红。
     要测消费链路就在用例里手工调一次处理方法。
- TDD 的证据在 git 历史里：333 个提交中 32 个标题结尾带 `(red)`，`git log --oneline --grep='(red)'` 能列出来；
  `git show --stat <红> <绿>` 摊开看——红的只动 `src/test/`，绿的只动 `src/main/`、测试文件一行没碰。

**可能的追问**：→ 「并发测试不是很容易 flaky 吗？」——正因为怕 flaky 才拆成两半：确定性那一半管「逻辑对不对」，
并发那一半只断言「恰好一方赢、赢的一方后果自洽、两种赢法都出现过」，这三条都不依赖调度顺序。
→ 「更强的做法是什么？」

**别踩**：不要把「两种交错都跑到」说成形式化保证——**它是靠时延先手争取来的**，能挡住「这台机器上另一种顺序从没发生还一直绿」，
但挡不住「存在第三种更罕见的交错」。真正能穷举交错的是确定性调度工具（JPF、Lincheck 这类），**本项目没有用**。
也别说 `-DfailIfNoTests=false` 是无害参数——它会掩盖「我的测试根本没跑」，必须配合看 `Tests run` 的数字，不能只看 `BUILD SUCCESS`。

## 11. 可观测与排障

### Q11.1 一次请求的全链路怎么串起来？异步线程和 MQ 里 traceId 怎么续上？哪些链路没覆盖？  〔高频｜追问链：你怎么定位一次下单 → traceId 从哪来 → MDC 是 ThreadLocal，线程池怎么办 → MQ 跨进程怎么传 → 为什么不上 SkyWalking/Jaeger〕

**答**：没有分布式追踪系统，只有一个 32 位十六进制的 id 串三跳：nginx 用 `$request_id` 生成并写进访问日志、转成 `X-Trace-Id` 头；应用最外层的过滤器把它放进 MDC，日志格式串里的 `%X{traceId:-}` 让每一行日志自动带上；下单发消息时把它从 MDC 搬进消息体，落库时写进 `trade_order.trace_id` 这一列。所以一个买家「打到哪台实例、被哪台实例落的库、一分钟后是被谁关掉的」能从数据里查回来，而不是靠猜。覆盖面我得先说清楚：**HTTP 是全量的，MQ → DB 这一跳只接了秒杀链和关单链**，支付回调链和营销发放链没接。

**展开**：
- **第 0 跳（边缘）**：nginx 里一个 map——调用方带了头就用它，没带就用 `$request_id`；访问日志格式第一列就是这个 id，后面是上游地址、状态码、请求耗时，所以「打到哪个实例、耗时多少」在应用之外就能回答。证据：runbook 第 7 节第一条命令 `grep '<traceId>' .../access.log`。
- **第 1 跳（HTTP → MDC）**：`TraceIdFilter` 注册成最高优先级，排在所有过滤器和拦截器之前——被准入漏斗第一层售罄标记挡掉、被登录校验挡掉的请求恰恰最值得查，晚一步它们就没有 id。外来的头先过 `TraceContext.accept`：非空、≤64 字符、只允许字母数字连字符下划线，**不合法直接换新的，绝不修补**（它会进这次请求的每一行日志，能塞换行的人就能伪造日志行）。响应头在 `chain.doFilter` 之前就设，因为业务可能提前提交响应，之后设头会被无声丢掉；`finally` 里把 MDC 清空，因为容器线程复用。异步派发也走这个过滤器（`shouldNotFilterAsyncDispatch` 返回 false），否则异步那一段会掉 id。
- **第 2 跳（MDC → 消息体）**：秒杀消息体上多一个 traceId 字段，发送时**只在消息体还没有 id 时才从 MDC 取**。要讲准：目前另一个发送方是对账器，它从 Redis 预占重建的消息压根不带 id、它那条定时线程 MDC 也是空的，所以这个判断在今天的代码里从没救回过一个 id，它真正保证的是「任何重投都不会伪造一个 id」——代价是这类订单那一列为空，而空值本身有信息量：说明这单不是某次请求直接建的。
- **第 3 跳（消息体 → 订单行）**：**批量路径不往 MDC 写任何 id**，因为一个批次里混着几百个买家、批次不属于任何一个 trace；每条消息的 id 只是随 `INSERT IGNORE` 写进那一行的字段。只有退化到单条路径时才 `TraceContext.runWith` 装上、执行完还原。从消息体拿出来的 id 在写库、装线程、塞进关单消息之前都要再过一遍同一道 `accept` 校验，因为它同样来自进程外。
- **为什么落库用列不用 SQL 注释**：批量 INSERT 没有单一 trace，注释写谁都不对；每请求不同的注释会让预编译语句文本每次都变，等于在热路径上扔掉语句缓存；而且列比日志轮转活得久。这一列是 `varchar(64) ascii_bin` 且可空（迁移 V17，业务库与分片库两套 Flyway 各加一次）。
- **第 4 跳（时间上的一跳）**：落库成功后给关单主题发定时消息，带着买家的 id；关单消费者 `runWith` 把 id 装到池化的消费线程上、执行完还原，于是「未支付订单已关闭」那一行和当初那次下单共用一个 id，落在三个实例哪一个上都无所谓。M8 全链路演练最后一步就是拿一个已关闭订单的 trace 反查，从 nginx 访问日志一路对到 `trade_order.trace_id`（ADR 0009「实测」第 1 条）。
- **为什么不上 OTel / SkyWalking**：要回答的问题很具体——一个买家跨三个实例的一条链，MDC 里一个 id 加一列字段就够；引入完整追踪体系要多跑采集器和存储，而且**订单行上那一列是追踪系统给不了的**（追踪数据有保留期，订单行没有）。代价写在下面。

**可能的追问**：→ Q11.2；→「批量落库的日志你怎么查？」（只能靠券 id、批大小、时间去对，逐条级别的还带订单号，可以从订单号反查回 trace）；→「不合法的头为什么不修补？」；→「MDC 在线程池里为什么会串？」；→ 详见笔记 11 第三节 3.1。

**别踩**：
- 不要说「实现了全链路追踪」。没有 span、没有父子关系、没有跨服务耗时拓扑，「这一跳花了多久」只能靠同一个 id 的日志行时间戳相减。
- 不要说「所有链路都带 trace」。MQ → DB 只接了秒杀与关单；支付回调、营销发放没接。
- 不要说「批量落库那台实例的日志能按 trace 查」。批量路径全程不写 MDC，那些日志行不带 id——订单行上有，日志行上没有。
- 不要把「对账器重投的消息带着原 trace」说成事实。ADR 0009 里那句话写得比代码乐观，**以代码为准：重建的消息不带 id**。
- 不要说日志是集中收集的。多实例时就是逐个实例的日志文件，按 id 查要一个文件一个文件 grep。

### Q11.2 你的指标有哪些？每个指标各回答什么问题？积压怎么观测？  〔常见｜追问链：有没有监控 → 埋了哪些指标 → 标签怎么设计 → 积压怎么发现 → 有没有告警和看板〕

**答**：指标走 Micrometer 暴露成 Prometheus 格式，端点挂在独立的管理端口、默认只绑 127.0.0.1，只开 health 和 prometheus 两个端点。我这边有一条硬规则：**任意字符串永远不会变成标签值**，所有维度都是枚举，并且在组件构造时把组合预先注册一遍。指标分三类：漏斗/缓存/认证这类「结局计数」、落库耗时与批大小这类「分布」、以及七个积压与年龄的 gauge。**没有看板、没有告警**——这是已知的缺口。

**展开**：
- **各个指标回答什么问题**：
  - 准入漏斗的放行/拒绝/不可用 + 拒绝原因 → 「这一批人是在哪一层被挡的、是限流还是售罄还是 Redis 不可用」。这一组是**手工列出真实搭配**注册的，不做叉乘，否则会造出「放行，原因是 Redis 故障」这种永远不发生的空序列。
  - 秒杀消费结局（十种枚举：已落库、已成功、已失败、认领被占、预占归属不符、状态缺失、已补偿、临时错误、补偿错误、格式错误）→ 「多放出来的人到底在哪一步被挡下」。复制空窗演练里这个问题的答案就藏在这几个计数器的相对大小里。
  - **批大小，故意分两个阶段量**：「Broker 投递给消费者的一批有多少条」和「一条 INSERT 加一次扣库存真正承载了多少单」。这两个数的差就是一次批量落库快或慢的全部故事——M6 一开头正是这个仪表量出**批大小实测 1.03**，把瓶颈从「提交速率不够」改判成「批根本没攒起来」。
  - 落库耗时（成功/失败两种）、批次退化原因、缓存命中与回源、认证结局、检索同步结果。
  - 两个和积压无关的 gauge：两种本地受限读资源当前握着的许可数。
- **积压怎么被看见**：可靠性靠几条异步补偿链（对账器、点赞发件箱、通知发件箱），它们的特点是不容易出错、只会变慢，**变慢的唯一表现就是积压**。所以两个采样器低频只读地把「待办条数」和「队头年龄」写成 gauge：点赞发件箱的待处理条数与最老一条年龄、热榜快照年龄、秒杀处理中索引里已到期的预占数与最老一条超期多久、券发放通知发件箱的条数与最老一条年龄，一共七个。
- **采样的节奏与自我约束**：整体一个开关（关掉时组件连实例都不创建），启动后先等 10 秒给依赖留连接时间，之后**固定延迟 30 秒**（不是固定频率，上一轮慢了不会堆出第二轮），配置校验**强制最小 15 秒**——采样要读库读 Redis，间隔太小观测本身就变成负载。
- **秒杀那一组稍微特殊**：库存分桶，所以待办数是各桶之和、最老超期取各桶最大值；每个桶跑一个只读 Lua，**脚本第一件事是取 Redis 服务端时间**而不是接受应用传进来的时间戳，因为多实例时钟不一定一致，只有服务端时间才能让「到期」在所有采样者眼里是同一个基准。
- **失败行为是这里最值得讲的**：任何异常都不往上抛，而是把这一组 gauge **置成 NaN** 并给这个采样器的失败计数加一。置 NaN 而不是留住上一轮的值，是因为留旧值会让一个已经瞎了的仪表看起来一切正常，那是监控里最危险的假象；抓取端看到 NaN 就知道「这个数现在不可信」，和「这个数确实是 0」完全区分得开。采样器自己的成功/失败也是计数器，所以「仪表为什么没数」本身也可观测——不过这只做到三个，券发放通知那个采样器只置 NaN、没有成对计数器，是个已知的漏。
- **为什么预注册**：一是基数封顶，指标长期驻留在注册表里，标签值一旦来自券 id、用户 id 或异常消息，注册表会随流量无限增长；二是让「零」也成为一个值，预注册之后一个从未发生过的结局也会以 0 出现在抓取结果里，看板不会因为序列不存在而画不出线，也不会把「没发生」和「没埋点」混为一谈。每一次自增、每一次耗时记录都包了 try/catch——**一个已经提交的批次不能因为指标出错而失败**。

**可能的追问**：→ Q11.4；→「积压之外怎么判断落库侧健康？」（看投递批大小与落库批大小的差，再看提交次数/秒——1/2/3 实例下都在 70–115 之间、与实例数无关，指向每批都要更新的同一行库存，详见笔记 12）；→「指标端点暴露在公网怎么办？」；→ 详见笔记 11 第三节 3.2、3.3。

**别踩**：
- 不要说「有监控告警」。**没有看板、没有任何阈值会主动通知人**；原计划里的 Grafana 看板在 M8 被砍掉了。NaN 也只是一个值，没人盯就没人知道。说到这里要主动承认。
- 不要说「积压仪表统一」。空积压的年龄在两处不一致：点赞发件箱条数为 0 时年龄写 0，券发放通知发件箱写 NaN。两种都说得通，但同一套仪表里应该统一，现在没有。
- 不要说「消费结局只有一套计数」。单条消费路径上还留着一对更早的成功/失败计数器，和那十种结局并存，同一件事被数了两遍。
- 不要把 1.03 这个数说成「优化后的批大小」——它是**优化前量出来的病症**。
- 别把指标端点说成跟业务端口同一个：它是独立管理端口、默认只绑回环。

### Q11.3 线上 CPU 飙到 100%，你怎么排查？完整说一遍命令。  〔高频｜追问链：CPU 高怎么办 → top -H 之后呢 → nid 为什么要转十六进制 → jstack 和火焰图有什么区别 → 你自己用过哪个〕

**答**：我先把话说在前面——**这一套线上排障命令链本项目没有实际用到**，我这台机器上的性能问题是用压测脚本自带的仪表定位的（actuator 指标 + 火焰图 + 结果 CSV），不是用线上工具链。所以我分两段讲：通用套路是 `top -H` → `printf '%x'` → `jstack` 按 nid 定位；**本项目真正跑过的是 async-profiler 采火焰图**。

**展开**：
- **通用做法（本项目未实际用到）**，三条命令：
  1. `top -H -p <pid>` —— `-H` 是 threads 模式按线程显示，`-p` 限定进程，找出占 CPU 最高那个线程的十进制 tid。
  2. `printf '%x\n' <tid>` —— 转十六进制，因为 `jstack` 输出里的 `nid=` 是十六进制。
  3. `jstack <pid> | grep -A 30 'nid=0x...'` —— 在线程栈里按 nid 定位，`-A 30` 打印命中行之后 30 行也就是那一段调用栈。
  - **要连着抓三次栈比对**，反复出现在栈顶的那几帧才是热点；单次栈是一张快照，可能正好抓到一个无关的瞬间。
- **本项目实际用的是这一条**：`scripts/bench.sh profile 30 seckill-hot`，内部执行 `asprof -d 30 -e itimer -f raw/seckill-hot.html <pid>`。
  - `-d 30` 采样 30 秒；`-f xxx.html` 直接输出可交互火焰图；最后一个参数是目标 JVM 的 pid。
  - `-e itimer` 这个参数是被逼出来的：**默认的 `cpu` 事件要用 perf 的硬件事件，而这台机器的 `perf_event_paranoid` 大于 1 拿不到权限**，所以退到基于定时器信号的 `itimer`。另一个常用值是 `wall`（墙钟采样），能看见**阻塞中的线程**——CPU 采样看不见在等锁、等 IO 的线程，而 Q11.4 那种「接口慢但 CPU 不高」要看的恰恰是它们。
- **火焰图怎么读**（这一步常被追）：横轴**不是时间，是样本数占比**，一个格子越宽说明采样时越经常「正在执行它或它的子调用」；纵轴是调用栈深度、向上是被调用方。看法是从底往上找第一个「宽得不合理」的格子，那是热点入口；顶上一大片同宽的平顶就是真正在烧 CPU 的叶子方法。
- **和 jstack 的区别**：jstack 是手动稀疏采样、而且会 safepoint 暂停；async-profiler 是高频采样，还支持 `-e wall` / alloc / lock 多种事件，代价小得多。
- **如果这是我们系统真出问题**，我会先分清 CPU 高在哪一类：业务线程（热路径本身重）、GC 线程（转 Q11.4 的 `jstat`）、还是 Redis/MQ 客户端的 IO 线程。本项目里有一条具体线索可用：准入漏斗那一组拒绝原因计数器能立刻告诉我是不是流量形态变了（大量请求打到 Redis 而不是被本地售罄标记挡住），这一条是**项目里真有的**。

**可能的追问**：→ Q11.4；→「arthas 会用吗」；→「火焰图看到 JIT 编译线程占大头说明什么」；→ 详见笔记 12 第九节 9.1。

**别踩**：
- **最容易翻车的就是把这套命令说成自己线上敲过的**。诚实地讲「通用做法，我没有真实线上环境用过；我用的是火焰图」，反而比背熟命令更有说服力——面试官追一句「那一次你定位到什么方法」就穿帮了。
- 不要把 `jstack` 说成无代价：它会触发 safepoint。
- 不要把火焰图的横轴说成时间轴。
- 不要说 `-e itimer` 是我的偏好，它是权限受限下的退让，说清楚原因比说选择更可信。
- 不要说「CPU 100% 一定是死循环/GC」，先分清是哪类线程在烧。

### Q11.4 接口突然变慢，排查顺序是什么？连接池等待怎么看？  〔常见｜追问链：接口变慢先看什么 → GC 怎么看 → 不是 GC 呢 → 怎么确认是连接池打满 → 你们实际遇到过吗〕

**答**：同样分两段。通用顺序是：先分清「全部接口慢」还是「某一个接口慢」，全部慢先看 GC（`jstat -gcutil`）和机器负载，再看下游（数据库、Redis、MQ）和连接池；单个慢就直接采墙钟火焰图看阻塞栈。**`jstat` 和 `ss -s` 这两条本项目未实际用到**；本项目在这个场景下真正做的是三件事：看 actuator 的 Prometheus 指标（延迟分位、批大小分布、退化计数）、用 `asprof -e wall` 看阻塞栈、按 traceId 把慢请求在边缘日志和应用日志里对上。

**展开**：
- **GC（通用做法，本项目未实际用到）**：`jstat -gcutil <pid> 1000 10`，每 1000 毫秒打一次、共 10 次。列的含义：`S0`/`S1` 两个 survivor、`E` eden、`O` 老年代、`M` 元空间的使用百分比，`YGC`/`YGCT` young GC 次数与累计秒数，`FGC`/`FGCT` full GC 次数与累计秒数。判异常的形状是**`O` 一直高位不降且 `FGC` 在涨**，那是老年代回收不掉；`YGCT` 增量除以 `YGC` 增量就是平均每次 young GC 的耗时。
- **连接池等待（通用做法，本项目未实际用到）**：`ss -s` 打印各状态套接字总数。方向是：`timewait` 巨大通常是短连接没复用；`estab` 贴着连接池上限说明池打满了。更直接的其实是连接池自己的指标（HikariCP 的 pending / active / 等待时长），这属于「我知道该看什么，但本项目没有埋 Hikari 那组指标」。
- **本项目里连接池相关的事实来自另外两个地方，这两条是真用过的**：
  1. 压测脚本在扫描消费参数时**把连接池上限跟着线程数一起调（线程数 + 8）**——因为消费线程数和池大小不匹配时，量到的是池的排队而不是落库能力。
  2. nginx 到上游用 keepalive 长连接：`keepalive 512`、`keepalive_requests 100000`、`proxy_set_header Connection ""`，理由写在配置旁边——**不这么做，测出来的是 TIME_WAIT 的性能而不是应用的**。这里有一个必答的细节：nginx 默认用 HTTP/1.0 回源且带 `Connection: close`，所以 `proxy_http_version 1.1` 和清空 `Connection` 头必须一起写，只写一个 keepalive 不生效。
- **本项目这个场景真实走过的路**：M6 一开头「落库跟不上」的定位，用的不是任何一条上面的命令，而是那个分两阶段的批大小仪表——投递批大小和落库批大小的差直接给出答案（实测 1.03，是「批没攒起来」不是「提交太慢」）。后来 M8 判「加实例不加吞吐」，看的也是指标：提交次数/秒恒在 70–115、与实例数无关。这是我最想讲的一点：**排查顺序的终点不是某条命令，而是「哪个数把两种解释区分开」**。
- **慢请求的定位入口**：拿到 traceId 之后三条命令（runbook 第 7 节）——边缘日志看这个请求打到哪台实例、状态码和耗时；应用日志按 id grep 每一行；再按 trace 反查订单行。要说明的是按 trace 反查订单要扫八张物理表（trace 不是分片键），所以脚本里是按券 id 先取一个订单再拿它的 trace 回去 grep。

**可能的追问**：→ Q11.3；→「为什么不直接看数据库慢查询日志」；→「p99 高但 p50 正常说明什么」；→ 详见笔记 12 第九节 9.2 / 9.4 与第八节 8.10。

**别踩**：
- **不要把 `jstat` / `ss -s` 说成本项目用过**，也不要顺口说「我们线上遇到过连接池打满」——本项目没有线上，压测里也没有出现过这个结论。
- 不要说「接口慢先看 CPU 火焰图」：CPU 采样看不见在等锁、等 IO 的线程，这种场景要 `-e wall`。
- 不要说「有 Hikari 连接池监控面板」——没有埋，也没有看板。
- 不要把「提交次数/秒 70–115」说成一个优化目标或好数字，它是**水平扩展被卡住的证据**，指向每批都要更新的同一行库存。
- 不要说「按 traceId 一条命令就能查到慢请求全貌」：日志没有集中收集，多实例要逐个文件 grep；批量落库那段日志根本不带 id。
