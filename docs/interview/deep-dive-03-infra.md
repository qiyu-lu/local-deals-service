## 5. Redis Cluster 与故障演练

### Q5.1 Redis 挂了还能下单吗？降级到什么程度？〔高频｜追问链：Redis 挂了还能下单吗 → 那你降级到什么程度 → 为什么不降级到直接打 MySQL → 用户看到什么〕

**答**：不能。下单路径上的准入脚本是**强依赖**，它所在的那个 slot 不可写，买家就拿不到预占，接口直接返回 503「系统繁忙，请稍后重试」。这是**有意选的 fail-closed**：准入脚本同时做限频、判重、扣减和写预占，绕过它去打 MySQL 等于把 99% 注定失败的流量直接灌到库存那一行，正是 M0 那个被 Broker 先压垮的形态。真正降级的只有**查订单状态**这一条读路径。

**展开**：

- 准入调用抛异常时，下单主流程先做一次**歧义补救**：拿刚才那个订单号回查预占，如果预占确实存在（状态是处理中或成功），说明脚本已经执行成功、只是回包丢了，这次请求仍然算准入通过；只有回查也不成立才计一次 `UNAVAILABLE` 指标并抛 503。
- 状态查询接口是**双读**：先读预占，读不到（或 Redis 抛异常）就回查数据库的订单行；两边都没有时，Redis 不可用返回「订单状态暂不可用，请稍后重试」，Redis 可用则返回「订单不存在或状态已过期」——两句话不同，因为前者是「不知道」，后者是「确实没有」。落库之后 MySQL 才是权威，所以这条降级是安全的。
- 一个反直觉的边界：售罄标记是**进程内**的，跑在鉴权之前。Redis 挂掉时如果这张券的每个桶都已被标记过，买家收到的是「库存不足」而不是 503——这不是骗人，标记是真发生过的，但它确实会在故障期间盖住真实原因。这条写在笔记 04 的已知边界里。
- 已经准入、消息没发出去的那批人不受影响：预占本身就是准入的发件箱，发消息是 best-effort，发失败只记一个计数，留给对账器（详见笔记 05）。

**可能的追问**：→ Q5.10（用户看到什么、代价多大）；→ Q5.7（那正确性靠谁）；→「为什么不做本地库存兜底」

**别踩**：不要说「Redis 挂了走 MySQL 兜底下单」——本项目没有这条路径，说了会被一句「那你的限频和判重怎么办」问死。也不要把「可丢的性能层」说成「可用性不受影响」：可丢指的是**数据可丢**（正确性不依赖它），不是**服务可丢**。

### Q5.2 Redis 是异步复制，主节点宕机丢了预占会怎样？会超卖吗？〔高频｜追问链：Redis 异步复制会丢 → 丢了预占会怎样 → 会不会超卖 → 那谁兜底〕

**答**：会丢，但丢的方向是**库存复活**，不是超卖。丢掉的是「已经卖出去」这件事——新主带着几秒前的库存数回来，于是把同一批库存**再卖一遍**，Redis 层面放进比真实库存更多的人。超卖不会发生，因为最终建单要过 MySQL 那条带条件的扣减；条件不成立整批被拒，那些人拿到的是**假的成功**，最后会被明确告知失败。

**展开**：

- 两类后果要分开说。第一类：**预占丢了、消息还在**。消费者认领时发现预占状态不在，这条消息不会被落库（消费侧不会凭消息本身造订单）。第二类：**库存复活**。复活的份额被重新卖出，多出来的批次走到落库层被条件更新拒掉。
- 落库层两条路都是条件更新：批量路径是 `UPDATE tb_seckill_voucher SET stock = stock - n WHERE voucher_id = ? AND stock >= n`，影响行数不是 1 就整批回滚、降级逐条重放；逐条路径是带 `stock > 0` 的条件更新，不成立抛库存耗尽。
- 逐条失败的处置是有序的：**先挂起这张券**（停止新的准入，因为 Redis 与 DB 已经背离，需要人介入对账），再做精确幂等的补偿归还预占，然后通知买家失败。顺序反过来就会边补库存边放新人进来。
- 证据：M8 的四轮空窗演练里 Redis 最多多放 10.3%（33104 对 30000），MySQL 每轮恰好建 30000 单、超卖恒为 0；其中一轮条件更新拒批 337 次（压测报告第 3 节第 8 条）。

**可能的追问**：→ Q5.4（为什么直接杀主复现不出来）；→ Q5.6（多出来的人分别在哪挡下）；→ Q5.11（`min-replicas-to-write`）

**别踩**：不要说「Redis 保证不超卖」——本项目的结论恰恰相反，Redis 是**允许丢**的准入层，数据库的条件更新才是最后防线。也不要把「多放」说成「超卖」：多放是准入层放进的人多于库存，超卖是订单数多于库存，本项目前者实测最多 10.3%、后者恒为 0。

### Q5.3 你演练过主节点宕机吗？结果是什么？〔高频｜追问链：演练过吗 → 怎么杀的 → 结果什么 → 代价是什么〕

**答**：演练过，两轮，直接 `docker kill` 掉当时正在服务 0 号桶的那个主节点（节点是运行时查出来的，不是写死名字）。结果是**丢失预占 0、库存差 0、超卖 0**，转移 5.2 / 7.8 s，每个桶重新可读 7.3 / 9.4 s，收敛 40.2 / 31.4 s。代价不是零：那一轮约 1.26 万个 503，占全部请求的 42%。

**展开**：

- 设计上有两个细节值得讲。第一，**被杀的节点运行时决定**：第一轮被杀的节点重启后会变成「自己那个已被提升的副本」的从节点，第二轮再按名字杀它，杀的就是一个从节点，什么也证明不了。第二，**读数据只连幸存节点**，否则读的就是被杀的那台。
- 记两个不同的时刻：集群**察觉**主节点没了，和每个桶**重新可读**。应用感受到的是后者，前几秒幸存节点还在说一切正常。
- 收敛判据是可判定的谓词，不是看曲线：**预占数等于订单数、且处理中索引为空**，同时 Redis 库存等于 DB 库存。
- 同一套演练体系里还有另外两种：`kill -9` 打死应用（M5 上是 56.8 s 收敛），以及先杀 Broker 再杀应用（制造「脚本成功、消息从没存下来」的残局）。三次演练见笔记 12 第五节。

**可能的追问**：→ Q5.4（全是 0 是不是等于没测到）；→ Q5.10（1.26 万个 503 怎么来的）

**别踩**：这一轮**没有**证明 MySQL 条件更新兜住了超放，那条防线这次根本没上场。把「全是 0」说成「防线成立」是这道题最大的坑，面试官只要追一句「那你的兜底被触发了吗」就穿了——所以这句必须自己先说。

### Q5.4 第一次演练 RPO 是 0、你说的那条最后防线根本没被触发，你怎么办的？〔坑｜区分度最高｜追问链：结果全是 0 → 那防线被触发了吗 → 没触发说明什么 → 你后来怎么逼出来的 → 失败了几次〕

**答**：先承认一件事：一整行 0 读起来像「防线成立」，其实是「什么都没测」。RPO = 0 不是运气，是机制——主节点一死，它负责的 slot 直接不可写，买家收到的是 503 而不是一个假的成功，**被拒绝的买家不算丢失**，真正的丢失窗口只有不到 1 ms 的复制延迟。于是这个设计赖以成立的最后一道防线，到 M5 为止一次都没被真实触发过。我把这件事作为待办记进计划，在 M8 用**人为制造复制空窗**的办法把它逼了出来。

**展开**：

- 为什么直接杀主复现不出来：要丢数据，必须存在「主收了写、从一个字节都没收到、然后主死了」的窗口。直接杀主没有这个窗口——主活着时 slot 可写但复制正常，主死了 slot 就不可写。
- 逼出来的做法见 Q5.5，四次才对，三次失败各自说明一件事（时机、机制、负载形态）。
- 为此在结果行里加了一个字段 `window_effective`：**让一次时机不对的运行自己说出来**，而不是靠事后回忆。这是我从第一次失败里学到的最有用的一条——演练脚本要能自证这一轮赌上了东西。
- 我更愿意讲这段而不是结论本身：一个「全是 0」的结果，默认应该先当成可疑的。

**可能的追问**：→ Q5.5（空窗怎么造）；→ Q5.6（逼出来之后数字是什么）；→「你还有哪些结论是推理不是实测」

**别踩**：不要把 M5 的 RPO = 0 包装成「我们做得好所以不丢」——那是实验没设计到位，不是系统强。也不要说成「Redis Cluster 不丢数据」：Redis Cluster 就是异步复制，会丢，M8 已经实测丢给你看了。

### Q5.5 复制空窗是怎么制造出来的？用了什么命令？〔常见｜追问链：怎么造空窗 → 为什么 DEBUG SLEEP 不够 → 顺序能不能换 → 还需要什么条件〕

**答**：三步，顺序不能换：**先让副本睡着**（`DEBUG SLEEP n`，睡着的副本无法重连），**再从主节点这一侧掐断复制链路**（`CLIENT KILL TYPE replica`），然后让主节点在空窗里继续接单几秒，最后 `docker kill` 杀掉主节点。被提升的副本就带着几秒前的世界观回来了。

**展开**：

- **为什么只 `DEBUG SLEEP` 不行**——这是第二次失败教的：它只让副本停止**应用**复制流，字节早就躺在它的 socket 缓冲区里，睡醒一股脑全应用上，RPO 仍然是 0。要真丢，主节点必须**停止发送**，所以才有第二步。`TYPE replica` 限定只杀复制连接，不误伤业务客户端。
- 这几条 `redis-cli` **故意不加 `-c`**：加了集群模式，一次重定向就会把 `DEBUG SLEEP` 发到别的节点去。反过来读演练数据时必须加 `-c`，否则跨槽的 key 直接报 MOVED。
- `docker kill` 与 `docker stop` 的区别，正好对应 `kill -9` 与 `kill`：要的是没有机会收尾的那一种。
- 另外两个必要条件：**杀早不杀晚**（杀的那一刻库存必须还没卖完，否则复活的副本本来就没东西可信，这是第一次失败），以及**买家必须多于库存**（否则复活的库存没人来抢，条件更新一次都不会开火，这是第三次失败）。
- 代价要主动说：副本在 `DEBUG SLEEP` 期间也无法参与选举，所以这一轮的转移时间比直接杀主那两次长——这是制造空窗的代价，不是回归。

**可能的追问**：→ Q5.6（结果数字）；→ Q5.11（生产上怎么避免这个窗口）

**别踩**：别把顺序讲反（先切链路再让副本睡，副本会立刻重连补齐）。也别说这是「线上故障复现」——这是实验室里人为构造的极端窗口，真实故障下窗口通常小得多。

### Q5.6 空窗演练里 Redis 多放了多少人、MySQL 超卖多少？多出来的人分别在哪一层被挡下的？〔高频｜追问链：多放多少 → 超卖多少 → 多的人去哪了 → 他们知道自己失败了吗〕

**答**：两晚四轮，库存都是 30000。Redis 最多多放 **10.3%**（33104 对 30000），**MySQL 每一轮都恰好建 30000 单，超卖恒为 0**。多出来的人在两个地方之一被挡下：要么**预占随主节点一起死了**，消费者认领时发现状态不在；要么**复活的库存被重新卖掉**，批次走到 MySQL 才被条件更新整批拒绝（第二轮 337 次）。

**展开**：

| 轮次 | 杀主时未售 | Redis 放进 | MySQL 建单 | 多放 | 条件更新拒批 | 超卖 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 9-21 03:41 ① | 14001 | 30124 | 30000 | 124 | 10 | **0** |
| 9-21 03:41 ② | 14051 | 33096 | 30000 | 3096 | 337 | **0** |
| 9-21 04:43 ① | 14123 | 33104 | 30000 | 3104 | 0 | **0** |
| 9-21 04:43 ② | 14047 | 33101 | 30000 | 3101 | 0 | **0** |

- 两条路径通向同一个结果，区别只在于**复活的库存有没有在「丢失预占的那批消息」被处理之前被抢走**：抢走了就轮到条件更新开火（第二轮），没抢走就是认领时状态缺失（后两轮）。所以后两轮拒批为 0 不是防线失效，是没轮到它。
- 被条件更新拒掉的人**知道自己失败了**：整批回滚后降级逐条重放，逐条撞上库存耗尽，就走挂券 → 精确补偿预占 → 推送失败通知这条链。冒烟阶段第一次看见这条防线开火时是 4000 库存放进 4697 人、建 4000 单、拒 86 批、超卖 0，697 个人拿到了假的成功（冒烟数字，只用于确认机制成立，不进正式结论）。
- 量化的四个指标：条件更新拒批次数、被告知抢到却没有订单的人数、Redis 相信的库存减去真实库存、超卖数。

**可能的追问**：→ Q5.7（那最终防线是什么）；→ Q5.8（收敛多久）；→「假的成功对用户体验的伤害怎么算」

**别踩**：别把「多放 10.3%」说成「超卖 10.3%」。也别声称「所有多放的人都被条件更新挡下」——有两轮拒批是 0，实际是在认领阶段就断了；把两条路径说成一条会被数据当场打脸。

### Q5.7 那最终防线到底是什么？为什么说 Redis 是可以丢的？〔高频｜追问链：谁保证不超卖 → 为什么不是 Redis → 那 Redis 还有什么用 → Redis 挂了正确性会不会变〕

**答**：最终防线是 MySQL 上那条带条件的扣减：批量路径 `UPDATE tb_seckill_voucher SET stock = stock - n WHERE voucher_id = ? AND stock >= n`，逐条路径是带 `stock > 0` 的同类更新。它和库存那一行的行锁绑定，是这套系统里**唯一一个单调、不可回退**的数字。Redis 之所以可丢，是因为它在这条链上只承担**准入**——决定谁有资格去建单，而不是决定库存对不对。

**展开**：

- 手段：Redis 准入 + MySQL 条件更新，两级都收口到同一个不变量「订单数 ≤ 库存」。Redis 多放，结果只是**有人白等一场**；Redis 少放（比如整个挂掉），结果只是**少卖**。两种偏差都不破坏不变量。
- 为什么不能让 Redis 当权威：它是异步复制，故障转移就可能回退到几秒前的状态。把最后一道防线建在一个会回退的数字上，等于没有防线。同理，订单分库分表时 `tb_seckill_voucher` **明确不做广播表**——广播写要 2PC 才能自洽，把最后防线建在需要分布式事务的数字上只会把问题变复杂（详见笔记 08）。
- 代价要说清楚：这条防线是**事后**的，它只能拒绝，不能把「你抢到了」这句话收回。所以设计上必须接受「假的成功」存在，并且给它一条明确的用户可见失败路径（挂券 + 补偿 + 通知）。
- 这个不变量还有一个副作用是已经实测的：那一行同时是**写路径水平扩展的上限**，三个实例提交次数/s 恒在 70–115、与实例数无关（压测报告第 3 节第 7 条）。正确性和吞吐在这里是一对矛盾，我选了正确性，并把拆那一行记成下一步。

**可能的追问**：→ Q5.2；→「那一行是瓶颈你打算怎么拆」；→「为什么不用分布式事务」

**别踩**：别说「Redis + Lua 原子所以不会超卖」——原子性解决的是并发交错，解决不了节点故障后的状态回退，这两件事经常被混为一谈。也别说这条防线「从来没用上」：它在空窗演练里真开过火。

### Q5.8 收敛要多久？靠谁收敛？〔常见｜追问链：多久收敛 → 靠谁 → 收敛的判据是什么 → 为什么要这么久〕

**答**：靠**对账器**，收敛判据是「预占数等于订单数、处理中索引为空、Redis 库存等于 DB 库存」。直接杀主那两轮 40.2 / 31.4 s；复制空窗那四轮 150–308 s；`kill -9` 打死应用那条线随版本演进从 102.8 s 降到 44.7 s（批量消费之后）、上 Cluster 后 56.8 s。

**展开**：

- 为什么空窗轮明显更久：预占写进处理中索引时带的到期时间是准入时算好的，默认**两分钟**之后才「到期」；对账器**固定间隔 10 秒**跑一轮，每轮处理**最多 100 条**。所以一条被丢掉的预占从产生到被看见，天然有两分钟的下限。这不是卡住，是设计出来的静默期——太短会和正常消费抢同一批消息。
- 对账器做的事：扫处理中索引里到期的预占，回查写库确认订单是否真的不存在，不存在就**重投消息**（预占本来就是准入的发件箱），只有过了硬超时（默认 15 分钟）且补偿开关打开才精确补偿。多实例下每条预占先抢一把调度锁，避免两个实例同时动同一条。
- 一轮扫描失败是 **fail-closed** 的：读不到就记一次扫描错误直接返回，不会凭猜测去补偿。
- 另一个已经实测的慢点：先杀 Broker 再杀应用的变体要重投几千条，耗时 574.2 s（M3）/ 572.1 s（M4），**因为对账器自己没有批量化**——这是已知没做的事。

**可能的追问**：→「两分钟能不能调小」；→「多实例下对账器会不会重复补偿」；→ Q5.6

**别踩**：不要把收敛时间说成「秒级自愈」。也不要说对账器会「自动退款」——它在硬超时前只重投不补偿，补偿还挂着一个独立开关。

### Q5.9 Cluster 为什么是 16384 个槽？你的 Lua 里几个 key、跨槽怎么办？〔高频｜追问链：为什么 16384 → 槽怎么映射 → 你的脚本几个 key → 跨槽会怎样 → hash tag 怎么设计的〕

**答**：16384 = 2^14，key 到槽是 `CRC16(key) mod 16384`。选这个数的通行解释是：集群节点心跳里要带一张槽位图，16384 位压成 2 KB，8 位组就得 8 KB，心跳是每秒都在发的；同时 16384 对几百个节点这个规模已经足够细。我的准入脚本一次传 **7 个 key**：库存、活动元数据、预占、订单状态、桶内处理中索引、用户限频前缀、IP 限频前缀。它们全部带同一个 hash tag `{sk:b<n>}`，所以整次调用落在**一个 slot、一个 RTT**。

**展开**：

- 跨槽的后果很硬：Lua 脚本的 key 不在同一个 slot，Redis 直接报错（`CROSSSLOT`），不是慢，是不执行。所以 tag 不是优化，是这个脚本能不能存在的前提。
- tag 设计上做了一个反直觉的取舍：**tag 里不带券号**（`{sk:b3}` 而不是 `{v17:b3}`）。理由是秒杀期间热的就是一张券，它的 K 个桶已经散在 K 个 slot 上；而带券号的代价是任何 key 都得先知道券号才能拼出来——订单状态轮询接口只有订单号，没有券号也没有用户 id。代价是不同券的同号桶会落在同一个 slot，多张券同时热时略不均，这条写在 ADR 里。
- 桶由**用户**决定（`userId % K`，K 是 2 的幂且 ≤ 1024），不是由请求决定：同一用户永远落同一桶，判重因此天然原子；订单号低位带着 `userId % 1024` 的基因，所以只拿订单号也能反推出桶。准入时还会校验订单号的基因与买家一致，不一致直接拒——否则它的状态 key 会落到别的桶、别的 slot，之后谁也查不回来。
- 活动元数据因此必须**按桶复制 K 份**（脚本只能读本桶 slot 的 key），写入点只有三处，是静态冗余。
- 客户端两侧都要认识 Cluster：Lettuce 周期 10 秒刷新拓扑 + 打开全部自适应触发；不加这一条，转移之后客户端会一直用旧拓扑。

**可能的追问**：→ Q5.10（拓扑刷新和 MOVED）；→「桶空了但整券还有货怎么办」；→「K 怎么选」

**别踩**：16384 那个理由要说成「心跳位图带宽的权衡」，别说成「性能更好」或「作者随便定的」。另外别把分桶说成「解决了 MySQL 的行锁」——分的是 Redis 的 key，DB 至今一张券一行，这一点我在 ADR 里专门改正过一次错误预期。

### Q5.10 故障转移期间客户端报什么错、用户看到什么？你为此付出了什么代价？〔常见｜追问链：客户端报什么 → 为什么不是超时 → 用户看到什么 → 代价多大 → 能不能不让用户看见〕

**答**：转移期间那些 slot 没有主节点，命令**直接失败**而不是排队等超时——Lettuce 配的是断连即拒绝命令。应用把它当成 Redis 不可用，返回 **503「系统繁忙，请稍后重试」**。代价是可量化的：那一轮约 **1.26 万个 503，占全部请求的 42%**；库存明明还有，买家却被拒。这就是「Redis 是可丢的性能层」的真实价格。

**展开**：

- 为什么选**快速失败**而不是排队等超时：排队会让连接池和线程在故障的几秒里被占满，故障从「一部分槽不可用」扩散成「整个进程不可用」。快速失败把影响面限制在那几个槽上，其余槽的买家完全无感。
- 转移之后靠什么恢复：拓扑刷新。周期 10 秒兜底 + 全部自适应触发（重定向、持续重连都会触发一次刷新），并且允许动态发现节点源。没有这一条，转移后每条命令都会一直收到 MOVED，直到重启进程。
- 演练里刻意记了两个时刻：集群**察觉**（5.2 / 7.8 s）和每个桶**重新可读**（7.3 / 9.4 s）。应用感受到的是后者。
- 这 42% 里有多少是「注定失败的请求」我没有拆开统计——压测形态本身就是首秒售罄、其余 99% 注定失败，所以这个比例读作「故障期间接口的失败率」，不要读作「42% 的人本来能买到」。

**可能的追问**：→ Q5.1（降级到什么程度）；→ Q5.11（脑裂）；→「能不能重试兜过这几秒」

**别踩**：不要说「用户无感知」。也不要把 42% 当成「本该成功却失败的比例」——这个数是失败请求占全部请求，两者不是一回事，敢报数就要敢说它的口径。

### Q5.11 脑裂你防了吗？`min-replicas-to-write` 配了吗？〔常见｜追问链：脑裂了解吗 → 你配了 min-replicas 吗 → 配了代价是什么 → WAIT 呢 → RedLock 呢〕

**答**：**本项目没做。** 演练用的 3 主 3 从集群只配了 `cluster-node-timeout 5000`，没有配 `min-replicas-to-write` / `min-replicas-max-lag`，没有用 `WAIT`，也没有用 RedLock。我的做法是反过来的：**承认 Redis 会丢**，把正确性放到 MySQL 的条件更新上，然后用演练把「丢了会怎样」量出来（Q5.6）。另外那套集群是 `--appendonly no --save ""`，**完全不持久化**——这是演练环境的取舍，必须声明。

**展开**（下面是「会怎么做」，不是本项目做过的事）：

- **`min-replicas-to-write N` + `min-replicas-max-lag S`**：主节点发现健康副本不足 N 个、或滞后超过 S 秒时，**主动拒绝写**。它能压掉「少数派主节点在分区里继续接单」这类脑裂窗口，也能压掉我人为制造的那种空窗。代价很直白：把一部分**丢数据**换成**不可用**——副本一抖，主就拒写，秒杀场景下这意味着更多的 503。对本项目来说方向是对的，因为拒写产生的是「被拒的买家」，而被拒的买家不算丢失。
- **`WAIT numreplicas timeout`**：在准入脚本之后同步等待 N 个副本确认，把写变成准同步。代价是每次准入多一个 RTT，而准入是这条链上唯一的热路径；而且 `WAIT` 超时返回的是已确认副本数，不回滚，所以它只是**缩小**窗口，并不提供强保证。以本项目「Redis 可丢」的定位，这个代价不值得。
- **RedLock**：我这里**用不上**，因为准入的原子性来自「所有 key 同 tag、单 slot、一次 Lua」，本来就不需要跨节点分布式锁。项目里唯一用到 Redisson 锁的地方是对账器的调度，那是一把**性能锁不是正确性锁**——锁失效最坏结果是两个实例同时看同一条预占，而重投与落库都是幂等的。RedLock 在异步复制和时钟漂移下的争议（Kleppmann 那套论证）也正好说明：不该把正确性建在锁上。
- **多副本切换 / 多机房**：没做，明确写在诚实边界里；消息中间件的多副本切换、数据库主从切换同样没做。
- 生产上我会先做的顺序：开持久化（AOF everysec）→ 配 `min-replicas-to-write 1` + `max-lag 10` → 再考虑要不要在关键写上加 `WAIT`。

**可能的追问**：→ Q5.5（你制造的空窗和真实脑裂的区别）；→「RedLock 的争议你怎么看」；→「AOF everysec 还是 always」

**别踩**：别把 `min-replicas-to-write` 说成「防止脑裂」——它只是**缩小**少数派主节点继续接写的窗口，不是共识协议，Redis Cluster 本身不提供线性一致。也别为了答得好看而声称配过——配置文件里没有，面试官一翻就露。没做就说没做，然后把代价讲清楚，这比假装配过更有说服力。

## 6. 分库分表

> 本节的流程细节不重抄，路由与落位见笔记 08 第三节，决策与踩坑见 ADR 0008 / 0009。
> 凡是本项目没做的机制，先写「没做」，再写「会怎么做」并标明那是方案不是证据。

### Q6.1 为什么要分库分表？数据量真到瓶颈了吗，还是为了写简历？  〔高频｜质疑题｜追问链：为什么分 → 数据量多少 → 不分行不行 → 分了之后性能变好了吗〕

**答**：诚实说，数据量没到瓶颈，我本机压测的订单量是几万到十万级，单表完全扛得住。做它的理由是订单是这个系统里唯一持续增长且没有上限的对象——券、店铺、用户都是有限的，订单不是。而分片键这件事一旦上线就改不动了，所以我是在还改得动的时候先把它落下来。它买的是水平扩展的可能性，不是当下的吞吐。

**展开**：
- 手段：把 `trade_order` 和四张附属表（审计流水、支付流水、退款流水、券资产）拆成 2 库 × 4 表 = 8 个槽位，其余表（券、库存、店铺、用户、营销、权限）声明成单表留在第一个库。
- 为什么现在做：分片键是一次性决策。订单号的基因（用户 id 的低十位）在 M3 做准入漏斗的时候就已经埋进去了，当时写的理由就是「为分片做准备」——这一步如果没提前埋，后面再想让「按用户查」和「按订单号查」同片就得整体换号。
- 本项目的证据：分片没有让准入变慢，这是我唯一敢下的性能结论。同场对照里 10k 档 9936.5 → 9961.7 req/s（p99 68.3 → 58.6 ms），20k 档 19725.1 → 19721.5（p99 87.3 → 101.0），每档 `accepted = stock`、无超卖。
- 落库那一行报告里是 982.7 → 2088.9 单/s（中位），负载停止后的积压 10.7 / 55.8 / 16.1 s 降到 0.1 / 0.1 / 0.1 s，**但那一档同时调了消费参数**，所以这个提升不能单独归给分片。
- 正确的说法：分片在这台机器上是「没有可测代价」，不是「变快了」。真正的写路径上限实测是库存表的那一行——三实例落库 2415 / 2435 / 3026 单/s 而 CPU 从 1.41 涨到 4.0 核，提交次数每秒恒在 70–115、与实例数无关。分订单表解决不了它。

**可能的追问**：→ Q6.2（那为什么是用户 id）；→ Q6.7（库存那一行怎么办）；→「那你为什么不干脆先拆库存表？」（答：拆的方向是按券分桶，不是复制到两个库，见 Q6.7）

**别踩**：
- 不要说「分库分表提升了吞吐」。本项目的对照结论是准入无退化、落库那一栏被消费参数污染了，说成分片带来的提升会被一句「你怎么归因的」问穿。
- 不要编造数据量（「订单表一亿行」）。承认「没到瓶颈、是提前埋」反而是加分项，因为下一句就能接「但分片键改不动」。
- 不要说八张表比一张表快。单表几万行的时候八张表只会更慢一点（多一层解析），快慢不是这件事的卖点。

### Q6.2 分了几库几表？分片键选什么？为什么不是订单号？  〔高频｜追问链：几库几表 → 分片键是什么 → 为什么不用订单号 → 那按订单号查怎么办 → 唯一键还成立吗〕

**答**：2 个库、每库 4 张表，一共 8 个槽位；`slot = key % 8`，库 = `slot % 2`，表 = `slot / 2`，所以连号的用户交替落两个库而不是先把一个库填满。分片键是**用户 id**。订单号其实**也是**分片键——它低十位就是用户 id 的基因，两者算出同一个槽位，所以问题不是「二选一」，而是「让它们必然相等」。

**展开**：
- 为什么不选券 id：一场秒杀的全部订单会压在一片上，等于没分。
- 更要命的是唯一键：限购键是（用户 id、券 id、活跃标记），选券 id 的话限购就变成跨片判重，而限购是秒杀的最后一道去重（详见笔记 06）。选用户 id 之后一个用户的所有行都在同一张物理表里，片内唯一就是全局唯一。
- 为什么「不是订单号」这个问法本身有问题：如果只把订单号当分片键，买家查自己的订单只带用户 id，就会退化成对八张表广播——那分片就白做了。基因法让两者算出同一个槽位，这才是这一章的全部价值（见 Q6.3、Q6.4）。
- 8 这个数怎么定：约束是必须整除订单号里那 1024 的基因空间，所以只能取 2 的幂；8 是在「能演示分库 + 分表两层」和「单机压测跑得动」之间选的。
- 本项目的证据：`OrderShardRoutingIT` 对 8 个槽位逐一用**物理连接**核对——订单行和它的审计行都只出现在 `slot = user_id % 8` 指定的那一张表里，按订单号查和按用户 id 查拿到同一行；限购在片内挡住同一用户，另外 7 个槽位照常下单。

**可能的追问**：→ Q6.3；→ Q6.4；→ Q6.5；→「热点用户怎么办」（答：C 端买家维度没有大 V，真正的热点在券维度，见 Q6.7）

**别踩**：
- 不要说「分片键是订单号」或「分片键是用户 id，订单号只能广播」。两句都是错的，正确说法是两个键指向同一个槽位。
- 不要把「2 库 4 表」说成「分了 8 个库」。库和表是两层，算法被调用两次、取同一个槽位的不同一半。
- 不要说取模分片天生不如范围分片。范围分片在这里根本不适用——按时间范围分会让当天的订单全压在最后一片上。

### Q6.3 基因法讲一下：塞几位、和分片数什么关系、以后扩容怎么办？  〔高频｜追问链：基因法是什么 → 塞几位 → 为什么是 2 的幂 → 扩容怎么办 → 在线扩容做了吗〕

**答**：订单号是本地雪花，64 位从高到低是 41 位毫秒、5 位实例号、7 位序列、**最低 10 位放用户 id 对 1024 取模**。槽位是键对 8 取模，而 **8 整除 1024**，所以订单号对 8 取模恒等于用户 id 对 8 取模。基因法的全部收益来自这一个整除关系。**在线扩容本项目没做**。

**展开**：
- 位数和分片数的关系：基因占 10 位，也就是基因空间 1024。分片数必须整除 1024，因此只能取 2 的幂且不超过 1024。扩到 16 个槽位基因仍然够用（1024 整除 16），扩到 2048 就不行了——那时基因位数决定了扩容的天花板。
- 塞这 10 位的代价：位是从序列位借的。序列只剩 7 位，也就是同一实例同一毫秒最多发 128 个号。这是真实的代价，不是白拿的。
- 扩容的性质：改槽位数要**重新搬数据**。取模是 2 的幂时有一个便利——从 8 扩到 16，每个旧槽位的行只会分裂成两个新槽位（`k` 和 `k+8`），也就是只需要搬一半，不需要全量重洗。但即使这样，本项目**没有做在线扩容**：没有双写、没有灰度读、没有数据校验，改槽位数就等于停机搬数据。
- **会怎么做（业界成熟方案，不是本项目的实现）**：常见是「成倍扩容 + 双写迁移」——先给新库做全量同步（DTS 或 binlog 订阅），再进入双写窗口，写两侧、读旧侧，中间跑一个全量 + 增量的对账校验；校验干净后按券/按用户灰度把读切到新拓扑，观察一段时间再停双写、清旧数据。代价是：迁移期间写放大一倍、需要一个可回滚的路由开关、需要一套对账工具，而且双写本身不是原子的（一侧成功一侧失败要靠补偿或重放 binlog 收敛）。另一条路是一致性哈希/虚拟槽（像 Redis Cluster 那样把数据先分成固定的很多个槽，再把槽映射到库），好处是扩容只搬槽不改算法，代价是要维护一张槽位路由表并保证所有实例对它的视图一致。
- 我为什么没做：这两条都需要一套迁移工具 + 对账 + 灰度开关，属于另一个子系统的工作量，而这个项目的数据量根本没到要扩容的点（见 Q6.1）。这是我写在已知边界里的，不是忘了。

**可能的追问**：→ Q6.4；→「双写期间不一致怎么发现」（答：全量 + 增量对账，本项目没做）；→「为什么不用一致性哈希从一开始就做」（答：它解决的是扩容，不解决「一行两种叫法」，而后者是这里的主要矛盾）

**别踩**：
- 别把「8 整除 1024」说反成「1024 整除 8」。整除方向说反，整个论证就垮了。
- 别说「基因法以后扩容零成本」。基因法只保证「两种查法同片」，不解决扩容搬数据。
- 别说自己做了在线扩容/双写。先说没做，再讲方案，比含糊带过安全得多。
- 别忘了序列位被借走这件事。面试官问「那你一毫秒能发多少号」的时候答不上来，说明你没真的设计过这个号。

### Q6.4 按订单号查和按用户查为什么必然同片？  〔高频｜追问链：基因法 → 为什么必然同片 → 派生单号呢 → 有没有例外 → 例外怎么处理〕

**答**：因为订单号的低十位就是用户 id 对 1024 取模，而槽位是对 8 取模、8 整除 1024，所以两者取模的结果是同一个数。不是「大概率同片」，是恒等。所有由订单号派生出来的单号也继承这个基因，所以支付回调、退款、券核销都是单片命中。

**展开**：
- 派生链：支付单号是「订单号-第几次」；退款单号是「RU + 订单号」（买家发起）或「RA + 支付单号」（按支付单自动退）；购买得到的券编号是「P + 订单号」。算法按前缀/分隔符把它们剥回订单号，再算槽位。
- 剥出来的订单号还要求大于 0（订单号是 2^57 以上的数），否则报告为算不出——拿一个不可能是订单号的值猜槽位，会把语句发到一个根本不可能有这行的片上。
- **唯一的例外**：营销发放的券编号是「G + 发放 id」，**不含基因**。算法对它报告「算不出」，于是按这个编号单独查会广播。
- 例外怎么处理：算不出槽位的那一列被**跳过**，由旁边的用户 id 定位，而不是整条语句退化成广播。多列之间取**交集不是并集**，因为它们是对同一行的谓词，每多一个只可能更窄（详见笔记 08 第三节）。
- 本项目的证据：`OrderShardRoutingIT` 里有一条 `bothWaysOfNamingAnOrderFindTheSameRow`，按订单号查和按用户 id 查拿到同一行；槽位换算本身由 `OrderShardSlotsTest` 覆盖，路由语义由 `OrderShardingAlgorithmTest` 覆盖。

**可能的追问**：→ Q6.5；→ Q6.6；→「两列算出不同槽位怎么办」（答：不选边，返回全部节点，于是 INSERT 被中间件当场拒绝——一行自己的两个键互相矛盾是 bug，不该被悄悄写进其中一片）

**别踩**：
- 不要说「所有编号都有基因」。营销发放的券编号没有，漏掉这个例外正好是面试官想挖的地方。
- 不要说「算不出就广播」。本项目的实现是跳过这一列参与交集，退化成广播是最后的兜底而不是第一反应。
- 不要说「基因法就是把用户 id 拼在订单号后面」。是塞进固定的低位并保证取模关系，拼字符串不构成整除关系。

### Q6.5 分片之后唯一索引还管用吗？片内唯一为什么等于全局唯一？  〔高频｜追问链：唯一键还在吗 → 哪些还是全局的 → 哪些不是 → 不是全局的那几个有风险吗 → 主键怎么办〕

**答**：数据库分片之后只能保证「一张物理表内唯一」，所以每个唯一键都要重新回答一次「它还成立吗」。结论分三档：限购键和所有由订单号派生的单号**语义完全不变**；渠道流水号、渠道退款单号、核销码**收窄成片内唯一**，这是真放弃了一点东西；附属表的自增主键**直接换掉**。

**展开**：
- 为什么片内唯一等于全局唯一：唯一性只在「可能冲突的两行」之间才有意义。限购键是（用户 id、券 id、活跃标记），可能冲突的两行必然同一个用户，而一个用户的所有订单行永远在同一张物理表里——所以物理表内唯一就覆盖了全部可能的冲突。同理，支付单号、退款单号、购买券编号都由订单号派生，可能撞的两行必然同表。
- 活跃标记是个生成列：状态为已关闭或已退款时为 NULL，否则为 1，靠 NULL 不参与唯一性让同一个用户在同一张券上只能有一笔活跃订单（详见笔记 06）。
- 收窄的那三个为什么能接受：渠道流水号、渠道退款单号只会被**同时带着支付单号 / 退款单号**的语句碰到，所以回调幂等仍然是按支付单那一行判的，不靠渠道号；核销码是 80 bit 随机串，跨片撞号不是需要设计的事情。
- 诚实的一点：渠道流水号和核销码我写了列注释说明它只在片内唯一，**渠道退款单号那一列漏了注释**。
- 附属四张表的主键去掉了自增——八张物理表会各自从 1 数起。没有任何查询按它路由，于是交给中间件的雪花生成。代价是它不再是递增的小整数，但按它排序仍然是时间序。这个换法带来的新问题见 Q6.10。
- 本项目的证据：`OrderShardRoutingIT.thePurchaseLimitBindsInsideAShardAndNowhereElse`——限购在片内挡住同一用户，另外 7 个槽位照常下单。

**可能的追问**：→ Q6.10；→「如果真需要全局唯一怎么办」；→「分布式唯一 id 你还知道哪些方案」

**别踩**：
- 不要笼统说「分片后唯一索引失效了」。三档要分清，否则下一句「那你限购怎么保证」就答不上。
- 不要说「用中间件就能做全局唯一索引」。ShardingSphere 不提供跨库唯一约束，能做的只有把 id 生成得不重复。
- **会怎么做（本项目没做）**：如果真需要一个和分片键无关的全局唯一约束，业界做法是单独建一张「唯一性登记表」（按那个字段自己分片），先写登记再写业务行，靠它的唯一索引挡住；或者做一条异构索引（binlog → 一张按该字段分片的映射表）。代价分别是多一次跨库写 + 失败补偿，和异构索引只能是最终一致，不能当强约束用。

### Q6.6 哪些 SQL 被分片拒绝了？最危险的是哪一类？  〔坑｜追问链：分片透明吗 → 哪些写法不能用 → 报错的好办还是不报错的好办 → 你怎么发现的〕

**答**：分片绝不是「加个中间件就透明」。这次被当场挡住、必须改写的有五类。最危险的恰恰是**唯一不报错的那一类**：不带分片键的 `SELECT ... FOR UPDATE`——它不会失败，只会在八张表上各锁一行，变慢和多锁。

**展开**（每类的改法详见笔记 08 第三节 3.4）：
1. `INSERT INTO 分片表 ... SELECT ... JOIN 单表`：报「插入的表和查询的表必须是同一张」。改成应用侧先读一次券快照，再拼普通多值 `VALUES`。
2. 多表 `DELETE ... JOIN`：报「不支持多表 DML」。改成先查键再逐条删（主要在测试清理路径）。
3. `UPDATE 分片表 ... LIMIT n`：报「带 LIMIT 的 UPDATE 不能路由到多个节点」。栽在这里的是券的过期任务。**这个拒绝是对的**：放行的话 LIMIT 会**按节点**生效，「这一批最多过期 500 张」会变成每张物理表各 500 张，八倍。改成先 `SELECT` 出键（跨片归并的语义是对的）再逐条按键更新，更新语句自己还带状态与有效期的判断，所以重复执行安全。
4. **不带分片键的 `WHERE 主键 = ? ... FOR UPDATE`：不报错**。一条按券资产自增主键锁行的语句会在八张表上各锁一行。改法是谓词里带上用户 id 让它单片命中。订单、支付、退款那三处的行锁本来就按订单号 / 支付单号 / 退款单号取，天然带基因，不受影响。
5. `SELECT ... FROM 单表 WHERE EXISTS (SELECT 1 FROM 分片表 ...)`：最隐蔽的一类，它不是 join 是子查询，SQL 表面上看不出跨了两种表，结果被路由到一个没有那张单表的库。栽在这里的是营销那边「这个用户和这个商户有没有业务关系」的判定，拆成三问在应用里合。
- 还有一条不属于这五类但同样的教训：一条**从未分片**的点赞清理语句，用了 `TIMESTAMPADD(SECOND, ...)` 这种把单位当参数的写法，单位被解析成列名，每次都报「未知列 SECOND」。改成 `DATE_SUB(..., INTERVAL ? SECOND)`。所以「只有分片表要小心」是错的判断——解析器对每条语句都生效。
- 为什么说不报错的最危险：报错的四类在测试里当场红，改完就完了；第四类和那条 `TIMESTAMPADD` 都是**冒烟或集成测试才抓到的**，单测握着 mock 的 JdbcTemplate 只能检查「发出去的 SQL 长什么样」，永远回答不了「有没有人接受它」。现在有两个集成测试把四条定时语句真的对分片数据源各执行一次。

**可能的追问**：→ Q6.8（跨库事务）；→ Q6.9（跨库分页）；→「你怎么知道还有没有漏网的」（答：把每条定时语句真执行一次是现在的办法；全量 SQL 的静态检查没做）

**别踩**：
- 不要把中间件的拒绝说成「中间件的毛病」。第三类的拒绝救了一个八倍放大的 bug，这一点讲清楚比抱怨有分量得多。
- 不要说「都被拒绝了所以我全改成单片查询」。第五类的改法是拆成三问在应用里合，不是硬凑分片键。
- 不要忘了第四类的危险在于**静默**。面试官问「最危险的是哪一类」，答一个报错的类就没答到点上。

### Q6.7 库存表为什么不做广播表？  〔常见｜追问链：单表还是广播表 → 为什么不广播 → 那它不是瓶颈吗 → 打算怎么拆〕

**答**：因为它的库存字段是**写热点**，不是只读配置。广播表的写会复制到每个库，两个库里的同一个库存数要保持是同一个数字就需要分布式事务——而数据库里的 `stock >= n` 条件更新是这个系统最后一道防线，把最后一道防线建立在一个需要 2PC 才能自洽的数字上，是把问题变复杂。所以它被声明成**单表**，只在第一个库。

**展开**：
- 什么表适合广播：真正低频只读、每个库都要 join 的字典表。库存表看起来像配置表，其实是全系统写压力最集中的一行。
- 留在第一个库的还有：券、店铺、用户、营销（活动/发放/标签/批次）、权限。它们全部声明成单表而不是广播表。
- 它确实是瓶颈，而且是**实测**的：三实例压测里落库 2415 / 2435 / 3026 单/s 而 CPU 从 1.41 涨到 4.0 核，**提交次数每秒恒在 70–115、与实例数无关**。写路径的水平扩展上限就是这一行。
- 拆的方向是**按券分桶**（一张券的库存拆成 K 行，各自条件更新），不是复制到两个库。这跟 Redis 那边的分桶是同一个思路（详见笔记 05），但 Redis 的分桶分的是 key，数据库这一行至今没拆。
- 诚实的边界：**这一行我明确没有拆**，已测实、未修。

**可能的追问**：→ Q6.8；→「按券分桶之后怎么保证总量不超卖」（答：分桶后每桶各自条件更新，总量是各桶之和，代价是尾部要在桶之间借货）；→ Q6.1

**别踩**：
- 不要说「广播表就是每个库一份，读快」。这题的关键是**写**，不是读。
- 不要把这一行的瓶颈说成「MySQL 慢」。它是同一行的行锁竞争，换更快的盘不解决。
- 不要说「Redis 已经扣过库存了所以数据库这一行不重要」。恰恰相反，Redis 是允许丢的准入层，数据库的条件更新才是最后防线——复制空窗演练里 Redis 最多多放 10.3%，而 MySQL 每轮恰好建 30000 单、超卖恒 0。

### Q6.8 跨库事务怎么办？为什么选 LOCAL 不选 XA？崩在两次提交之间会发生什么？  〔高频｜追问链：一个事务跨几个库 → 用的什么事务 → 为什么不上 XA → 崩了会怎样 → 你测过吗〕

**答**：一个消费批次是一个事务，它**通常同时写两个库**：批次里的买家来自不同槽位，订单行和审计行分散在两个库的八张表上，而库存那一行只在第一个库。用的是中间件默认的 **LOCAL** 事务——逐个物理连接提交，不保证跨库原子。我没有上 XA。

**展开**：
- 事务里做三件事：一条多行 `INSERT IGNORE` 写订单、一次 `stock >= n` 的条件更新扣库存、一条多行 INSERT 写审计。
- 为什么不上 XA：代价和收益不成比例。2PC 的额外往返和锁持有时间正好落在落库这条热路径上，而原子性并不是这条链路正确性的唯一来源。**XA 的代价我没有实测，所以不报数字**；在有证据说明 LOCAL 不够用之前不引入。
- 崩在两次提交之间会怎样——这是推理，但推理链是完整的：没提交的那一半订单仍然持有 Redis 预占，对账器发现数据库里没单会重投，`INSERT IGNORE` 让重放幂等；但这一批的库存已经扣过一次，重放会再扣一次，于是数据库库存**比真实值更低**。所以后果是**有界的少卖，不是超卖**——方向是安全的，量级被批大小限住，而且要求进程恰好死在两次提交之间那个窗口里。
- 「一个批次确实横跨两个库」是被测试钉死的事实：`OrderShardRoutingIT.oneBatchOfOrdersIsOneTransactionOverBothDatabases` 放 8 个不同槽位的买家，用**物理连接**分别去数，第一个库 4 行、第二个库 4 行，库存只扣一次。非原子窗口的存在是这条测试的直接推论。
- **故障注入没有做，窗口有多宽我也没有量过。** 这一条是推理加机制证据，不是实测，我不会说成实测。
- **会怎么做（如果要求强原子）**：一是 XA / ShardingSphere 的 XA 事务管理器，代价是两阶段的额外往返、协调者日志、以及参与者崩溃期间锁不释放；二是 Seata AT 那类通过反向补偿实现的柔性事务，代价是要维护全局锁和 undo log，热点行上的全局锁反而会更慢；三是最省的办法——**把跨库写改成不跨库**（把库存扣减拆出去单独提交，用消息或状态位对齐），代价是把原子性问题换成了最终一致 + 补偿。以这条链路的性质（已经有对账器重驱动、`INSERT IGNORE` 幂等、方向安全）第三条才是我认为对的演进方向。

**可能的追问**：→ Q6.7；→「对账器多久跑一次、会不会重复建单」（详见笔记 05）；→「那窗口到底多宽」（答：没量过）

**别踩**：
- 不要把推理说成实测。「故障注入没做」这句话一定要自己先说出来，等面试官问出来就变成被戳穿。
- 不要说「LOCAL 事务保证一致」。它保证的是每个物理连接各自的原子性，跨库没有。
- 不要说「XA 太慢所以不能用」——这是没有证据的断言。正确的说法是「代价我没测，但它正好落在热路径上，而且原子性不是这条链路正确性的唯一来源」。
- 不要把后果说成超卖。这里的方向恰恰是少卖，说反了会被认为没想清楚。

### Q6.9 商户后台按商户分页怎么查？扩展吗？  〔常见｜追问链：非分片键的查询怎么办 → 分页深了呢 → 为什么不做异构索引 → 打算怎么做〕

**答**：它**不扩展**，这是我明确不修的一条边界。商户后台按商户 id 分页查订单不带分片键，中间件会向八张物理表各发一次查询再归并——结果正确，但不随分片数扩展，分页越深越贵。我不会说「分片之后商户查询也很快」。

**展开**：
- 为什么必然广播：商户 id 是下单时的快照字段，和用户基因无关，没有任何办法从它算出槽位。索引 `idx(merchant_id, create_time)` 在每张物理表里都建了，所以单片内是走索引的，贵的是「八份结果再归并」这一层，以及深分页时每个节点都要取 offset+size 行。
- 当前代码就是一个普通的分页查询（MyBatis-Plus 的 `selectPage` 加 `merchant_id` 等值条件），页大小上限 100。量级上可接受，因为它是低频的后台查询，不是 C 端热路径。
- 同样是广播的还有两个取单行的查询：按核销码查（店员扫码核销，低频）、按营销发放的券编号查（没有基因）。这两个的量级我接受。
- 另有一类**本来就该广播**的：兜底扫描和券过期扫描这种按状态和时间取一批的查询，它们不带任何可路由列，中间件并行发往全部八个节点再归并正是想要的行为，`ORDER BY ... LIMIT` 的归并语义也是对的，应用层不需要再分片一次。
- **这一项计划里原本有、后来明确砍掉**（2026-09-20 决定）：原计划是做一条 binlog 订阅 → MQ → 搜索引擎的订单读模型，最后没做，因为那是另一个子系统。
- **会怎么做（没做的方案）**：(a) **异构索引 / 读模型**——binlog 订阅（Canal 之类）把订单变更推进 MQ，再投到一份按商户维度组织的索引里，商户后台查那一份。代价是多一条链路要运维、读到的是最终一致（订单刚下、后台还没有），以及要处理乱序和重放。(b) **跨库分页的二次查询法**——不做异构索引也能把深分页做得便宜些：先把 `LIMIT offset, size` 改写成每个节点取 `LIMIT 0, offset+size`，拿到各节点结果后取其中**最小的那个排序值**作为新下界，用这个下界回各节点做第二次查询，再根据每个节点第一次返回的首条位置推算出全局偏移，最后在归并结果里精确切出那一页。它的好处是第二次查询的数据量可控、不需要额外组件；代价是**要发两轮查询**，而且要求排序字段是可比较、可作为范围条件下推的（这里是创建时间）。(c) 最省事的一条：产品上**不提供深分页**，只给「最近 N 天 + 游标翻页」，用创建时间当游标，这样每个节点只取一小段。这三条我都没实现，说的是「如果要修，我会按 (c) → (b) → (a) 的顺序上」。

**可能的追问**：→ Q6.6；→「异构索引和主库不一致怎么办」（答：对账 + 重投，本项目在点赞那条链路上做过类似的发件箱，详见笔记 10）；→「为什么不把商户 id 也做成基因」（答：一个订单只有一个位置，基因位只能给一个维度；给商户做基因就等于放弃用户维度的单片命中，而 C 端查询频率远高于后台）

**别踩**：
- 不要说「加个索引就好了」。索引解决的是单片内的扫描，解决不了「八份结果归并」和深分页。
- 不要说「分片之后所有查询都变快了」。这题就是来挖这句话的。
- 讲二次查询法的时候要注明这是**方案不是实现**，否则面试官顺着问「你们线上跑下来多少毫秒」就穿帮了。

### Q6.10 附属表主键用了 ShardingSphere 的雪花，多实例上出了什么事？  〔坑｜追问链：主键怎么生成 → 为什么不用自增 → 多实例呢 → 怎么发现的 → 为什么不复用已有的发号器〕

**答**：出了主键冲突。全链路冒烟第一次跑就抓到：**1000 单里 24 次** `Duplicate entry ... order_state_log_3.PRIMARY`。原因是这个应用里有**两个雪花**——订单号那个的实例号来自 Redis 租约，两个实例不可能拿到同一个；而给附属表主键用的中间件雪花，它的 workerId **从自己的属性里读、默认 0**，两个实例都是 0，于是同一毫秒铸出同一个 id。

**展开**：
- 为什么不继续用自增：八张物理表的自增会各自从 1 数起，同一个 id 在八张表里各有一行。没有任何查询按它路由，所以换成中间件的雪花。
- 修法：规则文件里放一个占位符，在中间件解析之前填掉，启动时打一行日志。号的来源是显式配置优先，没配就用进程监听的端口对 1024 取模。
- **为什么不复用订单号那个雪花的 Redis 租约**（一个机制显然比两个好）：分片数据源要跑数据库迁移，从 Redis 取号意味着 Redis 一挂就没有任何数据库能迁移。端口对「同一台机器上跑几个实例」这种部署形态够用——一台机器不可能把同一个端口给两个实例。
- **留着的缺口**：跨机部署端口会重复，那时必须显式配置。这写在已知边界里。
- 这一条真正的价值在「怎么发现的」：**一个实例永远看不到它**——所以此前每一次单测、每一次压测都是绿的（当时 473 个单测、94 个集成测试全绿）。它是多实例冒烟第一次跑就抓到的。同一轮冒烟还抓到另一件测试看不见的事：关掉框架自带迁移之后，一个 bean 上的「依赖于迁移 bean」声明指向了一个不再存在的 bean，应用在正常配置下启动失败，而那个 bean 在测试 profile 下根本不创建，唯一会创建它的是真实 jar。
- 结论我会这么收尾：换一个机制就得接管它的全部前提。自增的前提是「一张表」，换成雪花的前提是「每个实例的编号不同」——前提没接管，测试再绿也没用。

**别踩**：
- 不要把两个雪花混成一个。这题的全部张力就在「同一个应用里两个发号机制、只有一个接管了实例号」。
- 不要把 24 次说成「偶发」或四舍五入成别的数。就是 1000 单里 24 次，抄原数。
- 不要说「加了 worker id 就彻底解决了」。跨机端口重复这个缺口还在，主动说出来。
- 不要说「测试覆盖不够所以没发现」。覆盖率不是原因——单实例下这个缺陷在物理上不可能出现，这是测试**形态**的问题不是数量的问题。
