# 压测报告：方法、逐里程碑演进、已知边界

> 这份报告回答三个问题：**怎么测的**、**每个里程碑改了什么、数字怎么动的**、**哪些话不能说**。
> 每个里程碑的完整数据在各自的 `benchmark/v2/m<n>/comparison.md`，这里只保留能连成一条线的部分。
>
> 状态（2026-09-21）：**第 1、4 节已定稿**（它们不依赖任何一次运行的结果）；第 2、3 节的 M8 行
> 等 `scripts/bench.sh m8` 那一晚跑完回填。冒烟数字不进这份报告。

## 1. 方法

### 1.1 开环，不是闭环

V1 的证据是 JMeter 1000 线程 / 5 s ramp-up 得到的 208 req/s。那是**发压速率**不是系统容量：
线程发完一个请求要等响应才发下一个，系统越慢，压力越小，所以永远测不出拐点，也永远不会过载。

V2 全部用 k6 的 `constant-arrival-rate`：请求**按目标速率到达，与系统响应快慢无关**。系统跟不上时
表现为延迟上升和 `dropped_iterations`，这才是拐点的定义。「拐点」在本报告里固定指
**p99 < 100 ms 且丢弃 < 1% 的最高档**。

### 1.2 分核

一台 8C/16T 的机器上同时跑被测系统、依赖和压测客户端，不分核等于三方互相偷 CPU。所有运行按物理核
分配（SMT 兄弟为 N 与 N+8）：

| 角色 | M0–M6（单实例） | M8（多实例） |
| --- | --- | --- |
| 应用 | `0-3,8-11`（4C/8T） | 每实例一对：`0,8` / `1,9` / `2,10` |
| nginx | — | `3,11` |
| 依赖（MySQL / Redis / Broker / ES） | `4-5,12-13` | 同左 |
| k6 | `6-7,14-15` | 同左 |

**M8 的扩展曲线因此是「每实例 2 核」的曲线**，与 M0–M6 的「一个实例 8 核」不可直接比较。给每个
实例独占的核而不是切分一份固定预算，是因为后者只能测出多开进程的开销，测不出扩展性。

### 1.3 预热、用户轮转与配置偏离

- **预热**：每次测量前先以 500 req/s 跑 30 s，不记入 `summary.csv`。
- **用户轮转**：10 万预生成 token，每轮从上一轮停下的位置继续，所以同一个用户不会落进自己的
  每用户限流窗口。每个请求是不同的用户——首秒售罄、其余 99% 是注定失败的请求，这正是秒杀的形态。
- **配置偏离（必须声明）**：`traffic.seckill.ip-limit` 调到 10 万。所有压测请求来自 127.0.0.1，
  默认的每 IP 限流会让 99% 的请求在最外层就 429，测到的将只是限流器。每用户限流保持默认。
  M8 的 nginx **不开 `limit_req`**，同一个理由。
- **支付渠道**：M8 的全链路场景里由压测脚本扮演渠道——按 `PaymentSigner` 的规范签名发
  `/payment/callback`。mock 渠道的支付登记在进程内存里，收银台只在下单的那个实例上有效；真实
  渠道本来就是外部系统，而多实例下必须站得住的端点是回调。

### 1.4 每一列是怎么算出来的

| 列 | 来源 |
| --- | --- |
| `achieved_rps` / `dropped` / `p50..p99` | k6 summary JSON |
| `accepted` | 应答里 `success=true` 的计数（= 真正拿到预占的人数） |
| `app_cpu_cores` | k6 窗口内 `/proc/<pid>/stat` 的 utime+stime 差值 ÷ 墙钟；**多实例时是所有实例之和** |
| `mysql/redis/broker_cpu_cores` | 容器 cgroup `cpuacct.usage` 差值 ÷ 墙钟；Redis 列在 Cluster 下是六个节点之和 |
| `k6_cpu_cores` | 压测容器自己的 cgroup；**它满了，阶梯就到顶了，与被测系统无关** |
| `edge_cpu_cores`（`edge.csv`） | nginx 容器的 cgroup。曲线不线性时先看它 |
| `persist_orders_per_s` | 每秒轮询一次 `COUNT(*)`，取已接收订单从 10% 到 90% 落库之间的斜率 |
| `batch_mean` | 本轮 `local_deals.seckill.consume.batch.size{stage=delivered}` 的 sum 差 ÷ count 差。**接近 1 表示批量消费一次只提交了一单**，无论 `consumeMessageBatchMaxSize` 配了多少 |
| `half_msgs` / `order_msgs` | 事务半消息主题与订单主题的队列最大 offset 之和的差值 |

### 1.5 一次运行能不能被采信

`scripts/bench.sh <场景>` 是无人值守的单一入口，结果写在 `benchmark/v2/m<n>/<时间戳>-<场景>/`：

- `status`：`RUNNING` / `DONE` / `FAILED: <阶段>: <原因>`。**不是 DONE 就不要分析**。
- `manifest.json`：commit、场景参数、分核方式、JVM 参数、机器型号与开跑/收尾时的 loadavg、
  同时在跑的其他容器。
- 启动前 preflight 会拒绝：**工作区有未提交改动**（结果必须对应得上一个 commit）、端口被占、
  磁盘不足、没有 JDK 21、docker 不可用。
- 每个阶段有超时；第一个失败就停下、写明原因，并且无论如何拆掉自己的栈。

M8 那一晚是**一条命令四个场景**（`scripts/bench.sh m8`）：每个场景是独立进程、独立栈、独立结果
目录和独立 status，失败的那个记进 `scenarios.csv`，后面的照跑。

## 3. 瓶颈是怎么一层层移动的

1. **M0**：瓶颈在 Broker。每个请求——包括 99% 注定失败的——都先发一条事务半消息，15k 档 Broker 先
   流控。落库 264 单/s，火焰图里 44.7% 花在 `tb_seckill_voucher` 那一行的行锁上，49.5% 在连接池等待。
2. **M3** 把 99% 的请求挡在最便宜的层：half message 从「等于请求数」变成 0，应用 CPU 在 10k 档
   从 3.04 核降到 0.60 核，拐点从 5k 抬到 20k。**准入侧从此不再是瓶颈**，之后每个里程碑的准入数字
   只用来证明没有回退。
3. **M4** 把落库从「每单一次提交」变成「每批一次提交」，吞吐翻倍，但没到目标。仪表补上后（M6 开头）
   发现真正卡住的是**批大小**而不是提交速率：批大小实测 1.03——消费线程本来就跟得上到达速率，
   队列里永远没有第二条消息在等。
4. **M6 补的消费参数扫描**：拉取间隔是唯一有干净单旋钮证据的一项，`batch_mean` 2.16（0 ms）→
   12.68（50 ms）。换成 `256:4:50ms:256` 后 2001.5 单/s，而且那是场景发压速率的上限不是系统的。
5. **`tb_seckill_voucher` 那一行明确不拆**（ADR 0007 决策 4）：同一轮里同一行被量到约 394 次/s 与
   约 73 次/s 两段，说明那 80 次/s 是双稳态的慢档不是那一行的能力。回归条件写在计划里。
6. **M8**：待回填。要回答的是「加实例加不加吞吐，不加的话卡在共享的哪一层」。

## 4. 已知边界

- **单机测得的是这台机器上的拐点和扩展趋势，不是生产容量。**「万级」的论证方式是：单实例实测值
  × 已验证的水平扩展性 + 各层无共享瓶颈的设计说明。
- M8 的扩展曲线里，Redis Cluster、Broker、两个订单库、nginx 和 k6 本身都是**共享的**。
- 支付是 mock 渠道；不涉及真实资金、对账文件、风控。
- **没做**：多机房、RocketMQ 多副本切换、MySQL 主从切换、日终对账（M6b 砍）、多级缓存（M7 砍）。
- 商户后台按 `merchant_id` 分页是跨 8 张表的广播归并：结果正确，不扩展（ADR 0008）。
- ShardingSphere 附属表主键的 Snowflake workerId 默认取 `server.port % 1024`；跨机部署端口会重复，
  必须显式配 `local-deals.sharding.worker-id`（ADR 0009）。
- traceId：HTTP 全量覆盖；MQ → DB 只接了秒杀链与关单链。
