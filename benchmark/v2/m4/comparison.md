# M4 批量消费复测：同场对照 `v2.0-m3`

> 数字全部来自 [summary.csv](summary.csv) 与 [kill-drill.csv](kill-drill.csv)，由
> `scripts/bench.sh m4` 一次无人值守跑出（结果目录 [`20260920-143242-m4/`](20260920-143242-m4/)，
> `status=DONE`，14:32–15:18，45 分钟）。`7a2ac04` = tag `v2.0-m3` 的 jar（对照组），
> `cc1ab1a` = M4 分支 HEAD，与 `manifest.json` 里记录的 commit 一致。
> 原始 k6 JSON 与订单落库采样在 `20260920-143242-m4/raw/`（gitignore，只在本机）。
> 三次冒烟目录同样保留，**不用于结论**（理由见 ADR 0005 最后一节）。

## 1. 方法

| 项 | 值 |
| --- | --- |
| 分核 | 应用 `0-3,8-11`；MySQL/Redis/RocketMQ/ES `4-5,12-13`；k6 `6-7,14-15`——与 M0–M3 相同 |
| 运行时 | 应用 jar，Java 21，`-Xms2g -Xmx2g`；隔离栈 `ld-m3bench`，端口 38083 |
| 阶梯 | 10k / 20k req/s × 30 s，库存 1000。M4 不动准入端，阶梯只用来证明没有回退 |
| 落库 | 每轮一张新券、库存 2 万，以 2000 req/s 全部接收，测「最后一个请求返回后还要多久落完」与落库速率；对照组与 HEAD **交替 3 轮** |
| 参数扫描 | HEAD 再跑 5 轮落库，逐轮改 `consume.batch-size:thread-count`（Hikari 池 = 线程数 + 8）。`1:16` 即本版本**关掉批量** |
| 演练 | 库存 2 万、2000 req/s，第 6 秒 `kill -9` 应用一次；再来一次「先杀 Broker 再杀应用」 |
| 机器负载 | 起始 loadavg 4.55，结束 5.20；宿主机上还跑着其它项目的容器（见 manifest.json） |

落库速率有两个口径，本文都给：`persist_orders_per_s` 是脚本口径（第 10% 单到第 90% 单的斜率，
写在 summary.csv 里），`平均` 是 2 万单从第一单到最后一单的整体平均。结论用后者交叉验证前者。

## 2. 落库吞吐（2 万单，交替 3 轮）

| 轮次 | 对照组 `v2.0-m3`：追平 s / 斜率 / 平均 | M4 `cc1ab1a`：追平 s / 斜率 / 平均 |
| --- | --- | --- |
| 1 | 114.6 / 137.6 / 158 | **11.6 / 945.2 / 837** |
| 2 | 105.6 / 156.3 / 170 | 47.7 / 319.1 / 330 |
| 3 | 74.2 / 247.4 / 230 | 53.2 / 294.1 / 302 |
| 中位 | **105.6 / 156.3 / 170** | **47.7 / 319.1 / 330** |

- **中位提升约 2 倍（156 → 319 单/s），最好一轮 6 倍（945 单/s），「负载结束后还要排多久」从
  105 s 降到 12–53 s。** 计划里 M4 的待验证目标是 ≥ 3000 单/s，**没有达到**。
- 1000 单的阶梯档里差距更干净（那里没有 2 万单的长尾）：10k 档 172.9 → **703.1**，
  20k 档 144.8 → **691.5** 单/s，约 4 倍。
- M4 的三轮自身差了 2.9 倍（945 / 319 / 294），原因见第 4 节——不是噪声，是批次填充度。

### 2.1 提升确实来自批量，不是 M4 的其它改动

参数扫描里的 `1:16` 是**同一个 HEAD 把批量关掉**（每批 1 条），其余改动（Redis 认领取代
Redisson 锁、通知不再每单查库、异步排关单）全部保留：

| 配置 | 追平 s | 斜率 单/s | 平均 单/s | 采样 p50 单/s |
| --- | ---: | ---: | ---: | ---: |
| 对照组 `v2.0-m3`（中位） | 105.6 | 156.3 | 170 | 84 |
| `1:16`（HEAD，关批量） | 128.0 | 168.7 | 142 | 81 |
| `32:16` | **10.7** | **1056.2** | **904** | 488 |
| `64:16`（默认） | 10.8 | 975.3 | 860 | 499 |
| `64:32` | 46.1 | 438.4 | 337 | 87 |
| `256:32` | 50.6 | 309.3 | 319 | 92 |

`1:16` 与对照组落在同一档（142 vs 170 单/s，采样 p50 都是 81–84 单/s）。**去掉消费锁、去掉
每单补查 merchantId、异步排关单，这三项加起来在落库吞吐上测不出差别**；M0 火焰图里那 25% 的
通知补查省下的是 CPU，不是这条路径的等待。真正的提速只来自「每批每券一次 `UPDATE`」。

### 2.2 线程数 16 好过 32

扫描里两个 32 线程的配置（`64:32`、`256:32`）都掉回 320–440 单/s，而 16 线程的两个是 860–900。
批大小从 32 加到 64 没有区别，加到 256 反而更差。**多开消费线程只是让更多线程去抢同一行库存的
行锁**；批大小超过一次拉取能攒到的量也没有意义。默认 `64:16` 是这次扫描里的合理选择。

## 3. 准入端没有回退（阶梯，库存 1000 × 30 s）

| 目标 req/s | 实际（M3 → M4） | 丢弃率 | p99 ms | 应用 CPU 核 | k6 CPU 核 | half message | 普通消息 |
| ---: | --- | --- | --- | --- | --- | ---: | ---: |
| 10 000 | 9943.0 → 9906.9 | 0.56% → 0.92% | 86.4 → 104.2 | 0.71 → 0.65 | 1.46 → 1.44 | 0 → 0 | 1000 → 1000 |
| 20 000 | 19726.4 → 19764.7 | 1.4% → 1.2% | 86.8 → 87.3 | 1.01 → 0.96 | 2.70 → 2.70 | 0 → 0 | 1000 → 1000 |

两档吞吐、CPU 都相同；10k 档 p99 86 → 104 ms 是同场单次采样的抖动（20k 档两组一致，
应用 CPU 反而更低）。**每档 `accepted = stock = 1000`，无超卖**，half message 恒为 0、普通消息
恒等于成功数——M3 的结论在 M4 上保持。

## 4. 瓶颈：提交速率被钉在约 80 次/s，吞吐 = 80 × 批大小

把每轮的落库采样拆成每秒速率，所有 11 轮只出现三种状态：

| 状态 | 速率 | 出现在 |
| --- | ---: | --- |
| A | 75–110 单/s | 对照组的大部分时间、`1:16` 的 94%、M4 慢轮的 60% |
| B | 400–500 单/s | 三个版本都有，成段出现 |
| C | 2000–9200 单/s | **只有批量版本有**，多在负载停止后的收尾段 |

- `1:16`（每批 1 条）整轮稳定在 **81 单/s**，对照组的 p50 是 **84 单/s**。也就是说
  **一次「插入 + 扣库存」提交的速率上限约 80 次/s**（约 12 ms 一次），这就是 M0 以来火焰图里
  同一行 `UPDATE tb_seckill_voucher SET stock = stock - 1` 的行锁 + 提交代价。
- 批量版本的 C 段峰值 2257 / 2388 / 4718 / 6315 / 9198 单/s ≈ 80 × 30–110。**批量并没有让提交更快，
  它让一次提交带走整批订单**：吞吐 ≈ 80 × 实际批大小。
- 所以三轮差 2.9 倍的原因是**实际批大小不同**，不是机器噪声：快轮（945、1056、975）整轮都在
  B/C 段，慢轮（319、294、438、309）有 60% 的时间掉回 A 段——批里只有一两条。

**这一条目前是推断，不是实测。** 缺的证据是「每批实际多少条」，而它这次没被采下来：
`LocalDealsMetrics` 没有批大小的分布指标，`scripts/bench.sh` 也没有把每一轮的 `app.log` 和
actuator 指标归档（`app.log` 每次 `app-start` 覆盖，最后只剩演练那一次）。为什么在负载期间
批攒不满，是 RocketMQ 的每队列流控（`pullThresholdForQueue`、`consumeConcurrentlyMaxSpan`）
还是消息到达的节奏，现在无法区分。

要突破 3000 单/s，两条路是叠加的：把批填满（80 × 40 = 3200），或者把「80 次/s」这个上限本身抬
上去——后者正是 **M5 的库存分桶**：K 个桶就是 K 行，每行各自约 80 次/s。ADR 0005 里已经写明
「同一张券的并发批次仍然争同一行，分桶留给 M5」，这次的数字把它量化了。

## 5. 故障演练（库存 2 万，2000 req/s，第 6 秒下手）

| 演练 | 重投 | kill 时已预占 | 预占 | 订单 | Redis 库存 | DB 库存 | 残留 PROCESSING | 收敛 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `kill -9` 应用 | 20 | 11 163 | 11 163 | 11 163 | 8 837 | 8 837 | 0 | **44.7 s**（M3：102.8 / 102.7 s） |
| 先杀 Broker 再杀应用 | 4 448 | 11 679 | 11 679 | 11 679 | 8 321 | 8 321 | 0 | **572.1 s**（M3：574.2 s） |

- 两次演练都**三方一致**：预占数 = 订单数，Redis 剩余库存 = DB 剩余库存，无残留 `PROCESSING`。
  M4 把消费锁换成 Redis 内认领（claimOwner + 租约）之后，「消费者落库中 + 对账器到期」没有造成
  任何误补偿——这正是 ADR 0005 §4 要证明的。
- `kill -9` 收敛 102.8 → **44.7 s**：崩溃时积压的消息重投后走批量路径，落得更快。
- 先杀 Broker 的收敛 **几乎没变**（574.2 → 572.1 s），符合 ADR 0005 的预告：那 4448 条无消息预占
  由对账器重驱动，而**对账器本身没有批量化**，节奏仍是 `fixed-delay` × `batch-size`。
- 这次 `kill -9` 有 20 条重投（M3 是 0）：崩溃点恰好落在「预占成功、消息还没发」的窗口里 20 次，
  属于方案 B 的正常路径，20 条全部被对账器补回。

## 6. 复现

```bash
scripts/bench.sh m4          # 完整场景，约 45 分钟，无人值守

```
