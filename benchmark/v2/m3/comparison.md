## 1. 方法

| 项 | 值 |
| --- | --- |
| 分核 | 应用 `0-3,8-11`（4C/8T）；MySQL/Redis/RocketMQ/ES `4-5,12-13`；k6 `6-7,14-15`（2C/4T）——与 M0/M1/M2 相同 |
| 运行时 | 应用 jar，Java 21，`-Xms2g -Xmx2g`；MySQL 8.0、Redis 6.2、RocketMQ 5.3.2；隔离栈 `ld-m3bench`，端口 38083 |
| 压测模型 | k6 2.2.0 `constant-arrival-rate`（开环），每档一张新券、库存 1000、30 s；10 万预生成用户轮转，每个请求都是不同用户 |
| 顺序 | 同一场次内先跑对照组再跑 HEAD；落库对比交替 3 轮 |
| 配置偏离 | 两组都把 `ip-limit` 放到 100000（请求全部来自 127.0.0.1）；对照组另放开 `activity-limit`（M3 已无此配置，改为 L2 本地令牌桶）；两组 `pay-timeout=24h`，压测期间不关单。M3 组 k6 用同一密钥自签秒杀令牌，服务端照常验签 |
| 机器负载 | 起始 loadavg 4.81，结束 5.50；宿主机上还跑着其它项目的容器（见 manifest.json） |

按 M0 的拐点口径（最后一档 p99 < 100 ms 且丢弃 < 1%）：

- **拐点 5 000 → 20 000 req/s（4 倍）。** 对照组这一场在 10k 档就已经 p99 128 ms（M0 当天是
  63 ms，机器更闲），M3 组到 20k 档仍是 p99 83 ms、丢弃 0.75%。以 M0 原始基线的 1 万 req/s 计，
  也是 2 倍。M3 的待验证目标「单实例准入 ≥ 1 万 req/s」**达成**。
- **天花板 13.2k → ≥ 26.2k req/s。** 对照组在 15k 档见顶（13.2k），继续加压反而掉到 12.1–12.5k；
  M3 组一路单调上升到 30k 档的 26.2k，**还没见顶**。
- **每档 1000 单全部被接收，两组都无超卖**（`accepted = stock`，`http_fail_rate` ≤ 0.08%，
  失败全是 L2 的 429）。
- 429 只出现在 10k / 15k / 20k 档（23 / 163 / 490 个），25k、30k 档为 0：速率越高售罄越快，
  L2「剩余库存 × 系数」的放行窗口越短，其后的请求由 L1 本地售罄标记直接挡下。

### 2.1 D1 / D2 的验收

- **half message：= 请求数 → 0。** 对照组每档的 `RMQ_SYS_TRANS_HALF_TOPIC` 增量等于请求数
  （30k 档 37.7 万条），M3 组恒为 0；`seckill-order-topic` 恒为 1000 = 成功数。计划要求的
 「half message 从=请求数降到=成功数」，因为选了方案 B（普通发送 + 预占重投），实际是
  「half 消失、普通消息=成功数」。
- **Broker CPU 0.85–0.94 → 0.07–0.09 核**（约 1/11），**Redis 0.38–0.42 → 0.01–0.02 核**（约 1/25）。
  失败请求不再碰 Redis（L1）、不再碰 Broker（只有成功者发消息），D1、D2 关闭。
- **应用 CPU 在更高吞吐下反而更省**：30k 档 3.42 → 1.19 核，而吞吐是它的 2.1 倍；
  折算单请求成本约为原来的 1/6。

### 2.2 现在的瓶颈在压测端，不在应用

新增的 `k6_cpu_cores` 列给出答案：30k 档 k6 用 **3.57 核**，而它只被分到 2C/4T，
已经贴着 4 线程的上限；同档应用只用 1.19 核（分到 8 线程）。对照组同档 k6 只要 1.81 核——
因为应用回得慢，k6 大量迭代根本没发出去。所以 M3 组 25k / 30k 档的 6.4% / 12.7% 丢弃，
主要是压测机发不出请求，不是应用拒绝：应用侧 CPU、Redis、Broker 三项都还有大量余量。
**在这台机器上，单实例准入的真实天花板没有被测到。** 要继续往上测需要把 k6 挪到另一台机器
或多给核（M8 全链路压测时处理）。

本次跑的是无人值守场景，脚本不采火焰图（`scripts/bench.sh profile` 是单独的手动子命令），
所以准入端没有本场的火焰图。上一会话的探索性采样与这里的 CPU 列一致：漏斗之后准入端的
热点从三次 Redis RTT + 事务消息，变成 nginx→Tomcat 的网络栈本身。

## 3. 消费落库（2 万单以 2000 req/s 放入，交替 3 轮）

| 轮次 | 对照组 追平 s / 单每秒 | M3 追平 s / 单每秒 |
| --- | --- | --- |
| 1 | 63.2 / 267.2 | 129.8 / 144.8 |
| 2 | 130.1 / 124.2 | 99.6 / 196.2 |
| 3 | 90.5 / 217.5 | 104.4 / 154.9 |
| 中位数 | **90.5 / 217.5** | **104.4 / 154.9** |

两组区间大幅重叠（对照 124–267 单/s，M3 145–196 单/s），与 M0（123–478）、M2（139–427）一样
抖动。**消费侧测不出差别，也不该有差别**：M3 只改准入端与消息的发法，消费逻辑没动。
落库仍是 150–220 单/s 这一档，瓶颈仍是 M0/M2 火焰图里的同一行库存 `UPDATE` 行锁 + 连接池等待
（44% / 24%），**归 M4 处理**。

一个可见的副作用：M3 第 1 轮 `seckill-order-topic` 收到 20 023 条消息而不是 20 000——
23 条是对账器对「预占存在、订单还没落库」的重投（重复无害，消费者看到已有订单就确认）。
落库慢时重投会提前触发，属于 ADR 0004「对账器重投速度是瓶颈」那条已知代价。

## 4. 故障演练（库存 2 万，2000 req/s，第 6 秒下手）

| 演练 | 重投 | kill 时已预占 | 预占 | 订单 | Redis 库存 | DB 库存 | 残留 PROCESSING | 收敛 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `kill -9` 应用 #1 | 0 | 11 290 | 11 290 | 11 290 | 8 710 | 8 710 | 0 | 102.8 s |
| `kill -9` 应用 #2 | 0 | 11 173 | 11 173 | 11 173 | 8 827 | 8 827 | 0 | 102.7 s |
| 先杀 Broker 再杀应用 | 4 249 | 11 459 | 11 459 | 11 459 | 8 541 | 8 541 | 0 | 574.2 s |

- 三次演练都**三方一致**：预占数 = 订单数，Redis 剩余库存 = DB 剩余库存，没有残留 `PROCESSING`。
  方案 B 要求的「Lua 成功后进程立刻被 kill，订单最终收敛」得到证明。
- 自然 `kill -9` 打不中「Lua 成功、消息没发出去」那个亚毫秒窗口（重投 0），所以必须先杀 Broker
  才能造出真正无消息的预占：**4 249 个无消息预占全部被重投并落库**。
- 代价也量化了：收敛 574 s。对账器默认 stale-after 2 分钟、每 10 秒 100 单，这个速度是收敛时间的
  上限来源，不影响正确性。M4 批量化后重投速度一并提高。
