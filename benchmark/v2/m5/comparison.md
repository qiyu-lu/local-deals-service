## 1. 方法

| 项 | 值 |
| --- | --- |
| 分核 | 应用 `0-3,8-11`；MySQL/Redis/RocketMQ/ES `4-5,12-13`；k6 `6-7,14-15`——与 M0–M4 相同 |
| 运行时 | 应用 jar，Java 21，`-Xms2g -Xmx2g`；隔离栈 `ld-m3bench`，端口 38083 |
| A/B 的不对称 | 对照组 `v2.0-m4` 的 key **没有 hash tag，在 Cluster 上跑不起来**，所以对照组跑单节点、当前版本跑 3 主 3 从。这是这次 A/B 唯一的结构性差异，读数字时必须记住 |
| 阶梯 | 10k / 20k req/s × 30 s，库存 1000。M5 不动准入逻辑，阶梯只用来证明没有回退 |

| 演练 | `kill -9` 应用一次；**`docker kill` 一个 Redis master 两次**（库存 2 万、2000 req/s、第 6 秒下手） |

## 2. 准入端：没有回退，尾延迟略升

| 档位 | 对照组 `v2.0-m4`（单节点） | M5 `f5dfbae`（16 桶 + Cluster） |
| --- | --- | --- |
| 10k req/s | 9944.5 达成 / p99 **76.6** ms / 应用 0.66 核 / Redis 0.01 核 | 9956.3 达成 / p99 **121.4** ms / 应用 0.69 核 / Redis 0.02 核 |
| 20k req/s | 19661.5 达成 / p99 **96.0** ms / 应用 0.98 核 / Redis 0.01 核 | 19333.3 达成 / p99 **124.0** ms / 应用 1.05 核 / Redis 0.03 核 |

- **达成速率基本持平**（10k 档持平，20k 档 −1.7%），`accepted = stock = 1000` 两档两版本都成立，
  **无超卖**；`half_msgs` 恒为 0、`order_msgs = 1000`，M3/M4 的性质在 Cluster 上保持。
- 代价是尾延迟：p99 上升 45 ms（10k）/ 28 ms（20k）。方向可以解释——准入仍然是一个 RTT、一个
  slot，但客户端多了一层 slot 路由，且 Cluster 的六个节点共享同两个核（`4-5,12-13`），
  而对照组只有一个 Redis 进程独占。**这一项不是干净对照**，见第 1 节。
- 20k 档 M5 的 `http_429` 从 21 涨到 1480。L2 令牌桶按券的下限在实现里除以 K 分摊
  （ADR 0006 决策 5），16 个桶各自限流，合起来比单桶更早开始丢——这是设计里写明的行为，
  不是回退：被 429 的请求本来就抢不到 1000 件库存里的任何一件。

## 4. 为什么量不出来：A/B 两个状态，和桶数无关

把九轮落库采样拆成每秒速率，M4 复测第 4 节描述的三个状态**原样复现**，而且每轮的整轮平均
几乎完全由「在 A 状态待了多久」决定：

| 轮次（版本:K） | A 段 75–150 单/s | B 段 400–1200 单/s | C 段 >1200 单/s | 整轮平均 |
| --- | ---: | ---: | ---: | ---: |
| k8 `f5dfbae` | 0% | 91% | 9% | 860 |
| 基线 r3 | 4% | 87% | 8% | 795 |
| M5 r1 | 46% | 42% | 12% | 447 |
| k64 `f5dfbae` | 59% | 33% | 7% | 349 |
| 基线 r1 | 72% | 23% | 4% | 410 |
| 基线 r2 | 87% | 6% | 7% | 225 |
| M5 r2 | 84% | 12% | 4% | 258 |
| M5 r3 | 90% | 7% | 2% | 232 |
| k1 `f5dfbae` | 94% | 1% | 5% | 190 |

- A% 与整轮平均单调相关，**基线和 M5 混在同一条曲线上**：两个版本各自都出现过 A=4% 的快轮和
  A=90% 的慢轮。桶数同样不相关——K=1 最慢（A=94%），K=8 最快（A=0%），K=64 居中。
- 状态在一轮之内会翻转（例如 M5 r1 前 18 s 稳在 450 单/s，随后 19 s 掉到 90 单/s，
  负载停止后升到 1900 单/s）。**所以它不是机器噪声，是消费端的一个双稳态**，
  而这次 9 轮里它落在哪一侧像抛硬币。

### 4.1 为什么 M5 不可能抬高那个上限——M4 复测的预期是错的

M4 复测第 4 节写「抬高 80 次/s 这个上限正是 M5 的库存分桶」，计划 5 节的 M4 偏差段也照抄了这句。
**这句话在 M5 的实现下不成立**：那 80 次/s 是 MySQL 里 `UPDATE tb_seckill_voucher SET stock = stock - n`
**同一行**的行锁 + 提交代价，而 M5 分的是 **Redis 的 key**。`tb_seckill_voucher` 至今仍是一张券一行
（`SeckillVoucherMapper`、`SeckillOrderBatchPersister`），ADR 0006 决策 4 自己也写了
「落库仍然按券分组……桶不改变 DB 分组」——只是同一篇 ADR 的「背景」还留着「把那一行变成 K 行」的说法。
**本次数据与「M5 不碰 DB 热点行」完全一致：落库没有提升是预期结果，不是 M5 的缺陷。**

### 4.2 双稳态的成因仍然没有实测证据

缺的仍然是 M4 就列出、**M5 没有补上**的两件事：

1. `LocalDealsMetrics` 里没有批大小的分布指标，也没有「退化为逐条重放」的计数——
   `SeckillOrderBatchConsumer` 里一个指标都没有。所以「A 段 = 批里只有一两条」依旧是推断。
2. `scripts/bench.sh` 仍然没有按阶段归档 `app.log` 和一次 actuator 快照（`app.log` 每次
   `app-start` 被覆盖），所以事后也查不回去。

在补上这两件事之前，**任何关于落库吞吐的 A/B 结论都不可信**，包括本节的表。

## 5. Redis master 宕机演练：零超卖、零丢失预占，代价是 1.26 万个 503

库存 2 万、2000 req/s、第 6 秒 `docker kill` 一个**当前 master**（脚本按角色选，不按名字）：

| 轮 | 被杀节点 | 杀时已预占 / Redis 余量 | 集群察觉 | 恢复可写 | accepted | 订单 | 预占 | Redis 库存 | DB 库存 | 残留 PROCESSING | **丢失预占** | **库存差** | **超卖** | 收敛 |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | `redis-c3` | 11386 / 8546 | 5.2 s | 7.3 s | 15897 | 15897 | 15897 | 4103 | 4103 | 0 | **0** | **0** | **0** | 40.2 s |
| 2 | `redis-c4` | 11228 / 8692 | 7.8 s | 9.4 s | 15887 | 15887 | 15887 | 4113 | 4113 | 0 | **0** | **0** | **0** | 31.4 s |

两轮都满足：`accepted = 订单数 = 预占数`、`Redis 库存 = DB 库存`、`accepted + 余量 = 20000`、
无残留 PROCESSING、无超卖。故障转移 5–9 秒，全链路 31–40 秒收敛。

**用户可见的代价**：轮 1 有 12618 个 `HTTP 503`（占全部请求 42%，841/s），轮 2 有 12837 个。
库存明明还有，买家却被拒——**这就是「Redis 是可丢的性能层」的真实价格**，它不是零。

### 5.1 诚实说明：这次演练**没有**复现计划预期的「超放」

计划 M5 写的预期是「异步复制会丢最近的预占与扣减 → 新主库存变多 → Redis 层超放，由 MySQL
`stock >= n` 兜底」。实测 **RPO = 0 条预占，库存差 = 0**，兜底那一步根本没被触发。原因不是运气：

- 丢失窗口只有「写在旧 master 上成功、但还没复制到 replica」的那几毫秒。故障转移期间
  （5–9 秒）那些 slot 根本不可写，请求直接 503——**被拒绝的买家不算丢失**，他们从未被告知抢到。
- 该 master 上的写入速率约 2000/3 ≈ 667 次/s，复制延迟远小于 1 ms，所以期望丢失量本来就是 0–1 条。

所以本次能证明的是「**主从切换的正确性代价为零，可用性代价是 7 秒 × 42% 请求失败**」，
**不能**证明「MySQL 条件更新作为最后防线拦住了超放」——那条防线这次没上场。要把它逼出来，
需要在杀之前先 `CLIENT PAUSE` / 断开复制链路制造一个几秒的复制空窗，或者把写速率提高一到两个数量级。
这是 M5 留给 M8 的一件事。

## 6. 应用 `kill -9` 演练（回归，非 M5 新增）

| 版本 | 重投 | 杀时已预占 | 预占 | 订单 | Redis 库存 | DB 库存 | 残留 PROCESSING | 收敛 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `f5dfbae` | 0 | 11005 | 11005 | 11005 | 8995 | 8995 | 0 | 56.8 s |

预占 = 订单、Redis 库存 = DB 库存、无残留。收敛 44.7 s（M4）→ 56.8 s：慢了约 12 s，方向与
「对账器的到期索引从 1 个 ZSET 变成 16 个、每轮按桶均分取份额」（ADR 0006 决策 7）一致，
但**单轮数据不足以称之为回退**。
